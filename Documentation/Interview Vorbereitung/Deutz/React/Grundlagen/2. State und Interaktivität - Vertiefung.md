> [!important] Das Snapshot-Modell in drei Sätzen
> **1.** Ein Render ist eine Momentaufnahme: Innerhalb eines Renders ist `count` eine Konstante, die sich nicht mehr ändert.

## 1. Events

### 1.1 Funktion übergeben, nicht aufrufen

Deine Antwort war vollständig richtig, inklusive der Folge.

```jsx
<button onClick={handleClick}>   // ✅ React bekommt die Funktion und ruft sie beim Klick auf
<button onClick={handleClick()}> // ❌ die Funktion läuft SOFORT beim Rendern
```

Im zweiten Fall wird `handleClick` während des Renderns ausgeführt, und ihr **Rückgabewert** landet als `onClick`-Prop — meist `undefined`. Das hat zwei Symptome zugleich: Es passiert etwas beim Laden, was nicht passieren sollte, und beim Klick passiert nichts.

Der Bezug nach hinten: Das ist zugleich ein Verstoß gegen die Reinheit aus [[1. React-Grundlagen - Vertiefung#6. Reinheit von Komponenten|Block 1, Abschnitt 6]] — ein Seiteneffekt während des Renderns. Ruft die Funktion einen State-Setter auf, entsteht eine Endlosschleife: Render → Setter → Render → …

**Merksatz:** `onClick` will eine Funktion, keinen Funktionsaufruf. Ein `()` hinter dem Namen macht aus dem einen das andere.

### 1.2 Argumente an einen Handler übergeben

> [!warning] Frage verfehlt — hier wurde nach dem *Wie* gefragt, nicht nach dem *Warum*
> Du hast geantwortet: „Weil die Sache nur als Reaktion auf ein Event ausgeführt werden soll." Das ist die Begründung aus 1.1, nicht die Antwort auf 1.2. Dazu unten mehr im [[#Das Muster hinter den Fehlern|Muster]] — es ist in diesem Block dreimal passiert.

Die Antwort: **Man wickelt den Aufruf in eine Arrow Function.**

```jsx
<button onClick={() => loesche(produkt.id)}>Löschen</button>
```

Was hier passiert: `() => loesche(produkt.id)` ist selbst eine Funktion — sie wird übergeben, nicht ausgeführt. Erst beim Klick ruft React sie auf, und *sie* ruft dann `loesche` mit dem Argument auf. Die Arrow Function ist die Verpackung, die das sofortige Ausführen verhindert.

Das ist unmittelbar die Anwendung von [[0. JavaScript für React - Vertiefung#1.2 Implizites Return — und die Falle darin|Block 0, 1.2]]: Eine Arrow Function ist ein *Wert*, ein Aufruf ist eine *Ausführung*.

Die Alternative, die man seltener sieht:

```jsx
<button onClick={loesche.bind(null, produkt.id)}>   // funktioniert, ist aber altmodisch
```

Für dein Projekt ist das die Zeile in [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 8 — Auswahl und Detailbereich: State nach oben ziehen|Schritt 8]]: `onClick={() => onAuswahl(produkt.id)}`.

> [!note] Kein Performance-Problem
> Eine häufige Sorge: „Aber dann wird bei jedem Render eine neue Funktion erzeugt!" Stimmt — und ist praktisch immer irrelevant. Funktionen zu erzeugen ist in JavaScript billig. Relevant wird es erst in Verbindung mit `memo`, und dafür gibt es `useCallback`. Das als Vokabel zu kennen ist gut; es vorsorglich einzusetzen ist der klassische Anfängerfehler in die andere Richtung.

### 1.3 Ereignisse nach oben melden

Deine Antwort war richtig: Die Eltern reichen einen Handler hinein, das Kind ruft ihn auf. Und *inverse data flow* ist der passende Begriff — den hattest du schon in [[1. React-Grundlagen - Vertiefung#8.1 Die fünf Schritte|Block 1]] korrekt genannt.

Der Name, der dir fehlte: In React heißen diese Props **Callback-Props** oder **Event-Handler-Props**. Konvention ist die Vorsilbe `on…` für das Prop und `handle…` für die Funktion dahinter:

```jsx
function Zeile({ produkt, onAuswahl }) {          // Prop:    onAuswahl
  return <li onClick={() => onAuswahl(produkt.id)}>{produkt.name}</li>
}

function Liste() {
  function handleAuswahl(id) { setAusgewaehlt(id) }   // Funktion: handleAuswahl
  return <Zeile produkt={p} onAuswahl={handleAuswahl} />
}
```

**Der Vergleich mit Dependency Injection ist gut** — behalte ihn. In beiden Fällen bekommt das Innere seine Fähigkeit von außen gereicht, statt sie selbst zu beschaffen, und wird dadurch austauschbar und testbar. `Zeile` weiß nicht, *was* bei einer Auswahl passiert; es meldet nur, dass eine stattfand. Genau dieselbe Umkehrung wie bei den `Depends`-Abhängigkeiten in deiner FastAPI aus [[Documentation/Traineeship/Grundlagen der Software Entwicklung/1.5 REST APIs & Layered Architecture/1.5 REST APIs & Layered Architecture - Vertiefung|Kapitel 1.5]].

Im Gespräch ist dieser Brückenschlag wertvoll — er zeigt, dass du ein bekanntes Muster wiedererkennst statt React-Vokabeln zu wiederholen.

## 2. Was State ist und warum eine Variable nicht reicht

### 2.1 Die zwei Gründe

Du hast **einen** von zwei genannt — und den wichtigeren. Beide:

**Grund 1: Lokale Variablen überleben den Render nicht.** Die Komponentenfunktion läuft bei jedem Render komplett neu durch. `let count = 0` wird dabei jedes Mal neu auf 0 gesetzt. Es gibt kein Gedächtnis. Das hattest du.

**Grund 2: Eine Änderung löst keinen Render aus.** Selbst wenn die Variable den Render überlebte, würde React nichts davon merken. React weiß nichts von deinen lokalen Variablen — es gibt keinen Mechanismus, der bei `count++` ein Neurendern anstößt.

```jsx
function Zaehler() {
  let count = 0                             // ❌ beide Probleme
  return <button onClick={() => { count++; console.log(count) }}>{count}</button>
}
```

Die Konsole zeigt 1, 2, 3 — der Bildschirm bleibt bei 0. Das ist die anschaulichste Demonstration: Die Variable *funktioniert*, sie erreicht nur die Oberfläche nicht.

`useState` löst genau diese beiden Probleme: **Es merkt sich den Wert zwischen den Renders, und es sagt React Bescheid, wenn er sich ändert.** Das ist die Ein-Satz-Definition von State, die im Gespräch trägt.

Deine Formulierung „sie funktionieren schon, aber nicht um Dinge zu persistieren" war übrigens genau richtig gedacht — der Instinkt, dass die Variable nicht *kaputt* ist, sondern nur nicht das leistet, was hier gebraucht wird, ist der richtige.

### 2.2 Was `useState` zurückgibt

Richtig beantwortet. Zur Vollständigkeit, weil das in Block 0 noch unklar war: Es ist **ein Array mit genau zwei Elementen** — der aktuelle Wert und die Setter-Funktion. Die Array-Form erlaubt freie Namensvergabe beim Destructuring ([[0. JavaScript für React - Vertiefung#2.1 Array-Destructuring — und was useState wirklich zurückgibt|Block 0, 2.1]]).

Drei Feinheiten, die als Nachfrage kommen können:

- **Der Anfangswert zählt nur beim ersten Render.** In allen weiteren Renders wird `useState(0)` zwar erneut aufgerufen, aber die `0` ignoriert — React gibt den gespeicherten Wert zurück. Ein häufiger Irrtum ist, dass ein geänderter Anfangswert den State zurücksetzt. Tut er nicht.
- **Die Setter-Funktion ist stabil.** `setCount` ist bei jedem Render dieselbe Funktion. Deshalb darf sie im Dependency-Array eines Effects weggelassen werden (Block 3).
- **Teurer Anfangswert gehört in eine Funktion.**
  ```jsx
  useState(teureBerechnung())      // läuft bei JEDEM Render, Ergebnis wird verworfen
  useState(() => teureBerechnung())  // läuft nur beim ersten Render
  ```
  Das heißt *lazy initial state*. Kein Muss für dein Projekt, aber eine gute Antwort auf „kennen Sie Fallstricke bei `useState`?".

### 2.3 State ist pro Instanz isoliert

Richtig — und deine Klammerbemerkung war die beste Einzelantwort dieses Blocks:

> „Nein, der State ist unabhängig (außer es handelt sich um mutable Dinge i.e. objects und sie werden falsch behandelt)"

Das ist exakt der Sonderfall, und die wenigsten sehen ihn:

```jsx
const start = { treffer: 0 }         // EIN Objekt

function Zaehler() {
  const [daten, setDaten] = useState(start)   // beide Instanzen bekommen dieselbe Referenz
  …
}
<Zaehler /> <Zaehler />
```

Die State-*Slots* sind getrennt — aber beide zeigen auf **dasselbe Objekt**. Solange man korrekt unveränderlich arbeitet (`setDaten({...daten, treffer: 1})`), fällt das nie auf, weil jedes Update eine neue Kopie erzeugt. Mutiert man dagegen (`daten.treffer++`), ändern sich beide Instanzen — und das sieht nach einem React-Bug aus, ist aber Referenzsemantik aus [[0. JavaScript für React - Vertiefung#4.1 Was bei einer Zuweisung wirklich kopiert wird|Block 0, 4.1]].

Der Regelfall bleibt: **Jede Verwendung einer Komponente hat ihren eigenen, vollständig isolierten State.** `<Zaehler />` zweimal geschrieben heißt zwei unabhängige Zähler. State gehört nicht der Komponente (der Funktion), sondern der **Stelle im Baum**, an der sie gerendert wird.

Das ist auch die Korrektur zu deiner Block-1-Annahme „eine Komponente hat keinen inneren Zustand" — sie hat einen, und zwar pro Instanz.

### 2.4 Wo der State liegt

„Außerhalb, irgendwo von React verwaltet" — richtig.

Präzise: React führt für jede Komponenteninstanz einen internen Datensatz (den **Fiber-Knoten**, siehe [[1. React-Grundlagen - Vertiefung#7.3 Virtual DOM und Reconciliation|Block 1, 7.3]]). Darin liegt eine **Liste** der State-Werte dieser Instanz. Beim Rendern arbeitet React diese Liste der Reihe nach ab: Der erste `useState`-Aufruf bekommt den ersten Eintrag, der zweite den zweiten, und so weiter.

Zwei Dinge folgen daraus, und beide sind Interviewstoff:

1. **Die Zuordnung läuft über die Aufrufreihenfolge, nicht über Namen.** React weiß nicht, dass dein erster State „count" heißt — es zählt mit. Deshalb dürfen Hooks nicht in Bedingungen stehen: Eine ausgelassene Zeile verschiebt die gesamte Liste. Das ist die Antwort auf „warum gibt es die Hook-Regeln?" (Block 3, Abschnitt 5) — und du hast die Grundlage dafür schon hier.
2. **State hängt an der Position im Baum.** Rendert React an derselben Stelle denselben Komponententyp, bleibt der State. Ändert sich Typ oder `key`, wird die Instanz weggeworfen und der State mit ihr — der Bogen zurück zu [[1. React-Grundlagen - Vertiefung#5.2 Wozu key dient — und an wen es sich richtet|Block 1, 5.2]].

> - [[Lückenschluss (Pricing-Dashboard)#Das Denkmodell — wo React den State aufbewahrt|Denkmodell]]: Speicherplätze nach Aufrufreihenfolge

## 3. State als Snapshot

### 3.1 Warum `console.log` den alten Wert zeigt

Richtig beantwortet, und richtig formuliert — ohne das Wort „Verzögerung", das hier fast alle benutzen und das falsch ist.

```jsx
function Zaehler() {
  const [count, setCount] = useState(0)
  function handleClick() {
    setCount(count + 1)
    console.log(count)      // 0 — nicht 1
  }
}
```

`count` ist eine **`const` innerhalb dieses Renders**. Sie kann sich nicht ändern; das erlaubt JavaScript gar nicht. `setCount` ändert keine Variable — es teilt React mit, dass der *nächste* Render einen anderen Wert bekommen soll. In diesem Render bleibt `count` für immer `0`.

Die Formulierung fürs Gespräch: *„Es ist nicht verzögert, es ist ein anderer Wert in einem anderen Render. `count` ist eine Konstante dieses Renders — und der Handler wurde mit den Werten dieses Renders erzeugt."*

Der Grund, warum es kein Timing-Problem ist: Auch ein `setTimeout` von drei Sekunden würde `0` loggen, wenn der Handler aus diesem Render stammt. Der Wert ist im Handler **eingeschlossen** — das ist eine Closure, und damit ist der optionale Artikel aus [[Documentation/Interview Vorbereitung/Deutz/React/Grundlagen/Leseliste#Block 0 — JavaScript für React|Block 0]] nachträglich relevant geworden.

### 3.2 Der Klassiker: dreimal `setCount(count + 1)`

**Richtig beantwortet — die schwerste Frage des Blocks.** Deine Herleitung („er ersetzt alle `count` durch 0 am Anfang und setzt damit count dreimal auf 1") ist genau das Modell, das `react.dev` „substitution" nennt.

Ausgeschrieben, weil du es im Gespräch so vorführen können solltest:

```jsx
// Im ersten Render ist count = 0. Ersetze count durch seinen Wert:
setCount(0 + 1)   // → 1
setCount(0 + 1)   // → 1
setCount(0 + 1)   // → 1
// React nimmt den letzten: 1
```

Nach einem Klick steht `1`, nach drei Klicks `3`. Nicht `3` nach einem Klick — das ist die Falle, in die die Frage lockt.

Eine Präzisierung zu deiner Formulierung: „der Button wertet alles gleichzeitig aus" trifft das Ergebnis, aber nicht den Mechanismus. Richtiger: **React sammelt die drei Aufrufe und verarbeitet sie erst, wenn der Handler fertig ist.** Das ist Batching ([[#4.1 Was Batching ist|4.1]]). Die drei Aufrufe laufen nacheinander, sie werden nur gemeinsam *verarbeitet* — und weil alle drei denselben eingefrorenen `count` benutzen, rechnen alle drei dasselbe aus.

### 3.3 „Ein Render sieht einen eingefrorenen Snapshot"

Nicht beantwortet — aber du hast es in 3.1 und 3.2 der Sache nach schon erklärt. Hier der Begriff dazu:

**Ein Render erzeugt eine vollständige Momentaufnahme.** React ruft deine Komponentenfunktion auf, und alles, was dabei entsteht — die JSX-Ausgabe, die Event-Handler, die Variablen — ist mit den Werten *dieses* Aufrufs gefüllt. Diese Momentaufnahme ändert sich nie mehr. Ein neuer Wert bedeutet einen neuen Aufruf, also eine neue Momentaufnahme.

Der Beweis, den `react.dev` dafür bringt und den du im Gespräch erzählen kannst:

```jsx
function Zaehler() {
  const [count, setCount] = useState(0)
  return <button onClick={() => {
    setCount(count + 5)
    setTimeout(() => alert(count), 3000)   // zeigt 0, nicht 5
  }}>+5</button>
}
```

Drei Sekunden später ist der State längst `5` — die Meldung zeigt trotzdem `0`. Weil der Handler aus dem Render stammt, in dem `count` gleich `0` war, und diesen Wert eingeschlossen hat.

Der Nutzen dieses Verhaltens: Es macht Event-Handler **vorhersehbar**. Ein Handler arbeitet konsistent mit dem Zustand, den der Nutzer beim Klicken gesehen hat — nicht mit einem, der sich zwischenzeitlich verschoben hat. Bei einem Formular heißt das: Abgeschickt wird, was auf dem Bildschirm stand.

## 4. Batching und Updater-Funktionen

### 4.1 Was Batching ist

Richtig beantwortet, Kellner-Analogie inklusive.

**React wartet, bis alle Event-Handler fertig gelaufen sind, und rendert dann einmal.** Nicht nach jedem `setState` einzeln. Der Kellner nimmt die ganze Bestellung auf, bevor er in die Küche geht — er läuft nicht nach jedem Gericht einmal hin und her.

Zwei Gewinne:

- **Leistung.** Ein Render statt drei.
- **Konsistenz.** Es gibt keinen Zwischenzustand, in dem die Oberfläche halb aktualisiert ist — etwa ein neuer Preis bei noch alter Menge.

Seit React 18 heißt das **Automatic Batching** und gilt überall: in Event-Handlern, in Promises, in `setTimeout`, in nativen Handlern. Vorher wurde nur in React-Event-Handlern gebündelt — ein `setTimeout` mit zwei Updates erzeugte zwei Renders. Das als historische Einordnung zu kennen, ist eine gute Antwort auf „was hat sich in React 18 geändert?".

### 4.2 Wann die Updater-Form nötig ist

Du hast **eine** von zwei Situationen genannt. Die Frage verlangte zwei.

**Situation 1 — mehrere Updates im selben Handler.** Das hattest du:

```jsx
setCount(c => c + 1)   // jeder Aufruf bekommt das Ergebnis des vorherigen
setCount(c => c + 1)   // → +2 insgesamt
```

React arbeitet die Warteschlange der Reihenfolge nach ab und reicht jeder Funktion das Ergebnis der vorherigen weiter. Statt dreimal derselben eingefrorenen Zahl.

**Situation 2 — der Aufruf erfolgt später, aus einem veralteten Render.** Alles, was zeitversetzt läuft: ein `setTimeout`, ein `setInterval`, der `.then`-Teil einer Anfrage, ein Effect.

```jsx
// ❌ count ist auf dem Stand von damals eingefroren
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000)
  return () => clearInterval(id)
}, [])

// ✅ liest immer den aktuellsten Wert
useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000)
  return () => clearInterval(id)
}, [])
```

Das ist das **stale closure**-Problem — dieselbe Mechanik wie beim `setTimeout`-Beispiel in [[#3.3 „Ein Render sieht einen eingefrorenen Snapshot"|3.3]], nur mit echten Folgen. Der Zähler bliebe bei 1 stehen.

**Für dein Projekt ist das direkt relevant:** In [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 11 — Preislauf starten und verfolgen|Schritt 11]] pollst du den Status per Intervall. Alles, was dort aus dem Callback heraus State setzt und dabei auf den vorherigen Wert aufbaut, braucht die Updater-Form.

**Die Faustregel:** Hängt der neue Wert vom alten ab, nimm die Updater-Form. Sie ist nie falsch — nur manchmal überflüssig.

### 4.3 Die Reparatur

Richtig beantwortet. `setCount(n => n + 1)` dreimal ergibt `+3` pro Klick, weil jeder Aufruf auf dem Ergebnis des vorigen aufsetzt statt auf dem eingefrorenen Wert.

Die unmittelbare Nachfolgefrage ist *„Und wie fügen Sie dann ein Element zu einer Liste im State hinzu?"*. Darauf zu schweigen entwertet die erste Antwort komplett, weil es so aussieht, als hättest du das Prinzip nur zitiert.
>

### 5.1 Warum nicht mutiert werden darf

Makellos beantwortet:

> „Weil dann kein neuer Render getriggert wird (das Objekt hat sich ja auch nicht geändert, es zeigt immer noch auf dieselbe Adresse, nur was unter dieser Adresse steht ist anders)"

Das ist die vollständige Antwort, und sie zieht die Linie von [[0. JavaScript für React - Vertiefung#4.3 Identität statt Inhalt — und warum React darauf baut|Block 0, 4.3]] sauber durch. Zum Formulieren im Gespräch:

React vergleicht mit `Object.is` — praktisch `===` —, ob der neue State-Wert ein **anderer** ist als der alte. Es vergleicht **nicht** die Inhalte; das wäre bei jeder Tastatureingabe viel zu teuer. Mutierst du, bleibt die Referenz dieselbe, React sieht `alt === neu` und rendert nicht. Der Bildschirm zeigt den alten Zustand, die Daten sind neu — ein Fehler ohne Fehlermeldung.

Zwei Ergänzungen, die die Antwort abrunden:

- **Es gibt noch einen zweiten Grund:** Unveränderlichkeit macht Optimierungen erst möglich. `memo` und der React Compiler entscheiden über Referenzvergleiche, ob eine Teilkomponente übersprungen werden darf. Mit Mutation wären diese Vergleiche unzuverlässig.
- **Und einen dritten:** Alte Zustände bleiben erhalten. Das ist die Grundlage von Undo/Redo und von Time-Travel-Debugging.

### 5.2 Objekte im State aktualisieren

Hier fehlte der Code, und der verschachtelte Fall — der eigentliche Kern der Frage — blieb offen. Also beides:

**Flach:**

```jsx
const [produkt, setProdukt] = useState({ id: 1, name: 'Kajak', preis: 12 })

setProdukt({ ...produkt, preis: 15 })      // ✅ neues Objekt, neue Referenz
produkt.preis = 15                          // ❌ mutiert, kein Render
```

**Verschachtelt — und hier ist der Punkt:**

```jsx
const [produkt, setProdukt] = useState({
  id: 1,
  name: 'Kajak',
  anbieter: { name: 'Nordsport', ort: 'Kiel' },
})

// ❌ FALSCH — sieht richtig aus, ist es nicht
setProdukt({ ...produkt, anbieter: { ...produkt.anbieter, ort: 'Hamburg' } })   // ✅ doch richtig
setProdukt({ ...produkt })                     // ❌ anbieter ist dieselbe Referenz
produkt.anbieter.ort = 'Hamburg'               // ❌ mutiert das verschachtelte Objekt
```

**Was sich ändert:** Spread ist eine **flache** Kopie ([[0. JavaScript für React - Vertiefung#4.2 Spread — eine flache Kopie|Block 0, 4.2]]). Die oberste Ebene ist neu, alles darunter sind dieselben Referenzen wie vorher. Willst du in der Tiefe etwas ändern, musst du **jede Ebene auf dem Weg dorthin neu erzeugen** — sonst mutierst du ein Objekt, das React für unverändert hält.

Bei drei Ebenen wird das unangenehm — und genau deshalb lautet das Prinzip aus [[#6. Die richtige State-Struktur wählen|Abschnitt 6]] „avoid deeply nested state". Die beste Lösung ist meist, den State flacher zu schneiden. Für die Fälle, wo das nicht geht: `structuredClone` oder die Bibliothek **Immer**, die mutierend *aussehenden* Code in unveränderliche Updates übersetzt. Immer als Vokabel zu kennen ist im Gespräch nützlich.

### 5.3 Die vier Operationen — die Tabelle

Die Frage war unglücklich gestellt („übertrag die Tabelle") — sie setzte voraus, dass du die Tabelle von `react.dev` vor Augen hast. Hier ist sie, in der Form, in der du sie brauchst. **Das ist der Merkstoff dieses Blocks.**

| Operation | ❌ vermeiden (mutiert) | ✅ stattdessen (neues Array) |
|---|---|---|
| **Hinzufügen** | `arr.push(x)`, `arr.unshift(x)` | `[...arr, x]` · `[x, ...arr]` |
| **Entfernen** | `arr.pop()`, `arr.splice(i, 1)` | `arr.filter(e => e.id !== id)` |
| **Ersetzen** | `arr[i] = x`, `arr[i].feld = x` | `arr.map(e => e.id === id ? { ...e, feld: x } : e)` |
| **Sortieren / Umdrehen** | `arr.sort()`, `arr.reverse()` | `[...arr].sort(…)` · `arr.toSorted(…)` |
| **Einfügen an Position** | `arr.splice(i, 0, x)` | `[...arr.slice(0, i), x, ...arr.slice(i)]` |

Die vier Zeilen, die wirklich sitzen müssen — mehr braucht kein Mensch im Gespräch:

```js
setListe([...liste, neu])                                        // anfügen
setListe(liste.filter(e => e.id !== id))                          // entfernen
setListe(liste.map(e => e.id === id ? { ...e, preis: 15 } : e))   // ändern
setListe([...liste].sort((a, b) => a.preis - b.preis))            // sortieren
```

Zwei Merkhilfen, die dich auch dann tragen, wenn die Tabelle weg ist:

- **Beim Ändern braucht man `map` plus Spread** — `map` erzeugt das neue Array, der Spread das neue Objekt darin. Nur `map` allein genügt nicht, wenn du das Element selbst anfasst: `arr.map(e => { e.preis = 15; return e })` mutiert die Objekte.
- **Alles, was wie ein Befehl klingt, mutiert** (`push`, `pop`, `sort`, `reverse`, `splice`); **alles, was wie eine Frage klingt, gibt neu zurück** (`map`, `filter`, `slice`). Das ist dieselbe Eselsbrücke wie in Block 0 — jetzt mit einem Grund, sie zu behalten.

### 5.4 Der Rückbezug auf Block 0

Die Frage wollte nur eines: dass du bemerkst, dass die Einteilung „mutierend vs. neu zurückgebend" aus [[0. JavaScript für React - Vertiefung#3.2 Die Tabelle: verändert das Original vs. gibt ein neues Array zurück|Block 0]] **exakt** die React-Regel ist. Es gibt keine zweite Liste zu lernen.

Deine Antwort — „welche die Seiteneffekte haben" — trifft es sogar begrifflich: Eine mutierende Methode *ist* ein Seiteneffekt auf das übergebene Array. Und ein Seiteneffekt während des Renderns verstößt gegen die Reinheit aus [[1. React-Grundlagen - Vertiefung#6. Reinheit von Komponenten|Block 1, Abschnitt 6]]. Drei Blöcke, ein Prinzip.

**Die Kurzfassung fürs Gespräch:** *„In React behandle ich State wie unveränderliche Daten. Praktisch heißt das: nur die Array-Methoden, die ein neues Array zurückgeben — `map`, `filter`, Spread — und niemals `push`, `splice` oder `sort` direkt auf dem State. Sonst bleibt die Referenz gleich und React rendert nicht."*

## 6. Die richtige State-Struktur wählen

### 6.1 Die fünf Prinzipien

Alle fünf richtig genannt — und das aus dem Kopf. Mit je einem Satz:

1. **Group related state.** Werte, die sich immer gemeinsam ändern, in ein Objekt. Zwei Koordinaten, die nie einzeln gesetzt werden, gehören zusammen.
2. **Avoid contradictions in state.** Keine Kombination zulässig machen, die es fachlich nicht gibt. `istLadend` *und* `istFertig` als zwei Booleans erlauben den Zustand „beides true". Besser ein Status-String: `'leer' | 'laedt' | 'fertig' | 'fehler'`.
3. **Avoid redundant state.** Was sich aus Props oder anderem State berechnen lässt, gehört nicht in den State.
4. **Avoid duplication in state.** Dasselbe Datum nicht an zwei Stellen halten. Statt des ausgewählten *Objekts* die ausgewählte **ID** speichern und das Objekt daraus ableiten.
5. **Avoid deeply nested state.** Flach schneiden — sonst wird jedes Update zur Kopierorgie ([[#5.2 Objekte im State aktualisieren|5.2]]).

Punkt 4 ist für dein Dashboard unmittelbar relevant und in [[1. React-Grundlagen - Vertiefung#8.3 Angewandt auf dein Dashboard|Block 1, 8.3]] schon so entworfen: `ausgewaehlteProduktId` im State, das Produkt selbst per `find` abgeleitet. Speicherst du das Objekt, hast du es doppelt — und nach einem Neuladen der Liste zeigt die Detailansicht das alte.

### 6.2 Redundanter State

„Weil man vergessen kann, korrekt abzudaten" — richtige Richtung, aber zu knapp für ein Gespräch. Ausformuliert am gefragten Beispiel:

```jsx
const [produkte, setProdukte] = useState([])
const [gefilterteProdukte, setGefilterteProdukte] = useState([])   // ❌ redundant
```

Was daran falsch ist: `gefilterteProdukte` ist vollständig aus `produkte` und `suchbegriff` berechenbar. Als eigener State muss es **von Hand synchron gehalten** werden — bei jeder Änderung des Suchbegriffs, bei jedem Neuladen der Produkte, bei jedem Hinzufügen. Jede dieser Stellen ist eine Gelegenheit, es zu vergessen.

**Und die Folge ist keine Fehlermeldung, sondern eine Lüge auf dem Bildschirm:** Die Oberfläche zeigt einen Zustand an, den es in den Daten nicht gibt — Produkte, die längst gelöscht sind, oder ein Filterergebnis, das nicht zum Suchfeld passt.

Die Lösung ist eine Zeile, die während des Renderns läuft:

```jsx
const gefiltert = produkte.filter(p => p.name.toLowerCase().includes(suche.toLowerCase()))
```

Ein abgeleiteter Wert **kann per Konstruktion nicht veralten**, weil er bei jedem Render neu entsteht.

Das ist derselbe Gedanke wie Normalisierung in [[Documentation/Traineeship/Skalierbarkeit & ETL/2.2 OLAP Datenmodellierung & Datawarehousing/2.2 OLAP Datenmodellierung & Datawarehousing - Vertiefung|Kapitel 2.2]]: Redundant gespeicherte Information ist eine Inkonsistenz in Wartestellung. **Diesen Bogen solltest du im Gespräch schlagen** — „State ist die Datenbank meiner Oberfläche, und er will normalisiert sein" ist eine Antwort, die man sich merkt.

Und es ist zugleich die Brücke zu Block 3: Die falsche Reparatur wäre ein `useEffect`, der bei jeder Suchänderung `setGefilterteProdukte` aufruft. Genau davor warnt „You Might Not Need an Effect".

### 6.3 „Don't mirror props in state"

Nicht beantwortet. Gemeint ist dieses Muster:

```jsx
function Karte({ produkt }) {
  const [name, setName] = useState(produkt.name)   // ❌ Prop in State kopiert
```

Das Problem: Der Anfangswert von `useState` zählt **nur beim ersten Render** ([[#2.2 Was useState zurückgibt|2.2]]). Ändert sich `produkt.name` später, bleibt `name` auf dem alten Wert stehen. Die Komponente zeigt veraltete Daten und niemand merkt es. Richtig ist, `produkt.name` einfach direkt zu benutzen.

**Die Ausnahme** — und die ist häufig genug, um sie zu kennen: Wenn der Prop-Wert bewusst nur als *Anfangswert* dient und die Komponente ihn danach selbst besitzt. Etwa ein Bearbeitungsformular, das mit dem gespeicherten Wert startet und dann dem Nutzer gehört. Die Konvention ist, das im Prop-Namen sichtbar zu machen:

```jsx
function Formular({ initialerName }) {          // „initial…" signalisiert: nur der Startwert
  const [name, setName] = useState(initialerName)
```

Braucht man doch ein Zurücksetzen bei geändertem Prop, ist der saubere Weg ein `key` von außen — dann verwirft React die Instanz und baut sie mit neuem Anfangswert auf. Wieder derselbe Mechanismus wie in [[1. React-Grundlagen - Vertiefung#5.2 Wozu key dient — und an wen es sich richtet|Block 1, 5.2]].

## 7. State teilen: Lifting State Up und kontrollierte Komponenten

### 7.1 Lifting State Up

Richtig beantwortet: gemeinsamen Vorfahren suchen, State dorthin heben, per Props nach unten geben — und per Callback-Props wieder nach oben melden.

```jsx
function Panel() {
  const [suche, setSuche] = useState('')          // der gemeinsame Besitzer
  const gefiltert = produkte.filter(p => p.name.includes(suche))
  return (
    <>
      <Suchfeld wert={suche} onWertAendern={setSuche} />
      <Liste produkte={gefiltert} />
    </>
  )
}
```

Der Name des Musters ist **Lifting State Up** — „den State hochziehen". Das Prinzip dahinter: **Es gibt für jeden Wert genau eine Quelle der Wahrheit** (*single source of truth*), und die liegt so tief wie möglich, aber hoch genug, dass alle Interessenten sie erreichen.

### 7.2 Kontrolliert vs. unkontrolliert

Nicht gewusst — und das ist eine Tier-2-Interviewfrage, die du außerdem heute beim Bauen brauchst ([[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 6 — Ein kontrolliertes Suchfeld|Schritt 6]]).

**Unkontrolliert:** Das DOM-Element verwaltet seinen Wert selbst. React setzt höchstens einen Anfangswert und liest bei Bedarf über eine Ref nach.

```jsx
<input defaultValue="Kajak" />     // der Browser merkt sich, was getippt wurde
```

**Kontrolliert:** React besitzt den Wert. Das Feld zeigt immer, was im State steht, und meldet jede Änderung zurück.

```jsx
const [suche, setSuche] = useState('')
<input value={suche} onChange={(e) => setSuche(e.target.value)} />
```

Der Kreislauf dabei — und den solltest du erzählen können, weil er das ganze React-Modell in einem Beispiel zeigt:

1. Nutzer tippt „K"
2. `onChange` feuert, `setSuche('K')`
3. React rendert die Komponente neu
4. `<input value="K">` — das Feld zeigt jetzt „K"

**Der Buchstabe erscheint also nicht, weil der Nutzer ihn getippt hat, sondern weil React neu gerendert hat.** Die Eingabe löst den State-Wechsel aus, der State bestimmt die Anzeige.

> [!warning] Die Probe aufs Exempel
> Lass `onChange` weg und behalte `value`: **Das Feld lässt sich nicht mehr beschreiben.** Man tippt, und nichts erscheint — weil `value` bei jedem Render auf den unveränderten State zurückgesetzt wird. React warnt dann in der Konsole.
>
> Das ist die beste Zwei-Sekunden-Demonstration dafür, was „kontrolliert" heißt, und eine gute Antwort auf die Frage. **Probier es heute beim Bauen einmal aus** — dann hast du es gesehen statt gelesen.

**Wann welches?** Kontrolliert ist der Normalfall in React: Nur so kann man validieren, formatieren, Felder voneinander abhängig machen oder den Absende-Button abhängig vom Inhalt deaktivieren. Unkontrolliert ist einfacher und ausreichend bei Formularen, die man nur einmal beim Absenden ausliest — und der einzige Weg bei `<input type="file">`, dessen Wert aus Sicherheitsgründen nicht gesetzt werden darf.

### 7.3 Der Preis von Lifting State Up

Richtig beantwortet: Bei tiefen Bäumen werden Daten durch viele Komponenten gereicht, die sie selbst nicht brauchen.

Der Begriff dafür ist **Prop Drilling** — „Durchbohren" der Komponentenhierarchie. Die Zwischenkomponenten werden zu Durchreichestationen; ein neues Prop bedeutet Änderungen in jeder Ebene dazwischen.

Die Lösungen, in der Reihenfolge, in der man sie erwägt:

1. **Komponenten anders schneiden.** Oft löst `children` das Problem ganz ([[1. React-Grundlagen - Vertiefung#3.3 children|Block 1, 3.3]]): Statt Daten durchzureichen, gibt man das fertige Element von oben hinein.
2. **Context** — für Werte, die *viele* Komponenten auf *vielen* Ebenen brauchen: Theme, Sprache, angemeldeter Nutzer, API-Konfiguration. Block 3, Abschnitt 6.
3. **Eine State-Management-Bibliothek** — Redux, Zustand — bei größeren Anwendungen mit komplexen Datenflüssen.

Wichtig für das Gespräch: **Prop Drilling über zwei Ebenen ist kein Problem.** Context dagegen zu setzen ist überzogen und macht die Datenflüsse unsichtbarer, nicht klarer. Die Fähigkeit, das abzuwägen, ist wertvoller als die Kenntnis von Context.

### 7.4 Der Suchbegriff in deinem Dashboard

Die Schlussfolgerung stimmte, die Begründung fehlte. Sie hat zwei Teile:

**Erstens — wer braucht den Wert?** Das `Suchfeld` (um ihn anzuzeigen) und die `ProduktListe` (um zu filtern). Zwei Geschwister, also gehört er ihrem gemeinsamen Vorfahren: `ProduktPanel`. Das ist Lifting State Up nach Regel.

**Zweitens — warum nicht im Suchfeld?** Läge er dort, könnte die Liste ihn nicht lesen — Daten fließen nur nach unten ([[1. React-Grundlagen - Vertiefung#3.4 Einseitiger Datenfluss|Block 1, 3.4]]), nicht zwischen Geschwistern. Das Suchfeld wird dadurch zur **kontrollierten Komponente** ([[#7.2 Kontrolliert vs. unkontrolliert|7.2]]): Es besitzt nichts, es zeigt an und meldet.

Und der Anschluss, der die Kette schließt: Die gefilterte Liste wird **nicht** gespeichert, sondern im Render abgeleitet ([[#6.2 Redundanter State|6.2]]). Damit hast du in einem einzigen Feature drei Prinzipien beisammen — Lifting State Up, kontrollierte Komponente, abgeleiteter Wert.

> [!tip] Das ist dein bestes Gesprächsbeispiel
> Ein Suchfeld über einer Liste klingt banal und enthält trotzdem die halbe React-Lehre. Wenn im Gespräch „haben Sie ein Beispiel?" kommt, ist das die Geschichte: *„In meinem Dashboard filtert ein Suchfeld eine Produktliste. Der Suchbegriff liegt beim gemeinsamen Elternteil, weil beide ihn brauchen — das Feld ist kontrolliert, es besitzt den Wert nicht. Und die gefilterte Liste habe ich bewusst nicht in den State gelegt, sondern im Render berechnet, weil sie sonst mit den Rohdaten auseinanderlaufen kann."*
>
> Das ist die Art Antwort, die gefragt wird — und du hast alle drei Teile heute schon beisammen. **Sag sie einmal laut, bevor du weiterbaust.**

## 7. Einordnung: was es sonst noch gibt

*Kein Prüfungsstoff — das hier ist dein **Vokabular für Nachfragen**. Ziel ist nicht Kompetenz, sondern Orientierung: sagen können, was es ist und wofür man es nimmt, und dann ehrlich ergänzen „damit habe ich nicht gearbeitet". Genau diese Kombination wirkt souverän; so zu tun, als kenne man es, fliegt bei der zweiten Frage auf.*

### 7.1 — `useReducer`

Ein eingebauter Hook als Alternative zu `useState`, wenn die State-Logik komplex wird. Statt vieler Setter schreibt man **eine Reducer-Funktion** `(state, action) => neuerState` und schickt aus den Komponenten nur noch **Actions** — beschreibende Objekte wie `{ type: 'produkt_gewaehlt', id: 7 }`.

Der Gewinn: Alle Übergänge stehen an einer Stelle, sind ohne React testbar, und die Komponenten beschreiben nur noch, *was passiert ist*, nicht *wie sich der State ändert*. Sinnvoll, sobald mehrere Werte zusammenhängend geändert werden oder der nächste Zustand stark vom vorherigen abhängt.

**Abgrenzung zu Redux:** dasselbe Denkmodell (Reducer, Actions, unveränderliche Updates) — Redux hat es populär gemacht, React hat es eingebaut. Der Unterschied ist die Reichweite: `useReducer` ist **lokal** in einer Komponente, Redux ein **globaler** Store für die ganze Anwendung, mit Middleware und DevTools. Faustregel: `useReducer` plus Context deckt vieles ab, wofür man früher Redux genommen hat.

### 7.2 — `memo`, `useMemo`, `useCallback`

Drei Werkzeuge gegen unnötige Arbeit beim Rendern:

- **`memo(Komponente)`** überspringt das Neurendern, wenn sich die Props nicht geändert haben — geprüft per Referenzvergleich.
- **`useMemo(() => berechne(a), [a])`** merkt sich ein **Rechenergebnis** zwischen Renders.
- **`useCallback(fn, [deps])`** merkt sich eine **Funktion**, damit sie ihre Referenz behält — sonst wäre ein `memo`-Kind trotzdem bei jedem Render neu zu rendern.

**Wichtiger als die Syntax ist die Haltung, und die zählt im Gespräch:** Das ist Optimierung, kein Standard. Vorsorglich eingesetzt macht es den Code schwerer lesbar, ohne messbar etwas zu bringen. Erst messen, dann optimieren. Der **React Compiler** (7.7) soll das künftig überflüssig machen.

### 7.3 — React Router

Die verbreitetste Bibliothek für Routing in einer Single-Page-Application: URLs auf Komponenten abbilden, ohne dass der Browser die Seite neu lädt. Man definiert Routen (`/produkte`, `/produkte/:id`), React Router rendert die passende Komponente und hält die Adresszeile synchron — inklusive Vor/Zurück und Lesezeichen.

Nicht in React selbst enthalten: React ist eine Bibliothek für Oberflächen, kein Framework mit Routing und Datenhaltung. Das ist zugleich ein Teil der Antwort auf „Warum Next.js?" — dort ist Routing eingebaut.

### 7.4 — TanStack Query

Eine Bibliothek für **Server-State**: Daten, die eigentlich dem Server gehören und die man im Client nur zwischenlagert. Sie übernimmt genau das, was man beim Selberbauen mit `useEffect` mühsam nachbaut — Caching, Zusammenfassen gleicher Anfragen, Hintergrund-Aktualisierung, Wiederholversuche, Lade- und Fehlerzustände, Invalidierung nach Änderungen.

**Die Antwort auf „Wie holen Sie Daten?":** *„In meinem Übungsprojekt mit einem eigenen Hook auf Basis von `useEffect` und `fetch` — bewusst, um den Mechanismus zu verstehen. In einem echten Projekt würde ich TanStack Query nehmen, weil Caching und Race Conditions dort gelöst sind."* Eine starke Antwort, weil sie zeigt, dass du weißt, was dein eigener Code **nicht** kann.

Der begriffliche Kern dahinter ist die Unterscheidung **Server-State vs. UI-State**: Serverdaten sind geliehen und können veralten; UI-Zustand — was ist ausgewählt, was steht im Suchfeld — gehört wirklich dir.

### 7.5 — Redux / Zustand

**Redux** (heute in der Form *Redux Toolkit*) ist der klassische globale Store: ein zentraler State-Baum, Änderungen nur über Actions und Reducer, hervorragende DevTools mit Zeitreise. Sehr strukturiert, aber mit spürbarem Aufwand — und seit Context und Hooks in vielen Projekten nicht mehr nötig.

**Zustand** ist die moderne, minimalistische Antwort darauf: ein Store in wenigen Zeilen, ohne Boilerplate und ohne Provider-Verschachtelung.

Die Einordnung, die im Gespräch zählt: So etwas braucht man für **globalen UI-State**, der viele Teile der Anwendung betrifft. Für reine Serverdaten ist TanStack Query meist die bessere Wahl — der häufigste Fehler ist, API-Antworten in Redux zu legen.

### 7.6 — Next.js, SSR, Server Components

**Next.js** ist das verbreitetste React-Framework: Routing, Datenholen, Bundling und Deployment fertig zusammengesetzt. Vite plus React ist eine reine **Client-Anwendung**; Next.js kann zusätzlich auf dem Server rendern.

- **CSR** (Client-Side Rendering, dein Setup): Der Browser lädt ein fast leeres HTML plus JavaScript und baut die Seite selbst. Erster Eindruck langsamer, Suchmaschinen sehen zunächst wenig.
- **SSR** (Server-Side Rendering): Der Server liefert fertiges HTML, der Browser zeigt es sofort, danach wird es „hydriert" — React übernimmt die Interaktivität. Besser für Ladezeit und Auffindbarkeit.
- **React Server Components** (React 19): Komponenten, die **nur** auf dem Server laufen und deren Code nie zum Browser geht. Sie dürfen direkt auf die Datenbank zugreifen und machen das Bundle kleiner. Derzeit der größte Umbruch im React-Ökosystem.

**Deine ehrliche Antwort:** *„Ich habe bewusst mit Vite und reinem Client-Rendering gearbeitet, um React selbst zu lernen. Next.js kenne ich als das Framework, das Routing und Server-Rendering mitbringt — eingesetzt habe ich es nicht."*

### 7.7 — Neues in React 19

Erschienen im Dezember 2024, aktuell ist **19.3**.

- **Actions** — Funktionen, die einen asynchronen Übergang kapseln; zusammen mit `useActionState` und `useFormStatus` werden Lade- und Fehlerzustände bei Formularen automatisch geführt statt von Hand.
- **`use`** — ein neuer Hook, der ein Promise oder einen Context direkt im Render lesen kann und sich dabei mit Suspense verträgt. Anders als die übrigen Hooks darf er in Bedingungen stehen.
- **`ref` als normales Prop** — `forwardRef` entfällt. Kleine Änderung, aber sehr sichtbar gegenüber älterem Code.
- **`useOptimistic`** — zeigt ein Ergebnis sofort an, bevor der Server bestätigt hat, und nimmt es bei einem Fehler zurück.
- **React Compiler** — memoisiert automatisch, macht `useMemo`/`useCallback` weitgehend überflüssig, und **funktioniert nur, weil Komponenten rein sein müssen** ([[1. React-Grundlagen - Vertiefung#6.2 Was React dadurch gewinnt|Block 1, 6.2]]). Genau diesen Bogen solltest du im Gespräch schlagen: Die Reinheitsregel ist kein Formalismus, sie ist die Voraussetzung dafür.

### 7.8 — Error Boundaries und Suspense

**Error Boundary:** eine Komponente, die Fehler in ihrem Teilbaum abfängt und statt der abgestürzten Stelle eine Ersatzdarstellung zeigt. Ohne sie reißt ein Fehler in einer einzigen Komponente die ganze Anwendung ab. Das ist die einzige Stelle, an der man heute noch eine **Klassenkomponente** schreiben muss — oder eine fertige Bibliothek nimmt.

**Suspense:** `<Suspense fallback={<Spinner />}>` zeigt eine Ersatzdarstellung, solange etwas darunter noch nicht bereit ist — nachgeladener Code (`lazy`) oder, mit passender Anbindung, noch laufende Daten. Es verschiebt die Lade-Behandlung von der einzelnen Komponente an eine gemeinsame Stelle im Baum.

Beide zusammen sind die deklarative Antwort auf „was zeigen wir, während es lädt oder wenn etwas kaputtgeht" — statt in jeder Komponente `if (laedt)` und `if (fehler)` zu schreiben.

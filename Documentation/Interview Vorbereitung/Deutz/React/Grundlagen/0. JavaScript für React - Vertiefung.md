## 1. Funktionen, Arrow Functions und Template Literals

### 1.1 Die drei Formen, eine Funktion zu schreiben

```js
// 1. Function Declaration — benannt, wird gehoisted (siehe 8.1)
function addiere(a, b) {
  return a + b
}

// 2. Function Expression — eine Funktion als Wert, einer Variablen zugewiesen
const addiere = function (a, b) {
  return a + b
}

// 3. Arrow Function — kompakte Schreibweise für Function Expressions
const addiere = (a, b) => a + b
```

Die Form, die dir in deiner Antwort gefehlt hat, ist die **Function Expression**. Sie ist historisch die wichtigste: Sie macht sichtbar, dass Funktionen in JavaScript ganz normale Werte sind — man kann sie einer Variablen zuweisen, in ein Array legen, als Argument übergeben und zurückgeben. Genau das tust du in React ständig: `onClick={handleClick}` übergibt eine Funktion als Prop, `array.map(b => …)` übergibt eine Funktion als Argument.

In React-Code siehst du fast nur zwei davon:

- **Function Declaration** für Komponenten: `export default function ProduktKarte({ titel }) { … }`. Das ist die Form, die `react.dev` durchgehend verwendet.
- **Arrow Function** für alles, was inline übergeben wird: Event-Handler, `map`-Callbacks, Effekt-Bodies.

Deine Einschätzung „Arrow Function am häufigsten" stimmt gemessen an der Anzahl der Vorkommen. Gemessen an den *Komponenten* ist es umgekehrt — beides zu wissen ist besser als eine Faustregel.

> [!note] Der Python-Vergleich
> `function` ≈ `def`. Die Arrow Function ist **nicht** Pythons `lambda`: Ein `lambda` darf nur einen einzelnen Ausdruck enthalten, eine Arrow Function darf einen kompletten Funktionskörper haben. Die Arrow Function ist mächtiger; sie ist eine vollwertige Funktion mit kürzerer Schreibweise.

### 1.2 Implizites Return — und die Falle darin

Eine Arrow Function hat zwei Körperformen, und der Unterschied ist folgenreich:

```js
// Expression-Body: der Wert des Ausdrucks wird implizit zurückgegeben
const sum = (a, b) => a + b        // → 5 bei sum(2, 3)

// Block-Body: geschweifte Klammern → du MUSST return schreiben
const sum = (a, b) => { return a + b }   // → 5
```

> [!warning] Korrektur — dein Beispiel gab `undefined` zurück
> Du hast geschrieben: `let sum = (a, b) => { a+b }`. Diese Funktion gibt **`undefined`** zurück, nicht `5`.
>
> Sobald geschweifte Klammern da sind, interpretiert JavaScript sie als **Funktionskörper**, nicht als Ausdruck. Ohne `return` fällt die Funktion einfach durch, und wie jede Funktion ohne `return` liefert sie `undefined`. Dein *Konzept* war richtig formuliert — der Code war es nicht. Das ist ein Anfängerfehler, der sich stundenlang verstecken kann, weil nichts abstürzt: Du bekommst einfach überall `undefined`.
>
> **Merksatz:** Klammern auf → `return` nicht vergessen.

Die dritte Variante brauchst du in React sofort, sobald du ein Objekt zurückgeben willst:

```js
// Falsch: die {} werden als Funktionskörper gelesen
const machPunkt = (x, y) => { x: x, y: y }

// Richtig: runde Klammern drumherum sagen „das ist ein Ausdruck"
const machPunkt = (x, y) => ({ x: x, y: y })
```

Genau deshalb siehst du in React-Code Konstrukte wie `setState(alt => ({ ...alt, name: 'neu' }))` — die runden Klammern um das Objekt sind kein Stil, sie sind notwendig.

Weitere Kurzformen, die du lesen können musst:

```js
const verdopple = x => x * 2          // ein Parameter: Klammern optional
const jetzt = () => Date.now()        // kein Parameter: leere Klammern Pflicht
```

### 1.3 Template Literals

```js
const name = 'Nick'
const preis = 12.5
const text = `Hallo ${name}, das kostet ${preis.toFixed(2)} €`
```

Drei Punkte:

- **Backticks**, keine Anführungszeichen. Das ist der häufigste Tippfehler am Anfang.
- In `${…}` steht ein **beliebiger Ausdruck**, nicht nur ein Variablenname — Methodenaufrufe, Rechnungen, ternäre Operatoren.
- Template Literals dürfen über mehrere Zeilen gehen; die Zeilenumbrüche landen im String.

Das Python-Gegenstück ist der f-String. Deine Antwort war richtig. Der Unterschied: Python braucht das Präfix `f` und normale Anführungszeichen, JavaScript braucht Backticks und kein Präfix.

In deinem Projekt siehst du das bei jeder URL: `` fetch(`${BASIS_URL}/products/${id}`) ``.

## 2. Destructuring

Destructuring heißt: Werte aus einem Array oder Objekt **beim Zuweisen** auspacken, statt sie einzeln herauszuholen. Es ist reine Schreiberleichterung — aber React-Code besteht zu großen Teilen daraus, deshalb ist es Pflichtstoff.

### 2.1 Array-Destructuring — und was `useState` wirklich zurückgibt

```js
const [erstes, zweites] = ['a', 'b']
// erstes === 'a', zweites === 'b'
```

Links vom `=` steht kein Array, sondern ein **Muster**. JavaScript gleicht es Position für Position gegen das Array rechts ab.

Damit zu deiner Frage: `useState(0)` gibt **ein Array mit genau zwei Elementen** zurück:

1. den aktuellen Wert des States
2. eine Funktion, mit der man ihn setzt

```js
const zustand = useState(0)
const count = zustand[0]        // 0
const setCount = zustand[1]     // eine Funktion

// dasselbe, kompakt:
const [count, setCount] = useState(0)
```

> [!warning] Korrektur — „falls eine zweite existiert"
> Du hast vermutet, die zweite Variable werde nur belegt, *falls* ein zweiter Wert existiert. Das ist nicht der Fall: `useState` gibt **immer** genau zwei Elemente zurück. Die Unsicherheit kam daher, dass du nicht wusstest, was `useState` liefert — das ist in Ordnung, du hattest React noch nicht gelesen. Wichtig ist die Konsequenz: `const [a, b, c] = useState(0)` würde für `c` schlicht `undefined` liefern, ohne Fehler. JavaScript beschwert sich beim Destructuring nicht über zu viele Namen.

**Warum ein Array und kein Objekt?** Weil du die Namen frei wählen können sollst. Bei einem Array zählt die **Position**, nicht der Name:

```js
const [count, setCount] = useState(0)
const [name, setName] = useState('')
const [istOffen, setIstOffen] = useState(false)
```

Dreimal derselbe Hook, dreimal andere Namen — das ginge mit Objekt-Destructuring nicht ohne Umbenennung. Das ist ein bewusstes API-Design, und es ist eine gute Antwort auf eine typische Nachfrage im Gespräch.

### 2.2 Objekt-Destructuring — und der Props-Parameter

```js
const buch = { titel: 'Dune', autor: 'Herbert', jahr: 1965 }
const { titel, autor } = buch
// titel === 'Dune', autor === 'Herbert'
```

Hier zählt der **Name**, nicht die Position. `const { autor, titel } = buch` liefert dasselbe Ergebnis.

Umbenennen und Rest sammeln:

```js
const { titel: buchTitel, ...rest } = buch
// buchTitel === 'Dune', rest === { autor: 'Herbert', jahr: 1965 }
```

> [!warning] Korrektur — das ist der wichtigste Fehler in diesem Block
> Auf die Frage, wie `function Card({ title, price })` ohne Destructuring aussähe, hast du geantwortet: `Card(title, price)`, man sei „auf die richtige Reihenfolge angewiesen".
>
> **Das stimmt nicht — und der Irrtum wird dich in Block 1 direkt einholen.** Eine React-Komponente bekommt **immer genau ein Argument**: ein einzelnes Objekt, das alle Props enthält. Ohne Destructuring sähe dieselbe Komponente so aus:
>
> ```jsx
> function Card(props) {
>   return <h3>{props.title} — {props.price}</h3>
> }
> ```
>
> `{ title, price }` im Parameter ist also kein „zweites Argument", sondern ein **Muster, das das eine Props-Objekt auspackt**. Die geschweiften Klammern sind Destructuring, keine Parameterliste.
>
> **Woher der Irrtum kommt:** aus Python. Dort schreibt man `def card(title, price)` und ruft `card("Dune", 12.5)` positionsabhängig auf. In React gibt es diese Positionsabhängigkeit nicht — deshalb ist die Reihenfolge der Props beim Aufruf auch völlig egal: `<Card price={12.5} title="Dune" />` funktioniert genauso wie umgekehrt.
>
> **Die Konsequenz, die im Gespräch zählt:** Props sind ein Objekt. Deshalb kann man sie mit Spread weiterreichen (`<Card {...buch} />`), deshalb gibt es `props.children`, und deshalb ist „wie viele Argumente bekommt eine Komponentenfunktion?" eine Fangfrage mit der Antwort „eins".

### 2.3 Standardwerte

```js
const { titel = 'Ohne Titel', preis = 0 } = buch
function Card({ title, price = 0 }) { … }
```

Deine Antwort („mit `=`") war richtig. Eine Feinheit, die im Gespräch punktet:

> [!note] Der Standardwert greift nur bei `undefined` — nicht bei `null`
> ```js
> const { a = 5 } = { a: undefined }   // a === 5
> const { a = 5 } = { a: null }        // a === null  (!)
> ```
> Das ist dieselbe Logik wie beim `??`-Operator (siehe [[#5.3 Die drei Operatoren im Vergleich]]) und ein häufiger Stolperstein, wenn eine API `null` statt `undefined` liefert — was deine FastAPI für optionale Felder genau so tut.

## 3. Arrays und ihre Methoden

### 3.1 map, filter, find, reduce

```js
const buecher = [
  { id: 1, titel: 'Dune', preis: 12 },
  { id: 2, titel: 'Neuromancer', preis: 9 },
  { id: 3, titel: 'Solaris', preis: 15 },
]

buecher.map(b => b.titel)          // ['Dune', 'Neuromancer', 'Solaris']  — gleiche Länge
buecher.filter(b => b.preis < 13)  // [Dune, Neuromancer]                 — höchstens gleiche Länge
buecher.find(b => b.id === 2)      // das Objekt Neuromancer  — oder undefined
buecher.reduce((summe, b) => summe + b.preis, 0)   // 36
```

Deine Antwort zu `map`/`filter` war richtig. Die Präzisierung, die im Gespräch den Unterschied macht:

| | Callback liefert | Ergebnis | Länge |
|---|---|---|---|
| `map` | den neuen Wert für dieses Element | neues Array **transformierter** Werte | immer gleich |
| `filter` | truthy oder falsy | neues Array der **ursprünglichen** Elemente, die durchkamen | 0 bis n |
| `find` | truthy oder falsy | das **erste** passende Element (kein Array) | — |
| `reduce` | den neuen Akkumulator | ein **einzelner** Wert beliebigen Typs | — |

Die Python-Brücke: `map` ≈ Listcomprehension mit Ausdruck, `filter` ≈ Listcomprehension mit `if`, `reduce` ≈ `functools.reduce`. Anders als in Python geben die JS-Varianten sofort ein **Array** zurück, keinen Iterator — kein `list(...)` nötig.

In React ist `map` die Methode, mit der Listen gerendert werden:

```jsx
<ul>
  {buecher.map(b => <li key={b.id}>{b.titel}</li>)}
</ul>
```

Das ist keine React-Magie, sondern gewöhnliches JavaScript: Aus einem Array von Daten wird ein Array von Elementen, und React rendert Arrays von Elementen nacheinander.

### 3.2 Die Tabelle: verändert das Original vs. gibt ein neues Array zurück

Hier stand bei dir `idk`. **Das ist die wichtigste Einzelinformation dieses Blocks** — sie entscheidet in Block 2 darüber, welche Zeile Code funktioniert und welche einen stillen Bug erzeugt. Lern diese Tabelle.

| Verändert das Original (**mutierend**) | Gibt ein neues Array zurück (**nicht-mutierend**) |
|---|---|
| `push` — hinten anfügen | `map` |
| `pop` — hinten entfernen | `filter` |
| `shift` / `unshift` — vorne entfernen/anfügen | `slice` — Ausschnitt kopieren |
| `splice` — an Position entfernen/einfügen | `concat` — anhängen |
| `sort` — sortieren | `[...arr]` — Spread-Kopie |
| `reverse` — umdrehen | `toSorted`, `toReversed`, `toSpliced`, `with` *(ES2023)* |

Merkhilfen, die verlässlicher sind als Auswendiglernen:

- **`slice` kopiert, `splice` schneidet.** Ein Buchstabe Unterschied, gegenteiliges Verhalten — der Klassiker.
- **Alles, was eine Frage beantwortet, ist nicht-mutierend** (`map`, `filter`, `find`, `slice`). **Alles, was einen Befehl ausdrückt, mutiert** (`push`, `pop`, `sort`, `reverse`).
- **Der Rückgabewert verrät es:** `push` gibt die neue *Länge* zurück, `pop` das *entfernte Element*. Wer `const neu = arr.push(x)` schreibt, bekommt eine Zahl — ein sicheres Zeichen, dass man die falsche Methode benutzt.

Und die React-Übersetzung, die du in Block 2 brauchst:

```js
// Element anfügen
arr.push(neu)                    // ❌ mutiert
const neuArr = [...arr, neu]     // ✅

// Element entfernen
arr.splice(i, 1)                 // ❌
const neuArr = arr.filter(x => x.id !== id)   // ✅

// Element ändern
arr[i].titel = 'neu'             // ❌ (mutiert sogar das Objekt darin, siehe 4.2)
const neuArr = arr.map(x => x.id === id ? { ...x, titel: 'neu' } : x)   // ✅
```

### 3.3 Sortieren, ohne das Original zu verändern

Deine Antwort — „kopieren und dann sort" — war im Ansatz richtig und hat die Hälfte getroffen. Die zweite Hälfte ist die, an der fast jeder einmal hängenbleibt:

```js
// Kopieren, dann sortieren
const sortiert = [...buecher].sort((a, b) => a.preis - b.preis)

// Seit ES2023 direkt, ohne Kopierschritt:
const sortiert = buecher.toSorted((a, b) => a.preis - b.preis)
```

> [!warning] `sort` sortiert ohne Vergleichsfunktion als **Text**
> ```js
> [10, 9, 100].sort()    // → [10, 100, 9]   (!)
> ```
> JavaScript wandelt die Elemente in Strings um und vergleicht lexikografisch: `"10" < "100" < "9"`. Bei Zahlen brauchst du **immer** eine Vergleichsfunktion.
>
> Die Konvention: `(a, b) => a - b` sortiert aufsteigend, `(a, b) => b - a` absteigend. Die Funktion muss eine negative Zahl, 0 oder eine positive Zahl liefern — nicht `true`/`false`.
>
> Für Strings: `(a, b) => a.titel.localeCompare(b.titel)` — das sortiert Umlaute richtig, `<`/`>` tut das nicht.

Für dein Dashboard relevant: Wenn du die Empfehlungen nach Preis sortiert anzeigen willst, gehört genau dieser Ausdruck in den Render — **nicht** in einen zweiten State (siehe [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 7 — Filtern ohne zweiten State|Schritt 7]]).

## 4. Objekte, Referenzen und Kopien

Dieser Abschnitt ist das Fundament unter der wichtigsten React-Regel. Deine Antworten hier waren die besten des Blocks — das trägt jetzt.

### 4.1 Was bei einer Zuweisung wirklich kopiert wird

```js
const a = { titel: 'Dune' }
const b = a
b.titel = 'Solaris'
console.log(a.titel)   // 'Solaris'  — a hat sich mitverändert
```

Deine Antwort war richtig: Kopiert wird die **Referenz** (die Adresse), nicht das Objekt. `a` und `b` sind zwei Namen für dasselbe Objekt im Speicher.

Der Unterschied zu primitiven Werten:

```js
let x = 5
let y = x
y = 10
console.log(x)   // 5 — unverändert
```

Zahlen, Strings, Booleans, `null`, `undefined`, Symbol und BigInt sind **Primitives** und werden als Wert kopiert. Objekte, Arrays und Funktionen sind **Referenztypen**.

> [!note] Genau wie in Python
> Hier trägt die Brücke vollständig: Auch in Python ist `b = a` bei einer Liste keine Kopie, und auch dort ist `a is b` dann `True`. Wer Pythons `copy`/`deepcopy` verstanden hat, versteht diesen Abschnitt sofort. `const` ändert daran übrigens nichts — es verhindert nur die *Neuzuweisung* des Namens, nicht die Veränderung des Objekts dahinter. Deshalb ist `const buch = {...}; buch.titel = 'neu'` völlig legal.

### 4.2 Spread — eine flache Kopie

```js
const buch = { titel: 'Dune', autor: { name: 'Herbert', jahr: 1965 } }
const kopie = { ...buch, preis: 12 }
```

Was hier passiert, Schritt für Schritt:

1. Ein **neues, leeres Objekt** wird angelegt.
2. Alle eigenen aufzählbaren Eigenschaften von `buch` werden hineinkopiert.
3. `preis: 12` wird ergänzt.

Deine Antwort („es tut alles andere in `...obj`") traf die Richtung, ließ aber zwei Punkte offen, die beide im Gespräch vorkommen:

**Erstens: Die Reihenfolge entscheidet.** Was später steht, gewinnt.

```js
{ ...buch, titel: 'Neu' }   // titel ist 'Neu'
{ titel: 'Neu', ...buch }   // titel ist 'Dune' — der Spread überschreibt!
```

Das ist der Unterschied zwischen „Standardwerte setzen" und „Werte überschreiben", und es ist ein realer Bug-Kandidat in React, wenn man Props weiterreicht.

**Zweitens — und das ist der wichtige Teil: Die Kopie ist flach.**

```js
kopie.titel = 'Solaris'         // betrifft nur kopie ✅
kopie.autor.name = 'Lem'        // ändert AUCH buch.autor.name ❌
```

Die oberste Ebene ist kopiert, aber `autor` war eine Referenz — und die Referenz wurde kopiert, nicht das Objekt dahinter. Beide zeigen weiter auf denselben Autor.

Verschachtelt korrekt aktualisieren heißt: **jede Ebene auf dem Weg nach unten neu erzeugen.**

```js
const kopie = {
  ...buch,
  autor: { ...buch.autor, name: 'Lem' },
}
```

Genau deshalb steht in `react.dev` der Hinweis, State flach zu halten — tief verschachtelter State macht jedes Update mühsam. Für den Notfall gibt es `structuredClone(obj)` (echte Tiefkopie, im Browser eingebaut) und die Bibliothek Immer; beides ist Vokabelwissen, kein Pflichtstoff.

### 4.3 Identität statt Inhalt — und warum React darauf baut

```js
{ a: 1 } === { a: 1 }   // false
[1, 2] === [1, 2]       // false
```

Deine Antwort war richtig: verglichen werden die Referenzen, nicht die Inhalte. JavaScript hat keinen eingebauten Inhaltsvergleich für Objekte.

Jetzt die Verbindung, wegen der dieser Abschnitt im Block steht:

> [!important] Warum React verlangt, dass du State nie mutierst
> React prüft bei einem State-Update mit `Object.is` (praktisch: `===`), ob der neue Wert ein **anderer** ist als der alte. Es vergleicht **nicht** die Inhalte — das wäre bei großen Datenstrukturen bei jedem Tastendruck viel zu teuer.
>
> ```js
> // ❌ React sieht keine Änderung
> buecher.push(neu)
> setBuecher(buecher)        // dieselbe Referenz → kein Re-Render
>
> // ✅ neue Referenz → React rendert neu
> setBuecher([...buecher, neu])
> ```
>
> Im ersten Fall hat sich der Inhalt geändert, die Referenz aber nicht. React vergleicht `alt === neu`, bekommt `true`, und rendert nicht. Die Oberfläche bleibt stehen, obwohl die Daten stimmen — ein Bug ohne Fehlermeldung, der einen halben Tag kosten kann.
>
> **Das ist die vollständige Antwort auf die Interviewfrage „Warum darf man State nicht mutieren?".** Nicht „weil React das so will", sondern: *weil React Änderungen an der Referenzidentität erkennt, und eine Mutation die Identität nicht ändert.* Wer das so sagen kann, hat den Kern verstanden.

## 5. Kurzschluss-Operatoren, Vergleiche und sicherer Zugriff

### 5.1 Truthy und falsy

Der Begriff, den JavaScript für „gilt in einer Bedingung als wahr" verwendet. **Falsy sind genau acht Werte:**

```
false    0    -0    0n    ""    null    undefined    NaN
```

Alles andere ist truthy — auch `"0"`, `"false"`, `[]` und `{}`. Besonders das leere Array überrascht: `if ([])` ist wahr, `if ([].length)` ist falsch.

Diese Liste musst du kennen, weil `&&`, `||` und `if` alle darauf beruhen — und weil `0` und `""` darin vorkommen, was in einer Preis- und Datenanwendung wie deiner ständig relevant ist.

### 5.2 `&&` und `||` geben keine Booleans zurück

Das ist der Punkt, den fast alle falsch erinnern:

```js
0 && 'hallo'        // 0            — nicht false!
'a' && 'b'          // 'b'
'' || 'Standard'    // 'Standard'
'x' || 'Standard'   // 'x'
```

Die Regel: **Der Operator gibt einen der beiden Operanden zurück, nicht `true`/`false`.**

- `a && b` — ist `a` falsy, gib `a` zurück; sonst `b`. („Beide müssen stimmen, also scheitere am ersten, der nicht stimmt.")
- `a || b` — ist `a` truthy, gib `a` zurück; sonst `b`. („Einer reicht, also nimm den ersten, der stimmt.")

Der rechte Operand wird gar nicht erst ausgewertet, wenn der linke schon entscheidet — das ist die **Kurzschlussauswertung**, und sie erlaubt Muster wie `daten && verarbeite(daten)`.

Deine Antwort auf 5.1 war komplett richtig — inklusive `0 && "hallo"` → `0`. Behalte das, denn:

> [!important] Der `0`-Bug in React
> ```jsx
> {buecher.length && <Liste buecher={buecher} />}
> ```
> Bei leerer Liste ist `buecher.length` gleich `0`. Der Ausdruck ergibt also `0` — und React rendert die Zahl **0** sichtbar auf die Seite. Nicht „nichts", sondern eine einsame Null im Layout.
>
> Der Grund: React rendert `false`, `null` und `undefined` als „nichts", aber `0` ist eine gültige Zahl und wird angezeigt.
>
> Richtig ist eine echte Bedingung:
> ```jsx
> {buecher.length > 0 && <Liste buecher={buecher} />}
> ```
> Das wird dir in [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 4 — Lade- und Fehlerzustände|Schritt 4 des Projekts]] begegnen. Es ist außerdem eine beliebte Interviewfrage, weil sie genau prüft, ob jemand `&&` wirklich verstanden hat oder nur nachgeahmt.

### 5.3 Die drei Operatoren im Vergleich

Deine Antwort auf 5.2 — „`??` für Standardwerte, `||` für or" — war zu unscharf. `||` wird sehr wohl für Standardwerte benutzt, und genau daraus entsteht der Fehler, nach dem gefragt war:

```js
const preis = 0

preis || 9.99      // 9.99  ❌ ein Preis von 0 € wird als „nicht gesetzt" behandelt
preis ?? 9.99      // 0     ✅
```

| Operator | Weicht aus bei | Nimm ihn, wenn |
|---|---|---|
| `||` | allen **falsy** Werten (`0`, `''`, `false`, `NaN`, `null`, `undefined`) | jeder leere Wert durch den Standard ersetzt werden soll |
| `??` | nur `null` und `undefined` | `0`, `''` oder `false` **gültige** Werte sind |

Die Faustregel: **Sobald `0`, ein leerer String oder `false` echte Werte in deinen Daten sein können, ist `??` richtig und `||` ein Bug.** In deiner Pricing-Domäne ist das fast immer der Fall — ein Rabatt von 0 %, eine Kapazität von 0, ein leerer Kommentar.

### 5.4 Optional Chaining

```js
daten?.produkte?.length
```

Deine Antwort war richtig. Präzise formuliert: Ist der Wert links vom `?.` **`null` oder `undefined`**, bricht die gesamte Kette ab und der Ausdruck ergibt `undefined` — statt einen `TypeError: Cannot read properties of undefined` zu werfen.

Das ist genau der Fall, der in React beim ersten Render eintritt: Der State ist noch `null`, die API-Antwort unterwegs, die Komponente rendert aber schon.

Drei Formen:

```js
obj?.feld          // Eigenschaft
obj?.[schluessel]  // dynamischer Schlüssel
obj.methode?.()    // Methode, die es vielleicht nicht gibt
```

Sehr gut kombinierbar mit `??`:

```js
const anzahl = daten?.produkte?.length ?? 0
```

> [!note] Nicht überall streuen
> `a?.b?.c?.d` überall hinzuschreiben verbirgt Fehler, statt sie zu lösen. Wenn `daten` an einer Stelle *nie* `null` sein kann, schreib dort `daten.feld` — sonst merkst du nicht, wenn doch etwas fehlt. Optional Chaining gehört genau an die Stellen, an denen ein fehlender Wert **erwartbar** ist.

### 5.5 `==` vs. `===`

```js
0 == ''        // true   (!)
0 == '0'       // true
null == undefined   // true
NaN == NaN     // false

0 === ''       // false
0 === '0'      // false
```

`==` wandelt vorher die Typen um (Type Coercion), `===` nicht. Die Umwandlungsregeln sind verwinkelt genug, dass praktisch jeder Style Guide sagt: **immer `===`.**

Die eine sinnvolle Ausnahme ist `x == null` — das ist `true` für `null` *und* `undefined` und ein verbreitetes Idiom. Wer es nicht mag, schreibt `x === null || x === undefined`.

### 5.6 `null` vs. `undefined`

JavaScript hat zwei „nichts"-Werte, und der Unterschied ist Absicht:

| | Bedeutung | Entsteht typischerweise |
|---|---|---|
| `undefined` | „war nie gesetzt" | nicht belegte Variable, fehlendes Objektfeld, fehlendes Argument, Funktion ohne `return` |
| `null` | „bewusst leer gesetzt" | von dir oder von einer API explizit vergeben |

Python kennt nur `None`. Für dich heißt das: Deine FastAPI liefert für ein optionales Feld im JSON `null`; greifst du auf ein Feld zu, das es im JSON gar nicht gibt, bekommst du `undefined`. Beide sind falsy, beide werden von `?.` und `??` gleich behandelt — aber `typeof null` ist `'object'` (ein historischer Fehler in der Sprache, den man nicht mehr repariert hat) und `typeof undefined` ist `'undefined'`.

In React ist der Unterschied praktisch relevant für Initialwerte: `useState(null)` heißt „noch nichts geladen", `useState(undefined)` sagt dasselbe unschärfer. Nimm `null`.

## 6. Asynchrones JavaScript und fetch

### 6.1 Was ein Promise ist

> [!warning] Korrektur — ein Promise ist keine Funktion
> Du hast geschrieben: „ein Promise ist eine Funktion, welche eine Weile braucht, aber verspricht …". Das Konzept — Platzhalter für ein späteres Ergebnis, entweder Wert oder Fehler — hast du richtig beschrieben. Die Kategorie stimmt nicht: **Ein Promise ist ein Objekt, kein ausführbares Ding.**
>
> Der Unterschied ist nicht pedantisch. Eine Funktion *ruft man auf*; ein Promise *existiert bereits* und man *wartet darauf*. Deshalb kann man ein Promise in einer Variablen halten, in ein Array legen und an `Promise.all` übergeben. Und deshalb läuft die Arbeit schon, sobald das Promise existiert — nicht erst, wenn man `await` schreibt.
>
> Formulierung fürs Gespräch: *„Ein Promise ist ein Objekt, das für ein Ergebnis steht, das es noch nicht gibt. Es hat drei Zustände: pending, fulfilled, rejected — und es geht genau einmal von pending in einen der beiden anderen über."*

Die drei Zustände:

- **pending** — läuft noch
- **fulfilled** — erfolgreich, mit einem Wert
- **rejected** — fehlgeschlagen, mit einem Grund

`await` hält die umgebende `async`-Funktion an, bis das Promise sich entscheidet: Bei *fulfilled* liefert `await` den Wert, bei *rejected* wirft es eine Exception, die du mit `try/catch` fangen kannst.

> [!note] Wo der Python-Vergleich trägt — und wo nicht
> **Gleich:** `async`/`await` als Schlüsselwörter, `await` nur innerhalb einer `async`-Funktion (bzw. auf oberster Modulebene), eine `async`-Funktion gibt immer ein Promise zurück — genau wie eine Python-Coroutine-Funktion immer eine Coroutine zurückgibt.
>
> **Anders, und das ist der entscheidende Unterschied:** Ein Promise startet **sofort bei der Erzeugung**. `const p = fetch(url)` schickt den Request los, auch ohne `await`. Eine Python-Coroutine tut bis zum `await` bzw. bis zum Scheduling durch die Event-Loop gar nichts. JS-Promises sind *eager*, Python-Coroutinen *lazy*.
>
> Praktische Folge: In JavaScript kannst du zwei Requests parallel laufen lassen, indem du sie erst startest und dann beide abwartest:
> ```js
> const p1 = fetch(a)
> const p2 = fetch(b)
> const [r1, r2] = await Promise.all([p1, p2])
> ```

### 6.2 Warum zwei `await`

```js
const res = await fetch(url)
const data = await res.json()
```

Deine Antwort war im Kern richtig. Die genaue Fassung:

1. **Erstes `await`:** Das Promise von `fetch` wird erfüllt, sobald der **Antwortkopf** da ist — Statuscode und Header. Der Body ist zu diesem Zeitpunkt noch gar nicht vollständig übertragen.
2. **Zweites `await`:** `res.json()` liest den Body **als Stream** zu Ende und parst ihn. Auch das dauert und ist deshalb ebenfalls asynchron.

Die Trennung ist Absicht: Man kann am Statuscode entscheiden, ob man den Body überhaupt lesen will — bei einem 500er etwa nicht. Und man kann zwischen `res.json()`, `res.text()`, `res.blob()` wählen, je nachdem, was geliefert wurde.

Ein Body ist übrigens nur **einmal** lesbar. `await res.json()` nach `await res.text()` wirft einen Fehler; wer beides braucht, ruft `res.clone()` auf.

### 6.3 `fetch` wirft bei 404 nicht

Deine Antwort war richtig: `res.ok` verrät es.

Die Regel: **`fetch` lehnt sein Promise nur bei einem Netzwerkfehler ab** — kein Server erreichbar, DNS kaputt, Verbindung abgebrochen, von CORS blockiert. Eine HTTP-Antwort mit 404 oder 500 ist aus Sicht von `fetch` ein **Erfolg**: Der Server hat geantwortet, die Kommunikation hat funktioniert.

```js
const res = await fetch(url)
res.ok        // true bei Status 200–299, sonst false
res.status    // 404
res.statusText
```

Für deine Pricing-API heißt das konkret: `GET /v1/products/999` liefert einen sauberen 404 mit JSON-Body — `fetch` wirft nichts, und ohne `res.ok`-Prüfung versuchst du, den Fehlerbody als Produkt zu rendern.

### 6.4 Fehler vollständig behandeln

Hier stand `idk`. Das vollständige Muster deckt **beide** Fehlerarten ab, und du brauchst es in [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 3 — Echte Daten holen|Schritt 3]]:

```js
async function holen(pfad) {
  try {
    const res = await fetch(`${BASIS_URL}${pfad}`, {
      headers: { 'X-API-Key': API_KEY },
    })

    // Fall 1: Server hat geantwortet, aber mit einem Fehlerstatus
    if (!res.ok) {
      throw new Error(`HTTP ${res.status}: ${res.statusText}`)
    }

    return await res.json()
  } catch (fehler) {
    // Fall 2: gar keine Antwort — Netzwerk, DNS, CORS
    console.error('Anfrage fehlgeschlagen:', fehler)
    throw fehler   // weiterreichen, damit die Komponente es anzeigen kann
  }
}
```

Drei Dinge daran sind wichtig:

- **`try/catch` fängt nur Fall 2**, den Netzwerkfehler. Fall 1 musst du selbst zu einem Fehler machen — daher das `throw` bei `!res.ok`.
- **Nicht stillschweigend schlucken.** Ein `catch`, das nur loggt und `undefined` zurückgibt, erzeugt später einen unverständlichen Folgefehler. Weiterreichen und in der Komponente anzeigen.
- **`finally`** gibt es auch — der richtige Ort für `setLaedt(false)`, weil er in beiden Fällen läuft.

Die Alternative ohne `async`/`await` ist die Kettenschreibweise, die du in fremdem Code sehen wirst:

```js
fetch(url)
  .then(res => res.json())
  .then(daten => setDaten(daten))
  .catch(fehler => setFehler(fehler.message))
  .finally(() => setLaedt(false))
```

Funktional gleichwertig; `async`/`await` ist besser lesbar, die Kette kompakter. Im `useApi`-Hook in [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 9 — Ein eigener Hook|Schritt 9]] benutzt du die Kette, weil sie sich dort besser mit dem Cleanup verträgt.

## 7. Module: import und export

Nicht beantwortet — das holen wir hier nach. Der Stoff ist klein, aber du liest ihn in jeder React-Datei in der ersten Zeile.

### 7.1 Default-Export und Named Export

```js
// buecher.js
export default function BuchKarte() { … }      // genau einer pro Datei
export function formatierePreis(p) { … }        // beliebig viele
export const MAX_TREFFER = 50
```

```js
// woanders
import BuchKarte from './buecher.js'                      // Default: Name frei wählbar
import { formatierePreis, MAX_TREFFER } from './buecher.js'  // Named: Name muss passen
import Irgendwas, { formatierePreis } from './buecher.js'    // beides zusammen
import { formatierePreis as fmt } from './buecher.js'        // umbenennen
```

Der praktische Unterschied:

| | Default-Export | Named Export |
|---|---|---|
| Anzahl pro Datei | höchstens einer | beliebig viele |
| Geschweifte Klammern beim Import | nein | ja |
| Name beim Import | frei wählbar | muss übereinstimmen (außer mit `as`) |
| Tippfehler fallen auf | nein — du bekommst einfach einen anderen Namen | ja, direkt beim Import |

**Konvention in React:** Eine Komponente pro Datei als Default-Export, Hilfsfunktionen und Konstanten als Named Exports. Genau das erzeugt Vite auch in `App.jsx`.

> [!note] Der Python-Vergleich, der nur halb trägt
> `import { x } from './modul.js'` ≈ `from modul import x`. Aber: Python kennt keinen Default-Export, und in JavaScript braucht der Pfad relative Angaben (`./`) und bei eigenen Dateien oft die Endung. Ohne `./` sucht der Bundler in `node_modules` — `import React from 'react'` meint das Paket, `import App from './App'` die Datei daneben.

### 7.2 Warum nur ein Default pro Datei

Weil der Default-Export kein Name ist, sondern eine **Position**: „der eine Wert, für den dieses Modul steht". Ein Modul kann nur *eine* Hauptsache sein. Named Exports sind dagegen Einträge in einer Tabelle — davon kann es beliebig viele geben, weil jeder seinen eigenen Schlüssel hat.

Technisch: `export default x` ist eine Kurzform für einen Export unter dem reservierten Namen `default`. Zwei davon wären ein doppelter Schlüssel im selben Objekt.

Der Preis der Bequemlichkeit: Weil der Importeur den Namen frei wählt, kann dieselbe Komponente in drei Dateien unter drei Namen auftauchen. Manche Teams verbieten Default-Exports deshalb ganz. Für dein Projekt spielt das keine Rolle — kennen solltest du das Argument trotzdem.

## 8. Die Ränder: Scope, `this` und das DOM

Drei Themen, die bewusst nicht in der Leseliste standen — sie kosten mehr Zeit, als sie für ein Konzeptgespräch einbringen. Trotzdem gehören sie in die Notiz, damit die Lücke bewusst bleibt statt unbemerkt.

### 8.1 `var`, `let`, `const` und Scope

```js
const x = 1     // nicht neu zuweisbar, Block-Scope      → Standardwahl
let y = 2       // neu zuweisbar, Block-Scope            → wenn nötig
var z = 3       // Function-Scope, gehoisted             → nicht mehr benutzen
```

**Block-Scope** heißt: Die Variable existiert nur zwischen den `{}`, in denen sie deklariert wurde — in einem `if`, einer Schleife, einem beliebigen Block. `var` ignoriert das und gilt in der ganzen umgebenden Funktion; das hat jahrzehntelang Bugs erzeugt, besonders in Schleifen.

**Hoisting** heißt: Deklarationen werden gedanklich an den Anfang ihres Scopes gezogen. Bei `var` bedeutet das, dass die Variable vor ihrer Zeile bereits existiert — mit dem Wert `undefined`. Bei `let`/`const` existiert sie zwar auch schon, ein Zugriff davor wirft aber einen `ReferenceError` (die sogenannte Temporal Dead Zone). Function Declarations sind vollständig gehoistet und deshalb vor ihrer Definition aufrufbar; Function Expressions und Arrow Functions nicht.

**Regel für dich:** `const` als Standard, `let` nur, wenn du wirklich neu zuweist, `var` nie. In React-Code kommt `var` praktisch nicht mehr vor.

### 8.2 `this`, Klassen und Prototypen — und warum React sie hinter sich gelassen hat

Bis React 16.8 (Anfang 2019) schrieb man Komponenten als Klassen:

```jsx
class Zaehler extends React.Component {
  constructor(props) {
    super(props)
    this.state = { count: 0 }
    this.handleClick = this.handleClick.bind(this)   // ← der ständige Schmerz
  }
  handleClick() { this.setState({ count: this.state.count + 1 }) }
  render() { return <button onClick={this.handleClick}>{this.state.count}</button> }
}
```

Der Grund für das `bind`: In JavaScript hängt `this` davon ab, **wie** eine Funktion aufgerufen wird, nicht davon, wo sie definiert wurde. Reicht man eine Methode als Callback weiter, geht der Bezug zum Objekt verloren und `this` ist `undefined`. Arrow Functions haben kein eigenes `this` und übernehmen es aus dem umgebenden Code — deshalb wurden sie zur Standardlösung.

Mit Hooks entfällt das komplett: Funktionskomponenten haben kein `this`, State kommt aus `useState`, und es gibt nichts zu binden.

**Was du davon brauchst:** genug, um auf „Haben Sie schon mit Klassenkomponenten gearbeitet?" antworten zu können — *„Nein, ich habe mit Funktionskomponenten und Hooks gelernt. Klassenkomponenten sind der ältere Stil, bei dem State über `this.state` lief und man Methoden binden musste; sie funktionieren weiter, aber neuer Code entsteht so nicht mehr."* Das ist eine vollständig ausreichende Antwort.

Prototypen — JavaScripts Vererbungsmechanismus, bei dem Objekte auf ein anderes Objekt als Vorlage zeigen — brauchst du für React gar nicht. Nur die Einordnung: `class` in JavaScript ist syntaktischer Zucker über Prototypen, keine eigene Sprachebene wie in Python.

### 8.3 Das DOM und was React davon übernimmt

Das **DOM** ist die Objektdarstellung des HTML-Dokuments im Browser — ein Baum aus Knoten, den man per JavaScript lesen und verändern kann:

```js
// klassisches, imperatives DOM
const el = document.getElementById('titel')
el.textContent = 'Neuer Titel'
el.classList.add('aktiv')
```

Das ist **imperativ**: Du beschreibst die einzelnen Schritte der Veränderung. Bei wachsender Oberfläche wird das unhaltbar, weil jeder Zustandsübergang von Hand gepflegt werden muss — „wenn der Nutzer X tut und Y gerade offen ist, dann entferne die Klasse Z".

React ersetzt das durch eine **deklarative** Beschreibung: Du sagst, wie die Oberfläche bei einem gegebenen State *aussehen soll*, und React ermittelt die nötigen DOM-Operationen selbst.

```jsx
<h1 className={aktiv ? 'aktiv' : ''}>{titel}</h1>
```

Praktisch heißt das: **Du fasst das DOM in React nicht mehr direkt an.** Kein `document.getElementById`, kein `innerHTML`. Die einzige Ausnahme sind Refs für Dinge, die React nicht abdeckt — Fokus setzen, scrollen, eine Nicht-React-Bibliothek einbinden (siehe [[3. Effects, Daten und Architektur - Vertiefung#1. Refs|Block 3]]).

CSS bleibt CSS. React ändert daran nichts, außer dass das Attribut `className` statt `class` heißt (weil `class` in JavaScript ein reserviertes Wort ist) und Inline-Styles als Objekt geschrieben werden: `style={{ color: 'red' }}`.

### Das Muster hinter den Fehlern

Drei Dinge, und alle drei sind wiederkehrend — nicht zufällig:

**1. Das Konzept sitzt, der Beleg fehlt.** Bei 1.2, 4.2, 5.2 und 6.2 hast du jeweils die richtige Idee benannt und dann bei der Präzisierung verloren: das Codebeispiel gab `undefined` zurück, die flache Kopie fehlte, das Preis-0-Beispiel kam nicht. In einem Konzeptgespräch ist genau das die kritische Stelle — die erste Antwort bekommst du hin, die **Nachfrage** entscheidet. „`??` ist für Standardwerte" hält keine zehn Sekunden; „`||` ersetzt auch eine 0, `??` nur `null` und `undefined` — bei einem Preis von 0 macht das den Unterschied" hält.

> **Maßnahme für Block 1:** Zu jeder Antwort ein Mini-Beispiel dazuschreiben, und sei es zweizeilig. Wenn dir keins einfällt, hast du die Stelle gefunden, an der es noch nicht sitzt.

**2. Python-Reflexe an genau den Stellen, wo die Brücke nicht trägt.** Zwei der drei Fehler sind derselbe Fehler: `Card(title, price)` (mehrere Positionsargumente wie bei `def`) und „ein Promise ist eine Funktion" (Verwechslung mit der Coroutine-*Funktion*). Die Brücke Python→JavaScript hat dich in diesem Block weit getragen — bei Referenzsemantik und `async` hat sie glatt funktioniert. Aber wo sie bricht, bricht sie unbemerkt, weil die Analogie *plausibel* bleibt.

> **Maßnahme für Block 1:** Die Frage „Wo trägt der Python-Vergleich hier *nicht*?" explizit in den Notizen beantworten. Bei Props ist das schon klar. Der nächste Kandidat ist der Komponentenbegriff: Eine Komponente ist **keine** Klasse und **kein** Objekt mit Methoden.

**3. Eine echte inhaltliche Lücke mit Folgen.** Frage 3.2 — mutierend vs. nicht-mutierend — war das einzige vollständige `idk` bei einer Frage, die nicht nachgeschlagen, sondern gelernt werden muss. Das ist genau die Information, ohne die Block 2 nicht funktioniert: Jedes State-Update mit Array oder Objekt hängt daran, und die Interviewfrage „Warum darf man State nicht mutieren?" ist ohne sie nicht beantwortbar.

> **Maßnahme, heute noch:** Die Tabelle aus [[#3.2 Die Tabelle verändert das Original vs. gibt ein neues Array zurück|3.2]] plus den Merksatz aus [[#4.3 Identität statt Inhalt — und warum React darauf baut|4.3]] einmal aus dem Kopf aufschreiben. ### Was gut war

Der Referenz-Abschnitt (4.1, 4.3) und die Kurzschluss-Operatoren (5.1) saßen vollständig — inklusive `0 && "hallo"` → `0`, was erfahrungsgemäß mehr Leute falsch haben als richtig. Das sind nicht die einfachen Fragen, sondern die, die in Block 2 am meisten tragen. Darauf lässt sich aufbauen.

## 1. Was eine Komponente ist

### 1.1 Die Definition, vollständig

Deine Antwort — „pure ist und JSX herausgibt" — hat die richtige Hälfte getroffen. Was fehlte, ist die Eingangsseite. Die vollständige Fassung:

> **Eine React-Komponente ist eine JavaScript-Funktion, die ein Props-Objekt entgegennimmt und ein React-Element zurückgibt — eine Beschreibung dessen, was auf dem Bildschirm erscheinen soll.**

```jsx
function ProduktKarte({ titel, preis }) {     // rein: ein Props-Objekt
  return <article><h3>{titel}</h3><p>{preis} €</p></article>   // raus: ein Element
}
```

Drei Präzisierungen, die im Gespräch zählen:

- **Rein geht ein Objekt**, nicht mehrere Argumente. Das hattest du in Block 0 noch falsch und in [[#3.1 Was Props technisch sind|Frage 3.1]] korrigiert — das ist gesessen.
- **Raus kommt kein HTML.** Es kommt ein React-Element: ein einfaches JavaScript-Objekt, das beschreibt, *was* dargestellt werden soll. Mehr dazu in [[#2.4 Was mit JSX wirklich passiert|2.4]] — dort steckt dein einziger echter Fehler dieses Blocks.
- **„Rein" ist nicht optional**, sondern Voraussetzung dafür, dass React die Funktion beliebig oft aufrufen darf. Dazu [[#6. Reinheit von Komponenten|Abschnitt 6]].

Eine Komponente darf auch `null` zurückgeben (dann erscheint nichts), Strings und Zahlen (werden als Text gerendert) und Arrays von Elementen (werden nacheinander gerendert — genau das nutzt `map`).

### 1.2 Warum der Name großgeschrieben sein muss

Deine Antwort war richtig. Die Begründung eine Ebene tiefer, weil genau danach nachgefragt wird:

JSX wird in Funktionsaufrufe übersetzt, und **die Groß-/Kleinschreibung entscheidet, was als Argument eingesetzt wird**:

```jsx
<card />     →   jsx('card', …)     // String: ein eingebautes HTML-Tag namens "card"
<Card />     →   jsx(Card, …)       // Variable: deine Komponentenfunktion
```

Kleingeschrieben nimmt React den Namen als **Zeichenkette** und reicht ihn ans DOM durch — der Browser bekommt ein unbekanntes Element `<card>`, zeigt nichts Sinnvolles an und meldet keinen Fehler. Großgeschrieben nimmt React die **Variable aus dem Geltungsbereich** und ruft sie auf.

Das ist der Grund, warum ein vergessener Großbuchstabe zu einer stillen leeren Stelle in der Oberfläche führt statt zu einer Fehlermeldung — einer der unangenehmsten Anfängerfehler.

### 1.3 Einordnung: Schichtenarchitektur und der Vergleich zur Klasse

**Die Schicht.** Deine Zuordnung „Presentation" ist richtig, aber es lohnt, sie zu schärfen, weil du das Backend selbst gebaut hast: In deiner Pricing-Anwendung ist `src/pricing/presentation/api/routers/` die Präsentationsschicht **des Backends** — sie übersetzt HTTP in Domänenaufrufe und zurück. Das React-Frontend ist keine weitere Schicht *innerhalb* dieser Anwendung, sondern eine **eigenständige zweite Anwendung**, die über die HTTP-Grenze auf die erste zugreift.

Das ist die Antwort, mit der du im Gespräch punktest: *„Die REST-API ist die Grenze. Darüber sitzt eine separate Präsentationsanwendung, die ihren eigenen Zustand hat — nämlich den UI-Zustand, der im Backend nichts zu suchen hat: was gerade ausgewählt ist, was im Suchfeld steht, ob ein Dialog offen ist."* Genau dieser Unterschied zwischen **Serverdaten** und **UI-Zustand** ist das Thema, das ab Block 2 alles bestimmt.

Innerhalb der React-App gibt es die Schichtung übrigens wieder, nur flacher: Komponenten (Darstellung) · Hooks (wiederverwendbare Logik) · ein API-Modul (Zugriff). Deine `useApi`-Hook aus [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 9 — Ein eigener Hook|Schritt 9]] ist genau diese Trennung.

**Der Klassenvergleich.**

> [!warning] Korrektur — „Es hat natürlich keinen inneren Zustand"
> Doch, und zwar genau das ist der Kern von React. Eine Komponente **hat** inneren Zustand: `useState` gibt ihr ein Gedächtnis, das Render für Render überlebt. Und jede *Verwendung* der Komponente hat ihren **eigenen, isolierten** Zustand:
>
> ```jsx
> <Zaehler />   // dieser hat count = 3
> <Zaehler />   // dieser hat count = 0 — völlig unabhängig
> ```
>
> Du hast das noch nicht gelesen (State ist Block 2), insofern ist die Annahme nachvollziehbar. Wichtig ist, sie jetzt zu ersetzen — sonst baust du die Vorstellung „Komponente = zustandslose Template-Funktion" auf, und die ist falsch.
>
> **Und damit wird dein Klassenvergleich sogar besser, als du dachtest:** Eine Komponente verhält sich wie eine Klasse in *beiden* Hinsichten — wiederverwendbar (das hattest du) *und* mit Instanzen, die je eigenen Zustand tragen. `<Zaehler />` zweimal zu schreiben ist wie zweimal `Zaehler()` zu instanziieren.

Wo der Vergleich **nicht** trägt — und das ist die Stelle, an der dein Python-Reflex aus Block 0 wieder lauert:

| | Python-Klasse | React-Komponente |
|---|---|---|
| Instanz erzeugen | du: `z = Zaehler()` | React: beim Rendern von `<Zaehler />` |
| Zustand | `self.count`, von dir verwaltet | `useState`, von React verwaltet |
| Zustand ändern | `self.count += 1` direkt | `setCount(…)` — nie direkt |
| Methoden | `z.inkrementieren()` | keine — Funktionen im Komponentenkörper |
| Lebensdauer | bis keine Referenz mehr zeigt | solange React sie an derselben Stelle im Baum sieht |

Der letzte Punkt ist der fremdeste: **Du hältst nie eine Referenz auf eine Komponenteninstanz.** React verwaltet sie, anhand der Position im Baum. Das ist der Grund, warum ein geänderter `key` den Zustand zurücksetzt — für React ist es dann eine andere Instanz.

## 2. JSX

### 2.1 Drei Unterschiede zu HTML

Deine drei waren richtig. Hier vollständig, mit Begründung:

| JSX | HTML | Grund |
|---|---|---|
| Jedes Tag muss geschlossen sein: `<img />`, `<br />` | `<img>` reicht | JSX wird geparst wie Code, nicht wie Markup — es gibt keine Sonderregeln für einzelne Tags |
| `className`, `htmlFor` | `class`, `for` | `class` und `for` sind **reservierte Wörter in JavaScript**. JSX-Attribute werden zu Objekt-Eigenschaften |
| `onClick`, `onChange` (camelCase) | `onclick` (kleingeschrieben) | JavaScript-Konvention, und die Eigenschaften landen direkt im Props-Objekt |
| `{ausdruck}` für Werte | nur Text | JSX ist Teil eines JavaScript-Ausdrucks |
| genau ein Wurzelelement | beliebig viele | siehe [[#2.2 Warum genau ein Wurzelelement\|2.2]] |
| `style={{ color: 'red' }}` | `style="color: red"` | Inline-Styles sind ein JavaScript-Objekt |

Der Merksatz für das Gespräch: **„JSX sieht aus wie HTML, ist aber JavaScript."** Alle Abweichungen folgen aus diesem einen Satz.

### 2.2 Warum genau ein Wurzelelement

Deine Antwort zu Fragments (`<>…</>`) war richtig — auch der Name. Die Begründung, die dir fehlte, ist einfacher als du vermutet hast und folgt direkt aus [[#2.4 Was mit JSX wirklich passiert|2.4]]:

**Weil JSX zu einem Funktionsaufruf wird, und eine Funktion genau einen Wert zurückgeben kann.**

```jsx
return (
  <h1>Titel</h1>
  <p>Text</p>
)
```

wird zu `return jsx('h1', …) jsx('p', …)` — zwei Ausdrücke hintereinander, ohne Verknüpfung. Das ist kein React-Problem, sondern ein JavaScript-Syntaxfehler. Es ist derselbe Grund, aus dem `return 1 2` nicht geht.

Die Lösungen:

```jsx
// 1. Ein echtes Element drumherum — wenn du es im DOM willst
return <div><h1>…</h1><p>…</p></div>

// 2. Fragment — wenn du kein zusätzliches DOM-Element willst
return <><h1>…</h1><p>…</p></>

// 3. Lange Schreibweise — nötig, wenn du einen key brauchst
return <Fragment key={id}><h1>…</h1><p>…</p></Fragment>
```

**Wozu Fragments überhaupt?** Weil ein überflüssiges `<div>` nicht harmlos ist: Es taucht im DOM auf und kann Layouts zerstören — besonders bei Tabellen (`<tr>` darf kein `<div>` als Elternteil haben) und bei Flexbox/Grid, wo jede zusätzliche Ebene die Anordnung ändert. Fragments gruppieren, ohne im DOM zu erscheinen.

### 2.3 `{}` und `{{}}`

Deine Antwort war vollständig richtig — auch die Erkennung, dass das innere Klammerpaar ein **Objektliteral** ist. Das haben erfahrungsgemäß mehr Leute falsch als richtig, weil `{{ }}` wie eine eigene Syntax aussieht.

```jsx
<h1>{titel}</h1>                        // ein Ausdruck
<img src={produkt.bildUrl} />           // ein Ausdruck als Attributwert
<div style={{ color: 'red' }}>          // äußere {} = Ausdruck, innere {} = Objekt
<Card daten={{ id: 1, titel: 'X' }} />  // dasselbe Muster bei jedem Objekt-Prop
```

In `{…}` steht **jeder gültige JavaScript-Ausdruck**: Variablen, Rechnungen, Methodenaufrufe, ternäre Operatoren, `map`. Was *nicht* hineinpasst, sind **Anweisungen** — kein `if`, kein `for`, kein `return`. Ein Ausdruck hat einen Wert, eine Anweisung nicht. Daher die ternären Operatoren in [[#4. Bedingtes Rendern|Abschnitt 4]]: Sie sind die Ausdrucksform des `if`.

### 2.4 Was mit JSX wirklich passiert

> [!warning] Korrektur — JSX wird **nicht** in HTML umgewandelt
> Du hast geantwortet: „Es wird vollständig in html umgewandelt." Das ist der eine echte Fehler in diesem Block, und er lohnt eine ausführliche Korrektur, weil ein ganzes Bündel anderer Antworten daran hängt.
>
> **JSX wird in JavaScript-Funktionsaufrufe übersetzt.** Zuständig ist ein Compiler (bei dir: Vite über Babel/SWC), der schon vor der Auslieferung an den Browser läuft. Der Browser sieht nie JSX.
>
> ```jsx
> // du schreibst
> <h1 className="titel">Hallo</h1>
> ```
> ```js
> // Vite liefert aus (moderne JSX-Transform, React 17+)
> jsx('h1', { className: 'titel', children: 'Hallo' })
> ```
>
> Und dieser Aufruf erzeugt **ein gewöhnliches JavaScript-Objekt**:
> ```js
> { type: 'h1', props: { className: 'titel', children: 'Hallo' }, key: null, … }
> ```
>
> Dieses Objekt heißt **React-Element**. Es ist HTML weder in Form noch in Funktion — es ist eine *Beschreibung*. HTML entsteht erst ganz am Ende, wenn React aus solchen Beschreibungen echte DOM-Knoten baut (siehe [[#7. Render und Commit — was React eigentlich tut|Abschnitt 7]]).

Warum das mehr ist als Wortklauberei — vier Dinge, die sich daraus sofort erklären:

1. **Ein Wurzelelement** ([[#2.2 Warum genau ein Wurzelelement|2.2]]): Ein Funktionsaufruf liefert einen Wert.
2. **JSX ist ein Wert.** Deshalb darfst du es in eine Variable legen, in ein Array packen, aus einer Funktion zurückgeben, mit `map` erzeugen — es ist nichts Besonderes.
   ```jsx
   const gruss = <h1>Hallo</h1>
   const liste = buecher.map(b => <li key={b.id}>{b.titel}</li>)
   ```
3. **`className` statt `class`**: Es sind Objekteigenschaften, und JavaScript hat reservierte Wörter.
4. **`key` ist kein normales Prop**: Im Element-Objekt oben steht `key` *neben* `props`, nicht darin. Deshalb kommt `key` nie in deiner Komponente an — es ist eine Angabe an React, nicht an dich. Das ist gleich der Kern von [[#5.2 Wozu key dient — und an wen es sich richtet|5.2]].

> [!note] Der Python-Vergleich, der hier nicht trägt
> Es ist **kein** Templating wie Jinja2. Ein Jinja-Template erzeugt einen HTML-String, den man wegschicken kann. JSX erzeugt eine Objektstruktur im Speicher, die React weiter verarbeitet. Der Unterschied ist genau der, der React „reaktiv" macht: Weil die Beschreibung ein Objekt ist, kann React sie mit der vorigen **vergleichen**. Mit einem String ginge das nicht.

## 3. Props und der einseitige Datenfluss

### 3.1 Was Props technisch sind

Deine Antwort war richtig und ist die Korrektur deines Block-0-Fehlers: **Eine Komponentenfunktion bekommt genau ein Argument — ein Objekt, das alle Props enthält.**

```jsx
<ProduktKarte titel="Dune" preis={12} istNeu />

// kommt an als:
function ProduktKarte(props) {
  // props === { titel: 'Dune', preis: 12, istNeu: true }
}
```

Vier Folgerungen, die als Nachfrage kommen können:

- **Die Reihenfolge beim Aufruf ist egal** — es sind benannte Eigenschaften, keine Positionsargumente.
- **Ein Attribut ohne Wert bedeutet `true`**: `istNeu` ist gleichbedeutend mit `istNeu={true}`.
- **Props lassen sich mit Spread weiterreichen**: `<ProduktKarte {...produkt} />`. Praktisch, aber mit Vorsicht — man sieht dann nicht mehr, was die Komponente eigentlich bekommt.
- **Props sind nicht auf Strings und Zahlen beschränkt.** Objekte, Arrays, Funktionen und sogar JSX sind gültige Prop-Werte. Funktionen als Props sind der Mechanismus für den Rückfluss nach oben ([[#3.4 Einseitiger Datenfluss|3.4]]).

### 3.2 Warum Props unveränderlich sind

Deine Antwort („weil sie pure ist, Bugs beim mehrmaligen Aufrufen") traf die Richtung. Die drei Gründe im Einzelnen — jeder davon allein wäre schon ausreichend:

**1. Props gehören der Elternkomponente, nicht dir.** Und hier greift direkt [[0. JavaScript für React - Vertiefung#4.1 Was bei einer Zuweisung wirklich kopiert wird|Block 0, Abschnitt 4.1]]: Bekommst du ein Objekt als Prop, hast du eine **Referenz auf das Objekt der Eltern**. Schreibst du hinein, veränderst du die Daten der Eltern — ohne dass die davon erfahren.

```jsx
function Karte({ produkt }) {
  produkt.preis = 0        // ❌ ändert das Objekt im State der Eltern
  return <p>{produkt.preis}</p>
}
```

**2. React merkt es nicht.** Die Referenz bleibt dieselbe, also sieht React keine Änderung und rendert nicht neu. Der Bildschirm zeigt den alten Wert, die Daten sind neu — ein Fehler ohne Fehlermeldung. Das ist derselbe Mechanismus wie bei State ([[0. JavaScript für React - Vertiefung#4.3 Identität statt Inhalt — und warum React darauf baut|Block 0, 4.3]]).

**3. Die Reinheit bricht.** Eine reine Funktion muss bei gleichen Props dieselbe Ausgabe liefern. Verändert sie ihre Eingabe, liefert der zweite Aufruf etwas anderes als der erste — und React darf Komponenten beliebig oft aufrufen ([[#6. Reinheit von Komponenten|Abschnitt 6]]).

**Was tut man stattdessen?** Zwei Wege, und die Unterscheidung ist wichtig:

- Soll sich der Wert *in dieser Komponente* ändern → das ist **State**, nicht Props (Block 2).
- Sollen sich die Daten *der Eltern* ändern → die Eltern geben eine Funktion als Prop mit, du rufst sie auf. Das ist [[#3.4 Einseitiger Datenfluss|3.4]].

### 3.3 `children`

Deine Antwort war zu unscharf. `children` ist ein **spezielles Prop**, das alles enthält, was du zwischen öffnendes und schließendes Tag schreibst:

```jsx
function Panel({ titel, children }) {
  return (
    <section className="panel">
      <h2>{titel}</h2>
      <div className="inhalt">{children}</div>
    </section>
  )
}

// Verwendung
<Panel titel="Empfehlungen">
  <p>Noch nichts berechnet.</p>
  <button>Preislauf starten</button>
</Panel>
```

`children` ist hier das Array aus `<p>` und `<button>`. Du musst nichts dafür tun — React füllt das Prop automatisch.

**Wofür man es benutzt:** für Komponenten, die einen **Rahmen** bilden, ohne den Inhalt zu kennen — Karte, Dialog, Panel, Layout, Fehlergrenze. Die generische Hülle weiß, *wie* etwas aussieht; der Aufrufer bestimmt, *was* darin steht.

Der Gewinn ist Entkopplung: Ohne `children` bräuchtest du für jede Inhaltsvariante ein eigenes Prop oder eine eigene Komponente. Im Gespräch ist die Formulierung *„`children` erlaubt Komposition statt Konfiguration"* eine starke Antwort.

Für dein Dashboard: ein `<Panel titel="…">` für die drei Bereiche ist genau dieser Fall.

### 3.4 Einseitiger Datenfluss

Deine Antwort war richtig, inklusive des Rückwegs. Zum Ausformulieren:

**Daten fließen nach unten.** Eine Komponente reicht Werte an ihre Kinder, nie an ihre Eltern oder Geschwister. Der Datenfluss folgt dem Baum, immer in eine Richtung. React nennt das *one-way data binding* — im Gegensatz zu *two-way binding*, wie es Angular und Vue in Teilen anbieten, wo Kind und Eltern sich gegenseitig ändern können.

**Der Rückweg sind Funktionen.** Die Eltern geben eine Funktion als Prop mit; das Kind ruft sie auf. Die Entscheidung, was passiert, bleibt bei den Eltern — das Kind meldet nur ein Ereignis.

```jsx
// Eltern: besitzen die Daten und die Änderungsfunktion
function Liste() {
  const [ausgewaehlt, setAusgewaehlt] = useState(null)
  return <Zeile produkt={p} onAuswahl={setAusgewaehlt} />
}

// Kind: meldet nur, es entscheidet nichts
function Zeile({ produkt, onAuswahl }) {
  return <li onClick={() => onAuswahl(produkt.id)}>{produkt.name}</li>
}
```

Der Fachbegriff für diesen Rückweg ist **inverse data flow** — den hattest du in [[#8.1 Die fünf Schritte|Frage 8.1]] als fünften Schritt von „Thinking in React" schon korrekt genannt. Es ist derselbe Begriff; gut, dass du ihn kennst, nimm ihn auch hier.

**Warum diese Einschränkung ein Gewinn ist:** Sie macht Fehlersuche endlich. Steht auf dem Bildschirm ein falscher Wert, gibt es nur einen Weg, auf dem er dorthin gekommen sein kann — von oben. Du gehst den Baum hoch, bis du die Quelle findest. Bei beidseitiger Bindung kann jede beteiligte Komponente der Verursacher sein.

> [!example] Im Übungsprojekt
> - [[Lückenschluss (Pricing-Dashboard)#4.6 — Warum passt der Setter als `onAuswahl`? ❌|4.6]]: der Setter als Callback-Prop
> - [[Lückenschluss (Pricing-Dashboard)#7.4 — Event-Handler statt Effect, und warum der Handler nicht in der Aktionsleiste steht 🟡|7.4]]: das Kind meldet, der Besitzer des States entscheidet

## 4. Bedingtes Rendern

### 4.1 Die drei Schreibweisen

> [!warning] Korrektur — `??` ist keine Schreibweise für bedingtes Rendern
> Du hast `? :`, `??` und ein ausgeschriebenes `if` genannt. Die dritte Standardform ist **`&&`**, nicht `??`.
>
> `??` ist der Nullish-Coalescing-Operator aus [[0. JavaScript für React - Vertiefung#5.3 Die drei Operatoren im Vergleich|Block 0, 5.3]] — er wählt einen **Ersatzwert**, wenn etwas `null` oder `undefined` ist. Damit rendert man keine Bedingung, damit füllt man eine Lücke: `{produkt.beschreibung ?? 'Keine Beschreibung'}`. Nützlich, aber ein anderes Werkzeug.

Die drei Formen, die du kennen musst:

```jsx
// 1. if — außerhalb des JSX, für frühe Rückgaben
if (laedt) return <Spinner />
if (fehler) return <Fehlermeldung text={fehler} />
return <Liste daten={daten} />

// 2. Ternär — für ein Entweder-Oder mitten im JSX
<p>{istVerfuegbar ? 'Auf Lager' : 'Ausverkauft'}</p>

// 3. && — für „rendere das, oder gar nichts"
{istAdmin && <button>Löschen</button>}
```

Wann welche:

| Form | Passt für | Grund |
|---|---|---|
| `if` mit `return` | ganze Zustände der Komponente (lädt / Fehler / leer / Daten) | am besten lesbar, spart tiefe Verschachtelung |
| `? :` | ein Wert oder ein kleines Element, zwei Alternativen | einziger Weg, ein `if` *innerhalb* von JSX auszudrücken — es ist ein Ausdruck ([[#2.3 {} und {{}}\|2.3]]) |
| `&&` | optionales Element, keine Alternative | kürzeste Form — mit der Falle aus 4.2 |

Der Ausdruck-vs.-Anweisung-Punkt ist die Begründung, die im Gespräch gut ankommt: *„`if` ist eine Anweisung und passt deshalb nicht in `{…}`. Der ternäre Operator ist die Ausdrucksform derselben Verzweigung — deshalb sieht man ihn in JSX so oft."*

### 4.2 Die `0`-Falle

Deine Antwort war richtig: Es erscheint eine **`0`** auf der Seite.

Die Begründung, in beide Richtungen: `&&` gibt einen der Operanden zurück, keinen Boolean ([[0. JavaScript für React - Vertiefung#5. Kurzschluss-Operatoren, Vergleiche und sicherer Zugriff|Block 0, Abschnitt 5.2]]). Ist `anzahl` gleich `0`, ist `0` falsy, also gibt der Ausdruck `0` zurück. Und React rendert `false`, `null` und `undefined` als nichts — **`0` aber ist eine gültige Zahl und wird angezeigt.**

Zur Behebung: Dein „explizites if" funktioniert, ist aber schwerer als nötig. Die idiomatische Lösung ist, die linke Seite zu einem echten Boolean zu machen:

```jsx
{anzahl > 0 && <Liste />}          // ✅ üblich und am klarsten
{Boolean(anzahl) && <Liste />}     // ✅ funktioniert ebenso
{anzahl ? <Liste /> : null}        // ✅ explizit
{anzahl && <Liste />}              // ❌ rendert 0
```

**Merksatz:** Links von `&&` gehört eine Bedingung, kein Wert. Sobald dort eine Zahl oder ein String steht, ist es ein Bug in Wartestellung.

### 4.3 Wenn eine Komponente `null` zurückgibt

Deine Antwort war richtig. Eine Präzisierung, die in Block 3 wichtig wird:

**Die Komponente wird trotzdem ausgeführt.** React ruft die Funktion auf, sie läuft komplett durch, Hooks darin laufen mit — nur das Ergebnis ist „nichts darzustellen". Es wird kein DOM-Knoten erzeugt.

Das ist der Unterschied zwischen *nichts rendern* und *nicht gerendert werden*: Im ersten Fall existiert die Komponenteninstanz weiter samt State, im zweiten (die Eltern rendern sie gar nicht erst) wird sie aus dem Baum entfernt und ihr State verworfen. Das ist eine typische Nachfrage bei „Warum ist mein State plötzlich weg?".

Dasselbe gilt für `false`, `undefined` und `true` — alle rendern nichts. Nur `0` und `''` sind Fallen: `0` erscheint als Text, `''` erzeugt einen leeren Textknoten.

## 5. Listen und Keys

### 5.1 Listen rendern

Deine Antwort war richtig:

```jsx
const eintraege = produkte.map(p => <li key={p.id}>{p.name}</li>)
return <ul>{eintraege}</ul>

// oder direkt inline, häufiger:
return <ul>{produkte.map(p => <li key={p.id}>{p.name}</li>)}</ul>
```

**Warum `map` und nicht `forEach`?** Weil `map` ein **neues Array zurückgibt** und `forEach` `undefined` — siehe die Tabelle aus [[0. JavaScript für React - Vertiefung#3.2 Die Tabelle: verändert das Original vs. gibt ein neues Array zurück|Block 0, 3.2]]. Du brauchst einen Wert, den du in JSX einsetzen kannst; `forEach` liefert keinen.

**Und warum funktioniert es, einfach ein Array in JSX zu schreiben?** Weil React Arrays von Elementen rendern kann — es geht sie durch und rendert jedes einzeln. Das ist kein Spezialfall für Listen, sondern folgt aus [[#2.4 Was mit JSX wirklich passiert|2.4]]: Elemente sind Werte, Arrays von Werten sind gültig.

### 5.2 Wozu `key` dient — und an wen es sich richtet

> [!warning] Korrektur — Keys richten sich an React, nicht an den Browser, und es geht nicht um die Reihenfolge
> Du hast geantwortet: „an den browser damit die Reihenfolge bekannt ist." Beide Hälften stimmen nicht, und weil das eine Tier-1-Interviewfrage ist, lohnt sich die genaue Fassung.
>
> **Der Empfänger ist React.** Der Browser sieht `key` nie — es landet nicht im DOM und nicht einmal im Props-Objekt deiner Komponente (siehe [[#2.4 Was mit JSX wirklich passiert|2.4]]: `key` steht im Element-Objekt *neben* `props`). Wenn du in einer Komponente `props.key` liest, bekommst du `undefined`. Das ist Absicht.
>
> **Die Aufgabe ist Identität, nicht Reihenfolge.** Die Reihenfolge kennt React ohnehin — sie steht im Array. Was React *nicht* von selbst weiß, ist, **welches Element von vorher welchem Element von jetzt entspricht**.

Das Problem, das Keys lösen: Zwischen zwei Renderings bekommt React zwei Listen von Elementen und muss sie einander zuordnen. Ohne zusätzliche Information kann es nur nach Position vergleichen — und dann sieht ein Einfügen am Anfang so aus, als hätten sich *alle* Einträge geändert.

Mit `key` ist die Zuordnung eindeutig:

- **gleicher Key, gleiche Stelle** → dasselbe Element, React aktualisiert nur, was sich geändert hat
- **Key ist neu** → neues Element, wird erzeugt
- **Key fehlt jetzt** → Element wurde entfernt, wird abgebaut
- **Key an anderer Position** → dasselbe Element, nur verschoben — der DOM-Knoten und der **State** wandern mit

Der letzte Punkt ist der wichtigste und der Grund, warum Keys mehr sind als eine Optimierung: **Am Key hängt der State.** Behält ein Eintrag seinen Key, behält er seinen Zustand — den Text in seinem Eingabefeld, ob er aufgeklappt ist, den Fokus. Ändert sich der Key, wirft React die alte Instanz weg und baut eine neue: Zustand verloren.

Anforderungen an einen Key:

- **eindeutig unter Geschwistern** (nicht global)
- **stabil über die Zeit** — derselbe Eintrag hat bei jedem Render denselben Key
- **aus den Daten**, nicht beim Rendern erzeugt. `key={Math.random()}` oder `key={crypto.randomUUID()}` im Render ist der schlimmste Fall: Jeder Render erzeugt neue Keys, React hält alles für neu und baut die gesamte Liste jedes Mal ab und wieder auf.

Fehlt der Key ganz, warnt React in der Konsole und fällt auf die Position zurück — also auf das Verhalten von Frage 5.3.

### 5.3 Warum der Index als Key meistens falsch ist

Deine Antwort — „weil dieser nicht statisch ist" — war richtig in der Richtung, aber die Frage verlangte ein **konkretes Szenario**, und genau daran hängt, ob die Antwort im Gespräch trägt. Also hier das Szenario zum Mitnehmen:

Eine Liste mit drei Produkten, jedes mit einem Eingabefeld für einen Wunschpreis:

```jsx
{produkte.map((p, i) => (
  <li key={i}>
    {p.name} <input type="number" placeholder="Wunschpreis" />
  </li>
))}
```

| | Index | Produkt | Eingabe |
|---|---|---|---|
| vorher | 0 | Kajak | *(leer)* |
| | 1 | Kanu | **99** |
| | 2 | Floß | *(leer)* |

Jetzt löschst du **Kajak**. Das Array ist nun `[Kanu, Floß]`, und die Indizes rutschen nach: Kanu hat Index 0, Floß Index 1.

React vergleicht nach Key. Key `0` war vorher Kajak und ist jetzt Kanu — für React ist das **dasselbe Element mit geändertem Text**. Also behält es den DOM-Knoten samt dessen Zustand und tauscht nur die Beschriftung aus.

| | Index | Produkt | Eingabe |
|---|---|---|---|
| nachher | 0 | Kanu | *(leer)* ← Kajaks leeres Feld |
| | 1 | Floß | **99** ← Kanus 99 ist hier gelandet |

**Die 99 steht jetzt beim falschen Produkt.** Nichts stürzt ab, nichts wird geloggt — die Daten sind einfach verrutscht. Mit `key={p.id}` wäre Kajak verschwunden und Kanu hätte seine 99 behalten.

Dasselbe passiert mit Checkboxen, Fokus, Animationen, aufgeklappten Bereichen und dem State jeder Kindkomponente.

**Wann der Index in Ordnung ist** — auch das ist eine gute Gesprächsantwort, weil sie zeigt, dass du die Regel verstanden hast und nicht nur auswendig kannst. Alle drei Bedingungen müssen gelten:

1. Die Liste wird nie umsortiert oder gefiltert.
2. Es wird nie etwas eingefügt oder entfernt außer am Ende.
3. Die Einträge haben keinen eigenen Zustand.

Also: statische Listen. Bei allem, was aus einer API kommt und gefiltert wird — deinem Fall — nie.

### 5.4 Der Key in deinem Dashboard

„Ich gebe ihnen eine id" — richtig, aber die entscheidende Nachfrage lautet *woher*. Und die Antwort darf nicht „ich erzeuge eine" sein:

- **Richtig:** Die ID kommt **aus der API-Antwort**. Deine Produkte haben in der Datenbank einen Primärschlüssel, der in der Pydantic-Response mitkommt. `key={produkt.id}` — stabil, eindeutig, unabhängig von Sortierung und Filterung. Nachsehen kannst du das in `http://localhost:8000/docs`.
- **Falsch:** beim Rendern eine ID erzeugen. Das verletzt die Stabilität *und* die Reinheit ([[#6. Reinheit von Komponenten|Abschnitt 6]]) — `Math.random()` im Render macht die Komponente nichtdeterministisch.
- **Falls eine Entität wirklich keinen Schlüssel hat:** ein fachlicher zusammengesetzter Schlüssel. Bei deinen Kapazitätszeilen wäre das etwa `` key={`${zeile.produktId}-${zeile.datum}`} `` — das ist genau der Grain, den du in [[Documentation/Traineeship/Skalierbarkeit & ETL/2.2 OLAP Datenmodellierung & Datawarehousing/2.2 OLAP Datenmodellierung & Datawarehousing - Vertiefung|Kapitel 2.2]] modelliert hast. Derselbe Gedanke, anderer Kontext.

## 6. Reinheit von Komponenten

### 6.1 Was „rein" bedeutet

Deine Antwort war richtig und vollständig: keine Seiteneffekte, deterministisch — und das Gegenbeispiel mit der veränderten externen Variable ist genau das kanonische.

Ausformuliert gelten zwei Regeln:

1. **Gleiche Eingaben, gleiche Ausgabe.** Dieselben Props und derselbe State ergeben dasselbe Ergebnis.
2. **Nichts verändern, was vor dem Aufruf schon existierte.** Keine Variablen außerhalb, keine Props, keinen State, kein DOM.

```jsx
let gesamt = 0

function Zeile({ betrag }) {
  gesamt += betrag              // ❌ verändert etwas von außerhalb
  return <li>{gesamt}</li>      // Ergebnis hängt davon ab, wie oft gerendert wurde
}
```

Innerhalb des Aufrufs erzeugte Dinge zu ändern ist dagegen völlig in Ordnung — **lokale Mutation**:

```jsx
function Liste({ produkte }) {
  const zeilen = []                    // hier entstanden
  for (const p of produkte) zeilen.push(<li key={p.id}>{p.name}</li>)   // ✅ erlaubt
  return <ul>{zeilen}</ul>
}
```

Weitere typische Verstöße: `Math.random()` oder `Date.now()` im Render, ein `fetch` im Komponentenkörper, `document.title = …`, das Schreiben in ein Prop-Objekt ([[#3.2 Warum Props unveränderlich sind|3.2]]), das Aufrufen einer State-Setter-Funktion während des Renderns.

### 6.2 Was React dadurch gewinnt

„Macht auswerten viel leichter" ist als Instinkt richtig, aber im Gespräch zu dünn — auf so eine Antwort kommt sofort „inwiefern?". Hier die konkreten Gewinne:

- **React darf jederzeit rendern, beliebig oft.** Wenn ein Aufruf nichts verändert, ist ein zusätzlicher Aufruf folgenlos. Darauf beruht die gesamte Strategie, bei Bedarf neu zu rendern.
- **React darf Rendern auch *auslassen*.** Haben sich Props und State nicht geändert, muss das Ergebnis dasselbe sein — also kann React das vorherige wiederverwenden. Das ist die Grundlage von `memo` und in React 19 des Compilers, der solche Optimierungen automatisch einbaut.
- **Rendern ist unterbrechbar.** React kann mit dem Rendern beginnen, abbrechen, weil etwas Wichtigeres passiert, und später neu anfangen. Mit Seiteneffekten wäre ein halb gerenderter Baum ein halb ausgeführter Nebeneffekt — nicht reparierbar.
- **Dasselbe Ergebnis in verschiedenen Umgebungen.** Auf dem Server (SSR) gibt es kein DOM. Eine reine Komponente läuft trotzdem.
- **StrictMode kann Fehler aufdecken.** Im Development ruft React Komponenten absichtlich **zweimal** auf. Ist die Komponente rein, fällt das nicht auf. Ist sie es nicht, siehst du doppelte Zähler oder verdoppelte Einträge — und hast damit einen Bug gefunden, der in Produktion sonst zufällig auftauchen würde. Dieses Doppelte ist kein Fehler von React, sondern ein eingebauter Test. Du wirst es in Block 3 bei Effects wiedersehen.

Die Kurzfassung fürs Gespräch: *„Reinheit ist der Vertrag, der es React erlaubt, das Rendern selbst zu planen — öfter, seltener, unterbrochen oder woanders."*

### 6.3 Wohin Seiteneffekte gehören

„In die äußere Schicht" beschreibt die richtige Intuition in Backend-Vokabular. In React heißen die Orte konkret, und die Reihenfolge ist eine Rangfolge:

**1. In einen Event-Handler — der Normalfall.** Alles, was als Reaktion auf eine Nutzerhandlung passiert: speichern, absenden, navigieren, Daten ändern.

```jsx
<button onClick={() => starteLauf()}>Preislauf starten</button>
```

Event-Handler laufen *nach* dem Rendern und müssen nicht rein sein. Das ist der eigentliche Platz für Seiteneffekte — und die Antwort, die im Interview am meisten zeigt, weil die meisten sofort „useEffect" sagen.

**2. In einen Effect — nur wenn es sich nicht vermeiden lässt.** Für Synchronisation mit etwas außerhalb von React, die durch das *Anzeigen* der Komponente ausgelöst wird und nicht durch eine Handlung: ein Abonnement öffnen, einen Timer starten, einen Chat verbinden.

**3. Gar nicht — oft die beste Antwort.** Viele vermeintliche Effekte sind in Wahrheit abgeleitete Werte, die man einfach während des Renderns berechnet. Das ist das Thema von „You Might Not Need an Effect" in Block 3 und von [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 7 — Filtern ohne zweiten State|Schritt 7]] deines Projekts.

Merksatz für morgen: **Erst Event-Handler, dann gar nicht, dann Effect.** Die meisten React-Bugs entstehen dadurch, dass diese Reihenfolge umgedreht wird.

## 7. Render und Commit — was React eigentlich tut

Dieser Abschnitt war der schwächste (zwei übersprungen, einer falsch) und ist zugleich der, aus dem die Tier-2-Frage *„Was passiert, wenn sich State ändert?"* kommt. Lies ihn morgen früh noch einmal.

### 7.1 Die drei Phasen

Die Analogie aus der Doku: React ist der Kellner, der Bestellungen aufnimmt und in die Küche bringt.

**1. Trigger — jemand bestellt.** Zwei Auslöser, und nur diese zwei:

- der **erste Render** beim Start der Anwendung (`createRoot(…).render(<App />)`)
- eine **State-Änderung** in dieser Komponente oder in einer ihrer Vorfahren

**2. Render — die Küche kocht.** React ruft deine Komponentenfunktion auf und bekommt ein Element zurück. Enthält es weitere Komponenten, ruft React auch diese auf — und so weiter, rekursiv durch den Baum, bis nur noch DOM-Elemente übrig sind. Das Ergebnis ist ein vollständiger Baum aus Beschreibungen.

**Wichtig: In dieser Phase passiert nichts am Bildschirm.** Es wird nur gerechnet. Deshalb muss sie rein sein — und deshalb darf React sie abbrechen und neu starten.

Beim ersten Render wird der ganze Baum aufgebaut. Bei jedem weiteren vergleicht React den neuen Baum mit dem alten und ermittelt die Unterschiede — das ist die **Reconciliation** aus [[#7.3 Virtual DOM und Reconciliation|7.3]].

**3. Commit — der Kellner serviert.** Jetzt fasst React das echte DOM an, und zwar **nur an den Stellen, die sich unterscheiden**. Beim ersten Mal per `appendChild` für alles; danach so wenig wie möglich — oft nur ein einzelner geänderter Textknoten. Anschließend malt der Browser neu (*Paint*) und die Effects laufen.

> [!important] Der Satz, der die ganze Frage beantwortet
> *„State ändern → React ruft die betroffenen Komponenten neu auf → es vergleicht das Ergebnis mit dem vorherigen → es ändert am echten DOM nur den Unterschied → der Browser zeichnet neu."*
>
> Das ist die komplette Antwort auf eine der wahrscheinlichsten Fragen des Gesprächs. Sag sie einmal laut.

Der entscheidende Punkt daran: **Ein Re-Render bedeutet nicht, dass das DOM neu gebaut wird.** „React rendert neu" heißt zunächst nur „React ruft deine Funktion erneut auf". Ob daraus eine DOM-Änderung wird, entscheidet der Vergleich. Ändert sich nichts, passiert im Commit nichts — sichtbar daran, dass ein Eingabefeld seinen Fokus und seinen Text behält, obwohl die Komponente hundertmal neu gerendert wurde.

### 7.2 Wer deine Komponente aufruft

> [!warning] Korrektur — die Antwort ist kurz und wichtig
> **React ruft sie auf. Niemals du.**
>
> Das ist keine Nebensächlichkeit, sondern der Grund, warum React ein Framework ist und keine Bibliothek im engen Sinn: Du gibst die Kontrolle ab. Du schreibst `<ProduktKarte produkt={p} />` — das ist eine *Beschreibung*, kein Aufruf. Wann und wie oft `ProduktKarte(…)` tatsächlich ausgeführt wird, entscheidet React.

**Wie oft?** Mindestens einmal beim ersten Render, und danach bei jeder State-Änderung in ihr selbst oder in einer Vorfahrenkomponente. Im Development zusätzlich doppelt durch StrictMode ([[#6.2 Was React dadurch gewinnt|6.2]]). Die ehrliche Antwort ist: **unbestimmt oft — und genau deshalb muss sie rein sein.**

Was daraus folgt, und was im Gespräch gut klingt: *„Ich rufe eine Komponente nie selbst auf. `ProduktKarte(produkt)` direkt aufzurufen würde zwar ein Element zurückgeben, aber React wüsste nichts von einer Komponenteninstanz — es gäbe keinen State und keine Hooks. Der Unterschied zwischen `<ProduktKarte />` und `ProduktKarte()` ist der zwischen ‚React, rendere das' und ‚führ mal diese Funktion aus'."*

### 7.3 Virtual DOM und Reconciliation

Nicht beantwortet — und eine der wahrscheinlichsten Interviewfragen überhaupt, besonders von erfahreneren Entwicklern. Hier die Antwort in drei Teilen.

**Der Virtual DOM** ist die Baumstruktur aus React-Elementen im Speicher — also genau die Objekte aus [[#2.4 Was mit JSX wirklich passiert|2.4]]. Eine leichtgewichtige Beschreibung des gewünschten Zustands der Oberfläche, als reines JavaScript, ohne Verbindung zum Browser.

**Warum es ihn gibt:** DOM-Operationen sind teuer. Jede Änderung kann Layout-Neuberechnung und Neuzeichnen auslösen, und wer das unkoordiniert hundertfach tut, macht eine Oberfläche zäh. Objekte im Speicher zu vergleichen ist dagegen billig. React arbeitet deshalb auf der Kopie und fasst das echte DOM erst am Ende an — einmal, gebündelt, minimal.

**Reconciliation** ist der Vergleich: React hält zwei Bäume nebeneinander — den vorherigen und den neuen — und ermittelt die kleinste Menge an DOM-Operationen, die vom einen zum anderen führt. Die Regeln dabei sind bewusst einfach gehalten, weil ein allgemeiner Baumvergleich zu langsam wäre:

- **Anderer Typ an derselben Stelle** (`<div>` wird zu `<span>`, `Profil` wird zu `Einstellungen`) → alter Teilbaum wird komplett abgebaut, neuer aufgebaut, **State verworfen**.
- **Gleicher Typ** → Element bleibt, React aktualisiert nur die geänderten Attribute, **State bleibt**.
- **Kinderlisten** → über `key` zugeordnet ([[#5.2 Wozu key dient — und an wen es sich richtet|5.2]]). Ohne Key nach Position.

Damit schließt sich der Kreis zu den Keys: Sie sind der Hinweis, den du der Reconciliation gibst, damit sie nicht nach Position raten muss.

> [!note] Warum der Begriff in der heutigen Doku kaum noch vorkommt
> Das React-Team vermeidet „Virtual DOM" inzwischen aus zwei Gründen. Erstens ist er irreführend: Es wird nichts „virtualisiert", es ist schlicht eine Objektbeschreibung. Zweitens ist er zu eng — React rendert auch dorthin, wo es gar kein DOM gibt (React Native, Server). Die heutige Sprachregelung lautet „React Elements" und „Reconciliation"; das interne Modell heißt seit React 16 **Fiber**.
>
> **Im Gespräch trotzdem beides bedienen.** Eine starke Antwort: *„Gemeint ist die Element-Baumstruktur im Speicher, die React mit der vorherigen vergleicht, um minimal am DOM zu arbeiten. Das React-Team nennt das heute lieber Reconciliation, weil ‚Virtual DOM' suggeriert, es gäbe ein zweites DOM — tatsächlich sind es einfache JavaScript-Objekte."* Das beantwortet die Frage und zeigt zugleich, dass du auf aktuellem Stand bist.

### 7.4 Deklarativ vs. imperativ

Deine Definition war richtig — „man beschreibt das Ziel und das Framework entscheidet den Weg" gegen „man beschreibt alle Schritte". Was fehlte, war das verlangte **konkrete Beispiel**, und genau das macht den Unterschied zwischen einer auswendig gelernten und einer verstandenen Antwort. Also hier beides nebeneinander:

**Imperativ** — jeder Zustandsübergang von Hand:

```js
const button = document.getElementById('absenden')
const status = document.getElementById('status')

function starteLaden() {
  button.disabled = true
  button.textContent = 'Lädt …'
  status.classList.add('versteckt')
}

function beendeLaden(fehler) {
  button.disabled = false
  button.textContent = 'Absenden'
  if (fehler) {
    status.textContent = fehler
    status.classList.remove('versteckt')
  }
}
```

**Deklarativ** — ein Ausdruck, der für jeden Zustand gilt:

```jsx
function Absenden({ laedt, fehler, onKlick }) {
  return (
    <>
      <button disabled={laedt} onClick={onKlick}>
        {laedt ? 'Lädt …' : 'Absenden'}
      </button>
      {fehler && <p className="fehler">{fehler}</p>}
    </>
  )
}
```

Was man daran sieht — und das ist der Teil, den man erzählen sollte:

- Imperativ musst du **jeden Übergang** schreiben: von normal nach lädt, von lädt nach fertig, von lädt nach Fehler, von Fehler nach lädt. Bei fünf Zustandsgrößen sind das schnell zwanzig Pfade, und einen vergisst man immer — das ist der Button, der nach einem Fehler dauerhaft deaktiviert bleibt.
- Deklarativ beschreibst du nur **die Zustände selbst**. Die Übergänge ergeben sich; React rechnet den Unterschied aus.
- Der imperative Code ist an eine bestimmte Stelle im DOM gebunden (`getElementById`). Der deklarative ist eine Funktion, die man beliebig oft verwenden kann.

Die Ein-Satz-Fassung: *„Imperativ beschreibe ich die Übergänge, deklarativ beschreibe ich die Zustände — und überlasse die Übergänge React."*

## 8. Thinking in React

### 8.1 Die fünf Schritte

Vollständig und in der richtigen Reihenfolge beantwortet — der beste Einzelpunkt dieses Blocks. Zum Festigen mit je einem Satz:

1. **Die Oberfläche in eine Komponentenhierarchie zerlegen.** Ein Entwurf oder Screenshot, Kästen drumherum. Das Kriterium ist dasselbe wie bei Funktionen und Klassen: **eine Verantwortung pro Komponente**. Oft spiegelt die Komponentenhierarchie die Struktur der Daten — was kein Zufall ist, weil beide dasselbe Fachmodell abbilden.
2. **Eine statische Version bauen.** Komponenten, die Daten über Props bekommen und darstellen — **ohne jeden State**. Das trennt das stupide Tippen vom eigentlichen Nachdenken.
3. **Die minimale State-Darstellung finden.** Die kleinste Menge an Werten, aus der sich alles andere berechnen lässt (Kriterien in 8.2).
4. **Bestimmen, wo der State wohnt.** Für jeden State-Wert: Welche Komponenten benutzen ihn? Ihr **nächster gemeinsamer Vorfahr** bekommt ihn — oder eine Komponente darüber.
5. **Den umgekehrten Datenfluss ergänzen.** Callback-Props, damit Kinder den State der Eltern ändern lassen können ([[#3.4 Einseitiger Datenfluss|3.4]]).

Warum diese Liste so wertvoll ist: Sie ist eine fertige Antwort auf *„Wie gehen Sie an eine neue Oberfläche heran?"* — eine Frage, die in Konzeptgesprächen sehr häufig kommt und bei der die meisten improvisieren.

### 8.2 Die Kriterien für State

Ebenfalls vollständig beantwortet. Ein Wert ist **kein** State, wenn mindestens eine der drei Fragen mit Ja beantwortet wird:

| Gegenfrage | Wenn ja, dann … |
|---|---|
| Bleibt er über die Zeit unverändert? | Konstante — einfach hinschreiben |
| Kommt er per Props von oben? | gehört den Eltern, nicht dir |
| Lässt er sich aus vorhandenem State oder Props **berechnen**? | während des Renderns ableiten |

Die dritte ist die folgenreichste und der häufigste Anfängerfehler. Klassiker: Neben `produkte` und `suchbegriff` noch `gefilterteProdukte` in den State zu legen. Die gefilterte Liste ist ableitbar — sie gehört nicht in den State, sondern in eine Zeile im Render:

```jsx
const gefiltert = produkte.filter(p => p.name.includes(suchbegriff))
```

Warum das kein Stilthema ist: **Zwei State-Werte, die dasselbe ausdrücken, können auseinanderlaufen.** Vergisst man an einer Stelle das Nachziehen, zeigt die Oberfläche einen Zustand an, den es nicht gibt. Ein abgeleiteter Wert kann das per Konstruktion nicht.

Das ist wörtlich dieselbe Überlegung wie bei der Normalisierung in [[Documentation/Traineeship/Skalierbarkeit & ETL/2.2 OLAP Datenmodellierung & Datawarehousing/2.2 OLAP Datenmodellierung & Datawarehousing - Vertiefung|Kapitel 2.2]]: redundant gespeicherte Information ist eine Inkonsistenz in Wartestellung. State ist die Datenbank deiner Oberfläche, und er will normalisiert sein. **Diesen Bogen solltest du im Gespräch schlagen** — er zeigt, dass du nicht React auswendig gelernt, sondern ein bekanntes Prinzip wiedererkannt hast.

Hier stand „ist mir jetzt zu nervig". Nachvollziehbar am Ende eines dichten Tages — aber ausgerechnet dieser Schritt ist der, der im Gespräch am meisten wert ist: Er ist die Grundlage deiner Drei-Minuten-Story und das, woran du morgen beim Bauen entlanggehst.

Deshalb hier ein **Entwurf, den du prüfen sollst** — nicht als Vorgabe. Widersprich, wo du es anders siehst; das ist der Lerneffekt.

**Schritt 1 — Hierarchie**

```

├─ Kopfzeile
├─ Aktionsleiste        (Preislauf starten, Status anzeigen)
├─ ProduktPanel
│  ├─ Suchfeld
```

**Schritt 2 — Statische Version.** Alles mit fest verdrahteten Beispieldaten, kein `useState`, kein `fetch`. Das sind die Schritte 1–2 des [[Pricing-Dashboard Plan & Syntax-Tutorial|Projektplans]].

**Schritt 3 — Minimaler State.** Kandidaten, jeder gegen die drei Fragen geprüft:

| Wert | State? | Begründung |
|---|---|---|
| `produkte` (von der API) | **ja** | ändert sich über die Zeit, kommt nicht als Prop, nicht ableitbar |
| `suchbegriff` | **ja** | reiner UI-Zustand, ändert sich bei jedem Tastendruck |
| `ausgewaehlteProduktId` | **ja** | reiner UI-Zustand |
| `empfehlungen` | **ja** | eigene Serverdaten, hängen an der Auswahl |
| `laufId`, `laufStatus` | **ja** | Fortschritt des Preislaufs |
| `laedt`, `fehler` | **ja** | je Ladevorgang; wandern später in `useApi` |
| ~~`gefilterteProdukte`~~ | **nein** | aus `produkte` + `suchbegriff` ableitbar → [[Pricing-Dashboard Plan & Syntax-Tutorial#Schritt 7 — Filtern ohne zweiten State\|Schritt 7]] |
| ~~`ausgewaehltesProdukt`~~ | **nein** | `produkte.find(p => p.id === ausgewaehlteProduktId)` |
| ~~`anzahlTreffer`~~ | **nein** | `gefiltert.length` |

Die drei durchgestrichenen sind der ganze Punkt der Übung — jeder davon wäre eine Inkonsistenz in Wartestellung.

**Schritt 4 — Wo der State wohnt**

| State | Besitzer | Warum |
|---|---|---|
| `produkte` | `App` | `ProduktPanel` zeigt sie, `DetailPanel` braucht den Namen zum Ausgewählten → nächster gemeinsamer Vorfahr |
| `suchbegriff` | `ProduktPanel` | nur `Suchfeld` und `ProduktListe` brauchen ihn — nicht höher als nötig |
| `ausgewaehlteProduktId` | `App` | `ProduktListe` setzt sie (Markierung), `DetailPanel` liest sie |
| `empfehlungen`, `laedt`, `fehler` | `DetailPanel` | niemand sonst braucht sie |
| `laufId`, `laufStatus` | `App` | `Aktionsleiste` zeigt den Status, `DetailPanel` muss nach Abschluss neu laden |

Die Regel dahinter: **so tief wie möglich, so hoch wie nötig.** State, den nur eine Komponente braucht, gehört in diese Komponente — alles andere macht die App unnötig verflochten.

**Schritt 5 — Umgekehrter Datenfluss**

- `Suchfeld` bekommt `wert` und `onWertAendern` → kontrollierte Komponente (Block 2)
- `ProduktZeile` bekommt `onAuswahl` und meldet ihre ID
- `Aktionsleiste` bekommt `onLaufStarten`

# n-tier Architektur

## Warum das Thema am Anfang steht

Der Leitfaden stellt in der [[1.5 REST APIs & Layered Architecture - Leitfaden#Motivation|Motivation]] fest: Das Projekt besteht aktuell im Wesentlichen aus zwei Schichten — Repository (Datenhaltung) und Business Logic (Kernverhalten). Die REST API kommt als **dritte** Schicht obendrauf. Bevor man sie einbaut, muss klar sein, *wohin* sie gehört und was sie **nicht** tun darf — sonst entsteht genau das, was man in der Praxis am häufigsten sieht: ein Controller, der SQL-Abfragen absetzt und Preisformeln rechnet, und eine Anwendung, die ohne HTTP-Server nicht mehr testbar ist.

Der eigentliche Punkt einer Schichtenarchitektur ist nicht „Ordnung im Ordnerbaum", sondern **Abhängigkeitsrichtung**. Eine Schicht ist erst dann eine Schicht, wenn man sagen kann, wen sie kennen darf und wen nicht.

## Layer vs. Tier — der Unterschied, der im Namen steckt

Die Begriffe werden ständig vermischt, meinen aber zwei verschiedene Dinge:

| Begriff | Bedeutung | Wo sichtbar |
|---|---|---|
| **Layer** (Schicht) | **Logische** Aufteilung des Codes | Pakete, Module, Namespaces |
| **Tier** (Rang/Stufe) | **Physische** Verteilung auf Maschinen/Prozesse | Deployment, Server, Container |

„n-tier" beschreibt also streng genommen das *Deployment*: 1-Tier = alles auf einer Maschine, 2-Tier = Client + Datenbankserver, 3-Tier = Client + Applikationsserver + Datenbankserver. „n-layer" beschreibt den *Code*.

Beides fällt oft zusammen, muss es aber nicht:

- Unsere Anwendung hat **drei Layer** (gleich mehr dazu), läuft aber als **ein** Prozess gegen eine Postgres-Instanz im Docker-Container — also faktisch 2 Tiers.
- Umgekehrt kann ein einziger Layer über mehrere Tiers verteilt sein (z. B. drei Instanzen desselben API-Service hinter einem Load Balancer).

> [!tip] Merksatz
> **Layer = wie der Code aufgeteilt ist. Tier = auf wie vielen Maschinen er läuft.**
> Layer sind eine Entwurfsentscheidung, Tiers eine Betriebsentscheidung.

Im Alltag (und im Leitfaden) meint „n-tier Architektur" meistens trotzdem das klassische Schichtenmodell — man sollte den Unterschied nur kennen, wenn er in einem Gespräch aufkommt.

## Die klassischen Schichten

Das kanonische Modell (Fowler, *Patterns of Enterprise Application Architecture*) kennt drei Schichten:

```
┌─────────────────────────────────────┐
│  Presentation Layer                 │  ← REST-Controller, CLI, UI
│  nimmt Anfragen entgegen, gibt      │    "Wie redet die Außenwelt mit uns?"
│  Antworten zurück                   │
├─────────────────────────────────────┤
│  Business/Domain Layer              │  ← Regeln, Berechnungen, Abläufe
│  weiß, WAS fachlich passieren soll  │    "Was ist die Anwendung fachlich?"
├─────────────────────────────────────┤
│  Data Access/Persistence Layer      │  ← Repositories, ORM, SQL, Dateien
│  weiß, WIE Daten gespeichert werden │    "Wo liegen die Daten?"
└─────────────────────────────────────┘
              ↓ Abhängigkeit zeigt nach unten
```

Die eiserne Regel: **Abhängigkeiten zeigen nach unten, niemals nach oben.** Presentation kennt Business, Business kennt Persistence. Umgekehrt nie.

Was das konkret verbietet:

```python
# ❌ Persistence-Schicht ruft Presentation-Schicht auf
class PriceRepository:
    def save(self, rec):
        ...
        from ..api.routes import notify_client   # Abhängigkeit nach OBEN
        notify_client("gespeichert")
```

Warum das so hart ist: Sobald eine untere Schicht eine obere kennt, ist sie ohne diese nicht mehr benutzbar, nicht mehr isoliert testbar, und die Zyklen machen jedes Refactoring zur Kettenreaktion. Ein Repository, das den HTTP-Layer importiert, kann man nicht mehr in einem Batch-Skript verwenden.

Zusätzlich zu diesen drei Schichten trifft man häufig auf eine **Service-** oder **Application-Schicht** zwischen Presentation und Domain: Sie orchestriert Abläufe („lade Daten, berechne, schreibe weg"), enthält aber selbst keine fachlichen Regeln. Genau diese Rolle spielt in unserem Projekt `PricingApp`.

## Strict Layering vs. Layer Bridging

Eine der Kontrollfragen. Die beiden Begriffe beantworten die Frage: **Darf eine Schicht eine andere überspringen?**

**Strict Layering (geschlossene Schichten):** Jede Schicht darf ausschließlich mit der *direkt* darunterliegenden reden.

```
Presentation → Business → Persistence     ✅
Presentation ─────────────→ Persistence   ❌ nicht erlaubt
```

**Layer Bridging / Relaxed Layering (offene Schichten):** Eine Schicht darf auch tiefer liegende Schichten direkt aufrufen, also eine überspringen.

```
Presentation → Business → Persistence     ✅
Presentation ─────────────→ Persistence   ✅ auch erlaubt
```

| | Strict | Bridging |
|---|---|---|
| **Vorteil** | Maximale Entkopplung; man kann eine Schicht austauschen, ohne dass es die übernächste merkt | Weniger Boilerplate; keine Methoden, die nur durchreichen („Pass-Through"-/Sinkhole-Layer) |
| **Nachteil** | Viel Durchreicherei; ein simples „gib mir alle Datensätze" braucht in jeder Schicht eine Methode | Die übersprungene Schicht kann Regeln nicht mehr garantieren; Änderungen an der Persistenz schlagen bis in die API durch |

**Praxis:** Die meisten Teams fahren strict als Standard und erlauben Bridging bewusst und begründet für reine Lesepfade (typischer Fall: eine Report-/Listenansicht, bei der die Business-Schicht ohnehin nichts zu tun hätte). Wichtig ist, dass es eine *Entscheidung* ist und nicht schleichend passiert — sonst hat man am Ende keine Schichten mehr, sondern nur noch Ordner.

## Die Kontrollfragen des Leitfadens

*Die Antworten sind eingeklappt — erst selbst beantworten, dann aufklappen.*

> [!question]- Sollte eine tiefere Schicht die Dienste einer höheren Schicht aufrufen?
> **Nein.** Das ist die zentrale Regel der Schichtenarchitektur: Abhängigkeiten zeigen nur nach unten. Ein Aufruf nach oben erzeugt einen Zyklus, macht die untere Schicht ohne die obere unbenutzbar und untestbar und zerstört die Austauschbarkeit.
>
> Wenn eine untere Schicht eine obere „informieren" muss, dreht man die Abhängigkeit um, statt sie zuzulassen — per **Dependency Inversion**: Die untere Schicht definiert ein Interface (Callback, Event, Protocol), die obere implementiert es und reicht es hinein. Genau dieses Muster steckt schon in unserem Projekt in `ports.py`.

> [!question]- Was ist der Unterschied zwischen Strict Layering und Layer Bridging?
> Siehe Abschnitt oben: Bei **Strict Layering** darf jede Schicht nur die unmittelbar darunterliegende aufrufen; bei **Layer Bridging** darf sie Schichten überspringen und direkt auf tiefere zugreifen. Strict ist entkoppelter, aber geschwätziger; Bridging ist schlanker, gibt aber die Kontrolle der übersprungenen Schicht auf.

> [!question]- Welche Vor- und Nachteile treten bei der Schichtenarchitektur auf? Was sind Usecases, die dafür und dagegen sprechen?
> **Vorteile**
> - **Austauschbarkeit:** CSV-Quelle → Datenbank-Quelle, ohne die Fachlogik anzufassen (im Projekt bereits erlebt, siehe [[1.2 Relationale Datenbanken & ORM - Vertiefung|1.2]]).
> - **Testbarkeit:** Jede Schicht ist einzeln testbar, die Nachbarschicht wird gemockt — genau das, was in [[1.3 Testing mit PyTest - Vertiefung|1.3]] die Test-Suite überhaupt erst ermöglicht hat.
> - **Verständlichkeit & Arbeitsteilung:** Man weiß, wo man suchen muss; mehrere Leute können parallel an verschiedenen Schichten arbeiten.
> - **Wiederverwendung:** Dieselbe Business-Schicht bedient REST API, CLI und Batch-Job.
>
> **Nachteile**
> - **Overhead/Boilerplate:** Jede neue Funktion muss durch alle Schichten „durchgereicht" werden.
> - **Sinkhole-Anti-Pattern:** Schichten, die eine Anfrage nur weiterleiten, ohne etwas beizutragen.
> - **Performance:** Mehr Indirektion, teils mehrfaches Mapping derselben Daten (Entity → Domain-Objekt → DTO).
> - **Kein Skalierungsmodell:** Layer sagen nichts über Deployment; ein geschichteter Monolith bleibt ein Monolith.
>
> **Dafür:** klassische Business-/CRUD-Anwendungen mit fachlichen Regeln, langlebige Systeme, Teams > 1 Person, wechselnde Datenquellen oder Frontends.
> **Dagegen:** kleine Skripte und Prototypen (die Schichten kosten mehr, als sie bringen), sehr latenzkritische Pfade, und Systeme, deren Komplexität nicht fachlich, sondern rein technisch ist (z. B. eine reine Datenpipeline ohne Regeln).

> [!question]- Welche Schicht ist am schwierigsten umzubauen und generiert dadurch bei Änderungen den größten Aufwand und die meisten Kosten?
> Die **Datenschicht** — genauer: das Datenmodell/Schema.
>
> Gründe: Daten sind **persistent** und überleben jeden Code-Release. Ein Schema-Umbau bedeutet Migration von Bestandsdaten, meist unter Verfügbarkeitsdruck und ohne die Möglichkeit, „einfach zurückzurollen". Außerdem hängt *alles* daran: Jede darüberliegende Schicht kennt die Daten in irgendeiner Form, und häufig greifen auch fremde Systeme (Reports, BI-Tools, andere Teams) direkt auf dieselbe Datenbank zu — die kann man nicht mitdeployen.
>
> Als Data Engineer ist das die berufsrelevante Variante der Frage: Der Presentation Layer wird ständig neu gebaut, das Schema trägt man jahrelang mit sich.

> [!question]- Warum trennt man zwischen der Serviceschicht und der Datenzugriffsschicht? Welche Vorteile ergeben sich daraus?
> Weil es zwei verschiedene Arten von Wissen sind: Die **Serviceschicht** weiß, *was* fachlich passieren soll (Regeln, Abläufe, Reihenfolge), die **Datenzugriffsschicht** weiß, *wie* Daten geholt und gespeichert werden (SQL, ORM, Dateiformat, Verbindungen, Transaktionen).
>
> Vorteile:
> - **Austauschbarkeit der Persistenz:** CSV, Postgres, REST-Fremdsystem — die Fachlogik bleibt gleich.
> - **Testbarkeit:** Die Fachlogik lässt sich mit einem In-Memory-Fake testen, ohne laufende Datenbank (in unserer Test-Suite genau so gelöst).
> - **Keine Vermischung von Dialekten:** SQL-Details, Session-Handling und Lazy Loading verschmutzen die Regeln nicht.
> - **Ein Ort für technische Querschnittsthemen:** Retry, Transaktionen, Connection Pooling liegen gebündelt unten.
> - **Fachliche Regeln bleiben an einem Ort** und werden nicht über mehrere Repositories dupliziert.

## Bezug zum eigenen Projekt

Der Leitfaden verlangt als ersten Teil der Aufgabe eine **Analyse des Ist-Stands**. Grobe Einordnung von `src/pricing/` (Details gehören in den [[Umsetzungsstand (REST APIs & Layered Architecture)|Umsetzungsstand]]):

# Client/Server

## Warum das Stichwort hier steht

Layering beantwortet, wie der Code *innerhalb* eines Programms aufgeteilt ist. Client/Server beantwortet die Frage daneben: Was passiert, wenn zwischen zwei Teilen des Systems ein **Netzwerk** liegt?

Das ist genau der Sprung, den dieses Kapitel macht. Bisher wurde unsere Anwendung gestartet, lief durch und war fertig — ein einziger Prozess, der sich selbst aufruft. Mit einer REST API wird sie zu einem **Server**: einem Prozess, der wartet, bis jemand anders etwas will. Und dieses „jemand anders" ist ein fremder Prozess, oft auf einer fremden Maschine, geschrieben von fremden Leuten, der jederzeit verschwinden kann.

Der Kern des Stichworts ist deshalb: **Ein Methodenaufruf über das Netzwerk ist kein Methodenaufruf.** Er sieht im Code nur so aus.

## Die Grundidee

Client/Server ist ein Architekturstil mit einer **asymmetrischen Rollenverteilung**:

| | Client | Server |
|---|---|---|
| **Initiative** | Beginnt die Kommunikation | Wartet passiv auf Anfragen |
| **Wissen** | Muss die Adresse des Servers kennen | Kennt seine Clients nicht im Voraus |
| **Lebenszyklus** | Kommt und geht | Läuft dauerhaft |
| **Anzahl** | Viele | Einer (oder eine austauschbare Menge) |

Die Rollen sind an die **Interaktion** gebunden, nicht an die Maschine. Unser Pricing-Service ist Server gegenüber dem HTTP-Aufrufer und gleichzeitig Client gegenüber Postgres. Jedes nicht-triviale System ist beides — deshalb ist „ist das ein Client oder ein Server?" fast immer die falsche Frage; richtig ist „in welcher Beziehung?".

**Request/Response** ist das zugehörige Kommunikationsmuster: Der Client schickt eine Anfrage, der Server antwortet genau einmal, danach ist der Austausch vorbei. HTTP ist die bekannteste Umsetzung davon. Gegenmodelle, die es auch gibt (nur zur Einordnung): Publish/Subscribe, Message Queues, WebSockets für bidirektionale Verbindungen, Polling.

## Warum das Netzwerk alles ändert

Der wichtigste Teil dieses Stichworts, und der, den man in der Praxis schmerzhaft lernt. Ein lokaler Funktionsaufruf ist schnell, zuverlässig und lokal. Ein Netzwerkaufruf ist nichts davon:

| Lokaler Aufruf                                  | Netzwerkaufruf                                                                 |
| ----------------------------------------------- | ------------------------------------------------------------------------------ |
| Nanosekunden                                    | Millisekunden bis Sekunden (Faktor ~10⁶)                                       |
| Gelingt oder wirft eine Exception               | Kann **hängen** — man erfährt nie, ob er ankam                                 |
| Objekte werden per Referenz übergeben           | Daten müssen **serialisiert** werden (JSON) und verlieren dabei Typinformation |
| Kein Sicherheitsproblem                         | Jede Eingabe kommt von einem potenziellen Angreifer                            |
| Aufrufer und Aufgerufener sind dieselbe Version | Client und Server werden **unabhängig** deployt                                |

Der dritte Punkt in der zweiten Spalte ist der unangenehmste: Bei einem Timeout weiß der Client **nicht**, ob der Server die Anfrage nie erhalten hat, sie gerade noch verarbeitet, oder sie erfolgreich verarbeitet hat und nur die Antwort verloren ging. Alle drei Fälle sehen für ihn identisch aus. Genau daraus folgt später die praktische Bedeutung von **Idempotenz** — der Eigenschaft, dass ein wiederholter Aufruf dasselbe Ergebnis hat wie ein einzelner (Details beim Stichwort [[#Die 4 zentralen HTTP-Methoden in REST-Controllern]]).

> [!warning] Die „Fallacies of Distributed Computing"
> Eine klassische Liste (Peter Deutsch, Sun Microsystems) falscher Annahmen, die Entwickler beim Bau verteilter Systeme immer wieder treffen:
> 1. Das Netzwerk ist zuverlässig
> 2. Latenz ist null
> 3. Bandbreite ist unbegrenzt
> 4. Das Netzwerk ist sicher
> 5. Die Topologie ändert sich nicht
> 6. Es gibt genau einen Administrator
> 7. Transportkosten sind null
> 8. Das Netzwerk ist homogen
>
> Jede dieser Annahmen ist falsch, und jede von ihnen kostet irgendwann eine Nachtschicht. Merksatz: Wer eine API baut, baut ein verteiltes System — auch wenn beides auf demselben Laptop läuft.

## Statuslosigkeit (Stateless)

Eine Eigenschaft, die REST vom generischen Client/Server-Modell zusätzlich verlangt und die im nächsten Stichwort wieder auftaucht: **Der Server merkt sich zwischen zwei Anfragen nichts über den Client.** Jede Anfrage bringt alles mit, was zu ihrer Bearbeitung nötig ist.

```
# ❌ zustandsbehaftet — Server merkt sich "aktuelle Auswahl"
POST /select-unit/42
GET  /current-price          → Preis der "aktuell ausgewählten" Einheit

# ✅ zustandslos — jede Anfrage steht für sich
GET  /units/42/price
```

Warum das so wichtig ist:

- **Skalierbarkeit:** Jede Anfrage kann von einer beliebigen Serverinstanz beantwortet werden. Man stellt einfach eine zweite Instanz daneben. Bei zustandsbehafteten Servern bräuchte man „Sticky Sessions" und ein geteiltes Session-Backend.
- **Ausfallsicherheit:** Stirbt eine Instanz, geht keine Sitzung verloren.
- **Nachvollziehbarkeit:** Eine einzelne Anfrage im Log erklärt sich selbst — man muss nicht die Vorgeschichte kennen. (Direkter Bezug zu [[1.4 Logging & Exceptionhandling - Vertiefung|1.4]]: zustandslose Anfragen sind erheblich leichter zu debuggen.)
- **Testbarkeit:** Jeder Endpunkt ist einzeln testbar, ohne vorher eine Sitzung aufzubauen.

Wichtige Abgrenzung: Zustandslos heißt **nicht** „speichert nichts". Die Datenbank ist selbstverständlich zustandsbehaftet und soll es sein. Gemeint ist ausschließlich der **Sitzungszustand** des Clients — der gehört entweder in die Anfrage (Token, IDs) oder in die Datenbank, aber nicht in den Arbeitsspeicher des Servers.

## Thin vs. Fat Client

Die Frage, wie viel Arbeit auf welcher Seite passiert — historisch der eigentliche Streitpunkt des Client/Server-Modells:

- **Thin Client:** Der Client zeigt nur an, der Server rechnet. (Terminal am Mainframe; klassische serverseitig gerenderte Webseite.)
- **Fat/Rich Client:** Der Client hält Logik und ggf. Daten vor, der Server liefert nur Rohdaten. (Desktop-Anwendung; moderne Single-Page-App mit React.)

Für den Bau einer REST API folgt daraus eine Regel, die man ernst nehmen muss: **Der Server darf sich nie darauf verlassen, dass der Client sich korrekt verhält.** Validierung im Client ist Bedienkomfort, Validierung im Server ist Sicherheit. Jede Anfrage kann auch von `curl` kommen — mit beliebigem Inhalt. Deshalb wird die Request-Validierung im Server später ein eigenes Stichwort ([[#Validierung von Request/Response (Pydantic)]]) und keine Nebensache.

## Bezug zum eigenen Projekt

Was der Wechsel zum Server für `pricing` konkret bedeutet:

| Bisher (Batch) | Künftig (Server) |
|---|---|
| `main.py` läuft durch und endet | Prozess läuft dauerhaft und wartet |
| Eingaben stehen fest (CSV, DB) | Eingaben kommen von außen und sind **nicht vertrauenswürdig** |
| Ein Ablauf, seriell | Mehrere Anfragen, potenziell **gleichzeitig** |
| Fehler = Programm bricht ab, Traceback in der Konsole | Fehler = **eine** Anfrage scheitert mit passendem Statuscode, Server läuft weiter |
| Laufzeit egal | Antwortzeit ist Teil der Schnittstelle |

Besonders die letzten beiden Zeilen sind ein echter Umbau und kein reines Hinzufügen: Ein `raise` in `core/` darf künftig nicht mehr den Prozess beenden, sondern muss in eine HTTP-Antwort übersetzt werden — die Verbindung von [[1.4 Logging & Exceptionhandling - Vertiefung|Kapitel 1.4]] zu diesem Kapitel. Und `_compute()` lädt derzeit bei *jedem* Aufruf sämtliche Daten neu; als Batch-Job ist das egal, als HTTP-Endpunkt ist es ein Problem, sobald zwei Leute gleichzeitig anfragen.

# Softwarearchitektur

## Warum ein eigenes Stichwort für den Oberbegriff

Die bisherigen zwei Stichworte waren konkret: eine bestimmte Aufteilung (Layer) und eine bestimmte Rollenverteilung (Client/Server). Dieses Stichwort tritt einen Schritt zurück und fragt: **Was ist Architektur überhaupt — und wie unterscheidet sie sich von „normalem" Programmieren?**

Das ist keine akademische Frage. Sie entscheidet darüber, welche Entscheidungen du in Ruhe später treffen kannst und welche du **jetzt** treffen musst, weil sie später teuer werden. Genau das ist die Frage, die dich beim Einbau der REST API in dein Projekt erwartet.

## Was ist Softwarearchitektur?

Es gibt keine kanonische Definition — aber zwei sehr brauchbare.

**Martin Fowler (halb im Scherz, ganz im Ernst):**

> „Architecture is about the important stuff. Whatever that is."

Der Punkt dahinter ist ernst und besteht aus zwei Teilen:
1. **Architektur ist das gemeinsame Verständnis** der erfahrenen Entwickler vom Aufbau des Systems.
2. **Architektur ist das, was schwer zu ändern ist** — und man sollte versuchen, davon möglichst wenig zu haben.

Der zweite Teil ist das nützlichere Kriterium: *Wenn eine Entscheidung später nur mit großem Aufwand revidierbar ist, ist sie architektonisch.* Das Datenbankschema (siehe [[#n-tier Architektur]]) ist architektonisch. Der Name einer lokalen Variable ist es nicht.

**Richards & Ford** definieren Architektur über **vier Dimensionen** — das ist die praktisch brauchbarste Zerlegung:

| Dimension | Frage | Beispiel aus unserem Projekt |
|---|---|---|
| **Struktur** | Welcher Architekturstil? | Schichtenarchitektur mit Ports & Adapters |
| **Architekturmerkmale** | Welche „-ilities" muss das System erfüllen? | Testbarkeit, Austauschbarkeit der Datenquelle |
| **Architekturentscheidungen** | Welche Regeln gelten verbindlich? | „Der Controller kennt `adapters/` nicht" |
| **Entwurfsprinzipien** | Welche Leitlinien gelten als Empfehlung? | „Fachlogik gehört nach `core/`" |

Der Unterschied zwischen den letzten beiden ist wichtig: Eine **Entscheidung** ist eine harte Regel, gegen die man nicht verstoßen darf (ohne sie explizit zu ändern). Ein **Prinzip** ist eine Leitlinie, von der man begründet abweichen kann.

## Architektur vs. Entwurf (Design)

Beide beschäftigen sich mit Struktur, aber auf unterschiedlichen Ebenen und mit unterschiedlichen Kosten:

| | Architektur | Entwurf / Design |
|---|---|---|
| **Reichweite** | Das System als Ganzes | Ein Modul, eine Klasse, eine Funktion |
| **Änderbarkeit** | Teuer, oft systemweit | Billig, meist lokal |
| **Beispiel** | „Wir bauen eine REST API statt einer CLI" | „Diese Klasse bekommt eine Factory-Methode" |
| **Wer merkt es** | Alle Teams, Betrieb, ggf. Kunden | Meist nur die Person, die die Datei aufmacht |

Die Grenze ist fließend und kontextabhängig — was in einem Ein-Personen-Projekt eine Design-Entscheidung ist, kann bei 200 Entwicklern eine Architekturentscheidung sein. Nützliches Kriterium bleibt: **Wie viele Leute muss ich fragen, bevor ich das ändere?**

## Architekturmerkmale („-ilities")

Der wichtigste Begriff dieses Stichworts, weil er erklärt, *warum* es verschiedene Architekturstile gibt. Architekturmerkmale sind die **nicht-funktionalen** Anforderungen — sie beschreiben nicht, *was* das System tut, sondern *wie gut* es das tut:

- **Testbarkeit** — wie leicht lässt sich Verhalten isoliert prüfen?
- **Modifizierbarkeit / Wartbarkeit** — wie teuer ist eine Änderung?
- **Deploybarkeit** — wie schnell und risikoarm kommt eine Änderung in Produktion?
- **Performance / Skalierbarkeit** — Antwortzeit bzw. Verhalten unter Last
- **Verfügbarkeit / Fehlertoleranz** — was passiert, wenn ein Teil ausfällt?
- **Sicherheit**, **Beobachtbarkeit** (Logging/Monitoring — vgl. [[1.4 Logging & Exceptionhandling - Vertiefung|1.4]]), **Portabilität**, …

Ein System kann **nicht alle gleichzeitig maximieren**. Die Merkmale stehen in direkter Konkurrenz zueinander: Mehr Schichten erhöhen Testbarkeit und Modifizierbarkeit, senken aber Performance. Microservices erhöhen Deploybarkeit und Skalierbarkeit, senken aber massiv die Einfachheit und die Datenkonsistenz.

> [!important] Die zwei Gesetze der Softwarearchitektur (Richards & Ford)
> **1. Alles in der Softwarearchitektur ist ein Trade-off.**
> Wenn dir jemand erzählt, seine Lösung habe keine Nachteile, hat er die Nachteile nur noch nicht gefunden.
>
> **2. Das *Warum* ist wichtiger als das *Wie*.**
> Dass eine Anwendung geschichtet ist, sieht man am Ordnerbaum. *Warum* sie so geschnitten wurde und welche Alternative man verworfen hat, sieht man nirgends — deshalb muss es aufgeschrieben werden.

Das zweite Gesetz ist der Grund, warum es **Architecture Decision Records (ADR)** gibt: kurze, versionierte Dokumente, die je eine Entscheidung samt Kontext, Alternativen und Konsequenzen festhalten. In sechs Monaten weiß sonst niemand mehr — auch du nicht —, warum `ports.py` existiert.

## Code-First vs. Design-First

Die letzte Kontrollfrage aus dem Architektur-Teil. Sie fragt, **in welcher Reihenfolge** Schnittstelle und Implementierung entstehen:

- **Code-First:** Erst wird der Code geschrieben, die Schnittstellenbeschreibung wird daraus **generiert**. Genau das macht FastAPI: Aus deinen Python-Funktionen und Pydantic-Modellen entsteht automatisch das OpenAPI-Dokument.
- **Design-First (auch API-First):** Erst wird die Schnittstelle als Vertrag spezifiziert (z. B. als OpenAPI-YAML), abgestimmt und freigegeben — danach implementieren Server- und Client-Team parallel dagegen.

| | Code-First | Design-First |
|---|---|---|
| **Geschwindigkeit am Anfang** | Hoch — nichts liegt vor dem Code | Niedrig — erst Abstimmung, dann Code |
| **Parallelisierung** | Client-Team muss warten | Beide Teams starten sofort gegen den Vertrag |
| **Konsistenz über mehrere APIs** | Wächst zufällig, oft uneinheitlich | Erzwingbar über Guidelines und Linting |
| **Gefahr** | Die API bildet die interne Datenstruktur ab statt den fachlichen Bedarf | Overhead und „Vertrag am Bedarf vorbei" |
| **Typisch bei** | Kleinen Teams, internen APIs, Prototypen | Öffentlichen APIs, Team-Grenzen, Konzernumfeld |

> [!question]- Was ist der Unterschied zwischen Code-First und Design-First?
> **Code-First** bedeutet: Der Code ist die Quelle der Wahrheit, die API-Spezifikation wird daraus generiert. **Design-First** bedeutet: Die Spezifikation ist die Quelle der Wahrheit und entsteht *vor* dem Code; die Implementierung muss sich an den zuvor vereinbarten Vertrag halten.
>
> Der eigentliche Unterschied ist nicht die Reihenfolge, sondern **wer der Chef ist**: Bei Code-First folgt die Schnittstelle der Implementierung — ändert sich der Code, ändert sich (womöglich unbemerkt) die API. Bei Design-First folgt die Implementierung der Schnittstelle — der Vertrag ist stabil und kann unabhängig reviewt, versioniert und gegen Breaking Changes geprüft werden.
>
> **Für dieses Kapitel:** Wir arbeiten Code-First, weil FastAPI das OpenAPI-Dokument automatisch aus dem Code erzeugt (siehe [[#Swagger & OpenAPI]]). Das ist für ein Projekt dieser Größe die richtige Wahl. Wichtig ist nur, den Preis zu kennen: Wenn die Response-Modelle einfach die ORM-Klassen spiegeln, hat man keine API entworfen, sondern sein Datenbankschema veröffentlicht — und kann es danach nicht mehr ändern, ohne die Clients zu brechen.

## Bezug zum eigenen Projekt

Wenn der Leitfaden verlangt, den Ist-Stand zu analysieren und mit den Trainern zu *diskutieren*, dann ist genau das die Sprache, in der diese Diskussion geführt wird. Konkret für `pricing`:

- **Merkmale, die bisher priorisiert wurden:** Testbarkeit und Austauschbarkeit (`ports.py`, In-Memory-Fakes in den Tests), Beobachtbarkeit (Logging aus 1.4).
- **Merkmale, die bisher keine Rolle spielten:** Performance, Verfügbarkeit, Sicherheit, Skalierbarkeit — als Batch-Job schlicht irrelevant. Mit der REST API werden **alle vier** plötzlich relevant.
- **Die Architekturentscheidung dieses Kapitels**, in einem Satz formuliert: *„Die API-Schicht darf ausschließlich `PricingApp` aufrufen und kennt weder `adapters/` noch SQLAlchemy."* Das ist eine harte Regel, keine Empfehlung — und damit genau der Typ Satz, der in ein ADR gehört.
- **Der Trade-off, den man dabei eingeht:** Ein Endpunkt, der nur eine Liste ausgeben soll, muss trotzdem durch die Service-Schicht — mehr Code, langsamer. Bewusst akzeptiert, um die Schichtgrenze nicht aufzuweichen (vgl. Layer Bridging oben).

# Architekturmuster

## Warum das Stichwort den Architektur-Block abschließt

Das vorige Stichwort hat festgestellt: Architekturmerkmale konkurrieren miteinander, man kann nicht alle maximieren. Daraus folgt unmittelbar die Frage, um die es hier geht: **Wenn man sich entscheiden muss — welche bewährten Antworten gibt es schon?**

Architekturmuster sind genau das: erprobte Grundformen, die jeweils einen bestimmten Satz von Merkmalen begünstigen und andere opfern. Man erfindet Architektur nicht neu, man wählt aus und passt an. Und man sollte begründen können, warum man *diese* gewählt hat — das ist das zweite Gesetz aus dem letzten Stichwort.

## Entwurfsmuster vs. Architekturmuster

Die Kontrollfrage. Beide sind **wiederverwendbare Lösungen für wiederkehrende Probleme** — der Unterschied liegt in der Reichweite:

| | Entwurfsmuster (Design Pattern) | Architekturmuster (Architectural Pattern) |
|---|---|---|
| **Ebene** | Klassen und Objekte | Das System als Ganzes |
| **Beantwortet** | „Wie strukturiere ich *diesen* Code?" | „Wie strukturiere ich *das System*?" |
| **Umfang** | Eine Handvoll Klassen | Alle Komponenten, oft auch das Deployment |
| **Beispiele** | Strategy, Factory, Observer, Adapter, Repository | Schichten, Microservices, Event-Driven, Pipeline |
| **Kanonische Quelle** | „Design Patterns" (GoF, 1994) | POSA-Reihe; heute Richards & Ford |
| **Änderungskosten** | Gering, meist lokal | Hoch, oft systemweit |
| **Wer entscheidet** | Die Person, die die Datei schreibt | Das Team / die Architekturrolle |

Klassisch unterscheidet man sogar **drei** Abstraktionsebenen (POSA):

```
Architekturmuster   →  Grundstruktur des gesamten Systems      (Schichten, Pipeline)
      ↓
Entwurfsmuster      →  Struktur einzelner Komponenten          (Strategy, Factory)
      ↓
Idiome              →  sprachspezifische Umsetzungen           (Context Manager, Dunder-Methoden)
```

> [!important] Der wichtigste Punkt
> Die drei Ebenen **konkurrieren nicht**, sie liegen übereinander. Ein System hat gleichzeitig ein Architekturmuster, dutzende Entwurfsmuster und hunderte Idiome. Dein Projekt ist geschichtet (Architekturmuster), nutzt `DataSource`/`RecommendationWriter` als austauschbare Implementierungen (Entwurfsmuster: Strategy bzw. Adapter) und schreibt sie als `Protocol` (Python-Idiom).

> [!question]- Was ist der Unterschied zwischen einem Entwurfsmuster und einem Architekturmuster?
> Beide sind benannte, erprobte Lösungen für wiederkehrende Probleme — sie unterscheiden sich in **Abstraktionsebene und Reichweite**.
>
> Ein **Entwurfsmuster** löst ein Problem *innerhalb* einer Komponente, auf Klassen-/Objektebene: Wie mache ich einen Algorithmus austauschbar (Strategy)? Wie entkopple ich die Erzeugung eines Objekts von seiner Verwendung (Factory)? Es betrifft eine überschaubare Zahl von Klassen und ist billig zu ändern. Quelle: die „Gang of Four".
>
> Ein **Architekturmuster** legt die Grundstruktur des *gesamten* Systems fest: Wie sind die Hauptbausteine geschnitten, wie kommunizieren sie, wie wird deployt? Es betrifft alles, wird selten geändert und ist teuer, wenn doch. Beispiele: Schichtenarchitektur, Microservices, Event-Driven, Pipeline.
>
> **Nicht verwechseln mit „Muster vs. Stil":** Manche Autoren (u. a. Richards & Ford) unterscheiden zusätzlich zwischen dem *Architekturstil* als grober Gesamttopologie (geschichtet, microservices-basiert) und *Architekturmustern* als kleineren Lösungsbausteinen darin (CQRS, Saga, Circuit Breaker). Umgangssprachlich — und im Leitfaden — werden „Stil" und „Muster" auf dieser Ebene synonym verwendet.

## Die wichtigsten Architekturmuster im Überblick

Jeweils in einem Satz, mit dem Trade-off, den man eingeht:

**Schichtenarchitektur (Layered)** — Fachliche Trennung in horizontale Schichten.
✅ Einfach, verbreitet, gut testbar, jeder versteht es sofort. ❌ Schwer skalier- und deploybar, neigt zum Sinkhole-Effekt. **Der Standard-Startpunkt**, wenn nichts dagegenspricht.

**Pipeline / Pipes & Filters** — Daten fließen durch eine Kette unabhängiger Verarbeitungsschritte, jeder Filter macht genau eine Sache.
✅ Sehr gut komponierbar und testbar, Schritte sind einzeln austauschbar. ❌ Ungeeignet für interaktive Abläufe oder Anfragen, die hin- und herspringen. **Für dich besonders relevant:** Das ist die Grundform jeder ETL-Strecke und damit das Muster deines Berufsfelds.

**Microkernel / Plugin** — Ein minimaler Kern plus Erweiterungen, die sich an definierten Punkten einklinken.
✅ Neue Funktionen ohne Eingriff in den Kern. ❌ Die Plugin-Schnittstelle muss von Anfang an richtig sitzen. Beispiele: VS Code, Obsidian, pytest.

**Event-Driven** — Komponenten reagieren auf Ereignisse statt sich gegenseitig aufzurufen; Kommunikation läuft asynchron über einen Broker.
✅ Sehr lose gekoppelt, hoch skalierbar, gut erweiterbar. ❌ Der Ablauf steht nirgends komplett — Debuggen und Fehlerbehandlung sind deutlich schwerer. Zwei Spielarten: **Broker** (Ereignisse fließen frei, niemand koordiniert) und **Mediator** (eine Instanz orchestriert den Ablauf).

**Service-based** — Wenige grobkörnige Dienste, die sich meist eine Datenbank teilen.
✅ Der pragmatische Mittelweg zwischen Monolith und Microservices. ❌ Weniger unabhängig deploybar als echte Microservices.

**Microservices** — Viele kleine, unabhängig deploybare Dienste mit jeweils eigener Datenhaltung.
✅ Maximale Deploybarkeit, Skalierbarkeit und Teamautonomie. ❌ Verteiltes System mit allem, was daran hängt (siehe die Fallacies in [[#Client/Server]]): Netzwerklatenz, keine einfachen Transaktionen, aufwendiger Betrieb. **Keine Anfängerwahl** — und für ein Ein-Personen-Projekt fast immer die falsche.

**Space-based** — Zustand liegt im replizierten Arbeitsspeicher statt in einer zentralen Datenbank, um deren Flaschenhals zu umgehen.
✅ Extreme Lastspitzen (Ticketverkauf, Auktionen). ❌ Komplex und selten nötig. Nur zur Einordnung.

## Wie man auswählt

Die ehrliche Antwort lautet: **rückwärts, von den Architekturmerkmalen her.** Man wählt nicht „Microservices, weil modern", sondern stellt die Frage andersherum:

1. Welche Merkmale sind für dieses System *wirklich* gefordert (und von wem)?
2. Welche Muster begünstigen genau diese Merkmale?
3. Welchen Preis zahlt man dafür — und ist der akzeptabel?

Für unser Projekt durchgespielt: Gefordert sind Testbarkeit und Austauschbarkeit der Datenquelle; nicht gefordert sind unabhängige Deploybarkeit oder Skalierung auf tausende Anfragen. Damit fällt die Wahl auf die Schichtenarchitektur — und zwar begründet, nicht aus Gewohnheit.

## Bezug zum eigenen Projekt

In `pricing` lassen sich alle drei Ebenen gleichzeitig zeigen:

| Ebene | Was im Projekt | Wo |
|---|---|---|
| **Architekturmuster** | Schichtenarchitektur, angereichert um Ports & Adapters | Aufteilung `core/` ↔ `adapters/` |
| **Architekturmuster (zweites!)** | Pipeline — laden → bauen → berechnen → schreiben | `PricingApp._compute()` |
| **Entwurfsmuster** | Strategy/Adapter (austauschbare Quellen und Senken), Repository, Dependency Injection | `ports.py`, `PricingApp.__init__` |
| **Idiom** | `Protocol` statt abstrakter Basisklasse (strukturelle Typisierung), Context Manager fürs Session-Handling | `ports.py`, `adapters/db.py` |

Die zweite Zeile ist bemerkenswert: Deine Anwendung folgt *innen* einer Pipeline und ist *außen* geschichtet. Das ist kein Widerspruch, sondern der Normalfall — reale Systeme kombinieren Muster. Mit der REST API kommt lediglich eine Eingangstür an die bestehende Struktur, das Muster selbst ändert sich nicht.

# HTTP Basics

## Warum das Stichwort hier steht

Mit [[#Client/Server]] steht fest, *dass* künftig ein Netzwerk zwischen Aufrufer und Anwendung liegt. Offen ist, **in welcher Sprache** die beiden reden. Diese Sprache ist HTTP — und sie ist bemerkenswert klein: eine Handvoll Methoden, ein paar Dutzend Statuscodes, beliebig viele Header. Mehr ist es nicht.

> [!info] Die zwei Abkürzungen vorab
> Beide werden im Folgenden ständig benutzt und erst im nächsten Stichwort ([[#CRUD Basics]]) vollständig auseinandergenommen — hier schon einmal aufgelöst, damit nichts im Nebel bleibt:
>
> - **REST** = **Re**presentational **S**tate **T**ransfer. Wörtlich „Übertragung von Zustand in Form einer Repräsentation": Auf dem Server liegt eine **Ressource** (z. B. Einheit 42); über die Leitung geht nie die Ressource selbst, sondern eine **Repräsentation** davon — üblicherweise ein JSON-Objekt. Der Begriff stammt aus Roy Fieldings Dissertation (2000), die nachträglich beschreibt, warum das Web funktioniert, und daraus einen Architekturstil macht.
> - **CRUD** = **C**reate, **R**ead, **U**pdate, **D**elete. Die vier Grundoperationen auf gespeicherten Daten — der kleinste gemeinsame Nenner von Datenbanken (`INSERT`/`SELECT`/`UPDATE`/`DELETE`), ORMs und REST-APIs (`POST`/`GET`/`PUT`/`DELETE`). Der Begriff ist deutlich älter als das Web und stammt aus der Datenbankwelt.

Genau deshalb lohnt es sich, sie einmal *richtig* zu lernen statt nur zu benutzen. Denn REST erfindet nichts Neues, sondern **benutzt HTTP so, wie es gemeint war**: Ressourcen über URLs adressieren, Methoden nach ihrer definierten Bedeutung verwenden, Ergebnisse über Statuscodes ausdrücken. Wer HTTP nur als „Transportrohr für JSON" begreift, baut zwangsläufig APIs, die alles über `POST /doAction` machen und bei jedem Fehler `200 OK` zurückgeben. Das funktioniert — und wirft sämtliche Infrastruktur weg, die auf HTTP aufbaut: Caches, Proxies, Retries, Monitoring, Browser-Verhalten.

> [!tip] Merksatz
> REST ist kein Framework und keine Bibliothek. Es ist **die Disziplin, HTTP nicht zu missbrauchen.**

## Was HTTP ist — und was nicht

**HTTP** (HyperText Transfer Protocol) ist ein **Anwendungsprotokoll** auf Basis von TCP. Seine definierenden Eigenschaften:

| Eigenschaft | Bedeutung |
|---|---|
| **Request/Response** | Der Client schickt genau eine Anfrage, der Server genau eine Antwort. Der Server kann von sich aus nichts schicken. |
| **Client-initiiert** | Nur der Client beginnt. (Deshalb braucht man für Server-Push WebSockets oder Server-Sent Events.) |
| **Zustandslos** | Jede Anfrage steht für sich. Der Server merkt sich von der vorherigen nichts — siehe [[#Client/Server]]. |
| **Textbasiert (bis HTTP/1.1)** | Man kann eine Anfrage von Hand tippen und lesen. Das ist der Grund, warum HTTP so leicht zu debuggen ist. |
| **Medienunabhängig** | HTTP ist es egal, ob im Body JSON, HTML, ein PDF oder ein Video steckt. Der `Content-Type`-Header sagt, was es ist. |

Was HTTP **nicht** ist: kein Transportprotokoll (das ist TCP darunter), keine Verschlüsselung (das ist TLS → HTTPS), keine Datenbank-Semantik und keine Garantie für irgendetwas. HTTP definiert *Bedeutung*, keine Ausführung — dass ein `DELETE` wirklich löscht, ist eine Zusage deiner Anwendung, keine des Protokolls.

## Die URL — die Adresse einer Ressource

Bevor man über Anfragen redet, muss klar sein, *worauf* sie zeigen. Der zentrale Begriff in REST ist die **Ressource**: irgendetwas fachlich Benennbares (eine Buchung, eine Einheit, eine Preisempfehlung), das eine eigene Adresse hat.

```
https://api.example.com:8000/v1/units/42/prices?date=2026-07-30&limit=10#chart
└─┬─┘   └───────┬────────┘ └┬─┘└──────┬───────┘ └───────────┬──────────┘ └─┬─┘
scheme        host         port      path                 query         fragment
```

| Bestandteil  | Rolle                                             | Anmerkung                                                                   |
| ------------ | ------------------------------------------------- | --------------------------------------------------------------------------- |
| **Scheme**   | `http` oder `https`                               | `https` = HTTP innerhalb einer TLS-Verbindung. In Produktion ohne Ausnahme. |
| **Host**     | Wen frage ich?                                    | Wird per DNS zu einer IP aufgelöst.                                         |
| **Port**     | Welcher Dienst auf der Maschine?                  | Default: 80 (http), 443 (https). Lokal meist 8000 (Uvicorn).                |
| **Path**     | **Welche Ressource?**                             | Das Herzstück des REST-Designs — hierarchisch, mit Substantiven.            |
| **Query**    | Wie soll sie gefiltert/sortiert/paginiert werden? | `?key=value&key2=value2`                                                    |
| **Fragment** | Sprungmarke im Dokument                           | **Wird nie an den Server geschickt** — nur der Browser sieht es.            |

Die letzte Zeile ist ein beliebter Prüfungs-Fallstrick: Alles ab `#` bleibt im Client.

> [!important] Path vs. Query — die Regel
> **Path identifiziert, Query modifiziert.**
> `/units/42` bezeichnet *eine bestimmte* Einheit — ohne die 42 gibt es keine Ressource. `?limit=10` verändert nur die Sicht auf dieselbe Ressourcenmenge. Faustregel: Was die Ressource *ausmacht*, gehört in den Pfad; was die Sicht darauf einschränkt, in die Query.

## Anatomie einer HTTP-Request

Eine der Kontrollfragen — und der Grund, warum man HTTP einmal *roh* gesehen haben sollte. Eine Anfrage besteht aus **vier** Teilen, immer in dieser Reihenfolge:

```http
POST /v1/prices HTTP/1.1              ← 1. Request-Line: Methode · Ziel · Version
Host: api.example.com                 ← 2. Header (beliebig viele, "Name: Wert")
Content-Type: application/json
Accept: application/json
Authorization: Bearer eyJhbGciOi...
Content-Length: 54
                                      ← 3. Leerzeile: trennt Header vom Body
{"unit_id": 42, "price": 129.90, "date": "2026-07-30"}    ← 4. Body (optional)
```

1. **Request-Line** — `<Methode> <Pfad+Query> <HTTP-Version>`. Die Methode sagt, *was* mit der Ressource geschehen soll, der Pfad, *welche* es ist.
2. **Header** — Metadaten über die Anfrage: Format des Bodys, gewünschtes Antwortformat, Authentifizierung, Caching-Wünsche. Groß-/Kleinschreibung der Namen ist egal.
3. **Leerzeile** — rein syntaktisch, markiert das Ende der Header.
4. **Body** — die Nutzdaten. Bei `GET` und `DELETE` üblicherweise leer, bei `POST`/`PUT`/`PATCH` das eigentliche Objekt.

**Die wichtigsten Request-Header:**

| Header | Bedeutung |
|---|---|
| `Host` | Welcher virtuelle Host gemeint ist (ein Server bedient oft viele Domains) |
| `Content-Type` | Was **im Body mitgeschickt** wird, z. B. `application/json` |
| `Accept` | Was der Client **zurückhaben möchte** (Content Negotiation) |
| `Authorization` | Credentials, z. B. `Bearer <JWT>` oder `Basic <base64>` |
| `Content-Length` | Länge des Bodys in Bytes |
| `User-Agent` | Wer fragt (Browser, `curl`, Python-`httpx`) |

`Content-Type` und `Accept` werden ständig verwechselt: **`Content-Type` beschreibt, was ich schicke; `Accept` beschreibt, was ich haben will.**

## Anatomie einer HTTP-Response

Spiegelbildlich aufgebaut, nur die erste Zeile ist anders:

```http
HTTP/1.1 201 Created                  ← Status-Line: Version · Code · Reason Phrase
Content-Type: application/json        ← Header
Location: /v1/prices/1001
Content-Length: 78
                                      ← Leerzeile
{"id": 1001, "unit_id": 42, "price": 129.90, "date": "2026-07-30"}   ← Body
```

Die **Status-Line** trägt die eigentliche Information: Der Code sagt maschinenlesbar, wie es ausgegangen ist. Die „Reason Phrase" (`Created`) ist reine Lesehilfe für Menschen und darf beliebig lauten — Clients dürfen sich niemals auf sie verlassen, nur auf die Zahl.

Wichtige Response-Header: `Content-Type` (Format der Antwort), `Location` (wo die neu erzeugte Ressource liegt — gehört zu jedem `201`), `Cache-Control` / `ETag` (Caching), `Set-Cookie`, `Retry-After` (bei 429/503).

## Die HTTP-Methoden im Überblick

Die vier Kernmethoden bekommen ein eigenes Stichwort ([[#Die 4 zentralen HTTP-Methoden in REST-Controllern]]). Hier zunächst die Landkarte samt der zwei Eigenschaften, die alles erklären:

| Methode | Zweck | Safe | Idempotent | Body? |
|---|---|:---:|:---:|:---:|
| `GET` | Ressource **lesen** | ✅ | ✅ | nein |
| `POST` | Ressource **erzeugen** / Vorgang auslösen | ❌ | ❌ | ja |
| `PUT` | Ressource **vollständig ersetzen** | ❌ | ✅ | ja |
| `PATCH` | Ressource **teilweise ändern** | ❌ | ❌* | ja |
| `DELETE` | Ressource **löschen** | ❌ | ✅ | nein |
| `HEAD` | wie `GET`, aber nur Header (Existenz/Größe prüfen) | ✅ | ✅ | nein |
| `OPTIONS` | Welche Methoden sind erlaubt? (u. a. CORS-Preflight) | ✅ | ✅ | nein |

\* `PATCH` *kann* idempotent sein, ist es aber nicht zwingend (`{"increment": 1}` ist es nicht).

**Die zwei Eigenschaften, die man verstehen muss:**

- **Safe** (sicher): Die Anfrage **verändert nichts** auf dem Server. Man darf sie beliebig oft schicken, auch spekulativ. Deshalb dürfen Browser, Crawler und Prefetcher `GET` einfach so ausführen — und deshalb ist ein `GET /orders/42/delete` ein schwerer Designfehler: Der erste Crawler räumt die Datenbank leer.
- **Idempotent**: Das **Ergebnis** ist nach *n* identischen Aufrufen dasselbe wie nach einem. Das ist die direkte Antwort auf das Timeout-Problem aus [[#Client/Server]]: Nur bei idempotenten Methoden darf ein Client nach einem Timeout gefahrlos erneut senden. `POST /prices` zweimal → zwei Datensätze. `PUT /prices/1001` zweimal → derselbe Zustand.

Nur `GET`/`HEAD` sind praktisch **cacheable** — ebenfalls eine Folge von „safe".

> [!question]- Wie ist die Struktur einer HTTP-Request, und worin unterscheiden sich PUT/POST von GET?
> **Struktur:** Request-Line (`Methode Pfad HTTP/Version`) → Header (`Name: Wert`, beliebig viele) → Leerzeile → optionaler Body. Die Response ist identisch aufgebaut, nur mit Status-Line (`HTTP/Version Code Reason`) statt Request-Line.
>
> **Der Unterschied ist kein technischer, sondern ein semantischer** — und er hat vier praktische Konsequenzen:
>
> | | `GET` | `POST` / `PUT` |
> |---|---|---|
> | **Absicht** | lesen | schreiben (erzeugen / ersetzen) |
> | **Daten stehen** | in Pfad und Query | im **Body** |
> | **Safe** | ✅ ja — verändert nichts | ❌ nein |
> | **Idempotent** | ✅ ja | `PUT` ✅ / `POST` ❌ |
> | **Cacheable** | ✅ ja | nein |
> | **Browser-Verhalten** | Reload gefahrlos, Bookmark möglich, landet im Verlauf | Reload fragt „Formular erneut senden?" |
>
> Daraus folgt außerdem: Sensible Daten gehören **nie** in eine GET-Query — URLs landen in Server-Logs, Browser-Verlauf, Proxies und `Referer`-Headern. Und Query-Strings sind längenbegrenzt (praktisch ~2000 Zeichen), Bodys nicht.
>
> Der Unterschied **`POST` vs. `PUT`** wiederum: `POST` erzeugt etwas Neues an einer vom *Server* bestimmten Adresse (der Client kennt die ID vorher nicht), `PUT` legt den Zustand an einer vom *Client* bestimmten Adresse fest — und ist deshalb idempotent. Details beim Stichwort [[#Die 4 zentralen HTTP-Methoden in REST-Controllern]].

## Statuscodes

Der zweite Teil der HTTP-Semantik: Das Ergebnis wird über eine dreistellige Zahl ausgedrückt. **Die erste Ziffer ist die Klasse** und das Einzige, was man auswendig können muss:

| Klasse | Bedeutung | Merksatz |
|---|---|---|
| **1xx** | Informational | „Ich arbeite noch" (selten relevant) |
| **2xx** | Success | „Hat geklappt" |
| **3xx** | Redirection | „Woanders nachschauen" |
| **4xx** | Client Error | „**Du** hast einen Fehler gemacht" |
| **5xx** | Server Error | „**Ich** habe einen Fehler gemacht" |

Die Grenze zwischen 4xx und 5xx ist die wichtigste Linie im ganzen Protokoll: Sie sagt, **wer schuld ist** — und damit, ob ein Retry sinnvoll ist (4xx: unverändert nie; 5xx: ja, mit Backoff) und wen der Alarm wecken soll (die 5xx-Rate ist die klassische Monitoring-Metrik, 4xx meist nicht).

**Die Codes, die man wirklich braucht:**

| Code | Name | Wann |
|---|---|---|
| **200** | OK | Erfolgreicher `GET`, `PUT`, `PATCH` — mit Body |
| **201** | Created | Erfolgreicher `POST` — plus `Location`-Header auf die neue Ressource |
| **204** | No Content | Erfolg **ohne** Body — typisch für `DELETE` |
| **301 / 308** | Moved Permanently | Ressource ist dauerhaft umgezogen |
| **304** | Not Modified | Caching: „Deine Kopie ist noch aktuell" (Antwort auf `If-None-Match`) |
| **400** | Bad Request | Anfrage ist syntaktisch kaputt (z. B. ungültiges JSON) |
| **401** | Unauthorized | **Nicht authentifiziert** — „Wer bist du?" (der Name ist historisch irreführend) |
| **403** | Forbidden | **Nicht autorisiert** — „Ich weiß, wer du bist; du darfst das trotzdem nicht" |
| **404** | Not Found | Ressource existiert nicht |
| **405** | Method Not Allowed | Pfad existiert, Methode nicht (z. B. `DELETE` auf einer Liste) |
| **409** | Conflict | Zustandskonflikt — Duplikat, gleichzeitige Änderung |
| **422** | Unprocessable Content | JSON ist gültig, aber inhaltlich falsch (**FastAPI/Pydantic-Standard bei Validierungsfehlern**) |
| **429** | Too Many Requests | Rate Limit erreicht — meist mit `Retry-After` |
| **500** | Internal Server Error | Unbehandelte Exception — dein Bug |
| **502 / 503 / 504** | Bad Gateway / Service Unavailable / Gateway Timeout | Ein *nachgelagerter* Dienst (DB, Fremd-API) streikt |

Die drei Verwechslungspaare, die im Alltag zählen:

- **401 vs. 403** — fehlender vs. unzureichender Ausweis.
- **400 vs. 422** — „ich kann das gar nicht lesen" vs. „ich kann es lesen, aber es ergibt keinen Sinn". FastAPI antwortet auf Pydantic-Validierungsfehler mit **422**; das kommt beim Stichwort [[#Validierung von Request/Response (Pydantic)]] wieder.
- **404 vs. 403** — bei sensiblen Ressourcen antwortet man bewusst mit `404` statt `403`, um nicht zu verraten, *dass* es die Ressource überhaupt gibt.

> [!warning] Das häufigste Anti-Pattern überhaupt
> ```http
> HTTP/1.1 200 OK
>
> {"success": false, "error": "Einheit 42 existiert nicht"}
> ```
> „`200` mit Fehler im Body" ist bequem und kaputt: Jeder Client, jeder Proxy, jedes Monitoring-Dashboard und jede Retry-Logik hält diese Antwort für einen Erfolg. Der Fehler wird erst sichtbar, wenn jemand den Body von Hand liest. **Der Statuscode ist die Antwort — der Body ist nur das Detail.** Für den Fehler-Body gibt es sogar einen Standard: [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html).

> [!question]- Welche HTTP-Response-Codes gibt es? Welche sind die wichtigsten?
> Fünf Klassen, erkennbar an der ersten Ziffer: **1xx** informational, **2xx** Erfolg, **3xx** Umleitung, **4xx** Client-Fehler, **5xx** Server-Fehler. Die entscheidende Unterscheidung ist 4xx vs. 5xx: *Wer hat den Fehler gemacht?* — daran hängt, ob ein Retry sinnvoll ist und ob jemand geweckt werden muss.
>
> Die wichtigsten in der Praxis: **200** OK, **201** Created (+ `Location`), **204** No Content, **400** Bad Request, **401** nicht authentifiziert, **403** nicht autorisiert, **404** Not Found, **409** Conflict, **422** Validierungsfehler (FastAPI-Standard), **500** interner Fehler, **503** Dienst nicht verfügbar.
>
> Für eine gewöhnliche CRUD-API reichen faktisch: `200`, `201`, `204`, `400`/`422`, `404`, `409`, `500`.

## Statuslosigkeit, Cookies und Tokens

HTTP ist zustandslos — trotzdem bleibt man auf Webseiten „eingeloggt". Der Widerspruch löst sich so auf: Der Zustand wird bei **jeder** Anfrage erneut mitgeschickt, statt vom Server erinnert zu werden.

- **Cookies**: Der Server schickt `Set-Cookie: session=abc`, der Browser hängt danach automatisch `Cookie: session=abc` an jede weitere Anfrage an dieselbe Domain. Klassisch für Browser-Anwendungen, für APIs eher unüblich (und CSRF-anfällig).
- **Token** (`Authorization: Bearer <JWT>`): Der Client verwahrt selbst einen Ausweis und schickt ihn bei jeder Anfrage mit. Der Standard für APIs, weil er ohne Browser funktioniert und der Server nichts speichern muss.

In beiden Fällen bleibt der Server selbst zustandslos — das Wissen reist in der Anfrage mit.

## HTTP-Versionen (kurz zur Einordnung)

| Version | Kern | Relevanz für dich |
|---|---|---|
| **HTTP/1.1** (1997) | Text, eine Anfrage pro Verbindung zur Zeit, Keep-Alive | Das, was man beim Debuggen sieht; Uvicorn spricht es |
| **HTTP/2** (2015) | Binär, **Multiplexing** (viele Requests parallel über eine Verbindung), Header-Kompression | Löst das „Head-of-Line-Blocking" von 1.1 |
| **HTTP/3** (2022) | Über **QUIC/UDP** statt TCP, schnellerer Verbindungsaufbau | Vor allem für mobile/instabile Netze |

Wichtig: **Die Semantik ändert sich nicht.** Methoden, Statuscodes und Header bedeuten in allen drei Versionen dasselbe — nur die Übertragung auf dem Draht unterscheidet sich. (Genau deshalb wurde die Semantik 2022 in ein eigenes Dokument ausgelagert: RFC 9110.) Man schreibt seine API also nicht „für HTTP/2".

## Requests im Browser inspizieren

Die zweite Kontrollfrage — und eine Fähigkeit, die man täglich braucht.

**DevTools öffnen:** `F12` bzw. `Strg+Umschalt+I`, dann Reiter **Network** / **Netzwerkanalyse**.

**Inhalt untersuchen:** Auf eine Zeile klicken, dann die Unterreiter durchgehen:

| Reiter | Zeigt |
|---|---|
| **Headers** | Request-URL, Methode, **Statuscode**, alle Request- und Response-Header |
| **Payload** / **Request** | Was gesendet wurde (Body bzw. Query-Parameter) |
| **Response** | Rohe Antwort |
| **Preview** | Antwort aufbereitet — JSON als aufklappbarer Baum |
| **Timing** | Zeitliche Aufschlüsselung (s. u.) |

Nützliche Einstellungen, die man einmal kennen sollte: **Filter `Fetch/XHR`** blendet Bilder, CSS und Fonts aus und zeigt nur die API-Aufrufe. **Preserve log** überlebt Seitenwechsel und Redirects. **Disable cache** erzwingt echte Anfragen. Und der wichtigste Handgriff überhaupt: **Rechtsklick → Copy → Copy as cURL** — damit hat man den exakten Request als Kommandozeile und kann ihn im Terminal reproduzieren, abwandeln oder in ein Ticket kleben.

**Performance untersuchen:** Der **Waterfall** zeigt jede Anfrage als Balken auf einer Zeitachse — sofort sichtbar wird, was seriell läuft, obwohl es parallel laufen könnte. Der Reiter **Timing** zerlegt eine einzelne Anfrage:

```
Queueing → Stalled → DNS Lookup → Initial connection (TCP) → SSL (TLS)
         → Request sent → Waiting (TTFB) → Content Download
```

Die entscheidende Größe ist **TTFB (Time To First Byte)**: die Zeit zwischen „Anfrage raus" und „erstes Antwortbyte da". **Ein hoher TTFB ist Serverzeit** — deine Anwendung, deine Datenbankabfrage. Ist dagegen *Content Download* groß, ist die Antwort schlicht zu groß (es fehlt Paginierung). Sind *DNS/TCP/SSL* auffällig, ist es ein Verbindungs- und kein Anwendungsproblem — und beim zweiten Aufruf durch Keep-Alive meist verschwunden.

> [!question]- Wie inspizierst du Requests und Responses im Browser (Inhalt und Performance)?
> Über die **DevTools** (`F12`) im Reiter **Network**. Für den **Inhalt**: Anfrage anklicken und *Headers* (Methode, URL, Statuscode, Header), *Payload* (gesendeter Body/Query), *Response* bzw. *Preview* (Antwort roh bzw. als JSON-Baum) ansehen. Filter `Fetch/XHR` reduziert auf API-Aufrufe, *Preserve log* überlebt Redirects, *Copy as cURL* macht die Anfrage im Terminal reproduzierbar.
>
> Für die **Performance**: der **Waterfall** zeigt, welche Anfragen parallel bzw. seriell laufen; der Reiter **Timing** zerlegt eine Anfrage in Queueing, DNS, TCP, TLS, **Waiting (TTFB)** und Content Download. Hoher TTFB = der Server ist langsam (Anwendung/DB), hoher Content Download = die Antwort ist zu groß.
>
> **Ergänzend außerhalb des Browsers**, weil eine API meist gar kein Browser-Frontend hat: die von FastAPI mitgelieferte **Swagger UI** (`/docs`), `curl -v` bzw. **HTTPie** im Terminal sowie **Postman**/**Insomnia**/**Bruno**. Siehe [[#Swagger & OpenAPI]].

## Bezug zum eigenen Projekt

Was das konkret für `pricing` bedeutet, sobald die API steht:

| HTTP-Begriff | Entsprechung im Projekt |
|---|---|
| **Ressource** | `unit`, `booking`, `price_recommendation` — die Entitäten aus `domain.py` |
| **Pfad** | `/units/{unit_id}`, `/recommendations` — Substantive im Plural, keine Verben |
| **Query** | `?date=2026-07-30`, `?limit=50` — Filter, nie Identität |
| **`GET`** | Lesende Endpunkte — dürfen nichts verändern (`_compute()` darf also nichts schreiben, wenn es hinter einem `GET` hängt) |
| **`POST`** | Neue Buchung/Preisempfehlung anlegen → `201` + `Location` |
| **`404`** | `unit_id` existiert nicht |
| **`422`** | Pydantic lehnt den Request-Body ab (passiert automatisch) |
| **`500`** | Eine unbehandelte Exception aus `exceptions.py` |
| **`503`** | Postgres ist nicht erreichbar — *nicht* `500`, denn schuld ist ein nachgelagerter Dienst |

Die letzten vier Zeilen sind der eigentliche Brückenschlag zu [[1.4 Logging & Exceptionhandling - Vertiefung|Kapitel 1.4]]: Die dort definierte Exception-Hierarchie bekommt jetzt eine **zweite Aufgabe** — sie muss auf Statuscodes abgebildet werden. Eine fachliche „nicht gefunden"-Exception ist ein `404`, ein Validierungsproblem ein `422`, ein Datenbankausfall ein `503`, und alles Unerwartete ein `500` mit generischer Meldung nach außen und vollem Traceback im Log. Genau diese Zuordnungstabelle ist ein Artefakt, das später in den [[Umsetzungsstand (REST APIs & Layered Architecture)|Umsetzungsstand]] gehört.

# CRUD Basics

## Warum das Stichwort hier steht

HTTP ist geklärt: Methoden, Statuscodes, Header. Was noch fehlt, ist die Antwort auf die Frage, **was man über diese Leitung eigentlich anbietet**. Und hier lauert das Missverständnis, das die meisten APIs prägt: dass „REST" und „CRUD" dasselbe seien.

Sind sie nicht — und der Unterschied ist keine Wortklauberei, sondern entscheidet darüber, ob deine API in zwei Jahren noch benutzbar ist. Deshalb geht dieses Stichwort in drei Schritten vor: erst **CRUD** (die vier Operationen und ihr Ursprung in der Datenwelt), dann **REST** (der Architekturstil), und zum Schluss die Abgrenzung, an der sich in der Praxis alles entscheidet.

## CRUD — die vier Grundoperationen

**CRUD** steht für **C**reate, **R**ead, **U**pdate, **D**elete. Der Begriff stammt aus der Datenbankwelt (geprägt von James Martin, 1983) und ist damit deutlich älter als das Web. Die Idee dahinter ist bestechend einfach und deshalb so langlebig:

> [!important] Die CRUD-These
> **Alles, was man mit gespeicherten Daten tun kann, lässt sich auf vier Operationen zurückführen:** anlegen, lesen, ändern, löschen.
> Das ist der kleinste gemeinsame Nenner jeder Datenhaltung — von SQL über Dateisysteme bis zu REST-APIs. Und wie jeder kleinste gemeinsame Nenner ist er **vollständig, aber nicht ausdrucksstark** (dazu unten mehr).

Die Stärke des Begriffs ist, dass er sich über alle Schichten deiner Anwendung hinweg durchhält — genau die Schichten aus dem ersten Teil dieses Kapitels:

| CRUD       | SQL      | SQLAlchemy (dein Projekt)    | HTTP-Methode    |
| ---------- | -------- | ---------------------------- | --------------- |
| **C**reate | `INSERT` | `session.add(obj)`           | `POST`          |
| **R**ead   | `SELECT` | `session.get()` / `select()` | `GET`           |
| **U**pdate | `UPDATE` | Attribut setzen + `flush`    | `PUT` / `PATCH` |
| **D**elete | `DELETE` | `session.delete(obj)`        | `DELETE`        |

Die ersten drei Spalten kennst du bereits aus [[1.2 Relationale Datenbanken & ORM - Vertiefung|Kapitel 1.2]] — die vierte kommt jetzt dazu. Das ist der eigentliche inhaltliche Kern dieses Kapitels: **Die Presentation-Schicht macht dieselben vier Operationen über HTTP zugänglich, die die Persistenz-Schicht schon kann.**

> [!warning] Der Kurzschluss, vor dem das warnt
> Genau weil die Tabelle so schön aufgeht, entsteht die Versuchung, jede Datenbanktabelle 1:1 als Endpunkt zu veröffentlichen. Damit hat man aber keine API entworfen, sondern **sein Datenbankschema publiziert** — und kann es danach nicht mehr ändern, ohne alle Clients zu brechen (siehe „Preis von Code-First" bei [[#Softwarearchitektur]]). Die Tabelle oben ist eine *Übersetzungshilfe*, kein Bauplan.

## „Read" hat zwei Gesichter

Ein Detail, das im Akronym untergeht, im API-Design aber alles strukturiert: Lesen bedeutet zwei verschiedene Dinge, und dazu gehören **zwei verschiedene Ressourcen**.

```
GET /recommendations          → die Sammlung (Collection)  → Liste von Objekten
GET /recommendations/1001     → ein Element   (Item)       → ein einzelnes Objekt
```

Daraus folgt das Grundmuster jeder REST-API — **zwei Pfade pro Entität**, mit unterschiedlichen erlaubten Methoden:

| Pfad | `GET` | `POST` | `PUT` | `DELETE` |
|---|---|---|---|---|
| `/recommendations` (Sammlung) | Liste lesen | **neu anlegen** | ✗ (unüblich) | ✗ (unüblich) |
| `/recommendations/{id}` (Element) | eines lesen | ✗ | **ersetzen** | **löschen** |

Man erkennt die Logik sofort: `POST` geht immer an die **Sammlung** (weil das Element ja noch keine Adresse hat), `PUT` und `DELETE` immer an das **Element** (weil man wissen muss, welches). Ein `DELETE /recommendations` würde die gesamte Sammlung löschen — technisch definiert, praktisch fast nie angeboten. Die Details dazu im nächsten Stichwort ([[#Die 4 zentralen HTTP-Methoden in REST-Controllern]]).

## Was eine Ressource ist — und was nicht

Der Begriff **Ressource** ist der Dreh- und Angelpunkt und wird konsequent falsch verstanden. Eine Ressource ist:

- **Ein Ding, kein Vorgang.** `/bookings` ✅ · `/createBooking` ❌
- **Nicht identisch mit einer Datenbanktabelle.** Eine Ressource kann aus mehreren Tabellen zusammengesetzt sein oder eine berechnete Sicht darstellen, die nirgends gespeichert ist.
- **Nicht identisch mit einer Klasse.** Der Zuschnitt richtet sich nach dem, was der Client braucht, nicht nach deiner internen Struktur.
- **Alles, was einen Namen verdient.** Auch eine Beziehung (`/units/42/bookings`) oder ein Suchergebnis kann eine Ressource sein.

Und ganz zentral: **Was über die Leitung geht, ist nie die Ressource selbst, sondern eine Repräsentation davon.** Die Ressource „Buchung 1001" ist ein abstraktes Konzept; das JSON, das du bekommst, ist eine mögliche *Darstellung* dieses Konzepts — es könnte genauso gut XML, CSV oder HTML sein. Genau das steckt im **R** und **S** von REST: **Re**presentational **S**tate Transfer.

## REST — der Architekturstil hinter der Abkürzung

Roy Fielding hat REST 2000 in seiner Dissertation beschrieben. Wichtig für das Verständnis: Er hat es nicht *erfunden*, sondern **nachträglich beschrieben, warum das Web funktioniert** — und daraus einen übertragbaren Architekturstil destilliert. REST ist deshalb kein Framework, keine Bibliothek und keine Spezifikation, sondern ein Satz von **sechs Constraints** (Beschränkungen), die man sich auferlegt, um bestimmte Eigenschaften zu gewinnen:

| Constraint | Bedeutet | Gewinn |
|---|---|---|
| **1. Client/Server** | Trennung von Darstellung und Datenhaltung | Beide Seiten entwickeln sich unabhängig — siehe [[#Client/Server]] |
| **2. Stateless** | Der Server hält keinen Sitzungszustand | Skalierbarkeit, Ausfallsicherheit, Nachvollziehbarkeit |
| **3. Cacheable** | Antworten sagen, ob sie zwischengespeichert werden dürfen | Weniger Last, kürzere Antwortzeiten |
| **4. Uniform Interface** | **Alle** Ressourcen werden auf dieselbe Weise angesprochen | Entkopplung, Wiederverwendbarkeit — *das* Kern-Constraint |
| **5. Layered System** | Der Client weiß nicht, ob er mit dem Server oder einem Proxy spricht | Load Balancer, Gateways, CDNs sind einfügbar |
| **6. Code-on-Demand** *(optional)* | Der Server kann ausführbaren Code schicken (z. B. JavaScript) | Erweiterbarkeit des Clients |

Bemerkenswert: Die Constraints 1, 2, 3 und 5 kennst du inhaltlich schon — sie sind über die letzten Stichworte verteilt aufgetaucht. Constraint 5 ist besonders hübsch, weil er die **Schichtenarchitektur aus dem ersten Kapitelteil auf die Netzwerkebene hebt**: Auch dort gilt, dass eine Ebene ihre Nachbarn kennt, aber nicht wissen muss, was dahinter liegt.

### Das Uniform Interface — der eigentliche Kern

Constraint 4 ist der, aus dem sich fast alle praktischen REST-Regeln ableiten. Er zerfällt in vier Teile:

1. **Identifikation von Ressourcen** — Jede Ressource hat eine eigene, stabile URL. (Daher: Substantive im Pfad.)
2. **Manipulation über Repräsentationen** — Der Client verändert eine Ressource, indem er eine veränderte Repräsentation schickt, nicht durch einen Fernaufruf einer Methode.
3. **Selbstbeschreibende Nachrichten** — Jede Nachricht enthält alles, was zu ihrer Interpretation nötig ist: Methode, Statuscode, `Content-Type`. Ein Proxy, der die Fachlichkeit nicht kennt, kann trotzdem korrekt cachen oder wiederholen.
4. **HATEOAS** (*Hypermedia as the Engine of Application State*) — Die Antwort enthält **Links** auf die möglichen nächsten Schritte, so wie eine HTML-Seite Links enthält. Der Client muss die URLs nicht fest verdrahten.

Punkt 4 ist der berühmteste und der am wenigsten umgesetzte. In der Praxis begegnet er dir fast nie — was zur nächsten Frage führt.

## Richardson Maturity Model — wie „RESTful" ist eine API wirklich?

Martin Fowler hat Leonard Richardsons Reifegradmodell bekannt gemacht. Es ordnet APIs in vier Stufen ein und ist die ehrlichste Landkarte des Themas:

| Level | Kennzeichen | Beispiel |
|---|---|---|
| **0 — „The Swamp of POX"** | Ein einziger Endpunkt, alles per `POST`, HTTP nur als Transporttunnel | `POST /api` mit `{"action": "getBooking", "id": 42}` |
| **1 — Ressourcen** | Verschiedene URLs für verschiedene Dinge, aber weiterhin alles `POST` | `POST /bookings/42/get` |
| **2 — HTTP-Verben & Statuscodes** | Methoden nach ihrer Bedeutung, Statuscodes als Antwort | `GET /bookings/42` → `200` |
| **3 — Hypermedia (HATEOAS)** | Antworten enthalten Links auf mögliche Folgeaktionen | `{"id": 42, "_links": {"cancel": "/bookings/42/cancellation"}}` |

> [!important] Die ernüchternde und wichtige Wahrheit
> **Praktisch jede „REST-API" der Industrie steht auf Level 2** — auch die von großen Anbietern, auch die, die du bauen wirst. Level 3 ist selten, weil der Aufwand hoch und der Nutzen für typische Clients gering ist.
>
> Nach Fieldings strenger Definition ist eine API ohne HATEOAS **gar keine REST-API**. Er hat sich darüber öffentlich geärgert. Der pragmatische Umgang damit: *Level 2 anstreben und es „REST" nennen, wie alle anderen auch — aber wissen, dass man eine Abkürzung nimmt und welche.* Genau diese Art von bewusster, benennbarer Abkürzung ist das, was das zweite Gesetz der Architektur meint.

## REST ≠ CRUD — die entscheidende Abgrenzung

Jetzt der Punkt, auf den alles hinausläuft:

| | CRUD | REST |
|---|---|---|
| **Was ist es?** | Eine Menge von **Operationen** | Ein **Architekturstil** |
| **Herkunft** | Datenbanken (1983) | Web-Architektur (2000) |
| **Sagt etwas über** | *Was* man mit Daten tun kann | *Wie* ein verteiltes System aufgebaut sein sollte |

Daraus folgen zwei Sätze, die man auswendig können sollte:

- **Eine REST-API kann CRUD anbieten — muss aber nicht.**
- **Eine CRUD-API ist noch lange nicht RESTful** (siehe Level 0 und 1 oben).

Der praktische Schmerzpunkt entsteht immer an derselben Stelle: **Fachliche Vorgänge passen nicht in vier Verben.** „Buchung stornieren", „Preisempfehlung freigeben", „Neuberechnung anstoßen", „Passwort zurücksetzen" — das sind keine Create/Update/Delete-Operationen, das sind *Prozesse*. Wer sie in CRUD presst, landet bei `PUT /bookings/42` mit `{"status": "cancelled"}` und hat die eigentliche fachliche Bedeutung in ein Datenfeld versteckt: Der Server kann nicht mehr unterscheiden, ob jemand storniert oder nur ein Feld korrigiert, und kann daran folglich auch keine Regeln, Rechte oder Ereignisse hängen.

### Wie man Nicht-CRUD-Vorgänge modelliert

Drei etablierte Wege, in absteigender „Reinheit":

**1. Den Vorgang als eigene Ressource auffassen** — der REST-konforme Weg. Man fragt: *Was entsteht dabei?*

```
POST /bookings/42/cancellation      → eine Stornierung ist ein Ding, das entsteht
POST /pricing-runs                  → ein Berechnungslauf ist ein Ding mit Zustand
GET  /pricing-runs/77               → ... und kann danach abgefragt werden
```

Das ist mehr als Kosmetik: Der Lauf bekommt eine eigene Identität, kann Status haben (`running`, `done`, `failed`), ist abfragbar und protokollierbar. Für lang laufende Vorgänge ist das ohnehin der einzig sinnvolle Weg (Antwort `202 Accepted` plus `Location` auf die Vorgangs-Ressource).

**2. Eine Sub-Ressource für den Zustand** — pragmatisch und weit verbreitet:

```
PUT /bookings/42/status             → {"value": "cancelled"}
```

**3. Ein Verb als „Action"-Endpunkt** — der unreine, aber manchmal ehrlichste Weg:

```
POST /bookings/42/cancel
```

Große Anbieter machen das (Stripe, GitHub), wenn ein Vorgang sich beim besten Willen nicht als Substantiv fassen lässt. Wichtig ist nur, dass es die **begründete Ausnahme** bleibt und nicht der Normalfall — sonst ist man wieder bei Level 0 mit hübscheren URLs.

> [!tip] Die Frage, die weiterhilft
> Wenn ein Vorgang nicht in CRUD passt, frag nicht „welche Methode nehme ich?", sondern: **„Welches Ding entsteht hier eigentlich?"** In den meisten Fällen gibt es eines — eine Stornierung, ein Lauf, eine Freigabe, eine Zahlung — und damit eine Ressource.

## Bezug zum eigenen Projekt

Deine Entitäten stehen bereits fest (aus `adapters/orm.py` bzw. `domain.py`): `Capacity`, `Booking`, `Price`, `PriceRecommendation`. Die Aufgabe verlangt CRUD über die Entitäten plus die zwei Endpunkte aus der Bewerberaufgabe. Ein erster Zuschnitt:

| Ressource | Sinnvolle Operationen | Anmerkung |
|---|---|---|
| `/bookings` | `GET` (Liste, gefiltert), `POST`, `GET /{id}`, `PUT /{id}`, `DELETE /{id}` | Klassisches CRUD — hier passt es wirklich |
| `/prices` | `GET`, `POST`, `GET /{id}`, `PUT /{id}` | Stammdaten |
| `/capacity` | `GET`, `POST`, `GET /{id}`, `PUT /{id}` | Stammdaten |
| `/recommendations` | **nur `GET`** (Liste + Element) | ← der interessante Fall |

Die letzte Zeile ist die eigentliche Design-Entscheidung: **Eine Preisempfehlung wird nicht angelegt, sie wird berechnet.** Ein `POST /recommendations` mit einem vom Client mitgebrachten Empfehlungswert wäre fachlicher Unsinn — die Ressource ist ein *Ergebnis*, kein Eingabedatum. Damit hat dein Projekt genau den Fall, an dem CRUD an seine Grenze stößt, und die Frage lautet: Wie stößt ein Client eine Neuberechnung an?

```
POST /pricing-runs        → startet _compute(), liefert 201/202 + Location
GET  /pricing-runs/{id}   → Status und Ergebnis des Laufs
GET  /recommendations     → die berechneten Empfehlungen (nur lesend)
```

Das ist Variante 1 von oben und passt bemerkenswert gut auf die vorhandene Struktur: `PricingApp._compute()` **ist** bereits ein Lauf — er hat nur bisher keine Identität, weil ihn niemand von außen anstoßen konnte. Alternativ (und für den Anfang völlig legitim): ein simples `POST /recommendations/compute` als bewusste Ausnahme, dokumentiert als solche.

Zwei weitere Punkte, die sich daraus ergeben:

- **Die Ressourcen sind nicht deine ORM-Klassen.** `PriceRecommendation` in der Datenbank hat `capacity_id` als Fremdschlüssel; ein API-Client will vermutlich `product_id` und `calendar_date` sehen, nicht eine interne ID. Genau hier entsteht der Bedarf an einem eigenen Modell für die Außenschicht — das ist das **DTO**, das beim Stichwort [[#Validierung von Request/Response (Pydantic)]] drankommt.
- **`GET` muss safe bleiben.** Wenn `GET /recommendations` intern `_compute()` triggert und dabei schreibt, verletzt das die HTTP-Semantik — mit allen Folgen aus [[#HTTP Basics]] (Crawler, Caches, Retries). Lesen und Rechnen müssen getrennte Endpunkte sein.

# Die 4 zentralen HTTP-Methoden in REST-Controllern

## Warum das Stichwort hier steht

[[#HTTP Basics]] hat die Methoden aufgezählt, [[#CRUD Basics]] hat geklärt, worauf sie zeigen. Jetzt geht es um das Handwerk: **Wie sieht ein einzelner Endpunkt konkret aus — was nimmt er an, was gibt er zurück, wie heißt er, und wo im Code steht er?**

Das ist der Teil des Kapitels, der sich am unmittelbarsten in Code übersetzt, und gleichzeitig der, in dem die meisten stillen Fehler passieren. Nicht weil er schwer wäre, sondern weil jede Entscheidung *für sich* plausibel wirkt und die Summe trotzdem eine API ergibt, die niemand vorhersagen kann.

## Was ein „Controller" überhaupt ist

Der Begriff kommt aus MVC (Model-View-Controller) und hat sich für die Presentation-Schicht eingebürgert. In FastAPI heißt dasselbe Ding **Router**, in Flask **Blueprint**, in Django **View**. Gemeint ist immer: **die Sammlung von Funktionen, die HTTP-Anfragen entgegennimmt.**

Was ein Controller tun soll — und zwar genau das und nichts mehr:

```
1. Anfrage entgegennehmen        (Pfad, Query, Body)
2. Eingabe validieren            (in FastAPI: automatisch durch Pydantic)
3. An die Service-Schicht delegieren
4. Ergebnis übersetzen           (Domain-Objekt → Antwortmodell)
5. Statuscode setzen
```

Was er **nicht** tun darf: rechnen, SQL abysetzen, Sessions verwalten, fachliche Regeln prüfen. Das ist keine Stilfrage, sondern die Architekturentscheidung aus [[#Softwarearchitektur]] („die API-Schicht ruft ausschließlich `PricingApp` auf"). Ein guter Controller-Handler ist meist **drei bis zehn Zeilen lang**. Wird er länger, ist mit hoher Wahrscheinlichkeit Fachlogik hineingerutscht.

> [!tip] Der Lackmustest
> Frage dich bei jeder Zeile im Controller: *Würde diese Zeile auch in einem CLI-Kommando oder einem Batch-Job stehen müssen?* Wenn ja, gehört sie nicht in den Controller, sondern eine Schicht tiefer.

## `GET` — lesen

Die häufigste Methode und die einzige, die man ohne Nachdenken cachen darf.

| | |
|---|---|
| **Semantik** | Repräsentation einer Ressource abrufen |
| **Safe / Idempotent** | ✅ / ✅ |
| **Request-Body** | keiner (technisch erlaubt, praktisch verboten — viele Proxies verwerfen ihn) |
| **Erfolg** | `200 OK` **mit** Body |
| **Fehler** | `404` (Element existiert nicht), `400`/`422` (ungültige Query) |

Die zwei Ausprägungen aus [[#CRUD Basics]]:

```
GET /bookings                     → 200, Body: [ {...}, {...} ]
GET /bookings/42                  → 200, Body: {...}  |  404 wenn es 42 nicht gibt
GET /bookings?product_id=X&limit=50&offset=0   → gefiltert und paginiert
```

> [!warning] Der Klassiker: leere Liste ist kein 404
> ```
> GET /bookings?product_id=GIBTSNICHT   → 200 OK, Body: []     ✅
>                                       → 404 Not Found        ❌
> ```
> Die **Sammlung** `/bookings` existiert — sie ist nur gerade leer. Ein `404` würde bedeuten, dass es den Endpunkt nicht gibt, und zwingt jeden Client, einen Fehlerfall zu behandeln, der keiner ist. `404` gilt ausschließlich für ein **Element**, das es nicht gibt.

Zwei Dinge, die man bei `GET` von Anfang an mitdenken sollte, weil sie später teuer nachzurüsten sind: **ein Default-Limit** (sonst liefert die Sammlung irgendwann alles) und **stabile Sortierung** (ohne `ORDER BY` ist Paginierung bedeutungslos, weil die Reihenfolge zwischen zwei Anfragen wechseln kann).

## `POST` — erzeugen

Die vielseitigste und am häufigsten missbrauchte Methode.

| | |
|---|---|
| **Semantik** | Der Ressource *untergeordnet* etwas Neues erzeugen bzw. einen Vorgang auslösen |
| **Safe / Idempotent** | ❌ / ❌ |
| **Ziel** | die **Sammlung** (`/bookings`), nicht das Element |
| **Erfolg** | `201 Created` + **`Location`-Header** + Body der erzeugten Ressource |
| **Fehler** | `422` (Validierung), `409` (Duplikat/Konflikt), `400` |

```http
POST /bookings HTTP/1.1
Content-Type: application/json

{"product_id": "A1", "start_date": "2026-08-01", "nights": 3}
```
```http
HTTP/1.1 201 Created
Location: /bookings/1042
Content-Type: application/json

{"id": 1042, "product_id": "A1", "start_date": "2026-08-01", "nights": 3, "status": "open"}
```

Warum der Body zurückkommt, obwohl der Client die Daten doch selbst geschickt hat: Weil der Server sie **ergänzt** hat — `id`, `status`, Zeitstempel, normalisierte Werte. Der Client soll nicht raten müssen, wie das Objekt jetzt aussieht, und keine zweite Anfrage brauchen.

**Die fehlende Idempotenz ist das eigentliche Thema bei `POST`.** Genau hier greift das Timeout-Problem aus [[#Client/Server]]: Der Client weiß nach einem Timeout nicht, ob die Buchung angelegt wurde — sendet er erneut, hat er womöglich zwei. Die industrietaugliche Lösung ist der **`Idempotency-Key`**: Der Client erzeugt eine eindeutige ID, schickt sie im Header mit, und der Server erkennt daran eine Wiederholung und liefert die ursprüngliche Antwort erneut, statt ein zweites Objekt anzulegen.

`POST` ist außerdem das **Auffangbecken** für alles, was nicht in die anderen drei Methoden passt — Vorgänge (siehe [[#CRUD Basics]]) und Suchanfragen, die zu komplex für eine URL sind (`POST /bookings/search`). Beides ist vertretbar, sollte aber jeweils eine bewusste Entscheidung sein.

---

## `PUT` — vollständig ersetzen (und `PATCH`)

| | `PUT` | `PATCH` |
|---|---|---|
| **Semantik** | Ressource **vollständig** ersetzen | Ressource **teilweise** ändern |
| **Body enthält** | das **komplette** Objekt | nur die zu ändernden Felder |
| **Idempotent** | ✅ immer | ⚠️ nicht garantiert |
| **Ziel** | das **Element** (`/bookings/42`) | das Element |
| **Erfolg** | `200 OK` + Body **oder** `204 No Content` | `200 OK` + Body |
| **Fehler** | `404`, `422`, `409`, ggf. `412` |  |

> [!warning] Der teuerste Anfängerfehler bei `PUT`
> `PUT` bedeutet **„die Ressource soll ab jetzt genau so aussehen"** — nicht „ändere die Felder, die ich mitschicke".
> ```
> Bestand:  {"id": 42, "product_id": "A1", "nights": 3, "status": "open"}
> PUT /bookings/42  {"nights": 5}
> ```
> Korrekt umgesetzt sind `product_id` und `status` danach **leer**. Wer nur `nights` ändern will, muss entweder das ganze Objekt schicken oder `PATCH` nehmen. In der Praxis führt die Verwechslung zu stillem Datenverlust — das Objekt ist noch da, nur halb leer, und niemand merkt es, bis jemand nachfragt.

Ein Detail, das oft überrascht: **`PUT` darf erzeugen.** Wenn der Client die Adresse bestimmen kann (etwa bei fachlichen Schlüsseln wie `/capacity/A1/2026-08-01`), ist `PUT` auf eine noch nicht existierende Ressource ein legitimes Upsert — Antwort dann `201 Created` statt `200`. Faustregel: **Server vergibt die ID → `POST`. Client kennt die ID → `PUT`.**

Für `PATCH` gibt es zwei standardisierte Body-Formate, die man kennen sollte: **JSON Merge Patch** (RFC 7396 — sieht aus wie das Teilobjekt, `null` löscht ein Feld) und **JSON Patch** (RFC 6902 — eine Liste von Operationen: `[{"op": "replace", "path": "/nights", "value": 5}]`). In der Praxis nimmt man meist Ersteres, oft ohne den Namen zu kennen.

**Das Lost-Update-Problem**, das an `PUT`/`PATCH` hängt: Zwei Clients lesen dasselbe Objekt, beide ändern etwas, beide schreiben zurück — die zweite Änderung überschreibt die erste unbemerkt. Die HTTP-Antwort darauf ist **optimistisches Locking** mit `ETag`: Der Client schickt `If-Match: <etag>`, und der Server antwortet mit `412 Precondition Failed`, wenn sich die Ressource inzwischen geändert hat. Sobald mehrere Clients schreiben, ist das kein Luxus mehr.

## `DELETE` — löschen

| | |
|---|---|
| **Semantik** | Ressource entfernen |
| **Safe / Idempotent** | ❌ / ✅ |
| **Ziel** | das **Element** |
| **Request-Body** | keiner |
| **Erfolg** | `204 No Content` (üblich) · `200 OK` + Body · `202 Accepted` (asynchron) |
| **Fehler** | `404`, `409` (z. B. noch referenziert) |

> [!important] Warum `DELETE` idempotent ist, obwohl der zweite Aufruf `404` liefert
> Ein häufiger Stolperstein. **Idempotenz ist eine Aussage über den Zustand des Servers, nicht über den Statuscode.** Nach dem ersten `DELETE /bookings/42` ist die Buchung weg; nach dem zweiten ist sie immer noch weg — der Zustand ist identisch, die Methode also idempotent. Dass der zweite Aufruf `404` statt `204` antwortet, ändert daran nichts.
>
> (Manche APIs antworten deshalb bewusst immer mit `204`, auch wenn nichts zu löschen war. Beides ist vertretbar; nur konsistent muss es sein.)

Praktisch entscheidet man bei `DELETE` außerdem, ob wirklich gelöscht wird (**Hard Delete**) oder nur ein `deleted_at` gesetzt wird (**Soft Delete**). Bei Soft Delete stellt sich die Folgefrage, was ein späteres `GET` liefert: `404` (so tun, als wäre es weg) oder `410 Gone` (ehrlicher: „gab es, gibt es nicht mehr").

## Was geben POST, PUT und DELETE zurück?

> [!question]- Welche Antworten geben POST/PUT und DELETE nach REST Best Practice zurück?
> | Methode | Statuscode | Body | Header |
> |---|---|---|---|
> | **`POST`** (erzeugt) | **`201 Created`** | die **erzeugte Ressource** (mit ID und servergesetzten Feldern) | **`Location`** auf die neue Ressource — verpflichtend |
> | **`POST`** (Vorgang, asynchron) | `202 Accepted` | Status des Vorgangs | `Location` auf die Vorgangs-Ressource |
> | **`PUT`** (ersetzt) | `200 OK` mit Body **oder** `204 No Content` | die aktualisierte Ressource bzw. keiner | — |
> | **`PUT`** (hat erzeugt) | `201 Created` | die erzeugte Ressource | `Location` |
> | **`PATCH`** | `200 OK` | die aktualisierte Ressource | — |
> | **`DELETE`** | **`204 No Content`** (oder `200` mit Body, `202` asynchron) | üblicherweise **keiner** | — |
>
> **Die Begründungen dahinter — wichtiger als die Tabelle:**
> - **`POST` → Body zurückgeben**, weil der Server Felder ergänzt hat (ID, Status, Zeitstempel). Der Client spart sich ein sofortiges `GET`.
> - **`Location` bei `201`**, weil der Client die Adresse der neuen Ressource sonst nicht kennt — er hat die ID ja nicht vergeben.
> - **`PUT` darf `204`**, weil der Client den Inhalt bereits kennt: Er hat ihn gerade selbst geschickt. Body zurückzugeben ist trotzdem freundlicher, wenn der Server normalisiert oder ergänzt.
> - **`DELETE` → `204`**, weil es zu einer gelöschten Ressource nichts mehr zu sagen gibt. Ein `204` **darf** definitionsgemäß keinen Body haben.
> - **Fehler immer über den Statuscode**, nie über ein Feld im Body (siehe das Anti-Pattern in [[#HTTP Basics]]).
>
> **Die eigentliche Best Practice ist Konsistenz:** Es ist weniger schlimm, `DELETE` mit `200` statt `204` zu beantworten, als es *manchmal* so und *manchmal* anders zu tun.

## Naming-Konventionen für REST-Endpunkte

> [!question]- Wie sind die Naming-Konventionen von REST-Endpunkten?
> Es gibt keinen verbindlichen Standard, aber einen sehr breiten Konsens (am besten dokumentiert in den [Zalando RESTful API Guidelines](https://opensource.zalando.com/restful-api-guidelines/)):
>
> | Regel | ✅ | ❌ |
> |---|---|---|
> | **Substantive, keine Verben** — die Methode ist das Verb | `POST /bookings` | `POST /createBooking` |
> | **Plural für Sammlungen** | `/bookings`, `/bookings/42` | `/booking/42` |
> | **Kleinschreibung** | `/price-recommendations` | `/PriceRecommendations` |
> | **Bindestrich statt Unterstrich** im Pfad | `/price-recommendations` | `/price_recommendations` |
> | **Kein abschließender Slash** | `/bookings` | `/bookings/` |
> | **Keine Dateiendungen** — Format über `Accept` | `/bookings` | `/bookings.json` |
> | **Hierarchie für Beziehungen** | `/units/42/bookings` | `/getBookingsForUnit?id=42` |
> | **Filter in die Query, nicht in den Pfad** | `/bookings?status=open` | `/bookings/open` |
> | **Version am Anfang** (falls versioniert) | `/v1/bookings` | `/bookings/v1` |
>
> **Die zwei Regeln dahinter, aus denen sich der Rest ableitet:**
> 1. **Der Pfad beschreibt ein *Ding*, die Methode die *Handlung*.** Steht ein Verb im Pfad, ist meistens die Methode falsch gewählt.
> 2. **Verschachtelung höchstens eine Ebene tief.** `/units/42/bookings` ist gut, `/units/42/bookings/7/items/3` nicht — ab da nimmt man eine eigene Top-Level-Ressource mit Filter (`/items?booking_id=7`). Sonst hängt jede URL von einer Hierarchie ab, die sich fachlich ändern kann.
>
> **Zum JSON-Body** (eine eigene Frage): Feldnamen konsistent in *einem* Stil — im Python/FastAPI-Umfeld üblicherweise `snake_case`, im JS-lastigen Umfeld `camelCase`. Wichtiger als die Wahl ist, dass es überall gleich ist. Zeitstempel als **ISO 8601** mit Zeitzone (`2026-08-01T14:30:00Z`), Datumsangaben als `2026-08-01`.

## Ein Controller oder viele?

> [!question]- Wann sollte man statt eines großen Controllers mehrere kleine nutzen? Wie managt man mehrere Controller (speziell in Python/FastAPI)?
> **Die Grundregel: ein Controller pro Ressource** — genauer: pro *Aggregat*, also pro fachlich zusammengehöriger Einheit. `bookings.py`, `prices.py`, `capacity.py`, `recommendations.py`. Nicht ein Controller pro Endpunkt (zu kleinteilig) und nicht einer für alles (unwartbar).
>
> **Konkrete Anlässe zum Aufteilen:**
> - Die Datei überschreitet grob **200–300 Zeilen** oder ~10 Endpunkte.
> - Die Endpunkte gehören **verschiedenen fachlichen Themen** an — das ist das eigentliche Kriterium, nicht die Zeilenzahl.
> - Sie haben **unterschiedliche Zugriffsrechte** (öffentlich vs. Admin) oder unterschiedliche Lebenszyklen.
> - Die Swagger-UI wird unübersichtlich: Die **Gruppierung dort entsteht aus den Routern** (`tags`), sie ist also auch ein UX-Argument nach außen.
>
> **In FastAPI heißt das Werkzeug `APIRouter`.** Jeder Router ist ein eigenständiges Bündel von Endpunkten mit gemeinsamem Präfix, gemeinsamen Tags und gemeinsamen Abhängigkeiten; die Hauptanwendung setzt sie zusammen:
>
> ```python
> # api/routers/bookings.py
> from fastapi import APIRouter
>
> router = APIRouter(prefix="/bookings", tags=["bookings"])
>
> @router.get("")                 # → GET /bookings
> def list_bookings(...): ...
>
> @router.get("/{booking_id}")    # → GET /bookings/42
> def get_booking(...): ...
> ```
> ```python
> # api/main.py
> from fastapi import FastAPI
> from .routers import bookings, prices, recommendations
>
> app = FastAPI(title="Pricing API")
> app.include_router(bookings.router)
> app.include_router(prices.router)
> app.include_router(recommendations.router)
> ```
>
> Der Gewinn ist derselbe wie bei Schichten: **Das Präfix steht an genau einer Stelle**, die Gruppierung in der Dokumentation ergibt sich von selbst, und jeder Router ist einzeln testbar. Wächst die API weiter, kommt eine Ebene dazu — ein `api/v1/`-Router, der alle Unterrouter bündelt und selbst unter `/v1` eingehängt wird.
>
> **Was man dabei nicht tun sollte:** die Router nach *technischer* Ähnlichkeit schneiden (`alle_gets.py`, `alle_posts.py`) statt nach Fachlichkeit. Das ist der API-Ebenen-Zwilling von „Package by Layer statt Package by Feature".
>
> **Gemeinsame Abhängigkeiten** (Datenbank-Session, `PricingApp`, Authentifizierung) gehören nicht in jeden Router einzeln, sondern über FastAPIs `Depends` an einen Ort — entweder pro Router (`APIRouter(dependencies=[...])`) oder global. Das ist die FastAPI-Ausprägung von Dependency Injection und kommt beim Stichwort [[#FastAPI + Uvicorn + Pydantic in Python]] ausführlich.

## Bezug zum eigenen Projekt

Ein konkreter Zuschnitt für `pricing`, der die Vorgabe aus dem Leitfaden (je 2 × POST/PUT/GET/DELETE) erfüllt:

| Methode & Pfad | Was passiert | Antwort |
|---|---|---|
| `GET /bookings` | Liste, gefiltert über `?product_id=&from=&to=&limit=` | `200` + Liste |
| `GET /bookings/{id}` | eine Buchung | `200` / `404` |
| `POST /bookings` | Buchung anlegen | `201` + `Location` + Objekt |
| `PUT /bookings/{id}` | Buchung ersetzen | `200` / `404` |
| `DELETE /bookings/{id}` | Buchung löschen | `204` / `404` |
| `GET /prices` · `GET /prices/{id}` | Preise lesen | `200` / `404` |
| `POST /prices` | Preis anlegen | `201` + `Location` |
| `PUT /prices/{id}` | Preis ersetzen | `200` / `404` |
| `DELETE /prices/{id}` | Preis löschen | `204` / `404` |
| `GET /recommendations` | berechnete Empfehlungen, gefiltert | `200` + Liste |
| `POST /pricing-runs` | `PricingApp._compute()` anstoßen | `201`/`202` + `Location` |

Vier Punkte, die dabei zur Entscheidung anstehen:

1. **Die Element-URL von `/recommendations`** — `/recommendations/{id}` (interne DB-ID) oder `/recommendations/{product_id}/{date}` (fachlicher Schlüssel)? Die zweite Variante ist für Clients brauchbarer, koppelt die URL aber an das fachliche Modell. Eine echte API-Design-Entscheidung, kein Detail.
2. **`capacity`** — braucht es Schreibendpunkte, wenn die Daten ohnehin über `ingest.py` kommen? Eine API anzubieten, die niemand nutzen soll, ist auch eine Entscheidung.
3. **Router-Aufteilung** — vier Router (`bookings`, `prices`, `capacity`, `recommendations`) plus ggf. `pricing_runs`. Bei dieser Größe könnte man auch alles in eine Datei legen; die Aufteilung jetzt vorzunehmen kostet fast nichts und erspart das spätere Umsortieren.
4. **Die Exception-Zuordnung aus [[#HTTP Basics]] gehört genau hier hin** — aber **nicht** in jeden Handler als `try/except`. Der richtige Ort ist ein zentraler **Exception-Handler** (`@app.exception_handler(...)`), der die Hierarchie aus `exceptions.py` einmal auf Statuscodes abbildet. Sonst steht in jedem der elf Handler dieselbe Fehlerbehandlung.

Punkt 4 ist der wichtigste, weil er verhindert, dass die Controller aufgehen wie Hefeteig: **Ein Handler, der nur den Erfolgsfall beschreibt, bleibt kurz genug, um lesbar zu sein.**

# FastAPI + Uvicorn + Pydantic in Python

> [!info] Syntax steht woanders
> Dieser Abschnitt erklärt **Zusammenhang und Einordnung** — was die drei Bibliotheken sind, warum es genau drei sind und wie sie zusammenspielen. Die **Syntax zum Nachschlagen** (Dekoratoren, Parameter, Modelle, Dependencies, Konfiguration) steht in der eigenen Notiz [[FastAPI, Uvicorn & Pydantic - Syntax|FastAPI, Uvicorn & Pydantic – Syntax]] — analog zum [[SQLAlchemy Tutorial|SQLAlchemy Tutorial]] aus Kapitel 1.2.

## Warum das Stichwort hier steht

Alles Bisherige war sprachunabhängig: Schichten, HTTP, Ressourcen, Methoden. Jetzt kommt die Frage, mit welchen Werkzeugen man das in Python tatsächlich baut — und warum es dafür **drei** Bibliotheken braucht statt einer.

Genau das ist der erste Stolperstein: „FastAPI" wird umgangssprachlich für den ganzen Stack benutzt, obwohl FastAPI selbst weder einen Server mitbringt noch die Validierung macht. Wer die Aufgabenteilung nicht kennt, versteht später weder die Fehlermeldungen noch die Deployment-Anleitungen.

## Drei Bibliotheken, drei Aufgaben

| Bibliothek | Ist ein/e … | Beantwortet die Frage | Ohne sie … |
|---|---|---|---|
| **Uvicorn** | ASGI-**Server** | Wie kommen HTTP-Bytes vom Netzwerk in Python? | … läuft die Anwendung gar nicht |
| **FastAPI** | Web-**Framework** | Welche Funktion bearbeitet welchen Pfad? | … müsste man Routing selbst schreiben |
| **Pydantic** | **Datenvalidierung** | Sind diese Daten gültig, und was sind sie für Typen? | … wäre jeder Body ein ungeprüftes `dict` |

Der Weg einer Anfrage durch den Stapel:

```
Netzwerk (TCP)
   │
   ▼
┌───────────────────────────────────────────────┐
│ Uvicorn      rohe Bytes → HTTP parsen → ASGI  │  ← der Server
├───────────────────────────────────────────────┤
│ Starlette    Routing, Middleware, Request/     │  ← das ASGI-Toolkit
│              Response-Objekte                  │     (steckt in FastAPI drin)
├───────────────────────────────────────────────┤
│ FastAPI      Endpunkt finden, Parameter aus    │  ← das Framework
│              Pfad/Query/Body einsammeln        │
├───────────────────────────────────────────────┤
│ Pydantic     Daten prüfen und in echte Python- │  ← die Validierung
│              Typen umwandeln                   │
└───────────────────────────────────────────────┘
   │
   ▼
deine Handler-Funktion → PricingApp → …
```

Bemerkenswert ist die zweite Zeile: **Starlette** taucht in keiner Anleitung auf, macht aber die halbe Arbeit. FastAPI ist im Kern eine dünne, sehr clevere Schicht über Starlette (HTTP-Mechanik) und Pydantic (Daten) — genau deshalb ist es so klein und gleichzeitig so leistungsfähig.

## Wie Python zum Web kam — die kurze Geschichte

Die Aufteilung in drei Bibliotheken wirkt willkürlich, bis man weiß, wie sie entstanden ist. Sie ist das Ergebnis von 25 Jahren, in denen jeweils ein konkretes Problem gelöst wurde:

| Zeit | Schritt | Das Problem, das gelöst wurde |
|---|---|---|
| **1990er** | **CGI** | Der Webserver startet für *jede* Anfrage einen neuen Python-Prozess. Funktioniert, ist aber absurd langsam. |
| **2003** | **WSGI** (PEP 333) | Jedes Framework brachte seinen eigenen Serveradapter mit — Framework und Server waren fest verdrahtet. WSGI definiert **eine** Schnittstelle dazwischen: Seitdem läuft jedes Framework auf jedem Server. |
| **2005 / 2010** | **Django / Flask** | Zwei Gegenentwürfe: Django „batteries included" (ORM, Admin, Templates, alles dabei), Flask minimal („Microframework", man baut sich den Rest zusammen). |
| **2014** | **`asyncio`** (PEP 3156) | Python bekommt einen eingebauten Event Loop und mit `async`/`await` eine Syntax dafür. |
| **2016** | **ASGI** | WSGI ist strukturell synchron und kann kein `async`, keine WebSockets, keine langlebigen Verbindungen. ASGI ist der Nachfolger, der genau das nachrüstet. |
| **2018** | **FastAPI** | Typannotationen (seit Python 3.5) lagen brach — sie wurden nur von Editoren und mypy gelesen. FastAPI macht sie **zur Laufzeit** nutzbar und leitet daraus alles ab. |

Zwei Dinge werden daran sichtbar. Erstens: **Die Trennung Server ↔ Framework ist eine bewusste Errungenschaft**, keine Umständlichkeit. Sie ist derselbe Gedanke wie die Ports in deinem Projekt — eine Schnittstelle in der Mitte, damit beide Seiten unabhängig austauschbar sind. Zweitens: FastAPI ist nicht deshalb entstanden, weil jemand ein schnelleres Flask wollte, sondern weil **eine Sprachfunktion reif war, die vorher niemand ausgenutzt hatte**.

## WSGI und ASGI — warum es zwei Welten gibt

Um Uvicorn zu verstehen, muss man wissen, welches Problem es löst. Ein Python-Programm kann nicht direkt HTTP sprechen — irgendjemand muss den TCP-Socket aufmachen, Bytes lesen, die Anfrage parsen und sie in Python-Datenstrukturen übergeben. Damit nicht jedes Framework seinen eigenen Server mitbringen muss, gibt es dafür eine **Schnittstelle**:

| | **WSGI** (1997, PEP 333) | **ASGI** (ab 2016) |
|---|---|---|
| **Modell** | synchron, ein Aufruf pro Anfrage | asynchron, Ereignisse (`receive`/`send`) |
| **Nebenläufigkeit** | über Threads/Prozesse | über einen **Event Loop** |
| **Kann kein** | WebSockets, Server-Sent Events, langlebige Verbindungen | — |
| **Server** | Gunicorn, uWSGI, mod_wsgi | **Uvicorn**, Hypercorn, Daphne |
| **Frameworks** | Flask, Django (klassisch), Bottle | FastAPI, Starlette, Django (modern) |

Der Kern des Unterschieds ist nicht „schneller", sondern **wie gewartet wird**. Bei einer typischen API-Anfrage wartet der Prozess die meiste Zeit — auf die Datenbank, auf eine fremde API, auf die Festplatte. Im WSGI-Modell blockiert dieser Thread währenddessen und kann nichts anderes tun; will man 100 gleichzeitige Anfragen bedienen, braucht man ~100 Threads (jeder mit eigenem Stack und Kontextwechselkosten).

Im ASGI-Modell **gibt** die Funktion beim Warten die Kontrolle **zurück** an den Event Loop, der in derselben Zeit andere Anfragen bearbeitet. Ein einziger Thread bedient so tausende wartende Verbindungen. Das ist der ganze Trick — und der Grund, warum das ausgerechnet für Webserver so gut passt: **API-Arbeit ist fast reines Warten (I/O-bound), kaum Rechnen.**

> [!warning] Die Falle, die daraus folgt
> Ein **blockierender** Aufruf in einer `async def`-Funktion legt den **gesamten** Event Loop lahm — also alle gleichzeitigen Anfragen, nicht nur die eigene. Der Klassiker ist eine synchrone Datenbankabfrage (SQLAlchemy im Standardmodus!) oder `time.sleep()` in einer `async`-Route.
>
> **Die pragmatische Regel für dein Projekt:** Solange die Anwendung synchron arbeitet (synchrones SQLAlchemy), schreibst du die Endpunkte als normales **`def`** — nicht `async def`. FastAPI führt `def`-Handler automatisch in einem **Threadpool** aus, wo Blockieren unschädlich ist. `async def` nimmt man erst, wenn wirklich alles darunter asynchron ist.
>
> Das ist die häufigste Fehlerquelle bei FastAPI-Einsteigern: `async def` überall hinzuschreiben, weil es modern aussieht, und damit den Server *langsamer* zu machen als ohne.

## Was eine ASGI-Anwendung wirklich ist

Der Punkt, an dem der ganze Stapel aufhört, magisch zu wirken. „ASGI-Anwendung" klingt nach einem großen Konzept — tatsächlich ist es **eine einzige Funktion mit drei Parametern**:

```python
async def app(scope, receive, send):
    await send({"type": "http.response.start", "status": 200,
                "headers": [(b"content-type", b"text/plain")]})
    await send({"type": "http.response.body", "body": b"Hallo"})
```

Das ist eine vollständige, lauffähige Webanwendung — `uvicorn modul:app` startet sie. Mehr verlangt die ASGI-Spezifikation nicht:

| Parameter | Was es ist |
|---|---|
| `scope` | ein `dict` mit den Metadaten der Verbindung: Methode, Pfad, Header, Client-Adresse |
| `receive` | eine Funktion, mit der man auf eingehende Ereignisse wartet (z. B. Body-Teile) |
| `send` | eine Funktion, mit der man Ereignisse zurückschickt (Status + Header, dann Body) |

> [!important] Was das erklärt
> **Alles, was FastAPI tut, mündet in genau diese Funktion.** Deine App ist am Ende ein aufrufbares Objekt, das Uvicorn mit `scope`, `receive` und `send` aufruft — Routing, Validierung und Serialisierung sind das, was FastAPI *davor* schaltet.
>
> Daraus folgt auch, warum die Trennung so sauber funktioniert: **Uvicorn muss über FastAPI nichts wissen** — nur, dass da eine Funktion mit dieser Signatur liegt. Genau dasselbe Muster wie `ports.py` in deinem Projekt: eine schmale Schnittstelle, hinter der beliebige Implementierungen liegen dürfen.

## Nebenläufigkeit: Prozesse, Threads, Event Loop

Drei Wege, mehrere Anfragen gleichzeitig zu bedienen — sie schließen sich nicht aus, sondern werden kombiniert:

| | **Prozesse** | **Threads** | **Event Loop** |
|---|---|---|---|
| **Was** | mehrere Python-Interpreter | mehrere Ausführungsstränge in einem Prozess | ein Strang, der zwischen wartenden Aufgaben wechselt |
| **Kosten pro Einheit** | hoch (eigener Speicher) | mittel (eigener Stack) | sehr gering |
| **Gut für** | **CPU-Arbeit** (umgeht die GIL) | blockierende Bibliotheken | **I/O-Warten** |
| **In diesem Stack** | `uvicorn --workers 4` | `def`-Handler (Threadpool) | `async def`-Handler |

Der Begriff, der das zusammenhält, ist die **GIL** (Global Interpreter Lock): In einem Python-Prozess kann immer nur *ein* Thread Python-Bytecode ausführen. Deshalb bringen Threads bei **Rechenarbeit** nichts — wohl aber beim **Warten**, denn während ein Thread auf die Datenbank wartet, gibt er die GIL frei.

Daraus folgt die Praxisregel für den Betrieb: **Der Event Loop skaliert das Warten, Prozesse skalieren das Rechnen.** Eine typische API wartet fast nur, deshalb reicht meist ein Event Loop pro CPU-Kern — also `--workers` in der Größenordnung der Kernanzahl, nicht mehr.

## Uvicorn — der Server

> [!question]- Was ist Uvicorn?
> Uvicorn ist ein **ASGI-Webserver** für Python: das Programm, das tatsächlich auf einem Port lauscht. Es nimmt TCP-Verbindungen an, parst HTTP, übersetzt die Anfrage in ASGI-Ereignisse, ruft deine Anwendung auf und schreibt die Antwort zurück auf den Socket.
>
> Es ist ausdrücklich **kein Framework**: Uvicorn kennt weder Routen noch Modelle noch deine Fachlichkeit. Es kennt nur die ASGI-Schnittstelle — deshalb kann derselbe Uvicorn jede ASGI-Anwendung ausführen (FastAPI, Starlette, Django).
>
> **Warum es schnell ist:** Es setzt auf `uvloop` (ein Event Loop auf Basis von libuv, derselben Bibliothek wie in Node.js) und `httptools` (HTTP-Parser aus nginx-Code) — beides C-Implementierungen.
>
> **Die Arbeitsteilung merkt man sich am besten am Startbefehl:**
> ```bash
> uvicorn pricing.api.main:app --reload
> #  └─┬──┘ └────────┬───────┘ └─┬─┘  └──┬───┘
> #  Server    Modulpfad      Objekt   nur Entwicklung!
> ```
> **FastAPI beschreibt die Anwendung, Uvicorn führt sie aus.**
>
> **Entwicklung vs. Produktion:** `--reload` startet bei jeder Dateiänderung neu und ist ausschließlich für die Entwicklung. In Produktion nimmt man mehrere **Worker** (`--workers 4`, mehrere Prozesse gegen die GIL-Grenze) und stellt üblicherweise einen Reverse Proxy (nginx, Traefik) davor, der TLS, Kompression und statische Dateien übernimmt.

## Bibliothek oder Framework? — der Unterschied, der hier sichtbar wird

Der Leitfaden fragt nach der „beliebtesten **Library**". Genau genommen sind die drei aber nicht dasselbe, und der Unterschied ist mehr als Wortklauberei:

| | **Bibliothek** | **Framework** |
|---|---|---|
| **Wer ruft wen?** | **Du** rufst den Code auf | **Der Code ruft dich** auf |
| **Kontrollfluss** | liegt bei dir | liegt beim Framework |
| **Beispiele hier** | Pydantic, SQLAlchemy, `requests` | FastAPI, Django, pytest |

Das Prinzip dahinter heißt **Inversion of Control**, umgangssprachlich das **„Hollywood-Prinzip": *Don't call us, we'll call you.*** Du schreibst keine `main()`, die Anfragen abholt — du **registrierst** Funktionen (per Dekorator) und übergibst die Kontrolle. Wann deine Funktion läuft, entscheidet FastAPI.

Zwei Dinge werden dadurch klar:

- **Ein Framework ist eine Architekturentscheidung** im Sinne von [[#Softwarearchitektur]] — schwer zu ändern, weil die gesamte Presentation-Schicht seine Form annimmt. Eine Bibliothek tauscht man aus, ein Framework nicht.
- **Pytest funktioniert genauso** (du schreibst `test_*`-Funktionen, pytest ruft sie auf) — das Muster ist dir aus [[1.3 Testing mit PyTest - Vertiefung|Kapitel 1.3]] also längst vertraut, es hatte nur noch keinen Namen.

Genau deshalb ist es so wichtig, dass der Controller dünn bleibt: **Alles, was in einer FastAPI-Handler-Funktion steht, ist an FastAPI gebunden.** Was in `core/` steht, ist es nicht.

## FastAPI — das Framework

> [!question]- Was macht FastAPI zur aktuell beliebtesten Library für API-Design?
> Die kurze Antwort: **Es benutzt Pythons Typannotationen als einzige Quelle der Wahrheit.** Eine Deklaration erledigt fünf Aufgaben gleichzeitig.
>
> ```python
> @app.post("/bookings", status_code=201)
> def create_booking(booking: BookingCreate) -> BookingRead:
>     ...
> ```
> Aus diesen zwei Zeilen folgt automatisch:
> 1. **Routing** — Pfad und Methode
> 2. **Deserialisierung** — JSON-Body → Python-Objekt
> 3. **Validierung** — falsche Typen ⇒ `422` mit präziser Fehlermeldung, ohne eine Zeile Prüfcode
> 4. **Serialisierung** — Rückgabeobjekt → JSON, gefiltert auf die Felder von `BookingRead`
> 5. **Dokumentation** — OpenAPI-Schema und Swagger UI (siehe [[#Swagger & OpenAPI]])
>
> Dazu kommen Autovervollständigung und Typprüfung im Editor, weil alles echte Typen sind.
>
> **Das Problem, das FastAPI damit löst:** In klassischen Frameworks steht jedes Detail **dreimal** — im Validierungscode, in der Serialisierung und in der Dokumentation. Diese drei laufen zwangsläufig auseinander, und die Dokumentation ist zuerst gelogen. FastAPI macht Divergenz strukturell unmöglich, weil es nur *eine* Definition gibt.
>
> **Die weiteren Gründe für die Beliebtheit:**
> - **Dependency Injection** als eingebautes Konzept (`Depends`) — Datenbank-Session, Authentifizierung, gemeinsame Parameter sauber und testbar, mit einfachem Ersetzen in Tests (Dependency Overrides). Das ist genau das Muster aus [[#n-tier Architektur]], nur auf Framework-Ebene.
> - **Async nativ**, ohne Nachrüstlösung — und trotzdem funktionieren synchrone Handler korrekt (Threadpool).
> - **Standards statt Eigenbau**: OpenAPI, JSON Schema, OAuth2, JSON:API-kompatible Fehler. Man lernt Standards, nicht Framework-Folklore.
> - **Ausgezeichnete Dokumentation** — sie ist gleichzeitig das beste Tutorial zum Thema und einer der realen Gründe für die Verbreitung.
> - **Geschwindigkeit** — durch ASGI und den Rust-Kern von Pydantic v2 in der Spitzengruppe der Python-Frameworks. Das ist der *am häufigsten genannte* und ehrlicherweise der **am wenigsten wichtige** Grund: In fast jeder realen Anwendung ist die Datenbank der Flaschenhals, nicht das Framework.
>
> **Was man dazusagen sollte:** FastAPI ist jung, kleiner im Funktionsumfang als Django (kein ORM, kein Admin, keine Templates, keine Migrationen — all das bringt man selbst mit) und hing lange stark an einer einzelnen Person (Sebastián Ramírez). Für eine reine API ist genau dieser Zuschnitt aber ein Vorteil, kein Mangel.

## Warum Typannotationen überhaupt zur Laufzeit wirken können

Der Trick, auf dem der gesamte Stack beruht — und ein Punkt, der in Tutorials fast nie erklärt wird.

**Normalerweise tut Python mit Typannotationen nichts.** Sie sind reine Metadaten:

```python
def f(x: int) -> str:
    return x          # läuft ohne Fehler durch — Python prüft nichts

f("kein int")         # ebenfalls kein Laufzeitfehler
```

Annotationen werden zur Laufzeit lediglich in `__annotations__` abgelegt. Wer sie prüft, sind **externe, statische** Werkzeuge: mypy, Pyright, der Editor — alle **vor** der Ausführung.

```python
f.__annotations__     # → {'x': <class 'int'>, 'return': <class 'str'>}
```

**Genau hier setzen Pydantic und FastAPI an:** Sie lesen dieses Dictionary **zur Laufzeit** aus (per `inspect.signature` und `typing.get_type_hints`) und bauen daraus Validierungsregeln, JSON-Schemata und Konvertierungen.

> [!important] Die Kernaussage
> **Statische Typprüfung** (mypy) und **Laufzeitvalidierung** (Pydantic) benutzen dieselbe Schreibweise für zwei völlig verschiedene Dinge:
> - mypy sagt dir **vor** dem Start, dass dein *Code* nicht zusammenpasst.
> - Pydantic sagt dir **während** des Laufs, dass die *Daten* nicht passen.
>
> Beides ist nötig, und keines ersetzt das andere: Dein Code kann perfekt typgeprüft sein und trotzdem Müll von außen bekommen (siehe [[#Client/Server]] — Eingaben sind nicht vertrauenswürdig).

Das erklärt auch eine häufige Verwirrung: Warum FastAPI aus `nights: int` einen `422`-Fehler machen kann, mypy denselben Fehler aber nicht findet. mypy sieht nur deinen Code — die eingehende JSON-Nachricht existiert für es gar nicht.

## Pydantic — Datenvalidierung

> [!question]- Wofür braucht man Pydantic?
> Pydantic ist die Bibliothek, die aus **unbekannten Daten von außen** geprüfte Python-Objekte macht. Sie sitzt genau an der Systemgrenze, die in [[#Client/Server]] beschrieben wurde: Alles, was über HTTP hereinkommt, ist erst einmal nicht vertrauenswürdig.
>
> Was sie konkret leistet:
> - **Validierung** — stimmen Typen, Pflichtfelder, Wertebereiche, Formate (E-Mail, URL, Datum)?
> - **Konvertierung (Parsing)** — der String `"2026-08-01"` aus dem JSON wird zu einem echten `datetime.date`, `"42"` zu `int`. JSON kennt weder `date` noch `Decimal`; irgendjemand muss übersetzen.
> - **Serialisierung** — der Rückweg: Python-Objekt → JSON, inklusive Feldauswahl und Aliasnamen.
> - **Schema-Erzeugung** — daraus entsteht das JSON Schema, aus dem FastAPI die OpenAPI-Doku baut.
> - **Konfiguration** — `pydantic-settings` liest Einstellungen aus Umgebungsvariablen und prüft sie beim Start, statt beim ersten Zugriff (relevant für deine DB-URL).
>
> **Der Denkansatz dahinter** heißt „**Parse, don't validate**": Man prüft Daten nicht nur und arbeitet danach weiter mit dem rohen `dict`, sondern **verwandelt** sie in einen Typ, der ungültige Zustände gar nicht mehr darstellen kann. Danach ist die Prüfung im Typ *enthalten* — man muss nie wieder `if "nights" in data` schreiben. Alles hinter der Grenze arbeitet mit garantiert gültigen Objekten.
>
> **Warum ohne Pydantic der Aufwand explodiert:** Ohne sie steht in jedem Handler dieselbe Prüfkaskade („ist der Schlüssel da? ist es eine Zahl? ist sie positiv? ist das Datum parsbar?"), fehleranfällig, uneinheitlich formuliert und ohne jede Dokumentation. Pydantic ersetzt das durch eine Klassendefinition.
>
> **Pydantic v1 vs. v2:** v2 (2023) hat den Kern in Rust neu geschrieben (`pydantic-core`) und ist um ein Vielfaches schneller, aber die API hat sich an einigen Stellen geändert (`@validator` → `@field_validator`, `.dict()` → `.model_dump()`, `class Config` → `model_config`). Beim Lesen von Blogposts und Stack-Overflow-Antworten immer prüfen, welche Version gemeint ist — das ist die häufigste Quelle für Beispiele, die nicht laufen.

## Der Lebenszyklus einer Anfrage, Schritt für Schritt

Alles Bisherige an einem einzigen `POST /bookings` durchgespielt — das ist die Erzählung, mit der man den Stack im Gespräch erklärt:

| # | Wer | Was passiert |
|---|---|---|
| 1 | Betriebssystem | Ein TCP-Paket trifft auf Port 8000 ein |
| 2 | **Uvicorn** | Liest die Bytes, parst die HTTP-Anfrage (`httptools`), baut den `scope` |
| 3 | **Uvicorn** | Ruft die ASGI-Anwendung auf: `app(scope, receive, send)` |
| 4 | **Starlette** | Middleware-Kette von außen nach innen (CORS, Logging, Request-ID …) |
| 5 | **Starlette** | Routing: Welcher Endpunkt passt zu `POST /bookings`? Kein Treffer → `404`, falsche Methode → `405` |
| 6 | **FastAPI** | Löst die Dependencies auf (`Depends`) — z. B. wird die DB-Session geöffnet |
| 7 | **FastAPI** | Sammelt die Parameter ein: Pfad, Query, Header, Body |
| 8 | **Pydantic** | Validiert und konvertiert den Body → bei Fehler **sofort `422`**, dein Code läuft nie an |
| 9 | **dein Handler** | Wird aufgerufen — mit fertigen, typisierten Objekten |
| 10 | **PricingApp** | Fachlogik, Persistenz — die unteren Schichten |
| 11 | **Pydantic** | Serialisiert das Ergebnis anhand des Response-Modells (Felder filtern!) |
| 12 | **FastAPI** | Baut die Response: Statuscode, Header, JSON-Body |
| 13 | **Starlette** | Middleware-Kette rückwärts von innen nach außen |
| 14 | **FastAPI** | Räumt die Dependencies auf (Code nach dem `yield` — Session schließen) |
| 15 | **Uvicorn** | Schreibt die Antwort auf den Socket |

Drei Beobachtungen, die sich daraus ergeben und die man sich merken sollte:

- **Schritt 8 ist die Systemgrenze.** Ab hier arbeitet *dein* Code ausschließlich mit gültigen Daten. Ungültige Anfragen erreichen deine Fachlogik nie — das ist der eigentliche Gewinn von Pydantic.
- **Die Middleware ist eine Zwiebel**, kein Stapel: außen → innen → Handler → innen → außen. Deshalb kann dieselbe Middleware sowohl die Dauer messen als auch Header an die Antwort hängen.
- **Schritt 14 kommt nach Schritt 12.** Das ist der Grund, warum die Session in einer `yield`-Dependency liegen muss und nicht im Handler geschlossen werden darf: Beim Serialisieren (Schritt 11) kann noch auf die Datenbank zugegriffen werden — bei ORM-Objekten mit Lazy Loading ist das der berüchtigte Fehler „Session is closed".

## FastAPI im Vergleich — Flask und Django

Zur Einordnung, weil die drei ständig gegeneinander gestellt werden:

| | **Flask** | **Django** | **FastAPI** |
|---|---|---|---|
| **Ansatz** | Microframework | „Batteries included" | API-fokussiert |
| **Enthält** | Routing, Templates | ORM, Admin, Auth, Migrationen, Templates, Forms | Routing, Validierung, Doku |
| **Validierung** | selbst / marshmallow | Forms & Serializers (DRF) | **eingebaut** über Pydantic |
| **API-Doku** | Zusatzpaket | Zusatzpaket (drf-spectacular) | **automatisch** |
| **Async** | nachgerüstet (WSGI) | seit 4.x, teilweise | **nativ** |
| **Stärke bei** | kleinen Diensten, voller Kontrolle | großen Anwendungen mit Datenmodell + Backoffice | **reinen REST-/JSON-APIs** |

Die ehrliche Zusammenfassung: **Django ist ein Haus, FastAPI ein sehr guter Werkzeugkasten.** Wer eine Anwendung mit Benutzerverwaltung, Adminoberfläche und HTML-Seiten baut, ist mit Django meist schneller. Wer eine JSON-API baut — dein Fall — ist mit FastAPI klar besser bedient, muss aber ORM (SQLAlchemy), Migrationen (Alembic) und Konfiguration selbst zusammenstellen. Genau das ist der Trade-off aus [[#Softwarearchitektur]] in Reinform: **Vollständigkeit gegen Passgenauigkeit.**

## Die Kehrseite des Stacks

Zum zweiten Gesetz der Architektur gehört, die Nachteile benennen zu können — auch bei Werkzeugen, die man mag:

- **Viel passiert implizit.** Woher ein Parameter kommt, entscheidet FastAPI anhand von Typ und Pfad. Das ist elegant, solange es funktioniert, und schwer zu durchschauen, wenn nicht — Fehlermeldungen zeigen dann in Framework-Interna statt in deinen Code.
- **Bindung an das Framework.** Alles, was im Handler steht, ist FastAPI-Code. Deshalb ist die Regel „Controller dünn halten" hier keine Kosmetik: Sie ist der Preis, den man **nicht** zahlen will, wenn das Framework einmal gewechselt wird.
- **Kein Standardaufbau.** Django gibt eine Projektstruktur vor, FastAPI nicht. Jedes Projekt erfindet seinen `api/`-Ordnerbaum neu — Freiheit, die ohne Disziplin in Beliebigkeit endet.
- **Versionsdynamik.** Der Bruch Pydantic v1 → v2 hat ein ganzes Ökosystem beschäftigt; FastAPI selbst ändert regelmäßig empfohlene Schreibweisen (`Query(None)` → `Annotated`). Man muss beim Lesen fremder Beispiele immer auf das Datum schauen.
- **`async` verleitet zu Fehlern.** Der Stack macht Asynchronität leicht *schreibbar*, aber nicht leicht *verstehbar* — siehe die Warnung oben.
- **Ein Ökosystem mit Lücken.** Kein Admin, keine Migrationen, keine Benutzerverwaltung. Für jedes davon muss man eine Entscheidung treffen und sie verantworten.

## Wo die drei in der Schichtenarchitektur leben

Der Bogen zurück zum Kapitelanfang — und die Antwort auf die Frage, was der Controller darf:

| Baustein | Schicht | Darf davon wissen |
|---|---|---|
| Uvicorn | außerhalb — Betrieb | nichts von deinem Code (nur ASGI) |
| FastAPI-Router / Handler | **Presentation** | die Service-Schicht (`PricingApp`), die Pydantic-Modelle |
| Pydantic-Modelle (DTOs) | **Presentation** (Grenze) | nur sich selbst — keine ORM-Klassen, keine Sessions |
| `PricingApp`, `core/` | Application/Business | Domain und Ports |
| SQLAlchemy, `adapters/` | Persistence | die Datenbank |

Die dritte Zeile ist die wichtige und wird später zur eigenen Kontrollfrage („warum müssen wir unsere Objekte nun doppelt definieren?"): **Pydantic-Modelle sind nicht dasselbe wie SQLAlchemy-Modelle**, auch wenn sie sich ähneln. Das eine beschreibt den **Vertrag nach außen**, das andere das **Speicherlayout**. Warum das kein vermeidbarer Doppelaufwand ist, kommt beim Stichwort [[#Validierung von Request/Response (Pydantic)]].

## Bezug zum eigenen Projekt

Der Stack ergänzt das, was schon steht — ohne es zu ersetzen:

```
src/pricing/
├── domain.py, core/, ports.py      ← unverändert, weiß nichts von HTTP
├── adapters/                       ← unverändert (SQLAlchemy)
├── main.py                         ← Composition Root des Batch-Laufs
└── api/                            ← NEU: die Presentation-Schicht
    ├── main.py                     ← FastAPI-App, Router einhängen, Exception-Handler
    ├── deps.py                     ← Depends: DB-Session, PricingApp bereitstellen
    ├── schemas/                    ← Pydantic-Modelle (DTOs)
    └── routers/                    ← bookings.py, prices.py, recommendations.py
```

Drei Punkte, die dabei zur Entscheidung anstehen:

1. **Zwei Composition Roots** — `main.py` (Batch) und `api/main.py` (Server) bauen dieselben Objekte zusammen. Die Frage aus den [[Weiterführende Stichpunkte|weiterführenden Stichpunkten]] wird hier real: Wie vermeidet man Duplikation? (Kandidat: eine gemeinsame Factory-Funktion, die beide aufrufen.)
2. **Lebensdauer der Objekte** — Die SQLAlchemy-`Engine` gehört einmal pro Prozess, die `Session` **pro Anfrage**. Das ist der klassische Fehler: eine globale Session, die nach dem ersten Fehler unbrauchbar ist und Daten zwischen Anfragen vermischt. FastAPIs `Depends` ist genau dafür da.
3. **`def` statt `async def`** — weil `adapters/` synchron ist. Bewusste Entscheidung, kein Versehen; sie gehört in den [[Umsetzungsstand (REST APIs & Layered Architecture)|Umsetzungsstand]].

# Validierung von Request/Response (Pydantic)

> [!info] Syntax steht woanders
> `Field`, `field_validator`, `model_validator`, `ConfigDict`, `model_dump` — die Schreibweisen stehen in [[FastAPI, Uvicorn & Pydantic - Syntax#5. Validierung - Field, Constraints, eigene Validatoren|FastAPI, Uvicorn & Pydantic – Syntax]]. Hier geht es um die Entwurfsfragen: **was** man wo validiert und **warum** die Modelle so geschnitten sind.

## Warum das Stichwort hier steht

Das vorige Stichwort hat Pydantic als Werkzeug vorgestellt. Jetzt kommt die Frage, die tatsächlich Entwurfsarbeit ist: **Welche Modelle legt man an, und was prüft man wo?**

Das klingt nach einer Detailfrage und ist in Wahrheit die Stelle, an der die Schichtenarchitektur aus dem ersten Kapitelteil konkret wird. Denn ein Pydantic-Modell ist nicht einfach „das Objekt in JSON-Form" — es ist der **Vertrag zwischen deiner Anwendung und der Außenwelt**. Und Verträge macht man nicht aus Versehen.

## Validierung ist eine Schichtgrenze, kein Feature

Der wichtigste Gedanke vorweg: Validierung passiert nicht an *einer* Stelle, sondern auf **drei Ebenen**, die unterschiedliche Fragen beantworten:

| Ebene | Frage | Wer prüft | Fehler |
|---|---|---|---|
| **Protokoll** | Ist das überhaupt eine lesbare Anfrage? | Starlette/FastAPI | `400 Bad Request` |
| **Form (Schema)** | Sind die Felder da, richtig typisiert, im erlaubten Bereich? | **Pydantic** | `422 Unprocessable Content` |
| **Fachlichkeit** | Ergibt das *inhaltlich* Sinn — gibt es Produkt `A1`, ist die Einheit frei? | **`core/`**, nicht Pydantic | `404`, `409`, `422` |

Die Grenze zwischen Zeile 2 und 3 ist die entscheidende und wird ständig verletzt. Die Faustregel, die trägt:

> [!important] Die Trennlinie
> **Pydantic prüft alles, was sich ohne Datenbank und ohne Fachwissen entscheiden lässt.**
> Alles, wofür man *nachschauen* oder *rechnen* muss, gehört in die Business-Schicht.
>
> - `nights` ist eine positive ganze Zahl ≤ 365 → **Pydantic**
> - `start_date` liegt vor `end_date` → **Pydantic** (rein struktureller Vergleich)
> - Produkt `A1` existiert → **Business-Schicht** (braucht die Datenbank)
> - Es sind noch Einheiten frei → **Business-Schicht** (Fachregel)
>
> Warum das hart sein muss: Sobald ein Validator die Datenbank anfassen müsste, hat die Presentation-Schicht eine Abhängigkeit nach unten übersprungen — genau das, was [[#n-tier Architektur]] verbietet. Das DTO wäre dann nicht mehr isoliert testbar und nicht mehr wiederverwendbar.

Und die Regel aus [[#Client/Server]] bleibt bestehen: Eine Prüfung im Client ist Bedienkomfort, die Prüfung im Server ist Sicherheit. Jede Anfrage kann von `curl` kommen.

## Was ein DTO ist

> [!question]- Was ist ein DTO? Wofür braucht man es? Mit welcher Bibliothek setzt man es in Python um?
> Ein **DTO (Data Transfer Object)** ist ein Objekt, dessen einziger Zweck es ist, **Daten über eine Grenze zu transportieren**. Es enthält Felder und keine Fachlogik. Der Begriff stammt von Martin Fowler (*Patterns of Enterprise Application Architecture*) und entstand ursprünglich, um bei teuren Fernaufrufen nicht zwanzig Einzelabfragen zu machen, sondern alles Nötige in **einem** Objekt zu übertragen.
>
> **Wofür man es braucht — vier Gründe:**
> 1. **Entkopplung.** Der API-Vertrag ist unabhängig von den internen Klassen. Du kannst `domain.py` oder das Datenbankschema umbauen, ohne dass Clients brechen.
> 2. **Kontrolle darüber, was nach außen geht.** Interne Felder, Fremdschlüssel, Passwort-Hashes, `deleted_at` — alles, was im DTO nicht steht, kann nicht versehentlich veröffentlicht werden. Das ist ein **Sicherheitsmerkmal**, kein Komfort.
> 3. **Kontrolle darüber, was hereinkommt.** Ein Client soll `id` und `status` nicht selbst setzen dürfen. Steht es nicht im Eingangs-DTO, ist es unmöglich (statt „wird hoffentlich ignoriert").
> 4. **Ein passender Zuschnitt.** Die API-Sicht muss nicht der Datenstruktur folgen: Felder aus zwei Tabellen zusammenziehen, berechnete Werte ergänzen, Interna weglassen.
>
> **In Python setzt man DTOs mit Pydantic um** (`BaseModel`) — weil man dort Validierung, Serialisierung und Schema-Erzeugung geschenkt bekommt. Alternativen, die reine Datencontainer ohne Validierung sind: `dataclasses` (Standardbibliothek), `attrs`, `NamedTuple`, `TypedDict`, `msgspec` (schneller, schmaler). Für eine API ist Pydantic praktisch alternativlos, weil FastAPI daraus zusätzlich die OpenAPI-Doku baut.
>
> **Die Abgrenzung, die oft fehlt:** Ein DTO ist **kein Domain-Objekt**. `PriceableUnit` in deinem `domain.py` hat Regeln, Invarianten und berechnete Eigenschaften (`occupancy`, `total_capacity`) — es *bedeutet* etwas. Ein DTO bedeutet nichts, es transportiert nur.

## Ein Modell pro Richtung, nicht eines für alles

Die häufigste Einsteigerentscheidung ist ein einziges `Booking`-Modell für alles. Sie geht immer schief, weil **dieselbe Entität in verschiedenen Situationen verschiedene Felder hat**:

| Feld | `BookingCreate` (rein) | `BookingUpdate` (rein) | `BookingRead` (raus) |
|---|:---:|:---:|:---:|
| `id` | ✗ vergibt der Server | ✗ steht im Pfad | ✅ |
| `product_id` | ✅ Pflicht | ✅ Pflicht | ✅ |
| `nights` | ✅ Pflicht | ✅ Pflicht | ✅ |
| `status` | ✗ Server setzt `"open"` | ✅ | ✅ |
| `created_at` | ✗ | ✗ | ✅ |

Man sieht sofort, was ein einziges Modell erzwingen würde: Alle Felder müssten optional sein, damit alle Fälle passen — und damit validiert es nichts mehr. Der Vertrag wäre „schick irgendwas".

Zwei Konsequenzen, die daraus folgen:

- **`response_model` ist eine Sicherheitsgrenze.** FastAPI filtert die Antwort auf die Felder des Response-Modells. Gibt dein Handler versehentlich ein vollständiges ORM-Objekt zurück, wird trotzdem nur ausgeliefert, was im Modell steht. Ein Passwort-Hash, der im DTO fehlt, verlässt das System nicht — auch nicht durch ein Versehen.
- **`extra="forbid"` gehört an Eingangsmodelle.** Standardmäßig ignoriert Pydantic unbekannte Felder stillschweigend. Bei einem Request-Modell ist das die falsche Voreinstellung: Schickt ein Client `nigths: 3` (Tippfehler), soll er einen `422` bekommen und nicht wortlos eine Buchung mit Default-Werten.

Für `PATCH` gilt noch etwas Besonderes: Dort muss man zwischen „**Feld nicht geschickt**" und „**Feld auf `null` gesetzt**" unterscheiden können. Pydantic löst das über `model_dump(exclude_unset=True)` — ohne diese Unterscheidung überschreibt ein `PATCH` unbeabsichtigt Felder mit `None`.

## Warum die Objekte jetzt doppelt definiert werden

> [!question]- Warum müssen wir unsere Objekte nun doppelt definieren (Pydantic *und* SQLAlchemy)? Ist das nicht unnötig?
> **Kurzantwort: Nein — weil die beiden Modelle verschiedene Fragen beantworten und sich aus verschiedenen Gründen ändern.**
>
> | | **SQLAlchemy-Modell** | **Pydantic-Modell (DTO)** |
> |---|---|---|
> | **Beschreibt** | wie Daten **gespeichert** werden | wie Daten **übertragen** werden |
> | **Vertragspartner** | die Datenbank | die API-Clients |
> | **Enthält** | Spalten, Typen, Indizes, Fremdschlüssel, Beziehungen | Felder, Validierungsregeln, Beispiele, Beschreibungen |
> | **Ändert sich, wenn** | das Schema optimiert wird (Index, Normalisierung, Spaltentyp) | der fachliche Bedarf der Clients sich ändert |
> | **Schicht** | Persistence | Presentation |
>
> Die entscheidende Zeile ist die vierte: **Die beiden ändern sich zu unterschiedlichen Zeitpunkten aus unterschiedlichen Gründen.** Genau das ist das Kriterium, an dem man Verantwortlichkeiten trennt (Single Responsibility, hier auf Modellebene).
>
> **Was man verlöre, wenn man die ORM-Klassen direkt als API-Modelle nutzte:**
> - **Jede Schema-Änderung wäre ein Breaking Change.** Eine Spalte umbenennen, weil es intern sauberer ist — und alle Clients brechen. Man kann das Datenbankschema dann faktisch nicht mehr anfassen (vgl. „der Preis von Code-First" in [[#Softwarearchitektur]] und die teuerste Schicht in [[#n-tier Architektur]]).
> - **Interna würden veröffentlicht.** `capacity_id` als Fremdschlüssel interessiert keinen Client — verrät aber die interne Struktur. Passwort-Hashes und Löschmarkierungen wären standardmäßig sichtbar.
> - **Der Client könnte Felder setzen, die ihm nicht gehören** (`id`, `status`, `created_at`) — **Mass Assignment**, eine klassische Sicherheitslücke.
> - **Der Zuschnitt passte nicht.** Ein Client will `product_id` und `calendar_date` sehen, nicht `capacity_id`. In deinem Projekt ist das kein hypothetisches Beispiel, sondern genau der Fall bei `PriceRecommendation`.
> - **Lazy Loading würde durchschlagen.** Beim Serialisieren eines ORM-Objekts könnten unbeabsichtigt Nachladeabfragen ausgelöst werden — inklusive des „Session is closed"-Fehlers aus dem Lebenszyklus oben.
>
> **Die ehrliche Gegenposition** (die man kennen sollte, statt sie wegzudiskutieren): Bei einer kleinen, internen CRUD-Anwendung, bei der die API ohnehin nur die Tabelle spiegelt und es genau einen Client gibt, **ist** die doppelte Definition Overhead. Genau dafür gibt es **SQLModel** (vom FastAPI-Autor): eine Klasse, die gleichzeitig SQLAlchemy-Tabelle und Pydantic-Modell ist. Der Preis ist die Kopplung — man tauscht Trennung gegen Tippersparnis. Für ein Lernprojekt, in dem es *um* Schichten geht, ist die Trennung die richtige Wahl; in einem Prototyp kann SQLModel vernünftig sein.
>
> **Der Satz, den man sich merken sollte:** Es sind nicht zwei Definitionen desselben Dings, sondern **ein Ding und sein Vertrag**. Dass sie sich anfangs ähneln, ist ein Zufall des ersten Tages — sie driften auseinander, sobald das System lebt.

## Der Weg der Daten durch die Modelle

In deinem Projekt gibt es sogar **drei** Modellebenen, weil `domain.py` schon existiert:

```
JSON  ──►  BookingCreate  ──►  Booking          ──►  ORM-Booking  ──►  DB
          (Pydantic/DTO)      (domain.py)          (SQLAlchemy)
          Presentation         Domain               Persistence

DB  ──►  ORM-Booking  ──►  Booking  ──►  BookingRead  ──►  JSON
```

Wo die Übersetzung stattfindet, ist die eigentliche Entwurfsfrage:

| Übergang | Wo | Wie |
|---|---|---|
| JSON → DTO | FastAPI/Pydantic | automatisch |
| DTO → Domain | **Controller** (dünn!) oder eine Mapper-Funktion | explizit |
| Domain → ORM | Adapter (`adapters/`) | wie bisher |
| ORM → Domain → DTO | Adapter, dann Controller | `model_validate(...)` mit `from_attributes=True` |

Die eiserne Regel dabei: **`core/` und `domain.py` dürfen Pydantic nicht kennen.** Sonst hängt die Fachlogik an einer Presentation-Bibliothek, und der Batch-Lauf müsste FastAPIs Abhängigkeiten mitschleppen. Der Import zeigt immer nur nach innen.

> [!tip] Wenn drei Ebenen zu viel erscheinen
> Das ist ein berechtigtes Gefühl, und die Antwort lautet: Für ein System dieser Größe **darf** die Domain-Ebene beim Durchreichen manchmal übersprungen werden — solange es eine bewusste Entscheidung ist (vgl. Layer Bridging in [[#n-tier Architektur]]). Was nicht passieren darf, ist der umgekehrte Weg: dass Pydantic-Modelle in `core/` auftauchen, weil es gerade schneller ging.

## Wie ein Validierungsfehler aussieht

FastAPI liefert bei einem Pydantic-Fehler automatisch `422` mit einer **strukturierten** Antwort — das ist mehr wert, als es zunächst aussieht:

```json
{
  "detail": [
    {
      "type": "greater_than",
      "loc": ["body", "nights"],
      "msg": "Input should be greater than 0",
      "input": -3
    }
  ]
}
```

- **`loc`** ist der Pfad zum fehlerhaften Feld (`body`, `query`, `path` + Feldname, bei Verschachtelung auch tiefer). Ein Client kann damit den Fehler **am richtigen Formularfeld** anzeigen — deshalb ist eine Liste von Einzelfehlern besser als ein Fehlertext.
- Es werden **alle** Fehler auf einmal gemeldet, nicht nur der erste. Der Nutzer korrigiert einmal statt fünfmal.
- Die Meldungen sind englisch und technisch. Wer eigene Texte oder das Format aus [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) will, überschreibt den Handler für `RequestValidationError` — einmal zentral, nicht pro Endpunkt.

## Bezug zum eigenen Projekt

Ein konkreter Zuschnitt für `api/schemas/`:

| Modell | Zweck | Besonderheit |
|---|---|---|
| `BookingCreate` | `POST /bookings` | ohne `id`, `status` serverseitig |
| `BookingUpdate` | `PUT /bookings/{id}` | vollständig, ohne `id` |
| `BookingRead` | Antworten | mit `id`, `from_attributes=True` |
| `PriceCreate` / `PriceRead` | Preise | `Decimal` mit `decimal_places=2` — **nicht `float`** |
| `RecommendationRead` | nur lesend | fachlicher Zuschnitt statt `capacity_id` |
| `PricingRunRead` | Status eines Laufs | `id`, `status`, `started_at` |

Vier Punkte, die dabei zur Entscheidung anstehen:

1. **`RecommendationRead` ist der interessante Fall.** Die ORM-Klasse hat `capacity_id` als Fremdschlüssel; das DTO sollte stattdessen `product_id` und `calendar_date` zeigen. Damit ist die doppelte Definition an deinem eigenen Projekt belegt: **Die beiden Modelle haben nicht einmal dieselben Felder.**
2. **`Decimal` statt `float` für Preise** — konsequent aus Kapitel 1.2 weitergeführt. Pydantic serialisiert `Decimal` standardmäßig als JSON-Zahl; ob man Geldbeträge lieber als String überträgt (um Rundungsfehler in JavaScript-Clients zu vermeiden), ist eine bewusste Entscheidung.
3. **Die Validatoren aus `domain.py` nicht duplizieren.** `PriceableUnit` prüft bereits `booked_units >= 0` und wirft `DomainError`. Dieselbe Regel zusätzlich in Pydantic zu schreiben, klingt gründlich und ist gefährlich: Zwei Stellen, die auseinanderlaufen können. Besser: Pydantic prüft das **Format** (ist es überhaupt ein `int`?), die Domain prüft die **Regel**.
4. **`DomainError` → Statuscode.** Wenn die Fachvalidierung erst in `core/` zuschlägt, muss der zentrale Exception-Handler daraus einen `422` (oder `409`) machen. Das ist die letzte fehlende Zeile in der Zuordnungstabelle aus [[#HTTP Basics]].

# Swagger & OpenAPI

## Warum das Stichwort das Kapitel abschließt

Die API steht. Was fehlt, ist die Antwort auf eine Frage, die außerhalb des eigenen Rechners sofort gestellt wird: **Woher weiß jemand anders, was diese API kann?**

Die schlechte Antwort ist ein Word-Dokument im Firmenlaufwerk, das nach drei Wochen falsch ist. Die gute Antwort ist ein **maschinenlesbarer Vertrag**, der aus dem Code entsteht und deshalb nicht veralten kann. Genau das ist OpenAPI — und es ist der Grund, warum das Stichwort ans Ende gehört: Es macht aus einer laufenden Anwendung eine **benutzbare Schnittstelle**.

Und es schließt einen Bogen zum Anfang des Kapitels: Was hier entsteht, ist die Code-First-Variante aus [[#Softwarearchitektur]] — der Vertrag folgt der Implementierung, weil FastAPI ihn erzeugt.

## Die Begriffe auseinanderhalten

Die beiden Wörter werden synonym benutzt und meinen Verschiedenes:

|              | **OpenAPI**                                                 | **Swagger**                                 |
| ------------ | ----------------------------------------------------------- | ------------------------------------------- |
| **Was**      | eine **Spezifikation** — ein Dateiformat                    | eine **Werkzeugfamilie**                    |
| **Konkret**  | wie ein API-Beschreibungsdokument aufgebaut ist (JSON/YAML) | Swagger UI, Swagger Editor, Swagger Codegen |
| **Analogie** | die Grammatik                                               | die Programme, die sie lesen                |

Die Verwirrung hat historische Gründe: **Swagger** war ursprünglich beides — Format *und* Werkzeuge (ab 2011, später SmartBear). **2015 wurde die Spezifikation an die Linux Foundation gespendet** und in **OpenAPI Specification** umbenannt; die Werkzeuge behielten den Namen Swagger. Seither gilt:

> [!tip] Die saubere Sprechweise
> **Das Dokument heißt OpenAPI. Die Oberfläche, die es anzeigt, heißt Swagger UI.**
> „Swagger-Datei" sagt man umgangssprachlich trotzdem — meist ist ein OpenAPI-Dokument gemeint, gelegentlich aber tatsächlich noch die alte Version 2.0 (`swagger: "2.0"` in der ersten Zeile). Aktuell sind 3.0.x und 3.1.x; FastAPI erzeugt 3.1.

## Was in einem OpenAPI-Dokument steht

Es ist eine einzige JSON- oder YAML-Datei, die die gesamte API beschreibt:

```yaml
openapi: 3.1.0
info:                          # Titel, Version, Beschreibung, Kontakt, Lizenz
  title: Pricing API
  version: 0.1.0
servers:                       # unter welchen Basis-URLs die API erreichbar ist
  - url: http://localhost:8000
paths:                         # ← das Herzstück: alle Endpunkte
  /bookings/{booking_id}:
    get:
      summary: Buchung abrufen
      tags: [bookings]
      parameters:
        - name: booking_id
          in: path
          required: true
          schema: {type: integer, minimum: 1}
      responses:
        "200":
          content:
            application/json:
              schema: {$ref: "#/components/schemas/BookingRead"}
        "404":
          description: Buchung nicht gefunden
components:
  schemas:                     # alle Datenmodelle, einmal definiert und referenziert
    BookingRead: {...}
  securitySchemes: {...}       # wie man sich authentifiziert
```

Die Struktur bildet exakt das ab, was in diesem Kapitel besprochen wurde: **Pfade** (Ressourcen), **Methoden**, **Parameter** (Pfad/Query/Header), **Request Bodies**, **Responses pro Statuscode**, **Schemas**. Wer das Kapitel verstanden hat, kann ein OpenAPI-Dokument lesen — es ist die formale Fassung derselben Begriffe.

Zwei Details, die wichtig sind:

- **`components.schemas` benutzt JSON Schema.** Deshalb passt Pydantic so verlustfrei hinein: Pydantic *erzeugt* JSON Schema. In OpenAPI 3.1 ist die Kompatibilität sogar vollständig (in 3.0 gab es noch kleine Abweichungen).
- **`$ref` verweist statt zu duplizieren.** Ein Modell steht einmal da und wird überall referenziert — dieselbe Idee wie eine Klasse im Code.

## Wie FastAPI das Dokument erzeugt

FastAPI baut das Dokument **zur Laufzeit** aus dem, was ohnehin im Code steht — und stellt drei Endpunkte bereit:

| Endpunkt | Was | Wofür |
|---|---|---|
| `/openapi.json` | das rohe Dokument | für Werkzeuge |
| `/docs` | **Swagger UI** | zum **Ausprobieren** |
| `/redoc` | **ReDoc** | zum **Lesen** |

Woher die Inhalte kommen — das ist die praktisch nützlichste Tabelle des Stichworts:

| Im Dokument | Kommt aus |
|---|---|
| Pfad und Methode | dem Dekorator (`@router.get("/{booking_id}")`) |
| `tags` | `APIRouter(tags=[...])` bzw. dem Dekorator |
| `summary` | dem Funktionsnamen (oder explizit gesetzt) |
| `description` | dem **Docstring** der Handler-Funktion (Markdown!) |
| `parameters` | den Funktionsparametern samt `Path(...)`/`Query(...)`-Constraints |
| `requestBody` | dem Pydantic-Eingangsmodell |
| `responses["200"]` | `response_model` bzw. dem Rückgabetyp |
| Erfolgs-Statuscode | `status_code=201` |
| `components.schemas` | allen benutzten Pydantic-Modellen |
| Feldbeschreibungen | `Field(description=..., examples=[...])` |

Das erklärt auch, wie man die Doku **verbessert**, ohne sie zu schreiben: Docstrings ergänzen, `response_model` konsequent setzen, Beispiele in `Field` hinterlegen, Fehlerfälle über `responses={404: {"description": "..."}}` deklarieren. Jede dieser Maßnahmen verbessert gleichzeitig Code, Doku und Editor-Unterstützung — das ist der Kern des Code-First-Versprechens.

> [!warning] Die Kehrseite, die man kennen muss
> **Generierte Doku ist nur so gut wie der Code.** FastAPI garantiert, dass die Beschreibung **strukturell korrekt** ist — nicht, dass sie **verständlich** ist. Was OpenAPI systematisch *nicht* enthält:
> - Wie man anfängt („hol dir einen Token, dann …")
> - Warum es einen Endpunkt gibt und wann man ihn benutzt
> - Fachliche Zusammenhänge zwischen mehreren Aufrufen
> - Was die Werte *bedeuten* (`status: "open"` — und dann?)
>
> Eine API-Referenz ist eine **Landkarte, kein Reiseführer**. Beides wird gebraucht.

## Swagger UI und ReDoc

Beide zeigen dasselbe Dokument mit entgegengesetzter Absicht:

| | **Swagger UI** (`/docs`) | **ReDoc** (`/redoc`) |
|---|---|---|
| **Stärke** | **interaktiv** — „Try it out" schickt echte Anfragen | **lesbar** — dreispaltig, ruhig, gut für lange APIs |
| **Kann** | Anfragen ausführen, Auth eintragen, `curl`-Befehl zeigen | nur anzeigen |
| **Gut für** | Entwicklung und schnelles Ausprobieren | Referenz für Nutzer der API |

Der „Try it out"-Knopf in der Swagger UI ist das eigentliche Arbeitswerkzeug im Alltag: Formular ausfüllen, ausführen, Antwort und Statuscode sehen — und darunter den fertigen `curl`-Befehl zum Kopieren.

### Was `/docs` technisch zurückgibt

Naheliegende Annahme: eine statische HTML-Seite. Fast richtig — es ist HTML, aber es ist **fast leer** und liegt als Datei nirgends.

| # | Wer | Was |
|---|---|---|
| 1 | Browser | `GET /docs` |
| 2 | **FastAPI** | ruft `get_swagger_ui_html()` auf — eine **Python-Funktion**, die ~25 Zeilen HTML als String baut und als `HTMLResponse` zurückgibt |
| 3 | Browser | lädt `swagger-ui.css` und `swagger-ui-bundle.js` **vom CDN** (jsdelivr), nicht vom eigenen Server |
| 4 | Swagger-UI-JS | `GET /openapi.json` |
| 5 | **FastAPI** | erzeugt das OpenAPI-Dokument aus Routen und Pydantic-Modellen, cached es in `app.openapi_schema` |
| 6 | Swagger-UI-JS | rendert daraus die Oberfläche im Browser |

Das ausgelieferte HTML enthält **kein einziges Wort über deine Endpunkte** — nur ein leeres `<div id="swagger-ui">`, zwei CDN-Verweise und den Aufruf `SwaggerUIBundle({url: "/openapi.json"})`. Die gesamte Substanz kommt aus Schritt 5, und die ist **JSON**.

> [!important] `/docs` ist ein Client deiner eigenen API
> Die Swagger UI hat keinen privilegierten Zugang zu deiner Anwendung. Sie ruft denselben öffentlichen Endpunkt auf, den auch Postman oder ein Codegenerator benutzen würden — sie wird nur zufällig mitgeliefert. `/redoc` ist dasselbe Dokument mit einem anderen Renderer.

Selbst ansehen:

```bash
curl -s http://127.0.0.1:8000/docs          # das fast leere Ladeprogramm
curl -s http://127.0.0.1:8000/openapi.json | jq '.paths | keys'   # die Substanz
```

Drei praktische Konsequenzen:

1. **`/docs` braucht Internet — im Browser, nicht im Server.** Die CDN-Anfrage stellt der Browser. Eine vom Netz isolierte Anwendung liefert weiterhin ein funktionierendes `/docs`, solange der *Betrachter* online ist. Ohne Internet sieht man eine leere weiße Seite, obwohl die API einwandfrei läuft. Für abgeschottete Umgebungen hostet man die Assets selbst per `StaticFiles`.
2. **`/openapi.json` ist standardmäßig öffentlich** — auch wenn alle Router an `Depends(require_api_key)` hängen, denn FastAPI registriert `/docs`, `/redoc` und `/openapi.json` selbst und ohne diese Abhängigkeit. Das Dokument legt die **komplette API-Oberfläche** offen. In Produktion daher üblicherweise `docs_url=None, redoc_url=None, openapi_url=None` oder hinter Authentifizierung.
3. **„Try it out" braucht trotzdem den Schlüssel.** Die Oberfläche ist offen, die Aufrufe dahinter nicht.

## HTTP-Clients in der Entwicklung

> [!question]- Wie nutzt man HTTP-Clients wie Postman, Insomnia oder die Swagger UI bei der Entwicklung von REST APIs?
> Man benutzt sie **nicht alternativ, sondern in Phasen** — jedes Werkzeug hat eine Aufgabe, für die es das beste ist:
>
> | Werkzeug | Stärke | Grenze | Typischer Einsatz |
> |---|---|---|---|
> | **Swagger UI** (`/docs`) | sofort da, kennt das Schema, keine Einrichtung | keine gespeicherten Abläufe, keine Variablen, Auth umständlich | **Während des Entwickelns**: Endpunkt gerade geschrieben, sofort ausprobieren |
> | **Postman / Insomnia / Bruno** | Collections, Umgebungen (`{{base_url}}`), Variablen, Aufruf**ketten**, Tests, Teilen im Team | eigenes Werkzeug, das gepflegt werden will | **Wiederkehrende Abläufe**: Login → Buchung anlegen → abfragen |
> | **`curl` / HTTPie** | reproduzierbar, skriptbar, überall vorhanden | keine Historie, keine Oberfläche | **Ticket, README, CI, schnelle Prüfung** |
> | **`TestClient` (pytest)** | automatisiert, läuft bei jeder Änderung | kein exploratives Arbeiten | **Regression** — das Einzige, was dauerhaft schützt |
>
> **Der Arbeitsablauf, der sich in der Praxis einspielt:**
> 1. Endpunkt schreiben → **Swagger UI** öffnen, „Try it out", Fehler sehen, korrigieren. Der schnellste Kreislauf, den es gibt.
> 2. Funktioniert es, den `curl`-Befehl aus der Swagger UI kopieren — für die Notiz, das Ticket, den Kollegen.
> 3. Wird der Ablauf wiederkehrend (Auth, mehrere Schritte nacheinander), in **Postman/Insomnia/Bruno** als Collection ablegen. **Wichtig: nicht abtippen** — die Clients können `/openapi.json` **importieren** und erzeugen alle Anfragen daraus automatisch.
> 4. Was sich bewährt hat, wandert in einen **automatisierten Test**. Ein manueller Klick prüft einmal, ein Test prüft für immer.
>
> **Zwei Empfehlungen dazu:**
> - **Bruno** ist der jüngere Kandidat und für ein Repo besonders praktisch, weil er Anfragen als **Dateien im Projekt** speichert — versionierbar, reviewbar, kein Cloud-Konto. Postman ist mächtiger, drängt aber zunehmend in seine Cloud.
> - **Nie manuell testen, was ein Test prüfen kann.** Die Clients sind zum **Erkunden** da (was passiert, wenn ich das schicke?), nicht zum Absichern. Sobald du dieselbe Anfrage zum dritten Mal von Hand schickst, gehört sie in `tests/`.

## Was das Dokument sonst noch kann

Der Punkt, der Neulinge am meisten überrascht: Das OpenAPI-Dokument ist **kein Nebenprodukt für Menschen**, sondern maschinell weiterverwendbar:

- **Client-Code generieren** — `openapi-generator` erzeugt fertige Client-Bibliotheken für Python, TypeScript, Java und ein Dutzend andere Sprachen. Ein Frontend-Team programmiert dann gegen typisierte Funktionen statt gegen URLs.
- **Mock-Server** — Werkzeuge wie Prism liefern aus dem Dokument sofort eine Fake-API, gegen die andere Teams entwickeln können, bevor deine Implementierung fertig ist. (Das ist der praktische Kern von Design-First aus [[#Softwarearchitektur]].)
- **Linting** — **Spectral** prüft das Dokument gegen Style-Regeln („jeder Endpunkt braucht eine `summary`", „Pfade in Kebab-Case", „kein `POST` ohne `201`"). So werden aus den Naming-Konventionen erzwingbare Regeln statt Bitten.
- **Breaking Changes erkennen** — zwei Versionen des Dokuments vergleichen (`oasdiff`) und in der CI rot werden lassen, wenn ein Feld verschwindet. Die konkrete Antwort auf die Versionierungsfrage aus dem Architekturteil.
- **Import in Clients und Gateways** — Postman, Insomnia, Bruno, aber auch API-Gateways und Portale lesen das Dokument direkt ein.

## Bezug zum eigenen Projekt

Der Leitfaden verlangt ausdrücklich, sich mit der Swagger UI vertraut zu machen. Konkret:

1. **Anschauen, was ohne Zutun entsteht.** `uvicorn` starten, `/docs` öffnen — die Endpunkte sind bereits vollständig beschrieben, inklusive Modellen und `422`-Fehlerformat. Danach `/openapi.json` ansehen, um zu verstehen, dass die Oberfläche nur ein Betrachter für dieses Dokument ist.
2. **Aufräumen, was hässlich aussieht.** Fehlende `summary`, generische Namen, fehlende `tags`, Endpunkte ohne Beschreibung. Faustregel: **Wenn die Swagger UI unübersichtlich ist, ist die API unübersichtlich** — die Oberfläche ist ein ehrlicher Spiegel des Entwurfs.
3. **Fehlerfälle deklarieren.** Standardmäßig steht dort nur der Erfolgsfall und `422`. Dass ein `GET /bookings/{id}` auch `404` liefern kann, muss man ergänzen — sonst ist die Doku unvollständig, obwohl der Code korrekt ist.
4. **`/openapi.json` in Postman/Bruno importieren**, statt die Anfragen abzutippen.
5. **Optional, aber lehrreich:** Das Dokument in die Versionsverwaltung legen und bei Änderungen im Diff betrachten. Man sieht dann sehr direkt, welche Codeänderung den öffentlichen Vertrag verändert — und lernt dabei mehr über API-Design als aus jedem Artikel.

# Die drei Bausteine

| Baustein | Rolle |
|---|---|
| **`DeclarativeBase`** | Basisklasse; sammelt alle Modelle in einer Registry |
| **`MetaData`** | Der **Katalog aller Tabellen**. Hängt an `Base.metadata`. Aus ihm heraus passiert `create_all()`, und Alembic vergleicht später dagegen |
| **`Mapped[…]` / `mapped_column(…)`** | Eine Spalte. Die *Annotation* liefert Typ und Nullability, das *Argument* die Details |

```python
class Base(DeclarativeBase):
    metadata = MetaData(naming_convention=NAMING_CONVENTION)
    type_annotation_map = {str: Text}      # jedes Mapped[str] wird TEXT statt VARCHAR
```

`type_annotation_map` ist der bequeme Weg, projektweite Typentscheidungen einmal zu treffen, statt sie in jeder Spalte zu wiederholen.

# Wie aus einer Annotation eine Spalte wird

```python
product_id: Mapped[str] = mapped_column(Text, ForeignKey("products.product_id"))
#            └──┬───┘     └─┬─┘  └────────────┬──────────────┘
#          Typ + NOT NULL  Typ      Constraint
```

| Schreibweise | Ergebnis im DDL |
|---|---|
| `Mapped[str]` | `NOT NULL` |
| `Mapped[str \| None]` | nullable |
| `Mapped[int]` | `INTEGER` |
| `Mapped[float]` | `FLOAT` (in Postgres = `double precision`) |
| `Mapped[Decimal]` + `Numeric(12, 2)` | `NUMERIC(12,2)` |
| `Mapped[date]` | `DATE` |
| `Mapped[datetime]` + `DateTime(timezone=True)` | `TIMESTAMP WITH TIME ZONE` |
| `Mapped[str]` **ohne** Typangabe | ⚠️ `VARCHAR`, **nicht** `TEXT` |

**Die Nullability steckt in der Annotation, nicht in `nullable=`.** Das ist der 2.0-Stil und die häufigste Fehlerquelle beim Übersetzen von bestehendem SQL: Eine Spalte, die in der Datenbank `NULL` erlaubt, muss `Mapped[X | None]` sein — sonst erzeugt SQLAlchemy stillschweigend ein `NOT NULL`.

# Primärschlüssel — Identity, SERIAL, autoincrement

Die Frage, die den Unterschied macht: **Wer erzeugt den Zahlenwert, und darf man ihn überschreiben?**

| Schreibweise | DDL | Bedeutung |
|---|---|---|
| `mapped_column(BigInteger, primary_key=True)` | `BIGSERIAL` | SQLAlchemy nimmt automatisch `autoincrement` an → Postgres-Altlast: implizite Sequence + `DEFAULT nextval(...)`. Eigene Werte sind erlaubt. |
| `mapped_column(BigInteger, Identity(), primary_key=True)` | `GENERATED BY DEFAULT AS IDENTITY` | SQL-Standard. Sequence gehört zur Spalte. Eigene Werte sind erlaubt. |
| `mapped_column(BigInteger, Identity(always=True), primary_key=True)` | `GENERATED ALWAYS AS IDENTITY` | SQL-Standard. **Eigene Werte werden abgelehnt** (nur mit `OVERRIDING SYSTEM VALUE` möglich). |

**Warum `always=True` hier die richtige Wahl ist:** Die IDs vergibt ausschließlich die Datenbank. Der Ingest schreibt sie per `COPY` gar nicht mit (die Spalte steht nicht in der Spaltenliste), und niemand soll versehentlich eine ID mitliefern können. `GENERATED ALWAYS` macht daraus eine von der Datenbank durchgesetzte Regel statt einer Konvention.

`SERIAL` ist funktional ähnlich, gilt aber als überholt: Die Sequence ist ein separates Objekt, das man versehentlich löschen oder aus dem Tritt bringen kann, und das Verhalten ist nicht standardisiert.

# Berechnete Spalten — Computed

```python
net_revenue: Mapped[Decimal | None] = mapped_column(
    Numeric(12, 2),
    Computed("gross_revenue - discount_amount", persisted=True),
)
```

→ `net_revenue NUMERIC(12,2) GENERATED ALWAYS AS (gross_revenue - discount_amount) STORED`

- **`persisted=True`** = `STORED`: Der Wert wird **berechnet und gespeichert**, kostet Platz, ist beim Lesen gratis.
- **`persisted=False`** = `VIRTUAL`: bei jedem Lesen neu berechnet. (Postgres unterstützt das erst ab Version 18.)
- **In diese Spalte darf nie geschrieben werden.** SQLAlchemy markiert sie intern als nicht einfüg- und nicht änderbar; der `COPY`-Befehl im Ingest lässt sie korrekt weg.

Der Sinn dahinter: Die Regel „Nettoumsatz = Brutto − Rabatt" ist **in der Datenbank festgeschrieben** und kann von keinem Schreiber verletzt werden — auch nicht von einem Importskript, das an der Anwendung vorbei schreibt.

# Defaults — `default` vs. `server_default`

Zwei Dinge, die gleich klingen und es nicht sind:

| | Wo ausgewertet | Steht im DDL? | Gilt auch für … |
|---|---|---|---|
| `default=...` | **in Python**, von SQLAlchemy beim INSERT | ❌ nein | nur Schreibvorgänge über SQLAlchemy |
| `server_default=...` | **in der Datenbank** | ✅ ja (`DEFAULT …`) | *jeden* Schreibvorgang, auch `COPY` oder `psql` |

```python
base_currency: Mapped[str] = mapped_column(Text, server_default=text("'STG'"))
computed_at: Mapped[datetime] = mapped_column(DateTime(timezone=True),
                                              server_default=func.now())
```

> [!warning] Die Anführungszeichen-Falle
> `server_default="STG"` erzeugt `DEFAULT STG` — Postgres liest das als **Bezeichner** und bricht ab. Für einen Zeichenketten-Default braucht es die inneren Anführungszeichen: `text("'STG'")`.

**Warum hier `server_default` und nicht `default`:** Weil der Ingest per `COPY` schreibt — also an SQLAlchemys INSERT-Mechanik vorbei. Ein Python-seitiger `default` würde dabei schlicht nie greifen.

Verwandt: `onupdate=` (Python-seitig bei UPDATE) und `server_onupdate=` (nur Dokumentation; Postgres braucht dafür einen Trigger).

# Constraints und Indizes

Alles, was **mehrere Spalten** betrifft oder einen eigenen Namen braucht, kommt in `__table_args__`:

```python
__table_args__ = (
    UniqueConstraint("product_id", "calendar_date"),
    CheckConstraint("nights >= 1", name="nights_positive"),
    Index("ix_capacity_calendar_date", "calendar_date"),
)
```

| Konstrukt | Zweck |
|---|---|
| `ForeignKey("tabelle.spalte")` | am `mapped_column`; erzeugt den FK **und** bestimmt die Reihenfolge beim Anlegen |
| `UniqueConstraint("a", "b")` | Eindeutigkeit über mehrere Spalten (bei einer Spalte reicht `unique=True`) |
| `CheckConstraint("ausdruck", name=...)` | fachliche Regel in der Datenbank |
| `Index("name", "spalte", …)` | Index; alternativ `mapped_column(index=True)` für Einspaltenindizes |

> [!warning] Drei Fallen
> 1. **`__table_args__` ist ein Tupel** — bei einem einzigen Eintrag das Komma nicht vergessen: `(Index(...),)`
> 2. **`Index("name")` ohne Spalte** rendert `CREATE INDEX name ON tabelle ()` — ungültiges SQL, das erst beim Ausführen auffällt.
> 3. **Jede `CheckConstraint` braucht `name=`**, sobald die Naming Convention `%(constraint_name)s` benutzt.

# Naming Convention

```python
NAMING_CONVENTION = {
    "ix": "ix_%(table_name)s_%(column_0_name)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

Ohne sie vergibt Postgres die Namen selbst (`bookings_product_id_fkey`) oder es entstehen namenlose Constraints. **Der Grund, das gleich am Anfang zu setzen:** Ein Migrationswerkzeug muss eine Constraint zum Löschen benennen können — `DROP CONSTRAINT ???` geht nicht. Nachträglich einzuführen bedeutet, alle bestehenden Constraints umzubenennen.

# `create_all` — und was es nicht tut

```python
Base.metadata.create_all(engine)
```

- Legt **fehlende** Tabellen an; vorhandene werden übersprungen (`checkfirst=True` ist Default).
- Sortiert automatisch nach Fremdschlüssel-Abhängigkeit (`metadata.sorted_tables`).
- **Ändert niemals eine bestehende Tabelle** — kein `ALTER`, keine Warnung, kein Hinweis. Wer eine Spalte ergänzt und sich wundert, warum sie fehlt, hat diese Falle gefunden.

Das DDL ansehen, ohne eine Datenbank zu brauchen — sehr nützlich zum Prüfen:

```python
from sqlalchemy.schema import CreateTable
from sqlalchemy.dialects import postgresql

print(CreateTable(Booking.__table__).compile(dialect=postgresql.dialect()))
```

# Rohes SQL: `text()` vs. `psycopg.sql`

Sobald man an SQLAlchemy vorbei arbeitet (etwa für `COPY`), muss man wissen, **wessen** Werkzeug man gerade in der Hand hält:

| Aufruf | Ebene | Richtig ist |
|---|---|---|
| `conn.execute(…)` | SQLAlchemy-`Connection` | **`text("TRUNCATE …")`** |
| `cur.copy(…)` / `cur.execute(…)` | psycopg-`Cursor` | **`sql.SQL(…)`**, ggf. mit `sql.Identifier` |

`text()` erzeugt ein SQLAlchemy-Objekt (`TextClause`) — psycopg kennt es nicht und würde damit scheitern. Umgekehrt genauso.

**Die Regel, die dahintersteckt: Platzhalter gelten nur für Werte, nie für Bezeichner.**

```python
cur.execute("COPY %s (...) FROM STDIN", [table_name])   # ❌ funktioniert nicht
```

Ein Platzhalter wird zu einem *Literal* — daraus würde `COPY 'bookings'`, also eine Zeichenkette statt eines Tabellennamens. Für Tabellen- und Spaltennamen gibt es deshalb `sql.Identifier`:

```python
from psycopg import sql

stmt = sql.SQL("COPY {table} ({cols}) FROM STDIN").format(
    table=sql.Identifier(table.name),
    cols=sql.SQL(", ").join(map(sql.Identifier, cols)),
)
# -> COPY "bookings" ("source_id", "bkg_id", …) FROM STDIN
```

Der Gewinn gegenüber einem f-String: korrektes Quoting, richtige Behandlung von Groß-/Kleinschreibung, und es funktioniert auch bei Spalten, die zufällig `order` oder `group` heißen. Wenn die Namen aus dem eigenen `Table`-Objekt stammen, ist ein f-String zwar nicht *gefährlich* — aber das richtige Werkzeug kostet vier Zeilen und macht die Frage „kommt das vielleicht doch mal von außen?" gegenstandslos.

# Muster: Staging-Tabelle + `INSERT … SELECT`

Das klassische ETL-Muster, wenn beim Schreiben ein **Fremdschlüssel aufgelöst** werden muss. Im Projekt umgesetzt in `persistence/writers.py`.

## Das Problem

`price_recommendations.capacity_id` verweist auf `capacity.id`. Ein Domänen-Objekt kennt aber keine Datenbank-IDs — nur `product_id` und `calendar_date`. Irgendwer muss übersetzen.

**Der naive Weg:** die ganze `capacity`-Tabelle in ein Python-`dict` laden und nachschlagen. Bei 1,33 Mio. Zeilen sind das ~208 MB und ein kompletter Tabellentransfer — pro Schreibvorgang.

**Der bessere Weg:** die eigenen Zeilen kurz in der Datenbank ablegen und *sie* den Join machen lassen.

## Der Aufbau

```python
# Eigene MetaData! Die Staging-Tabelle darf NICHT in Base.metadata landen,
# sonst legt create_all() sie als permanente Tabelle an.
_staging_metadata = MetaData()

_tmp_recs = Table(
    "tmp_recs",
    _staging_metadata,
    Column("product_id", Text, nullable=False),
    Column("calendar_date", Date, nullable=False),
    # … weitere Spalten …
    prefixes=["TEMPORARY"],          # -> CREATE TEMPORARY TABLE
    postgresql_on_commit="DROP",     # -> ON COMMIT DROP
)

_TMP_COLS = tuple(c.name for c in _tmp_recs.c)   # Spaltenliste faellt ab
```

| Argument | Wirkung |
|---|---|
| `prefixes=["TEMPORARY"]` | Tabelle existiert nur in **dieser Sitzung**; parallele Läufe stören sich nicht, obwohl beide `tmp_recs` heißen |
| `postgresql_on_commit="DROP"` | verschwindet beim Commit — kein Aufräumcode |

Bewusst **ohne** Indizes, Constraints und Primärschlüssel: Es ist ein Zwischenlager, kein Datenmodell.

```python
_INSERT_FROM_TMP = insert(orm.PriceRecommendation).from_select(
    ["capacity_id", "days_until_travel", ...],          # Zielspalten
    select(orm.Capacity.id, _tmp_recs.c.days_until_travel, ...)
    .select_from(
        _tmp_recs.join(
            orm.Capacity,
            (orm.Capacity.product_id == _tmp_recs.c.product_id)
            & (orm.Capacity.calendar_date == _tmp_recs.c.calendar_date),
        )
    ),
)
```

`insert(X).from_select(spalten, abfrage)` heißt: **„Füge in X die Zeilen ein, die diese Abfrage liefert."** Kein Python dazwischen.

Zwei Fallstricke:
- **Die Zuordnung ist positionell**, nicht namentlich: erste Zielspalte ↔ erster Select-Ausdruck.
- **Ein INNER JOIN filtert automatisch**: Zeilen ohne Partner fallen heraus. Das ersetzt eine `if … is None: continue`-Schleife in Python.

## Warum es schneller ist

| | Python-dict | Staging + Join |
|---|---|---|
| DB → Python | 1,33 Mio. Zeilen | 0 |
| Speicher | ~208 MB | — |
| Join | 96k dict-Lookups | in Postgres |

Der entscheidende Punkt: `capacity` hat ein `UNIQUE (product_id, calendar_date)` — also **genau den Index, über den der Join läuft**. Ein Python-`dict` ist nichts anderes als ein selbstgebauter Index; die Datenbank hat ihren bereits fertig und muss ihn nicht bei jedem Lauf neu aufbauen.

> [!tip] Die verallgemeinerbare Lehre
> **Der Join gehört dorthin, wo die Indizes liegen.**

## Der `COPY`-Teil im Detail

```python
copy_stmt = sql.SQL("COPY {tbl} ({cols}) FROM STDIN").format(
    tbl=sql.Identifier(_tmp_recs.name),
    cols=sql.SQL(", ").join(map(sql.Identifier, _TMP_COLS)),
)

with raw.cursor() as cur, cur.copy(copy_stmt) as copy:
    for r in recs:
        copy.write_row([getattr(r, c) for c in _TMP_COLS])
```

**Der Befehl** wird aus psycopg-Bausteinen zusammengesetzt (nicht `str.format`!):

| Baustein | Bedeutung | Ergebnis |
|---|---|---|
| `sql.SQL("…")` | vertrauenswürdiges SQL-Fragment | wörtlich |
| `sql.Identifier("x")` | Bezeichner (Tabelle/Spalte) | `"x"` — korrekt gequotet |
| `sql.SQL(", ").join([...])` | Bausteine verbinden | `"a", "b", "c"` |

→ `COPY "tmp_recs" ("product_id", "calendar_date", …) FROM STDIN`

**`getattr(r, c)` ist identisch zu `r.c`** — der Unterschied ist, dass der Attributname aus einer *Variable* kommt und damit aus einer Schleife stammen kann.

**Der Punkt dahinter:** Ein `COPY` hat zwei Listen, deren Reihenfolge übereinstimmen muss — den Header und die Werte. Schreibt man die Werte von Hand (`[r.product_id, r.calendar_date, …]`), existiert die Reihenfolge an **zwei** Stellen: Der Header wird aus der Tabellendefinition abgeleitet und ändert sich mit, die Werte-Zeile nicht. Mit `getattr` wird über **dieselbe Liste** iteriert, aus der auch der Header entsteht — Auseinanderlaufen ist damit strukturell unmöglich.

> [!warning] Der reale Fall im Projekt
> Der alte handgeschriebene COPY im Ingest lautete `COPY prices (…, current_price, length_of_stay)`, das ORM-Modell definiert aber `…, length_of_stay, current_price` — **vertauscht**. Solange beide Listen von Hand gepflegt wurden, passte es zufällig. Hätte man nur den Header aus dem Modell abgeleitet, wären Preis und Aufenthaltsdauer vertauscht in die Datenbank gewandert.
>
> Hier wäre es aufgefallen (`"3N"` ist kein `NUMERIC`). Bei zwei Spalten **gleichen Typs** — etwa `source_id` und `bkg_id`, beide `TEXT` — hätte Postgres es klaglos geschluckt und der Fehler wäre erst Wochen später in den Daten aufgetaucht.

`copy.write_row(werte)` schiebt eine Zeile in den Datenstrom; psycopg übersetzt die Python-Werte ins COPY-Format (`date` → `2027-04-22`, `Decimal` → `10.275000`, `None` → `\N`) und **streamt** sie — kein riesiger SQL-String, keine Rückfrage pro Zeile.

# Beziehungen — `relationship`, `back_populates`, `secondary`

Das ORM-Feature, das aus Tabellen einen **Objektgraphen** macht:

```python
class Product(Base):
    __tablename__ = "products"
    product_id: Mapped[str] = mapped_column(Text, primary_key=True)
    bookings: Mapped[list["Booking"]] = relationship(back_populates="product")

class Booking(Base):
    __tablename__ = "bookings"
    product_id: Mapped[str] = mapped_column(ForeignKey("products.product_id"))
    product: Mapped["Product"] = relationship(back_populates="bookings")
```

Danach kann man navigieren: `booking.product.bedroom_type` oder `product.bookings`.

| Begriff | Bedeutung |
|---|---|
| **`relationship()`** | Definiert die Navigation. **Erzeugt kein DDL** — der Fremdschlüssel kommt weiterhin von `ForeignKey`. |
| **`back_populates="…"`** | Verbindet beide Seiten explizit. Setzt man `booking.product = p`, taucht die Buchung sofort auch in `p.bookings` auf — ohne Datenbankzugriff. Beide Seiten müssen deklariert werden. |
| **`backref="…"`** | Kurzform: erzeugt die Gegenseite automatisch, ohne dass sie im Code steht. Gilt heute als überholt, weil sie implizit ist — man sieht der `Booking`-Klasse nicht an, dass sie ein `product`-Attribut hat. |
| **`secondary=…`** | Für **n:m**-Beziehungen über eine Zwischentabelle: `relationship(secondary=booking_tags)`. In diesem Projekt gibt es keine n:m-Beziehung. |
| **`lazy=…`** | *Wann* nachgeladen wird: `"select"` (Default, faul → **N+1**), `"selectin"` / `"joined"` (im Voraus), `"raise"` (verbietet faules Nachladen — sehr nützlich als Sicherheitsnetz) |

Die Ladestrategie lässt sich auch pro Abfrage setzen: `select(Booking).options(selectinload(Booking.product))`.

# Warum dieses Projekt keine `relationship()` benutzt

Eine berechtigte Frage — die Antwort ist bewusst und hat vier Teile:

**1. Die ORM-Klassen sind nicht das Domänenmodell.** Sie sind eine dünne Abbildung der Tabellen; das eigentliche Modell steht in `domain/entities.py`. Dort trägt `Booking` ein schlichtes `product_id: str` und kein `product`-Objekt. Eine `relationship()` würde eine Navigation anbieten, die niemand aufruft — jede geladene Zeile wird sofort in ein Domänenobjekt übersetzt und die ORM-Instanz weggeworfen.

**2. Das Zugriffsmuster ist ein völlig anderes.** Die Anwendung liest **ganze Tabellen** (1,33 Mio. Kapazitätszeilen, 940k Buchungen) und verknüpft sie danach in Python: `PriceableUnitBuilder` zählt die Buchungsnächte per `Counter` auf `(product_id, calendar_date)`. Objektweise Navigation wäre bei diesen Mengen genau das falsche Werkzeug.

**3. Lazy Loading ist über Schichtgrenzen hinweg eine Falle.** Der Default `lazy="select"` lädt beim ersten Attributzugriff nach. Zwei Folgen: **N+1-Abfragen** in Schleifen, und `DetachedInstanceError`, sobald der Zugriff nach dem Schließen der Session passiert — also genau dort, wo eine Schichtenarchitektur die Objekte hinreicht. Das ist derselbe Mechanismus, der später bei der API zum berüchtigten „Session is closed" führt.

**4. Es gibt keine n:m-Beziehung.** `secondary` hat schlicht keinen Anwendungsfall im Schema.

> [!tip] Wann es sich lohnen würde — vermutlich bald
> Mit der REST API entsteht ein anderes Zugriffsmuster: `GET /bookings/42`, das auch den `bedroom_type` aus `products` mitliefern soll, oder `GET /products/A1/bookings`. Dann sind Beziehungen genau richtig — **aber mit eifrigem Laden**:
> ```python
> stmt = select(Booking).options(selectinload(Booking.product)).where(...)
> ```
> Innerhalb der Session laden, ins DTO übersetzen, Session schließen. Und `lazy="raise"` als Voreinstellung setzen, damit ein versehentlicher fauler Zugriff einen lauten Fehler gibt statt einer stillen Zusatzabfrage.
>
> Kurz: Beziehungen sind hier nicht *falsch*, sie sind für das **jetzige** Zugriffsmuster nur nutzlos — und bringen Risiken mit, die man ohne Gegenwert nicht einkauft.

# Spickzettel

| Ich will … | Schreibweise |
|---|---|
| Spalte, `NOT NULL` | `x: Mapped[str] = mapped_column(Text)` |
| Spalte, nullable | `x: Mapped[str \| None] = mapped_column(Text)` |
| Primärschlüssel, DB vergibt zwingend | `mapped_column(BigInteger, Identity(always=True), primary_key=True)` |
| Fremdschlüssel | `mapped_column(ForeignKey("products.product_id"))` |
| Berechnete Spalte | `Computed("a - b", persisted=True)` |
| Default in der Datenbank | `server_default=text("'STG'")` bzw. `func.now()` |
| Mehrspaltige Eindeutigkeit | `UniqueConstraint("a", "b")` in `__table_args__` |
| Prüfregel | `CheckConstraint("nights >= 1", name="…")` |
| Index | `Index("ix_tabelle_spalte", "spalte")` |
| `TEXT` statt `VARCHAR` überall | `type_annotation_map = {str: Text}` auf `Base` |
| Schema anlegen | `Base.metadata.create_all(engine)` |
| DDL ansehen ohne DB | `CreateTable(X.__table__).compile(dialect=postgresql.dialect())` |
| Beziehung, beidseitig | `relationship(back_populates="…")` auf **beiden** Klassen |
| Beziehung eifrig laden | `.options(selectinload(Booking.product))` |
| Faules Nachladen verbieten | `relationship(..., lazy="raise")` |

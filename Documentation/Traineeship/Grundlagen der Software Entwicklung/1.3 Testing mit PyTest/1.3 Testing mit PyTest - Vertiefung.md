# Mike Cohns Testpyramide

## Warum überhaupt eine „Pyramide"? — Das Grundproblem des Testens

Der [[1.3 Testing mit PyTest - Leitfaden#Motivation|Motivation]]-Abschnitt sagt es klar: Ausreichend komplexe Software enthält *immer* Bugs. Wir können Fehlerfreiheit nicht beweisen — aber wir können systematisch dafür sorgen, dass Fehler früh, schnell und günstig auffallen, statt spät, langsam und teuer. Genau darum geht es beim automatisierten Testen.

Sobald man beschließt zu testen, stellt sich aber sofort eine Ressourcenfrage: *Auf welcher Ebene* teste ich, und *wie viele* Tests welcher Art schreibe ich? Denn Tests sind nicht gratis — sie kosten Zeit beim Schreiben, beim Ausführen und bei der Pflege. Man könnte theoretisch alles nur über die fertige Benutzeroberfläche testen („klickt sich die App korrekt durch?"). Man könnte auch jede einzelne Funktion isoliert prüfen. Beides in Reinform ist eine schlechte Idee. **Mike Cohns Testpyramide** ist die bis heute einflussreichste Heuristik, um diese Frage zu beantworten: Sie gibt eine empfohlene *Verteilung* der Testarten vor.

Der Begriff stammt von **Mike Cohn** aus seinem Buch *Succeeding with Agile* (2009). Cohn brachte damit ein Bild auf den Punkt, das das Bauchgefühl vieler erfahrener Entwickler traf: **viele kleine, schnelle Tests unten — wenige große, langsame Tests oben.**

## Das Bild: drei Schichten

Die klassische Pyramide hat drei Ebenen. Wichtig ist nicht die exakte Zahl der Schichten (verschiedene Autoren zeichnen 3–5), sondern die *Form* und was sie über jede Ebene aussagt:

```text
            /\
           /  \        UI- / End-to-End-Tests
          / E2E\       → wenige, langsam, teuer, "echt"
         /------\
        /        \     Integrations- / Service-Tests
       /  Integr. \    → mittlere Anzahl
      /------------\
     /              \  Unit- / Modultests
    /   Unit-Tests   \ → viele, schnell, billig, isoliert
   /------------------\
```

Von unten nach oben:

| Ebene | Was wird getestet? | Beispiel in unserer App |
|---|---|---|
| **Unit / Modultests** (Basis) | Eine einzelne, isolierte „Einheit" (Funktion, Methode, Klasse) — ohne Datenbank, Netzwerk, Dateisystem. | „Berechnet `PriceableUnit.available_units()` korrekt `bookable - booked`?" |
| **Integration / Service** (Mitte) | Das *Zusammenspiel* mehrerer Einheiten oder das Zusammenspiel mit externer Infrastruktur (echte DB, echtes Dateisystem, API). | „Schreibt das Repository ein Objekt korrekt in die PostgreSQL-Tabelle und liest es wieder?" |
| **UI / End-to-End (E2E)** (Spitze) | Das *gesamte* System aus Nutzersicht, alle Schichten zusammen, oft über die Oberfläche. | „Nutzer legt Produkt an, bucht es, sieht korrekten Restbestand im Frontend." |

## Die Achsen, entlang derer sich die Ebenen unterscheiden

Die Pyramide ist deshalb so überzeugend, weil sich **mehrere Eigenschaften gleichzeitig** von unten nach oben verändern — und zwar alle in dieselbe Richtung. Je höher man klettert, desto:

| Eigenschaft | Unten (Unit) | Oben (E2E) |
|---|---|---|
| **Umfang (scope)** | winzig — eine Einheit isoliert | riesig — das ganze System |
| **Geschwindigkeit** | Millisekunden; Tausende laufen in Sekunden | Sekunden bis Minuten pro Test |
| **Kosten** (Schreiben + Warten) | niedrig | hoch |
| **Anzahl** (empfohlen) | sehr viele | sehr wenige |
| **Fehlerlokalisierung** | präzise — ein roter Test zeigt genau die kaputte Funktion | vage — „irgendwo in der Kette ist etwas kaputt" |
| **Realitätsnähe / Aussagekraft** | gering — testet nur den Baustein, nicht das Ganze | hoch — testet, was der Nutzer wirklich erlebt |
| **Stabilität** (Gegenteil: *Flakiness*) | hoch — deterministisch | niedrig — anfällig für Timing, Netzwerk, Umgebung |

Der entscheidende Zielkonflikt steht in den letzten drei Zeilen: **Unit-Tests lokalisieren Fehler präzise und laufen stabil, sagen aber wenig über das Gesamtsystem. E2E-Tests sind maximal aussagekräftig, aber langsam, teuer und flaky.** Die Pyramidenform ist Cohns Antwort auf diesen Konflikt: Hol dir das Beste aus beiden Welten, indem du das *Gewicht* nach unten verlagerst.

> **Was heißt „flaky"?** Ein *flaky* („wackeliger") Test ist einer, der bei unverändertem Code mal grün, mal rot ist — z. B. weil er von Timing, Netzwerklatenz, Testreihenfolge oder Zufallsdaten abhängt. Flaky Tests sind Gift: Man gewöhnt sich an rote Tests und übersieht irgendwann *echte* Fehler. Je höher in der Pyramide, desto größer die Flakiness-Gefahr — ein weiterer Grund, die Basis breit zu halten.

## Warum genau *diese* Form? — Die Kernbegründung

Die Pyramide ist breit unten und schmal oben, weil das die **schnellste Rückkopplung pro investiertem Aufwand** liefert. Drei Argumente machen das greifbar:

1. **Feedback-Geschwindigkeit.** Eine gute Testsuite läuft man *ständig* — idealerweise nach jeder kleinen Änderung. Das funktioniert nur, wenn sie in Sekunden durchläuft. Tausend Unit-Tests schaffen das; tausend E2E-Tests bräuchten Stunden und würden nie mehr regelmäßig laufen. Schneller Durchlauf = enger Feedback-Loop = Fehler werden entdeckt, *während* man noch im Kontext ist.

2. **Präzise Fehlerlokalisierung.** Schlägt ein Unit-Test fehl, weißt du sofort, *welche* Funktion kaputt ist. Schlägt ein E2E-Test fehl, beginnt die Detektivarbeit: War es die Datenbank? Die Berechnung? Das Netzwerk? Die Basis der Pyramide gibt dir chirurgische Genauigkeit.

3. **Der „Kosten-eines-Bugs steigt mit der Zeit"-Effekt.** Ein Bug, der schon beim Schreiben der Funktion von einem Unit-Test gefangen wird, kostet Minuten. Derselbe Bug, der erst in Produktion beim Kunden auffällt, kostet ein Vielfaches (Debugging, Hotfix, evtl. Datenschaden, Vertrauen). Viele billige Tests unten fangen die meisten Fehler an der günstigsten Stelle ab.

Die obere Schicht wird dadurch *nicht* wertlos — im Gegenteil: Ein paar E2E-Tests sind unverzichtbar, weil nur sie beweisen, dass die *verdrahteten* Teile im Ganzen funktionieren. Aber sie sind ein **teures Gewürz, kein Grundnahrungsmittel**: Man deckt mit ihnen die wichtigsten durchgehenden Nutzerpfade („happy paths") ab, nicht jeden Sonderfall. Sonderfälle gehören nach unten.

## Anti-Muster: Woran man erkennt, dass etwas schiefläuft

Die Pyramide definiert sich auch über ihre Gegenbilder — die tauchen in Teams real auf:

- **Die Eistüte / das umgekehrte Dreieck (*ice cream cone*).** Viele langsame UI-/manuelle Tests oben, kaum Unit-Tests unten. Symptom: Die Testsuite braucht ewig, ist flaky, und niemand traut sich mehr, Code umzubauen, weil jede Änderung irgendwo bricht und niemand schnell sieht, wo. Entsteht oft, wenn Testen erst *nachträglich* über die fertige Oberfläche „draufgesetzt" wird.
- **Die Sanduhr (*hourglass*).** Viele Unit-Tests und viele E2E-Tests, aber die Integrationsschicht in der Mitte fehlt. Symptom: Einzelbausteine funktionieren, das Gesamtsystem auch — aber genau die *Übergänge* zwischen Modulen sind ungetestet und brechen unbemerkt.

> **Moderne Ergänzung — Kent C. Dodds' „Testing Trophy".** In der JavaScript-/Frontend-Welt wurde die Pyramide zur *Trophy* weiterentwickelt: Sie betont die **Integrationsschicht** stärker (macht sie zur breitesten) mit dem Leitsatz *„Write tests. Not too many. Mostly integration."* Die Idee dahinter: Integrationstests treffen oft den besten Punkt aus Realitätsnähe und Geschwindigkeit. Das ist keine Widerlegung der Pyramide, sondern eine Akzentverschiebung — und kontextabhängig. Für uns bleibt die Pyramide der richtige mentale Anker, weil unser Fokus (siehe unten) auf der soliden Unit-Basis liegt.
>
> Wie die Branche das aktuell handhabt und ob der Trend tatsächlich von Unit-Tests wegführt: [[Testtrends 2026|Testtrends 2026]].

## Was ist überhaupt eine „Unit"? — die berühmte Unschärfe

Ein Punkt, an dem sich die Geister scheiden und der viele Diskussionen erklärt: Der Begriff **Unit** ist bewusst nicht scharf definiert. Es gibt zwei Denkschulen:

- **Solitary / „London School" (isoliert):** Eine Unit ist *eine* Klasse/Funktion, und *alle* ihre Abhängigkeiten werden durch Test-Doubles (Mocks/Stubs) ersetzt. Maximale Isolation, maximale Präzision. → Genau hier kommt das nächste Stichwort ins Spiel: [[#Mocks / Simulation von Verhalten echter Objekte]].
- **Sociable / „Detroit/Classicist School" (gesellig):** Eine Unit ist ein *Verhalten*, und man lässt ruhig mehrere echte, schnelle Objekte zusammenarbeiten, solange kein langsames externes System (DB, Netz) beteiligt ist. Man mockt nur an den Rändern.

Beide sind legitim; die Wahrheit liegt meist in der Mitte. Wichtig fürs Verständnis: Die Frage „Unit- oder Integrationstest?" ist oft weniger eine harte Grenze als ein Kontinuum — der Übergang ist fließend, und die Grenze verläuft praktisch dort, wo ein Test anfängt, **langsame oder unzuverlässige externe Infrastruktur** anzufassen.

## Einordnung in die PyTest-Welt

Die Pyramide ist *werkzeugunabhängig* — sie gilt für jede Sprache. In unserem konkreten Werkzeugkasten:

- **Unit- und Integrationstests** schreiben wir mit **`pytest`** (dem Framework dieses Kapitels). Dasselbe Tool bedient beide unteren Ebenen; der Unterschied liegt nicht im Framework, sondern darin, *was* der Test anfasst (isolierte Funktion vs. echte DB).
- Für die **Isolation** in Unit-Tests nutzen wir Mocking (`unittest.mock` / `pytest`-Fixtures) — eigenes Stichwort.
- **E2E-Tests** (Browser-Automatisierung o. ä., z. B. mit Selenium/Playwright) sind für unser aktuelles Kapitel [[1.3 Testing mit PyTest - Leitfaden#Out of Scope|Out of Scope]] — wir haben (noch) keine Oberfläche und konzentrieren uns bewusst auf die Basis.

## Verbindung zur Übungsaufgabe

Der Leitfaden gibt die Richtung vor: *„Wir konzentrieren uns in diesem Kapitel auf die Modultests."* In Pyramiden-Sprache heißt das: **Wir bauen jetzt die breite Basis.** Das ist kein willkürlicher Anfang, sondern der didaktisch und praktisch richtige: Die Basis liefert das beste Verhältnis aus Aufwand und Nutzen, ist Voraussetzung für alles Weitere, und die dafür nötigen Techniken (Testfälle formulieren, Verhalten mocken, Abdeckung messen) sind genau die nächsten drei Stichworte.

Konkret heißt „solide Basis" für unsere Anwendung aus [[1.1 OOP - Leitfaden|1.1]]/[[1.2 Relationale Datenbanken & ORM - Leitfaden|1.2]]: Die Rechen- und Regel-Logik (Preisberechnungen, Invarianten wie „Preis nie negativ", Verfügbarkeits-Berechnungen) gehört massiv mit Unit-Tests abgedeckt. Die Datenbank-Anbindung aus 1.2 ist dann Kandidat für einige wenige Integrationstests. Eine E2E-Spitze braucht es hier noch nicht.

# Modultests

## Was ist ein Modultest — und wozu genau schreibe ich ihn? (Kontrollfrage)

> **Kontrollfrage aus dem Leitfaden:** *Wozu genau schreibe ich Modultests?*

Ein **Modultest** (englisch *unit test*) prüft eine **einzelne, isolierte Einheit** deines Codes — meist eine Funktion oder eine Methode — auf ein erwartetes Verhalten, und zwar *ohne* langsame externe Abhängigkeiten wie Datenbank, Netzwerk oder Dateisystem. Er ist die breite Basis der [[#Mike Cohns Testpyramide|Testpyramide]].

Die naheliegende Antwort „um Bugs zu finden" ist richtig, aber zu kurz. Modultests zahlen auf *mehrere* Ziele gleichzeitig ein — und die zweite Hälfte davon wird oft unterschätzt:

1. **Korrektheit nachweisen.** Der offensichtliche Zweck: belegen, dass die Einheit für typische Eingaben, Randfälle und Fehlerfälle das Richtige tut.
2. **Regressionsschutz** (vielleicht der *wichtigste* Grund). Eine Regression ist ein Fehler, der etwas *vorher Funktionierendes* wieder kaputt macht. Ohne Tests merkst du das oft erst spät. Mit einer grünen Testsuite bekommst du sofort Bescheid, wenn eine Änderung an Stelle A unbeabsichtigt Stelle B bricht. Das ist der Sicherheitsgurt, der überhaupt erst **furchtloses Refactoring** ermöglicht — du kannst Code umbauen und vertraust darauf, dass die Tests dich warnen, falls du etwas zerstörst. (Genau das schließt an die [[SOLID-Prinzipien|SOLID]]-/Clean-Code-Gedanken aus 1.1 an: guter, entkoppelter Code ist auch *testbarer* Code.)
3. **Design-Feedback.** Ein schwer zu testender Code ist fast immer auch schlecht *entworfener* Code — zu viele Verantwortlichkeiten, harte Kopplung, versteckte Abhängigkeiten. Der Schmerz beim Testen ist ein ehrliches Frühwarnsignal für Design-Probleme. Tests zwingen dich, über Schnittstellen nachzudenken (was geht rein, was kommt raus?).
4. **Ausführbare Dokumentation.** Ein gut benannter Test beschreibt präzise, *wie sich die Einheit verhalten soll* — und kann, anders als ein Kommentar, nicht „veralten", ohne dass es auffällt (ein veralteter Test wird rot). Neue Teammitglieder lesen Tests, um Verhalten zu verstehen.
5. **Schnelleres Debugging.** Ein fehlschlagender Modultest zeigt *punktgenau* die kaputte Einheit — kein stundenlanges Durchsteppen durch das Gesamtsystem.

> **Kurz:** Modultests finden nicht nur *heutige* Fehler, sie verhindern vor allem *zukünftige* (Regressionen), verbessern das Design und dokumentieren Verhalten. Der Leitfaden formuliert das Ziel für alle kommenden Aufgaben unmissverständlich: *„ab jetzt soll deine Anwendung immer sinnvoll getestet sein."*

## Die Anatomie eines Tests: Arrange – Act – Assert (AAA)

Fast jeder gute Modultest folgt derselben Drei-Schritt-Struktur. Sie explizit im Kopf (oder sogar durch Leerzeilen im Code) zu halten, macht Tests lesbar:

| Phase | Bedeutung | Frage |
|---|---|---|
| **Arrange** | Ausgangszustand herstellen: Objekte/Eingabedaten vorbereiten. | *Was ist die Vorbedingung?* |
| **Act** | Die zu testende Aktion *einmal* ausführen. | *Was tue ich?* |
| **Assert** | Das Ergebnis gegen die Erwartung prüfen. | *Was muss herauskommen?* |

```python
def test_available_units_zieht_gebuchte_von_buchbaren_ab():
    # Arrange
    unit = PriceableUnit(bookable_units=5, booked_units=2)
    # Act
    result = unit.available_units()
    # Assert
    assert result == 3
```

Ein bewährter Grundsatz: **ein logisches Verhalten pro Test.** Nicht „ein `assert` pro Test" wörtlich nehmen — mehrere Asserts, die *denselben* Sachverhalt prüfen, sind ok — aber ein Test sollte nicht drei völlig verschiedene Dinge gleichzeitig prüfen. Sonst weißt du bei Rot nicht, *welches* Verhalten kaputt ist. (Die Denkschule „Given–When–Then" aus dem BDD-Umfeld ist übrigens dasselbe Muster mit anderen Worten.)

## Was macht einen *guten* Modultest aus? — die FIRST-Prinzipien

Ein verbreitetes Akronym für die Eigenschaften guter Unit-Tests ist **FIRST**:

| Buchstabe | Prinzip | Bedeutung |
|---|---|---|
| **F** | *Fast* | Millisekunden. Nur schnelle Tests werden ständig ausgeführt. |
| **I** | *Isolated / Independent* | Unabhängig voneinander und von externer Infrastruktur. Kein Test darf einen anderen beeinflussen; die Reihenfolge darf egal sein. |
| **R** | *Repeatable* | Deterministisch — gleiches Ergebnis bei jedem Lauf, egal wann/wo (keine Abhängigkeit von Uhrzeit, Zufall, Netzwerk). |
| **S** | *Self-validating* | Der Test entscheidet selbst grün/rot per `assert`. Kein Mensch muss Ausgaben „per Auge" prüfen. |
| **T** | *Timely* | Zeitnah geschrieben — idealerweise mit (oder direkt nach) dem Produktivcode, nicht Monate später. |

Das **I** (Isolation) ist der Grund, warum das nächste Stichwort — [[#Mocks / Simulation von Verhalten echter Objekte|Mocking]] — überhaupt existiert: Sobald deine Einheit eine langsame/unzuverlässige Abhängigkeit hat (DB, HTTP-Call), musst du sie durch einen kontrollierbaren Ersatz ersetzen, um Fast + Isolated + Repeatable zu erreichen.

## PyTest konkret: der erste Test

**`pytest`** ist das De-facto-Standard-Testframework für Python (mächtiger und schlanker als das eingebaute `unittest`). Der große Charme: **einfache Funktionen + das eingebaute `assert`.** Keine Boilerplate-Klassen, keine `self.assertEqual(...)`-Methoden.

**Test-Discovery** — woran pytest Tests automatisch erkennt (Konventionen):

- Dateien heißen `test_*.py` oder `*_test.py` (üblich: `test_*.py`).
- Testfunktionen beginnen mit `test_`.
- Optional gruppiert in Klassen `Test*` (ohne `__init__`).
- Tests liegen üblicherweise in einem eigenen `tests/`-Ordner neben dem Quellcode.

```python
# tests/test_priceable_unit.py
from myapp.models import PriceableUnit


def test_available_units_normalfall():
    unit = PriceableUnit(bookable_units=5, booked_units=2)
    assert unit.available_units() == 3
```

Ausführen auf der Kommandozeile:

```bash
pytest                     # alle Tests entdecken und laufen lassen
pytest -v                  # verbose: jeder Test einzeln mit Namen + Ergebnis
pytest -q                  # quiet: knappe Ausgabe
pytest tests/test_x.py     # nur eine Datei
pytest -k "available"      # nur Tests, deren Name "available" enthält
pytest -x                  # beim ersten Fehler abbrechen (stop on first failure)
pytest --lf                # "last failed": nur die zuletzt fehlgeschlagenen erneut
```

Das Besondere an pytests `assert`: Dank **assertion rewriting** zeigt pytest bei `assert unit.available_units() == 3` im Fehlerfall die *tatsächlichen Werte* an (`assert 4 == 3`) — man braucht keine speziellen Vergleichsmethoden. Ein simples `assert` genügt fast immer.

## Fehlerfälle testen: `pytest.raises`

Ein Test soll nicht nur den *Erfolg* prüfen, sondern auch, dass die Einheit bei ungültiger Eingabe *korrekt fehlschlägt*. Dafür gibt es den Kontextmanager `pytest.raises`:

```python
import pytest


def test_negative_buchung_wirft_valueerror():
    unit = PriceableUnit(bookable_units=5, booked_units=0)
    with pytest.raises(ValueError):
        unit.book(-1)          # negative Buchung ist unzulässig

    # optional: auch die Fehlermeldung prüfen
    with pytest.raises(ValueError, match="darf nicht negativ"):
        unit.book(-1)
```

Das ist die Test-Seite genau der Invarianten, die wir in [[1.1 OOP - Vertiefung|1.1]] mit Kapselung/Validierung eingebaut haben („Preis nie negativ", „nicht mehr buchen als verfügbar"). Erst der Test *beweist*, dass die Invariante wirklich greift.

## Welche Testfälle brauche ich? — systematisch Fälle finden

Eine der wichtigsten praktischen Fähigkeiten: nicht nur den „happy path" testen. Bewährte Denkraster:

- **Happy Path** — der typische, gültige Normalfall.
- **Randfälle / Grenzwerte (boundary values)** — genau an den Grenzen passieren die meisten Fehler: `0`, `1`, der maximale Wert, leere Liste, `available == 0` (ausgebucht). Faustregel „an der Grenze und knapp daneben".
- **Fehlerfälle** — ungültige Eingaben, die eine Exception auslösen sollen (negativer Wert, `None`, falscher Typ).
- **Äquivalenzklassen (equivalence partitioning)** — Eingaben, die sich gleich verhalten, zu Klassen zusammenfassen und je *einen* Vertreter testen (statt 1000 positive Zahlen genügt *eine* positive Zahl). Das hält die Testzahl sinnvoll klein.

> Kombiniert man Äquivalenzklassen (welche *Gruppen* von Eingaben) mit Grenzwertanalyse (die *Ränder* jeder Gruppe), findet man mit erstaunlich wenigen Tests erstaunlich viele Fehler.

## Test-Benennung: Konventionen (Kontrollfrage)

> **Kontrollfrage aus dem Leitfaden:** *Wie sollte man Tests benennen? Welche Konventionen gibt es?*

Der Testname ist Dokumentation — er sollte das *erwartete Verhalten* beschreiben, nicht nur die Methode nennen. Ein guter Name macht bei Rot sofort klar, *was* nicht mehr stimmt, ohne in den Code zu schauen. Verbreitete Muster:

| Muster | Beispiel |
|---|---|
| `test_<Einheit>_<Bedingung>_<erwartetes Ergebnis>` | `test_book_mehr_als_verfuegbar_wirft_error` |
| „should"-Stil | `test_should_reject_negative_price` |
| Given-When-Then | `test_given_ausgebucht_when_book_then_valueerror` |

Faustregeln: **beschreibend statt nummeriert** (`test_1`, `test_2` sind wertlos), das *Warum/Was* statt das *Wie* ausdrücken, und lieber zu lang als zu kurz — Testnamen werden selten getippt, aber oft gelesen. Innerhalb einer Klasse `TestPriceableUnit` kann der Klassenname den Kontext tragen, sodass die Methode kürzer sein darf.

## Wiederkehrendes Setup: Fixtures (Kurzüberblick)

Wenn viele Tests denselben Ausgangszustand brauchen (das „Arrange"), lagert man ihn in eine **Fixture** aus — pytests Mechanismus für wiederverwendbares Setup (und optionales Teardown). Eine Fixture ist eine mit `@pytest.fixture` dekorierte Funktion; ein Test bekommt sie, indem er ihren Namen als **Parameter** deklariert (Dependency Injection — vgl. [[Dependency Injection und Inversion of Control|DI aus 1.1]]):

```python
import pytest


@pytest.fixture
def unit():
    return PriceableUnit(bookable_units=5, booked_units=2)


def test_available(unit):          # pytest injiziert die Fixture per Name
    assert unit.available_units() == 3


def test_book_reduziert_verfuegbarkeit(unit):
    unit.book(1)
    assert unit.available_units() == 2
```

Setup *und* Aufräumen kombiniert man elegant mit `yield` (alles vor `yield` = Setup, alles danach = Teardown):

```python
@pytest.fixture
def temp_file():
    f = open("scratch.txt", "w")
    yield f              # <- hier bekommt der Test die Datei
    f.close()           # Teardown: läuft garantiert nach dem Test
```

Fixtures, die *mehrere* Testdateien teilen sollen, legt man in eine Datei namens **`conftest.py`** — pytest findet sie automatisch, ohne Import. (Fixtures sind auch das Einfallstor für Mocking im nächsten Stichwort.)

## Dieselbe Logik, viele Eingaben: parametrisierte Tests (Kontrollfrage)

> **Kontrollfrage aus dem Leitfaden:** *Wie funktionieren parametrisierte Tests in Python? Welche Möglichkeiten habe ich?*

Oft will man *dieselbe* Prüf-Logik mit vielen Eingabe/Erwartungs-Paaren durchspielen. Statt den Test zu kopieren (oder eine Schleife *im* Test zu bauen — schlecht, weil dann alles *ein* Testfall wäre und beim ersten Fehler abbräche), nutzt man `@pytest.mark.parametrize`:

```python
import pytest


@pytest.mark.parametrize(
    "bookable, booked, erwartet",
    [
        (5, 2, 3),      # Normalfall
        (5, 5, 0),      # ausgebucht (Grenzwert)
        (5, 0, 5),      # nichts gebucht
        (1, 0, 1),      # minimaler Fall
    ],
)
def test_available_units(bookable, booked, erwartet):
    unit = PriceableUnit(bookable_units=bookable, booked_units=booked)
    assert unit.available_units() == erwartet
```

pytest erzeugt daraus **vier eigenständige Testfälle** (in der Ausgabe einzeln sichtbar). Der große Vorteil: Schlägt einer fehl, laufen die anderen trotzdem, und du siehst *genau*, welche Eingabekombination bricht. Weitere Möglichkeiten:

- **`ids=[...]`** vergibt sprechende Namen je Fall (statt `[5-2-3]`).
- **`pytest.param(..., marks=pytest.mark.xfail)`** markiert einen einzelnen Fall (z. B. als erwarteter Fehlschlag).
- **Stapeln:** Mehrere `@parametrize`-Dekoratoren über derselben Funktion bilden das **Kreuzprodukt** aller Wertelisten (Vorsicht, wächst schnell).
- Alternativen im Ökosystem: **`@pytest.fixture(params=[...])`** parametrisiert über eine Fixture; Bibliotheken wie **Hypothesis** erzeugen Eingaben sogar automatisch (*property-based testing*) — für uns Ausblick, nicht Pflicht.

## Ausblick: Test-Driven Development (TDD)

Eng verwandt, aber eine eigene *Disziplin*: Bei **TDD** schreibt man den Test **zuerst** — er ist zunächst rot —, dann den minimalen Code, der ihn grün macht, dann räumt man auf. Der Rhythmus heißt **Red – Green – Refactor**. TDD ist kein Muss für dieses Kapitel, aber das „Timely" aus FIRST zeigt in genau diese Richtung: je näher Test und Code zeitlich beieinander entstehen, desto besser.

## Verbindung zur Übungsaufgabe

Jetzt wird der Auftrag konkret umsetzbar: *„Ergänze deine Anwendung um sinnvolle Tests."* Konkret für die App aus [[1.1 OOP - Leitfaden|1.1]]/[[1.2 Relationale Datenbanken & ORM - Leitfaden|1.2]]:

2. Beginne mit der **reinen Logik** (Preisberechnung, `available_units`, Invarianten) — die ist ohne DB testbar und liefert die meisten Tests fürs Geld.

4. Der Teil, der die **Datenbank** anfasst (das Repository aus 1.2), braucht Isolation — dort kommt das nächste Stichwort ([[#Mocks / Simulation von Verhalten echter Objekte|Mocking]]) ins Spiel, bevor wir am Ende mit [[#Testabdeckung / Code-Coverage|Coverage]] messen, wie weit wir gekommen sind.

# Mocks / Simulation von Verhalten echter Objekte

## Das Problem: echte Abhängigkeiten machen Unit-Tests kaputt

Erinnern wir uns an das **I** (Isolated) und **R** (Repeatable) der [[#Was macht einen *guten* Modultest aus? — die FIRST-Prinzipien|FIRST-Prinzipien]]. Sobald die Einheit, die wir testen wollen, eine „echte" Abhängigkeit anfasst, sind beide in Gefahr. Stell dir eine Funktion vor, die den Restbestand berechnet, dafür aber die Buchungslage aus der PostgreSQL-Datenbank aus [[1.2 Relationale Datenbanken & ORM - Leitfaden|1.2]] liest, oder einen Preis von einer externen HTTP-API holt:

- **Langsam** — jeder Test macht einen echten DB-/Netz-Roundtrip (statt Millisekunden → Sekunden). Das **F** (Fast) ist dahin.
- **Nicht-deterministisch** — die API ist mal offline, die DB enthält heute andere Daten als morgen. Das **R** (Repeatable) ist dahin.
- **Nicht isoliert** — der Test schlägt fehl, wenn die *Abhängigkeit* kaputt ist, obwohl unsere *eigene* Logik korrekt ist. Das **I** ist dahin, und die Fehlerlokalisierung wird unscharf.
- **Nebenwirkungen** — ein Test, der eine echte E-Mail verschickt oder eine Zeile in die Produktions-DB schreibt, ist inakzeptabel.

Die Lösung: Wir ersetzen die echte Abhängigkeit im Test durch ein **kontrolliertes Double** — einen Platzhalter, der *so tut, als wäre er* das echte Objekt, dessen Verhalten wir aber vollständig in der Hand haben.

## Der Vorteil des Mockens (Kontrollfrage)

> **Kontrollfrage aus dem Leitfaden:** *Welchen Vorteil bietet mir die Simulation von Verhalten, also das Mocken an dieser Stelle?*

Das Mocken (allgemeiner: der Einsatz von *Test-Doubles*) bringt konkret:

1. **Isolation** — wir testen *nur* unsere Einheit, nicht die halbe Welt dahinter. Ein roter Test bedeutet garantiert: *unser* Code ist kaputt, nicht die DB.
2. **Geschwindigkeit** — kein Roundtrip; die Suite bleibt schnell und wird ständig ausgeführt.
3. **Determinismus** — wir bestimmen exakt, was die Abhängigkeit zurückgibt, also auch schwer reproduzierbare Zustände.
4. **Fehlerfälle simulieren** — wie testet man „Was passiert, wenn die Datenbank einen Timeout wirft"? Bei einer echten DB kaum herstellbar; ein Mock kann auf Kommando *jede* Exception werfen (`side_effect`). Das ist oft der *eigentliche* Gewinn.
5. **Nebenwirkungen vermeiden** — keine echten E-Mails, keine Schreibzugriffe, keine Kosten für externe API-Calls.
6. **Unabhängige Entwicklung** — man kann gegen eine *noch nicht existierende* Komponente testen, indem man ihr Verhalten mockt.

## Die Familie der Test-Doubles

„Mock" wird umgangssprachlich als Sammelbegriff benutzt, aber Gerard Meszaros (*xUnit Test Patterns*) unterscheidet fünf Arten von **Test-Doubles**. Die Begriffe sauber zu trennen hilft enorm — besonders **Stub vs. Mock**, danach wird explizit gefragt:

| Double | Zweck | Merksatz |
|---|---|---|
| **Dummy** | Wird nur übergeben, um eine Signatur zu füllen, aber nie benutzt. | „Platzhalter, der nur herumsteht." |
| **Stub** | Liefert **vordefinierte Antworten** auf Aufrufe (canned answers). Ersetzt eine *eingehende* Datenquelle. | „Gibt Daten *rein*, damit mein Code weiterläuft." |
| **Spy** | Wie ein Stub, **zeichnet aber zusätzlich auf**, wie er aufgerufen wurde (zum späteren Prüfen). | „Stub mit Notizblock." |
| **Mock** | Kennt die **erwarteten Aufrufe im Voraus** und **verifiziert**, dass sie so passieren. | „Prüft, *wie* mein Code ihn benutzt." |
| **Fake** | Eine echte, aber *vereinfachte* Arbeits-Implementierung (z. B. In-Memory-DB statt PostgreSQL). | „Funktioniert wirklich, nur leichtgewichtig." |

### Stub vs. Mock — der entscheidende Unterschied (Kontrollfrage)

> **Kontrollfrage aus dem Leitfaden:** *Was ist der Unterschied zwischen einem Mock und einem Stub?*

Der Kern liegt in **was** sie prüfen — man nennt das **State Verification vs. Behavior Verification**:

- Ein **Stub** liefert nur Eingaben, damit dein Code laufen kann. Du prüfst danach das **Ergebnis / den Zustand** (state verification). Der Stub selbst wird *nicht* geprüft. → *„Angenommen, das Repository liefert diese Buchungslage — rechnet meine Funktion dann richtig?"*
- Ein **Mock** hat **Erwartungen an die Interaktion**. Du prüfst, **ob und wie** dein Code den Mock aufgerufen hat (behavior verification): richtige Methode, richtige Argumente, richtige Anzahl. → *„Ruft meine Funktion `repository.save(unit)` genau einmal mit dem richtigen Objekt auf?"*

Eine Faustregel: **Stub für *Abfragen* (queries), Mock für *Kommandos* (commands).** Ob eine Berechnung stimmt, prüft man am Ergebnis (Stub genügt). Ob ein *Seiteneffekt* ausgelöst wurde (speichern, senden, löschen), prüft man an der Interaktion (Mock). Ein Kernrat aus der Testliteratur: **Verifiziere Interaktionen nur für echte Seiteneffekte**, nicht für reine Abfragen — sonst testest du die *Implementierung* statt des *Verhaltens* (siehe „Over-Mocking" unten).

> **Praxis-Hinweis:** In Pythons `unittest.mock` sind Stub und Mock *technisch dasselbe Objekt* (`Mock`/`MagicMock`). Ob es als Stub oder als Mock *wirkt*, entscheidet, wie du es benutzt: Setzt du nur `return_value` und prüfst danach das Ergebnis → Stub-Nutzung. Prüfst du hinterher mit `assert_called_with(...)` → Mock-Nutzung.

## `unittest.mock` — das Bordmittel

Python bringt Mocking in der Standardbibliothek mit: `unittest.mock`. Die zentralen Bausteine:

```python
from unittest.mock import Mock

# Ein Mock-Objekt akzeptiert JEDEN Attribut-/Methodenzugriff und erfindet ihn zur Laufzeit
repo = Mock()

# 1) Rückgabewert festlegen (Stub-Verhalten)
repo.get_booked_units.return_value = 2

# 2) benutzen wie das echte Objekt
result = repo.get_booked_units("P-001")   # -> 2

# 3) Interaktion verifizieren (Mock-Verhalten)
repo.get_booked_units.assert_called_once_with("P-001")
```

Wichtige Werkzeuge im Überblick:

| Werkzeug | Zweck |
|---|---|
| `Mock()` / `MagicMock()` | Universal-Double. `MagicMock` unterstützt zusätzlich „magische" Methoden (`__len__`, `__iter__`, …). |
| `.return_value` | Fester Rückgabewert eines Aufrufs (Stub). |
| `.side_effect` | Funktion/Exception/Liste als Reaktion: eine Exception wird *geworfen*, eine Liste liefert bei Folgeaufrufen der Reihe nach ihre Elemente. |
| `.assert_called_once_with(...)` | Verifiziert genau einen Aufruf mit diesen Argumenten. |
| `.assert_called_with(...)` | Prüft den *letzten* Aufruf. |
| `.call_count`, `.call_args` | Rohdaten zur Nachkontrolle. |
| `create_autospec` / `autospec=True` | Erzeugt ein Double, das die **Signatur** des Originals erzwingt (siehe unten). |

**Fehlerfälle simulieren** mit `side_effect` — das ist oft der eigentliche Grund fürs Mocken:

```python
repo.save.side_effect = ConnectionError("DB nicht erreichbar")
with pytest.raises(ConnectionError):
    service.persist(unit)     # testet unseren Fehler-Umgang, ohne echte DB
```

## `patch` — und die goldene Regel „patch where it's used"

Oft erzeugt der Code seine Abhängigkeit *selbst* (statt sie übergeben zu bekommen). Dann tauscht man sie zur Testlaufzeit mit `patch` aus — als Dekorator, Kontextmanager oder manuell:

```python
from unittest.mock import patch

@patch("myapp.service.requests.get")     # ersetzt requests.get IM Modul service
def test_holt_preis_von_api(mock_get):
    mock_get.return_value.json.return_value = {"price": 19.99}
    assert get_current_price("P-001") == 19.99
    mock_get.assert_called_once()
```

> ⚠️ **Die häufigste Mock-Falle — „patch where it's used, not where it's defined".** Man patcht den Namen dort, wo er *nachgeschlagen/benutzt* wird, nicht dort, wo er *definiert* ist. Wenn `myapp/service.py` oben `import requests` hat und `requests.get(...)` aufruft, patcht man `"myapp.service.requests.get"` — **nicht** `"requests.get"`. Grund: `from x import y` bindet `y` als *neuen Namen im importierenden Modul*; nur diese Bindung sieht dein Code. Diese eine Regel erklärt gefühlt die Hälfte aller „mein Mock greift nicht"-Momente.

## Warum Dependency Injection das Mocken so viel einfacher macht

Es gibt einen direkten Draht zu [[Dependency Injection und Inversion of Control|Dependency Injection aus 1.1]]: Bekommt eine Klasse ihre Abhängigkeiten **übergeben** (per Konstruktor), statt sie sich selbst zu beschaffen, brauchst du im Test *gar kein* `patch` — du reichst einfach ein Double herein:

```python
class BookingService:
    def __init__(self, repository):       # Abhängigkeit wird injiziert
        self._repo = repository

    def available(self, product_id):
        return self._repo.get_bookable(product_id) - self._repo.get_booked(product_id)


def test_available_units():
    repo = Mock()                          # Stub-Nutzung
    repo.get_bookable.return_value = 5
    repo.get_booked.return_value = 2
    service = BookingService(repo)         # Double sauber hineingereicht

    assert service.available("P-001") == 3
```

Kein `patch`, keine Modulpfad-Fummelei — genau das meinte 1.1 mit „testbarem Design". **Schwer zu mockende Stellen sind ein Designsignal:** Oft lohnt es sich, die Abhängigkeit injizierbar zu machen, statt einen komplizierten Patch zu bauen.

## pytest-Wege zum Mocken

Neben `unittest.mock` gibt es im pytest-Ökosystem zwei idiomatische Wege:

- **`monkeypatch`** (eingebaute Fixture): setzt Attribute/Umgebungsvariablen/`dict`-Einträge temporär und macht sie nach dem Test automatisch rückgängig. Ideal für kleine, gezielte Eingriffe.

  ```python
  def test_liest_env(monkeypatch):
      monkeypatch.setenv("PRICE_API_URL", "http://test")
      monkeypatch.setattr("myapp.service.requests.get", fake_get)
  ```

- **`mocker`** (aus dem Plugin **`pytest-mock`**): eine dünne, komfortable Hülle um `unittest.mock`, die das manuelle Starten/Stoppen von Patches spart (kein `with`/Dekorator nötig, automatisches Aufräumen). In der pytest-Welt sehr verbreitet:

  ```python
  def test_holt_preis(mocker):
      mock_get = mocker.patch("myapp.service.requests.get")
      mock_get.return_value.json.return_value = {"price": 19.99}
      assert get_current_price("P-001") == 19.99
  ```

## `autospec`: Mocks, die nicht lügen

Ein rohes `Mock()` akzeptiert **jeden** Aufruf — auch Tippfehler oder Methoden, die es am echten Objekt gar nicht gibt (`repo.get_bookde_units()` läuft klaglos durch und liefert einen Mock). Das kann Tests **grün halten, obwohl der echte Code bräche**. Abhilfe: **`autospec`** (bzw. `create_autospec`) leitet die Doubles aus der *echten* Signatur ab — falsche Methodennamen oder falsche Argumentzahlen fliegen dann sofort auf.

```python
from unittest.mock import create_autospec
repo = create_autospec(Repository)     # kennt nur die echten Methoden/Signaturen
```

Faustregel: In ernsthaftem Code lieber `autospec=True` bzw. `create_autospec`, damit die Tests nicht an der Realität vorbei „grün lügen".

## Wann man *nicht* mocken sollte (Over-Mocking)

Mocking ist ein scharfes Messer — man kann sich schneiden:

- **Reine Logik niemals mocken.** Berechnungen, Wert-Objekte, einfache Datenklassen testet man mit *echten* Objekten. Mocks sind nur für die *langsamen/unzuverlässigen Ränder* (DB, Netz, Zeit, Zufall, Dateisystem).
- **Nicht die eigene Implementierung festnageln.** Wer jeden internen Methodenaufruf per Mock verifiziert, schreibt **brüchige (brittle) Tests**: Ein harmloses Refactoring, das das *Verhalten* nicht ändert, macht sie rot. Man testet dann das *Wie* statt das *Was*. → Interaktionen nur für echte Seiteneffekte prüfen (siehe Stub-vs.-Mock-Regel).
- **Über-Isolation verschleiert Integrationsfehler.** Wenn *alles* gemockt ist, testet man am Ende nur noch die Mocks. Deshalb gibt es die mittlere Ebene der [[#Mike Cohns Testpyramide|Pyramide]]: Ein paar Tests mit *echter* DB (oder einem **Fake**, z. B. SQLite/In-Memory statt PostgreSQL) fangen genau das, was Mocks per Definition übersehen.
- **Faustregel:** So viel mocken wie nötig, so wenig wie möglich. Je näher am Kern der Geschäftslogik, desto weniger Mocks; je näher am I/O-Rand, desto eher.

## Verbindung zur Übungsaufgabe

Der Leitfaden sagt: *„Simuliere Verhalten (Mocking) wo es sinnvoll ist."* Für unsere App heißt „sinnvoll" konkret:

- Die **reine Preis-/Verfügbarkeitslogik** aus [[1.1 OOP - Leitfaden|1.1]] → **ohne** Mocks testen (echte Objekte, siehe [[#Modultests]]).
- Das **Repository / die DB-Schicht** aus [[1.2 Relationale Datenbanken & ORM - Leitfaden|1.2]] → beim Testen der *darüberliegenden* Logik durch einen **Stub/Mock** ersetzen (kein echter DB-Zugriff im Unit-Test), und **Fehlerpfade** (DB nicht erreichbar) via `side_effect` provozieren.
- Wo der Code seine DB-Verbindung selbst beschafft: entweder per `patch("…where it's used…")` oder — besser — die Abhängigkeit **injizierbar** machen (DI), dann genügt ein hineingereichtes Double.
- Zusätzlich ein paar **Integrationstests** mit echter (Test-)Datenbank oder SQLite-Fake, um das zu prüfen, was Mocks nicht können: dass das echte SQL/ORM-Mapping stimmt.

# Testabdeckung / Code-Coverage

## Was ist Code-Coverage — und wie wird sie gemessen?

**Code-Coverage** (Testabdeckung) ist eine Kennzahl dafür, **wie viel deines Produktivcodes beim Ausführen der Testsuite tatsächlich durchlaufen wird** — üblicherweise als Prozentsatz. Sie beantwortet die Frage: *„Welche Teile meines Codes hat noch nie ein Test angefasst?"*

Technisch funktioniert das über **Instrumentierung**: Das Coverage-Werkzeug klinkt sich in die Ausführung ein (in Python über `sys.settrace`) und protokolliert jede Zeile/Verzweigung, die während des Testlaufs ausgeführt wird. Am Ende vergleicht es das Ausgeführte mit dem Gesamtcode und rechnet den Anteil aus.

In der Python-/pytest-Welt sind die Werkzeuge:

- **`coverage.py`** — die zugrunde liegende Bibliothek.
- **`pytest-cov`** — das pytest-Plugin, das `coverage.py` bequem in den Testlauf integriert.

```bash
pytest --cov=myapp                        # Coverage für Paket "myapp" messen
pytest --cov=myapp --cov-report=term-missing   # zeigt zusätzlich die NICHT abgedeckten Zeilennummern
pytest --cov=myapp --cov-report=html      # erzeugt interaktiven HTML-Report (htmlcov/index.html)
pytest --cov=myapp --cov-fail-under=80    # bricht ab, wenn Coverage < 80 %
```

Der `term-missing`- bzw. HTML-Report ist der eigentlich nützliche Teil: Nicht die *Zahl* ist wertvoll, sondern die **Liste der ungetesteten Stellen** — sie zeigt dir konkret, wo blinde Flecken sind.

## Die Coverage-Arten: Zeilen-, Zweig- und Pfadabdeckung (Kontrollfrage)

> **Kontrollfrage aus dem Leitfaden:** *Was ist der Unterschied zwischen Zeilen-, Zweig- und Pfadabdeckung?*

Es gibt nicht *die eine* Coverage — je nachdem, *was* man als „durchlaufen" zählt, ergeben sich unterschiedlich strenge Maße. Betrachten wir sie an einem Beispiel:

```python
def rabatt(preis, ist_stammkunde):
    if ist_stammkunde:
        preis = preis * 0.9
    return preis
```

### 1. Zeilenabdeckung / Statement Coverage (am schwächsten)

Misst, welcher **Anteil der Code-Zeilen (Anweisungen)** mindestens einmal ausgeführt wurde. Das gebräuchlichste, aber schwächste Maß.

Ein einziger Test mit `rabatt(100, True)` führt *alle drei Zeilen* aus → **100 % Zeilenabdeckung**. Aber Achtung: Der Fall `ist_stammkunde = False` (die `if`-Bedingung ist falsch, der Rabatt wird übersprungen) wurde **nie getestet**! Die Zeilenabdeckung meldet trotzdem 100 % — und übersieht damit einen ganzen Verhaltenspfad.

### 2. Zweigabdeckung / Branch Coverage (stärker)

Misst, ob **jede Verzweigung** (jeder Ausgang eines `if`/`while`/`for`) mindestens einmal in *beide* Richtungen genommen wurde — also `if` sowohl `True` als auch `False`.

Im Beispiel braucht 100 % Zweigabdeckung **zwei** Tests: `rabatt(100, True)` *und* `rabatt(100, False)`. Erst damit ist auch der „kein Rabatt"-Zweig geprüft. Branch Coverage fängt also genau die Lücke, die Statement Coverage übersieht. Deshalb schaltet man sie in der Praxis meist explizit ein:

```bash
pytest --cov=myapp --cov-branch
```

> Merksatz: **Zeilenabdeckung fragt „wurde die Zeile ausgeführt?", Zweigabdeckung fragt „wurden alle Ja/Nein-Ausgänge genommen?".** Ein `if` ohne `else` hat trotzdem zwei Zweige (der implizite „Bedingung war falsch"-Weg).

### 3. Pfadabdeckung / Path Coverage (am strengsten, meist unpraktikabel)

Misst, ob **jede mögliche Kombination von Verzweigungen** durch die Funktion durchlaufen wurde — also jeden *ganzen Weg* von Anfang bis Ende.

Das Problem: Die Zahl der Pfade **explodiert kombinatorisch**. Bei `n` unabhängigen `if`-Anweisungen hintereinander gibt es bis zu 2ⁿ Pfade; Schleifen machen es formal unendlich. Schon bei 10 Verzweigungen wären das 1024 Pfade. Deshalb ist vollständige Pfadabdeckung für realen Code fast nie erreichbar und wird in der Praxis kaum als Ziel gesetzt — sie ist eher ein theoretisches Ideal.

> **Ergänzung — Condition Coverage.** Noch feiner als Branch Coverage: Bei zusammengesetzten Bedingungen wie `if a and b` prüft sie, ob *jede Teilbedingung* (`a`, `b`) einzeln schon `True` und `False` war. Für uns nur zur Einordnung — Branch Coverage ist das praxisrelevante Ziel.

Zusammengefasst, von schwach nach streng:

| Maß | Was zählt als „abgedeckt"? | Beispiel-Testanzahl | Praxis |
|---|---|---|---|
| **Zeilen / Statement** | jede Zeile ≥ 1× ausgeführt | 1 | Standard, aber trügerisch |
| **Zweig / Branch** | jeder Ja/Nein-Ausgang genommen | 2 | **empfohlenes Ziel** |
| **Condition** | jede Teilbedingung einzeln T/F | mehr | selten explizit |
| **Pfad / Path** | jede Wegkombination | bis 2ⁿ | theoretisch, unpraktikabel |

## Wie viel Coverage macht Sinn? (Kontrollfrage)

> **Kontrollfrage aus dem Leitfaden:** *Wie viel Testabdeckung durch Modultests macht Sinn?*

Die ehrliche Antwort: **„100 % anstreben" ist die falsche Frage.** Der entscheidende Denkfehler ist, Coverage als *Ziel* statt als *Diagnosewerkzeug* zu behandeln. Drei Einsichten:

**1. Coverage ist notwendig, aber nicht hinreichend.** Sie misst, ob Code *ausgeführt* wurde — **nicht**, ob er *sinnvoll geprüft* wurde. Dieser Test hat 100 % Coverage und ist trotzdem wertlos:

```python
def test_rabatt():
    rabatt(100, True)      # führt den Code aus … prüft aber NICHTS (kein assert!)
```

Er durchläuft die Zeilen (Coverage steigt), aber ohne `assert` würde er selbst dann grün bleiben, wenn `rabatt` völligen Unsinn zurückgibt. **Coverage sagt dir, was du *nicht* getestet hast (wertvoll), aber nicht, ob dein Test *gut* ist.**

**2. Goodhart's Law.** *„When a measure becomes a target, it ceases to be a good measure."* Schreibt ein Team eine feste 100-%-Quote vor, entstehen genau solche assertion-losen Alibi-Tests, nur um die Zahl zu erreichen — die Metrik wird erfüllt, das Ziel (Vertrauen in den Code) verfehlt.

**3. Abnehmender Grenznutzen.** Die letzten Prozente sind die teuersten: Von 0 auf 70 % deckt man die wichtige Kernlogik ab; von 95 auf 100 % jagt man oft triviale oder kaum erreichbare Zweige (Logging, defensive `else`, `__repr__`). Der Aufwand steigt steil, der Nutzen sinkt.

**Praktische Orientierung** (keine Dogmen, sondern Richtwerte):

- **~70–85 %** ist für die meisten Projekte ein gesunder, üblicher Zielkorridor.
- **Kritische Geschäftslogik** (bei uns: Preisberechnung, Invarianten, Verfügbarkeit) sollte deutlich höher, idealerweise ~100 % **Branch**-Coverage haben.
- **Trivialer/Randcode** (Boilerplate, reine Weiterleitung, Logging) darf niedriger liegen; Zeilen bewusst ausschließen kann man mit dem Kommentar `# pragma: no cover`.
- **Wichtiger als der Absolutwert ist der Trend**: Coverage sollte nicht *sinken*. Viele Teams setzen daher in der CI eine Schwelle wie `--cov-fail-under=80`, die einen Merge blockiert, der die Abdeckung unter die Grenze drückt.

> **Kernbotschaft:** Nutze Coverage, um **ungetestete Stellen zu finden** (der `missing`-Report), nicht, um eine Prozentzahl zu maximieren. 80 % mit sinnvollen Asserts sind unendlich viel wert als 100 % ohne.

## Über Coverage hinaus: Mutation Testing (Ausblick)

Wenn Coverage nur *Ausführung* misst — wie misst man die *Qualität* der Asserts? Die Antwort heißt **Mutation Testing**. Das Werkzeug (in Python z. B. `mutmut` oder `cosmic-ray`) verändert deinen Produktivcode gezielt in winzigen „Mutationen" (macht z. B. aus `>` ein `>=`, aus `+` ein `-`, aus `True` ein `False`) und lässt dann die Tests laufen. Die Idee:

- Ist deine Testsuite gut, **schlägt** jetzt mindestens ein Test fehl — die Mutation wurde „getötet".
- **Überlebt** die Mutation (alle Tests bleiben grün), obwohl der Code verändert wurde, hast du eine Lücke: Diese Codestelle war zwar *abgedeckt*, aber nicht wirklich *geprüft*.

Mutation Testing ist rechenintensiv und für uns nur ein Ausblick — aber es ist die konzeptionell saubere Antwort auf die Schwäche der reinen Coverage-Zahl und schärft das Verständnis, *warum* 100 % Coverage nichts garantieren.

## Verbindung zur Übungsaufgabe

Der Leitfaden verlangt explizit: *„Miss danach die Testabdeckung in %."* Konkret:

1. Installiere `pytest-cov` und lauf `pytest --cov=<deinPaket> --cov-branch --cov-report=term-missing`.
2. Schau dir **nicht nur die Zahl**, sondern die **`missing`-Spalte** an: Welche Zeilen/Zweige sind ungetestet? Sind kritische darunter (eine ungetestete Invariante, ein Fehlerpfad)?
3. Schließe gezielt die *wichtigen* Lücken — vor allem in der Kernlogik aus [[1.1 OOP - Leitfaden|1.1]] — statt blind auf 100 % zu zielen.
4. Denk an das Zusammenspiel mit [[#Mocks / Simulation von Verhalten echter Objekte|Mocking]]: Coverage sollte auch die **Fehlerpfade** erfassen (den `except`-Zweig, der nur bei DB-Timeout läuft) — genau die erreichst du oft *nur* über einen `side_effect`-Mock. Coverage macht solche vergessenen Zweige sichtbar.

Damit schließt sich der Kreis des Kapitels: [[#Mike Cohns Testpyramide|Pyramide]] (wo teste ich?) → [[#Modultests]] (wie schreibe ich Tests?) → [[#Mocks / Simulation von Verhalten echter Objekte|Mocks]] (wie isoliere ich?) → **Coverage** (habe ich genug — und das Richtige — getestet?).

# Warum Containerisierung?

## 1. Das Problem hat einen Namen, und du kennst ihn schon

Das letzte Kapitel begann mit einer unbequemen Frage: *Dein Code ist versioniert — gilt das auch für dein Datenbankschema?* Die Antwort war nein, und der Zustand, in den ein Projekt ohne Werkzeug rutscht, hieß **Schema-Drift**.

Dieses Kapitel beginnt mit derselben Frage, eine Ebene tiefer:

> [!question] Dein Code ist versioniert — gilt das auch für die *Umgebung*, in der er läuft?

Und die Antwort ist wieder nein. Das Symptom hat ebenfalls einen Namen — **Umgebungs-Drift** — und einen Satz, den jeder Entwickler schon einmal gesagt hat:

> „Bei mir läuft's."

Das ist kein Scherz und keine Ausrede, sondern eine **präzise technische Aussage**: Auf *dieser* Maschine, mit *diesen* installierten Bibliotheken, *dieser* Interpreter-Version, *diesen* Umgebungsvariablen, *diesem* Locale und *diesem* Dateisystem-Layout funktioniert das Programm. Das Problem ist nicht, dass der Satz falsch wäre. Das Problem ist, dass er **nicht übertragbar** ist.

### Wie weit reicht deine Versionierung heute?

Schauen wir konkret in dein `pricing`-Projekt. Du hast dort mehr richtig gemacht als die meisten:

| Was                                             | Wo festgeschrieben                           | Reicht das?                             |
| ----------------------------------------------- | -------------------------------------------- | --------------------------------------- |
| Anwendungscode                                  | git                                          | ✅ vollständig                           |
| Python-Pakete (SQLAlchemy, FastAPI, …)          | `uv.lock` — exakte Versionen **plus Hashes** | ✅ vollständig                           |
| Python-Version                                  | `.python-version` (3.13)                     | ⚠️ als *Wunsch*, nicht als Auslieferung |
| Datenbankschema                                 | `alembic/versions/` (seit 1.6)               | ✅ vollständig                           |
| PostgreSQL-Version                              | `docker-compose.yml` → `postgres:18`         | ✅ (weil schon containerisiert!)         |
| Systembibliotheken (`libpq`, `libssl`, `glibc`) | —                                            | ❌ nichts                                |
| Betriebssystem                                  | —                                            | ❌ nichts                                |
| Locale, Zeitzone, `LANG`                        | —                                            | ❌ nichts                                |
| Startbefehl der Anwendung                       | README / dein Kopf                           | ❌ nichts                                |
| `uv` selbst                                     | —                                            | ❌ nichts                                |

Die obere Hälfte dieser Tabelle ist vorbildlich. Die untere Hälfte ist genau das, was Containerisierung adressiert.

> [!important] Der Kern in einem Satz
> Paketmanager wie `uv` schreiben fest, **was dein Programm importiert**. Container schreiben fest, **worauf dein Programm läuft**.

### Der Beweis liegt in deinem eigenen Projekt

Dass die untere Hälfte real ist und nicht theoretisch, hast du schon selbst erlebt — nur ohne es so zu nennen. In deiner `pyproject.toml` steht:

```toml
"psycopg[binary]>=3.2",
```

Das `[binary]`-Extra existiert **genau wegen dieses Problems**. Ohne es lädt `pip`/`uv` den Quellcode von psycopg und will ihn beim Installieren kompilieren — dafür braucht die Maschine einen C-Compiler, die PostgreSQL-Client-Header (`libpq-dev`) und passende Python-Header. Auf deinem Debian mag das vorhanden sein, auf einem frischen CI-Runner nicht. Das `[binary]`-Extra zieht stattdessen ein vorkompiliertes Wheel — in dem `libpq` bereits **mitgeliefert** ist.

Das ist bereits containerhaftes Denken auf Paketebene: *Nimm die Systemabhängigkeit mit ins Artefakt, statt sie auf dem Zielsystem vorauszusetzen.* Docker macht genau das, nur für **alle** Schichten gleichzeitig.

### Die Abhängigkeitsschichten, und wer welche abdeckt

Jedes laufende Programm sitzt auf einem Stapel:

```
┌───────────────────────────────────────────┐
│ 1. Dein Anwendungscode                    │  ← git
├───────────────────────────────────────────┤
│ 2. Python-Pakete (sqlalchemy, fastapi …)  │  ← uv.lock
├───────────────────────────────────────────┤
│ 3. Python-Interpreter (CPython 3.13)      │  ← uv (fast)
├───────────────────────────────────────────┤
│ 4. Systembibliotheken (glibc, libpq,      │  ← ❓ Docker-Image
│    libssl, zlib …)                        │
├───────────────────────────────────────────┤
│ 5. Betriebssystem-Userland                │  ← ❓ Docker-Image
│    (Debian? Alpine? welche Version?)      │
├───────────────────────────────────────────┤
│ 6. Linux-Kernel                           │  ← geteilt mit dem Host (!)
├───────────────────────────────────────────┤
│ 7. CPU-Architektur (amd64 / arm64)        │  ← nicht wegabstrahierbar
└───────────────────────────────────────────┘
```

Merk dir die Grenze zwischen **5 und 6**. Sie ist die wichtigste Linie dieses ganzen Kapitels:

- **Schicht 1–5** packt ein Container-Image ein. Deshalb ist ein Image typischerweise 50 MB bis 1 GB groß und startet in Millisekunden.
- **Schicht 6** wird mit dem Host **geteilt**. Genau daher kommt der gesamte Geschwindigkeits- und Größenvorteil gegenüber einer VM — und zugleich die wichtigste Einschränkung (dazu Abschnitt 4 und 7).
- **Schicht 7** bleibt ein echtes Problem. Ein für `amd64` gebautes Image läuft nicht ohne Weiteres auf einem Apple-Silicon-Mac (`arm64`) — dazu braucht es Emulation oder Multi-Arch-Images.

## 2. Wie man das Problem vor Docker gelöst hat

Containerisierung ist keine Idee, die 2013 vom Himmel fiel. Sie ist der vorläufige Endpunkt einer Reihe von Versuchen, und jeder Vorgänger erklärt, warum Docker aussieht, wie es aussieht.

### Stufe 0: Dokumentation

Eine `README.md` mit *„Installiere PostgreSQL 18, lege einen User `pricing` an, setze `DB_PRICING_PW`, dann `uv sync`."*

Das Problem ist nicht die Idee, sondern die Eigenschaft: **Prosa ist nicht ausführbar.** Sie wird nicht getestet, sie veraltet lautlos, und niemand merkt es, bis ein Neuer eine halbe Woche mit dem Setup verliert. Exakt dieselbe Kritik, die im letzten Kapitel gegen manuelle `ALTER TABLE`-Anweisungen sprach.

### Stufe 1: Setup-Skripte

`setup.sh` mit `apt-get install …`. Jetzt ist es ausführbar und liegt im Repo — ein echter Fortschritt. Aber:

- Es ist **nicht idempotent**: Zweimal laufen lassen macht evtl. etwas anderes als einmal.
- Es geht von einem **Ausgangszustand** aus, den es nicht prüft (welches OS? was ist schon installiert?).
- Es **verändert die Maschine unumkehrbar**. Wer es lokal ausführt, bekommt nachher sein System nicht sauber zurück.

### Stufe 2: Konfigurationsmanagement (Puppet, Chef, Ansible)

Ab ca. 2005–2012 der professionelle Standard: deklarativ beschreiben, wie ein Server auszusehen hat (*„Paket X installiert, Datei Y mit diesem Inhalt, Dienst Z läuft"*), das Werkzeug erzeugt diesen Zustand und **korrigiert Abweichungen** (Konvergenz).

Das war ein großer Schritt, hat aber einen konzeptionellen Restfehler: Der Server ist immer noch eine **langlebige Maschine mit Geschichte**. Er wird nicht neu gebaut, sondern *nachjustiert*. Nach zwei Jahren Konvergenz weiß niemand mehr genau, was auf der Kiste alles herumliegt. Der Fachbegriff dafür ist der **Snowflake-Server** — einzigartig, gewachsen, nicht reproduzierbar.

### Stufe 3: Virtuelle Maschinen (VMware, VirtualBox, Vagrant)

Die konsequente Antwort: Wenn die Umgebung das Problem ist, liefern wir die **ganze Maschine** mit. Ein VM-Image enthält Schicht 1–7 (inklusive eigenem Kernel). Vagrant (2010) machte das für Entwickler bedienbar — `vagrant up`, und alle im Team haben dieselbe virtuelle Maschine.

Das **löst** das Problem tatsächlich. Der Preis ist nur hoch:

| Problem | Auswirkung |
|---|---|
| Größe | VM-Images sind mehrere GB — pro Dienst |
| Startzeit | vollständiger OS-Boot: 30 Sekunden bis Minuten |
| Ressourcen | jede VM reserviert RAM und CPU fest, auch im Leerlauf |
| Dichte | ein Server trägt vielleicht 10–20 VMs |
| Doppelter Kernel | Host-Kernel *und* Gast-Kernel laufen parallel |

Für eine Microservice-Architektur mit 30 Diensten ist das nicht praktikabel. Und für den Entwickler-Alltag — „ich probiere mal schnell Redis aus" — ist eine 3-GB-VM mit 40 Sekunden Bootzeit absurd.

### Stufe 4: Container

Die Beobachtung, die zu Containern führt: **Ein zweiter Kernel ist Verschwendung.** Für 99 % aller Serveranwendungen ist der Linux-Kernel des Hosts völlig ausreichend — was fehlt, ist nur die *Illusion*, allein auf der Maschine zu sein.

Genau diese Illusion können Linux-Bordmittel erzeugen. Container sind der Kompromiss:

> Isolation und Reproduzierbarkeit **fast** wie bei einer VM, Ressourcenverbrauch und Startzeit **fast** wie bei einem normalen Prozess.

### Die Zeitleiste, damit die Einordnung stimmt

| Jahr | Meilenstein |
|---|---|
| 1979 | `chroot` in Unix V7 — ein Prozess sieht ein anderes Wurzelverzeichnis. Der Urahn (und *nur* Dateisystem-Isolation). |
| 2000 | **FreeBSD Jails** — erstmals auch Prozess- und Netzwerk-Isolation |
| 2004 | **Solaris Zones** |
| 2002–2013 | **Linux Namespaces** wachsen schrittweise in den Kernel (`mnt` 2002, `pid`/`net`/`ipc`/`uts` 2006–2009, `user` erst 3.8 / 2013) |
| 2008 | **cgroups** (von Google entwickelt) landen in Kernel 2.6.24; **LXC** setzt darauf auf |
| **2013** | **Docker** erscheint — anfangs nur ein Wrapper um LXC |
| 2014 | Docker ersetzt LXC durch eigenes `libcontainer` |
| 2015 | **OCI** (Open Container Initiative) gegründet — Standardisierung von Image- und Runtime-Format |
| 2017 | **containerd** an die CNCF gespendet; OCI-Specs 1.0 |
| 2022 | Kubernetes entfernt `dockershim` — Docker ist nicht mehr die Laufzeit in K8s |
| heute | Docker Engine 29.x, containerd 2.x, runc 1.4.x — das Format ist Standard, Docker eine Implementierung davon |

> [!tip] Die eigentliche Erfindung von Docker
> Docker hat **keine** der zugrundeliegenden Technologien erfunden. Namespaces, cgroups und Union-Dateisysteme gab es alle schon — sie waren nur unbenutzbar: LXC brauchte seitenweise Konfiguration, und es gab keinen Weg, eine fertige Umgebung *weiterzugeben*.
>
> Dockers Beitrag sind **drei Dinge, die zusammen ein Ökosystem ergeben**:
> 1. Ein **Image-Format mit Schichten** — Umgebungen werden kopier- und wiederverwendbar
> 2. Das **Dockerfile** — der Bauplan ist Text, liegt im Repo, durchläuft Code Review
> 3. Die **Registry** (Docker Hub) — Umgebungen bekommen eine Adresse, unter der man sie herunterlädt
>
> Punkt 3 ist der unterschätzte. Erst dadurch wurde `docker run postgres:18` möglich — und damit die Erwartung, dass jede Software als fertiges Image *existiert*.

## 3. Was ein Container wirklich ist (under the hood)

Jetzt die Frage, die der Leitfaden explizit stellt. Die Antwort ist überraschend unspektakulär:

> [!important] Definition
> Ein Container ist **ein ganz normaler Prozess auf dem Host-Kernel**, der mit einer eingeschränkten Sicht auf das System und einem begrenzten Ressourcenbudget gestartet wurde.

Kein Boot, kein eigener Kernel, keine Virtualisierung. Wenn du auf deinem Debian `docker compose up` ausführst, kannst du den PostgreSQL-Prozess mit `ps aux` auf dem Host sehen — er steht direkt in deiner Prozessliste, mit einer ganz normalen PID. Er weiß nur nichts davon.

Es gibt kein Kernel-Feature namens „Container". Es gibt **vier Bausteine**, die Docker kombiniert:

### a) Namespaces — *„was der Prozess sieht"*

Ein Namespace virtualisiert eine bestimmte **Systemressource**, sodass Prozesse darin ihre eigene, isolierte Instanz davon sehen.

| Namespace | Isoliert                        | Praktische Folge im Container                                                                        |
| --------- | ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `pid`     | Prozess-IDs                     | Der Hauptprozess ist **PID 1** und sieht keine Host-Prozesse                                         |
| `mnt`     | Mount-Punkte / Dateisystem      | Eigener Dateibaum — das ist `chroot` in stark                                                        |
| `net`     | Netzwerk-Stack                  | Eigene IP, eigene Ports, eigene Routing-Tabelle → zwei Container dürfen beide auf Port 5432 lauschen |
| `uts`     | Hostname / Domainname           | `hostname` im Container ist die Container-ID                                                         |
| `ipc`     | Shared Memory, Semaphoren       | Keine IPC-Kommunikation mit Host-Prozessen                                                           |
| `user`    | User- und Group-IDs             | `root` (UID 0) im Container kann auf UID 100000 des Hosts abgebildet werden                          |
| `cgroup`  | Sicht auf die cgroup-Hierarchie | Der Container sieht seine eigenen Limits nicht als Host-Pfad                                         |

Die **PID-1-Sache** ist mehr als eine Kuriosität und wird dich später beißen: PID 1 hat unter Linux Sonderrechte *und* Sonderpflichten. Sie ignoriert per Default Signale, für die kein Handler registriert ist — deshalb reagiert ein falsch gestarteter Container nicht auf `Strg+C`/`docker stop` und wird nach 10 Sekunden hart abgeschossen. Kommt beim Stichwort *Dockerfile* wieder (Stichwort: `exec`-Form vs. Shell-Form von `CMD`).

### b) cgroups (Control Groups) — *„wie viel er bekommt"*

Namespaces regeln die **Sicht**, cgroups regeln die **Menge**: CPU-Anteile, Arbeitsspeicher-Obergrenze, Block-I/O-Bandbreite, Anzahl Prozesse.

Der Unterschied ist wichtig, und man verwechselt ihn leicht:

> [!note] Namespaces vs. cgroups
> **Namespace** = *„Du siehst nur diesen Ausschnitt der Welt."*
> **cgroup** = *„Du darfst höchstens 512 MB RAM und eine halbe CPU verbrauchen."*
>
> Ohne cgroups könnte ein Container mit einem Speicherleck den gesamten Host in den OOM-Killer treiben — er *sieht* zwar nichts anderes, aber er *nimmt* sich alles.

Kleine Falle, die dir in Python begegnen wird: Viele Programme fragen die Hardware über den *Host* ab (`os.cpu_count()`) und ignorieren das cgroup-Limit. Ein Container mit `--cpus=1` auf einem 16-Kern-Rechner startet dann fröhlich 16 Worker.

### c) Union-Dateisystem (OverlayFS) — *„woraus sein Dateisystem besteht"*

Das ist der Baustein, der Docker *Docker* macht. Ein Image besteht aus **gestapelten, schreibgeschützten Schichten**; beim Start legt Docker eine dünne beschreibbare Schicht obendrauf. OverlayFS blendet den Stapel zu einem einzigen Dateibaum zusammen.

```
        ┌──────────────────────────────┐
Laufend │ beschreibbare Container-Schicht│  ← nur hier landen Änderungen
        ├──────────────────────────────┤
        │ Schicht 4: dein Code          │  ┐
Image   │ Schicht 3: uv sync (Pakete)   │  │ read-only,
(ro)    │ Schicht 2: apt-get libpq5     │  │ geteilt zwischen
        │ Schicht 1: debian:13-slim     │  ┘ ALLEN Containern
        └──────────────────────────────┘
```

Zwei Konsequenzen, die praktisch alles erklären:

1. **Schichten werden geteilt.** Zehn Container aus demselben Image belegen die Basis **einmal** auf der Platte. Deshalb ist „ein Container pro Dienst" bezahlbar, „eine VM pro Dienst" aber nicht.
2. **Änderungen im Container sind flüchtig.** Sie liegen nur in der obersten Schicht, die beim `docker rm` verschwindet. Genau daraus entsteht die Notwendigkeit von **Volumes** (Stichwort 6) — und genau deshalb hast du in deiner `docker-compose.yml` bereits `pricing_data:/var/lib/postgresql` stehen.

### d) Capabilities, seccomp, LSM — *„was er darf"*

Die letzte Ebene: Selbst wenn ein Prozess im Container `root` ist, entzieht Docker ihm standardmäßig die meisten der ~40 Linux-Capabilities (z. B. `CAP_SYS_ADMIN`) und blockiert per seccomp-Profil rund 44 Syscalls. AppArmor (auf Debian aktiv) oder SELinux kommen als weitere Schicht dazu.

> [!summary] Der ganze Zauber in einer Zeile
> **Container = Namespaces (Sicht) + cgroups (Menge) + Union-FS (Dateien) + Capabilities/seccomp (Rechte).**
> Docker ist die Bedienoberfläche, die diese vier Dinge zusammen mit einem Image-Format und einer Registry benutzbar macht.

## 4. Container vs. VM — die erste Kontrollfrage

> [!question] Kontrollfrage: Was ist ein Container und wie unterscheidet er sich von einer VM?

**Ein Container ist ein isolierter Prozess auf dem geteilten Host-Kernel.** Eine **VM ist eine simulierte Maschine mit eigenem Kernel**, die auf simulierter Hardware läuft. Der Unterschied ist *nicht* graduell („Container sind leichter"), sondern **strukturell**: Sie virtualisieren auf verschiedenen Ebenen.

- Eine **VM virtualisiert die Hardware**. Ein Hypervisor (KVM, VMware, Hyper-V) stellt CPU, RAM, Platte und Netzwerkkarte nach — darauf bootet ein vollständiges Gastbetriebssystem mit eigenem Kernel.
- Ein **Container virtualisiert das Betriebssystem-Interface**. Es gibt nichts zu booten, weil der Kernel schon läuft. Es wird lediglich ein Prozess gestartet, dem der Kernel eine eingeschränkte Weltsicht vorspielt.

```
        VIRTUELLE MASCHINEN                      CONTAINER
   ┌─────────┬─────────┬─────────┐        ┌────────┬────────┬────────┐
   │  App A  │  App B  │  App C  │        │ App A  │ App B  │ App C  │
   ├─────────┼─────────┼─────────┤        ├────────┼────────┼────────┤
   │ Bibl.   │ Bibl.   │ Bibl.   │        │ Bibl.  │ Bibl.  │ Bibl.  │
   ├─────────┼─────────┼─────────┤        └────────┴────────┴────────┘
   │Gast-OS  │Gast-OS  │Gast-OS  │  ← !   ┌──────────────────────────┐
   │+ Kernel │+ Kernel │+ Kernel │        │  Container Engine        │
   ├─────────┴─────────┴─────────┤        ├──────────────────────────┤
   │        Hypervisor           │        │  Host-Kernel (geteilt)   │  ← !
   ├─────────────────────────────┤        ├──────────────────────────┤
   │      Host-Betriebssystem    │        │  Host-Betriebssystem     │
   ├─────────────────────────────┤        ├──────────────────────────┤
   │          Hardware           │        │        Hardware          │
   └─────────────────────────────┘        └──────────────────────────┘
```

Die drei fehlenden Kernel-Kästen auf der rechten Seite sind der **gesamte** Unterschied. Alles andere folgt daraus:

|                       | Virtuelle Maschine                      | Container                                         |
| --------------------- | --------------------------------------- | ------------------------------------------------- |
| **Virtualisiert**     | Hardware                                | Betriebssystem-Interface                          |
| **Kernel**            | eigener pro VM                          | geteilt mit dem Host                              |
| **Startzeit**         | 30 s – Minuten (echter Boot)            | 50–500 ms (Prozessstart)                          |
| **Größe**             | GB (ganzes OS)                          | MB (nur Userland + App)                           |
| **RAM**               | fest zugeteilt, auch im Leerlauf        | nur was der Prozess tatsächlich braucht           |
| **Dichte pro Host**   | ~10–20                                  | Hunderte bis Tausende                             |
| **Isolation**         | sehr stark (Hardware-Grenze)            | gut, aber **schwächer** (ein Kernel für alle)     |
| **Gast-OS**           | beliebig (Windows auf Linux …)          | muss zum Host-Kernel passen (**Linux auf Linux**) |
| **Ausbruch bedeutet** | Hypervisor kompromittiert (sehr selten) | Kernel kompromittiert (deutlich häufiger)         |

### Wann trotzdem eine VM?

Das ist die Nachfrage, die den Unterschied wirklich prüft:

- **Anderes Betriebssystem nötig** — Windows-Software auf einem Linux-Host geht nur per VM. Ein Container *kann* das nicht, weil er keinen eigenen Kernel hat.
- **Harte Sicherheitsgrenze zwischen fremden Mandanten** — wer beliebigen fremden Code ausführt (Cloud-Anbieter, CI für Pull Requests von Unbekannten), setzt auf VMs oder auf Zwischenlösungen wie Firecracker/gVisor/Kata Containers.
- **Eigener Kernel oder Kernelmodul nötig** — spezielle Treiber, andere Kernel-Version, Echtzeit-Patches.
- **Compliance-Vorgaben**, die eine Hardware-Isolationsgrenze verlangen.

> [!warning] Die Frage ist kein Entweder-oder
> In der Praxis laufen Container **fast immer in VMs**: Jeder Kubernetes-Knoten in AWS/Azure/GCP ist eine VM, auf der dutzende Container laufen. Die VM zieht die Grenze zwischen *Kunden*, der Container die Grenze zwischen *Anwendungen*. Und auf macOS/Windows läuft Docker Desktop komplett in einer versteckten Linux-VM — weil es ohne Linux-Kernel keine Linux-Container gibt.
>
> **Für dich auf Debian 13 heißt das:** Du bist der Sonderfall, der es am einfachsten hat. Deine Container laufen direkt auf deinem Kernel, ohne VM-Zwischenschicht — kein Dateisystem-Performance-Problem wie bei Kollegen mit macOS, keine Docker-Desktop-Lizenzfrage (die betrifft nur Docker *Desktop* in größeren Firmen, nicht die Docker Engine unter Linux, die Apache-2.0-frei ist).

## 5. Was Containerisierung konkret einbringt

Bis hierher war es Technik. Jetzt die Frage nach dem Nutzen — in der Reihenfolge, in der sie im Alltag tatsächlich wirken.

### 1. Umgebungsparität: dasselbe Artefakt überall

Das ursprüngliche Versprechen. Was du lokal baust, ist **bitgleich** das, was in CI getestet und in Produktion ausgeliefert wird — kein Neubau, keine „aber der Server hat Python 3.11".

Der Unterschied zu einem Setup-Skript: Ein Skript beschreibt einen *Weg* und kann auf jeder Maschine anders enden. Ein Image ist ein *Ergebnis* und ist auf jeder Maschine identisch. (Erinnerung an 1.6: dort war die Migration bewusst der *Weg* — weil Daten existieren, die man nicht ersetzen kann. Hier ist die Umgebung bewusst das *Ergebnis* — weil man sie ersetzen darf. Der Gegensatz ist kein Widerspruch, sondern folgt genau daraus, ob Zustand erhalten bleiben muss.)

### 2. Isolation zwischen Projekten

Dein aktuelles Problem, das du bisher elegant umgangen hast: Du hast `postgres:18` in Compose. Sobald ein zweites Projekt PostgreSQL 15 verlangt, wäre das mit einer System-Installation ein Konflikt — mit Containern sind es zwei Zeilen in zwei Compose-Dateien.

Dasselbe gilt für Java-Versionen, Node-Versionen, `libssl`-Versionen. Und dein Debian bleibt sauber: Kein `apt install postgresql` hinterlässt Dienste, Datenverzeichnisse und Systemd-Units, die du in einem Jahr nicht mehr zuordnen kannst.

### 3. Wegwerfbarkeit — „Cattle, not Pets"

Der berühmte Vergleich: Ein **Haustier** hat einen Namen, wird gepflegt und beim Kranksein geheilt. **Vieh** ist nummeriert; wird ein Stück krank, wird es ersetzt.

Container sind Vieh. Etwas kaputt? `docker compose down && docker compose up` — nach 3 Sekunden ist der Zustand wieder exakt definiert. Diese Eigenschaft heißt **Immutable Infrastructure**: Man repariert nicht, man ersetzt. Das ist genau die Eigenschaft, die dem Snowflake-Server aus Abschnitt 2 fehlte.

> [!tip] Der Test, ob du es richtig machst
> Frag dich bei jedem Container: *„Kann ich ihn ohne Nachdenken löschen und neu starten?"* Wenn nein, liegt irgendwo Zustand an der falschen Stelle — die Antwort darauf sind Volumes (Stichwort 6).

### 4. Onboarding und Reproduzierbarkeit für andere

Die Aufgabe dieses Kapitels ist im Kern eine Onboarding-Aufgabe: *ein einziger Befehl*, und die gesamte Anwendung inklusive Datenbank läuft. Nicht „Postgres installieren, DB anlegen, `.env` befüllen, `alembic upgrade head`, dann `uvicorn` starten", sondern:

```bash
docker compose up
```

Das ist auch der Grund, warum die Trainer diese Aufgabe stellen: Sie ist der einzige belastbare Test, ob dein Projekt tatsächlich beschrieben ist — oder ob ein Teil davon nur in deinem Kopf und in deinem Dateisystem existiert.

### 5. Voraussetzung für alles, was danach kommt

CI/CD, Skalierung, Kubernetes, Serverless-Container, Blue-Green-Deployments — sie alle setzen ein **standardisiertes, startbares Artefakt** voraus. Ohne Container gäbe es kein Kubernetes (das im Leitfaden ausdrücklich *out of scope* ist, aber der Grund, warum das hier Pflichtstoff ist).

Auch dein Testing-Kapitel profitiert: Mit Containern kann ein Integrationstest eine **frische, echte PostgreSQL-Instanz** hochfahren, statt SQLite zu mocken — das Stichwort dazu heißt *Testcontainers*.

## 6. Was Docker *nicht* löst

Damit du das Werkzeug richtig einordnest — und weil in der Aufgabe genau diese Punkte auf dich zukommen:

| Missverständnis | Realität |
|---|---|
| „Container sind sicher wie VMs" | Nein. Ein geteilter Kernel heißt: Eine Kernel-Lücke gefährdet **alle** Container. Bei fremdem Code gilt: VM. |
| „Ein Image ist automatisch reproduzierbar" | Nein. `FROM python:3.13` ist ein **beweglicher Zeiger** — dasselbe Dockerfile baut heute und in vier Wochen unterschiedliche Images. Reproduzierbarkeit erfordert Disziplin: genaue Tags oder besser Digests (`python:3.13-slim@sha256:…`) plus `uv.lock`. |
| „Läuft überall" | Nur bei passender **Architektur** (amd64 ≠ arm64) und passendem Kernel-Typ (Linux-Container brauchen einen Linux-Kernel). |
| „Docker macht Deployments zustandslos" | Nein — es verschiebt den Zustand nur an eine explizit benannte Stelle (Volumes, externe DB). Das ist der Fortschritt, aber das Problem bleibt. |
| „Docker ersetzt Migrations-Tools" | Nein. Ein Image kann eine *frische* DB initialisieren; eine *bestehende* DB fortschreiben kann nur Alembic. Beides zusammen ist der Normalfall — siehe unten. |
| „Docker ist die einzige Option" | Nein. Das **Format** ist standardisiert (OCI). Podman (daemonlos, rootless per Default), containerd/nerdctl und Buildah bauen und starten dieselben Images. Docker ist die verbreitetste Implementierung, nicht die einzige. |

# Docker-Architektur: Engine, Daemon, Client

## 1. Der Satz, der alles erklärt

Fangen wir mit der Behauptung an, die beim ersten Lesen falsch klingt:

> [!important] Der `docker`-Befehl startet keine Container.
> Er ist ein **HTTP-Client**. Er nimmt deine Eingabe entgegen, formt daraus eine HTTP-Anfrage, schickt sie an einen **anderen, dauerhaft laufenden Prozess** und stellt dessen Antwort hübsch dar. Mehr nicht.

Wenn du `docker compose up` tippst, passiert auf deinem Debian ungefähr das: Ein kurzlebiges Programm schickt ein paar HTTP-Requests an einen Unix-Socket und beendet sich wieder. Die Container laufen dann als Kindprozesse von etwas ganz anderem.

Das erklärt sofort eine Reihe von Beobachtungen, die sonst willkürlich wirken:

| Beobachtung                                                               | Erklärung                                                            |
| ------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Container laufen weiter, wenn du das Terminal schließt                    | Sie gehören nie deiner Shell — sie gehören dem Daemon                |
| `docker ps` zeigt Container, die du nie in diesem Terminal gestartet hast | Du fragst einen zentralen Zustandshalter, nicht deine Sitzung        |
| `docker` braucht `sudo` oder Mitgliedschaft in der Gruppe `docker`        | Du brauchst Schreibrechte auf den **Socket**, nicht auf Container    |
| Du kannst Container auf einem *anderen Rechner* steuern                   | Der Client kann jeden erreichbaren Daemon ansprechen (`DOCKER_HOST`) |
| Bei `docker version` erscheinen **zwei** Versionsblöcke                   | Client und Server sind getrennte Programme mit getrennten Versionen  |

Dieses Stichwort geht diesem Satz auf den Grund — von deiner Tastatur bis zum `execve()` im Kernel.

## 2. Client/Server — und du kennst das Muster schon

In [[Documentation/Traineeship/Grundlagen der Software Entwicklung/1.5 REST APIs & Layered Architecture/1.5 REST APIs & Layered Architecture - Vertiefung|1.5]] hast du eine REST API gebaut: Ein Client schickt HTTP-Requests an Ressourcen-URLs, der Server hält den Zustand, die Antwort ist JSON. Docker ist **exakt dasselbe Muster** — nur dass der Server keine Preisempfehlungen verwaltet, sondern Container.

Die drei Begriffe des Leitfadens, sauber getrennt:

| Begriff | Was es ist | Konkret |
|---|---|---|
| **Docker Client** | Das CLI-Programm, das du tippst. Kurzlebig, zustandslos. | `/usr/bin/docker` |
| **Docker Daemon** | Der langlebige Serverprozess, der alles verwaltet und den Zustand hält. | `dockerd` |
| **Docker Engine** | **Sammelbegriff** für das ganze Produkt: Daemon + REST API + CLI. Kein eigener Prozess. | „Docker Engine 29.x" |

> [!warning] Häufiger Fehler in Prüfungsfragen
> „Docker Engine" ist **kein** Prozess und **keine** Komponente neben Daemon und Client. Es ist der Produktname für das Bündel aus beidem plus der API dazwischen. Wer im Vorstellungsgespräch „Engine, Daemon und Client kommunizieren miteinander" sagt, hat es nicht verstanden.

### Die Docker API ist wirklich eine REST API

Das ist kein Vergleich, sondern wörtlich zu nehmen — und du kannst es dir in einer Minute selbst beweisen:

```bash
# Direkt mit dem Daemon sprechen, ganz ohne docker-CLI:
curl --unix-socket /var/run/docker.sock http://localhost/v1.44/containers/json | jq

# Das Äquivalent zu `docker ps -a`:
curl --unix-socket /var/run/docker.sock 'http://localhost/v1.44/containers/json?all=true' | jq

# Systeminfos (= `docker info`):
curl --unix-socket /var/run/docker.sock http://localhost/v1.44/info | jq
```

Schau dir an, was da steht, und übersetze es in die Begriffe aus 1.5:

- **`/containers/json`** — eine **Collection-Ressource**, `GET` liefert die Liste. Genau die Namenskonvention (Substantiv im Plural), die du für deine eigenen Endpunkte gelernt hast.
- **`?all=true`** — ein **Query-Parameter** zum Filtern, nicht ein eigener Endpunkt `/containers/all`.
- **`/v1.44/`** — **Versionierung im Pfad**. Docker Engine 29 unterstützt Mindest-API-Version 1.44; ältere Clients dürfen mit neuen Daemons sprechen. Das ist gelebte Rückwärtskompatibilität einer öffentlichen API.
- **`POST /containers/create`**, dann **`POST /containers/{id}/start`** — ein `docker run` sind in Wahrheit *mehrere* Requests.
- Und es gibt eine **OpenAPI-Spezifikation** dafür, genau wie FastAPI sie dir automatisch erzeugt.

> [!tip] Warum das mehr ist als Trivia
> Weil daraus folgt: **Jedes Programm kann Docker steuern.** Compose, Portainer, Testcontainers, CI-Systeme, deine Python-Skripte (`pip install docker`) — sie alle reden dieselbe REST-API. Docker hat nie eine Plugin-Schnittstelle bauen müssen; die API *ist* die Schnittstelle.

### Der Transportweg: der Unix-Socket

Standardmäßig lauscht der Daemon nicht auf einem TCP-Port, sondern auf einem **Unix-Domain-Socket**: `/var/run/docker.sock` (ein Symlink auf `/run/docker.sock`).

Ein Unix-Socket ist eine Datei im Dateisystem, über die zwei Prozesse auf *derselben Maschine* kommunizieren. Der entscheidende Punkt für dich: **Er hat Dateirechte.**

```bash
$ ls -l /var/run/docker.sock
srw-rw---- 1 root docker 0 ... /var/run/docker.sock
#  ^        ^^^^ ^^^^^^
#  Socket   Besitzer root, Gruppe docker, rw für beide
```

Das ist die ganze Wahrheit hinter „Docker braucht sudo": Du brauchst kein Sonderrecht auf Container, du brauchst **Schreibrecht auf diese eine Datei**. Deshalb löst `usermod -aG docker $USER` das Problem — und deshalb ist genau das ein Sicherheitsproblem (Abschnitt 6).

Man kann den Daemon auch auf TCP lauschen lassen (`tcp://0.0.0.0:2376`), um ihn aus der Ferne zu steuern. Das sollte man **nur mit TLS-Client-Zertifikaten** tun, denn ein offener Docker-Port ist gleichbedeutend mit einem offenen Root-Zugang — es gibt Bots, die genau danach scannen.

Wohin der Client spricht, steuern zwei Dinge:

```bash
DOCKER_HOST=ssh://nick@server docker ps   # per Umgebungsvariable, einmalig
docker context ls                          # die saubere Variante: benannte Ziele
docker context use produktion              # dauerhaft umschalten
```

## 3. Was unter dem Daemon liegt

Jetzt wird es interessant, denn `dockerd` startet die Container auch nicht selbst. Unter ihm liegen noch drei Ebenen:

```
   docker CLI ─ docker compose ─ Portainer ─ Testcontainers ─ dein Skript
        │              │             │            │              │
        └──────────────┴──────┬──────┴────────────┴──────────────┘
                              │  REST API über /var/run/docker.sock
   ┌──────────────────────────▼──────────────────────────────────┐
   │ dockerd              — Netzwerke, Volumes, Images, Auth,     │
   │ (der "Docker Daemon")   Build-Orchestrierung, die API selbst │
   └──────────────────────────┬──────────────────────────────────┘
                              │  gRPC
   ┌──────────────────────────▼──────────────────────────────────┐
   │ containerd           — Container-Lebenszyklus, Image-Pull,   │
   │ (CNCF-Projekt)          Snapshots, Registry-Kommunikation    │
   └──────────────────────────┬──────────────────────────────────┘
                              │  startet einen Shim pro Container
   ┌──────────────────────────▼──────────────────────────────────┐
   │ containerd-shim-runc-v2 — bleibt als Elternprozess bestehen, │
   │ (einer je Container)      hält stdin/stdout, meldet Exit-Code│
   └──────────────────────────┬──────────────────────────────────┘
                              │  ruft einmalig auf
   ┌──────────────────────────▼──────────────────────────────────┐
   │ runc                 — OCI-Runtime: legt Namespaces + cgroups│
   │ (läuft, tut, endet)     an, wechselt das Root-FS, execve()   │
   └──────────────────────────┬──────────────────────────────────┘
                              │  Syscalls
   ┌──────────────────────────▼──────────────────────────────────┐
   │ Linux-Kernel  —  clone(), unshare(), cgroups, overlayfs      │
   └─────────────────────────────────────────────────────────────┘
```

Die Rollen im Einzelnen:

**`dockerd`** ist die *Benutzerfreundlichkeits-Schicht*. Er kennt Begriffe, die es weiter unten gar nicht gibt: Docker-Netzwerke, benannte Volumes, `docker build`, Login bei Registries, die `docker`-API. Er ist der Zustandshalter und die Instanz, die entscheidet, *was* passieren soll.

**`containerd`** ist die *Ausführungs-Schicht*: Images herunterladen und entpacken, Snapshots (die OverlayFS-Schichten aus Stichwort 1) verwalten, Container starten, stoppen, überwachen. Es ist ein eigenständiges CNCF-Projekt mit eigener API — und genau deshalb konnte Kubernetes 2022 den Umweg über Docker (`dockershim`) ersatzlos streichen und direkt mit containerd sprechen. Docker wurde dadurch nicht überflüssig, verlor aber seinen Platz *im Cluster*: Es ist heute vor allem das Entwickler-Werkzeug, containerd die Laufzeit im Rechenzentrum.

**`containerd-shim-runc-v2`** ist der unterschätzte Held. Für jeden Container bleibt ein kleiner Shim-Prozess bestehen, der:
- **Elternprozess** des Containers ist und dessen stdin/stdout/TTY hält,
- den **Exit-Code** einsammelt und meldet,
- vor allem aber: **den Container von containerd und dockerd entkoppelt.**

Das ist der Grund, warum du `dockerd` neu starten (oder aktualisieren) kannst, ohne dass alle Container sterben. Ohne Shim wären sie Kinder des Daemons und würden mit ihm untergehen. (Ob sie einen *Daemon-Shutdown* tatsächlich überleben, steuert die Option `live-restore` in `/etc/docker/daemon.json`.)

**`runc`** ist die eigentliche Arbeit — und läuft nur **wenige Millisekunden**. Es liest eine `config.json` nach OCI-Runtime-Spec und tut genau das, was in Stichwort 1 beschrieben wurde:

1. `clone()`/`unshare()` mit den Namespace-Flags → die neue Weltsicht
2. cgroup anlegen und Limits hineinschreiben → das Ressourcenbudget
3. Das Root-Dateisystem des Containers mounten und mit `pivot_root` hineinwechseln
4. Capabilities fallen lassen, seccomp-Profil setzen
5. **`execve()`** auf deinen Entrypoint — der Prozess *wird* die Anwendung
6. **runc beendet sich.**

> [!important] Der Moment, in dem der Container entsteht
> Schritt 5 ist die ganze Magie. Nach dem `execve()` läuft dort einfach `uvicorn` oder `postgres` — ein normaler Linux-Prozess. Es gibt keinen „Container-Prozess", der ihn überwacht oder einsperrt. Die Einschränkungen sind **Eigenschaften, die der Kernel dem Prozess angeheftet hat**, nicht ein Gefängnis, das um ihn herumsteht.
>
> Und genau deshalb ist `runc` nach dem Start weg. Es gibt nichts mehr zu tun.

### Warum diese Zwiebel? (Und warum das kein Overengineering ist)

Die Aufteilung sieht nach unnötiger Komplexität aus, hat aber einen konkreten Zweck: **Austauschbarkeit durch Standardisierung**. Die **OCI** (Open Container Initiative, 2015) definiert drei Spezifikationen — Image-Format, Runtime-Verhalten, Distribution (Registry-Protokoll). Jede Ebene der Zwiebel spricht eine standardisierte Schnittstelle nach unten.

Die Folge: `runc` ist ersetzbar, ohne dass sich für dich oben irgendetwas ändert.

| Runtime | Besonderheit | Wofür |
|---|---|---|
| **runc** | Referenzimplementierung, in Go | Standard |
| **crun** | in C, deutlich schneller und kleiner | Podman-Default, dichte Umgebungen |
| **gVisor (`runsc`)** | fängt Syscalls in einem *User-Space-Kernel* ab | fremder Code, ohne volle VM |
| **Kata Containers** | startet je Container eine **Mikro-VM** | echte Hardware-Isolation, VM-Preis |
| **youki** | in Rust | Performance-Experiment |

Damit relativiert sich auch die harte Aussage aus Stichwort 1: „Container sind unsicherer als VMs" gilt für die *Standard*-Runtime. Wer die Isolation braucht, tauscht die unterste Ebene aus — und behält Image-Format, Registry und CLI.

## 4. `docker run` in Zeitlupe

Alles zusammengesetzt. Was passiert bei `docker run -d -p 8000:8000 pricing-api:latest`?

| #   | Wer                      | Was                                                                                                  |
| --- | ------------------------ | ---------------------------------------------------------------------------------------------------- |
| 1   | **CLI**                  | Parst die Argumente, baut daraus einen JSON-Body                                                     |
| 2   | **CLI → Daemon**         | `POST /v1.44/containers/create` über den Unix-Socket                                                 |
| 3   | **dockerd**              | Ist `pricing-api:latest` lokal vorhanden? Wenn nein → Pull                                           |
| 4   | **containerd**           | Fragt die **Registry**: Manifest holen, fehlende Layer laden, entpacken                              |
| 5   | **containerd**           | Legt einen **Snapshot** an: Image-Layer (ro) + beschreibbare Schicht (rw)                            |
| 6   | **dockerd**              | Richtet das **Netzwerk** ein: `veth`-Paar, Bridge `docker0`, IP, `iptables`-Regel für `-p 8000:8000` |
| 7   | **dockerd**              | Hängt **Volumes/Mounts** in die Konfiguration                                                        |
| 8   | **dockerd → containerd** | „Erzeuge und starte diesen Container" (gRPC)                                                         |
| 9   | **containerd**           | Schreibt die OCI-`config.json` und startet einen **Shim**                                            |
| 10  | **Shim → runc**          | runc legt Namespaces + cgroups an, `pivot_root`, `execve()` — und endet                              |
| 11  | **Shim**                 | Bleibt als Elternprozess bestehen und wacht über den Prozess                                         |
| 12  | **CLI → Daemon**         | `POST /containers/{id}/start` war Teil davon; die Antwort ist die Container-ID                       |
| 13  | **CLI**                  | Druckt die ID und **beendet sich** — der Container läuft weiter                                      |

Bei `-d` (detached) endet es hier. Ohne `-d` bleibt der Client verbunden und streamt über einen weiteren API-Aufruf (`/containers/{id}/attach`) die Ausgabe in dein Terminal — er *hält* den Container aber immer noch nicht am Leben. `Strg+C` schickt lediglich ein Signal; der Container gehört weiterhin dem Shim.

## 5. Der zweite Pfad: der Build (BuildKit)

Eine Sache läuft nicht durch diese Kette: `docker build`. Seit Engine 23 geht der Build an **BuildKit** — eine eigene Build-Engine mit eigenem Daemon-Prozess (`buildkitd`), angesprochen über `docker buildx`.

Warum getrennt? Weil Bauen ein grundlegend anderes Problem ist als Ausführen. BuildKit kann:

- die Dockerfile-Anweisungen als **Graph** analysieren und unabhängige Zweige **parallel** bauen (bei Multi-Stage-Builds ein großer Gewinn),
- Schichten **überspringen**, die für das Ziel gar nicht gebraucht werden,
- **Cache-Mounts** (`--mount=type=cache`) bereitstellen — für uns direkt relevant: der `uv`-Paket-Cache überlebt damit den Build, ohne im Image zu landen,
- **Secrets** einbinden (`--mount=type=secret`), die *nicht* in einer Image-Schicht gespeichert werden,
- für **mehrere Architekturen** gleichzeitig bauen (amd64 + arm64).

Details kommen beim Stichwort *Dockerfile*. Hier reicht das architektonische Bild: **Ausführen** läuft über dockerd → containerd → runc, **Bauen** über dockerd → BuildKit.

## 6. Die Konsequenzen des Daemon-Modells

### Der Daemon läuft als root — und das färbt ab

Der klassische `dockerd` läuft als **root**. Er muss es, denn Namespaces anlegen, Netzwerkbrücken bauen und `iptables` schreiben sind privilegierte Operationen.

Daraus folgt eine Tatsache, die man einmal richtig verstanden haben muss:

> [!danger] Wer in der Gruppe `docker` ist, ist faktisch root auf diesem Rechner
> Nicht „fast root" oder „hat viele Rechte" — **root**, ohne Passwort, ohne `sudo`-Log. Der Beweis passt in eine Zeile:
>
> ```bash
> docker run -v /:/host -it alpine chroot /host sh
> ```
>
> Du bittest den root-Daemon höflich, dir das gesamte Wurzeldateisystem des Hosts in einen Container zu mounten — und bekommst darin eine root-Shell auf allem. Kein Exploit, keine Lücke: **so ist es gebaut.** Die Gruppe `docker` zu vergeben ist deshalb dasselbe wie passwortloses `sudo` zu vergeben, nur ohne dass es so aussieht.

Dasselbe gilt für den Socket. Wenn du in einem Container `/var/run/docker.sock` einhängst (manche CI-Werkzeuge und Portainer verlangen das), hat dieser Container vollen Zugriff auf den Host. Das Muster heißt *Docker-out-of-Docker* und ist genau so gefährlich, wie es klingt.

### Die Antwort darauf: Rootless Mode

Seit Version 20.10 kann Docker **rootless** laufen: `dockerd` startet als dein normaler Benutzer, innerhalb eines User-Namespace. Root *im* Container wird auf deine unprivilegierte UID abgebildet.

```bash
dockerd-rootless-setuptool.sh install   # einmalig, als normaler User
# Socket liegt dann unter $XDG_RUNTIME_DIR/docker.sock statt /var/run/
```

Der Preis sind ein paar Einschränkungen: Ports unter 1024 gehen nicht ohne Zusatzkonfiguration, das Netzwerk läuft über einen User-Space-Stack (RootlessKit/slirp4netns) und ist damit langsamer, und einige Storage-Treiber und cgroup-Funktionen brauchen aktuelle Kernel. Für Entwicklung auf einem Einzelplatzrechner ist es aber gut brauchbar.

> [!note] Für dich auf Debian 13
> Prüf einmal, wie deine Installation läuft:
> ```bash
> id -nG                  # bist du in der Gruppe "docker"?
> docker context ls       # zeigt der Endpunkt auf /var/run/ oder /run/user/1000/?
> docker info | grep -i -e "rootless" -e "storage driver" -e "cgroup"
> ```
> Für ein Traineeship-Projekt auf dem eigenen Rechner ist die Gruppe `docker` völlig üblich — man sollte nur wissen, was man damit vergeben hat, statt es für eine harmlose Bequemlichkeit zu halten.

### Die Grundsatzkritik: Podman

Die Existenz eines zentralen root-Daemons ist genau der Punkt, an dem **Podman** ansetzt. Podman ist **daemonlos**: Das CLI startet `conmon` (das Shim-Äquivalent) und `crun` direkt als Kindprozesse deines Benutzers. Es gibt keinen zentralen Server, kein root-Rechte-Bündel, und Container erscheinen als normale Prozesse *deiner* Sitzung — mit dem Nebeneffekt, dass systemd sie sauber verwalten kann.

Der Preis ist die Kehrseite von Abschnitt 2: Ohne zentralen Daemon gibt es auch keinen zentralen Zustandshalter. Podman baut das mit `podman generate systemd` bzw. Quadlet nach — es ist ein anderes Modell, kein reiner Gewinn. Und weil beide OCI-konform sind, sind die *Images* identisch: Ein Dockerfile, das du hier schreibst, baut und läuft unter Podman unverändert. Podman bietet dafür sogar bewusst eine CLI-kompatible Oberfläche (`alias docker=podman` funktioniert für den Alltag).

## 7. Die Registry — die vierte Komponente

Der Vollständigkeit halber: Die **Registry** gehört zur Architektur, ist aber kein Teil der Engine. Sie ist ein eigener HTTP-Dienst, der Images speichert und ausliefert — Docker Hub, GitHub Container Registry (`ghcr.io`), AWS ECR, GitLab, oder eine selbst betriebene.

Was dabei zu wissen ist:

- Der Daemon (bzw. containerd) spricht das **OCI-Distribution-Protokoll**, ebenfalls HTTP.
- Ein Pull holt zuerst ein **Manifest** (JSON: welche Layer, welche Architektur, welche Konfiguration), dann die fehlenden **Layer** — bereits vorhandene werden übersprungen. Das ist der Grund, warum das zweite Image einer Familie viel schneller lädt.
- Bei `postgres:18` ohne Registry-Präfix ist implizit `docker.io/library/postgres:18` gemeint.
- Docker Hub hat **Rate Limits** für anonyme Pulls. In CI-Pipelines läuft man da regelmäßig hinein — der klassische „warum ist der Build plötzlich rot"-Moment.

## 8. Compose ist auch nur ein Client

Damit schließt sich der Kreis zu deinem Projekt. **Docker Compose ist kein zusätzlicher Dienst**, sondern ein weiteres CLI-Plugin, das dieselbe REST-API aufruft wie `docker` selbst. Es liest deine `docker-compose.yml`, rechnet aus, welche Container, Netzwerke und Volumes es braucht, und schickt dieselben `POST /containers/create`-Requests — nur eben mehrere davon in der richtigen Reihenfolge.

Zwei Dinge fallen dabei an:

**Compose V1 vs. V2.** Das alte `docker-compose` (mit Bindestrich) war ein separates Python-Programm; das heutige `docker compose` (mit Leerzeichen) ist ein Go-Plugin der CLI. V1 ist seit 2023 abgekündigt. Für Dateinamen ist inzwischen `compose.yaml` der bevorzugte Name — `docker-compose.yml` funktioniert weiterhin, sodass deine Datei bleiben kann, wie sie ist.

**Der Projektname — und dein Erlebnis aus 1.6.** Compose stellt jeder Ressource einen **Projektnamen** voran, der standardmäßig aus dem **Verzeichnisnamen** abgeleitet wird. Genau darüber bist du im letzten Kapitel gestolpert: Der Ordnerwechsel von `REST_API` zu `DB_Migration_Tools` erzeugte ein neues, leeres Volume, weil das Volume in Wahrheit `db_migration_tools_pricing_data` heißt und nicht `pricing_data`.

Architektonisch ist jetzt klar, *warum*: Der Daemon kennt überhaupt keine „Projekte". Er kennt nur global eindeutige Namen für Container, Netzwerke und Volumes. Der Projektname ist reine **Client-seitige Namensraum-Konvention** von Compose — ein Präfix, das es allen Namen voranstellt, damit zwei Projekte sich nicht gegenseitig überschreiben. Wer das festnageln will:

```yaml
name: pricing        # oberste Ebene der compose.yaml — unabhängig vom Ordnernamen
```

## 9. Was in Engine 29 anders ist als in älteren Anleitungen

Eine Sache, die dir bei der Recherche Verwirrung ersparen wird: Seit **Engine 29** ist der **containerd image store** der Standard für Neuinstallationen. Früher hatte Docker eine eigene Image-Verwaltung (die „Graph Driver" wie `overlay2`) und containerd hielt Images parallel dazu.

Praktisch relevant wird das an zwei Stellen: Multi-Arch-Images und Image-Signaturen funktionieren nun nativ, und einige alte Kniffe (z. B. das direkte Manipulieren von `/var/lib/docker/overlay2`) stimmen nicht mehr. Wenn du auf einen Blogartikel stößt, dessen `docker info`-Ausgabe anders aussieht als deine: Das ist der Grund, nicht ein Fehler bei dir.

## 10. Bezug zum eigenen Projekt

Was du aus diesem Stichwort für die Aufgabe konkret mitnimmst:

1. **`docker compose up` startet nichts in deiner Shell.** Deine Container leben beim Daemon. Deshalb funktioniert `-d` überhaupt, und deshalb ist `docker compose down` nötig statt `Strg+C`.
2. **Die API ist deine Debugging-Ebene.** Wenn dein `api`-Container später nicht startet, sind `docker inspect`, `docker logs` und `docker events` Abfragen an denselben Zustandshalter — die Wahrheit steht immer beim Daemon, nicht in deinem Terminal-Scrollback.
3. **Das Volume-Rätsel aus 1.6 ist gelöst** und wird bei Stichwort *Volumes* noch einmal wichtig, wenn wir entscheiden, wie die Daten den Projektumzug überleben.
4. **Netzwerk-Setup ist Daemon-Sache** (Schritt 6 der Zeitlupe). Das ist der Grund, warum `depends_on` allein nichts über die *Erreichbarkeit* aussagt — der Daemon meldet „gestartet", sobald der Prozess läuft, nicht wenn PostgreSQL Verbindungen annimmt. Dein `healthcheck` schließt genau diese Lücke.
5. **Testcontainers** (siehe Quellen) funktioniert nur wegen Abschnitt 2: Eine Python-Bibliothek kann Container starten, weil die Steuerung eine ganz normale HTTP-API ist.

# Docker-Objekte: Images, Container, Volumes, Networks

## 1. Warum „Objekte" das richtige Wort ist

Im letzten Stichwort haben wir festgestellt: Der Daemon ist ein **Zustandshalter**. Dieses Stichwort beantwortet die Anschlussfrage — *welchen* Zustand hält er eigentlich?

Die Antwort ist ein **Objektbestand**. Und weil das konsequent durchgezogen ist, bekommst du die halbe CLI geschenkt, sobald du das Muster einmal siehst:

```bash
docker image ls        docker container ls        docker volume ls        docker network ls
docker image inspect   docker container inspect   docker volume inspect   docker network inspect
docker image rm        docker container rm        docker volume rm        docker network rm
docker image prune     docker container prune     docker volume prune     docker network prune
```

Jedes Objekt hat eine **ID** (SHA-256, meist auf 12 Zeichen abgekürzt), optional einen **Namen**, einen **Lebenszyklus** und die immer gleichen vier Verben. Wer das Muster kennt, muss die Befehle nicht auswendig lernen.

> [!note] Die alten Kurzformen
> `docker ps`, `docker images`, `docker rmi` sind Überbleibsel aus der Zeit vor dieser Systematik und funktionieren weiterhin. In Dokumentation und Skripten ist die lange Form (`docker container ls`) aber eindeutiger — und `docker ps` heißt so, weil es dem Unix-`ps` nachempfunden ist, was gut zur Erkenntnis aus Stichwort 1 passt: Container *sind* Prozesse.

Die vier Objekte teilen sich sauber in zwei Paare auf, und das ist mehr als Sortierung:

|  | **Bauzeit / Vorlage** | **Laufzeit / Instanz** |
|---|---|---|
| **Rechnen** | Image | Container |
| **Umgebung** | — | Volume, Network |

Ein **Image** ist eine unveränderliche Vorlage, ein **Container** ihre laufende Ausprägung. **Volumes** und **Networks** existieren *unabhängig* von beidem — sie überleben Container und werden zwischen ihnen geteilt. Genau diese Unabhängigkeit ist der Punkt, an dem die meisten Missverständnisse entstehen.

## 2. Images

> [!important] Definition
> Ein **Image** ist eine **unveränderliche, schreibgeschützte, aus Schichten aufgebaute Vorlage** für ein Container-Dateisystem — zusammen mit Metadaten, die beschreiben, wie ein Container daraus zu starten ist (Startbefehl, Umgebungsvariablen, Arbeitsverzeichnis, exponierte Ports, Benutzer).

Zwei Wörter sind entscheidend: **unveränderlich** und **Schichten**.

### Was physisch in einem Image steckt

Ein Image ist kein einzelnes Dateiformat, sondern ein kleines Bündel:

| Bestandteil | Inhalt |
|---|---|
| **Manifest** | JSON-Liste: welche Layer, welche Config, welche Größen — jeweils per Digest referenziert |
| **Config** | JSON: `Cmd`, `Entrypoint`, `Env`, `WorkingDir`, `User`, `ExposedPorts`, Architektur, Baugeschichte |
| **Layers** | je ein Tar-Archiv (meist gzip-komprimiert) mit den **Änderungen** dieser Schicht |

> [!tip] Der wichtigste Satz über Layer
> Eine Schicht enthält **nicht** das ganze Dateisystem, sondern nur die **Differenz** zur darunterliegenden: welche Dateien hinzugekommen, geändert oder gelöscht sind. Ein Layer ist ein *Diff* — genau wie ein git-Commit.

### Content-Addressing: warum die IDs Hashes sind

Jede Schicht und jede Config wird über den **SHA-256-Hash ihres Inhalts** adressiert. Das ist dasselbe Prinzip wie bei git-Commits und hat dieselben drei Folgen:

1. **Identischer Inhalt = identischer Hash = wird nur einmal gespeichert.** Wenn `pricing-api` und ein zweites Projekt beide auf `python:3.13-slim` aufbauen, liegt diese Basis genau einmal auf deiner Platte.
2. **Manipulationssicherheit.** Ein Layer kann sich nicht unbemerkt ändern, denn die Adresse *ist* der Inhalt.
3. **Effizienter Transfer.** Beim Pull überträgt die Registry nur Layer, deren Digest lokal fehlt.

### Tags sind bewegliche Zeiger, Digests nicht

Der vollständige Name eines Images sieht so aus:

```
docker.io  /  library  /  postgres  :  18       @  sha256:a1b2…
└ Registry ┘  └Namespace┘ └Repo────┘  └Tag┘        └── Digest ──┘
   (Default)   (Default)              (Default: latest)   (optional, unveränderlich)
```

Deshalb ist `postgres:18` die Kurzform von `docker.io/library/postgres:18`.

Ein **Tag** ist nur ein *Label*, das jederzeit auf ein anderes Image umgehängt werden kann. `postgres:18` zeigt heute auf 18.1 und in vier Wochen auf 18.2 — das ist genau der Punkt aus Stichwort 1, warum ein Dockerfile allein keine Reproduzierbarkeit erzeugt. Ein **Digest** (`@sha256:…`) ist dagegen unveränderlich: Er bezeichnet für immer exakt dieses eine Image.

> [!warning] `latest` ist kein „neuestes"
> `latest` ist schlicht das Tag, das Docker annimmt, wenn du keines angibst. Es hat **keine** eingebaute Bedeutung, wird nicht automatisch vergeben und zeigt bei vielen Projekten auf etwas Veraltetes oder etwas völlig anderes. In Produktion (und in Compose-Dateien, die jemand anderes benutzt) gehört ein expliziter Tag hin — du hast das mit `postgres:18` schon richtig gemacht.

### Multi-Arch: ein Tag, mehrere Architekturen

Was passiert eigentlich, wenn du `postgres:18` auf deinem amd64-Debian ziehst und ein Kollege dasselbe auf einem Apple-M-Mac (arm64) tut?

Hinter dem Tag steckt in Wirklichkeit oft ein **Image Index** (früher „Manifest List") — eine Liste von Manifesten, eines pro Plattform. Der Daemon sucht sich das passende heraus. Damit ist die Architektur-Frage aus Stichwort 1 zwar nicht *aufgelöst*, aber für den Nutzer unsichtbar gemacht — solange das Image für seine Plattform gebaut wurde.

### Die Falle, die dich später beißen wird: gelöschte Dateien bleiben drin

Weil Layer nur *additive Diffs* sind, kann eine höhere Schicht eine Datei nicht wirklich entfernen. Sie legt stattdessen eine **Whiteout-Markierung** an, die die Datei im zusammengesetzten Dateibaum unsichtbar macht. **Die Datei selbst liegt weiter in der unteren Schicht** — und die ist Teil des Images.

```dockerfile
COPY geheim.pem /tmp/          # Schicht 3: Datei ist im Image
RUN irgendwas-damit-tun
RUN rm /tmp/geheim.pem         # Schicht 4: nur unsichtbar gemacht, NICHT weg
```

Wer dieses Image weitergibt, gibt den Schlüssel mit — er ist mit `docker save` und einem Tar-Entpacker in einer Minute wiederherstellbar. Dasselbe gilt für Platz: `apt-get install …` in einer Schicht und `rm -rf /var/lib/apt/lists/*` in der nächsten macht das Image **nicht** kleiner. Die Lösungen (alles in einem `RUN`, Multi-Stage-Builds, BuildKit-Secrets) kommen beim Stichwort *Dockerfile*.

### Die wichtigsten Befehle

```bash
docker image ls                      # was liegt lokal?
docker image ls -a                   # inkl. Zwischenschichten
docker pull postgres:18              # holen
docker image inspect postgres:18     # Config: Cmd, Env, Volumes, ExposedPorts …
docker image history postgres:18     # jede Schicht mit Größe und erzeugendem Befehl
docker image rm postgres:18          # entfernen (geht nicht, solange ein Container darauf verweist)
docker image prune                   # "dangling" Images (<none>:<none>) aufräumen
```

`docker image history` ist unterschätzt: Es zeigt dir bei jedem fremden Image, wie es gebaut wurde und welche Schicht wie viel Platz kostet. Beim Optimieren des eigenen Images ist das der erste Befehl.

> [!note] Woher kommen die `<none>:<none>`-Images?
> Wenn du dein Image neu baust, hängt Docker den Tag `pricing-api:latest` auf das **neue** Image um. Das alte verliert damit seinen Namen, existiert aber weiter — es ist *dangling*. Nach einer Woche Entwicklung sammeln sich davon schnell mehrere Gigabyte an. `docker image prune` räumt genau das auf.

## 3. Container

> [!important] Definition
> Ein **Container** ist eine **Instanz eines Images**: dessen schreibgeschützte Schichten, ergänzt um eine **dünne beschreibbare Schicht** und eine **Laufzeitkonfiguration** (Name, Umgebungsvariablen, Portveröffentlichungen, Mounts, Netzwerkanschlüsse, Ressourcenlimits).

Der Satz, der die häufigste Verwirrung auflöst:

> [!warning] Ein Container ist nicht dasselbe wie „ein laufender Container"
> Ein Container **existiert auch im gestoppten Zustand** — mit seiner beschreibbaren Schicht, seiner Konfiguration und seinem Namen. Er belegt weiter Plattenplatz und blockiert weiter seinen Namen.
>
> Deshalb zeigt `docker ps` nur laufende Container, `docker ps -a` alle. Und deshalb bekommst du beim zweiten `docker run --name pricing-db …` ein „name is already in use", obwohl `docker ps` leer ist.

### Der Lebenszyklus

```
                    docker create
   [Image] ──────────────────────────► created
                                          │ docker start
                                          ▼
      docker run  ═══════════════════► running ◄────────┐
      (= create + start)                  │  │           │ docker unpause
                                          │  │ docker pause
                          docker stop     │  ▼           │
                          (SIGTERM,       │ paused ──────┘
                           dann SIGKILL)  │
                          docker kill     │
                          Prozess endet   │
                                          ▼
                                       exited
                                          │ docker rm
                                          ▼
                                      (gelöscht)
```

Was dabei wirklich wichtig ist:

**`docker run` ist kein eigenes Konzept**, sondern `create` + `start` in einem Befehl (plus optional `pull`, falls das Image fehlt). Wenn du das weißt, verstehst du auch, warum manche Optionen (`-e`, `-v`, `-p`, `--name`) nur bei `run`/`create` gehen und nicht bei `start`: Sie gehören zur **Erzeugung** des Containers, nicht zu seinem Start. Ein Container lässt sich nachträglich nicht umkonfigurieren — man löscht ihn und erzeugt einen neuen. Das ist Absicht und heißt *Immutable Infrastructure* (Stichwort 1).

**`docker stop` ist höflich, `docker kill` nicht.** `stop` schickt `SIGTERM`, wartet standardmäßig 10 Sekunden und schickt dann `SIGKILL`. Hier schließt sich der Kreis zur PID-1-Falle: Wenn dein Prozess das Signal nicht bekommt (weil eine Shell dazwischenhängt) oder nicht darauf reagiert, dauert jedes Herunterfahren 10 Sekunden und endet hart. Für PostgreSQL bedeutet hart abgeschossen: Recovery beim nächsten Start.

### Der Hauptprozess bestimmt die Lebensdauer

Die mit Abstand wichtigste Eigenschaft für die Fehlersuche:

> [!important] Ein Container lebt genau so lange wie sein PID-1-Prozess
> Endet der Hauptprozess, endet der Container — mit dessen Exit-Code. Es gibt keinen Container, der „läuft" und dabei nichts tut.

```bash
$ docker run debian:13
$                              # sofort wieder da — kein Fehler!
$ docker ps -a
CONTAINER ID   IMAGE       COMMAND   STATUS
a3f9…          debian:13   "bash"    Exited (0) 2 seconds ago
```

Das ist kein Defekt. Der Startbefehl des Images ist `bash`; ohne angeschlossenes Terminal liest bash von einem leeren stdin, bekommt EOF und beendet sich sauber. Der Container hat exakt das getan, was er sollte.

> [!tip] Die Debugging-Regel
> „Mein Container startet nicht" heißt fast immer „**mein Prozess ist beendet**". Erste drei Befehle, in dieser Reihenfolge:
> ```bash
> docker ps -a               # Status und Exit-Code — 0? 1? 137 (=SIGKILL, oft OOM)?
> docker logs <name>         # was hat der Prozess gesagt, bevor er ging?
> docker inspect <name>      # womit wurde er überhaupt gestartet?
> ```
> Erst danach lohnt es sich, das Dockerfile zu verdächtigen.

### Die wichtigsten Befehle

```bash
docker run -d --name api -p 8000:8000 pricing-api:latest
docker ps -a                         # alle Container, mit Status und Exit-Code
docker logs -f api                   # stdout/stderr des Hauptprozesses, -f = folgen
docker exec -it api bash             # zweiten Prozess IM laufenden Container starten
docker inspect api                   # die vollständige Wahrheit als JSON
docker stop api && docker rm api     # beenden und entfernen
docker run --rm …                    # Container nach dem Ende automatisch löschen
```

Zwei Hinweise dazu:

- **`docker exec` ist dein Fenster in den laufenden Container.** Damit prüfst du im Zweifel, was der Container *wirklich* sieht: `docker exec api env`, `docker exec api ls -la /app`, `docker exec db psql -U pricing`. In deinem Projekt wird das der Befehl sein, mit dem du dich mit der Datenbank verbindest, ohne einen Port nach außen zu öffnen.
- **`--rm` solltest du dir für Wegwerf-Container angewöhnen**, sonst füllt sich `docker ps -a` mit Leichen.

## 4. Der Speicherort der Wahrheit: `docker inspect`

Ein kurzer Einschub, der für alle vier Objekttypen gilt. `docker inspect` gibt den kompletten Zustand eines Objekts als JSON aus — und ist damit die Stelle, an der du nachsehen kannst statt zu raten:

```bash
docker inspect --format '{{.State.ExitCode}}' api
docker inspect --format '{{json .NetworkSettings.Networks}}' api | jq
docker inspect --format '{{range .Mounts}}{{.Source}} → {{.Destination}}{{"\n"}}{{end}}' db
```

Das Format-Argument benutzt Go-Templates. Man muss das nicht beherrschen, aber wissen, dass es existiert: Es ist der Unterschied zwischen „irgendwo in 400 Zeilen JSON" und einer Antwort.

## 5. Die Kontrollfrage: Image vs. Container

> [!question] Kontrollfrage: Erkläre den Unterschied zwischen einem Docker Image und einem Container.

**Ein Image ist eine unveränderliche Vorlage, ein Container eine laufende Instanz davon.** Aus einem Image lassen sich beliebig viele Container erzeugen, die sich die schreibgeschützten Schichten **teilen** und sich nur in ihrer eigenen dünnen beschreibbaren Schicht und ihrer Laufzeitkonfiguration unterscheiden.

Die Analogie, die für dich am nächsten liegt (aus [[Documentation/Traineeship/Grundlagen der Software Entwicklung/1.1 OOP/1.1 OOP - Vertiefung|1.1 OOP]]):

| OOP | Docker |
|---|---|
| **Klasse** — Bauplan, existiert einmal | **Image** — Vorlage, liegt einmal auf der Platte |
| **Objekt** — Instanz mit eigenem Zustand | **Container** — Instanz mit eigener beschreibbarer Schicht |
| `new Foo(x, y)` — Konstruktorargumente | `docker run -e … -p … image` — Laufzeitkonfiguration |
| Viele Objekte, eine Klasse | Viele Container, ein Image |

Ebenso tragfähig, und näher an der Wahrheit dieses Kapitels: **Programm auf der Festplatte** (Image) vs. **Prozess im Speicher** (Container).

> [!warning] Wo die Analogie endet
> Drei Dinge kann die Klasse/Objekt-Analogie nicht: Ein Image ist zusätzlich **aus Schichten aufgebaut** und kann seine Basis mit anderen Images teilen (eher Vererbung als Instanziierung). Ein Container **existiert auch, wenn er nicht läuft** — ein „Objekt im Ruhezustand" gibt es in OOP nicht. Und der Container-Zustand ist **flüchtig**: Er verschwindet mit `docker rm`, während Objektzustand in OOP von der Lebensdauer des Programms abhängt.

Die praktische Konsequenz, die man daraus mitnehmen soll:

```bash
docker run -d --name db1 -e POSTGRES_PASSWORD=a postgres:18
docker run -d --name db2 -e POSTGRES_PASSWORD=b postgres:18
docker run -d --name db3 -e POSTGRES_PASSWORD=c postgres:18
```

Drei völlig unabhängige Datenbanken, drei eigene Dateisysteme — und auf der Platte liegt das Image **trotzdem nur einmal**. Das ist die Eigenschaft aus Stichwort 1, die Container gegenüber VMs überhaupt erst bezahlbar macht, hier direkt sichtbar.

## 6. Volumes

Das Stichwort *Docker Volumes und Datenpersistenz* bekommt später einen eigenen, ausführlichen Abschnitt. Hier geht es nur um die **Objekt-Sicht**: was ein Volume *ist* und wie es sich zu Containern verhält.

### Das Problem in einem Satz

Die beschreibbare Schicht eines Containers wird bei `docker rm` gelöscht. Alles, was ein Container in sein eigenes Dateisystem schreibt, ist damit **an seine Lebensdauer gebunden** — und das ist für eine Datenbank offensichtlich unbrauchbar.

### Die drei Mount-Arten

| | **Named Volume** | **Bind Mount** | **tmpfs** |
|---|---|---|---|
| **Was** | Von Docker verwaltetes Verzeichnis | Ein konkreter Pfad des Hosts | Nur im Arbeitsspeicher |
| **Wo** | `/var/lib/docker/volumes/<name>/_data` | wo du sagst | nirgends (RAM) |
| **Syntax** | `pricing_data:/var/lib/postgresql` | `./src:/app/src` | `--tmpfs /tmp` |
| **Docker-Objekt?** | ✅ ja (`docker volume ls`) | ❌ nein | ❌ nein |
| **Portabel** | ✅ läuft überall gleich | ❌ hängt am Host-Pfad | ✅ |
| **Typischer Einsatz** | **Datenbanken, Produktivdaten** | **Quellcode in der Entwicklung** | Secrets, Caches |

Merkregel: **Named Volume, wenn die Daten wichtig sind. Bind Mount, wenn du sie selbst bearbeiten willst.**

Der Bind Mount ist das, was Live-Reload in der Entwicklung ermöglicht — du hängst deinen Quellcode in den Container, änderst ihn im Editor auf dem Host, und `uvicorn --reload` startet neu, ohne dass das Image neu gebaut werden muss. Der Preis: Der Pfad muss auf jedem Rechner existieren, und die Datei-Eigentümerrechte (UID/GID) des Hosts gelten auch im Container — die klassische Quelle für „Permission denied" und für Dateien, die dem Container-root gehören und die du auf dem Host nicht mehr löschen kannst.

### Volumes sind eigenständige Objekte — und das hat Folgen

> [!important] Ein Volume überlebt seinen Container
> `docker rm container` löscht das Volume **nicht**. Das ist gewollt (Daten sollen nicht versehentlich verschwinden), führt aber dazu, dass sich unbemerkt Volumes ansammeln.
>
> Bewusst löschen: `docker rm -v <container>`, `docker compose down -v`, oder `docker volume prune`.

Zwei Fallen, die daraus folgen:

**1. Anonyme Volumes.** Ein Dockerfile kann `VOLUME /pfad` deklarieren. Startest du so ein Image ohne eigenen Mount, legt Docker automatisch ein **anonymes Volume** mit zufälligem Hash-Namen an. Die Daten sind dann zwar persistent, aber unter einem Namen, den niemand wiedererkennt. Nach ein paar Wochen hat man ein Dutzend davon und weiß bei keinem, wozu es gehört.

**2. Ein leeres Volume verschluckt den Inhalt — und ein volles ihn auch.** Beim ersten Mount eines *leeren* Named Volume kopiert Docker den Inhalt des Zielverzeichnisses aus dem Image hinein (nur bei Named Volumes, nicht bei Bind Mounts — die überdecken den Inhalt kommentarlos). Ist das Volume dagegen bereits gefüllt, gewinnt immer das Volume. Genau das war dein Erlebnis aus 1.6: neues Verzeichnis → neuer Compose-Projektname → neues, leeres Volume → leere Datenbank.

### Ein konkreter Blick in dein Compose-File

```yaml
volumes:
  - pricing_data:/var/lib/postgresql       # ← deins
```

Das ist für `postgres:18` **richtig** — und zwar knapper, als dir vielleicht bewusst ist. Bis PostgreSQL 17 lautete der übliche Pfad `/var/lib/postgresql/data`; mit **Postgres 18 hat das offizielle Image sein `VOLUME` auf `/var/lib/postgresql` geändert** und `PGDATA` versionsspezifisch gemacht (`/var/lib/postgresql/18/docker`). Wer beim Upgrade von 17 auf 18 den alten Pfad stehen lässt, bekommt einen Container, der entweder nicht startet oder — schlimmer — eine leere Datenbank anlegt und die alten Daten unberührt im Volume liegen lässt.

> [!tip] Die Lehre daraus ist allgemein
> Wohin ein Image seine Daten schreibt, ist **Teil seines Vertrags** und kann sich zwischen Major-Versionen ändern. Nachsehen kann man es immer:
> ```bash
> docker image inspect postgres:18 --format '{{json .Config.Volumes}}'
> docker image inspect postgres:18 --format '{{json .Config.Env}}'   # PGDATA
> ```
> Das ist derselbe Reflex wie in 1.6 beim Lesen der Alembic-Changelogs: Bei Werkzeugen, die Zustand verwalten, sind Versionshinweise keine Kür.

## 7. Networks

### Die Grundidee

> [!info] Grundlagen dazu
> Wenn IP-Adressen, Ports, Bind-Adressen und `localhost` nicht sitzen, lies vorher [[IP-Adressen, Ports und Sockets - Grundlagen|IP-Adressen, Ports und Sockets – Grundlagen]]. Dieser Abschnitt setzt das voraus.

Aus Stichwort 1 weißt du: Jeder Container bekommt über den `net`-Namespace einen **eigenen Netzwerk-Stack** — eigene IP, eigene Ports, eigene Routing-Tabelle. Ein Docker-Netzwerk ist die **virtuelle Brücke**, die diese isolierten Stacks miteinander und mit der Außenwelt verbindet.

Technisch legt der Daemon dafür ein `veth`-Paar an (ein virtuelles Netzwerkkabel: ein Ende im Container, eines auf dem Host), hängt das Host-Ende in eine Linux-Bridge und schreibt `iptables`-Regeln für die Portveröffentlichung. Das war Schritt 6 der `docker run`-Zeitlupe.

### Die Netzwerktreiber

| Treiber | Verhalten | Wofür |
|---|---|---|
| **bridge** | eigenes virtuelles Netz, NAT nach außen | **Standard**, Einzelhost — dein Fall |
| **host** | kein eigener `net`-Namespace, teilt sich den Host-Stack | maximale Netzwerk-Performance, kein Port-Mapping möglich |
| **none** | nur Loopback, keine Verbindung | bewusste Totalisolation |
| **overlay** | verbindet Container über **mehrere Hosts** | Swarm/Cluster |
| **macvlan** | Container bekommt eigene MAC/IP im physischen LAN | Legacy-Integration |

### Der Unterschied, auf den es ankommt: Default-Bridge vs. eigenes Netzwerk

Das ist die wichtigste Einzelheit dieses Abschnitts:

> [!important] Nur in **selbst angelegten** Netzwerken funktioniert die DNS-Auflösung über Containernamen
> Im vorgegebenen `bridge`-Netzwerk (dort landen Container ohne `--network`) erreichen sich Container **nur über IP-Adressen** — und die ändert sich bei jedem Neustart.
>
> In einem selbst angelegten Netzwerk betreibt Docker einen eingebauten DNS-Server: Dort ist **der Containername ein auflösbarer Hostname**.

```bash
docker network create pricing-net
docker run -d --name db --network pricing-net postgres:18
docker run -d --name api --network pricing-net pricing-api
# Im api-Container: "db" löst auf die aktuelle IP des db-Containers auf.
```

**Und genau das ist der Grund, warum Compose funktioniert:** Compose legt für jedes Projekt automatisch ein eigenes Netzwerk an und hängt alle Dienste hinein. Deshalb ist der **Dienstname aus der Compose-Datei** ein gültiger Hostname — `db`, `adminer`, später `api`. Du musst dafür nichts konfigurieren; es ist der Standardfall, sobald man Compose benutzt.

Nebeneffekt: Zwei Compose-Projekte auf demselben Rechner sind netzwerkseitig **voneinander isoliert**, weil jedes sein eigenes Netzwerk bekommt.

### Ports veröffentlichen — und der Punkt, an dem dein Projekt bricht

```yaml
ports:
  - "127.0.0.1:5432:5432"      # host-ip : host-port : container-port
```

Drei Dinge dazu:

1. **Ohne `ports` ist ein Container von außen nicht erreichbar** — aber im selben Netzwerk sehr wohl. Container-zu-Container-Verkehr braucht **kein** Port-Mapping. Sobald deine API im selben Compose-Netz läuft wie `db`, ist die Veröffentlichung von 5432 nur noch für dich (psql, Adminer vom Host aus) da, nicht mehr funktional nötig.
2. **`127.0.0.1:` davorzuschreiben ist gut** — ohne diese Bindung lauscht der Port auf *allen* Interfaces. Das hast du richtig gemacht; es ist ein Fehler, den viele Tutorials machen (und der schon zu offenen Datenbanken im Internet geführt hat, weil Docker seine `iptables`-Regeln an der Firewall vorbei einträgt).
3. **`localhost` im Container ist der Container.** Das ist die direkte Folge des `net`-Namespace und der Punkt, an dem deine bisherige Konfiguration bricht:

```
   HEUTE (API auf dem Host)                    NACHHER (API im Container)
   db_host = "localhost"                       DB_HOST=db
             └─ der Host, wo der                       └─ DNS-Name des
                Port veröffentlicht ist                   Dienstes im Netz
```

> [!warning] `0.0.0.0` ist **nicht** localhost — und kommt an zwei Stellen vor
> `127.0.0.1` ist eine **konkrete Adresse** (die Loopback-Schnittstelle). `0.0.0.0` ist **keine Adresse**, sondern ein Platzhalter beim *Lauschen*: „auf allen Schnittstellen annehmen". Man verbindet sich nie *zu* `0.0.0.0`.
>
> Ein Container hat zwei Schnittstellen: `lo` (127.0.0.1) und `eth0` (die veth-IP, z. B. 172.17.0.2). Verkehr von außen kommt über **`eth0`** an. Ein Server, der auf `127.0.0.1` lauscht, nimmt ihn gar nicht erst an — er ist trotz Port-Mapping unerreichbar. Deshalb gilt im Container **immer `--host 0.0.0.0`**, während auf dem eigenen Rechner `127.0.0.1` die sichere Wahl ist.
>
> Verwirrend ist, dass dieselbe Schreibweise auch auf der Host-Seite auftaucht — etwa in der Fehlermeldung `failed to bind host port 0.0.0.0:8000`. Zwei verschiedene Maschinen, dieselbe Bedeutung „alle Schnittstellen":
>
> | Wo | Bedeutung |
> |---|---|
> | `uvicorn --host 0.0.0.0` | im **Container**: auf allen Container-Schnittstellen annehmen |
> | `-p 8000:8000` ohne IP-Präfix | auf dem **Host**: auf allen Host-Schnittstellen veröffentlichen (→ aus dem ganzen LAN erreichbar) |
>
> Und zur Portwahl: Die **linke** Zahl ist frei wählbar (`-p 8001:8000` geht), die **rechte** muss zu dem passen, worauf der Prozess im Container tatsächlich lauscht. Steht im `CMD` kein `--port`, ist es der Default des Programms — bei uvicorn 8000. Genau deshalb schreibt man ihn besser explizit hin, statt sich auf einen stillschweigenden Default zu verlassen.

Fürs Protokoll noch die Gegenrichtung: Wenn ein Container einmal einen Dienst auf dem **Host** erreichen muss, geht das unter Docker Desktop über `host.docker.internal`. Unter der Docker Engine auf Linux — also bei dir — musst du das explizit freischalten (`extra_hosts: ["host.docker.internal:host-gateway"]`). Für die Aufgabe brauchst du es nicht, aber es erklärt Tutorials, die bei dir „einfach nicht funktionieren".

### Die wichtigsten Befehle

```bash
docker network ls
docker network inspect pricing-net        # zeigt alle angeschlossenen Container mit IPs
docker network create meinnetz
docker network connect meinnetz api       # nachträglich anschließen (das geht!)
```

## 8. Aufräumen — und wo der Platz hingeht

Ein praktischer Abschluss, denn Docker ist berüchtigt dafür, unbemerkt die Platte zu füllen:

```bash
docker system df           # Übersicht: Images, Container, Volumes, Build-Cache
docker system df -v        # detailliert, pro Objekt — zeigt auch, was "reclaimable" ist
```

```bash
docker container prune     # gestoppte Container
docker image prune         # dangling Images (<none>)
docker image prune -a      # ALLE Images ohne laufenden Container
docker builder prune       # BuildKit-Cache (wird oft der größte Posten!)
docker system prune        # die ersten drei zusammen
```

> [!danger] Vorsicht bei zwei Optionen
> `docker system prune --volumes` und `docker volume prune` löschen **Volumes ohne zugeordneten Container** — also unter Umständen deine Datenbank, wenn der Container gerade entfernt ist. Es gibt keine Nachfrage pro Objekt und kein Rückgängig.
>
> Angewöhnen: erst `docker system df -v` lesen, dann gezielt löschen. `docker system prune -a --volumes` ist kein Aufräumbefehl, sondern ein Reset.

# Docker CLI: Grundlegende Befehle und Anwendung

## 1. Warum dieses Stichwort kurz sein darf

Die Objekt-Systematik aus dem letzten Stichwort hat die Hauptarbeit schon erledigt: Wer weiß, dass es vier Objekte mit je vier Verben gibt, kennt bereits die halbe CLI. Deshalb geht es hier nicht um eine Befehlsliste — die steht in `docker --help` und in der Referenz — sondern um drei Dinge, die man **nicht** nachschlagen kann:

1. Die **Grammatik** der Befehle (und die eine Stelle, an der sich jeder Anfänger vertut).
2. Die **Arbeitsabläufe**: welche Befehle in welcher Reihenfolge man in der Praxis tatsächlich tippt.
3. Die **Fehlermeldungen** und was sie wirklich bedeuten.

## 2. Die Grammatik

```
docker  [objekt]  <verb>  [optionen]  <ziel>  [befehl + argumente]
        └───────┬───────┘ └────┬────┘ └──┬──┘ └────────┬─────────┘
          was und wozu      Flags     Image /     was IM Container
                                      Container    laufen soll
```

Beispiel, vollständig zerlegt:

```bash
docker container run  -d --name api -p 8000:8000  pricing-api:latest  uvicorn --port 8000
       └──── Objekt+Verb ──┘ └──── Optionen ────┘  └──── Image ────┘  └──── Befehl ────┘
```

> [!warning] Der Fehler, den jeder genau einmal macht
> **Alles nach dem Image-Namen ist nicht mehr für Docker bestimmt**, sondern wird als Befehl *in* den Container gereicht.
>
> ```bash
> docker run pricing-api -p 8000:8000     # ❌ übergibt "-p 8000:8000" an DEIN Programm
> docker run -p 8000:8000 pricing-api     # ✅
> ```
>
> Die erste Variante gibt keinen Docker-Fehler — sie startet deinen Container mit sinnlosen Argumenten. Das kann man lange suchen. **Merksatz: Flags gehören vor das Image.**

Der Befehl am Ende ersetzt das `CMD` des Images. Das ist kein Sonderfall, sondern ein Werkzeug:

```bash
docker run --rm postgres:18 postgres --version   # Version prüfen, ohne die DB zu starten
docker run --rm -it python:3.13-slim bash        # eine Shell statt des Python-Interpreters
```

## 3. Die Flags, die man wirklich braucht

Statt einer alphabetischen Liste die Flags nach Zweck sortiert — und zwar nur die, die im Alltag vorkommen:

| Flag | Bedeutung | Wann |
|---|---|---|
| `-d`, `--detach` | Im Hintergrund starten, ID ausgeben | Dienste (DB, API) |
| `-it` | siehe unten | Interaktive Shells |
| `--rm` | Container nach dem Ende automatisch löschen | **Alle Wegwerf-Container** |
| `--name` | Fester Name statt `zealous_hopper` | Alles, was man wiederfinden will |
| `-p 8000:8000` | Port veröffentlichen (`host:container`) | Zugriff vom Host |
| `-v name:/pfad` | Volume oder Bind Mount einhängen | Persistenz, Quellcode |
| `-e KEY=wert` | Eine Umgebungsvariable setzen | Konfiguration |
| `--env-file .env` | Alle Variablen aus einer Datei | **Dein Fall** — statt `-e` fünfmal |
| `--network netz` | In ein bestimmtes Netzwerk hängen | Container-zu-Container |
| `-w /app` | Arbeitsverzeichnis überschreiben | Einzelbefehle |
| `-u 1000:1000` | Als anderer Benutzer laufen | Rechteprobleme bei Bind Mounts |
| `--entrypoint sh` | **Den Entrypoint überschreiben** | Debugging kaputter Images |
| `--restart unless-stopped` | Nach Absturz/Reboot neu starten | Dauerbetrieb |
| `-m 512m`, `--cpus 1.5` | cgroup-Limits setzen | Ressourcen begrenzen |

### `-it` ist zusammengesetzt, und der Unterschied zählt

- **`-i` (`--interactive`)** hält **stdin offen**. Ohne das bekommt der Prozess im Container sofort EOF — genau der Effekt aus dem letzten Stichwort, bei dem `docker run debian` sich sofort beendet.
- **`-t` (`--tty`)** weist ein **Pseudo-Terminal** zu. Das bringt Zeilenumbrüche, Farben, einen Prompt und die Signalweitergabe von `Strg+C`.

Daraus folgen die drei sinnvollen Kombinationen:

```bash
docker run -it   …  bash    # Shell zum Arbeiten — beides nötig
docker run -i    …  < datei.sql   # Eingabe aus einer Pipe: -i ja, -t nein!
docker run -d    …          # Dienst im Hintergrund — weder noch
```

> [!tip] `-it` und `-d` schließen sich nicht formal aus, sind aber fast immer ein Denkfehler
> `docker run -dit` startet einen Container mit TTY im Hintergrund. Das braucht man nur für den Trick „Container am Leben halten, obwohl er nichts tut" — und der ist meistens ein Zeichen dafür, dass etwas anderes falsch konstruiert ist.

## 4. Die Arbeitsabläufe

### Erkunden: ein fremdes Image verstehen, bevor man es benutzt

```bash
docker pull postgres:18
docker image inspect postgres:18 --format '{{json .Config}}' | jq   # Cmd, Env, Volumes, Ports
docker image history postgres:18                                     # wie wurde es gebaut?
docker run --rm -it postgres:18 bash                                 # drin umsehen, ohne DB-Start
```

Das ist ein Reflex, den man sich früh angewöhnen sollte: Ein Image ist eine Blackbox, bis man `inspect` und `history` darauf angewendet hat. `Config.Env` verrät die erwarteten Variablen, `Config.Volumes` die Datenpfade, `Config.Cmd` den Startbefehl.

### Beobachten: was tut mein Container gerade?

```bash
docker ps -a                          # Status + Exit-Code aller Container
docker logs -f --tail 50 api          # letzte 50 Zeilen und dann live weiter
docker logs --since 10m api           # nur die letzten 10 Minuten
docker stats                          # live: CPU, RAM (inkl. Limit!), Netz, I/O
docker top api                        # Prozessliste IM Container
docker events                         # live-Strom aller Daemon-Ereignisse
docker diff api                       # was hat der Container an seinem FS geändert?
```

Zwei davon werden unterschätzt:

**`docker stats`** zeigt in der Spalte `MEM USAGE / LIMIT` sowohl den Verbrauch als auch das cgroup-Limit. Das ist der Befehl, mit dem man einen Container findet, der gleich vom OOM-Killer erwischt wird.

**`docker diff`** listet jede Datei, die sich seit dem Start in der beschreibbaren Schicht geändert hat (`A` added, `C` changed, `D` deleted). Es ist die praktische Demonstration des Layer-Modells aus Stichwort 3 — und ein guter Weg herauszufinden, ob eine Anwendung heimlich in ihr eigenes Dateisystem schreibt statt in ein Volume.

**`docker logs` liest nur stdout/stderr des PID-1-Prozesses.** Wer in eine Datei im Container loggt, sieht hier nichts. Das ist der Grund, warum die Regel „Container loggen nach stdout" gilt — dein `logging_setup.py` aus 1.4 wird im Container also einen StreamHandler brauchen, keinen FileHandler.

### Eingreifen: hinein in den laufenden Container

```bash
docker exec -it api bash                  # Shell im laufenden Container
docker exec api env                       # nur einen Befehl, ohne Shell
docker exec -it db psql -U pricing        # direkt in die Datenbank
docker cp api:/app/logs/app.log ./        # Datei herausholen
docker cp ./fix.sql db:/tmp/              # Datei hineinlegen
```

> [!note] „`bash`: executable file not found"
> Viele schlanke Images haben **keine bash** — Alpine-basierte haben nur `sh`, „distroless"-Images gar keine Shell. Erste Alternative: `sh` probieren. Wenn auch das fehlt, ist das Absicht (kleinere Angriffsfläche), und man debuggt über `docker logs`, `docker inspect` oder einen temporären Debug-Container im selben Namespace.

### Ein kaputtes Image debuggen

Der wertvollste Trick des ganzen Stichworts. Wenn ein Container sofort mit einem Fehler endet und du nicht siehst, warum:

```bash
# 1. Was sagt er, bevor er stirbt?
docker logs <container>

# 2. Den Startbefehl umgehen und selbst nachsehen:
docker run --rm -it --entrypoint sh pricing-api:latest
#   → drin: ls -la /app, cat /app/..., env, python -c "import pricing"

# 3. Mit exakt derselben Konfiguration, aber anderer Shell:
docker compose run --rm --entrypoint sh api
```

Schritt 2 ist deshalb so nützlich, weil er **das Image mit allen seinen Schichten** startet, aber nicht deine Anwendung. Damit trennst du „das Image ist falsch gebaut" von „die Anwendung startet nicht".

### Aufräumen mit Filtern und Pipes

```bash
docker ps -aq                                    # nur IDs — für Pipes gemacht
docker rm $(docker ps -aq --filter status=exited)
docker ps --filter name=pricing --format 'table {{.Names}}\t{{.Status}}'
docker image ls --filter dangling=true
```

`-q` (quiet), `--filter` und `--format` sind die drei Optionen, die fast jeder Befehl versteht. Sie machen aus der CLI ein skriptbares Werkzeug — was wieder daran liegt, dass darunter nur eine REST-API mit JSON-Antworten steckt.

## 5. Die Compose-CLI

Für die Aufgabe wirst du fast nur noch `docker compose` tippen. Die Befehle sind bewusst parallel aufgebaut, arbeiten aber auf **Diensten** statt auf Containern:

| Docker | Compose | Anmerkung |
|---|---|---|
| `docker run` | `docker compose up` | startet **alle** Dienste der Datei |
| `docker stop` + `rm` | `docker compose down` | entfernt auch das Netzwerk |
| `docker ps` | `docker compose ps` | nur dieses Projekt |
| `docker logs -f api` | `docker compose logs -f api` | `api` = Dienstname, nicht Containername |
| `docker exec -it db psql` | `docker compose exec db psql` | kein `-it` nötig, ist Default |
| `docker build` | `docker compose build` | baut die Dienste mit `build:` |
| — | `docker compose config` | **löst die Datei auf und validiert sie** |
| — | `docker compose run --rm migrate` | **Einmal-Befehl in einem neuen Container** |

Die vier, die im Alltag zählen:

```bash
docker compose up -d --build      # bauen, wenn nötig, und im Hintergrund starten
docker compose logs -f api        # einem Dienst zusehen
docker compose down               # alles weg — Volumes bleiben!
docker compose down -v            # ... auch die Volumes. Vorsicht.
```

Und zwei, die du für die Aufgabe brauchen wirst:

**`docker compose config`** rechnet Variablen-Substitutionen, `.env`-Dateien, `extends` und Overrides aus und zeigt dir die **tatsächlich wirksame** Konfiguration. Bei „warum nimmt er meine Umgebungsvariable nicht?" ist das der erste Befehl, nicht der zehnte.

**`docker compose run --rm`** startet einen **neuen, einmaligen** Container aus einem Dienst — mit dessen Image, Netzwerk und Umgebung, aber einem anderen Befehl. Genau das braucht man für Migrationen:

```bash
docker compose run --rm api alembic upgrade head
```

> [!important] `run` vs. `exec` — der Unterschied, den man verwechselt
> **`exec`** braucht einen **laufenden** Container und startet einen zweiten Prozess *darin*.
> **`run`** erzeugt einen **neuen** Container (deshalb `--rm` nicht vergessen).
>
> Für `alembic upgrade head` ist `run` richtig: Die Migration soll unabhängig davon laufen, ob die API gerade läuft — und in einem Container, der danach verschwindet.

## 6. Fehlermeldungen übersetzt

Die Tabelle, die dir die meisten Suchmaschinen-Besuche spart:

| Meldung / Symptom | Bedeutung | Erste Maßnahme |
|---|---|---|
| `permission denied … /var/run/docker.sock` | Du darfst nicht auf den Socket schreiben | `sudo`, oder Gruppe `docker` (siehe Sicherheitshinweis in Stichwort 2) |
| `port is already allocated` | Der **Host**-Port ist belegt | `ss -tlnp \| grep 5432` — oft ein lokal installiertes PostgreSQL |
| `name is already in use` | Ein **gestoppter** Container hält den Namen | `docker rm <name>` |
| `no such host` / DNS schlägt fehl | Falsches Netzwerk oder Default-Bridge | Dienstname statt IP, gemeinsames Netz prüfen |
| `connection refused` an `db:5432` | Netz ist richtig, **Dienst noch nicht bereit** | Healthcheck + `depends_on: condition` |
| `Exited (0)` | Prozess **sauber** beendet — meist kein Fehler | Ist es ein Dienst? Dann fehlt der Vordergrundprozess |
| `Exited (1)` | Anwendungsfehler | `docker logs` |
| `Exited (137)` | 128+9 = **SIGKILL** — meist **OOM** oder `docker kill` | `docker stats`, Speicherlimit prüfen |
| `Exited (143)` | 128+15 = SIGTERM — normales `docker stop` | in Ordnung |
| `exec format error` | **Falsche Architektur** (arm64-Image auf amd64) | `docker image inspect … Architecture` |
| `toomanyrequests` beim Pull | Docker-Hub-**Rate-Limit** | einloggen oder Registry spiegeln |
| Änderung am Code wirkt nicht | Image nicht neu gebaut | `docker compose up -d --build` |

> [!tip] Der Exit-Code ist die schnellste Diagnose
> `docker ps -a` zeigt ihn immer an. **0** = sauber beendet, **1** = Anwendungsfehler, **137** = abgeschossen, **143** = gestoppt. Alles über 128 bedeutet „durch Signal beendet" (Signalnummer = Code − 128).

## 7. Ein realistischer Ablauf mit deinem Projekt

So wird sich die Arbeit an der Aufgabe anfühlen — als Vorschau auf die Befehle, die du tatsächlich tippen wirst:

```bash
# 1. Bauen und starten
docker compose up -d --build

# 2. Läuft alles? Was ist der Status?
docker compose ps

# 3. Die API meldet einen Fehler — nachsehen
docker compose logs -f api

# 4. Sind die DB-Variablen im Container wirklich das, was ich denke?
docker compose exec api env | grep -i -e db_ -e pricing
docker compose config | grep -A5 environment      # ... und was Compose daraus macht

# 5. Erreicht die API die Datenbank überhaupt?
docker compose exec api python -c "import socket; print(socket.gethostbyname('db'))"

# 6. Migration ausführen
docker compose run --rm api alembic upgrade head

# 7. In die Datenbank schauen
docker compose exec db psql -U pricing -d pricing -c '\dt'

# 8. Code geändert → neu bauen, nur diesen Dienst
docker compose up -d --build api

# 9. Feierabend
docker compose down          # OHNE -v, sonst ist die Datenbank weg
```

> [!note] Was daran auffällt
> Neun Befehle, und acht davon sind `docker compose`. Das ist der Normalfall in der Entwicklung — die einzelnen `docker`-Befehle brauchst du vor allem für **Diagnose** und für Wegwerf-Container. Wer Compose benutzt, tippt selten `docker run`.

# Dockerfile: Struktur und Best Practices

## 1. Was ein Dockerfile ist

> [!important] Definition
> Ein **Dockerfile** ist ein **Textrezept**, das Schritt für Schritt beschreibt, wie aus einem Basis-Image ein neues Image entsteht. Jede Anweisung wird der Reihe nach ausgeführt, und die meisten erzeugen dabei **eine neue Schicht**.

Hier lohnt ein Blick zurück auf die Unterscheidung aus 1.6: Ein Dockerfile ist ein **Weg**, kein Sollzustand. Es beschreibt nicht „so soll das Image aussehen", sondern „so kommst du von `python:3.13-slim` dorthin" — genau wie eine Alembic-Migration.

Der Unterschied zur Datenbank ist nur: Hier darf man den Weg jederzeit von vorne gehen, weil kein unersetzlicher Zustand dranhängt. Deshalb ist ein Dockerfile *editierbar* und eine ausgelieferte Migration nicht.

## 2. Der Build-Prozess (Kontrollfrage 3, Teil 1)

```bash
docker build -t pricing-api:0.1.0 .
#            └── Tag ───────────┘ └┬┘
#                                  └── der BUILD-KONTEXT
```

> [!warning] Der Punkt am Ende ist nicht „hier"
> Das letzte Argument ist der **Build-Kontext**: das Verzeichnis, dessen Inhalt **an BuildKit übertragen** wird, bevor der Build beginnt. Der Build läuft nicht in deinem Verzeichnis — er läuft in einem separaten Prozess, der nur sieht, was du ihm schickst.
>
> Deshalb kann `COPY` nur auf Dateien **innerhalb** des Kontexts zugreifen: `COPY ../geheim.env .` ist kein Rechteproblem, sondern schlicht außerhalb dessen, was übertragen wurde.

Der vollständige Ablauf:

| # | Was passiert |
|---|---|
| 1 | Die CLI packt den **Build-Kontext** (abzüglich `.dockerignore`) und schickt ihn an BuildKit |
| 2 | Das Dockerfile wird geparst und als **Abhängigkeitsgraph** analysiert |
| 3 | Das Basis-Image aus `FROM` wird aufgelöst und geholt (falls nicht lokal) |
| 4 | Jede Anweisung wird ausgeführt; wo möglich, wird der **Cache** benutzt |
| 5 | Jede `RUN`/`COPY`/`ADD` erzeugt eine **neue Schicht** (Diff zum Vorzustand) |
| 6 | Die **Config** wird geschrieben (`Cmd`, `Env`, `User`, `ExposedPorts`, …) |
| 7 | Manifest und Config bekommen ihren **Digest** — das Image existiert |
| 8 | Der **Tag** `pricing-api:0.1.0` wird darauf gesetzt |

### `.dockerignore` — nicht optional

Weil Schritt 1 den gesamten Kontext überträgt, ist eine `.dockerignore` bei einem Python-Projekt Pflicht. Ohne sie schickst du mit:

```
.venv/          ← hunderte MB, und für das Image völlig nutzlos
.git/           ← die gesamte Projekthistorie
__pycache__/    ← Bytecode der falschen Umgebung
.mypy_cache/  .pytest_cache/  .ruff_cache/
.env            ← ⚠️ Secrets, die im Image landen könnten
logs/  daily_data/  *.csv
```

Drei Gründe, warum das mehr als Kosmetik ist:

1. **Geschwindigkeit** — der Kontext wird bei *jedem* Build übertragen.
2. **Cache** — ein `COPY . .` wird durch **jede** Änderung im Kontext ungültig, auch durch eine neue Log-Datei. Ohne `.dockerignore` baut Docker ständig neu, ohne dass sich Relevantes geändert hat.
3. **Sicherheit** — was nicht im Kontext ist, kann nicht versehentlich ins Image kopiert werden.

> [!tip] Faustregel
> `.dockerignore` sollte mindestens alles enthalten, was in `.gitignore` steht — **plus `.git` selbst**.

## 3. Die Anweisungen

| Anweisung | Zweck | Merkposten |
|---|---|---|
| `FROM` | Basis-Image | Muss (fast) zuerst stehen; startet eine neue Stage |
| `ARG` | Build-Zeit-Variable | Vor dem ersten `FROM` erlaubt; **nicht im fertigen Image** |
| `ENV` | Laufzeit-Umgebungsvariable | Landet **im Image** und ist per `docker inspect` lesbar |
| `WORKDIR` | Arbeitsverzeichnis | Legt es an, falls nötig — besser als `RUN cd` (das wirkt nicht) |
| `COPY` | Dateien aus dem Kontext | **Standardwahl** |
| `ADD` | wie COPY + URL + Auto-Entpacken | Nur für lokale Tar-Archive; sonst `COPY` |
| `RUN` | Befehl **zur Bauzeit** | Erzeugt eine Schicht |
| `USER` | Benutzer für alles Folgende | Sollte am Ende auf einen Nicht-root wechseln |
| `EXPOSE` | Port dokumentieren | **Öffnet nichts!** Reine Metadaten |
| `CMD` | Standard-Argumente / Startbefehl | Von `docker run … <befehl>` überschreibbar |
| `ENTRYPOINT` | Das eigentliche Programm | Nur mit `--entrypoint` überschreibbar |
| `HEALTHCHECK` | Bereitschaftsprüfung | Wird von `depends_on: condition` genutzt |
| `VOLUME` | Pfad als Volume deklarieren | In **eigenen** Images meist unnötig (s. u.) |
| `LABEL` | Metadaten | z. B. `org.opencontainers.image.source` |

Vier Fallstricke, die man kennen muss:

**`EXPOSE` öffnet keinen Port.** Es ist Dokumentation im Image — ein Hinweis für Menschen und für `docker run -P`. Die tatsächliche Veröffentlichung macht `-p` bzw. `ports:` in Compose. Man kann einen Port veröffentlichen, der nie `EXPOSE`d wurde, und umgekehrt.

**`RUN cd /app` wirkt nicht.** Jede `RUN`-Anweisung startet eine eigene Shell; das Arbeitsverzeichnis ist danach wieder weg. Dafür gibt es `WORKDIR`.

**`ENV` bleibt im Image, `ARG` nicht.** Deshalb dürfen Secrets in *keinem* von beiden stehen — `ARG` ist zwar nicht im Environment des Containers, aber in der Build-Historie (`docker image history`) sichtbar. Für echte Secrets gibt es BuildKit-Secrets (Abschnitt 7).

**`VOLUME` in eigenen Images ist meist ein Fehler.** Es erzwingt ein anonymes Volume für jeden, der das Image benutzt (siehe Stichwort 3), und lässt sich nicht wieder abschalten. Die Entscheidung, wo Daten liegen, gehört in die Compose-Datei — also zu dem, der das Image *benutzt*, nicht zu dem, der es baut.

## 4. Layer-Caching — das wichtigste Konzept

Beim Bauen prüft BuildKit für jede Anweisung, ob das Ergebnis schon im Cache liegt. Wenn ja, wird die Schicht wiederverwendet; wenn nein, wird neu gebaut.

> [!important] Die eine Regel
> Sobald eine Schicht neu gebaut werden muss, werden **alle folgenden Schichten ebenfalls neu gebaut** — der Cache ist ab dort ungültig.

Woran der Cache erkennt, ob sich etwas geändert hat, ist je nach Anweisung unterschiedlich:

| Anweisung | Cache-Schlüssel |
|---|---|
| `COPY` / `ADD` | **Inhalt** der Dateien (Prüfsumme) |
| `RUN` | **nur der Befehlstext** (!) |
| `FROM` | Digest des Basis-Images |

Die Konsequenz aus Zeile 2 ist berüchtigt: `RUN apt-get update` liefert beim zweiten Build denselben Befehlstext und wird deshalb **aus dem Cache genommen** — obwohl sich die Paketlisten längst geändert haben. Das ist der Grund für die Regel, `update` und `install` **immer in einem `RUN`** zu verbinden.

### Die praktische Folge: Reihenfolge nach Änderungshäufigkeit

Das ist die wichtigste Strukturentscheidung in jedem Dockerfile. Was sich selten ändert, gehört nach oben; was sich bei jedem Commit ändert, nach unten.

```dockerfile
# ❌ Falsch: jede Code-Änderung wirft die Abhängigkeiten weg
COPY . .
RUN uv sync --frozen                # läuft bei JEDEM Build neu — Minuten

# ✅ Richtig: Abhängigkeiten zuerst, Code zuletzt
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev       # nur neu, wenn sich die Lockfile ändert
COPY src/ ./src/                    # ändert sich ständig — steht deshalb unten
```

Der Unterschied im Alltag ist der zwischen einem Build von zwei Sekunden und einem von zwei Minuten — bei jedem einzelnen Durchlauf. Genau dafür liegt die Abhängigkeitsliste in einer eigenen Datei: `pyproject.toml` und `uv.lock` ändern sich selten, `src/` ständig.

### Cache-Mounts: der Cache, der nicht ins Image gehört

BuildKit kann darüber hinaus ein Verzeichnis bereitstellen, das **zwischen Builds überlebt, aber nicht in einer Schicht landet**:

```dockerfile
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev
```

Damit muss uv bereits heruntergeladene Pakete nicht erneut holen — und trotzdem bläht der Download-Cache das Image nicht auf. Dasselbe Muster gibt es für `apt` und `pip`.

## 5. `CMD` vs. `ENTRYPOINT` — und die PID-1-Falle

Hier laufen mehrere Fäden des Kapitels zusammen.

### Die zwei Schreibweisen

```dockerfile
CMD ["uvicorn", "pricing.main:app", "--host", "0.0.0.0"]   # exec-Form  (JSON-Array)
CMD uvicorn pricing.main:app --host 0.0.0.0                # shell-Form (Text)
```

Sie sehen gleichwertig aus, sind es aber nicht:

| | exec-Form `["…"]` | shell-Form |
|---|---|---|
| Was läuft als PID 1 | **dein Programm** | `/bin/sh` |
| Dein Programm ist | PID 1 | PID 2, Kind der Shell |
| `SIGTERM` bei `docker stop` | kommt **an** | bleibt bei der Shell **hängen** |
| Variablen-Expansion (`$PORT`) | nein | ja |
| Braucht eine Shell im Image | nein | ja |

> [!danger] Warum die shell-Form fast immer falsch ist
> Bei `docker stop` schickt Docker `SIGTERM` an **PID 1** — also an die Shell. Die reicht es **nicht weiter**. Dein Uvicorn oder Postgres bekommt nichts mit, fährt nicht herunter, und nach 10 Sekunden kommt `SIGKILL` für alle.
>
> Symptome: Jedes `docker compose down` dauert exakt 10 Sekunden. Offene Verbindungen brechen ab. Die Datenbank macht beim nächsten Start Recovery. Und das alles ohne eine einzige Fehlermeldung.
>
> **Regel: immer die exec-Form.** Wer Variablen-Expansion braucht, schreibt ein kleines Entrypoint-Skript und beendet es mit `exec "$@"` — das `exec` ersetzt die Shell durch das Programm, das damit PID 1 wird.

> [!note] Die *zweite* PID-1-Falle: Zombies
> Die Signal-Falle oben ist die bekannte. Es gibt eine zweite, die ein anderes Problem beschreibt.
>
> Unter Linux hat PID 1 eine **Pflicht**: Stirbt ein Prozess, bevor sein Elternprozess ihn per `wait()` abgeholt hat, wird das verwaiste Kind an PID 1 weitergereicht. PID 1 muss es einsammeln — sonst bleibt ein **Zombie** in der Prozesstabelle stehen, ein Eintrag ohne Prozess, der nur den Exit-Code hält.
>
> Auf einem normalen System erledigt das `systemd`. Im Container ist PID 1 aber **deine Anwendung**, und die weiß von dieser Pflicht nichts. Bei Programmen, die Subprozesse forken (CI-Runner, `subprocess.run()` in Schleifen, Headless-Browser), füllt sich die Tabelle über Tage.
>
> Lösung ist ein winziges echtes Init-Programm davor:
> ```bash
> docker run --init …          # Docker schiebt "tini" als PID 1 davor
> ```
> ```yaml
> api:
>   init: true                 # dasselbe in Compose
> ```
> `tini` wird PID 1, startet die Anwendung als Kind, **leitet Signale weiter** und **sammelt Zombies ein** — es löst also beide Fallen zugleich.
>
> | | **Falle A: Signale** | **Falle B: Zombies** |
> |---|---|---|
> | Ursache | Shell als PID 1 leitet `SIGTERM` nicht weiter | PID 1 sammelt verwaiste Kinder nicht ein |
> | Symptom | `docker stop` dauert immer 10 s, hartes Ende | Prozesstabelle füllt sich langsam |
> | Lösung | **exec-Form** von `CMD` | `init: true` / `tini` |
>
> Dazu eine Kernel-Eigenheit, die Falle A verschärft: Signale mit Standardverhalten (wie `SIGTERM` → beenden) werden an PID 1 **gar nicht zugestellt**, solange kein eigener Handler registriert ist. Ein Programm ohne SIGTERM-Handler ignoriert `docker stop` also auch dann, wenn es korrekt PID 1 ist. uvicorn und PostgreSQL behandeln das Signal; ein selbstgeschriebenes Skript oft nicht.

### Die Rollenverteilung

- **`ENTRYPOINT`** = *was* ausgeführt wird — das Programm.
- **`CMD`** = *womit* — die Standard-Argumente, die man leicht überschreiben kann.

```dockerfile
ENTRYPOINT ["uvicorn", "pricing.main:app"]
CMD ["--host", "0.0.0.0", "--port", "8000"]
```

```bash
docker run img                              # → uvicorn … --host 0.0.0.0 --port 8000
docker run img --port 9000                  # → uvicorn … --port 9000   (CMD ersetzt)
docker run --entrypoint bash -it img        # → bash                    (ENTRYPOINT ersetzt)
```

Nur `CMD` (ohne `ENTRYPOINT`) ist die flexiblere Variante und für Anwendungs-Images meistens die richtige — dann funktioniert `docker compose run --rm api alembic upgrade head` einfach, weil der Befehl komplett ersetzt wird. Genau der Fall aus dem letzten Stichwort.

## 6. Multi-Stage Builds (Kontrollfrage 4)

### Das Problem

Um ein Python-Projekt zu installieren, braucht man Dinge, die zur **Laufzeit** niemand mehr braucht: `uv` selbst, unter Umständen einen C-Compiler, Header-Pakete, Download-Caches, Build-Artefakte. In einem einstufigen Build landet **alles davon im Image** — und wegen des Whiteout-Problems aus Stichwort 3 bringt nachträgliches `RUN rm -rf` nichts.

### Die Lösung

Mehrere `FROM`-Anweisungen in einer Datei. Jedes `FROM` beginnt eine neue **Stage** mit frischem Dateisystem; mit `COPY --from=<stage>` holt man gezielt einzelne Ergebnisse herüber. **Nur die letzte Stage wird das Image** — alles andere wird verworfen.

```dockerfile
# ---------- Stage 1: bauen ----------
FROM python:3.13-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev --no-install-project
COPY src/ ./src/
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --frozen --no-dev

# ---------- Stage 2: laufen ----------
FROM python:3.13-slim
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY --from=builder /app/src   /app/src
ENV PATH="/app/.venv/bin:$PATH"
USER 1000:1000
CMD ["uvicorn", "…"]
```

> [!note] Das ist ein **Muster**, kein fertiges Dockerfile für dein Projekt
> Es zeigt die Technik. Was davon für `pricing` passt, welche Pfade stimmen und wie der Startbefehl aussieht, erarbeitest du selbst — dazu kommt der abhakbare Plan (siehe Ende dieses Abschnitts).

Zwei Details, die man leicht übersieht:

- **`uv sync --no-install-project` in der ersten Runde**, dann Code kopieren, dann noch einmal `uv sync`. Damit hängt der teure Schritt (alle Abhängigkeiten) nur an der Lockfile und nicht am Quellcode — das Caching-Prinzip aus Abschnitt 4, konsequent angewandt.
- **`COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv`** holt eine einzelne Binärdatei aus einem *fremden Image*. `--from` kann nicht nur eigene Stages referenzieren.

### Warum das lohnt

| Vorteil | Erklärung |
|---|---|
| **Kleineres Image** | Compiler, `uv`, Header, Caches bleiben zurück — oft Faktor 2–5 |
| **Kleinere Angriffsfläche** | Was nicht im Image ist, kann nicht ausgenutzt werden |
| **Keine Secret-Reste** | Was in Stage 1 passiert, existiert in Stage 2 nicht — auch nicht in einer unteren Schicht |
| **Schnellere Deployments** | Weniger Bytes durch die Registry, bei jedem Rollout |
| **Parallelität** | BuildKit baut unabhängige Stages **gleichzeitig** |
| **Ein Dockerfile für mehrere Ziele** | `--target test` baut nur bis zur Test-Stage |

Der letzte Punkt ist elegant: Man kann eine Stage `test` einbauen, die `pytest` ausführt, und in CI `docker build --target test .` aufrufen — dieselbe Datei, ein anderer Endpunkt. Für dein Projekt eine naheliegende Erweiterung, nachdem die Grundversion läuft.

## 7. Best Practices, konsolidiert

### Das Basis-Image

| Variante | Größe | Wann |
|---|---|---|
| `python:3.13` | ~1 GB | selten — enthält Compiler und viel Werkzeug |
| **`python:3.13-slim`** | ~150 MB | **Standardwahl**, Debian-basiert |
| `python:3.13-alpine` | ~50 MB | **Vorsicht bei Python** — siehe unten |
| distroless / `scratch` | minimal | Fortgeschritten; keine Shell, kein `docker exec` |

> [!warning] Alpine ist bei Python die falsche Sparsamkeit
> Alpine benutzt **musl** statt **glibc**. Die vorkompilierten Wheels auf PyPI sind traditionell gegen glibc gebaut (`manylinux`) — auf Alpine greifen sie nicht, `pip`/`uv` fallen auf den Quellcode zurück und **kompilieren**. Dokumentiert sind Builds, die statt 30 Sekunden über 20 Minuten dauern und am Ende trotz „kleinerem" Basis-Image *größer* sind, weil Compiler und Header mitinstalliert werden mussten.
>
> Inzwischen gibt es `musllinux`-Wheels (PEP 656), und viele große Pakete — auch psycopg — liefern sie. Aber es ist keine Garantie, sondern eine Eigenschaft *jedes einzelnen Pakets*. Für dein Projekt mit `psycopg[binary]` und SQLAlchemy ist **`slim` die richtige Wahl**: die 100 MB Unterschied sind irrelevant gegenüber der Verlässlichkeit.

### Die Liste

1. **Reihenfolge nach Änderungshäufigkeit** — Abhängigkeiten oben, Quellcode unten.
2. **`.dockerignore` pflegen** — mindestens der Inhalt von `.gitignore`, plus `.git`.
3. **Nicht als root laufen** — `USER 1000:1000` am Ende. Ohne das ist der Prozess root im Container, und bei einem Ausbruch (oder einem Bind Mount) ist das direkt relevant. Kostet eine Zeile.
4. **exec-Form für `CMD`/`ENTRYPOINT`** — siehe PID-1-Falle.
5. **Ein Prozess pro Container** — kein `supervisord`, keine Datenbank im API-Image. Wenn zwei Dinge laufen sollen, sind es zwei Container. Das ist der Übergang zu Compose.
6. **Nach stdout loggen** — sonst zeigt `docker logs` nichts (Stichwort 4).
7. **Basis-Image mit Tag, besser mit Digest festnageln** — `python:3.13-slim` statt `python:latest`; für echte Reproduzierbarkeit `@sha256:…`.
8. **`apt-get`-Idiom in *einem* `RUN`:**
   ```dockerfile
   RUN apt-get update \
    && apt-get install -y --no-install-recommends libpq5 \
    && rm -rf /var/lib/apt/lists/*
   ```
   `update` und `install` getrennt → Cache-Problem aus Abschnitt 4. `rm` in einer eigenen Schicht → wirkungslos. `--no-install-recommends` spart erfahrungsgemäß den halben Platz.
9. **Keine Secrets** — weder `ENV`, noch `ARG`, noch `COPY .env`. Zur Bauzeit gibt es dafür BuildKit-Secrets:
   ```dockerfile
   RUN --mount=type=secret,id=pypi_token \
       PIP_TOKEN=$(cat /run/secrets/pypi_token) uv sync
   ```
   Zur Laufzeit kommt Konfiguration von außen — deine `pydantic-settings`-Config ist dafür schon richtig gebaut.
10. **`HEALTHCHECK` setzen**, wenn andere Dienste auf die Bereitschaft warten sollen — das ist die Brücke zu `depends_on: condition: service_healthy` in Compose.

## 8. Die Kontrollfragen 3 und 4

> [!question] Wie erstellt man ein Docker Image? Beschreibe den Prozess und die Rolle des Dockerfiles.

Man schreibt ein **Dockerfile** — ein versioniertes Textrezept im Repository, das von einem Basis-Image ausgehend jeden Schritt beschreibt — und ruft `docker build -t name:tag .` auf. Die CLI überträgt den **Build-Kontext** (das Verzeichnis am Ende, gefiltert durch `.dockerignore`) an **BuildKit**. Dieses arbeitet die Anweisungen der Reihe nach ab, wobei jede `RUN`/`COPY`/`ADD` eine **neue Schicht** als Diff zum Vorzustand erzeugt und wo möglich der **Cache** greift. Am Ende werden **Config** (Startbefehl, Umgebung, Benutzer, Ports) und **Manifest** geschrieben, das Ergebnis bekommt seinen **Digest**, und der Tag wird darauf gesetzt.

Die Rolle des Dockerfiles ist dabei die entscheidende: Es macht die Umgebung zu **Code** — versioniert, reviewbar, wiederholbar, im selben Repository wie die Anwendung. Das ist der Unterschied zu einem Server, den jemand von Hand eingerichtet hat (dem Snowflake aus Stichwort 1), und derselbe Gedanke wie bei Alembic-Migrationen: Was den Zustand des Systems bestimmt, gehört in die Versionskontrolle.

> [!question] Was ist ein Multi-Stage Docker Build und warum sollte ich ihn in vielen Fällen nutzen?

Ein Build mit **mehreren `FROM`-Anweisungen** in einer Datei. Jede beginnt eine neue **Stage** mit eigenem Dateisystem; mit `COPY --from=<stage>` überträgt man gezielt einzelne Artefakte, und **nur die letzte Stage wird zum ausgelieferten Image**.

Der Grund ist, dass **Bauen und Laufen verschiedene Abhängigkeiten haben**: Compiler, Paketmanager, Header und Caches braucht man zum Installieren, zur Laufzeit nie. In einem einstufigen Build bleibt all das im Image — und wegen des Whiteout-Problems (gelöschte Dateien existieren in unteren Schichten weiter) lässt es sich auch nicht nachträglich entfernen.

Multi-Stage löst das strukturell und bringt dabei: **kleinere Images** (oft Faktor 2–5), **kleinere Angriffsfläche**, **keine Secret- oder Quellcode-Reste** aus der Bauphase, **schnellere Deployments**, **parallel gebaute Stages** und die Möglichkeit, mit `--target` mehrere Ziele (z. B. eine Test-Stage) aus derselben Datei zu bauen.

# Docker Volumes und Datenpersistenz

## 1. Der Widerspruch, der dieses Stichwort nötig macht

Stichwort 1 endete mit einem Loblied auf die **Wegwerfbarkeit**: Container sind Vieh, nicht Haustiere; kaputt heißt neu, nicht reparieren. Und jetzt sollen ausgerechnet Datenbanken darin laufen — also das Einzige in der ganzen Anwendung, was man **nicht** wegwerfen darf.

Das ist derselbe Satz wie in [[1.6 Datenbank Migrations Tools - Vertiefung|1.6]], nur eine Ebene tiefer:

> [!important] Code ist ersetzbar, Daten sind es nicht
> Docker **löst** das Zustandsproblem nicht — es **lokalisiert** es. Der Gewinn ist nicht, dass Zustand verschwindet, sondern dass er an genau einer benannten, sichtbaren Stelle liegt statt überall verstreut.
>
> Ein Container ohne Volume ist vollständig wegwerfbar. Ein Container mit Volume ist wegwerfbar **bis auf einen Pfad**, den man explizit hingeschrieben hat. Das ist der ganze Trick.

## 2. Warum die Container-Schicht nicht nur flüchtig, sondern auch langsam ist

Aus Stichwort 3 kennst du die beschreibbare Schicht. Ihr zweiter Nachteil wird meist übersehen und ist bei Datenbanken sogar der wichtigere.

OverlayFS arbeitet nach dem Prinzip **Copy-on-Write**: Solange eine Datei nur gelesen wird, kommt sie aus der unteren, schreibgeschützten Schicht. Beim **ersten Schreibzugriff** muss sie in die obere Schicht kopiert werden — und zwar **vollständig**, nicht nur der geänderte Block.

```
   Container will 4 KB in einer 2 GB großen Datei ändern
        │
        ├─ Datei liegt in einer Image-Schicht (read-only)
        ├─ OverlayFS: copy_up  →  2 GB werden kopiert
        └─ danach erst: 4 KB schreiben
```

Für eine Datenbank, die ständig in große Dateien schreibt, ist das die denkbar schlechteste Zugriffsart. Dazu kommt der generelle Aufwand: Jeder Dateizugriff geht durch die Union-Schicht, die erst herausfinden muss, in welcher Ebene die Datei liegt.

> [!tip] Der doppelte Grund für Volumes
> **Persistenz** ist der bekannte Grund. **Performance** ist der zweite: Ein Volume ist ein normales Verzeichnis des Host-Dateisystems, das per Bind-Mount in den Container gehängt wird. Es **umgeht OverlayFS vollständig** — Schreibzugriffe gehen direkt und ohne Copy-on-Write auf die Platte.
>
> Deshalb steht in der Dokumentation praktisch jedes Datenbank-Images: „Benutze ein Volume." Nicht nur, damit die Daten überleben, sondern damit die Datenbank überhaupt brauchbar schnell ist.

## 3. Die drei Mount-Arten im Detail

### Named Volumes

```yaml
services:
  db:
    volumes:
      - pricing_data:/var/lib/postgresql       # Kurzform
volumes:
  pricing_data:                                 # Deklaration (leer = Standardtreiber)
```

Ein Named Volume ist ein **von Docker verwaltetes Verzeichnis**, physisch unter `/var/lib/docker/volumes/<name>/_data`. Der Punkt daran: **Du sollst diesen Pfad nicht kennen müssen.** Das Volume ist ein *Objekt mit Namen*, und wo es liegt, ist eine Implementierungsfrage — die sich bei anderen Treibern ändert.

Denn `local` ist nur der Standardtreiber. Über `driver_opts` kann derselbe Name auch auf ganz anderes zeigen:

```yaml
volumes:
  shared:
    driver: local
    driver_opts:
      type: nfs
      o: addr=10.0.0.5,rw
      device: ":/export/daten"
```

Für dich nicht relevant, aber es erklärt, warum die Abstraktion existiert: Der Container weiß nie, *was* an seinem Pfad hängt.

### Bind Mounts

```yaml
    volumes:
      - ./src:/app/src:ro          # relativ zur Compose-Datei, read-only
      - /abs/pfad:/daten
```

Ein konkreter Host-Pfad, direkt in den Container gehängt. Kein Docker-Objekt, keine Verwaltung, keine Portabilität — dafür siehst und bearbeitest du die Dateien mit deinen normalen Werkzeugen.

Der Haupteinsatz ist **Entwicklung**: Quellcode einhängen, im Editor ändern, `uvicorn --reload` startet neu — ohne Image-Neubau. Der zweite ist **Nur-Lese-Zugriff auf Eingabedaten**, wofür `:ro` genau richtig ist.

> [!warning] `-v` legt fehlende Pfade stillschweigend an
> Bei `docker run -v /pfad/den/es/nicht/gibt:/daten` erzeugt Docker das Host-Verzeichnis — **leer und root gehörend**. Statt eines Fehlers bekommst du einen Container, der ins Nichts schaut. Klassisch bei Tippfehlern im Pfad.
>
> Die ausführliche Syntax scheitert stattdessen sauber:
> ```bash
> docker run --mount type=bind,source=/pfad,target=/daten,readonly …
> ```
> `--mount` ist wortreicher, aber explizit und ohne Sonderregeln. In Compose entspricht das der *long syntax* mit `type:`, `source:`, `target:`.

### tmpfs

```yaml
    tmpfs:
      - /tmp
```

Nur im Arbeitsspeicher, verschwindet mit dem Container, landet nie auf einer Platte. Für Secrets, Scratch-Dateien und Caches, die ohnehin flüchtig sind.

## 4. Die Mount-Semantik: wer gewinnt?

Das ist die Regel, an der die meisten Überraschungen hängen — inklusive deiner aus 1.6.

Was passiert, wenn im Image an der Zielstelle bereits Dateien liegen?

| Situation | Ergebnis |
|---|---|
| **Named Volume, leer**, Ziel hat Inhalt im Image | Docker **kopiert den Image-Inhalt ins Volume** (einmalig, beim Erzeugen) |
| **Named Volume, gefüllt** | Das **Volume gewinnt** — der Image-Inhalt bleibt unsichtbar |
| **Bind Mount** (egal ob leer oder voll) | Der **Host-Pfad gewinnt immer**, es wird **nie** vorbefüllt |

> [!important] Die Konsequenz in einem Satz
> Ein Named Volume wird **genau einmal** aus dem Image befüllt — beim allerersten Mal. Danach ist es die Quelle der Wahrheit, und Änderungen im Image erreichen es nie mehr.

Damit ist dein Erlebnis aus 1.6 vollständig erklärt: Verzeichniswechsel → neuer Compose-Projektname → **neues, leeres** Volume → einmalige Erstbefüllung aus dem Image → eine frisch initialisierte, leere Datenbank. Kein Fehler, sondern exakt das dokumentierte Verhalten.

### Der Verschachtelungstrick

Aus derselben Regel folgt ein Muster, dem du in fremden Compose-Dateien ständig begegnen wirst:

```yaml
    volumes:
      - ./:/app                 # Quellcode vom Host
      - /app/.venv              # anonymes Volume — überdeckt den Bind Mount an dieser Stelle
```

Die zweite Zeile schützt ein Unterverzeichnis davor, vom Bind Mount überdeckt zu werden. In der JavaScript-Welt ist das `node_modules`, bei uns wäre es `.venv`: Das Image enthält eine im Container installierte Umgebung, der Host eine für sein eigenes System gebaute. Ohne die zweite Zeile würde die Host-`.venv` die des Containers überdecken — mit Bibliotheken, die für den Host kompiliert wurden. Der spezifischere (längere) Pfad gewinnt.

## 5. Das häufigste Praxisproblem: Rechte

Wenn du in diesem Kapitel an einer Stelle hängen bleibst, dann hier.

Im Container gibt es **keine Übersetzung von Benutzern**. Der Kernel kennt nur **numerische UIDs/GIDs**, und die sind auf Host und Container dieselben Zahlen — auch wenn sie unterschiedliche Namen tragen.

```
Host:      nick        = UID 1000
Container: appuser     = UID 1000     → dieselben Dateirechte!
Container: root        = UID 0        → schreibt Dateien, die dir auf dem Host gehören... niemandem
```

Daraus die beiden klassischen Symptome:

**1. „Permission denied" im Container.** Der Prozess läuft als UID 1000, die eingehängten Dateien gehören UID 0 (oder umgekehrt). Bei Bind Mounts gelten schlicht die Host-Rechte.

**2. Dateien, die du auf dem Host nicht löschen kannst.** Ein Container, der als root schreibt, erzeugt root-Dateien in deinem Projektverzeichnis. Danach hilft nur `sudo rm`.

Die Gegenmittel, in der Reihenfolge ihrer Nützlichkeit:

```dockerfile
COPY --chown=1000:1000 src/ ./src/     # beim Kopieren gleich richtig setzen
USER 1000:1000                          # nicht als root laufen
```

```bash
docker run -u "$(id -u):$(id -g)" …    # zur Laufzeit die eigene UID durchreichen
```

> [!important] Benutzer sind **Zahlen** — Namen sind nur ein Nachschlagewerk
> Der Kernel speichert bei jeder Datei zwei Integer (UID, GID) und vergleicht sie mit denen des Prozesses. Ein **Name kommt darin nirgends vor**: `nick`, `root`, `postgres` sind Zeilen in `/etc/passwd` und `/etc/group`, rein für Menschen.
>
> Daraus folgt: **`USER 1000:1000` funktioniert auch ohne passenden Eintrag im Image.** Nur Komfortfunktionen brechen dann — `whoami` und `id -un` scheitern, `$HOME` ist leer, `ls -l` zeigt `1000` statt eines Namens, und Programme mit `getpwuid()` können abbrechen. Sauberer ist deshalb:
> ```dockerfile
> RUN groupadd --gid 1000 app \
>  && useradd --uid 1000 --gid 1000 --no-create-home app
> ```
>
> **Wie der Wechsel technisch abläuft:** `USER` landet als String in der **Image-Config** (`docker inspect --format '{{.Config.User}}'`). Beim Start ruft `runc` vor dem `execve()` schlicht `setgid(1000); setuid(1000)` auf — das setzt ein Zahlenfeld im Prozess-Eintrag des Kernels. **Nichts wird nachgeschlagen, nichts automatisch gewählt.** Nachprüfbar mit einer Zahl, die in keinem Image existiert:
> ```bash
> docker run --rm -u 4711:4711 python:3.13-slim id    # → uid=4711 gid=4711
> docker run --rm -u gibtsnicht python:3.13-slim id   # → Error: unable to find user
> ```
> Die Übersetzung ist **nur bei Namen** nötig: Dann liest Docker `/etc/passwd` **im Image**, um den Namen in eine Zahl aufzulösen — und scheitert, wenn der Eintrag fehlt.
>
> **Warum ausgerechnet 1000?** Konvention der Distributionen: UID `0` = root, `1–999` = Systemkonten für Dienste, **ab `1000`** = menschliche Benutzer. Der erste Benutzer einer Debian-Installation — also du selbst — hat deshalb UID 1000 (`id` zeigt es). Genau darum nimmt man sie auch im Image: Bei einem Bind Mount passen die Zahlen dann zusammen, und Rechteprobleme entstehen gar nicht erst.
>
> **`--chown` gehört ans `COPY`, nicht in ein eigenes `RUN`:**
> ```dockerfile
> COPY --from=builder --chown=1000:1000 /app/.venv /app/.venv   # ✅ eine Schicht
> COPY --from=builder /app/.venv /app/.venv                     # ❌ und dann
> RUN chown -R 1000:1000 /app/.venv                             #    ~150 MB doppelt
> ```
> `chown` ändert die Metadaten **jeder einzelnen Datei** — und eine geänderte Datei landet vollständig in der neuen Schicht. Ein rekursives `chown` über ein großes Verzeichnis verdoppelt dessen Platzbedarf im Image, ohne dass sich ein Byte Inhalt ändert.
>
> **`USER` gilt für alles danach** — jedes `RUN`, den `HEALTHCHECK`, `CMD` und `ENTRYPOINT`. Es gehört deshalb ans **Ende** der Runtime-Stage.

> [!note] Wie das offizielle Postgres-Image es löst
> Der Entrypoint startet zunächst als root, korrigiert die Eigentümerrechte des Datenverzeichnisses und wechselt dann per `gosu` auf den `postgres`-Benutzer, bevor der eigentliche Serverprozess startet. Deshalb funktioniert `postgres:18` mit einem frischen Volume ohne Zutun — und deshalb ist es lehrreich, sich dessen `docker-entrypoint.sh` einmal anzusehen.
>
> Bei **Named Volumes** ist das Problem ohnehin kleiner: Beim ersten Anlegen übernimmt Docker die Rechte des Zielverzeichnisses aus dem Image. Bei **Bind Mounts** gibt es diese Hilfe nicht — dort musst du es selbst regeln.

## 6. Sichern, Wiederherstellen, Umziehen

> [!danger] Es gibt kein `docker volume backup`
> Docker bietet **keinen** eingebauten Sicherungsmechanismus. Ein Volume ist ein Verzeichnis; sichern musst du es selbst. Wer das nicht weiß, hat kein Backup — und merkt es beim ersten `docker volume prune`.

### Das allgemeine Muster

Ein temporärer Container hängt das Volume **und** ein Host-Verzeichnis ein und packt das eine ins andere:

```bash
# Sichern
docker run --rm \
  -v pricing_data:/quelle:ro \
  -v "$(pwd)":/backup \
  alpine tar czf /backup/pricing_data.tar.gz -C /quelle .

# Zurückspielen (in ein leeres Volume!)
docker run --rm \
  -v pricing_data:/ziel \
  -v "$(pwd)":/backup \
  alpine tar xzf /backup/pricing_data.tar.gz -C /ziel
```

Das Muster ist allgemein nützlich: **Ein Wegwerf-Container ist das Werkzeug, mit dem man an Volumes herankommt**, ohne etwas auf dem Host installieren zu müssen.

### Bei Datenbanken aber bitte anders

> [!warning] Ein Dateikopie einer **laufenden** Datenbank ist unbrauchbar
> PostgreSQL hält Daten im Arbeitsspeicher, schreibt asynchron und führt ein Write-Ahead-Log. Ein `tar` über das laufende Datenverzeichnis erwischt einen Zwischenzustand — die Sicherung sieht vollständig aus und ist es nicht. Man merkt es erst beim Wiederherstellen.
>
> Für Datenbanken gilt: **das Werkzeug der Datenbank benutzen**, nicht das des Dateisystems.

```bash
docker compose exec -T db pg_dump -U pricing pricing > backup.sql
docker compose exec -T db psql -U pricing -d pricing < backup.sql
```

Das `-T` schaltet die TTY-Zuweisung ab — nötig, sobald umgeleitet wird (der `-i`-ohne-`-t`-Fall aus Stichwort 4).

Das Volume-`tar` ist trotzdem nicht wertlos: Es ist der richtige Weg, wenn die Datenbank **gestoppt** ist, und der einzige Weg für Volumes, die keine Datenbank enthalten.

## 7. Wo Zustand *nicht* hingehört

Ein Volume ist die Antwort auf „diese Daten müssen überleben" — aber nicht auf jede Art von Zustand. Die Abgrenzung gehört dazu:

| Art von Daten | Gehört ins Volume? | Stattdessen |
|---|---|---|
| Datenbank-Datenverzeichnis | ✅ ja | — |
| Hochgeladene Dateien (klein, Einzelhost) | ✅ ja | in der Cloud: Objektspeicher (S3) |
| **Logs** | ❌ nein | **nach stdout**, der Daemon sammelt sie ein |
| Konfiguration, Secrets | ❌ nein | Umgebungsvariablen, Secret-Mechanismen |
| Caches, Temporäres | ❌ nein | `tmpfs` oder einfach die Container-Schicht |
| Quellcode (in Produktion) | ❌ nein | **ins Image**, es gehört zum Artefakt |

> [!important] Die Grenze, die man kennen muss
> **Ein Volume ist ein Einzelhost-Konzept.** Es liegt auf *dieser* Maschine. Sobald die Anwendung auf mehreren Knoten läuft, greift das Modell nicht mehr — dann braucht es Netzwerkspeicher, in Kubernetes `PersistentVolumes`, oder in der Cloud einen verwalteten Datenbankdienst.
>
> Und die ehrliche Einordnung: **In Produktion betreibt man Datenbanken häufig gar nicht selbst in Containern**, sondern nimmt einen verwalteten Dienst (RDS, Cloud SQL) — Backups, Failover und Updates sind schwierig genug, dass man sie ungern selbst macht. In der **Entwicklung** ist die Datenbank im Container dagegen ideal: exakt reproduzierbar, in Sekunden neu, ohne das System zu verschmutzen. Genau der Fall, in dem du dich befindest.

## 8. Die Kontrollfrage: Wie funktioniert Datenpersistenz in Docker?

> [!question] Wie funktioniert die Datenpersistenz in Docker? Erkläre Volumes.

Ein Container schreibt standardmäßig in seine **dünne beschreibbare Schicht**, die Teil des Containers ist und mit `docker rm` verschwindet. Persistenz entsteht dadurch, dass man **einzelne Pfade aus dieser Schicht heraushebt** und stattdessen auf Speicher außerhalb des Containers zeigen lässt — dafür gibt es drei Mechanismen: **Named Volumes**, **Bind Mounts** und **tmpfs**.

Ein **Volume** ist ein von Docker verwaltetes, **eigenständiges Objekt** mit eigenem Namen und eigenem Lebenszyklus. Es wird an einen Pfad im Container gehängt, umgeht dabei das Union-Dateisystem vollständig (was neben der Persistenz auch **deutlich bessere Schreibleistung** bedeutet) und **überlebt seinen Container** — `docker rm` löscht es nicht, dafür braucht es `docker rm -v`, `docker compose down -v` oder `docker volume prune`.

Beim Einhängen gilt: Ein **leeres** Volume wird **einmalig** aus dem Image-Inhalt des Zielverzeichnisses vorbefüllt; ein **gefülltes** Volume gewinnt immer gegen das Image. Ein **Bind Mount** überdeckt das Ziel dagegen immer und wird nie vorbefüllt.

Der konzeptionelle Kern: Docker macht Anwendungen nicht zustandslos, sondern **zwingt dazu, jeden Zustand explizit zu benennen**. Alles, was nicht in einem Volume steht, ist per Definition wegwerfbar — und das ist die eigentliche Eigenschaft, aus der Reproduzierbarkeit entsteht.

## 9. Für dein Projekt

Was daraus konkret folgt:

1. **`pricing_data` ist deine einzige unersetzliche Sache.** Der Rest deines Setups — Images, Container, Netzwerk — ist in Sekunden neu erzeugbar. Behandle die eine Zeile in der Compose-Datei entsprechend.
2. **`docker compose down` ist harmlos, `-v` nicht.** Gewöhn dir an, `-v` nur zu tippen, wenn du wirklich eine leere Datenbank willst (etwa um zu prüfen, ob deine Migrationen von Null durchlaufen — was ein guter Test ist).
3. **Die API braucht kein Volume.** Sie hält keinen Zustand; ihr Code gehört ins Image. Wenn du versucht bist, ihr eins zu geben, ist das ein Hinweis auf ein Designproblem.
4. **Logs nach stdout, nicht ins Volume.** Dein `logs/`-Verzeichnis aus 1.4 sollte im Container nicht entstehen — sonst siehst du in `docker logs` nichts und sammelst Dateien in einer Schicht, die keiner sichert.
5. **`daily_data/` ist ein Kandidat für `:ro`.** Wenn der Ingest CSVs vom Host liest, ist ein Read-only-Bind-Mount die passende Form: Der Container braucht Lesezugriff und soll nichts verändern können.
6. **Ein Backup-Befehl gehört in deine Doku.** `pg_dump` über `docker compose exec -T` ist eine Zeile — und der Unterschied zwischen „ich habe Daten" und „ich hatte Daten".
7. **Trennung im Kopf behalten:** Ein Image-Neubau ändert **nichts** an den Daten. Eine Alembic-Migration ändert **nur** die Daten und nichts am Image. Das sind zwei getrennte Versionierungssysteme für zwei getrennte Dinge — und genau deshalb hat Kapitel 1.6 vor Kapitel 1.7 stattgefunden.

# Docker Compose: Multi-Container-Anwendungen

## 1. Das Problem: die Befehlsschlange

Alles, was du bis hierher gelernt hast, lässt sich mit der CLI erledigen. Dein aktuelles Setup — Datenbank, Adminer, dazu bald die API — sähe ohne Compose so aus:

```bash
docker network create pricing-net
docker volume create pricing_data

docker run -d --name pricing-db --network pricing-net \
  -e POSTGRES_DB=pricing -e POSTGRES_USER=pricing -e POSTGRES_PASSWORD=pricing \
  -v pricing_data:/var/lib/postgresql -p 127.0.0.1:5432:5432 \
  --health-cmd 'pg_isready -U pricing -d pricing' --health-interval 5s \
  postgres:18

# warten, bis die DB bereit ist … irgendwie

docker run -d --name pricing-adminer --network pricing-net \
  -e ADMINER_DEFAULT_SERVER=db -p 127.0.0.1:8080:8080 adminer

docker build -t pricing-api:latest .
docker run -d --name pricing-api --network pricing-net \
  -e DB_HOST=db -e DB_PRICING_PW=pricing \
  -p 127.0.0.1:8000:8000 pricing-api:latest
```

Das funktioniert — und ist trotzdem unbrauchbar. Es ist **Prosa in Befehlsform**: nirgends versioniert, in der Reihenfolge fehleranfällig, beim zweiten Mal anders getippt, und für einen Kollegen bestenfalls als Copy-Paste-Block in einer README weiterzugeben.

Genau diese Kritik kennst du aus Stichwort 1, wo sie gegen Setup-Skripte für Server ging. Die Antwort ist hier dieselbe wie dort: **von imperativ zu deklarativ**.

> [!important] Die Symmetrie, die man einmal gesehen haben muss
>
> | | **Bauzeit** | **Laufzeit** |
> |---|---|---|
> | **Imperativ** | eine Kette von Befehlen | eine Kette von `docker run` |
> | **Deklarativ, im Repo** | **Dockerfile** | **`compose.yaml`** |
>
> Das Dockerfile beschreibt, *woraus ein Image besteht*. Die Compose-Datei beschreibt, *woraus eine Anwendung besteht* — welche Dienste, welche Netze, welche Volumes, welche Abhängigkeiten. Beides ist Text, liegt in git und durchläuft Code Review.

## 2. Anatomie einer `compose.yaml`

```yaml
name: pricing                      # Projektname — überschreibt den Verzeichnisnamen

services:                          # die Container
  db:
    image: postgres:18
    environment: …
    volumes: …
    healthcheck: …

  api:
    build:                         # dieser Dienst wird GEBAUT statt gezogen
      context: .
      dockerfile: Dockerfile
    depends_on:
      db:
        condition: service_healthy
    ports: ["127.0.0.1:8000:8000"]

volumes:                           # benannte Volumes deklarieren
  pricing_data:

networks:                          # optional — ohne Angabe legt Compose eines an
  default:
```

> [!note] `version:` ist tot
> Ältere Tutorials beginnen mit `version: "3.8"`. Das ist seit der Compose-Spezifikation **obsolet**; Compose V2 gibt dafür eine Warnung aus. Wenn du es in einem Beispiel siehst, ist der Artikel alt — was oft auch für den Rest seines Inhalts gilt.

Die Dienst-Schlüssel, die im Alltag zählen:

| Schlüssel | Zweck |
|---|---|
| `image` / `build` | fertiges Image ziehen **oder** selbst bauen |
| `command` / `entrypoint` | `CMD`/`ENTRYPOINT` des Images überschreiben |
| `environment` / `env_file` | Umgebungsvariablen (siehe nächster Abschnitt) |
| `ports` / `expose` | veröffentlichen / nur dokumentieren |
| `volumes` | Mounts, Kurz- oder Langform |
| `depends_on` | Startreihenfolge und -bedingung |
| `healthcheck` | Bereitschaftsprüfung |
| `restart` | `no` \| `on-failure` \| `always` \| `unless-stopped` |
| `user`, `working_dir` | wie die gleichnamigen Dockerfile-Direktiven |
| `profiles` | Dienst nur in bestimmten Szenarien starten |

## 3. `build` — der Dienst, der aus deinem Code entsteht

```yaml
  api:
    build:
      context: .                   # Build-Kontext (Stichwort 5!)
      dockerfile: Dockerfile
      target: runtime              # Multi-Stage: bis zu dieser Stage bauen
      args:
        PYTHON_VERSION: "3.13"
    image: pricing-api:latest      # Name für das ERGEBNIS des Builds
```

Hier verbinden sich die beiden letzten Stichworte: `context` ist genau der Build-Kontext aus Stichwort 5, `target` die Multi-Stage-Auswahl. Steht `image` zusammen mit `build`, ist es der Tag, unter dem das gebaute Image abgelegt wird.

**Wichtig für den Alltag:** `docker compose up` baut **nur, wenn das Image noch nicht existiert**. Nach einer Code-Änderung brauchst du `--build`:

```bash
docker compose up -d --build
```

Das ist die häufigste Ursache für „meine Änderung wirkt nicht".

## 4. Die drei Ebenen von Umgebungsvariablen

Das wird ständig verwechselt und kostet regelmäßig eine Stunde. Es gibt **drei verschiedene Dinge**, die alle nach „env" aussehen:

| Mechanismus | Wirkt auf | Beispiel |
|---|---|---|
| **`.env` im Projektverzeichnis** | die **Compose-Datei selbst** — Substitution von `${VAR}` | `POSTGRES_VERSION=18` → `image: postgres:${POSTGRES_VERSION}` |
| **`env_file:`** im Dienst | **den Container** — alle Variablen der Datei | `env_file: [.env]` |
| **`environment:`** im Dienst | **den Container** — einzeln benannt | `environment: {DB_HOST: "db"}` |

> [!warning] Die Falle
> Die Datei `.env` wird **automatisch** für die Variablensubstitution *in der Compose-Datei* gelesen — aber ihre Variablen landen deswegen **nicht** im Container. Wer erwartet, dass `DB_PRICING_PW` aus `.env` einfach in der Anwendung ankommt, sucht lange.
>
> Wenn die Variablen *auch* in den Container sollen, muss man `env_file: [.env]` explizit hinschreiben.

Reihenfolge bei Konflikten (später gewinnt): `environment:` schlägt `env_file:` schlägt `ENV` aus dem Dockerfile.

Und der Befehl, der jede Diskussion beendet:

```bash
docker compose config          # zeigt die vollständig aufgelöste Konfiguration
```

Für dein Projekt zahlt sich hier eine frühere Entscheidung aus: `pydantic-settings` liest Konfiguration aus Umgebungsvariablen. Das ist exakt der Weg, den Container erwarten — deine Anwendung ist konfigurationsseitig schon container-tauglich, ohne dass du dafür etwas ändern musst.

## 5. Startreihenfolge: `depends_on`, `healthcheck`, `condition`

Das wichtigste Detail dieses Stichworts für deine Aufgabe.

### `depends_on` allein reicht nicht

```yaml
  api:
    depends_on:
      - db          # ⚠️ wartet nur, bis der db-CONTAINER GESTARTET ist
```

Das garantiert die **Reihenfolge**, nicht die **Bereitschaft**. Der Daemon meldet „gestartet", sobald der Prozess läuft — PostgreSQL braucht danach aber noch Sekunden, bis es Verbindungen annimmt. Deine API startet in diese Lücke hinein und stirbt mit `connection refused`.

### Die Lösung: Healthcheck plus Bedingung

```yaml
  db:
    image: postgres:18
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U pricing -d pricing"]
      interval: 5s
      timeout: 5s
      retries: 5
      start_period: 10s        # Karenzzeit: Fehlschläge zählen hier noch nicht

  api:
    depends_on:
      db:
        condition: service_healthy    # ← wartet auf HEALTHY, nicht auf STARTED
```

Deinen `healthcheck` hast du schon — was gefehlt hat, war die `condition`, die ihn überhaupt erst benutzt. Ohne sie ist ein Healthcheck reine Anzeige in `docker ps`.

Die drei Bedingungen:

| `condition` | Bedeutet |
|---|---|
| `service_started` | Container läuft (Default, schwach) |
| `service_healthy` | **Healthcheck meldet gesund** |
| `service_completed_successfully` | Container ist **mit Exit-Code 0 beendet** |

`start_period` wird oft vergessen und ist wichtig: In dieser Zeit zählen fehlgeschlagene Prüfungen **nicht** gegen `retries`. Ohne sie gilt ein Dienst, der 30 Sekunden zum Hochfahren braucht, vorschnell als ungesund.

> [!important] `depends_on` gilt nur beim Start
> Wenn die Datenbank **im laufenden Betrieb** neu startet, hilft dir keine Compose-Einstellung. Die Anwendung muss Verbindungsabbrüche selbst überstehen — durch Wiederholversuche und einen Connection Pool, der tote Verbindungen erkennt.
>
> SQLAlchemy bringt dafür `pool_pre_ping=True` mit. Compose löst das Startproblem; die Robustheit im Betrieb bleibt Aufgabe der Anwendung.

### Das Migrationsmuster

`service_completed_successfully` ist genau für den Fall gemacht, den du brauchst: **Migrationen vor dem API-Start**. Drei Wege stehen zur Wahl:

| Ansatz | Wie | Bewertung |
|---|---|---|
| **A** — im Entrypoint der API | Ein Skript führt `alembic upgrade head` aus, dann `exec uvicorn …` | Einfach; aber bei mehreren API-Instanzen migrieren alle gleichzeitig |
| **B** — eigener Einmal-Dienst | Ein Dienst `migrate`, der nur `alembic upgrade head` ausführt und endet; die API wartet per `service_completed_successfully` | **Sauber und explizit**; ein Dienst mehr in der Datei |
| **C** — manuell | `docker compose run --rm api alembic upgrade head` | Explizit, aber **verletzt die Aufgabenstellung** („ein einziger Befehl") |

Die Aufgabe verlangt, dass **ein** `docker compose`-Befehl die gesamte Anwendung inklusive Datenbank hochfährt. Damit fällt C aus, und zwischen A und B entscheidest du — mit dem Hinweis, dass B das Muster ist, das man in echten Projekten häufiger sieht, weil es Migration und Anwendungsstart sauber trennt.

## 5b. Volume oder Bind Mount? Das erste Zeichen entscheidet

In der **Kurzform** unterscheidet Docker die Mount-Arten rein textuell an der linken Seite:

```yaml
    volumes:
      - pricing_data:/var/lib/postgresql     # Named Volume
      - ./daily_data:/app/daily_data:ro      # Bind Mount
      - /abs/pfad:/app/daten                 # Bind Mount
      - /app/.venv                           # anonymes Volume

volumes:                                      # ← Deklaration nur fuer NAMED Volumes
  pricing_data:
```

| Linke Seite beginnt mit | Interpretation | Ergebnis |
|---|---|---|
| `.` oder `/` | ein **Pfad** | **Bind Mount** |
| irgendetwas anderes | ein **Name** | **Named Volume** |
| *(nur ein Pfad, kein Doppelpunkt)* | nur ein Ziel | **anonymes Volume** |

`pricing_data:/var/lib/postgresql` und `./pricing_data:/var/lib/postgresql` unterscheiden sich um zwei Zeichen und bedeuten etwas völlig anderes. Fehlt die Deklaration unter dem Top-Level-`volumes:`, bricht Compose ab (`refers to undefined volume`) — Bind Mounts gehören dort **nicht** hin, sie sind keine Docker-Objekte.

Die **Langform** macht den Typ explizit:

```yaml
    volumes:
      - type: volume
        source: pricing_data
        target: /var/lib/postgresql
      - type: bind
        source: ./daily_data
        target: /app/daily_data
        read_only: true
      - type: tmpfs
        target: /tmp
```

Der Grund, sie zu benutzen, ist derselbe wie bei `--mount` gegenüber `-v`: Ein **Tippfehler im Host-Pfad** wird in der Kurzform als *anderer* Bind Mount interpretiert, und Docker legt das Verzeichnis stillschweigend an — leer und root gehörend. Der Container schaut dann ins Nichts, ohne dass etwas nach einem Fehler aussieht.

Was tatsächlich gemountet ist, verrät:

```bash
docker inspect <container> --format '{{range .Mounts}}{{.Type}}  {{.Source}} -> {{.Destination}}{{"\n"}}{{end}}'
```

Erste Spalte `volume` oder `bind`. Bei einem Named Volume steht als `Source` ein Pfad unter `/var/lib/docker/volumes/…`, bei einem Bind Mount der echte Projektpfad. (`docker volume ls` zeigt Bind Mounts gar nicht — sie sind keine Objekte.)

### Der Top-Level-`volumes:`-Block

Er ist die **Deklaration** — dieselbe Rolle, die `services:` für Dienste hat. Compose braucht ihn, weil es Named Volumes **verwaltet**: anlegen beim `up`, Projekt-Präfix davor, entfernen bei `down -v`.

```yaml
volumes:
  pricing_data:            # leerer Wert = alle Defaults (Treiber local)
```

Was dort sonst noch stehen kann:

| Option | Wirkung |
|---|---|
| `name: exakter-name` | überschreibt den generierten Namen (kein Projekt-Präfix) |
| `driver` / `driver_opts` | anderer Treiber, z. B. NFS |
| **`external: true`** | **Compose verwaltet es nicht** — siehe unten |

`external: true` sagt: *das gehört nicht diesem Projekt.*

| | normal | `external: true` |
|---|---|---|
| Beim `up`, falls nicht vorhanden | wird **angelegt** | **Fehler** (`external volume not found`) |
| Namensgebung | mit Projekt-Präfix | **exakt der angegebene Name** |
| Bei `down -v` | wird **gelöscht** | bleibt **unangetastet** |

Typische Gründe: ein Volume, das **zwei Projekte teilen**; **Produktionsdaten vor einem versehentlichen `down -v` schützen** (der häufigste Fall); oder ein Volume, das von außerhalb verwaltet wird (Administrator, Terraform, NFS).

> [!warning] `external` und `internal` verwechselt man leicht
> **`external: true`** gibt es bei Volumes *und* Netzwerken und regelt den **Besitz** („Compose verwaltet das nicht").
> **`internal: true`** gibt es **nur bei Netzwerken** und regelt die **Erreichbarkeit** („kein Weg nach draußen").
> Zwei völlig verschiedene Dinge mit ähnlich klingenden Namen.

## 6. Netzwerke in Compose

Das meiste passiert automatisch: Compose legt pro Projekt ein Netzwerk an, hängt alle Dienste hinein, und **der Dienstname ist der Hostname** (Stichwort 3). Zwei Dinge, die darüber hinausgehen:

**Interne Netze.** Ein Netz mit `internal: true` hat keine Verbindung nach außen. Damit kann man die Datenbank so isolieren, dass sie *nur* für die API erreichbar ist:

```yaml
networks:
  frontend:
  backend:
    internal: true
```

Die API hängt in beiden, die Datenbank nur in `backend`. Für dein Projekt Kür, aber es zeigt, dass Compose mehr als eine flache Ebene kann.

**Aliase.** `networks: {default: {aliases: [database]}}` gibt einem Dienst zusätzliche DNS-Namen — nützlich, wenn ein fester Hostname aus einer Konfiguration nicht änderbar ist.

## 7. Profile: ein File, mehrere Szenarien

```yaml
  adminer:
    image: adminer
    profiles: ["dev", "tools"]
```

Dienste mit `profiles` starten **nur**, wenn das Profil aktiv ist:

```bash
docker compose up -d                        # ohne adminer
docker compose --profile dev up -d          # mit adminer
```

Das ist für dein Setup direkt anwendbar: **Adminer ist ein Entwicklungswerkzeug** und hat in einer Produktionsumgebung nichts verloren (eine ungeschützte Datenbank-Oberfläche auf Port 8080). Mit einem Profil bleibt es in derselben Datei, startet aber nur, wenn du es willst.

## 8. Overrides: Entwicklung und Produktion aus einer Basis

Compose liest automatisch **zwei** Dateien, falls vorhanden: `compose.yaml` und `compose.override.yaml`. Die zweite überschreibt und ergänzt die erste.

```
compose.yaml            → die Basis: gilt überall
compose.override.yaml   → lokale Entwicklung (Bind Mounts, --reload, Debug-Ports)
compose.prod.yaml       → Produktion, explizit angegeben
```

```bash
docker compose up -d                                     # Basis + override
docker compose -f compose.yaml -f compose.prod.yaml up   # Basis + prod
```

Der typische Inhalt der Override-Datei ist genau das, was in Produktion falsch wäre: Quellcode als Bind Mount einhängen, `command` auf `uvicorn --reload` setzen, Ports zusätzlich öffnen.

> [!tip] `docker compose watch`
> Neuere Compose-Versionen können Dateien überwachen und bei Änderungen gezielt reagieren — synchronisieren, den Dienst neu starten oder neu bauen (`develop: watch:` im Dienst). Das ist die modernere Alternative zum Bind-Mount-plus-Reload-Muster. Für dein Projekt nicht nötig, aber gut zu wissen, wenn du es in fremden Dateien siehst.

## 9. Die Lebenszyklus-Befehle und was sie wirklich tun

| Befehl | Container | Netzwerk | Volumes | Images |
|---|---|---|---|---|
| `up -d` | erstellt/startet | erstellt | erstellt | baut nur, wenn nicht vorhanden |
| `up -d --build` | erstellt/startet | — | — | **baut immer** |
| `stop` | stoppt | bleibt | bleiben | — |
| `start` | startet vorhandene | — | — | — |
| `restart` | stoppt + startet | — | — | — |
| `down` | **entfernt** | **entfernt** | **bleiben** | bleiben |
| `down -v` | entfernt | entfernt | **entfernt!** | bleiben |
| `down --rmi all` | entfernt | entfernt | bleiben | **entfernt** |

Zwei Feinheiten:

**`up` erzeugt Container neu, wenn sich ihre Konfiguration geändert hat** — sonst startet es die vorhandenen. Das erklärt, warum eine Änderung an `environment:` sofort wirkt, eine am Code aber nicht (dafür muss das *Image* neu gebaut werden).

**`--no-deps` und `--wait`** sind die zwei Optionen, die man sich merken sollte: `docker compose up -d --no-deps api` startet nur die API neu, ohne die Datenbank anzufassen. `docker compose up --wait` kehrt erst zurück, wenn alle Dienste mit Healthcheck **gesund** sind — praktisch in CI-Skripten.

## 10. Die Kontrollfrage: Vorteile von Docker Compose

> [!question] Was sind die Vorteile der Verwendung von Docker Compose?

1. **Die gesamte Anwendungstopologie ist deklarativ und versioniert.** Welche Dienste es gibt, wie sie verbunden sind, welche Volumes und Netze existieren — das steht in einer Textdatei im Repository statt in einer Befehlshistorie oder einem README-Absatz. Genau das, was das Dockerfile für ein einzelnes Image tut, tut Compose für die Anwendung als Ganzes.
2. **Ein Befehl statt vieler.** `docker compose up` ersetzt ein Dutzend `docker run`-Aufrufe mit je fünf bis zehn Flags — reproduzierbar, in der richtigen Reihenfolge, ohne Tippfehler.
3. **Automatische Vernetzung mit DNS.** Compose legt ein eigenes Netzwerk an und macht Dienstnamen zu Hostnamen. Ohne Compose müsste man das Netzwerk selbst anlegen und daran denken, jeden Container hineinzuhängen.
4. **Abhängigkeiten und Startreihenfolge werden ausdrückbar** — inklusive „warte, bis die Datenbank *bereit* ist" und „führe die Migration aus, bevor die API startet".
5. **Isolation zwischen Projekten** über den Projektnamen: eigenes Netz, eigene Volume-Namen, eigene Container. Mehrere Projekte laufen konfliktfrei nebeneinander.
6. **Ein Modell für mehrere Umgebungen** — über Overrides und Profile lassen sich Entwicklung, CI und Produktion aus einer gemeinsamen Basis ableiten, statt drei Dateien parallel zu pflegen.
7. **Onboarding und CI werden trivial.** Ein Klon des Repositories und ein Befehl — das ist der belastbare Test dafür, ob eine Anwendung wirklich vollständig beschrieben ist.

Der Punkt, den ich für den wichtigsten halte, ist der erste: Compose macht aus der Frage *„wie läuft dieses System eigentlich?"* etwas, das man **lesen** kann, statt es zu rekonstruieren.

## 11. Die Grenzen

Damit die Einordnung ehrlich bleibt:

- **Compose ist ein Einzelhost-Werkzeug.** Es verteilt nichts über mehrere Server, hat kein Scheduling und keine Ausfallsicherheit. Dafür gibt es Swarm oder Kubernetes — im Leitfaden ausdrücklich *out of scope*, aber das ist die Richtung, in der es weitergeht.
- **Kein Rolling Update.** `up` stoppt und ersetzt Container; eine kurze Unterbrechung gehört dazu.
- **Kein Secret-Management.** `secrets:` in Compose ohne Swarm sind schlicht Dateien im Dateisystem.
- **Trotzdem produktionstauglich** — für einen einzelnen Server mit überschaubarer Last ist Compose eine völlig legitime Betriebsform, und viele kleinere Systeme laufen genau so. Der Sprung zu Kubernetes lohnt erst, wenn man mehrere Knoten oder automatische Skalierung wirklich braucht.

## 12. Für dein Projekt

Deine Datei wird von zwei auf drei bis vier Dienste wachsen. Die Entscheidungen, die dabei anstehen:

1. **Datei umbenennen?** `compose.yaml` ist heute der bevorzugte Name; `docker-compose.yml` funktioniert weiter. Deine Wahl — aber wenn, dann jetzt.
2. **`name: pricing` setzen?** Damit hängen Volume- und Containernamen nicht mehr am Verzeichnisnamen — genau das Problem aus 1.6. Ich würde dazu raten.
3. **Migrationen: Ansatz A oder B?** Siehe Abschnitt 5. Begründe deine Wahl in der Umsetzungsdokumentation.
4. **Wo werden `DB_HOST` und `DB_PRICING_PW` gesetzt?** Über `environment:` im Dienst (explizit sichtbar) oder über `env_file:`? Beachte dabei, dass deine `Settings`-Klasse zusätzlich eine `.env` aus dem Arbeitsverzeichnis liest — welche Quelle gewinnt im Container, und ist das die, die du willst?
5. **Adminer in ein Profil?** Siehe Abschnitt 7.
6. **Braucht `db` weiterhin `ports:`?** Sobald die API im selben Netz läuft, ist die Veröffentlichung nur noch für deinen eigenen Zugriff vom Host da — behalten ist bequem, weglassen ist sauberer.
7. **Override-Datei für Entwicklung?** Erst sinnvoll, wenn die Basis läuft. Nicht am Anfang verkomplizieren.

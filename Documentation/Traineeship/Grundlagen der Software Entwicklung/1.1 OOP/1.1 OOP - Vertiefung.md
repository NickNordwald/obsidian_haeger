# Objektorientierung

## Was ist ein Objekt?

Ein **Objekt** bündelt zwei Dinge, die in prozeduraler Programmierung typischerweise getrennt sind:

- **Zustand** (state) — Daten, die zum Objekt gehören (in Python: Attribute)
- **Verhalten** (behavior) — Funktionen, die auf diesen Daten arbeiten (in Python: Methoden)

Die Idee: Statt Daten (z. B. ein `dict` mit Preisinformationen) und die Funktionen, die diese Daten verarbeiten, lose nebeneinander zu haben, werden beide zu einer Einheit zusammengefasst — einem Objekt. Das Objekt "weiß", wie man mit den eigenen Daten umgeht, und ist verantwortlich dafür, seinen eigenen Zustand konsistent zu halten.

## Prozedural vs. objektorientiert — ein Vergleich

Stell dir vor, wir wollen (angelehnt an eure Übungsaufgabe) für ein Produkt eine Preisempfehlung berechnen.

**Prozedural** — Daten und Logik sind getrennt, Funktionen müssen alle relevanten Felder als Parameter durchreichen:

```python
# Prozeduraler Stil: Daten sind "dumme" Dictionaries,
# die Logik liegt komplett außerhalb.

def calculate_price_recommendation(base_price: float, demand_factor: float) -> float:
    return round(base_price * demand_factor, 2)

unit = {"id": "SKU-001", "base_price": 19.99, "demand_factor": 1.15}

recommendation = calculate_price_recommendation(
    unit["base_price"], unit["demand_factor"]
)
print(f"{unit['id']}: {recommendation}")
```

Das Problem: Nichts hindert einen daran, `unit["base_price"]` an einer anderen Stelle im Code fälschlicherweise auf einen negativen Wert zu setzen, oder die Berechnung mit falscher Parameterreihenfolge aufzurufen. Es gibt keinen "Ort", an dem die Regeln rund um eine `unit` durchgesetzt werden — die Verantwortung ist über den ganzen Code verstreut.

**Objektorientiert** — Daten und die dazugehörige Logik werden zusammengefasst:

```python
class PriceableUnit:
    """Repräsentiert ein Produkt, für das eine Preisempfehlung berechnet werden kann."""

    def __init__(self, unit_id: str, base_price: float, demand_factor: float):
        self.unit_id = unit_id
        self.base_price = base_price
        self.demand_factor = demand_factor

    def calculate_price_recommendation(self) -> float:
        return round(self.base_price * self.demand_factor, 2)


unit = PriceableUnit(unit_id="SKU-001", base_price=19.99, demand_factor=1.15)
print(f"{unit.unit_id}: {unit.calculate_price_recommendation()}")
```

Der Unterschied ist hier noch klein, aber das Prinzip trägt: `PriceableUnit` ist jetzt der einzige Ort, an dem definiert ist, was eine "Priceable Unit" ausmacht und wie sie eine Preisempfehlung berechnet. Wächst die Anwendung (mehr Regeln, mehr Feldvalidierung, mehrere Arten von "Priceable Units"), bleibt die Logik an einem Ort gebündelt statt über viele Funktionen verstreut.

## Warum ist OOP der Goldstandard?

1. **Modellierung der Realität**: Komplexe Systeme lassen sich oft natürlich als Zusammenspiel von Objekten mit eigenen Zuständigkeiten beschreiben (ein Kunde, eine Bestellung, ein Produkt …).
2. **Kapselung von Komplexität**: Ein Objekt kann seine internen Details verstecken und nach außen nur eine einfache Schnittstelle zeigen (mehr dazu in den Stichworten *Kapselung*/*Information Hiding* — folgt später).
3. **Wiederverwendbarkeit & Erweiterbarkeit**: Über Vererbung und Polymorphie (folgt später) lässt sich Verhalten wiederverwenden und punktuell anpassen, ohne bestehenden Code zu verändern.
4. **Wartbarkeit**: Wenn Zustand und Logik zusammengehören, ist Code leichter zu verstehen, zu testen und zu ändern — Änderungen an der Preislogik passieren an einer Stelle (in der Klasse), nicht an zehn verstreuten Funktionsaufrufen.
5. **Klarere Verantwortlichkeiten**: Jedes Objekt hat eine klar abgegrenzte Aufgabe (siehe später *Single Responsibility Prinzip*).

Diese Vorteile sind aber kein Selbstzweck — OOP kann auch überstrapaziert werden (unnötig tiefe Klassenhierarchien, "God Objects" etc.). Ein gesundes Maß und Verständnis der Prinzipien (die wir in diesem Kapitel noch durchgehen) ist wichtiger als OOP um jeden Preis einzusetzen.

## Python: (fast) alles ist ein Objekt

Ein zentraler Punkt, der Python von Sprachen wie Java/C++ unterscheidet: In Python ist OOP nicht nur "verfügbar", sondern die Sprache selbst ist bis in den Kern objektorientiert aufgebaut. Auch Dinge, die sich nicht wie "klassische Objekte" anfühlen, sind welche:

```python
x = 42
print(type(x))          # <class 'int'>
print(x.__class__)      # <class 'int'>
print(x.bit_length())   # int hat Methoden -> 6

def greet():
    pass

print(type(greet))      # <class 'function'> - selbst Funktionen sind Objekte!
print(greet.__name__)   # 'greet' - Attribute auf einer Funktion
```

Das ist der Grund, warum die Einleitung im Leitfaden betont: Python zwingt einen nicht zu OOP (man *kann* rein prozedural oder auch funktional programmieren), aber im Hintergrund ist ohnehin alles ein Objekt. Wichtig ist daher, die Konzepte zu verstehen, um sie *bewusst und gezielt* einzusetzen — nicht weil die Sprache es erzwingt, sondern weil es die bessere Lösung für das jeweilige Problem ist.

# Klassen

## Klasse vs. Instanz — der Bauplan-Vergleich

Eine **Klasse** ist ein Bauplan (blueprint) — sie definiert, welche Attribute und Methoden Objekte dieses Typs haben werden. Eine **Instanz** (auch "Objekt" genannt) ist ein konkretes, im Speicher existierendes Ding, das nach diesem Bauplan gebaut wurde.

```python
class PriceableUnit:
    pass

unit_a = PriceableUnit()  # eine Instanz
unit_b = PriceableUnit()  # eine andere, unabhängige Instanz

print(unit_a is unit_b)          # False - zwei verschiedene Objekte im Speicher
print(type(unit_a) is PriceableUnit)  # True - unit_a ist eine Instanz von PriceableUnit
```

Analogie: `PriceableUnit` ist wie der Bauplan für "ein Haus mit Grundriss X". `unit_a` und `unit_b` sind zwei tatsächlich gebaute Häuser nach diesem Plan — beide haben dieselbe Struktur, aber unterschiedliche, unabhängige Zustände (unterschiedliche Bewohner, unterschiedliche Möbel).

## `__init__` und `self`

`__init__` ist die **Initialisierungsmethode** ("Konstruktor" im umgangssprachlichen Sinn, technisch übernimmt `__new__` das eigentliche Erzeugen des Objekts — das ist aber ein Detail, das fast nie manuell angefasst wird). `__init__` wird automatisch aufgerufen, wenn eine neue Instanz erzeugt wird, und ist dafür da, den Anfangszustand des Objekts zu setzen.

```python
class PriceableUnit:
    def __init__(self, unit_id: str, base_price: float, demand_factor: float = 1.0):
        self.unit_id = unit_id
        self.base_price = base_price
        self.demand_factor = demand_factor

unit = PriceableUnit("SKU-001", 19.99)
```

**`self`** ist der Verweis auf "diese konkrete Instanz". Es ist eine Konvention (kein Keyword!) — der Name könnte theoretisch anders lauten, aber `self` als erster Parameter jeder Instanzmethode ist universeller Python-Standard und sollte nie geändert werden.

Wichtig zu verstehen: Wenn du `unit.calculate_price_recommendation()` aufrufst, übersetzt Python das intern zu `PriceableUnit.calculate_price_recommendation(unit)` — die Instanz wird automatisch als erstes Argument (`self`) mitgegeben. Das lässt sich direkt beobachten:

```python
class PriceableUnit:
    def __init__(self, base_price: float, demand_factor: float):
        self.base_price = base_price
        self.demand_factor = demand_factor

    def calculate_price_recommendation(self) -> float:
        return round(self.base_price * self.demand_factor, 2)

unit = PriceableUnit(19.99, 1.15)

# Diese beiden Aufrufe sind äquivalent:
print(unit.calculate_price_recommendation())
print(PriceableUnit.calculate_price_recommendation(unit))
```

## Instanzattribute vs. Klassenattribute

Das ist eine der häufigsten Fehlerquellen für OOP-Einsteiger in Python — und deshalb hier bewusst ausführlich.

- **Instanzattribute** werden pro Objekt in `__init__` (typischerweise via `self.xyz = ...`) gesetzt. Jede Instanz hat ihre eigene, unabhängige Kopie.
- **Klassenattribute** werden direkt im Klassenkörper (außerhalb von `__init__`) definiert. Sie gehören zur Klasse selbst und werden von **allen** Instanzen geteilt, solange sie nicht überschrieben werden.

```python
class PriceableUnit:
    currency = "EUR"  # Klassenattribut - für alle Units gleich (Default)

    def __init__(self, unit_id: str, base_price: float):
        self.unit_id = unit_id      # Instanzattribut
        self.base_price = base_price  # Instanzattribut

a = PriceableUnit("SKU-001", 19.99)
b = PriceableUnit("SKU-002", 29.99)

print(a.currency, b.currency)  # EUR EUR - beide greifen auf dasselbe Klassenattribut zu

a.currency = "USD"  # Das erzeugt KEIN Update des Klassenattributs,
                     # sondern legt ein neues Instanzattribut "currency" NUR auf a an!

print(a.currency, b.currency)  # USD EUR
print(PriceableUnit.currency)  # EUR - unverändert
```

Das Verhalten dahinter: Wenn du auf `a.currency` **liest**, sucht Python zuerst im Instanz-Namespace (`a.__dict__`), findet dort nichts und fällt zurück auf den Klassen-Namespace (`PriceableUnit.__dict__`). Wenn du auf `a.currency` **schreibst**, wird immer ein Eintrag im Instanz-Namespace erzeugt/überschrieben — nie im Klassen-Namespace. Das kannst du direkt sichtbar machen:

```python
print(a.__dict__)              # {'unit_id': 'SKU-001', 'base_price': 19.99, 'currency': 'USD'}
print(b.__dict__)              # {'unit_id': 'SKU-002', 'base_price': 29.99}
print(PriceableUnit.__dict__.keys())  # enthält u.a. 'currency', '__init__', ...
```

### Die klassische Falle: veränderliche (mutable) Klassenattribute

Weil Klassenattribute standardmäßig **geteilt** werden, ist es gefährlich, veränderliche Objekte (Listen, Dicts, Sets) als Klassenattribut zu verwenden:

```python
class PriceableUnit:
    applied_discounts = []  # GEFÄHRLICH: eine einzige, geteilte Liste für ALLE Instanzen!

    def __init__(self, unit_id: str):
        self.unit_id = unit_id

a = PriceableUnit("SKU-001")
b = PriceableUnit("SKU-002")

a.applied_discounts.append("BLACK_FRIDAY")  # verändert die geteilte Liste, kein neues Attribut!

print(b.applied_discounts)  # ['BLACK_FRIDAY'] - taucht fälschlich auch bei b auf!
print(a.applied_discounts is b.applied_discounts)  # True - dieselbe Liste im Speicher
```

Grund: `a.applied_discounts.append(...)` ist ein **Lesezugriff** auf `applied_discounts` (Python muss die Liste erst finden, um `.append()` darauf aufzurufen), gefolgt von einer Mutation dieses gefundenen Objekts. Es findet also die geteilte Klassen-Liste und verändert genau diese — es wird kein neues Instanzattribut angelegt (das würde nur bei `a.applied_discounts = [...]`, also einer direkten Zuweisung, passieren).

**Richtig**: veränderliche Defaults immer in `__init__` pro Instanz neu erzeugen:

```python
class PriceableUnit:
    def __init__(self, unit_id: str):
        self.unit_id = unit_id
        self.applied_discounts = []  # jede Instanz bekommt ihre EIGENE Liste

a = PriceableUnit("SKU-001")
b = PriceableUnit("SKU-002")
a.applied_discounts.append("BLACK_FRIDAY")
print(b.applied_discounts)  # [] - unberührt, wie erwartet
```

(Dasselbe Problem in einer anderen Verkleidung begegnet dir übrigens bei "mutable default arguments" von Funktionen, z. B. `def f(items=[])` — gleiche Ursache: ein einziges Objekt wird geteilt statt pro Aufruf neu erzeugt.)

## Methoden sind Funktionen im Klassen-Namespace

Eine Instanzmethode ist letztlich nichts anderes als eine ganz normale Funktion, die im Klassenkörper definiert ist und als ersten Parameter `self` erwartet:

```python
class PriceableUnit:
    def __init__(self, base_price: float, demand_factor: float):
        self.base_price = base_price
        self.demand_factor = demand_factor

    def calculate_price_recommendation(self) -> float:
        return round(self.base_price * self.demand_factor, 2)

    def apply_discount(self, percentage: float) -> None:
        self.base_price = round(self.base_price * (1 - percentage / 100), 2)
```

`apply_discount` verändert den Zustand der Instanz (`self.base_price`) direkt — das ist ein zentrales OOP-Muster: statt eine neue Preis-Variable irgendwo außerhalb zu verwalten, kennt und verändert das Objekt seinen eigenen Zustand.

## Introspection — Objekte zur Laufzeit untersuchen

Ein paar nützliche eingebaute Werkzeuge, um zu verstehen, was ein Objekt "ist" und "hat":

```python
unit = PriceableUnit(19.99, 1.15)

print(type(unit))                     # <class '__main__.PriceableUnit'>
print(isinstance(unit, PriceableUnit))  # True
print(unit.__dict__)                  # {'base_price': 19.99, 'demand_factor': 1.15}
print(hasattr(unit, "base_price"))    # True
print(dir(unit))                      # listet alle Attribute/Methoden (inkl. geerbte & dunder)
```

`isinstance()` ist dabei in der Regel die bevorzugte Variante gegenüber `type(unit) == PriceableUnit`, weil sie später mit Vererbung korrekt funktioniert (eine Subklasse *ist* auch eine Instanz der Elternklasse — mehr dazu, wenn wir zu *Vererbung* kommen).

# Vererbung

## Grundidee: die "ist-ein"-Beziehung

Vererbung erlaubt, eine neue Klasse (**Subklasse** / **Kindklasse**) auf Basis einer bestehenden Klasse (**Basisklasse** / **Elternklasse** / **Superklasse**) zu definieren. Die Subklasse übernimmt automatisch alle Attribute und Methoden der Basisklasse und kann sie erweitern oder überschreiben.

Wichtigstes Kriterium, um zu entscheiden, ob Vererbung das richtige Werkzeug ist: Besteht zwischen den beiden Konzepten eine **"ist-ein"-Beziehung**? Ein `DigitalProduct` *ist eine* `PriceableUnit` — das passt. Eine `PriceableUnit`, die *einen* Rabattmechanismus benutzt, ist dagegen keine "ist-ein"-, sondern eine "hat-ein"-Beziehung (→ Komposition, siehe weiter unten).

## Syntax: von einer Basisklasse erben

```python
class PriceableUnit:
    def __init__(self, unit_id: str, base_price: float):
        self.unit_id = unit_id
        self.base_price = base_price

    def calculate_price_recommendation(self) -> float:
        return round(self.base_price, 2)


class DigitalProduct(PriceableUnit):
    """Ein digitales Produkt - erbt von PriceableUnit, ohne vorerst etwas zu ändern."""
    pass


product = DigitalProduct(unit_id="EBOOK-001", base_price=9.99)
print(isinstance(product, DigitalProduct))   # True
print(isinstance(product, PriceableUnit))    # True - jede DigitalProduct IST AUCH eine PriceableUnit
print(product.calculate_price_recommendation())  # 9.99 - geerbte Methode funktioniert direkt, ohne Zutun
```

## `__init__` erweitern statt duplizieren: `super()`

Meistens soll eine Subklasse zusätzliche Attribute mitbringen, ohne den kompletten Initialisierungscode der Basisklasse zu duplizieren. `super().__init__(...)` ruft die `__init__`-Methode der Basisklasse auf:

```python
class DigitalProduct(PriceableUnit):
    def __init__(self, unit_id: str, base_price: float, license_type: str):
        super().__init__(unit_id, base_price)   # Basis-Initialisierung wiederverwenden
        self.license_type = license_type         # zusätzliches, subklassen-spezifisches Attribut


class PhysicalProduct(PriceableUnit):
    def __init__(self, unit_id: str, base_price: float, weight_kg: float):
        super().__init__(unit_id, base_price)
        self.weight_kg = weight_kg


ebook = DigitalProduct("EBOOK-001", 9.99, license_type="single-user")
book = PhysicalProduct("BOOK-001", 24.99, weight_kg=0.6)

print(ebook.unit_id, ebook.license_type)   # EBOOK-001 single-user - geerbtes + eigenes Attribut
print(book.unit_id, book.weight_kg)        # BOOK-001 0.6
```

Ohne `super().__init__(...)` müsstest du `self.unit_id = unit_id` und `self.base_price = base_price` in jeder Subklasse erneut hinschreiben — Codeduplikation, die bei jeder Änderung an der Basisklasse in mehreren Klassen synchron gehalten werden müsste (verstößt gegen DRY - *Don't Repeat Yourself*).

## Methoden überschreiben (Method Overriding)

Die eigentliche Stärke von Vererbung: Eine Subklasse kann eine geerbte Methode **überschreiben**, um abweichendes Verhalten zu definieren. Das haben wir in [[Antworten#Überschreiben von Methoden (Python)|Antworten.md]] am `Shape`/`Circle`-Beispiel schon kurz angerissen — hier nochmal am laufenden `PriceableUnit`-Beispiel:

```python
class PhysicalProduct(PriceableUnit):
    def __init__(self, unit_id: str, base_price: float, weight_kg: float, shipping_per_kg: float = 1.50):
        super().__init__(unit_id, base_price)
        self.weight_kg = weight_kg
        self.shipping_per_kg = shipping_per_kg

    def calculate_price_recommendation(self) -> float:
        # überschreibt die Basis-Implementierung komplett: Versandkosten fließen mit ein
        shipping_cost = self.weight_kg * self.shipping_per_kg
        return round(self.base_price + shipping_cost, 2)


book = PhysicalProduct("BOOK-001", 24.99, weight_kg=0.6)
print(book.calculate_price_recommendation())   # 25.89 statt nur 24.99 - eigene Preislogik greift
```

Wichtig: Zur Laufzeit wird immer die Methode der **konkretesten** Klasse verwendet - Python sucht beim Methodenaufruf zuerst in der Klasse der tatsächlichen Instanz, erst danach (falls dort nichts gefunden wird) in der Elternklasse, dann in deren Elternklasse usw. Diese Suchreihenfolge heißt **Method Resolution Order (MRO)** und lässt sich direkt inspizieren:

```python
print(PhysicalProduct.__mro__)
# (<class '__main__.PhysicalProduct'>, <class '__main__.PriceableUnit'>, <class 'object'>)
```

Willst du die überschriebene Methode nicht komplett ersetzen, sondern **erweitern** (Basisverhalten + etwas zusätzlich), rufst du mit `super().methodenname()` explizit die Elternversion mit auf — genau wie oben bei `super().__init__()`:

```python
class DiscountedDigitalProduct(DigitalProduct):
    def __init__(self, unit_id, base_price, license_type, discount_percent: float):
        super().__init__(unit_id, base_price, license_type)
        self.discount_percent = discount_percent

    def calculate_price_recommendation(self) -> float:
        base_recommendation = super().calculate_price_recommendation()  # Basisverhalten wiederverwenden
        return round(base_recommendation * (1 - self.discount_percent / 100), 2)


promo_ebook = DiscountedDigitalProduct("EBOOK-002", 19.99, "single-user", discount_percent=20)
print(promo_ebook.calculate_price_recommendation())  # 15.99
```

## Mehrfachvererbung und Method Resolution Order (kurzer Ausblick)

Im Unterschied zu Java (dort erbt eine Klasse maximal von *einer* anderen Klasse) erlaubt Python **Mehrfachvererbung** — eine Klasse kann von mehreren Basisklassen gleichzeitig erben:

```python
import datetime

class TimestampedMixin:
    def touch(self) -> None:
        self.last_modified = datetime.datetime.now()


class DigitalProduct(PriceableUnit, TimestampedMixin):
    pass
```

Das ist mächtig, aber auch eine häufige Quelle von Komplexität, sobald mehrere Basisklassen dieselbe Methode definieren (klassisches **"Diamond Problem"**). Python löst das deterministisch über den **C3-Linearisierungsalgorithmus** — nachschaubar über `KlassenName.__mro__` bzw. `KlassenName.mro()`. Für den Alltag reicht als Faustregel: Mehrfachvererbung sparsam einsetzen, am ehesten für kleine, fokussierte **Mixins** (wie `TimestampedMixin` oben), die genau eine Zusatzfähigkeit beisteuern und selbst keinen komplexen eigenen Zustand mitbringen.

## Vererbung vs. Komposition — "ist-ein" vs. "hat-ein"

Eine der wichtigsten Design-Entscheidungen in der OOP: Nicht jede Code-Wiederverwendung sollte über Vererbung gelöst werden. Häufig zitierte Faustregel: **"favor composition over inheritance"** — Komposition der Vererbung vorziehen, wo beides möglich wäre.

- **Vererbung** ("ist-ein"): passend, wenn die Subklasse wirklich eine speziellere Variante der Basisklasse *ist* und deren komplette Schnittstelle sinnvoll erfüllt.
- **Komposition** ("hat-ein"): Ein Objekt *benutzt* ein anderes Objekt als Baustein, statt von ihm zu erben.

```python
# Statt Vererbung ...
class DiscountablePriceableUnit(PriceableUnit):
    def calculate_price_recommendation(self) -> float:
        ...  # Rabattlogik direkt fest hier verdrahtet

# ... lieber Komposition: die Rabattlogik ist ein eigenständiger, austauschbarer Baustein
class PercentageDiscount:
    def __init__(self, percent: float):
        self.percent = percent

    def apply(self, price: float) -> float:
        return round(price * (1 - self.percent / 100), 2)


class PriceableUnit:
    def __init__(self, unit_id: str, base_price: float, discount: "PercentageDiscount | None" = None):
        self.unit_id = unit_id
        self.base_price = base_price
        self.discount = discount   # PriceableUnit HAT (optional) einen Discount, IST aber keiner

    def calculate_price_recommendation(self) -> float:
        price = self.base_price
        if self.discount is not None:
            price = self.discount.apply(price)
        return round(price, 2)


unit = PriceableUnit("SKU-001", 100.0, discount=PercentageDiscount(10))
print(unit.calculate_price_recommendation())   # 90.0
```

Vorteil der Komposition hier: `PercentageDiscount` lässt sich unabhängig testen, wiederverwenden (auch außerhalb von `PriceableUnit`) und austauschen (z. B. gegen eine spätere `FixedAmountDiscount`), ohne eine tiefe, starre Klassenhierarchie mit `DiscountedPriceableUnit`, `DiscountedDigitalProduct`, `DiscountedPhysicalProduct`, … aufzubauen, die schnell unübersichtlich wird.

## `isinstance()` und `issubclass()` mit Vererbung

```python
print(isinstance(ebook, DigitalProduct))     # True
print(isinstance(ebook, PriceableUnit))      # True - erbt transitiv
print(isinstance(ebook, PhysicalProduct))    # False - andere Astgabel der Hierarchie

print(issubclass(DigitalProduct, PriceableUnit))   # True - Klassenvergleich, keine Instanz nötig
print(issubclass(PriceableUnit, DigitalProduct))   # False - nicht umgekehrt
```

Das erklärt auch, warum `isinstance()` in [[Documentation/Traineeship/Grundlagen der Software Entwicklung/1.1 OOP/Anki Karteikarten|den Karteikarten]] als bevorzugte Variante gegenüber `type(obj) == Klasse` genannt wurde: Sie berücksichtigt die gesamte Vererbungskette, nicht nur den exakten Typ.

# Polymorphie

## Grundidee: eine Schnittstelle, viele Formen

"Poly" (viele) + "morphe" (Formen). Polymorphie bedeutet: Objekte unterschiedlicher Klassen lassen sich über **dieselbe Schnittstelle** (denselben Methodennamen) ansprechen, obwohl jede Klasse dahinter eine eigene, passende Implementierung hat. Der aufrufende Code muss den konkreten Typ nicht kennen — er verlässt sich darauf, dass die Methode "irgendwie sinnvoll" funktioniert.

Das ist direkt die technische Grundlage für `calculate_all_price_recommendations()` aus eurer Übungsaufgabe: Die Funktion kann über eine gemischte Liste verschiedenster `PriceableUnit`-Subklassen iterieren, ohne mit `if isinstance(unit, DigitalProduct): ... elif isinstance(unit, PhysicalProduct): ...` jeden Fall einzeln unterscheiden zu müssen.

## Beispiel: einheitliche Iteration über unterschiedliche Subklassen

```python
units: list[PriceableUnit] = [
    DigitalProduct("EBOOK-001", 9.99, license_type="single-user"),
    PhysicalProduct("BOOK-001", 24.99, weight_kg=0.6),
    DiscountedDigitalProduct("EBOOK-002", 19.99, "single-user", discount_percent=20),
]

def calculate_all_price_recommendations(units: list[PriceableUnit]) -> None:
    for unit in units:
        # Jede Subklasse "weiß selbst", wie SIE ihre Preisempfehlung berechnet -
        # calculate_all_price_recommendations() muss das nicht unterscheiden.
        print(f"{unit.unit_id}: {unit.calculate_price_recommendation()}")

calculate_all_price_recommendations(units)
# EBOOK-001: 9.99
# BOOK-001: 25.89
# EBOOK-002: 15.99
```

Das ist **Laufzeit-Polymorphie über Methodenüberschreibung**: Welche konkrete `calculate_price_recommendation()`-Implementierung ausgeführt wird, entscheidet sich erst zur Laufzeit anhand des tatsächlichen Objekttyps (vgl. MRO oben) — nicht zur "Compile-Zeit" (Python hat ohnehin keine echte Compile-Zeit-Typprüfung, aber das Prinzip gilt konzeptionell genauso in statisch typisierten Sprachen wie Java).

## Zwei Wege zu Polymorphie in Python: Vererbung vs. Duck Typing

Wichtig zu unterscheiden, weil Python hier mehr Freiheit bietet als z. B. Java:

1. **Polymorphie über Vererbung (nominal)**: wie oben — Klassen erben von einer gemeinsamen Basisklasse und überschreiben deren Methoden. Der Zusammenhang ist explizit über die Klassenhierarchie sichtbar.
2. **Polymorphie über Duck Typing (strukturell)**: In Python reicht es oft, dass zwei Klassen **gar keine gemeinsame Basisklasse** haben, aber beide dieselbe Methode anbieten — "Wenn es wie eine Ente watschelt und quakt wie eine Ente, ist es für meinen Zweck eine Ente." Genau das haben wir in [[Antworten#Gegen gemeinsames Verhalten statt gegen konkrete Klassen programmieren|Antworten.md]] am `CsvExporter`/`JsonExporter`-Beispiel schon gesehen: `run_export()` funktioniert mit jedem Objekt, das eine `export()`-Methode hat, unabhängig von dessen Vererbungshierarchie.

```python
class FreeSample:
    """Hat KEINE gemeinsame Basisklasse mit PriceableUnit, bietet aber dieselbe Methode an."""
    def __init__(self, unit_id: str):
        self.unit_id = unit_id

    def calculate_price_recommendation(self) -> float:
        return 0.0

# funktioniert trotzdem, weil calculate_all_price_recommendations() nur die Methode braucht,
# nicht eine bestimmte Basisklasse:
calculate_all_price_recommendations(units + [FreeSample("SAMPLE-001")])
```

`typing.Protocol` (siehe [[Antworten#Protocol aus typing|Antworten.md]]) gibt dieser Art von Duck-Typing-Polymorphie zusätzlich statische Typsicherheit, ohne eine echte Vererbungsbeziehung zu erzwingen.

## Operator Overloading als Sonderfall von Polymorphie

Auch **Operator Overloading** (bereits in [[Antworten#Operator Overloading|Antworten.md]] behandelt) ist letztlich Polymorphie: derselbe Operator (`+`, \`\=\=\`, `len(...)`, …) verhält sich je nach Typ der beteiligten Objekte unterschiedlich — `1 + 1` (Integer-Addition) und `Money(1) + Money(1)` (eigene `__add__`-Logik) nutzen dieselbe Syntax für unterschiedliches Verhalten. In der Literatur wird das manchmal präziser als **Ad-hoc-Polymorphie** bezeichnet (im Gegensatz zur **Subtyp-Polymorphie** über Vererbung, die wir oben primär behandelt haben).

## Ausblick: `functools.singledispatch`

Nur als Randnotiz, falls dir der Begriff später begegnet: Python hat kein eingebautes "multiple dispatch" (eine Funktion, die je nach Typ des Arguments automatisch eine passende Implementierung wählt) wie manche andere Sprachen. `functools.singledispatch` bietet eine eingeschränkte Variante davon — eine Funktion mit typspezifischen Überladungen, ausgewählt anhand des **ersten** Arguments:

```python
from functools import singledispatch

@singledispatch
def describe(unit) -> str:
    return "unbekannte Einheit"

@describe.register
def _(unit: DigitalProduct) -> str:
    return f"Digitales Produkt: {unit.unit_id}"

@describe.register
def _(unit: PhysicalProduct) -> str:
    return f"Physisches Produkt: {unit.unit_id}, {unit.weight_kg}kg"

print(describe(ebook))   # Digitales Produkt: EBOOK-001
print(describe(book))    # Physisches Produkt: BOOK-001, 0.6kg
```

Out of Scope für dieses Kapitel im Detail, aber gut zu wissen, dass es diesen alternativen Weg zu "typabhängigem Verhalten" gibt, der nicht auf Methodenüberschreibung innerhalb einer Klasse beruht.

# Kapselung

## Grundidee: Zustand bündeln und Zugriff kontrollieren

Kapselung heißt: Zustand und Verhalten werden in einer Klasse gebündelt (das haben wir ganz am Anfang schon gesehen), UND der Zugriff auf den internen Zustand wird kontrolliert, statt ihn völlig offenzulegen. Das Ziel: Ein Objekt soll seine eigenen Invarianten (z. B. "der Preis ist nie negativ") selbst durchsetzen können, statt sich darauf zu verlassen, dass jeder Aufrufer überall im Code brav damit umgeht.

## Python hat kein echtes `private` — nur Konventionen

Anders als Java/C++ (dort gibt es `private`/`protected`/`public` als vom Compiler durchgesetzte Sichtbarkeit) kennt Python **keine echte Zugriffskontrolle**. Stattdessen gibt es zwei Namenskonventionen, die Absicht kommunizieren, aber technisch (fast) nichts erzwingen:

- **Einfacher Unterstrich** `_attribut`: Konvention für "das ist internes Implementierungsdetail, bitte nicht von außen anfassen" — wird von Python selbst nicht durchgesetzt, jeder kann trotzdem `obj._attribut` lesen/schreiben.
- **Doppelter Unterstrich** `__attribut` (ohne trailing double underscore, sonst wäre es ein Dunder): löst **Name Mangling** aus — Python benennt das Attribut intern in `_KlassenName__attribut` um.

```python
class PriceableUnit:
    def __init__(self, base_price: float):
        self.__base_price = base_price   # wird zu _PriceableUnit__base_price umbenannt

unit = PriceableUnit(19.99)
print(unit.__dict__)              # {'_PriceableUnit__base_price': 19.99}
print(unit._PriceableUnit__base_price)  # 19.99 - geht trotzdem, nur unbequemer/hässlicher zu schreiben
# print(unit.__base_price)        # AttributeError - unter DIESEM Namen existiert es nicht mehr
```

Name Mangling ist primär dafür gedacht, **Namenskollisionen bei Vererbung** zu vermeiden (zwei Klassen in einer Hierarchie können unabhängig ein `__x` verwenden, ohne sich gegenseitig zu überschreiben) — es ist **kein** Sicherheitsmechanismus und keine echte Kapselung im Sinne von Java `private`. In der Praxis wird in Python meist der einfache Unterstrich `_attribut` bevorzugt; doppelte Unterstriche nur, wenn Name Mangling wirklich gebraucht wird (z. B. in Basisklassen, die von Subklassen unabhängig bleiben sollen).

## `@property`: kontrollierter Zugriff ohne die öffentliche API zu ändern

Das zentrale Werkzeug für Kapselung in Python ist `@property` — Grundlagen dazu haben wir in den [[Antworten#Getter/Setter-Methoden in Python|Antworten]] schon vorweggenommen (Validierung im Setter). Hier nochmal am laufenden Beispiel, plus die Variante als **read-only, berechnetes Attribut**:

```python
# Auszug aus src/pricing/domain.py
from datetime import date


class PriceableUnit:
    """Eine buchbare Einheit - unveränderlicher Snapshot der Buchungslage."""

    def __init__(
        self,
        product_id: str,
        calendar_date: date,
        *,
        bookable_units: int,
        booked_units: int,
        optional_units: int,
    ):
        if booked_units < 0:                  # Invariante direkt bei der Erzeugung durchsetzen
            raise ValueError("booked_units darf nicht negativ sein")
        self._product_id = product_id         # aller Zustand privat (führender _)
        self._calendar_date = calendar_date
        self._bookable_units = bookable_units
        self._booked_units = booked_units
        self._optional_units = optional_units

    @property
    def booked_units(self) -> int:
        return self._booked_units             # read-only: nur Getter, kein Setter

    @property
    def total_capacity(self) -> int:
        """Berechnetes, read-only Attribut - kein gespeicherter Wert."""
        return self._bookable_units + self._optional_units + self._booked_units

    @property
    def occupancy(self) -> float:
        return self._booked_units / self.total_capacity


unit = PriceableUnit("P-001", date(2027, 4, 22), bookable_units=3, booked_units=2, optional_units=0)
print(unit.total_capacity)   # 5 - sieht aus wie ein Attribut, ist aber berechnet
print(unit.occupancy)        # 0.4 - ebenfalls berechnet
unit.total_capacity = 10     # AttributeError: property 'total_capacity' has no setter
```

Der entscheidende Vorteil gegenüber Java-artigen `getTotalCapacity()`-Methoden: Aufrufender Code schreibt weiterhin ganz normal `unit.total_capacity` — die öffentliche Schnittstelle ändert sich nicht, egal ob dahinter ein einfaches Attribut oder eine berechnete Property steckt. Diese `PriceableUnit` ist bewusst ein **unveränderlicher Snapshot**: Aller Zustand ist privat, es gibt **keine Setter**, und die einzige Invariante (`booked_units >= 0`) wird direkt im `__init__` durchgesetzt — so gilt sie über die gesamte Lebensdauer statt nur bei der Erzeugung. Umgekehrt erlaubt derselbe `@property`-Mechanismus auch den anderen Weg: mit einem simplen öffentlichen Attribut starten und erst **bei Bedarf** später (ohne Breaking Change für Aufrufer) eine Property mit Validierung/Setter nachrüsten.

## `functools.cached_property`: berechnetes Attribut mit Caching

Bereits in den [[Antworten#Decorators & Libraries für Klassenprogrammierung „under the hood"|Antworten]] als Stichwort genannt — hier der konkrete Unterschied zu `@property`: `@property` berechnet den Wert bei **jedem** Zugriff neu, `@cached_property` berechnet ihn nur beim **ersten** Zugriff und speichert das Ergebnis danach pro Instanz zwischen:

```python
from functools import cached_property
import time

class PriceableUnit:
    def __init__(self, base_price: float):
        self.base_price = base_price

    @cached_property
    def expensive_market_analysis(self) -> float:
        time.sleep(2)  # steht hier stellvertretend für eine teure Berechnung/einen API-Call
        return self.base_price * 1.1

unit = PriceableUnit(100.0)
print(unit.expensive_market_analysis)  # dauert ~2 Sekunden
print(unit.expensive_market_analysis)  # sofort - Ergebnis kam aus dem Cache
```

Wichtig zu wissen: Ändert sich `self.base_price` nachträglich, wird `expensive_market_analysis` **nicht** automatisch neu berechnet — der gecachte Wert bleibt stehen, bis man ihn manuell aus `unit.__dict__` löscht. `@cached_property` eignet sich daher nur für Werte, die sich über die Lebensdauer der Instanz nicht (oder nur selten, kontrolliert) ändern.

# Abstraktion

## Grundidee: relevante Eigenschaften modellieren, Details weglassen

Abstraktion bedeutet, beim Modellieren eines Konzepts bewusst nur die für den jeweiligen Zweck relevanten Eigenschaften abzubilden und alles andere wegzulassen. Eine `PriceableUnit` in unserer Übungsaufgabe braucht z. B. `base_price` und eine Methode zur Preisberechnung — sie muss nicht abbilden, wie das Produkt hergestellt wurde oder welche Lieferanten beteiligt waren, weil das für "Preisempfehlungen berechnen" schlicht irrelevant ist.

## Abstraktion vs. Kapselung — die zentrale Abgrenzung (Kontrollfrage!)

Diese beiden Begriffe werden oft verwechselt, weil sie eng zusammenspielen, aber sie beantworten unterschiedliche Fragen:

- **Abstraktion** ist eine **Design-Entscheidung**: *Was* muss ein Nutzer dieses Konzepts überhaupt wissen/können? Welche Schnittstelle ist die richtige, welche Details sind irrelevant? Sie existiert schon auf der Ebene der Modellierung, bevor überhaupt Code geschrieben wird.
- **Kapselung** ist ein **Implementierungsmechanismus**: *Wie* wird der Zugriff auf interne Details technisch kontrolliert (Konventionen, `@property`, siehe oben)? Sie ist das Werkzeug, mit dem eine einmal getroffene Abstraktion in Python tatsächlich durchgesetzt/geschützt wird.

Analogie Autofahren: Als Fahrer nutzt du die **Abstraktion** "Lenkrad, Gas-, Brems- und Kupplungspedal" — das ist alles, was du wissen musst, um zu fahren. Wie der Verbrennungsmotor oder das Getriebe im Detail funktioniert, bleibt dir verborgen — das ist **Kapselung**: die Details sind hinter der einfachen Schnittstelle versteckt. Übertragen auf unser Beispiel: `unit.price_with_vat` (Abstraktion: "ich will den Preis inkl. MwSt., fertig") versteckt via `@property` (Kapselung), dass dahinter tatsächlich `self._base_price * (1 + self._vat_rate)` gerechnet wird.

## Abstrakte Basisklassen in Python (`abc`-Modul)

Eine **abstrakte Klasse** definiert eine gemeinsame Schnittstelle (und ggf. schon etwas gemeinsame Logik) für eine Familie von Subklassen, kann aber selbst **nicht direkt instanziiert** werden — sie ist bewusst unvollständig und zwingt Subklassen, bestimmte Methoden selbst zu implementieren. In Python über das `abc`-Modul (`ABC` als Basisklasse, `@abstractmethod` als Decorator):

```python
from abc import ABC, abstractmethod

class PriceableUnit(ABC):
    def __init__(self, unit_id: str, base_price: float):
        self.unit_id = unit_id
        self.base_price = base_price

    @abstractmethod
    def calculate_price_recommendation(self) -> float:
        """Muss von jeder konkreten Subklasse implementiert werden."""
        ...

    def describe(self) -> str:
        # ganz normale, bereits fertig implementierte Methode - abstrakte Klassen
        # dürfen (und sollen oft) auch konkretes, gemeinsames Verhalten mitbringen
        return f"{self.unit_id}: {self.calculate_price_recommendation()}"


# unit = PriceableUnit("SKU-001", 10.0)  # TypeError: Can't instantiate abstract class
#                                         # PriceableUnit with abstract method calculate_price_recommendation

class DigitalProduct(PriceableUnit):
    def calculate_price_recommendation(self) -> float:
        return round(self.base_price, 2)

ebook = DigitalProduct("EBOOK-001", 9.99)   # funktioniert - implementiert die abstrakte Methode
print(ebook.describe())                      # EBOOK-001: 9.99
```

**Was unterscheidet eine abstrakte Klasse von einer "normalen" Klasse?** Eine normale Klasse ist immer vollständig und direkt instanziierbar. Eine abstrakte Klasse ist absichtlich unvollständig: Sie kann nicht instanziiert werden, solange mindestens eine mit `@abstractmethod` markierte Methode nicht überschrieben wurde — der Versuch führt zu einem `TypeError` zur Laufzeit (nicht schon beim Import/Parsen). Der Sinn: Man erzwingt, dass jede konkrete Subklasse eine bestimmte Fähigkeit garantiert mitbringt, und dokumentiert das direkt im Code statt nur in einem Kommentar.

## Interfaces (Java) und ihr Gegenstück in Python (Kontrollfrage!)

In Sprachen wie Java kann eine Klasse **Interfaces** implementieren: Ein Interface definiert ausschließlich Methodensignaturen **ohne jede Implementierung** und **ohne eigenen Zustand** — reine Verträge ("wer mich implementiert, garantiert diese Methoden anzubieten"). Wichtiger Unterschied zu Vererbung: Eine Java-Klasse kann nur von **einer** Klasse erben, aber **beliebig viele** Interfaces implementieren.

Python hat kein `interface`-Keyword, bietet aber zwei vergleichbare Wege:

1. **Abstrakte Basisklasse ohne jede konkrete Implementierung** (nur `@abstractmethod`s, kein Zustand) — kommt einem klassischen Interface am nächsten, erfordert aber wie oben eine explizite Vererbungsbeziehung (`class DigitalProduct(Exporter): ...`).
2. **`typing.Protocol`** (bereits in den [[Antworten#Protocol aus typing|Antworten]] eingeführt) — strukturelle Typisierung: Eine Klasse muss das Protocol nicht explizit implementieren/erben, es reicht, die geforderten Methoden zu besitzen (Duck Typing + statische Typprüfung durch `mypy`). Das ist in Python oft der idiomatischere Weg, weil er keine künstliche Vererbungsbeziehung erzwingt, nur um eine Schnittstelle zu erfüllen.

## Was unterscheidet ein Interface von einer abstrakten Klasse? (Kontrollfrage!)

| | Interface | Abstrakte Klasse |
|---|---|---|
| Implementierung | Keine — nur Methodensignaturen | Kann bereits konkrete, fertige Methoden enthalten (siehe `describe()` oben) |
| Zustand | Kein eigener Zustand | Kann Attribute/Zustand mitbringen (z. B. `unit_id`, `base_price`) |
| Mehrfachimplementierung | Eine Klasse kann viele Interfaces implementieren | In Java: eine Klasse erbt nur von einer abstrakten Klasse (Python erlaubt technisch Mehrfachvererbung auch bei ABCs, siehe Mehrfachvererbung oben — sollte aber sparsam genutzt werden) |
| Beziehung, die es ausdrückt | "Kann das" / reiner Funktionsvertrag | "Ist eine speziellere Variante von" ("ist-ein", siehe Vererbungskapitel) |

Kurzfassung: Ein Interface ist ein **reiner Vertrag ohne Substanz**, eine abstrakte Klasse ist eine **teilweise fertige Basis**, die sowohl Verträge (abstrakte Methoden) als auch bereits fertiges, gemeinsames Verhalten (konkrete Methoden) mitbringen kann.

## Warum ist es oft sinnvoller, Interfaces nach außen zu kommunizieren als konkrete Klassen? (Kontrollfrage!)

Das ist derselbe Gedanke wie **"Gegen gemeinsames Verhalten statt gegen konkrete Klassen programmieren"**, den wir in den [[Antworten#Gegen gemeinsames Verhalten statt gegen konkrete Klassen programmieren|Antworten]] schon behandelt haben, und eng verwandt mit dem **Dependency Inversion Principle**: Wenn eine Funktion/ein Modul nach außen nur ein Interface (bzw. ein Protocol) erwartet statt eine konkrete Klasse, bleibt die konkrete Implementierung austauschbar (CSV-Export → JSON-Export → Datenbank-Export), ohne den aufrufenden Code anzufassen. Kommuniziert man dagegen konkrete Klassen nach außen, koppelt man den aufrufenden Code fest an eine spezifische Implementierung — jede Änderung oder jeder Austausch dieser Implementierung zwingt potenziell auch den aufrufenden Code zur Änderung (Verstoß gegen *Loose Coupling*, das als eigenes Stichwort noch folgt).

# Information Hiding

## Grundidee: Details verstecken, damit sie sich ändern lassen

Information Hiding ist das übergeordnete **Design-Prinzip**, das erklärt, *warum* wir Abstraktion und Kapselung überhaupt betreiben: Implementierungsdetails werden vor der Außenwelt verborgen, damit sie sich später **ändern lassen, ohne Aufrufer zu brechen**. Nach außen wird nur eine stabile, möglichst einfache Schnittstelle gezeigt; alles, was dahinter passiert, kann sich frei weiterentwickeln, solange diese Schnittstelle gleich bleibt.

Zwei konkrete Vorteile, die daraus folgen:

1. **Weniger Kopplung**: Aufrufender Code hängt nur von der Schnittstelle ab, nicht von der internen Umsetzung — die Umsetzung darf sich ändern, ohne dass an zehn Stellen im restlichen Code etwas angepasst werden muss.
2. **Weniger kognitive Last**: Wer ein Objekt benutzt, muss nur die öffentliche Schnittstelle verstehen, nicht die komplette interne Implementierung.

## Beispiel: interne Datenstruktur austauschen, ohne Aufrufer zu berühren

```python
class PriceableUnit:
    def __init__(self, unit_id: str, base_price: float):
        self.unit_id = unit_id
        self.base_price = base_price
        self._applied_discount_codes: list[str] = []   # interne Repräsentation, Version 1

    def add_discount(self, code: str) -> None:
        if code not in self._applied_discount_codes:
            self._applied_discount_codes.append(code)

    def has_discount(self, code: str) -> bool:
        return code in self._applied_discount_codes    # bei einer Liste: O(n)


unit = PriceableUnit("SKU-001", 100.0)
unit.add_discount("BLACK_FRIDAY")
print(unit.has_discount("BLACK_FRIDAY"))   # True
```

Angenommen, `has_discount()` wird im Laufe des Projekts sehr häufig für Units mit hunderten Rabatt-Codes aufgerufen — die Liste (O(n) pro Prüfung) wird zum Performance-Problem. Dank Information Hiding lässt sich die interne Repräsentation austauschen, **ohne dass sich für Aufrufer irgendetwas ändert**:

```python
class PriceableUnit:
    def __init__(self, unit_id: str, base_price: float):
        self.unit_id = unit_id
        self.base_price = base_price
        self._applied_discount_codes: set[str] = set()  # interne Repräsentation, Version 2 - jetzt ein Set

    def add_discount(self, code: str) -> None:
        self._applied_discount_codes.add(code)          # set.add() statt Liste + Duplikatsprüfung

    def has_discount(self, code: str) -> bool:
        return code in self._applied_discount_codes      # bei einem Set: O(1)


unit = PriceableUnit("SKU-001", 100.0)
unit.add_discount("BLACK_FRIDAY")
print(unit.has_discount("BLACK_FRIDAY"))   # True - Aufrufer-Code ist identisch geblieben
```

Der komplette interne Wechsel von `list` auf `set` (plus die vereinfachte Duplikatsprüfung) bleibt für jeden Aufrufer von `add_discount()`/`has_discount()` unsichtbar — genau das ist der praktische Nutzen von Information Hiding: Die öffentliche Schnittstelle (Methodennamen, Parameter, Rückgabewerte) ist der stabile "Vertrag", das `_`-Präfix signalisiert, dass `_applied_discount_codes` selbst **nicht** Teil dieses Vertrags ist und sich jederzeit ändern darf.

## Der Dreiklang: Abstraktion, Kapselung, Information Hiding

Diese drei Begriffe hängen eng zusammen, beantworten aber unterschiedliche Fragen — hilfreich, um sie im Kontrollfragen-Kontext sauber auseinanderzuhalten:

| Prinzip | Beantwortet die Frage | Beispiel von oben |
|---|---|---|
| **Abstraktion** | WAS soll nach außen sichtbar/relevant sein? (Design-Entscheidung) | `add_discount()`/`has_discount()` als Schnittstelle, nicht "wie genau Rabatte gespeichert werden" |
| **Kapselung** | WIE wird der Zugriff technisch kontrolliert? (Mechanismus) | `_applied_discount_codes` mit Unterstrich-Konvention, ggf. `@property` |
| **Information Hiding** | WARUM machen wir das überhaupt? (Ziel/Nutzen) | Die interne Umstellung von `list` auf `set` erfordert keine Änderung an Aufrufer-Code |

Kurzfassung: Abstraktion trifft die Design-Entscheidung, Kapselung setzt sie technisch um, und Information Hiding ist der übergeordnete Grund, warum sich der Aufwand lohnt — nämlich Änderungsfreiheit und lose Kopplung (siehe *Loose Coupling*, das als eigenes Stichwort noch folgt).

## Information Hiding über Klassen hinaus: Module und Pakete

Information Hiding ist kein reines Klassen-Konzept, sondern gilt auf jeder Ebene:

- **Modulebene**: Ein führender Unterstrich im Dateinamen (`_internal_helpers.py`) oder in einem Funktions-/Variablennamen signalisiert "nicht Teil der öffentlichen API dieses Moduls".
- **Paketebene**: `__all__` in einer `__init__.py` legt explizit fest, was bei `from package import *` überhaupt exportiert wird — alles andere gilt als internes Detail.

Das ist derselbe Gedanke wie bei `_attribut` auf Klassenebene, nur eine Ebene höher.

# Separation of Concerns

## Grundidee: unterschiedliche Verantwortlichkeiten trennen

Separation of Concerns (SoC) besagt: Unterschiedliche Belange ("concerns") eines Programms sollten in getrennte, unabhängige Bausteine (Module, Klassen, Funktionen, Schichten) aufgeteilt werden, statt sie miteinander zu verweben. Ändert sich ein Belang (z. B. "wie wir Daten speichern"), soll das möglichst nur den dafür zuständigen Baustein betreffen — nicht querbeet den ganzen Code.

## Beispiel: Business-Logik und I/O trennen (direkt relevant für eure Übungsaufgabe!)

Genau das ist in eurer Übungsaufgabe angelegt: `calculate_all_price_recommendations()` soll Preisempfehlungen berechnen **und** in eine CSV-Datei schreiben. Das sind zwei unterschiedliche Concerns — Business-Logik (Preisberechnung) und I/O (Datei schreiben) — die man nicht in einer Funktion vermischen sollte:

```python
# Vermischt: Business-Logik und I/O in einer Funktion
def calculate_all_price_recommendations_bad(units: list[PriceableUnit], path: str) -> None:
    import csv
    with open(path, "w", newline="") as f:
        writer = csv.writer(f)
        for unit in units:
            recommendation = unit.calculate_price_recommendation()  # Business-Logik
            writer.writerow([unit.unit_id, recommendation])          # I/O - direkt verwoben


# Getrennt: zwei Bausteine mit je einem Concern
class PriceRecommendationCalculator:
    """Concern: Preisempfehlungen berechnen - reine Business-Logik, kein I/O."""
    @staticmethod
    def calculate_all(units: list[PriceableUnit]) -> list[tuple[str, float]]:
        return [(unit.unit_id, unit.calculate_price_recommendation()) for unit in units]


class CsvPriceRecommendationWriter:
    """Concern: Ergebnisse persistieren - reines I/O, keine Preislogik."""
    @staticmethod
    def write(path: str, recommendations: list[tuple[str, float]]) -> None:
        import csv
        with open(path, "w", newline="") as f:
            writer = csv.writer(f)
            writer.writerows(recommendations)


# main() verdrahtet beide Bausteine, kennt aber selbst keine Details von beiden
recommendations = PriceRecommendationCalculator.calculate_all(units)
CsvPriceRecommendationWriter.write("recommendations.csv", recommendations)
```

Vorteil: `PriceRecommendationCalculator` lässt sich isoliert testen (kein Dateisystem nötig, einfach Rückgabewerte prüfen), und `CsvPriceRecommendationWriter` ließe sich später gegen `JsonPriceRecommendationWriter` oder `DatabasePriceRecommendationWriter` austauschen, ohne die Preislogik überhaupt anzufassen. Genau dieses Muster (Berechnung getrennt von Persistenz) ist auch der Kern eurer Übungsaufgabe: "rein objektorientiertes Programm, das nur die Business-Logik abbildet" — Datenbank/CSV/REST-API sollen bewusst *nicht* mit der Kernlogik vermischt werden.

## Separation of Concerns vs. Single Responsibility Principle — Abgrenzung (Vorschau)

SoC ist das **allgemeinere** Prinzip und gilt auf jeder Granularitätsstufe (ganze Anwendungsschichten, Module, Klassen, sogar einzelne Funktionen). Das **Single Responsibility Principle** (folgt als eigenes Stichwort als Nächstes) ist im Grunde SoC, konkret angewendet auf die Ebene einer einzelnen Klasse: "Eine Klasse sollte nur einen Grund haben, sich zu ändern." Man kann sich SRP also als den Spezialfall von SoC für Klassendesign merken.

## Klassisches Beispiel: Schichtenarchitektur (Layers)

SoC begegnet euch typischerweise als Trennung in **Schichten** (Layers), z. B.:

- **Präsentationsschicht** (UI/API-Endpunkte) — nimmt Eingaben entgegen, zeigt Ergebnisse an.
- **Business-Logik-Schicht** — die eigentlichen fachlichen Regeln (wie unsere `PriceRecommendationCalculator`).
- **Datenzugriffsschicht** (Persistenz: Datenbank, Dateien, externe APIs) — wie/wo Daten herkommen bzw. landen.

Jede Schicht kommuniziert idealerweise nur mit der direkt benachbarten Schicht und kennt keine Interna der anderen. Das ist übrigens auch der Grund, warum aus euren Notizen hervorgeht, dass man als Data Engineer trotzdem verstehen sollte, wie Backend-Services funktionieren, für die man Data Pipelines baut — man arbeitet an der Datenzugriffs-/Pipeline-Schicht, muss aber die Schnittstelle zur Business-Logik-Schicht sauber respektieren.

## Warum SoC das Testen erleichtert (Ausblick Dependency Injection)

Weil `PriceRecommendationCalculator` oben **kein** I/O kennt, lässt er sich testen, indem man einfach eine Liste von `PriceableUnit`-Objekten übergibt und die Rückgabe prüft — kein echtes Dateisystem, keine echte Datenbank nötig. Sobald Concerns sauber getrennt sind, lässt sich der "unsaubere" Teil (Dateisystem, Datenbank, Netzwerk) beim Testen leicht durch ein Test-Double ersetzen — das ist die Brücke zum Stichwort **Dependency Injection**, das später noch ausführlich drankommt.

# Single Responsibility Prinzip

## Grundidee: ein Grund zur Änderung

Wir haben SRP schon in den [[Antworten#SRP, hohe Kohäsion, Open-Closed|Antworten]] kurz vorweggenommen: **"Eine Klasse sollte genau einen Grund haben, sich zu ändern."** (Formulierung von Robert C. Martin, "Uncle Bob"). Wichtig ist hier das Wort *Grund* — gemeint ist nicht "eine Methode" oder "eine Codezeile", sondern eine **Achse der Veränderung**: Wer oder was könnte einen Änderungswunsch an dieser Klasse haben, und aus wie vielen fachlich unabhängigen Richtungen kämen solche Wünsche?

## Beispiel: SRP-Verletzung erkennen und auflösen

```python
# Verletzt SRP: drei unabhängige "Gründe zur Änderung" in einer Klasse
class PriceableUnit:
    def __init__(self, unit_id: str, base_price: float):
        self.unit_id = unit_id
        self.base_price = base_price

    def calculate_price_recommendation(self) -> float:      # Grund 1: Preislogik ändert sich
        return round(self.base_price * 1.1, 2)

    def validate_input_format(self, raw: dict) -> bool:      # Grund 2: Input-Validierungsregeln ändern sich
        return "unit_id" in raw and "base_price" in raw

    def send_price_change_notification(self) -> None:        # Grund 3: Benachrichtigungs-/Versandlogik ändert sich
        print(f"Preisänderung für {self.unit_id} wurde verschickt")
```

Hier hätten drei völlig unterschiedliche Stakeholder Gründe, diese eine Klasse zu ändern: Das Fachteam für Preisregeln, das Team für Dateneingabe-Validierung und das Team für Benachrichtigungen/Messaging. Ändert sich z. B. nur das Benachrichtigungsformat (von `print` zu einer echten E-Mail), muss man in einer Klasse herumeditieren, die mit E-Mails eigentlich nichts zu tun haben sollte — und riskiert dabei, versehentlich auch Preislogik oder Validierung zu beschädigen.

Aufgelöst (das ist genau *Separation of Concerns* aus dem letzten Kapitel, angewendet auf Klassenebene):

```python
class PriceableUnit:
    def __init__(self, unit_id: str, base_price: float):
        self.unit_id = unit_id
        self.base_price = base_price

    def calculate_price_recommendation(self) -> float:
        return round(self.base_price * 1.1, 2)


class PriceableUnitInputValidator:
    @staticmethod
    def validate(raw: dict) -> bool:
        return "unit_id" in raw and "base_price" in raw


class PriceChangeNotifier:
    @staticmethod
    def notify(unit: PriceableUnit) -> None:
        print(f"Preisänderung für {unit.unit_id} wurde verschickt")
```

Jede Klasse hat jetzt genau einen Grund, sich zu ändern — und genau das ist SRP.

## Praktische Heuristiken, um SRP-Verletzungen zu erkennen

- **"Und"-Test**: Lässt sich die Verantwortung der Klasse nur mit einem "und" beschreiben ("berechnet Preise **und** validiert Eingaben **und** verschickt Benachrichtigungen")? Das ist ein starkes Warnsignal.
- **God Object/God Class**: Eine Klasse, die immer mehr Verantwortlichkeiten ansammelt, weil es "gerade bequem" war, noch eine Methode dort unterzubringen — klassisches Endergebnis wiederholter SRP-Verletzungen.
- **Änderungshäufigkeit aus unterschiedlichen Gründen**: Wird dieselbe Klasse in der Versionshistorie ständig aus fachlich völlig unterschiedlichen Anlässen geändert (Preislogik-Bugfix diese Woche, E-Mail-Template nächste Woche), ist das ein Indiz für zu viele "Gründe zur Änderung" an einem Ort.

## Häufiges Missverständnis: SRP heißt NICHT "eine Methode pro Klasse"

Ein verbreitetes Missverständnis ist, SRP verlange, dass eine Klasse nur eine einzige Methode haben darf. Das stimmt nicht: `PriceableUnit` oben darf durchaus mehrere Methoden haben (z. B. `calculate_price_recommendation()`, `apply_discount()`, `price_with_vat` als Property) — solange sie alle demselben *einen* fachlichen Zweck dienen (Preisberechnung/-verwaltung für eine Einheit) und aus demselben Grund geändert würden. SRP verbietet nicht viele Methoden, sondern **viele voneinander unabhängige Zwecke** in derselben Klasse.

# Loose Coupling vs. hohe Kohäsion (strong cohesion)

## Zwei verschiedene, aber zusammenhängende Metriken

Das sind zwei unterschiedliche Eigenschaften, die man an gutem Klassendesign misst — leicht zu verwechseln, aber sie schauen in unterschiedliche Richtungen:

- **Kopplung (Coupling)**: Wie stark hängen unterschiedliche Klassen/Module **voneinander** ab? Ziel: **lose Kopplung** (*loose coupling*) — eine Änderung in Klasse A soll möglichst wenige andere Klassen betreffen.
- **Kohäsion (Cohesion)**: Wie stark gehören die Dinge **innerhalb** einer Klasse tatsächlich zusammen? Ziel: **hohe Kohäsion** (*high/strong cohesion*) — alle Attribute und Methoden einer Klasse sollten thematisch eng zusammengehören und sich gegenseitig sinnvoll nutzen.

Die klassische Faustregel lautet **"loose coupling, high cohesion"** — beides gemeinsam anstreben, da sie sich gegenseitig unterstützen (dazu gleich mehr).

## Beispiel: enge vs. lose Kopplung

```python
# Enge Kopplung: PriceRecommendationCalculator kennt eine KONKRETE Exporter-Klasse
class PriceRecommendationCalculator:
    def calculate_and_export(self, units: list[PriceableUnit], path: str) -> None:
        recommendations = [(u.unit_id, u.calculate_price_recommendation()) for u in units]
        writer = CsvPriceRecommendationWriter()   # fest verdrahtet auf CSV
        writer.write(path, recommendations)
```

Jede Änderung am Export (neues Format, andere Konstruktor-Signatur von `CsvPriceRecommendationWriter`) zwingt dazu, `PriceRecommendationCalculator` anzufassen — obwohl dessen eigentlicher Zweck (Preise berechnen) davon unberührt sein sollte. Das ist enge Kopplung.

```python
# Lose Kopplung: PriceRecommendationCalculator kennt nur die Schnittstelle (Protocol), nicht die konkrete Klasse
from typing import Protocol

class RecommendationWriter(Protocol):
    def write(self, path: str, recommendations: list[tuple[str, float]]) -> None: ...

class PriceRecommendationCalculator:
    def __init__(self, writer: RecommendationWriter):
        self.writer = writer   # wird von außen hereingereicht, nicht selbst erzeugt

    def calculate_and_export(self, units: list[PriceableUnit], path: str) -> None:
        recommendations = [(u.unit_id, u.calculate_price_recommendation()) for u in units]
        self.writer.write(path, recommendations)


calculator = PriceRecommendationCalculator(writer=CsvPriceRecommendationWriter())
# später, ohne PriceRecommendationCalculator anzufassen:
# calculator = PriceRecommendationCalculator(writer=JsonPriceRecommendationWriter())
```

Das ist derselbe Gedanke wie bei "Gegen gemeinsames Verhalten statt gegen konkrete Klassen programmieren" ([[Antworten#Gegen gemeinsames Verhalten statt gegen konkrete Klassen programmieren|Antworten]]) — hier zusätzlich mit dem Baustein "der Writer wird von außen hereingereicht" statt intern selbst erzeugt. Genau dieses Muster (Abhängigkeiten werden übergeben statt selbst erzeugt) ist der Kern von **Dependency Injection**, das als eigenes Stichwort noch folgt.

## Beispiel: niedrige vs. hohe Kohäsion

```python
# Niedrige Kohäsion: eine "Utils"-Klasse mit thematisch unabhängigen Methoden
class Utils:
    @staticmethod
    def calculate_price_recommendation(base_price: float) -> float:
        return round(base_price * 1.1, 2)

    @staticmethod
    def send_email(to: str, subject: str) -> None:
        ...

    @staticmethod
    def parse_csv_line(line: str) -> list[str]:
        return line.split(",")
```

Diese drei Methoden haben nichts miteinander zu tun — sie teilen sich keinen gemeinsamen Zustand und dienen keinem gemeinsamen Zweck, sondern liegen nur "aus Bequemlichkeit" in derselben Klasse. Das ist niedrige Kohäsion — ein klassisches Warnsignal für eine kommende SRP-Verletzung bzw. ein "Grab" für Code, der eigentlich nirgendwo hingehört.

```python
# Hohe Kohäsion: alle Methoden arbeiten eng mit demselben Zustand und Zweck
class PriceableUnit:
    def __init__(self, base_price: float, vat_rate: float = 0.19):
        self.base_price = base_price
        self.vat_rate = vat_rate

    def calculate_price_recommendation(self) -> float:
        return round(self.base_price * 1.1, 2)

    def apply_discount(self, percentage: float) -> None:
        self.base_price = round(self.base_price * (1 - percentage / 100), 2)

    @property
    def price_with_vat(self) -> float:
        return round(self.base_price * (1 + self.vat_rate), 2)
```

Alle drei Methoden/Properties arbeiten mit denselben Attributen (`base_price`, `vat_rate`) und dienen demselben Zweck (Preisverwaltung für eine Einheit) — das ist hohe Kohäsion.

## Wie erkennt man Kopplung und Kohäsion informell (ohne Tooling)?

- **Kopplung**: Wie viele andere konkrete Klassen muss eine Klasse importieren/kennen, um zu funktionieren? Je mehr konkrete (statt abstrakte/Protocol-)Abhängigkeiten, desto enger gekoppelt.
- **Kohäsion**: Nutzt (fast) jede Methode einer Klasse (fast) alle Instanzattribute? Oder gibt es "Cluster" von Methoden+Attributen, die untereinander nie interagieren (ein Zeichen, dass die Klasse eigentlich zwei Klassen sein sollte)?

## Zusammenhang zwischen SRP, Kohäsion und Kopplung

Diese drei Prinzipien verstärken sich gegenseitig: Eine Klasse mit **hoher Kohäsion** (alle Methoden gehören wirklich zusammen) erfüllt fast automatisch auch **SRP** (sie hat dann typischerweise auch nur einen fachlichen Grund zur Änderung). Und Klassen, die **lose gekoppelt** sind (nur über Schnittstellen/Protocols voneinander abhängen statt über konkrete Implementierungen), lassen sich unabhängig voneinander ändern, testen und austauschen — Änderungen bleiben lokal, statt sich durch die ganze Anwendung zu ziehen. Alle drei Prinzipien verfolgen letztlich dasselbe übergeordnete Ziel wie *Information Hiding*: Änderungen sollen sich auf einen möglichst kleinen, vorhersehbaren Bereich des Codes beschränken.

# Open/Closed Prinzip

## Grundidee: offen für Erweiterung, geschlossen für Veränderung

Bereits kurz in den [[Antworten#SRP, hohe Kohäsion, Open-Closed|Antworten]] angerissen: Software-Bausteine (Klassen, Module, Funktionen) sollen **offen für Erweiterung**, aber **geschlossen für Veränderung** sein. Konkret heißt das: Neues Verhalten hinzufügen, ohne bestehenden, bereits getesteten Code anzufassen. Der Grund: Jede Änderung an funktionierendem Code ist ein Risiko (neue Bugs, Regressionen) — kann man neues Verhalten stattdessen rein additiv (durch neuen Code) hinzufügen, sinkt dieses Risiko drastisch.

## Klassische Verletzung: eine wachsende `if/elif`-Kette

```python
# Verletzt Open/Closed: Für jede neue Produktart muss diese Funktion geändert werden
def calculate_price_recommendation_bad(unit) -> float:
    if isinstance(unit, DigitalProduct):
        return round(unit.base_price, 2)
    elif isinstance(unit, PhysicalProduct):
        return round(unit.base_price + unit.weight_kg * unit.shipping_per_kg, 2)
    elif isinstance(unit, SubscriptionProduct):        # NEU hinzugefügt -> Funktion musste geändert werden!
        return round(unit.base_price * unit.duration_months, 2)
    # ... jede weitere Produktart erfordert einen weiteren elif-Zweig HIER
```

Jedes Mal, wenn eine neue Produktart dazukommt, muss diese eine zentrale Funktion angefasst werden — mit dem Risiko, dabei versehentlich bestehende, bereits funktionierende Zweige zu beschädigen. Das ist genau das, was Open/Closed vermeiden will.

## Auflösung über Polymorphie (Rückbezug auf Vererbung/Polymorphie)

Genau das haben wir im Vererbungs-/Polymorphie-Kapitel schon als Muster gesehen: Jede Subklasse implementiert `calculate_price_recommendation()` selbst, aufrufender Code kennt nur die gemeinsame Schnittstelle:

```python
class SubscriptionProduct(PriceableUnit):     # komplett NEUE Klasse
    def __init__(self, unit_id: str, base_price: float, duration_months: int):
        super().__init__(unit_id, base_price)
        self.duration_months = duration_months

    def calculate_price_recommendation(self) -> float:
        return round(self.base_price * self.duration_months, 2)


def calculate_all_price_recommendations(units: list[PriceableUnit]) -> None:
    for unit in units:
        print(f"{unit.unit_id}: {unit.calculate_price_recommendation()}")   # UNVERÄNDERT!

# SubscriptionProduct einfach mit in die Liste aufnehmen - calculate_all_price_recommendations()
# musste dafür kein einziges Zeichen geändert werden:
calculate_all_price_recommendations(units + [SubscriptionProduct("SUB-001", 9.99, 12)])
```

`calculate_all_price_recommendations()` ist **geschlossen für Veränderung** (wird nie mehr angefasst, egal wie viele Produktarten dazukommen) und gleichzeitig **offen für Erweiterung** (neue Produktarten werden einfach als neue Subklassen hinzugefügt). Das funktioniert nur, weil aufrufender Code gegen die gemeinsame Schnittstelle/Basisklasse programmiert ist, nicht gegen eine feste Aufzählung konkreter Typen — also dieselbe lose Kopplung, die wir im letzten Kapitel besprochen haben.

## Grenzen des Prinzips — kein Dogma

Open/Closed lässt sich nicht für *jede denkbare* zukünftige Änderung im Voraus einplanen — das würde in unnötig abstrakten, übermäßig flexiblen Konstruktionen enden ("Speculative Generality"), die niemand braucht (Rückbezug auf "OOP ist kein Selbstzweck" ganz am Anfang dieser Notiz). Praktikabler Ansatz: Open/Closed gezielt für Erweiterungsachsen anwenden, die **absehbar** sind (z. B. "es werden sicher weitere Produktarten dazukommen"), statt für alles und jedes eine Extension-Schnittstelle vorzubauen, nur weil es theoretisch mal gebraucht werden könnte.

# Clean Code (Grundzüge)

## Was ist Clean Code?

Clean Code bedeutet: Code, der leicht zu **lesen, verstehen und ändern** ist — nicht nur "funktioniert irgendwie". Der zentrale Gedanke: Code wird im Laufe seines Lebens sehr viel öfter **gelesen** als geschrieben (von Kolleg:innen, vom künftigen eigenen Ich, bei Code Reviews, beim Debuggen) — Code sollte daher in erster Linie für Menschen optimiert sein, nicht nur dafür, dass der Interpreter ihn irgendwie ausführen kann. Populäre Formulierung (Robert C. Martin): *"Clean code reads like well-written prose."*

## Kernprinzipien im Überblick

Vieles davon haben wir in diesem Kapitel bereits einzeln behandelt — Clean Code ist eher der **Dachbegriff**, unter dem diese Einzelprinzipien zusammenlaufen:

- **Aussagekräftige Namen**: Variablen-, Funktions- und Klassennamen sollen die Absicht verraten (`calculate_price_recommendation()` statt `calc()` oder `do_stuff()`).
- **Kleine Funktionen mit genau einer Aufgabe**: dieselbe Idee wie SRP, nur auf Funktionsebene statt Klassenebene angewendet.
- **DRY — Don't Repeat Yourself**: Duplikation vermeiden (haben wir konkret bei `super().__init__()` gesehen: ohne das müsste man Initialisierungscode in jeder Subklasse wiederholen).
- **Konsistente Formatierung**: automatisiert durchgesetzt über Tools wie `ruff` (siehe [[Antworten#ruff, mypy|Antworten]]).
- **Kommentare sparsam und gezielt**: Guter Code erklärt sich durch Namen/Struktur weitgehend selbst — Kommentare sollten das *Warum* erklären (eine nicht offensichtliche Design-Entscheidung), nicht das *Was* wiederholen, das im Code selbst schon lesbar ist.
- **Saubere Fehlerbehandlung**: keine leeren `except:`-Blöcke, die Fehler stillschweigend verschlucken; nicht zu tief verschachtelte try/except-Konstrukte.
- **Keine "Magic Numbers"/Strings**: feste Werte wie `1.19` oder `"BLACK_FRIDAY"` sollten benannte Konstanten sein (`VAT_RATE = 0.19`), damit ihre Bedeutung sofort ersichtlich ist und sie an nur einer Stelle geändert werden müssen.

## Kurzes Beispiel: unclean vs. clean

```python
# Unclean: kryptische Namen, Magic Number, alles in einer Zeile
def calc(u):
    return round(u.bp * 1.19, 2)

# Clean: sprechende Namen, benannte Konstante, klar lesbar
VAT_RATE = 0.19

def calculate_price_with_vat(unit: PriceableUnit) -> float:
    return round(unit.base_price * (1 + VAT_RATE), 2)
```

Beide Varianten tun exakt dasselbe — die zweite ist aber sofort verständlich, ohne den Rest des Programms studieren zu müssen, um `u`, `bp` oder `1.19` zu entschlüsseln.

## Clean Code als Dachbegriff — Querverweis auf bereits Gelerntes

An dieser Stelle lohnt sich ein Blick zurück: Sehr viele der bisherigen Stichworte in dieser Notiz sind eigentlich **konkrete Bausteine von Clean Code**:

- **SRP & Separation of Concerns** → kleine, fokussierte Bausteine statt God Classes.
- **Kapselung & Information Hiding** → klare, stabile öffentliche Schnittstellen statt frei zugänglichem internem Chaos.
- **Loose Coupling & hohe Kohäsion** → Code, der sich lokal und risikoarm ändern lässt.
- **Open/Closed** → neues Verhalten hinzufügen, ohne bewährten Code zu riskieren.

Clean Code ist also kein zusätzliches, isoliertes Regelwerk obendrauf, sondern das übergeordnete Ziel, dem all diese Einzelprinzipien dienen: Code, der langfristig verständlich, änderbar und wartbar bleibt.

# Dependency Injection

## Grundidee: Abhängigkeiten von außen hereinreichen statt selbst erzeugen

Das haben wir im Kopplungs-Kapitel schon vorweggenommen: `PriceRecommendationCalculator` bekam seinen `RecommendationWriter` per Konstruktor **hereingereicht**, statt ihn sich intern selbst zu erzeugen (`writer = CsvPriceRecommendationWriter()`). Genau das ist **Dependency Injection (DI)**: Eine Klasse fordert ihre Abhängigkeiten (andere Objekte, die sie zum Funktionieren braucht) nicht selbst an, sondern bekommt sie von außen ("injiziert") — typischerweise beim Erzeugen der Instanz.

## Welche Probleme löst DI konkret?

1. **Testbarkeit**: Beim Testen kann eine echte Abhängigkeit (Datenbank, Dateisystem, externe API) durch ein einfaches Test-Double ersetzt werden, ohne die zu testende Klasse selbst zu verändern.
2. **Lose Kopplung**: Die abhängige Klasse kennt nur die Schnittstelle (siehe `RecommendationWriter`-Protocol), nicht die konkrete Implementierung — austauschbar, ohne sie anzufassen (siehe Loose-Coupling-Kapitel).
3. **Konfigurierbarkeit**: Welche konkrete Implementierung tatsächlich verwendet wird, entscheidet sich zentral an einer Stelle (meist ganz am Anfang/"Wiring" der Anwendung), nicht verstreut über den Code.

## Die drei klassischen Formen von DI

```python
# 1. Constructor Injection (am häufigsten, siehe Kopplungs-Kapitel)
class PriceRecommendationCalculator:
    def __init__(self, writer: RecommendationWriter):
        self.writer = writer   # Abhängigkeit kommt beim Erzeugen der Instanz herein


# 2. Setter/Property Injection - Abhängigkeit wird NACH der Konstruktion gesetzt
class PriceRecommendationCalculator:
    def __init__(self):
        self.writer: RecommendationWriter | None = None

    def set_writer(self, writer: RecommendationWriter) -> None:
        self.writer = writer

calculator = PriceRecommendationCalculator()
calculator.set_writer(CsvPriceRecommendationWriter())   # erst danach einsatzbereit


# 3. Method/Parameter Injection - Abhängigkeit wird nur für EINEN Methodenaufruf übergeben,
#    gar nicht erst als Attribut gespeichert
class PriceRecommendationCalculator:
    def calculate_and_export(self, units: list[PriceableUnit], writer: RecommendationWriter, path: str) -> None:
        recommendations = [(u.unit_id, u.calculate_price_recommendation()) for u in units]
        writer.write(path, recommendations)
```

Constructor Injection ist der Standardfall (Abhängigkeit gehört zum "Lebenszyklus" des Objekts), Method Injection eignet sich, wenn eine Abhängigkeit nur für einen einzelnen Aufruf gebraucht wird und nicht dauerhaft zur Instanz gehören soll.

## Python braucht meist kein DI-Framework

In Java (z. B. mit Spring) ist Dependency Injection oft an ein schwergewichtiges Framework mit "DI-Container" gebunden, der automatisch entscheidet, welche konkrete Implementierung wo eingesetzt wird. In Python reicht dank dynamischer Typisierung und Duck Typing in den allermeisten Fällen **"Poor Man's Dependency Injection"**: ganz normale Konstruktor-Parameter wie oben, ohne jedes Framework. DI-Container-Bibliotheken (z. B. `dependency-injector`) existieren, lohnen sich aber meist erst bei sehr großen Anwendungen mit vielen, tief verschachtelten Abhängigkeiten.

## Beispiel: Testbarkeit durch ein Test-Double

```python
class FakeWriter:
    """Test-Double: sammelt die Aufrufe nur im Speicher, statt echte Dateien zu schreiben."""
    def __init__(self):
        self.written: list[tuple[str, list]] = []

    def write(self, path: str, recommendations: list[tuple[str, float]]) -> None:
        self.written.append((path, recommendations))


def test_calculate_and_export():
    fake_writer = FakeWriter()
    calculator = PriceRecommendationCalculator(writer=fake_writer)
    calculator.calculate_and_export([DigitalProduct("EBOOK-001", 9.99, "single-user")], "out.csv")

    assert fake_writer.written == [("out.csv", [("EBOOK-001", 9.99)])]   # kein echtes Dateisystem nötig!
```

Das ist die praktische Umsetzung dessen, was wir im Separation-of-Concerns-Kapitel als Vorteil angekündigt hatten: Weil `PriceRecommendationCalculator` seine Abhängigkeit nur über die `RecommendationWriter`-Schnittstelle kennt, lässt sich der Test komplett ohne echtes I/O schreiben.

## Kurze Abgrenzung: Dependency Injection vs. Dependency Inversion Principle

Leicht zu verwechseln, aber unterschiedliche Ebenen: Das **Dependency Inversion Principle** (das "D" in SOLID) ist ein **Design-Prinzip**: "Module sollen von Abstraktionen abhängen, nicht von konkreten Implementierungen." **Dependency Injection** ist die **Technik/das Muster**, mit dem man dieses Prinzip in der Praxis umsetzt (die Abstraktion — z. B. `RecommendationWriter` — wird injiziert, statt dass die abhängige Klasse selbst eine konkrete Implementierung anfordert). Kurz: DIP ist das *Was/Warum*, DI ist das *Wie*.

# dunder Methoden & Dataclasses

## Weitere wichtige dunder Methoden (Vertiefung zu den Antworten)

`__init__`, `__repr__`/`__str__` und Operator-Overloading-Dunder (`__add__`, `__eq__`, `__lt__`) haben wir bereits in den [[Antworten#Dunder Methoden|Antworten]] behandelt. Hier zwei weitere, sehr gebräuchliche Gruppen:

**Container-Verhalten** (`__len__`, `__getitem__`, `__iter__`) — damit eine eigene Klasse sich wie eine eingebaute Sammlung verhält:

```python
class PriceableUnitCollection:
    def __init__(self, units: list[PriceableUnit]):
        self._units = units

    def __len__(self) -> int:
        return len(self._units)

    def __iter__(self):
        return iter(self._units)

    def __getitem__(self, index: int) -> PriceableUnit:
        return self._units[index]


collection = PriceableUnitCollection([ebook, book])
print(len(collection))          # 2 - nutzt __len__
for unit in collection:         # nutzt __iter__
    print(unit.unit_id)
print(collection[0])            # nutzt __getitem__
```

**Context Manager** (`__enter__`/`__exit__`) — ermöglicht die Nutzung mit `with`, z. B. um sicherzustellen, dass Ressourcen (Dateien, Verbindungen) garantiert wieder freigegeben werden, selbst wenn im Block ein Fehler auftritt.

## Stolperfalle: `__eq__` ohne `__hash__`

Definierst du `__eq__` selbst, setzt Python automatisch `__hash__` auf `None` — die Instanz wird dadurch **unhashable** (kann nicht mehr als Dict-Key oder in ein `set` gelegt werden), es sei denn, du definierst `__hash__` explizit mit:

```python
class PriceableUnit:
    def __init__(self, unit_id: str):
        self.unit_id = unit_id

    def __eq__(self, other) -> bool:
        return isinstance(other, PriceableUnit) and self.unit_id == other.unit_id

    # Ohne diese Zeile: TypeError: unhashable type, sobald man z. B. {unit1, unit2} bilden will
    def __hash__(self) -> int:
        return hash(self.unit_id)
```

## Dataclasses: Boilerplate für Datencontainer-Klassen automatisch generieren

Bereits in den [[Antworten#Decorators & Libraries für Klassenprogrammierung „under the hood"|Antworten]] als Stichwort angekündigt: `@dataclass` generiert `__init__`, `__repr__` und `__eq__` automatisch aus type-annotierten Klassenattributen:

```python
from dataclasses import dataclass, field

@dataclass
class PriceableUnit:
    unit_id: str
    base_price: float
    applied_discount_codes: list[str] = field(default_factory=list)   # siehe unten!

    def calculate_price_recommendation(self) -> float:   # eigene Methoden bleiben ganz normal möglich
        return round(self.base_price, 2)


a = PriceableUnit("SKU-001", 19.99)
print(a)                                    # PriceableUnit(unit_id='SKU-001', base_price=19.99, applied_discount_codes=[])
                                             # __repr__ automatisch generiert
print(a == PriceableUnit("SKU-001", 19.99)) # True - __eq__ automatisch generiert, vergleicht alle Felder
```

`field(default_factory=list)` löst dabei **exakt dasselbe Problem**, das wir schon bei mutable Klassenattributen und mutable default arguments gesehen haben: Ein direktes `applied_discount_codes: list[str] = []` als Klassenattribut-Default würde (genau wie bei normalen Klassen) zwischen allen Instanzen geteilt werden — `dataclasses` verbietet das sogar explizit mit einer Fehlermeldung und verlangt stattdessen eine `default_factory` (eine Funktion, die bei jeder neuen Instanz frisch aufgerufen wird, um einen eigenen, unabhängigen Wert zu erzeugen).

Zwei nützliche Parameter des Decorators:

- **`@dataclass(frozen=True)`**: macht Instanzen unveränderlich — jeder Zuweisungsversuch nach der Erzeugung (`a.base_price = 5`) wirft einen `FrozenInstanceError`. Praktisch für Kapselung, wenn ein Objekt nach der Erzeugung garantiert konstant bleiben soll.
- **`@dataclass(order=True)`**: generiert zusätzlich `__lt__`, `__le__`, `__gt__`, `__ge__` basierend auf der Feld-Reihenfolge — vergleichbar mit dem, was `functools.total_ordering` (siehe [[Antworten#Decorators & Libraries für Klassenprogrammierung „under the hood"|Antworten]]) manuell ermöglicht, hier aber vollautomatisch.

## Wann eignen sich Dataclasses — und wann eher nicht?

Dataclasses eignen sich gut für Klassen, deren Hauptzweck das **Halten von Daten** ist (mit optional ein paar Methoden obendrauf, wie `calculate_price_recommendation()` oben — eine Dataclass ist nicht "nur Daten ohne Verhalten"). Braucht die Klasse dagegen aufwendige Validierung/Logik direkt bei der Erzeugung (mehr als das, was ein einfaches `__post_init__` abdeckt) oder soll der Zugriff auf einzelne Felder unterschiedlich kontrolliert werden (siehe Kapselungs-Kapitel, `@property` mit individueller Setter-Validierung pro Feld), ist eine normale Klasse mit von Hand geschriebenem `__init__` oft die klarere Wahl.

## Randnotiz: statische Methoden (Kontrollfrage aus dem Leitfaden)

Der Leitfaden hebt explizit hervor: *"Was sind „statische" Methoden? Wie, wann und warum nutzt man sie?"* — das haben wir bereits ausführlich in den [[Antworten#Klassenmethoden vs. Instanzmethoden vs. Static Methods|Antworten]] beantwortet: `@staticmethod` markiert eine Methode, die thematisch zu einer Klasse gehört (Namespace/Organisation), aber weder auf `self` (die Instanz) noch auf `cls` (die Klasse selbst, siehe `@classmethod`) zugreift — im Grunde eine ganz normale Funktion, die nur "der Ordnung halber" im Klassenkörper steht. Genutzt z. B. für reine Hilfsberechnungen ohne eigenen Zustand (siehe `PercentageDiscount`/`PriceRecommendationCalculator` weiter oben, die bewusst `@staticmethod` verwenden, weil sie keinen Instanzzustand brauchen).

# Objektorientierung

Ein Objekt bündelt **Zustand** (Attribute) und **Verhalten** (Methoden), die auf diesem Zustand arbeiten, in einer Einheit — statt Daten und die Funktionen darauf lose nebeneinander zu halten (prozeduraler Stil). Vorteile: natürliche Modellierung der Realität, Kapselung von Komplexität, Wiederverwendbarkeit über Vererbung/Polymorphie, bessere Wartbarkeit und klarere Verantwortlichkeiten. In Python ist ohnehin (fast) alles ein Objekt — auch Zahlen und Funktionen.

→ [[1.1 OOP - Vertiefung#Objektorientierung|mehr dazu (Prozedural-vs-OOP-Vergleich, Python-Objektmodell)]]

# Klassen

Eine **Klasse** ist der Bauplan, eine **Instanz** ein konkretes Objekt danach. `__init__` setzt den Anfangszustand, `self` ist der (Konventions-, kein Keyword-)Verweis auf die jeweilige Instanz. Wichtigste Stolperfalle: **Instanzattribute** (in `__init__` via `self.x`) gehören jeder Instanz einzeln, **Klassenattribute** (im Klassenkörper) werden von allen Instanzen geteilt — besonders gefährlich bei *veränderlichen* Klassenattributen (Listen/Dicts), die versehentlich global geteilt mutiert werden. Introspection (`type()`, `isinstance()`, `__dict__`, `dir()`) hilft, das zur Laufzeit nachzuvollziehen.

→ [[1.1 OOP - Vertiefung#Klassen|mehr dazu (Instanz- vs. Klassenattribute, mutable-Default-Falle)]]

# Vererbung

Vererbung modelliert eine **„ist-ein"-Beziehung**: Eine Subklasse übernimmt Attribute/Methoden einer Basisklasse und kann sie erweitern oder überschreiben. `super().__init__(...)` vermeidet Code-Duplikation bei der Initialisierung; `super().methode()` erweitert (statt ersetzt) eine überschriebene Methode. Die **Method Resolution Order (MRO)** bestimmt, welche Implementierung zur Laufzeit gewinnt. Python erlaubt Mehrfachvererbung (v. a. sparsam für **Mixins** sinnvoll). Faustregel **„favor composition over inheritance"**: Eine „hat-ein"-Beziehung (z. B. ein Rabattmechanismus) gehört als eigenständiger Baustein per **Komposition** eingebunden, nicht per Vererbung.

→ [[1.1 OOP - Vertiefung#Vererbung|mehr dazu (super(), MRO, Mehrfachvererbung, Komposition-Beispiel)]]
→ [[Vererbung und Polymorphie - Tiefenperspektive|noch tiefer (C3-Linearisierung im Detail, warum super() nicht „die Elternklasse" ist, __init_subclass__, virtuelle Subklassen, Liskov Substitution)]]

# Polymorphie

Objekte unterschiedlicher Klassen lassen sich über **dieselbe Schnittstelle** ansprechen, obwohl jede ihre eigene Implementierung mitbringt — aufrufender Code muss den konkreten Typ nicht kennen. Python kennt zwei Wege: **nominal** über eine gemeinsame Basisklasse (Vererbung + Method Overriding) und **strukturell** über **Duck Typing** (keine gemeinsame Basisklasse nötig, nur dieselbe Methode). Auch **Operator Overloading** (`__add__`, `__eq__`, …) ist eine Form von Polymorphie (Ad-hoc-Polymorphie).

→ [[1.1 OOP - Vertiefung#Polymorphie|mehr dazu (Duck Typing, Protocol, functools.singledispatch)]]
→ [[Vererbung und Polymorphie - Tiefenperspektive|noch tiefer (kooperative Mehrfachvererbung, MRO-Mechanik hinter der Polymorphie)]]

# Kapselung

Zustand + Verhalten werden gebündelt **und** der Zugriff auf internen Zustand kontrolliert, damit ein Objekt seine eigenen Invarianten selbst durchsetzen kann. Python hat **kein echtes `private`** — nur Konventionen: `_attribut` (Absicht: intern) und `__attribut` (Name Mangling, primär zur Vermeidung von Namenskollisionen bei Vererbung). Zentrales Werkzeug: **`@property`** erlaubt Validierung/berechnete, teils read-only Attribute, ohne die öffentliche Schnittstelle zu ändern. `functools.cached_property` berechnet einmalig und cached danach pro Instanz (Vorsicht: kein automatisches Invalidieren bei Änderung der Eingabedaten).

→ [[1.1 OOP - Vertiefung#Kapselung|mehr dazu (@property, cached_property, Name Mangling)]]

# Abstraktion

Abstraktion ist eine **Design-Entscheidung**: Was muss ein Nutzer eines Konzepts überhaupt wissen, welche Details sind irrelevant? Abgrenzung zu Kapselung (Kontrollfrage!): Abstraktion beantwortet das **WAS**, Kapselung das **WIE** (Mechanismus). Python setzt Abstraktion technisch um über **abstrakte Basisklassen** (`abc`-Modul, `@abstractmethod` — Instanziierung wirft `TypeError`, solange etwas nicht implementiert ist) und über **`typing.Protocol`** als strukturelles Pendant zu Java-Interfaces. Ein Interface ist ein reiner Vertrag ohne Zustand/Implementierung; eine abstrakte Klasse darf beides mitbringen. Gegen Interfaces/Protocols zu programmieren statt gegen konkrete Klassen hält Code austauschbar (Bezug: Dependency Inversion, Loose Coupling).

→ [[1.1 OOP - Vertiefung#Abstraktion|mehr dazu (abc/@abstractmethod, Interface vs. abstrakte Klasse, Autofahren-Analogie)]]

# Information Hiding

Das übergeordnete **Design-Prinzip**, das erklärt, *warum* Abstraktion und Kapselung betrieben werden: Implementierungsdetails werden verborgen, damit sie sich ändern lassen, **ohne Aufrufer zu brechen** (z. B. interne Liste gegen ein Set tauschen, ohne die öffentliche Schnittstelle anzufassen). Ergebnis: weniger Kopplung, weniger kognitive Last. Gilt nicht nur auf Klassenebene, sondern auch auf Modul- (`_internal.py`) und Paketebene (`__all__`). Dreiklang-Merksatz: Abstraktion = WAS, Kapselung = WIE, Information Hiding = WARUM.

→ [[1.1 OOP - Vertiefung#Information Hiding|mehr dazu (list-zu-set-Beispiel, Modul-/Paketebene)]]

# Separation of Concerns

Unterschiedliche Belange (Business-Logik, I/O, Präsentation, …) gehören in getrennte, unabhängige Bausteine statt verwoben in einem Codeteil — typisches Beispiel: Preisberechnung (Business-Logik) getrennt von CSV-Export (I/O), z. B. als Schichtenarchitektur (Präsentation / Business-Logik / Datenzugriff). SoC ist das **allgemeinere** Prinzip; das Single Responsibility Prinzip ist SoC angewendet auf eine einzelne Klasse. Sauber getrennte Concerns lassen sich leichter isoliert testen (Brücke zu Dependency Injection).

→ [[1.1 OOP - Vertiefung#Separation of Concerns|mehr dazu (Business-Logik/I/O-Beispiel, Schichtenarchitektur)]]

# Single Responsibility Prinzip

„Eine Klasse sollte **genau einen Grund** haben, sich zu ändern" (Robert C. Martin) — gemeint ist eine fachliche **Änderungsachse**, nicht „eine Methode pro Klasse". Erkennungsheuristiken: der **„Und"-Test** (Verantwortung nur mit „und" beschreibbar?), **God Object** als Endstadium wiederholter Verletzungen, sowie Änderungen aus fachlich unabhängigen Gründen in der Versionshistorie.

# Loose Coupling vs. hohe Kohäsion

Zwei unterschiedliche Metriken guten Klassendesigns: **Kopplung** misst Abhängigkeit *zwischen* Klassen (Ziel: lose Kopplung, z. B. über ein `Protocol` statt eine konkrete Klasse zu kennen), **Kohäsion** misst Zusammengehörigkeit *innerhalb* einer Klasse (Ziel: hohe Kohäsion — alle Methoden nutzen denselben Zustand für denselben Zweck; das Gegenteil ist eine „Utils"-Klasse mit thematisch unabhängigen Methoden). Faustregel: **„loose coupling, high cohesion"** — hohe Kohäsion begünstigt fast automatisch SRP, lose Kopplung macht Klassen unabhängig änderbar/testbar/austauschbar.

→ [[1.1 OOP - Vertiefung#Loose Coupling vs. hohe Kohäsion (strong cohesion)|mehr dazu (Protocol-Beispiel, Utils-Antipattern)]]
→ [[SOLID-Prinzipien#Interface Segregation Principle (ISP)|noch tiefer (Interface Segregation Principle — schmale Schnittstellen als Fortsetzung von Loose Coupling)]]

# Open/Closed Prinzip

Bausteine sollen **offen für Erweiterung, geschlossen für Veränderung** sein: neues Verhalten möglichst additiv hinzufügen, statt bewährten, getesteten Code zu riskieren. Klassische Verletzung: eine wachsende `if isinstance(...): ... elif ...`-Kette, die bei jeder neuen Variante angefasst werden muss. Auflösung über Polymorphie: jede Subklasse implementiert die Methode selbst, aufrufender Code bleibt unverändert. Kein Dogma — nur für **absehbare** Erweiterungsachsen sinnvoll, sonst droht „Speculative Generality".

→ [[1.1 OOP - Vertiefung#Open/Closed Prinzip|mehr dazu (if/elif-Antipattern, Polymorphie-Auflösung)]]

# Clean Code

Code, der leicht zu **lesen, verstehen und ändern** ist — weil Code deutlich öfter gelesen als geschrieben wird. Der Dachbegriff, unter dem viele bereits behandelte Prinzipien zusammenlaufen: aussagekräftige Namen, kleine Funktionen mit einer Aufgabe (SRP auf Funktionsebene), DRY, konsistente Formatierung, sparsame *Warum*-Kommentare, saubere Fehlerbehandlung, keine Magic Numbers/Strings.

→ [[1.1 OOP - Vertiefung#Clean Code (Grundzüge)|mehr dazu (unclean-vs-clean-Beispiel, Querverweis auf SRP/SoC/Kapselung/Open-Closed)]]

# Dependency Injection

Eine Klasse fordert ihre Abhängigkeiten nicht selbst an, sondern bekommt sie **von außen hereingereicht** — meist per **Constructor Injection**, seltener per Setter- oder Method-Injection. Löst vor allem Testbarkeit (echte Abhängigkeit im Test durch ein Test-Double ersetzbar) und lose Kopplung. In Python meist ohne DI-Framework als „Poor Man's DI" über normale Konstruktor-Parameter. Abgrenzung: **Dependency Inversion Principle** ist das Design-Prinzip (Module sollen von Abstraktionen abhängen), **Dependency Injection** die Technik, die es umsetzt.

# dunder Methoden & Dataclasses

Weitere wichtige dunder Methoden: Container-Verhalten (`__len__`, `__getitem__`, `__iter__`) und Context Manager (`__enter__`/`__exit__`). Stolperfalle: Eigenes `__eq__` setzt `__hash__` automatisch auf `None` (unhashable), außer man definiert `__hash__` explizit mit. **`@dataclass`** generiert `__init__`/`__repr__`/`__eq__` automatisch aus typannotierten Attributen; mutable Defaults brauchen zwingend `field(default_factory=...)` (dieselbe Ursache wie bei mutable Klassenattributen/Default-Argumenten). `frozen=True` macht Instanzen unveränderlich, `order=True` generiert Vergleichsoperatoren. Dataclasses eignen sich für Datencontainer, nicht für Klassen mit aufwendiger Validierungslogik pro Feld.

→ [[1.1 OOP - Vertiefung#dunder Methoden & Dataclasses|mehr dazu (Container-/Context-Manager-Dunder, dataclass-Parameter)]]

# RDBMS insbesondere PostgreSQL

## Vom Datei-Chaos zur Datenbank — warum überhaupt?

In unserer [[1.2 Relationale Datenbanken & ORM - Leitfaden#Übungsaufgabe|Übungsaufgabe]] halten wir die Daten aktuell rein datei-gestützt (CSV) — genau das, was wir aus Kapitel [[1.1 OOP - Leitfaden|1.1]] mitgebracht haben. Das funktioniert für einen einzelnen Prozess, der eine Datei liest und eine neue schreibt. Sobald aber mehrere Nutzer/Prozesse *gleichzeitig* auf dieselben Daten zugreifen, Teilmengen effizient abgefragt werden sollen oder garantiert werden muss, dass keine halben/kaputten Datenstände entstehen, stößt „einfach eine Datei" schnell an harte Grenzen:

- **Nebenläufigkeit**: Was passiert, wenn zwei Prozesse gleichzeitig dieselbe CSV schreiben? Im besten Fall gewinnt einer, im schlechtesten ist die Datei danach korrupt. Es gibt keine eingebaute Sperr-/Koordinationslogik.
- **Suchen/Filtern**: „Gib mir alle Priceable Units mit `occupancy > 0.8`" bedeutet bei einer Datei: *die ganze Datei einlesen und in Python durchiterieren*. Bei Millionen Zeilen wird das langsam und speicherhungrig.
- **Integrität**: Nichts hindert einen daran, in eine CSV eine Zeile mit negativem Preis, fehlender ID oder einem Verweis auf ein nicht existierendes Produkt zu schreiben. Die Regeln leben nur im Anwendungscode — und nur solange *jeder* Schreibpfad sie einhält.
- **Beziehungen**: Ein Produkt hat viele Buchungen, eine Buchung gehört zu einem Kunden … Solche Verknüpfungen über mehrere CSV-Dateien hinweg konsistent zu halten, ist Handarbeit und fehleranfällig.

Ein **Datenbank-Management-System (DBMS)** ist genau die Software, die diese Probleme als *Infrastruktur* löst, statt sie in jeder Anwendung neu zu erfinden.

## Begriffe sauber trennen: Datenbank, DBMS, RDBMS

Diese drei Begriffe werden umgangssprachlich oft synonym benutzt, meinen aber unterschiedliche Dinge:

| Begriff | Bedeutung |
|---|---|
| **Datenbank (database)** | Die eigentliche, strukturierte Sammlung von Daten (die Tabellen und ihr Inhalt). |
| **DBMS** | Die *Software*, die Datenbanken verwaltet — nimmt Anfragen entgegen, sorgt für Nebenläufigkeit, Persistenz, Zugriffsrechte, Backups. (z. B. PostgreSQL, MySQL, SQLite, Oracle) |
| **RDBMS** | Ein DBMS, das dem **relationalen Modell** folgt: Daten liegen in Tabellen (Relationen), die über Werte miteinander in Beziehung stehen. PostgreSQL, MySQL, SQLite, SQL Server, Oracle sind allesamt RDBMS. |

Man spricht also z. B. korrekt: „PostgreSQL (das RDBMS) verwaltet die Datenbank `pricing`, die u. a. die Tabelle `priceable_units` enthält."

## Das relationale Modell — das „R" in RDBMS

Das relationale Modell (Edgar F. Codd, 1970) ist das theoretische Fundament. Seine Kernidee: Daten werden als **Relationen** (umgangssprachlich: Tabellen) dargestellt, und Beziehungen zwischen Daten werden **über Werte** hergestellt — nicht über Zeiger oder Speicheradressen. Das klingt simpel, ist aber der Grund für die enorme Flexibilität und mathematische Sauberkeit relationaler Datenbanken.

Die Vokabeln (formaler Begriff ↔ Praxisbegriff):

| Formal (Theorie) | Praxis (SQL) | Bedeutung |
|---|---|---|
| **Relation** | Tabelle | Eine Menge gleich strukturierter Datensätze, z. B. alle Produkte. |
| **Tupel** | Zeile (row) | Ein einzelner Datensatz, z. B. ein konkretes Produkt. |
| **Attribut** | Spalte (column) | Eine benannte Eigenschaft mit festem Datentyp, z. B. `base_price`. |
| **Domäne** | Datentyp der Spalte | Der erlaubte Wertebereich eines Attributs, z. B. `NUMERIC(10,2)`, `TEXT`, `DATE`. |
| **Grad (degree)** | Anzahl Spalten | Wie viele Attribute die Relation hat. |
| **Kardinalität** | Anzahl Zeilen | Wie viele Datensätze aktuell enthalten sind. |

Eine Tabelle für unsere Übungsaufgabe könnte konzeptionell so aussehen:

**`priceable_units`**

| product_id (PK) | calendar_date | base_price | bookable_units | booked_units |
|---|---|---|---|---|
| P-001 | 2027-04-22 | 19.99 | 3 | 2 |
| P-002 | 2027-04-22 | 29.99 | 5 | 0 |

Wichtige Eigenschaften, die aus dem relationalen Modell folgen:

1. **Jede Zeile ist eindeutig identifizierbar** über einen **Primärschlüssel (Primary Key, PK)** — hier `product_id` (bzw. genauer die Kombination aus Produkt und Datum, dazu später bei *Datenbankdesign*). Kein Datensatz existiert ohne eindeutige Identität.
2. **Jede Spalte hat einen festen Datentyp (Domäne)**. `base_price` ist z. B. eine Zahl mit zwei Nachkommastellen — der Versuch, dort `"kostenlos"` zu speichern, wird vom RDBMS abgelehnt. Das ist Datenintegrität *auf Infrastrukturebene*, nicht nur im Python-Code.
3. **Die Reihenfolge von Zeilen und Spalten ist logisch bedeutungslos.** Eine Relation ist eine *Menge*. Willst du eine bestimmte Reihenfolge, forderst du sie beim Abfragen explizit an (`ORDER BY`). Man verlässt sich nie auf „die Zeile steht an dritter Stelle".
4. **Beziehungen laufen über Werte.** Eine Buchung verweist auf ihr Produkt, indem sie dessen `product_id` als **Fremdschlüssel (Foreign Key)** speichert — nicht über einen Speicherzeiger. (Details bei *Foreign Keys* und *Beziehungstypen*.)

> Am Rande — **Atomarität der Werte**: In der klassischen relationalen Lehre soll jede Zelle einen *einzelnen, unteilbaren* Wert enthalten (keine Listen in einer Zelle). Das ist die Basis der 1. Normalform. PostgreSQL weicht das mit Array- und JSON-Typen pragmatisch auf — aber das ist bewusst eine Ausnahme, kein Standardvorgehen. Mehr dazu bei *Normalisierung*.

## Relational vs. nicht-relational (NoSQL) — Kontrollfrage

> **Kontrollfrage aus dem Leitfaden:** *Wie unterscheidet sich eine relationale von einer nicht-relationalen Datenbank?*

**Relationale Datenbanken** speichern Daten in Tabellen mit einem **festen, im Voraus definierten Schema** (welche Spalten, welche Datentypen, welche Beziehungen). Sie garantieren starke Konsistenz über **ACID**-Transaktionen (dazu ein eigener Abschnitt später) und werden über **SQL** abgefragt. Beziehungen zwischen Tabellen sind ein erstklassiges Konzept (Foreign Keys, Joins).

**Nicht-relationale (NoSQL) Datenbanken** sind ein Sammelbegriff für sehr unterschiedliche Ansätze, die bewusst *nicht* dem tabellarischen Modell folgen. Die vier gängigen Familien:

| NoSQL-Typ | Datenmodell | Beispiele | Typischer Einsatz |
|---|---|---|---|
| **Document Stores** | JSON-artige Dokumente, Schema flexibel | MongoDB, CouchDB | Heterogene, verschachtelte Daten ohne festes Schema |
| **Key-Value Stores** | Schlüssel → Wert, extrem simpel & schnell | Redis, DynamoDB | Caching, Sessions, Zähler |
| **Wide-Column Stores** | Spaltenfamilien, für riesige Datenmengen | Cassandra, HBase | Sehr große, verteilte Schreiblasten |
| **Graph-Datenbanken** | Knoten + Kanten | Neo4j | Stark vernetzte Daten (soziale Netze, Empfehlungen) |

Die zentralen Unterschiede auf den Punkt gebracht:

| Aspekt | Relational (SQL) | Nicht-relational (NoSQL) |
|---|---|---|
| **Schema** | Fest, vorab definiert (*schema-on-write*) | Flexibel / dynamisch (*schema-on-read*) |
| **Beziehungen** | Kernkonzept (Foreign Keys, Joins) | Oft in der Anwendung gelöst; Daten häufig dupliziert/verschachtelt |
| **Abfragesprache** | SQL (weitgehend standardisiert) | Produktspezifisch (Mongo Query Language, …) |
| **Konsistenz** | Stark, ACID | Oft eventual consistency (Fokus auf Verfügbarkeit/Skalierung) |
| **Skalierung** | Traditionell vertikal (stärkere Maschine); horizontal aufwendiger | Oft von Grund auf horizontal (viele Maschinen) |
| **Stärke bei** | Strukturierten Daten mit klaren Beziehungen & Integritätsanforderungen | Riesigen, unstrukturierten/wechselnden Datenmengen, hoher Schreiblast |

**Kernaussage:** Es gibt kein „besser" — es ist eine Frage des Anwendungsfalls. Für unsere Übungsaufgabe (Produkte, Preise, Buchungen mit klaren Beziehungen und Integritätsregeln wie „ein Preis ist nie negativ", „eine Buchung gehört zu einem existierenden Produkt") ist ein **relationales** System die natürliche Wahl. Man wählt NoSQL bewusst dort, wo dessen Stärken (flexibles Schema, extreme horizontale Skalierung) tatsächlich gebraucht werden — und nimmt dafür in Kauf, dass man Konsistenz und Beziehungen mehr selbst in der Hand hat.

## Was ist PostgreSQL — und warum ist es so beliebt? Kontrollfrage

> **Kontrollfrage aus dem Leitfaden:** *Wieso ist PostgreSQL die beliebteste Datenbanklösung?*

**PostgreSQL** (kurz „Postgres") ist ein freies, quelloffenes RDBMS mit über 35 Jahren Entwicklungsgeschichte. Es gilt als das ausgereifteste Open-Source-RDBMS und wird in Entwickler-Umfragen (z. B. Stack Overflow) seit Jahren als eine der beliebtesten Datenbanken geführt. Die Gründe:

1. **Open Source & kostenlos, ohne Vendor-Lock-in.** Keine Lizenzkosten, sehr permissive Lizenz (PostgreSQL License), riesige Community. Man ist nicht an einen Hersteller gebunden — anders als bei Oracle oder SQL Server.
2. **Extrem hohe Standardkonformität.** Postgres hält sich sehr eng an den SQL-Standard. Gelerntes SQL überträgt sich dadurch gut, und Verhalten ist vorhersehbar.
3. **Voll ACID-konform & zuverlässig.** Starke Transaktionsgarantien (siehe späterer *ACID*-Abschnitt) — man vertraut ihm auch geschäftskritische Daten an.
4. **„Objekt-relational" & enorm erweiterbar.** Postgres ist streng genommen ein *ORDBMS* (object-relational): Man kann eigene Datentypen, Operatoren und Funktionen definieren. Über Extensions wird es massiv erweitert — das prominenteste Beispiel heute ist **`pgvector`** für KI-/Embedding-Anwendungen; klassisch **PostGIS** für Geodaten.
5. **Reicher Funktionsumfang „out of the box".** Native Typen für `JSONB` (indizierbares, binäres JSON — relationale *und* dokumentorientierte Arbeitsweise in einem System), Arrays, `UUID`, Volltextsuche, Window Functions, CTEs, verschiedene Index-Typen (B-Tree, GIN, GiST, …) u. v. m.
6. **Nebenläufigkeit ohne unnötiges Blockieren (MVCC).** *Multi-Version Concurrency Control*: Lesende blockieren keine Schreibenden und umgekehrt — jeder sieht einen konsistenten Snapshot. Das macht Postgres unter paralleler Last performant und ist ein wesentlicher Grund für seinen Ruf.
7. **Robustes Ökosystem.** Erstklassige Anbindung an Python (`psycopg`, dazu **SQLAlchemy** im letzten Abschnitt dieses Kapitels), an alle großen Frameworks, plus Managed-Angebote aller Cloud-Provider (AWS RDS/Aurora, Google Cloud SQL, Azure).

Kurz: PostgreSQL trifft den „Sweet Spot" aus **kostenlos**, **standardkonform**, **zuverlässig** und **funktionsreich/erweiterbar** — und ist genau deshalb für unsere Übungsaufgabe die vorgegebene Wahl.

## Ein kurzer Blick auf die Praxis

Damit die Begriffe nicht abstrakt bleiben — so sieht das Anlegen und Befüllen einer Tabelle in PostgreSQL grob aus (die SQL-Syntax vertiefen wir im nächsten Stichwort *SQL*, hier nur zur Veranschaulichung):

```sql
-- Eine Relation (Tabelle) definieren: Attribute (Spalten) + ihre Domänen (Datentypen)
CREATE TABLE priceable_units (
    product_id      TEXT        NOT NULL,          -- Attribut mit Domäne TEXT
    calendar_date   DATE        NOT NULL,
    base_price      NUMERIC(10, 2) NOT NULL,       -- Geldbetrag: exakt, nicht FLOAT!
    bookable_units  INTEGER     NOT NULL,
    booked_units    INTEGER     NOT NULL DEFAULT 0,
    PRIMARY KEY (product_id, calendar_date)        -- eindeutige Identität je Zeile
);

-- Ein Tupel (Zeile) einfügen
INSERT INTO priceable_units (product_id, calendar_date, base_price, bookable_units, booked_units)
VALUES ('P-001', '2027-04-22', 19.99, 3, 2);

-- Abfragen: Filtern passiert im RDBMS, nicht in Python
SELECT product_id, base_price
FROM priceable_units
WHERE booked_units > 0;
```

Zwei Dinge sind hier schon zentral und tauchen als eigene Stichworte wieder auf:

- **`NUMERIC(10,2)` statt `FLOAT` für Geld.** Fließkommazahlen (`FLOAT`/`REAL`) können `19.99` nicht exakt darstellen (Rundungsfehler). Für Beträge nimmt man **immer** einen exakten Dezimaltyp (`NUMERIC`/`DECIMAL`). Das entspricht genau der Sorgfalt, die wir in [[1.1 OOP - Vertiefung#Kapselung|1.1]] mit Invarianten wie „Preis ist nie negativ" begonnen haben — nur jetzt auf Datenbankebene.
- **`NOT NULL`, `DEFAULT`, `PRIMARY KEY`** sind bereits **Constraints** — Regeln, die das RDBMS *selbst* durchsetzt (eigenes Stichwort später). Der große Gewinn: Die Regel gilt für *jeden* Schreibzugriff, egal aus welchem Code er kommt — nicht nur, wenn der Python-Code brav mitspielt.

# SQL

## Was ist SQL — und was heißt „deklarativ"?

**SQL** (Structured Query Language) ist die standardisierte Sprache, um mit einem relationalen Datenbanksystem zu „reden" — Daten definieren, einfügen, abfragen und verändern. Ausgesprochen wird es „S-Q-L" oder „Sequel". Der SQL-Standard (ISO) wird von den einzelnen RDBMS jeweils leicht unterschiedlich umgesetzt — man spricht von **Dialekten** (PostgreSQL, MySQL, SQLite, … weichen in Details voneinander ab). Der Kern (das, was wir hier lernen) ist aber über alle Dialekte hinweg fast identisch, und PostgreSQL hält sich besonders eng an den Standard.

Der zentrale Denkwechsel gegenüber Python: SQL ist **deklarativ**, nicht imperativ.

- **Imperativ** (Python, wie bisher): Du beschreibst *wie* etwas Schritt für Schritt passieren soll — „öffne die Datei, iteriere über jede Zeile, prüfe eine Bedingung, sammle Treffer in einer Liste".
- **Deklarativ** (SQL): Du beschreibst *was* du haben willst — „gib mir alle Produkte mit `booked_units > 0`, sortiert nach Preis". *Wie* das effizient beschafft wird (welcher Index genutzt wird, in welcher Reihenfolge Tabellen gelesen werden), entscheidet der **Query Planner** des RDBMS selbst.

```python
# Imperativ (Python): das WIE ausformuliert
result = []
for unit in all_units:
    if unit.booked_units > 0:
        result.append(unit)
result.sort(key=lambda u: u.base_price)
```

```sql
-- Deklarativ (SQL): nur das WAS
SELECT * FROM priceable_units
WHERE booked_units > 0
ORDER BY base_price;
```

Genau dieser Unterschied ist der Grund, warum eine Datenbank Abfragen über Millionen Zeilen so viel effizienter beantworten kann als handgeschriebener Schleifencode: Sie darf die Ausführung frei optimieren, weil du ihr nur das Ziel genannt hast, nicht den Weg.

## Die Teilsprachen von SQL (DDL, DML, DQL, DCL, TCL)

SQL wird üblicherweise in fünf Kategorien nach Zweck eingeteilt. Das ist keine Prüfungsspielerei — es hilft enorm, Befehle einzuordnen:

| Kürzel | Name | Zweck | Wichtigste Befehle |
|---|---|---|---|
| **DDL** | Data Definition Language | Struktur (Schema) definieren/ändern | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` |
| **DML** | Data Manipulation Language | Dateninhalt verändern | `INSERT`, `UPDATE`, `DELETE` |
| **DQL** | Data Query Language | Daten abfragen | `SELECT` |
| **DCL** | Data Control Language | Rechte vergeben/entziehen | `GRANT`, `REVOKE` |
| **TCL** | Transaction Control Language | Transaktionen steuern | `BEGIN`, `COMMIT`, `ROLLBACK` |

In diesem Abschnitt gehen wir DDL-Grundlagen, DML und vor allem DQL (`SELECT`) durch. **TCL** bekommt einen eigenen Abschnitt (*Transactions*), ebenso Themen, die auf `SELECT` aufbauen: *Joins und Unions*, *Views* und die verschiedenen *Constraints*.

> Konvention: SQL-Schlüsselwörter (`SELECT`, `FROM`, …) sind **case-insensitive**, werden aber per Konvention GROSS geschrieben, damit sie sich optisch von Tabellen-/Spaltennamen abheben. Jede Anweisung endet mit einem **Semikolon** `;`.

## DDL: Tabellen definieren

Bevor Daten hineinkommen, muss die Struktur stehen. Das kennen wir schon aus dem RDBMS-Abschnitt — hier etwas ausführlicher:

```sql
CREATE TABLE priceable_units (
    product_id      TEXT           NOT NULL,
    calendar_date   DATE           NOT NULL,
    base_price      NUMERIC(10, 2) NOT NULL,
    bookable_units  INTEGER        NOT NULL,
    booked_units    INTEGER        NOT NULL DEFAULT 0,
    PRIMARY KEY (product_id, calendar_date)
);
```

Nachträgliche Änderungen an einer bestehenden Tabelle laufen über `ALTER TABLE`:

```sql
ALTER TABLE priceable_units ADD COLUMN currency TEXT NOT NULL DEFAULT 'EUR';
ALTER TABLE priceable_units DROP COLUMN currency;
```

Und die ganze Tabelle löschen (Struktur + Daten!) mit `DROP TABLE priceable_units;`. Ein wichtiger, oft verwechselter Unterschied beim Leeren/Löschen:

- `DELETE FROM t;` — **DML**, entfernt zeilenweise (kann mit `WHERE` gefiltert werden, ist rückgängig machbar innerhalb einer Transaktion, löst Trigger aus).
- `TRUNCATE t;` — **DDL**, leert die ganze Tabelle in einem Rutsch (schneller bei großen Tabellen, kein `WHERE` möglich).
- `DROP TABLE t;` — **DDL**, entfernt die Tabelle *samt Struktur* — danach existiert sie nicht mehr.

## Die gängigsten PostgreSQL-Datentypen

Jede Spalte hat einen festen Typ (die *Domäne*). Ein Auszug der wichtigsten:

| Kategorie | Typen | Hinweis |
|---|---|---|
| **Ganzzahlen** | `SMALLINT`, `INTEGER`, `BIGINT` | `SERIAL`/`BIGSERIAL` = Auto-Inkrement (praktisch für künstliche IDs) |
| **Exakte Dezimalzahlen** | `NUMERIC(p, s)` / `DECIMAL(p, s)` | **Für Geld!** exakt, keine Rundungsfehler |
| **Fließkomma** | `REAL`, `DOUBLE PRECISION` | Nur für näherungsweise Wissenschafts-/Messwerte, **nicht** für Geld |
| **Text** | `TEXT`, `VARCHAR(n)`, `CHAR(n)` | In Postgres ist `TEXT` idiomatisch (kein Performance-Nachteil ggü. `VARCHAR`) |
| **Wahrheitswert** | `BOOLEAN` | `TRUE` / `FALSE` / `NULL` |
| **Datum/Zeit** | `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMPTZ` | `TIMESTAMPTZ` (mit Zeitzone) ist meist die richtige Wahl |
| **Eindeutige ID** | `UUID` | Global eindeutige Schlüssel |
| **Halbstrukturiert** | `JSONB`, Arrays | Postgres-Stärke; sparsam & bewusst einsetzen (vgl. Normalisierung) |

## DML: Daten einfügen, ändern, löschen

```sql
-- INSERT: neue Zeile(n) anlegen
INSERT INTO priceable_units (product_id, calendar_date, base_price, bookable_units, booked_units)
VALUES ('P-001', '2027-04-22', 19.99, 3, 2),
       ('P-002', '2027-04-22', 29.99, 5, 0);   -- mehrere Zeilen in einem Statement

-- UPDATE: bestehende Zeilen ändern - das WHERE ist entscheidend!
UPDATE priceable_units
SET booked_units = booked_units + 1
WHERE product_id = 'P-002' AND calendar_date = '2027-04-22';

-- DELETE: Zeilen entfernen
DELETE FROM priceable_units
WHERE product_id = 'P-001';
```

> ⚠️ **Die häufigste Katastrophe:** `UPDATE`/`DELETE` **ohne `WHERE`** betrifft *alle* Zeilen der Tabelle. `DELETE FROM priceable_units;` leert die komplette Tabelle. Immer erst mit einem `SELECT ... WHERE ...` prüfen, welche Zeilen betroffen wären, bevor man dieselbe `WHERE`-Klausel in ein `UPDATE`/`DELETE` übernimmt.

## DQL: `SELECT` — das Herzstück

`SELECT` ist der mit Abstand meistgenutzte und mächtigste Befehl. Die wichtigsten Klauseln in ihrer *geschriebenen* Reihenfolge:

```sql
SELECT   product_id, base_price          -- welche Spalten (Projektion)
FROM     priceable_units                 -- aus welcher Tabelle
WHERE    booked_units > 0                -- welche Zeilen (Filter, VOR Aggregation)
ORDER BY base_price DESC                 -- Sortierung
LIMIT    10;                             -- nur die ersten N Zeilen
```

Ein paar grundlegende Bausteine:

```sql
SELECT *              FROM priceable_units;   -- * = alle Spalten (in Ad-hoc-Abfragen ok,
                                              --     in Produktivcode besser Spalten explizit nennen)
SELECT DISTINCT calendar_date FROM priceable_units;   -- doppelte Werte entfernen
SELECT product_id AS produkt, base_price AS preis FROM priceable_units;  -- AS = Alias/Umbenennung
```

### `WHERE`: Zeilen filtern

Die `WHERE`-Klausel entscheidet Zeile für Zeile, ob sie ins Ergebnis kommt. Verfügbare Operatoren:

| Art | Operatoren / Beispiele |
|---|---|
| Vergleich | `=`, `<>` (ungleich), `<`, `<=`, `>`, `>=` |
| Logik | `AND`, `OR`, `NOT` |
| Bereich | `base_price BETWEEN 10 AND 30` |
| Mengenzugehörigkeit | `product_id IN ('P-001', 'P-002')` |
| Muster (Text) | `product_id LIKE 'P-%'` (`%` = beliebig viele Zeichen, `_` = genau eines); `ILIKE` = case-insensitive |
| NULL-Prüfung | `discount IS NULL`, `discount IS NOT NULL` |

### NULL und die dreiwertige Logik (wichtige Stolperfalle!)

`NULL` bedeutet in SQL **„unbekannt / kein Wert"** — es ist *nicht* dasselbe wie `0` oder ein leerer String `''`. Daraus folgt SQLs berüchtigte **dreiwertige Logik** (`TRUE`, `FALSE`, `UNKNOWN`):

```sql
-- Falsch gedacht: findet NICHT die Zeilen, bei denen discount NULL ist!
SELECT * FROM priceable_units WHERE discount = NULL;   -- liefert immer 0 Zeilen

-- Richtig:
SELECT * FROM priceable_units WHERE discount IS NULL;
```

Der Grund: Jeder Vergleich *mit* `NULL` (z. B. `discount = NULL`, `discount <> 5`) ergibt nicht `TRUE` oder `FALSE`, sondern `UNKNOWN` — und `WHERE` lässt nur Zeilen durch, deren Bedingung echt `TRUE` ist. Deshalb gibt es die eigenen Operatoren `IS NULL` / `IS NOT NULL`. Dieselbe Logik erklärt viele „warum fehlt diese Zeile im Ergebnis?"-Überraschungen — merk dir: **Mit `NULL` wird nie mit = verglichen.**

### Aggregatfunktionen und `GROUP BY`

Bisher haben wir Zeilen *gefiltert*. Oft will man Zeilen aber *zusammenfassen* — z. B. „wie viele Buchungen pro Produkt?". Das leisten **Aggregatfunktionen**:

| Funktion | Bedeutung |
|---|---|
| `COUNT(*)` | Anzahl Zeilen |
| `SUM(spalte)` | Summe |
| `AVG(spalte)` | Durchschnitt |
| `MIN(spalte)` / `MAX(spalte)` | Kleinster / größter Wert |

Ohne `GROUP BY` verdichten sie die *gesamte* Ergebnismenge auf eine einzige Zahl:

```sql
SELECT COUNT(*) AS anzahl, AVG(base_price) AS durchschnittspreis
FROM priceable_units;
```

Mit `GROUP BY` bildet man **Gruppen** und wendet die Aggregatfunktion pro Gruppe an:

```sql
-- Durchschnittspreis und Buchungssumme je Kalendertag
SELECT calendar_date,
       COUNT(*)          AS anzahl_produkte,
       AVG(base_price)   AS durchschnittspreis,
       SUM(booked_units) AS gesamt_buchungen
FROM priceable_units
GROUP BY calendar_date
ORDER BY calendar_date;
```

Faustregel: Jede Spalte in der `SELECT`-Liste muss entweder in `GROUP BY` stehen **oder** in einer Aggregatfunktion stecken — sonst wüsste die Datenbank nicht, welchen der vielen Werte einer Gruppe sie zeigen soll (PostgreSQL wirft dann sogar einen Fehler).

### `WHERE` vs. `HAVING` (Kontrollpunkt)

Beide filtern — aber an unterschiedlichen Stellen:

- **`WHERE`** filtert **einzelne Zeilen, bevor** gruppiert/aggregiert wird.
- **`HAVING`** filtert **ganze Gruppen, nachdem** aggregiert wurde (kann sich also auf Aggregatwerte beziehen).

```sql
-- Nur Tage, an denen der Durchschnittspreis über 25 liegt,
-- und dabei nur tatsächlich buchbare Produkte berücksichtigen:
SELECT calendar_date, AVG(base_price) AS durchschnittspreis
FROM priceable_units
WHERE bookable_units > 0            -- Zeilen-Filter VOR der Gruppierung
GROUP BY calendar_date
HAVING AVG(base_price) > 25         -- Gruppen-Filter NACH der Aggregation
ORDER BY durchschnittspreis DESC;
```

### Logische Ausführungsreihenfolge ≠ Schreibreihenfolge

Ein Aha-Moment, der viele SQL-Missverständnisse auflöst: SQL wird **anders ausgeführt, als es geschrieben wird**. Die logische Reihenfolge ist:

1. `FROM` (Tabelle(n) bereitstellen, ggf. Joins)
2. `WHERE` (Zeilen filtern)
3. `GROUP BY` (Zeilen zu Gruppen zusammenfassen)
4. `HAVING` (Gruppen filtern)
5. `SELECT` (Spalten auswählen/berechnen, Aliase entstehen erst hier)
6. `ORDER BY` (sortieren)
7. `LIMIT` (abschneiden)

Das erklärt zwei häufige Fehler:

- Warum man in `WHERE` **keinen Alias** aus der `SELECT`-Liste verwenden kann (`WHERE durchschnittspreis > 25` schlägt fehl) — der Alias existiert zu diesem Zeitpunkt logisch noch gar nicht, denn `SELECT` (Schritt 5) läuft *nach* `WHERE` (Schritt 2). In `ORDER BY` (Schritt 6, nach `SELECT`) darf man den Alias hingegen benutzen.
- Warum Aggregatbedingungen in `HAVING` statt `WHERE` gehören: `WHERE` läuft vor der Aggregation, die Aggregatwerte gibt es dort noch nicht.

# Datenbankdesign

## Was ist Datenbankdesign — und warum lohnt sich Sorgfalt?

**Datenbankdesign** (oder Datenmodellierung) ist der Schritt, in dem wir entscheiden, *welche* Tabellen es gibt, *welche* Spalten sie haben und *wie* sie miteinander verknüpft sind — **bevor** die erste Zeile Daten hineinkommt. Es ist das Fundament: Ein gutes Schema macht spätere Abfragen einfach, hält Daten konsistent und lässt sich erweitern. Ein schlechtes Schema rächt sich später mit widersprüchlichen Daten, komplizierten Abfragen und schmerzhaften Migrationen.

Das ist die direkte Fortsetzung dessen, was wir in [[1.1 OOP - Vertiefung#Abstraktion|1.1 bei der Abstraktion]] geübt haben: Wir bilden nur die für den Zweck relevanten Eigenschaften der realen Welt ab — jetzt aber als Tabellen statt als Klassen.

## Die drei Modellierungsebenen

Datenmodellierung läuft klassisch in drei zunehmend konkreten Ebenen ab. Das ist kein bürokratischer Selbstzweck, sondern hilft, „was gibt es fachlich?" von „wie setze ich es in PostgreSQL um?" zu trennen:

| Ebene | Frage | Ergebnis | Beispiel |
|---|---|---|---|
| **Konzeptionell** | Welche fachlichen Dinge und Beziehungen gibt es? | ER-Diagramm, technologieunabhängig | „Ein *Produkt* hat pro *Tag* eine Buchungslage." |
| **Logisch** | Welche Tabellen, Spalten, Schlüssel, Beziehungen? | Relationales Schema, noch DBMS-neutral | Tabellen `products`, `priceable_units` mit Primär-/Fremdschlüsseln |
| **Physisch** | Wie konkret in diesem RDBMS umgesetzt? | `CREATE TABLE`-Statements mit konkreten Typen, Indizes | `base_price NUMERIC(10,2)`, Index auf `calendar_date` |

Für kleine Projekte verschwimmen diese Ebenen oft, aber der gedankliche Dreischritt — *erst fachlich verstehen, dann Tabellen ableiten, dann physisch optimieren* — schützt zuverlässig davor, das Schema an der falschen Stelle festzuzurren.

## ER-Modellierung: Entitäten, Attribute, Beziehungen

Das **Entity-Relationship-Modell (ER-Modell)** ist die Standardsprache der konzeptionellen Ebene. Drei Bausteine:

- **Entität (entity)**: ein fachliches „Ding", über das wir Daten speichern wollen — wird meist zu einer *Tabelle*. Beispiele: `Produkt`, `Buchung`, `Kunde`.
- **Attribut (attribute)**: eine Eigenschaft einer Entität — wird zu einer *Spalte*. Beispiele: `base_price`, `calendar_date`.
- **Beziehung (relationship)**: eine fachliche Verbindung zwischen Entitäten — wird über *Fremdschlüssel* umgesetzt. Beispiel: „ein Produkt *hat viele* Buchungen".

Eine bewährte Heuristik, um aus einer fachlichen Beschreibung ein Modell zu gewinnen: **Substantive → Kandidaten für Entitäten/Attribute, Verben → Kandidaten für Beziehungen.** „Ein **Kunde** **bucht** ein **Produkt** an einem **Tag**" liefert direkt Entitäten (`Kunde`, `Produkt`) und eine Beziehung (`bucht`).

> Wie viele Zeilen der einen Seite mit wie vielen der anderen verknüpft sind (1:1, 1:n, n:m), nennt man **Kardinalität** der Beziehung. Das ist so zentral, dass es ein eigenes Stichwort bekommt → [[#Beziehungstypen — One-to-One, One-to-Many, Many-to-Many]]. Die technische Umsetzung über Fremdschlüssel → [[#Foreign Keys]].

## Schlüssel — das Rückgrat jeder Tabelle

Schlüssel sind das Mittel, mit dem Zeilen *eindeutig identifiziert* und Tabellen *verknüpft* werden. Die Begriffe sauber getrennt:

| Begriff | Bedeutung |
|---|---|
| **Superschlüssel** | Jede Spaltenkombination, die eine Zeile eindeutig identifiziert (auch mit „überflüssigen" Spalten). |
| **Kandidatenschlüssel** | Ein *minimaler* Superschlüssel — keine Spalte lässt sich weglassen, ohne die Eindeutigkeit zu verlieren. |
| **Primärschlüssel (PK)** | Der eine Kandidatenschlüssel, den man als *offizielle* Identität der Zeile auswählt. Ist automatisch `NOT NULL` und eindeutig. |
| **Alternativschlüssel** | Die übrigen Kandidatenschlüssel, die nicht PK wurden (in SQL als `UNIQUE`-Constraint abgebildet). |
| **Zusammengesetzter Schlüssel (composite key)** | Ein Schlüssel aus *mehreren* Spalten gemeinsam. |
| **Fremdschlüssel (FK)** | Eine Spalte, die auf den Primärschlüssel einer anderen (oder derselben) Tabelle verweist → stellt Beziehungen her. |

In unserer Übungsaufgabe identifiziert nicht `product_id` allein eine Zeile in `priceable_units`, sondern erst die **Kombination** `(product_id, calendar_date)` — dasselbe Produkt taucht an mehreren Tagen auf. Das ist ein klassischer **zusammengesetzter Primärschlüssel**.

### Natürlicher vs. künstlicher (Surrogat-)Schlüssel — eine zentrale Designentscheidung

Eine der wichtigsten (und meistdiskutierten) Entscheidungen beim Schlüsseldesign:

- **Natürlicher Schlüssel (natural key)**: ein Schlüssel aus fachlich vorhandenen Daten, der die Zeile ohnehin beschreibt — z. B. eine ISBN bei Büchern, oder `(product_id, calendar_date)` bei uns.
- **Künstlicher / Surrogatschlüssel (surrogate key)**: eine bedeutungslose, künstlich erzeugte ID ohne fachliche Aussage — z. B. eine `SERIAL`-Ganzzahl (`1, 2, 3, …`) oder eine `UUID`.

| | Natürlicher Schlüssel | Surrogatschlüssel |
|---|---|---|
| **Vorteil** | Keine Zusatzspalte, fachlich aussagekräftig, verhindert Duplikate „von Natur aus" | Stabil (ändert sich nie), kompakt, einfache Joins, unabhängig von fachlichen Änderungen |
| **Nachteil** | Ändert sich die Fachlichkeit (z. B. Produkt wird umbenannt), muss der Schlüssel überall mitgezogen werden; oft breit/zusammengesetzt | Trägt keine Bedeutung; man braucht trotzdem einen `UNIQUE`-Constraint auf den fachlichen Feldern, um echte Duplikate zu verhindern |

In der Praxis überwiegt heute meist der **Surrogatschlüssel** (`id BIGSERIAL PRIMARY KEY`) — vor allem, weil er stabil bleibt und Joins/ORMs (siehe letzter Abschnitt) das Leben erleichtern. Wichtig ist dann aber, die fachliche Eindeutigkeit *zusätzlich* per `UNIQUE`-Constraint abzusichern.

## Vom einen CSV-Blob zu einem sauberen Schema

Machen wir es konkret an der Übungsaufgabe. Bisher liegt alles flach in *einer* CSV — jede Zeile wiederholt sämtliche Produktinfos für jeden Tag:

```text
product_id, product_name, category,   calendar_date, base_price, bookable_units, booked_units
P-001,      "Segeltörn",  "Aktiv",    2027-04-22,    19.99,      3,              2
P-001,      "Segeltörn",  "Aktiv",    2027-04-23,    19.99,      3,              1
P-002,      "Kochkurs",   "Kulinarik",2027-04-22,    29.99,      5,              0
```

Man sieht sofort das Problem: `product_name` und `category` werden bei jedem Tag **redundant wiederholt**. Benennt man „Segeltörn" um, muss man das in *vielen* Zeilen ändern (und vergisst garantiert eine → widersprüchliche Daten). Der Design-Schritt: die **eine** Entität in **zwei** aufteilen — Stammdaten des Produkts einmal, die tages­abhängige Buchungslage separat:

```sql
-- Entität 1: Produkt-Stammdaten (einmal pro Produkt)
CREATE TABLE products (
    id             BIGSERIAL   PRIMARY KEY,     -- Surrogatschlüssel
    product_code   TEXT        NOT NULL UNIQUE,  -- fachlicher Schlüssel, zusätzlich abgesichert
    name           TEXT        NOT NULL,
    category       TEXT        NOT NULL
);

-- Entität 2: tagesabhängige Buchungslage (eine Zeile pro Produkt & Tag)
CREATE TABLE priceable_units (
    id             BIGSERIAL      PRIMARY KEY,
    product_id     BIGINT         NOT NULL REFERENCES products(id),  -- Fremdschlüssel = Beziehung
    calendar_date  DATE           NOT NULL,
    base_price     NUMERIC(10, 2) NOT NULL,
    bookable_units INTEGER        NOT NULL,
    booked_units   INTEGER        NOT NULL DEFAULT 0,
    UNIQUE (product_id, calendar_date)   -- fachliche Eindeutigkeit: je Produkt & Tag nur eine Zeile
);
```

Was dieser Entwurf erreicht:

- **Keine Redundanz**: `name`/`category` stehen genau einmal in `products`. Umbenennen = ein `UPDATE` an einer Stelle.
- **Beziehung explizit**: `priceable_units.product_id REFERENCES products(id)` macht die „gehört zu"-Beziehung für die Datenbank *durchsetzbar* (kein Verweis auf ein nicht existierendes Produkt möglich — Details bei [[#Foreign Keys]]).
- **Integrität abgesichert**: Der `UNIQUE (product_id, calendar_date)`-Constraint verhindert doppelte Buchungslagen für denselben Tag.

Diese Aufteilung nach dem Prinzip „jede Information nur an einer Stelle" ist genau das, was die **Normalisierung** systematisiert — das nächste Stichwort → [[#Normalisierung / Normalformen]]. Datenbankdesign liefert das *Warum* und den fachlichen Entwurf, die Normalformen liefern die *formalen Regeln*, um ihn zu überprüfen.

## Namenskonventionen (pragmatisch)

Konsistenz schlägt persönlichen Geschmack. Verbreitete, gut funktionierende Konventionen in der PostgreSQL-Welt:

- Tabellen- und Spaltennamen **klein und mit Unterstrich** (`snake_case`), z. B. `priceable_units`, `base_price`. (PostgreSQL faltet unquotete Namen ohnehin auf Kleinschreibung — `snake_case` erspart lästige Anführungszeichen.)
- Tabellennamen **im Plural** (`products`) oder konsistent im Singular — Hauptsache einheitlich.
- Fremdschlüsselspalten nach dem Muster `<referenzierte_tabelle_singular>_id`, z. B. `product_id`.
- Primärschlüssel schlicht `id`.
- Keine reservierten Wörter als Namen (`order`, `user`, `date` → besser `orders`, `users`, `calendar_date`).

# Normalisierung / Normalformen

## Wozu Normalisierung? — Anomalien vermeiden

Im [[#Datenbankdesign]]-Abschnitt haben wir intuitiv eine flache CSV in zwei Tabellen aufgeteilt, um Redundanz loszuwerden. **Normalisierung** ist genau dieses Vorgehen, aber *systematisiert* mit formalen Regeln: Man zerlegt Tabellen so, dass jede Information nur an *einer* Stelle steht. Ziel ist, drei Arten von **Anomalien** zu verhindern, die entstehen, wenn dieselbe Information redundant gespeichert wird.

Betrachten wir noch einmal die schlechte, unnormalisierte „alles in einer Tabelle"-Variante:

| product_id | product_name | category | calendar_date | base_price |
|---|---|---|---|---|
| P-001 | Segeltörn | Aktiv | 2027-04-22 | 19.99 |
| P-001 | Segeltörn | Aktiv | 2027-04-23 | 19.99 |
| P-002 | Kochkurs | Kulinarik | 2027-04-22 | 29.99 |

Die drei Anomalien daran:

- **Update-Anomalie**: Wird „Segeltörn" umbenannt, muss man *jede* Zeile dieses Produkts ändern. Vergisst man eine, widersprechen sich die Daten (mal „Segeltörn", mal „Segeltour").
- **Insert-Anomalie**: Ein neues Produkt, das noch keinen einzigen buchbaren Tag hat, lässt sich gar nicht anlegen — es gäbe keine `calendar_date`, und Teile des Schlüssels dürfen nicht leer sein.
- **Delete-Anomalie**: Löscht man die letzte Buchungszeile eines Produkts, verschwinden ungewollt auch dessen Stammdaten (`name`, `category`) — sie existierten nur in dieser Zeile.

Normalisierung beseitigt alle drei, indem sie Redundanz strukturell unmöglich macht.

## Die Grundbegriffe: funktionale Abhängigkeit

Der Schlüsselbegriff hinter allen Normalformen ist die **funktionale Abhängigkeit** (functional dependency). Man schreibt `A → B` und liest „A bestimmt B": Wenn man `A` kennt, ist `B` dadurch eindeutig festgelegt.

- `product_id → product_name` (kenne ich die Produkt-ID, kenne ich eindeutig den Namen).
- `(product_id, calendar_date) → base_price` (Produkt + Tag bestimmen den Preis).

Normalisierung dreht sich im Kern um die Frage: *Hängt jedes Nicht-Schlüssel-Attribut wirklich (nur) vom ganzen Primärschlüssel ab?* Wo das nicht stimmt, entsteht Redundanz — und die Normalform, die verletzt wird, sagt dir genau, *welche* Art von Fehlabhängigkeit vorliegt.

## Die Normalformen im Überblick

Normalformen bauen aufeinander auf: 2NF setzt 1NF voraus, 3NF setzt 2NF voraus usw. Für die Praxis (und die Übungsaufgabe) sind die ersten drei entscheidend — **NF4 und höher sind [[1.2 Relationale Datenbanken & ORM - Leitfaden#Out of Scope|Out of Scope]]**.

| Normalform | Kurzregel | Beseitigt |
|---|---|---|
| **1NF** | Atomare Werte, keine Listen/Wiederholgruppen in einer Zelle | Mehrwertige Felder |
| **2NF** | 1NF + jedes Nicht-Schlüssel-Attribut hängt vom *ganzen* Schlüssel ab | Partielle Abhängigkeiten |
| **3NF** | 2NF + kein Nicht-Schlüssel-Attribut hängt von einem *anderen* Nicht-Schlüssel-Attribut ab | Transitive Abhängigkeiten |

### 1. Normalform (1NF): atomare Werte

Eine Tabelle ist in **1NF**, wenn jede Zelle einen einzigen, unteilbaren (atomaren) Wert enthält — keine Listen, keine Mehrfachwerte, keine Wiederholgruppen. Das ist die Basisannahme des relationalen Modells (vgl. den Atomaritäts-Hinweis im [[#Das relationale Modell — das „R" in RDBMS|RDBMS-Abschnitt]]).

**Verletzt 1NF** (mehrere Tage in einer Zelle):

| product_id | name | available_dates |
|---|---|---|
| P-001 | Segeltörn | 2027-04-22, 2027-04-23 |

**In 1NF** (ein Wert pro Zelle, je eine Zeile):

| product_id | name | available_date |
|---|---|---|
| P-001 | Segeltörn | 2027-04-22 |
| P-001 | Segeltörn | 2027-04-23 |

> Warum ist das wichtig? Mit einer kommaseparierten `available_dates`-Zelle kannst du nicht sinnvoll nach einem einzelnen Datum filtern, keinen Index nutzen und keine Fremdschlüssel setzen — SQL arbeitet auf Zeilen, nicht auf dem Inneren von Zellen.

### 2. Normalform (2NF): keine partiellen Abhängigkeiten

Eine Tabelle ist in **2NF**, wenn sie in 1NF ist **und** jedes Nicht-Schlüssel-Attribut vom *gesamten* Primärschlüssel abhängt — nicht nur von einem *Teil* davon. 2NF wird also erst relevant, wenn der Primärschlüssel **zusammengesetzt** ist.

Beispiel — Primärschlüssel `(product_id, calendar_date)`:

| product_id | calendar_date | booked_units | product_name |
|---|---|---|---|
| P-001 | 2027-04-22 | 2 | Segeltörn |
| P-001 | 2027-04-23 | 1 | Segeltörn |

Problem: `booked_units` hängt vom *ganzen* Schlüssel ab (Produkt + Tag) — gut. Aber `product_name` hängt nur von `product_id` ab, also nur von einem **Teil** des Schlüssels. Das ist eine **partielle Abhängigkeit** → 2NF verletzt, und `product_name` wird für jeden Tag redundant wiederholt.

**Auflösung**: das partiell abhängige Attribut in eine eigene Tabelle auslagern, deren Schlüssel der Teil ist, von dem es abhängt:

```sql
products(id PK, product_code UNIQUE, name, category)          -- name hängt von product ab
priceable_units(id PK, product_id FK, calendar_date, booked_units,
                UNIQUE(product_id, calendar_date))            -- booked_units hängt von (produkt, tag) ab
```

### 3. Normalform (3NF): keine transitiven Abhängigkeiten

Eine Tabelle ist in **3NF**, wenn sie in 2NF ist **und** kein Nicht-Schlüssel-Attribut von einem *anderen Nicht-Schlüssel-Attribut* abhängt. Solche „Umweg-Abhängigkeiten" heißen **transitiv**: `Schlüssel → A → B`.

Beispiel in der `products`-Tabelle:

| id (PK) | name | category | category_tax_rate |
|---|---|---|---|
| 1 | Segeltörn | Aktiv | 0.19 |
| 2 | Klettern | Aktiv | 0.19 |
| 3 | Kochkurs | Kulinarik | 0.07 |

Hier gilt `id → category` (gut) **und** `category → category_tax_rate`. Der Steuersatz hängt also nicht direkt vom Produkt ab, sondern über die Kategorie: `id → category → category_tax_rate` — eine **transitive Abhängigkeit**. Folge: Der Steuersatz von „Aktiv" wird bei jedem Aktiv-Produkt wiederholt (Update-Anomalie lauert wieder).

**Auflösung**: das transitiv abhängige Attribut zur „Zwischen-Entität" auslagern:

```sql
categories(id PK, name UNIQUE, tax_rate)      -- tax_rate gehört zur Kategorie
products(id PK, name, category_id FK)         -- Produkt verweist nur noch auf die Kategorie
```

Merksatz für 3NF (verbreitete Eselsbrücke): *„Jedes Nicht-Schlüssel-Attribut hängt vom Schlüssel ab, vom ganzen Schlüssel und von nichts als dem Schlüssel"* — die drei Teile stehen für 1NF (überhaupt vom Schlüssel), 2NF (vom *ganzen* Schlüssel) und 3NF (von *nichts außer* dem Schlüssel).

## Kontrollfrage: Welche Normalformen gibt es, welche sind sinnvoll?

> **Kontrollfrage aus dem Leitfaden:** *Welche Normalformen gibt es? Welche sind sinnvoll? Warum sind manche nicht immer sinnvoll?*

Es gibt 1NF, 2NF, 3NF, die **Boyce-Codd-Normalform (BCNF)** als strengere Variante der 3NF, sowie 4NF, 5NF und 6NF. In der Praxis ist **3NF der De-facto-Standard und meist völlig ausreichend** — genau das fordert auch die Übungsaufgabe (NF3). BCNF wird gelegentlich noch angestrebt; NF4+ behandeln seltene Spezialfälle (mehrwertige/join-Abhängigkeiten) und sind hier bewusst Out of Scope.

Warum nicht immer *maximal* normalisieren? Höhere Normalisierung bedeutet **mehr Tabellen** und damit **mehr Joins** beim Abfragen. Das kostet Performance und macht Abfragen komplexer. Es gibt also einen Abwägungspunkt zwischen sauberer Struktur (Schreibseite: Integrität, keine Redundanz) und Abfrage-Effizienz (Leseseite).

## Kontrollfrage: Wann ist eine niedrigere Normalform (Denormalisierung) sinnvoll?

> **Kontrollfrage aus dem Leitfaden:** *Gibt es Szenarien, bei denen ein Wechsel in eine niedrigere Normalform sinnvoll ist? Beispiele …*

Ja — das nennt man **Denormalisierung**: das *bewusste* Wiedereinführen von Redundanz, um Lesezugriffe zu beschleunigen. Man tut das **erst**, wenn ein gemessenes Performance-Problem es rechtfertigt, nicht vorsorglich. Typische Szenarien:

- **Leselastige Analytics/Reporting/Data-Warehouses**: Hier dominieren große Auswertungen. Sternschemata (Star Schema) sind bewusst denormalisiert, um teure Joins zu sparen. (Relevant für Data Engineering!)
- **Teure, häufig gelesene Aggregate**: Einen oft gebrauchten Summen-/Zählwert als Spalte materialisieren (z. B. `booking_count` am Produkt), statt ihn bei jeder Abfrage neu zu joinen und zu aggregieren.
- **Caching selten geänderter Werte**: Einen fast nie geänderten Wert redundant mitspeichern, um einen Join im heißen Pfad zu vermeiden.

Der Preis ist immer derselbe: Man handelt sich die **Update-Anomalie wieder ein** und muss die Redundanz nun selbst konsistent halten (z. B. per Applikationslogik, Trigger oder periodischem Neuaufbau). Denormalisierung ist deshalb eine bewusste, dokumentierte Ausnahme — kein Standardvorgehen.

## Bezug zur Übungsaufgabe

Die Aufgabe verlangt ausdrücklich **NF3**. Unser Entwurf aus dem Datenbankdesign-Abschnitt (`products` + `priceable_units`) erfüllt das bereits: atomare Werte (1NF), keine partiellen Abhängigkeiten mehr, seit `name`/`category` aus `priceable_units` ausgelagert sind (2NF), und keine transitiven Abhängigkeiten. Der Hinweis in der Aufgabe „das mag aktuell noch einfach sein, aber unser Datenmodell wird evtl. erweitert" zielt genau auf Fälle wie das `category_tax_rate`-Beispiel oben: Sobald kategorieabhängige Attribute dazukommen, wird die saubere Auslagerung in eine `categories`-Tabelle nötig, um in 3NF zu bleiben.

# Indexes

## Das Problem: der sequentielle Scan

Ohne Index muss die Datenbank, um eine Abfrage wie

```sql
SELECT * FROM priceable_units WHERE calendar_date = '2027-04-22';
```

zu beantworten, im schlechtesten Fall **jede einzelne Zeile** der Tabelle lesen und die Bedingung prüfen. Das heißt **Sequential Scan** (oder „Full Table Scan"). Bei 1.000 Zeilen egal, bei 50 Millionen Zeilen eine Katastrophe — die Laufzeit wächst *linear* mit der Tabellengröße (O(n)).

Ein **Index** ist eine zusätzliche, sortierte Datenstruktur *neben* der Tabelle, die dieses „alles durchsuchen" in ein gezieltes Nachschlagen verwandelt. Die Analogie steckt schon im Namen: Genau wie das **Stichwortverzeichnis am Ende eines Buches** — du blätterst nicht das ganze Buch durch, um „Normalisierung" zu finden, sondern schlägst im alphabetischen Index nach und springst direkt zur Seite.

## Wie ein Index das beschleunigt: der B-Tree

Der Standard-Indextyp in PostgreSQL (und fast überall) ist der **B-Tree** (genauer: B+-Baum) — eine balancierte Baumstruktur, in der die Werte *sortiert* abgelegt sind. Statt linear zu suchen, „halbiert" die Datenbank bei jedem Schritt den Suchraum (wie beim Nachschlagen in einem Wörterbuch: aufschlagen, zu weit vorne/hinten, wieder halbieren). Die Suchzeit wächst dadurch nur noch **logarithmisch** (O(log n)) statt linear:

| Tabellengröße | Sequential Scan (O(n)) | B-Tree-Suche (O(log n)) |
|---|---|---|
| 1.000 Zeilen | ~1.000 Prüfungen | ~10 Schritte |
| 1.000.000 Zeilen | ~1.000.000 Prüfungen | ~20 Schritte |
| 1.000.000.000 Zeilen | ~1 Mrd. Prüfungen | ~30 Schritte |

Genau deshalb ist ein passender Index oft der Unterschied zwischen einer Abfrage in Millisekunden und einer in Minuten.

## Indizes anlegen

```sql
-- Einfacher Index auf eine häufig gefilterte Spalte
CREATE INDEX idx_priceable_units_date ON priceable_units (calendar_date);

-- Zusammengesetzter (mehrspaltiger) Index
CREATE INDEX idx_pu_product_date ON priceable_units (product_id, calendar_date);

-- Unique-Index: beschleunigt UND erzwingt Eindeutigkeit zugleich
CREATE UNIQUE INDEX idx_products_code ON products (product_code);
```

Wichtig zu wissen: **Manche Indizes entstehen automatisch.** PostgreSQL legt für jeden `PRIMARY KEY` und jeden `UNIQUE`-Constraint im Hintergrund bereits einen Index an — die musst du nicht selbst erstellen. Für **Fremdschlüssel-Spalten** hingegen legt Postgres **keinen** Index automatisch an; das muss man oft selbst tun (dazu unten mehr, und bei [[#Foreign Keys]]).

### Zusammengesetzte Indizes und die „Leftmost-Prefix"-Regel

Bei einem mehrspaltigen Index `(product_id, calendar_date)` ist die **Reihenfolge der Spalten entscheidend**. Der Index kann nur für Abfragen genutzt werden, die (mindestens) mit der *ersten* Spalte beginnen — das nennt man **Leftmost-Prefix-Regel**:

- `WHERE product_id = 5` → ✅ nutzt den Index
- `WHERE product_id = 5 AND calendar_date = '...'` → ✅ nutzt den Index (voll)
- `WHERE calendar_date = '...'` (nur zweite Spalte) → ❌ kann diesen Index nicht sinnvoll nutzen

Faustregel: Die Spalte, nach der am häufigsten (und am selektivsten) gefiltert wird, gehört nach vorne.

## Die Kehrseite: Kontrollfrage zu den negativen Effekten

> **Kontrollfrage aus dem Leitfaden:** *Welchen Sinn haben Indizes? Welche negativen Effekte haben sie?*

Ein Index ist kein „kostenloses schneller". Man tauscht **schnellere Lesezugriffe gegen mehrere Kosten** ein:

1. **Langsamere Schreibzugriffe**: Bei jedem `INSERT`, `UPDATE` (der indizierten Spalte) und `DELETE` muss **jeder** Index der Tabelle mitgepflegt (aktualisiert) werden. Zehn Indizes = zehn zusätzliche Datenstrukturen, die bei jedem Schreibvorgang aktualisiert werden müssen.
2. **Speicherplatz**: Jeder Index ist eine eigene, auf der Platte gespeicherte Struktur und braucht Platz (bei breiten/vielen Indizes durchaus in der Größenordnung der Tabelle selbst).
3. **Wartung/Overhead**: Indizes können „aufblähen" (bloat) und profitieren gelegentlich von Reorganisation; der Query Planner muss außerdem bei jeder Abfrage entscheiden, ob sich ein Index überhaupt lohnt.

Deshalb gilt: **Indizes gezielt setzen, nicht wahllos.** Ein Index lohnt sich für Spalten, nach denen häufig gefiltert (`WHERE`), verknüpft (`JOIN`) oder sortiert (`ORDER BY`) wird — nicht für jede Spalte „vorsorglich".

## Wann bringt ein Index (fast) nichts? — Selektivität

Ein Index hilft nur, wenn er die Ergebnismenge stark **einschränkt** (hohe *Selektivität*). Ein Index auf einer Spalte mit sehr wenigen verschiedenen Werten (z. B. ein `boolean is_active`, das bei 90 % der Zeilen `true` ist) bringt kaum etwas — die Datenbank müsste ohnehin fast alle Zeilen anfassen und wählt dann oft bewusst den Sequential Scan, weil der hier sogar schneller ist. Merke: Indizes sind am wertvollsten auf Spalten mit **vielen unterschiedlichen Werten**, nach denen selektiv gesucht wird.

## Nachschauen, ob ein Index genutzt wird: `EXPLAIN`

Ob eine Abfrage tatsächlich einen Index verwendet oder sequentiell scannt, verrät der Ausführungsplan:

```sql
EXPLAIN ANALYZE
SELECT * FROM priceable_units WHERE calendar_date = '2027-04-22';
```

Im Output erscheint dann entweder ein `Seq Scan on priceable_units` (kein/ungenutzter Index) oder ein `Index Scan using idx_priceable_units_date` (Index greift). Das ist das wichtigste Werkzeug, um Performance-Vermutungen durch **Messung** zu ersetzen — mehr dazu im Register unter *SQL → EXPLAIN* ([[Stichwörter Claudian|Stichwörter Claudian]]).

## Weitere Index-Typen (nur zur Einordnung)

Der B-Tree deckt den Großteil ab, aber PostgreSQL kennt weitere spezialisierte Typen — gut, die Namen einordnen zu können:

| Typ | Wofür |
|---|---|
| **B-Tree** | Standard: Gleichheit & Bereichsvergleiche (`=`, `<`, `>`, `BETWEEN`, `ORDER BY`) |
| **Hash** | Nur exakte Gleichheit (`=`) |
| **GIN** | „Inhalt von" — Volltextsuche, `JSONB`, Arrays |
| **GiST** | Geometrische/räumliche Daten, Nachbarschaftssuchen (PostGIS) |
| **BRIN** | Sehr große, physisch sortierte Tabellen (z. B. Zeitreihen) — winzig & grob |

## Bezug zur Übungsaufgabe

Die Aufgabe fordert, dass die Tabellen „sinnvolle Constraints und **Indizes**" erhalten. Konkret: Auf `priceable_units` wird man häufig nach `product_id` (welche Buchungslagen gehören zu einem Produkt?) und nach `calendar_date` (was ist an einem Tag los?) filtern — beides gute Index-Kandidaten. Der `UNIQUE (product_id, calendar_date)`-Constraint aus dem Design-Abschnitt bringt seinen Index ohnehin schon mit und deckt Abfragen ab, die mit `product_id` beginnen.

# Foreign Keys

## Grundidee: eine Beziehung, die die Datenbank durchsetzt

Ein **Fremdschlüssel (Foreign Key, FK)** ist eine Spalte (oder Spaltenkombination), deren Werte auf den **Primärschlüssel einer anderen Tabelle** verweisen. Er ist das technische Mittel, mit dem aus zwei separaten Tabellen eine **Beziehung** wird — und zwar eine, die das RDBMS selbst *garantiert*.

Wir haben ihn im [[#Datenbankdesign]]-Abschnitt schon eingeführt: `priceable_units.product_id` verweist auf `products.id`. Jetzt schauen wir genauer hin, *was* dieser Verweis eigentlich erzwingt.

```sql
CREATE TABLE products (
    id           BIGSERIAL PRIMARY KEY,
    product_code TEXT      NOT NULL UNIQUE,
    name         TEXT      NOT NULL
);

CREATE TABLE priceable_units (
    id            BIGSERIAL      PRIMARY KEY,
    product_id    BIGINT         NOT NULL
                  REFERENCES products(id),   -- <- das ist der Fremdschlüssel
    calendar_date DATE           NOT NULL,
    base_price    NUMERIC(10, 2) NOT NULL,
    UNIQUE (product_id, calendar_date)
);
```

Zwei Rollen sind hier zu unterscheiden:

- **Kindtabelle (child / referencing)**: `priceable_units` — sie *enthält* den Fremdschlüssel.
- **Elterntabelle (parent / referenced)**: `products` — auf deren Primärschlüssel wird *verwiesen*.

## Referenzielle Integrität — was der FK garantiert

Der zentrale Nutzen eines Fremdschlüssels heißt **referenzielle Integrität**: Die Datenbank stellt sicher, dass ein Fremdschlüssel **immer** entweder auf eine *tatsächlich existierende* Zeile der Elterntabelle zeigt oder `NULL` ist. Es kann also niemals eine „verwaiste" Buchungslage geben, die auf ein Produkt verweist, das gar nicht (mehr) existiert.

Das schützt vor zwei Fehlerklassen — jeweils auf **Infrastrukturebene**, egal welcher Code schreibt:

```sql
-- (1) INSERT mit ungültigem Verweis wird abgelehnt:
INSERT INTO priceable_units (product_id, calendar_date, base_price)
VALUES (999, '2027-04-22', 19.99);
-- FEHLER: insert or update on table "priceable_units" violates foreign key constraint
--         → es gibt kein products.id = 999

-- (2) Löschen eines noch referenzierten Elternteils wird (standardmäßig) abgelehnt:
DELETE FROM products WHERE id = 1;
-- FEHLER: update or delete on table "products" violates foreign key constraint
--         → auf products.id = 1 verweisen noch Zeilen in priceable_units
```

Das ist exakt derselbe Gedanke wie die Invarianten-Durchsetzung, die wir in [[1.1 OOP - Vertiefung#Kapselung|1.1 bei der Kapselung]] auf Objektebene geübt haben („ein Objekt hält seinen Zustand selbst konsistent") — nur dass jetzt die *Datenbank* die Konsistenz *tabellenübergreifend* garantiert, unabhängig von der Anwendung.

## `ON DELETE` / `ON UPDATE` — was passiert mit den Kindern?

Standardmäßig verhindert der FK das Löschen eines noch referenzierten Elternteils (`NO ACTION`/`RESTRICT`). Man kann aber explizit festlegen, was bei Löschen/Ändern des Elternteils mit den Kind-Zeilen geschehen soll — die **referenzielle Aktion**:

| Aktion | Verhalten bei `DELETE`/`UPDATE` des Elternteils |
|---|---|
| `NO ACTION` (Default) | Ablehnen, wenn noch Kinder existieren (Prüfung am Ende des Statements/der Transaktion) |
| `RESTRICT` | Wie `NO ACTION`, aber sofortige Prüfung (nicht aufschiebbar) |
| `CASCADE` | Die Kind-Zeilen **mitlöschen** bzw. mitändern |
| `SET NULL` | Den Fremdschlüssel der Kinder auf `NULL` setzen |
| `SET DEFAULT` | Den Fremdschlüssel der Kinder auf ihren Default-Wert setzen |

```sql
-- Beispiel: Löscht man ein Produkt, sollen seine Buchungslagen automatisch mit verschwinden
CREATE TABLE priceable_units (
    id         BIGSERIAL PRIMARY KEY,
    product_id BIGINT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    ...
);
```

**Vorsicht mit `CASCADE`**: Es ist bequem, aber mächtig — ein einziges `DELETE` am Elternteil kann eine ganze Kette von Kind-, Enkel- … Zeilen mitreißen. Bewusst und nur dort einsetzen, wo das Kind wirklich *existenzabhängig* vom Elternteil ist (z. B. „Bestellposition gehört zu Bestellung"). Für viele Fälle ist das absichtliche `RESTRICT`/`NO ACTION` (erst die Kinder aufräumen müssen) die sicherere Wahl.

## Wichtig: Fremdschlüssel bekommen KEINEN automatischen Index

Ein häufiger, performance-relevanter Stolperstein — direkt anschließend an den [[#Indexes]]-Abschnitt: PostgreSQL legt für einen Fremdschlüssel **keinen** Index automatisch an (anders als für `PRIMARY KEY`/`UNIQUE`). Das ist aus zwei Gründen oft ein Problem:

1. **Joins** über den FK (`... JOIN products ON products.id = priceable_units.product_id`) profitieren stark von einem Index auf der FK-Spalte.
2. Wird ein Elternteil **gelöscht/geändert**, muss die DB prüfen, ob es noch Kinder gibt — ohne Index auf der FK-Spalte ist das ein Sequential Scan der Kindtabelle bei *jedem* solchen Vorgang.

Deshalb ist es gute Praxis, FK-Spalten in der Regel selbst zu indizieren:

```sql
CREATE INDEX idx_priceable_units_product_id ON priceable_units (product_id);
```

## Zusammengesetzte und selbstreferenzierende Fremdschlüssel

- **Zusammengesetzt**: Verweist eine Kindtabelle auf einen mehrspaltigen Primärschlüssel, ist auch der FK mehrspaltig: `FOREIGN KEY (product_id, calendar_date) REFERENCES priceable_units (product_id, calendar_date)`.
- **Selbstreferenzierend**: Ein FK darf auf *dieselbe* Tabelle zeigen — der klassische Weg, Hierarchien abzubilden. Beispiel: eine `categories`-Tabelle mit `parent_id BIGINT REFERENCES categories(id)` für Ober-/Unterkategorien.

## Bezug zur Übungsaufgabe

Die Aufgabe verlangt ausdrücklich, dass „Tabellen entsprechend ihrer Beziehungen verknüpft sein" sollen — das sind genau die Fremdschlüssel. In unserem Schema stellt `priceable_units.product_id REFERENCES products(id)` sicher, dass beim Überführen der CSV-Daten keine Buchungslage auf ein nicht existierendes Produkt verweisen kann. Weil über diese Spalte auch gejoint und nach Produkt gefiltert wird, gehört (siehe oben) ein eigener Index darauf. Wie sich aus diesen paarweisen Verweisen die verschiedenen **Beziehungsformen** (1:1, 1:n, n:m) ergeben, ist das nächste Stichwort → [[#Beziehungstypen — One-to-One, One-to-Many, Many-to-Many]].

# Beziehungstypen — One-to-One, One-to-Many, Many-to-Many

## Kardinalität: wie viele hängen an wie vielen?

Im [[#Datenbankdesign]]-Abschnitt haben wir Beziehungen als ER-Baustein eingeführt und bei [[#Foreign Keys]] gesehen, *wie* ein einzelner Verweis technisch funktioniert. Jetzt die entscheidende Design-Frage: **Wie viele** Zeilen der einen Seite hängen mit **wie vielen** der anderen zusammen? Diese „Anzahl-Beziehung" heißt **Kardinalität**, und es gibt genau drei Grundformen:

| Typ | Bedeutung | Beispiel |
|---|---|---|
| **1:1** (one-to-one) | Eine Zeile A gehört zu höchstens einer Zeile B und umgekehrt | Nutzer ↔ Nutzerprofil |
| **1:n** (one-to-many) | Eine Zeile A gehört zu vielen Zeilen B, aber jede B zu genau einer A | Produkt ↔ Buchungslagen |
| **n:m** (many-to-many) | Viele A gehören zu vielen B und umgekehrt | Produkt ↔ Tag/Ausstattungsmerkmal |

Der springende Punkt: Eine relationale Datenbank kennt **nur** das Werkzeug „Fremdschlüssel". Alle drei Beziehungstypen werden allein durch die geschickte *Platzierung* von Fremdschlüsseln (und passende Constraints) umgesetzt. Schauen wir uns das einzeln an.

## One-to-Many (1:n) — der häufigste Fall

Die mit Abstand häufigste Beziehung. Umsetzung: Der Fremdschlüssel steht auf der **„many"-Seite** und zeigt auf den Primärschlüssel der „one"-Seite.

Genau unser Schema: *ein* Produkt hat *viele* tagesabhängige Buchungslagen, aber jede Buchungslage gehört zu genau *einem* Produkt. Also bekommt `priceable_units` (die „many"-Seite) den FK:

```sql
CREATE TABLE products (
    id   BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE priceable_units (          -- die "many"-Seite trägt den FK
    id            BIGSERIAL PRIMARY KEY,
    product_id    BIGINT NOT NULL REFERENCES products(id),
    calendar_date DATE NOT NULL,
    base_price    NUMERIC(10, 2) NOT NULL,
    UNIQUE (product_id, calendar_date)
);
```

Merksatz: **Der Fremdschlüssel steht immer auf der „many"-Seite** — er kann ja pro Zeile nur *einen* Wert haben und bildet damit natürlicherweise „viele Kinder verweisen auf ein Elternteil" ab. Der umgekehrte Versuch (eine Liste von Kind-IDs in der „one"-Zeile) würde die 1NF verletzen (siehe [[#1. Normalform (1NF): atomare Werte|1NF]]).

## One-to-One (1:1) — der Sonderfall

1:1 ist im Grunde ein 1:n, bei dem die „many"-Seite auf **maximal eine** Zeile beschränkt wird. Technisch: derselbe Fremdschlüssel wie bei 1:n, aber zusätzlich mit einem **`UNIQUE`-Constraint** auf der FK-Spalte — dadurch kann kein Elternteil mehr als ein Kind haben.

```sql
CREATE TABLE user_profiles (
    id      BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL UNIQUE REFERENCES users(id),  -- UNIQUE macht aus 1:n ein 1:1
    bio     TEXT
);
```

Wann nutzt man das überhaupt, statt alles in *eine* Tabelle zu packen? Typische Gründe:
- **Selten genutzte / optionale Attribute** auslagern (schlanke Haupttabelle).
- **Sensible Daten** in eine separate Tabelle mit strengeren Zugriffsrechten trennen.
- **Sehr große Spalten** (z. B. ein großes `TEXT`/Blob), die man nicht bei jedem Zugriff auf die Haupttabelle mitladen will.

Merke: 1:1 ist relativ selten — oft ist „einfach eine gemeinsame Tabelle" die richtige Wahl, und 1:1 erst bei einem der obigen konkreten Gründe.

## Many-to-Many (n:m) — die Verknüpfungstabelle (Kontrollfrage!)

> **Kontrollfrage aus dem Leitfaden:** *Wie setzt man eine Many-to-Many-Relationship in der Praxis um? Wie fragt man Entitäten aus solchen Modellen ab?*

n:m lässt sich **nicht** durch einen Fremdschlüssel auf einer der beiden Seiten abbilden — eine einzelne FK-Spalte kann ja nur *einen* Wert halten, wir bräuchten aber „viele auf beiden Seiten". Die Lösung ist eine **dritte Tabelle**, die sogenannte **Verknüpfungstabelle** (junction / join / association table, auch „Zwischentabelle"). Sie enthält je einen Fremdschlüssel auf *beide* Seiten und zerlegt damit das n:m in **zwei 1:n-Beziehungen**.

Beispiel: Ein Produkt kann mehrere **Ausstattungsmerkmale (Tags)** haben, und jedes Merkmal kann bei vielen Produkten vorkommen:

```sql
CREATE TABLE products (
    id   BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE tags (
    id   BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL UNIQUE
);

-- Verknüpfungstabelle: je ein FK auf beide Seiten
CREATE TABLE product_tags (
    product_id BIGINT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    tag_id     BIGINT NOT NULL REFERENCES tags(id)     ON DELETE CASCADE,
    PRIMARY KEY (product_id, tag_id)   -- zusammengesetzter PK: jede Kombination nur einmal
);
```

Zwei wichtige Details an der Verknüpfungstabelle:

- Der **zusammengesetzte Primärschlüssel `(product_id, tag_id)`** stellt sicher, dass dieselbe Zuordnung nicht doppelt entstehen kann, und dient gleichzeitig als Identität der Zeile.
- Eine Verknüpfungstabelle kann **eigene Attribute** tragen, wenn die *Beziehung selbst* Daten hat — z. B. `assigned_at TIMESTAMP` („wann wurde das Tag gesetzt?"). Dann wird aus der reinen Zuordnung eine eigenständige Entität (eine sogenannte *assoziative Entität*).

### Abfragen über eine n:m-Beziehung

Um „alle Tags eines Produkts" oder „alle Produkte mit einem bestimmten Tag" zu bekommen, verknüpft man **über die Zwischentabelle** — in der Regel mit zwei Joins (Joins bekommen ihr eigenes Stichwort → [[#Joins und Unions]], hier als Vorgriff):

```sql
-- Alle Tag-Namen des Produkts mit id = 1
SELECT t.name
FROM tags AS t
JOIN product_tags AS pt ON pt.tag_id = t.id
WHERE pt.product_id = 1;

-- Umgekehrt: alle Produkte, die das Tag 'Aktiv' tragen
SELECT p.name
FROM products AS p
JOIN product_tags AS pt ON pt.product_id = p.id
JOIN tags        AS t  ON t.id = pt.tag_id
WHERE t.name = 'Aktiv';
```

Das Muster ist immer dasselbe: von der einen Entität **über** die Verknüpfungstabelle zur anderen „hangeln".

## Übersicht: Wo steht der Fremdschlüssel?

| Beziehung | Umsetzung |
|---|---|
| **1:n** | FK auf der „many"-Seite → zeigt auf die „one"-Seite |
| **1:1** | FK wie bei 1:n, zusätzlich `UNIQUE` auf der FK-Spalte |
| **n:m** | Eigene Verknüpfungstabelle mit zwei FKs + zusammengesetztem PK; zerlegt n:m in zwei 1:n |

## Bezug zur Übungsaufgabe

Unser Kern-Schema ist eine klassische **1:n**-Beziehung (`products` → `priceable_units`). Sobald das Datenmodell wächst — z. B. Produkte mit mehreren Kategorien/Merkmalen oder Kunden, die mehrere Produkte über mehrere Buchungen belegen — kommen **n:m**-Beziehungen und damit Verknüpfungstabellen ins Spiel. Genau darauf zielt der Aufgaben-Hinweis „unser Datenmodell wird evtl. erweitert". Wie man diese Beziehungen dann elegant *abfragt*, ist das nächste große Stichwort → [[#Joins und Unions]].

# Constraints

## Grundidee: Regeln, die die Datenbank selbst durchsetzt (Kontrollfrage!)

> **Kontrollfrage aus dem Leitfaden:** *Warum sind Constraints wichtig? Was kann mit Constraints bewerkstelligt werden?*

Ein **Constraint** (Bedingung/Einschränkung) ist eine Regel über die erlaubten Werte in einer Tabelle, die das **RDBMS selbst durchsetzt**. Versucht ein `INSERT` oder `UPDATE`, die Regel zu verletzen, lehnt die Datenbank den Vorgang mit einem Fehler ab — die Daten bleiben konsistent.

Der entscheidende Punkt (und die eigentliche Antwort auf die Kontrollfrage): Ein Constraint schützt die Daten **auf Infrastrukturebene**, unabhängig davon, *welcher* Code schreibt. Ob die Anwendung, ein Migrationsskript, ein manuelles `psql`-`INSERT` oder ein Kollege in fünf Jahren — die Regel gilt immer. Das ist der fundamentale Unterschied zu einer Prüfung im Python-Code: Eine `if base_price < 0: raise ...`-Prüfung in *einer* Funktion greift nur, wenn der Code auch durch genau diese Funktion läuft. Ein `CHECK (base_price >= 0)` in der Datenbank kann **niemand** umgehen.

Das ist exakt das „Single Source of Truth für Invarianten"-Prinzip, das wir in [[1.1 OOP - Vertiefung#Kapselung|1.1 bei der Kapselung]] auf Objektebene kennengelernt haben — jetzt eine Ebene tiefer, für die Daten selbst.

## Die sechs Constraint-Typen

Viele davon sind uns in den vorigen Abschnitten schon begegnet — hier systematisch zusammengefasst:

| Constraint | Erzwingt | Schon behandelt bei |
|---|---|---|
| **`NOT NULL`** | Spalte muss einen Wert haben (kein `NULL`) | [[#SQL]] |
| **`UNIQUE`** | Keine zwei Zeilen haben denselben Wert (Duplikate ausgeschlossen) | [[#Datenbankdesign]] |
| **`PRIMARY KEY`** | `NOT NULL` **und** `UNIQUE` zugleich — die Identität der Zeile | [[#Datenbankdesign]] |
| **`FOREIGN KEY`** | Wert muss auf eine existierende Zeile einer anderen Tabelle verweisen | [[#Foreign Keys]] |
| **`CHECK`** | Ein frei formulierter Wahrheitsausdruck muss `TRUE` (oder `UNKNOWN`) sein | neu, s. u. |
| **`DEFAULT`** | (Streng genommen kein Constraint) Standardwert, wenn keiner angegeben wird | [[#SQL]] |

`PRIMARY KEY` ist also keine eigene „Magie", sondern die *Kombination* `NOT NULL` + `UNIQUE`, ausgezeichnet als offizielle Identität (und mit automatischem Index, siehe [[#Indexes]]).

### `CHECK` — der frei formulierbare Constraint

`CHECK` ist der flexibelste Typ: Er erlaubt einen beliebigen booleschen Ausdruck über die Spaltenwerte einer Zeile. Genau hier landen die fachlichen Invarianten, die es sonst nur im Anwendungscode gäbe:

```sql
CREATE TABLE priceable_units (
    id            BIGSERIAL PRIMARY KEY,
    product_id    BIGINT NOT NULL REFERENCES products(id),
    calendar_date DATE NOT NULL,
    base_price    NUMERIC(10, 2) NOT NULL CHECK (base_price >= 0),      -- kein negativer Preis
    bookable_units INTEGER NOT NULL CHECK (bookable_units >= 0),
    booked_units   INTEGER NOT NULL DEFAULT 0 CHECK (booked_units >= 0),
    -- mehrspaltiger CHECK: darf sich auf mehrere Spalten derselben Zeile beziehen
    CHECK (booked_units <= bookable_units),                             -- nie mehr gebucht als buchbar
    UNIQUE (product_id, calendar_date)
);
```

Damit ist die Invariante „`booked_units >= 0`", die wir in [[1.1 OOP - Vertiefung#Kapselung|1.1]] noch im `__init__` der `PriceableUnit`-Klasse durchgesetzt haben, jetzt zusätzlich in der Datenbank verankert — sie gilt selbst dann, wenn Daten unter Umgehung der Python-Klasse geschrieben werden.

> Randnotiz: Ein `CHECK` kann sich nur auf die **eigene Zeile** beziehen, nicht auf andere Zeilen/Tabellen (dafür bräuchte man Trigger — [[1.2 Relationale Datenbanken & ORM - Leitfaden#Out of Scope|Out of Scope]]). Und Vorsicht mit `NULL`: Ein `CHECK` gilt als erfüllt, wenn er `TRUE` **oder** `UNKNOWN` ergibt — ein `CHECK (base_price >= 0)` lässt also ein `base_price IS NULL` durch (deshalb zusätzlich `NOT NULL`).

## Spalten- vs. Tabellen-Constraints

Constraints lassen sich an zwei Stellen notieren:

- **Spalten-Constraint**: direkt hinter der Spaltendefinition (`base_price NUMERIC(10,2) NOT NULL CHECK (base_price >= 0)`). Kann sich nur auf *diese eine* Spalte beziehen.
- **Tabellen-Constraint**: als eigene Zeile im `CREATE TABLE` (`UNIQUE (product_id, calendar_date)`, `CHECK (booked_units <= bookable_units)`). **Nötig**, sobald sich der Constraint über *mehrere* Spalten erstreckt.

Beide sind funktional gleichwertig, wo beide möglich sind — mehrspaltige Regeln *müssen* aber als Tabellen-Constraint stehen.

## Constraints benennen und nachträglich ändern

Gibt man keinen Namen an, vergibt PostgreSQL automatisch einen (z. B. `priceable_units_base_price_check`). Für sprechende Fehlermeldungen und einfacheres späteres Ändern lohnt sich oft ein **expliziter Name**:

```sql
-- Beim Anlegen benennen
CONSTRAINT chk_booked_not_negative CHECK (booked_units >= 0)

-- Nachträglich hinzufügen / entfernen
ALTER TABLE priceable_units ADD CONSTRAINT chk_price_positive CHECK (base_price >= 0);
ALTER TABLE priceable_units DROP CONSTRAINT chk_price_positive;
```

## Warum Constraints statt Prüfung nur im Code? — die Kernbotschaft

Zusammengefasst, weil es die Kontrollfrage direkt beantwortet — Constraints leisten drei Dinge, die reine Anwendungsprüfungen nicht garantieren können:

1. **Zentral & unumgehbar**: Die Regel steht an *einer* Stelle (dem Schema) und gilt für *jeden* Schreibpfad — kein vergessener Code-Zweig, keine zweite App, kein manuelles `INSERT` kann sie aushebeln.
2. **Selbstdokumentierend**: Das Schema beschreibt die fachlichen Regeln explizit. Wer die Tabelle liest (`\d priceable_units`), sieht sofort, was gültige Daten ausmacht.
3. **Fail-fast & datenschützend**: Ungültige Daten kommen gar nicht erst hinein — statt später mühsam korrupte Datenbestände zu reparieren.

Der pragmatische Konsens in der Praxis: Wichtige Invarianten gehören **sowohl** in die Datenbank (als Sicherheitsnetz, das nie versagt) **als auch** in die Anwendung (für frühe, benutzerfreundliche Fehlermeldungen, bevor überhaupt die DB kontaktiert wird). Die Datenbank ist die *letzte Verteidigungslinie*.

## Bezug zur Übungsaufgabe

Die Aufgabe fordert „sinnvolle Constraints". Konkret ergeben sich aus unserem Modell: `NOT NULL` auf allen Pflichtfeldern, `PRIMARY KEY` je Tabelle, `FOREIGN KEY` von `priceable_units` auf `products`, `UNIQUE (product_id, calendar_date)` gegen doppelte Tageseinträge und `CHECK`-Constraints für die fachlichen Invarianten (`base_price >= 0`, `booked_units >= 0`, `booked_units <= bookable_units`). Damit wandert genau die Validierungslogik, die in der OOP-Lösung in den Klassen saß, als unumgehbares Sicherheitsnetz in die Datenbank.

# Joins und Unions

## Warum Joins? — die Kehrseite der Normalisierung

Die [[#Normalisierung / Normalformen|Normalisierung]] hat unsere Daten bewusst auf mehrere Tabellen verteilt (`products`, `priceable_units`, `tags`, …), damit jede Information nur an einer Stelle steht. Beim *Abfragen* wollen wir sie aber oft wieder **zusammengeführt** sehen — „zeig mir jede Buchungslage *mit* dem Produktnamen". Genau das leistet ein **JOIN**: Er kombiniert Zeilen aus zwei (oder mehr) Tabellen anhand einer **Verknüpfungsbedingung** (meist Fremdschlüssel = Primärschlüssel) zu einem gemeinsamen Ergebnis.

Join ≠ Union — die beiden werden gern verwechselt:

- Ein **JOIN** kombiniert Tabellen **nebeneinander** (fügt *Spalten* zusammen — „horizontal").
- Ein **UNION** stapelt Ergebnismengen **untereinander** (fügt *Zeilen* zusammen — „vertikal"). Mehr dazu am Ende.

## Die Ausgangslage

Für die Beispiele:

```sql
products                          priceable_units
+----+-----------+               +----+------------+---------------+------------+
| id | name      |               | id | product_id | calendar_date | base_price |
+----+-----------+               +----+------------+---------------+------------+
| 1  | Segeltörn |               | 10 | 1          | 2027-04-22    | 19.99      |
| 2  | Kochkurs  |               | 11 | 1          | 2027-04-23    | 19.99      |
| 3  | Klettern  |               | 12 | 2          | 2027-04-22    | 29.99      |
+----+-----------+               +----+------------+---------------+------------+
```

Beachte: Produkt 3 („Klettern") hat *keine* Buchungslage; Produkt-IDs in `priceable_units` verweisen alle auf existierende Produkte (dank Fremdschlüssel). Diese Asymmetrie macht gleich den Unterschied zwischen den Join-Typen sichtbar.

## INNER JOIN — nur die Treffer (Kontrollfrage!)

> **Kontrollfrage aus dem Leitfaden:** *Erkläre den Unterschied zwischen „INNER JOIN" und „LEFT JOIN". Nenne jeweilige Beispielszenarien.*

Ein **INNER JOIN** liefert nur die Zeilenkombinationen, für die die Bedingung auf **beiden** Seiten einen Treffer hat. Zeilen ohne Partner fallen weg.

```sql
SELECT p.name, pu.calendar_date, pu.base_price
FROM products AS p
INNER JOIN priceable_units AS pu ON pu.product_id = p.id;
```

Ergebnis — Produkt 3 („Klettern") fehlt, weil es keine passende `priceable_units`-Zeile hat:

| name | calendar_date | base_price |
|---|---|---|
| Segeltörn | 2027-04-22 | 19.99 |
| Segeltörn | 2027-04-23 | 19.99 |
| Kochkurs | 2027-04-22 | 29.99 |

**Beispielszenario**: „Alle tatsächlich gebuchten/buchbaren Einheiten mit ihrem Produktnamen" — Produkte ohne jede Buchungslage sind hier uninteressant. (`INNER` ist optional: `JOIN` allein bedeutet in SQL immer INNER JOIN.)

## LEFT JOIN — alle von links, Partner falls vorhanden

Ein **LEFT (OUTER) JOIN** liefert **alle** Zeilen der **linken** Tabelle (die im `FROM`) — und dazu die passenden Zeilen der rechten. Gibt es rechts keinen Partner, erscheint die linke Zeile trotzdem, die rechten Spalten sind dann `NULL`.

```sql
SELECT p.name, pu.calendar_date, pu.base_price
FROM products AS p
LEFT JOIN priceable_units AS pu ON pu.product_id = p.id;
```

Ergebnis — „Klettern" ist jetzt dabei, mit `NULL` in den rechten Spalten:

| name | calendar_date | base_price |
|---|---|---|
| Segeltörn | 2027-04-22 | 19.99 |
| Segeltörn | 2027-04-23 | 19.99 |
| Kochkurs | 2027-04-22 | 29.99 |
| Klettern | `NULL` | `NULL` |

**Beispielszenario**: „Alle Produkte auflisten, auch die *ohne* Buchungslage" (z. B. um Lücken zu finden). Der klassische Trick, **nur** die partnerlosen Zeilen zu bekommen (anti-join):

```sql
SELECT p.name
FROM products AS p
LEFT JOIN priceable_units AS pu ON pu.product_id = p.id
WHERE pu.id IS NULL;          -- Produkte ganz ohne Buchungslage → hier: Klettern
```

## Die übrigen Join-Typen im Überblick

| Join | Liefert | Merksatz |
|---|---|---|
| **INNER JOIN** | Nur Zeilen mit Treffer auf beiden Seiten | Schnittmenge |
| **LEFT JOIN** | Alle linken + passende rechte (sonst `NULL`) | Alles links |
| **RIGHT JOIN** | Alle rechten + passende linke (sonst `NULL`) | Alles rechts (= LEFT mit vertauschten Tabellen) |
| **FULL OUTER JOIN** | Alle Zeilen beider Seiten, `NULL` wo kein Partner | Vereinigung |
| **CROSS JOIN** | Jede Zeile links × jede Zeile rechts (kartesisches Produkt) | Alle Kombinationen |

In der Praxis dominieren **INNER** und **LEFT**. `RIGHT JOIN` schreibt man selten (man dreht lieber die Tabellen um und nimmt LEFT). `CROSS JOIN` entsteht oft *ungewollt*, wenn man die `ON`-Bedingung vergisst — dann explodiert die Zeilenzahl (3 × 3 = 9 statt 3).

## Mehrere Joins & Self-Join

Man kann beliebig viele Joins verketten — genau das brauchten wir schon bei der [[#Many-to-Many (n:m) — die Verknüpfungstabelle (Kontrollfrage!)|n:m-Abfrage]] über eine Verknüpfungstabelle (`products` → `product_tags` → `tags`). Und eine Tabelle lässt sich sogar **mit sich selbst** joinen (**Self-Join**) — nützlich bei selbstreferenzierenden FKs (z. B. Kategorie + Oberkategorie):

```sql
SELECT c.name AS kategorie, parent.name AS oberkategorie
FROM categories AS c
LEFT JOIN categories AS parent ON parent.id = c.parent_id;
```

## `ON` vs. `WHERE` bei OUTER Joins (feiner, wichtiger Unterschied)

Bei INNER JOIN ist es egal, ob eine Bedingung in `ON` oder `WHERE` steht. Bei **LEFT JOIN** nicht:

- Eine Bedingung in **`ON`** wird *vor* dem Auffüllen angewandt — sie entscheidet, was als „Partner" gilt, verwirft aber keine linken Zeilen.
- Eine Bedingung in **`WHERE`** wirkt *nach* dem Join — und filtert dann auch die mit `NULL` aufgefüllten linken Zeilen wieder heraus, wodurch ein LEFT JOIN faktisch zum INNER JOIN „degradiert".

Faustregel: Bedingungen an die **rechte** Tabelle eines LEFT JOIN gehören meist ins `ON`, nicht ins `WHERE`.

## UNION — Ergebnisse untereinander stapeln

**UNION** verbindet die Ergebnisse *zweier `SELECT`-Abfragen* zu einer Ergebnismenge (Zeilen untereinander). Voraussetzung: Beide `SELECT` liefern die **gleiche Spaltenanzahl** mit **kompatiblen Datentypen**.

```sql
SELECT name, 'Produkt' AS quelle FROM products
UNION
SELECT name, 'Tag'     AS quelle FROM tags;
```

Wichtig — zwei Varianten:

- **`UNION`** entfernt **Duplikate** (führt zusätzlich eine Sortierung/Deduplizierung durch → etwas teurer).
- **`UNION ALL`** behält **alle** Zeilen inkl. Duplikate (schneller). Wenn du weißt, dass es keine Duplikate gibt (oder sie behalten willst), nimm `UNION ALL`.

Verwandte Mengenoperatoren (nur zur Einordnung): `INTERSECT` (Schnittmenge beider Ergebnisse) und `EXCEPT` (Zeilen der ersten, die nicht in der zweiten vorkommen).

> **JOIN vs. UNION merken**: JOIN = mehr *Spalten* (Tabellen nebeneinander, verknüpft über eine Bedingung). UNION = mehr *Zeilen* (gleichgeformte Ergebnisse gestapelt).

## Bezug zur Übungsaufgabe

Sobald die Daten normalisiert in `products` + `priceable_units` liegen, brauchst du für praktisch jede sinnvolle Ausgabe einen JOIN — z. B. um die Preisempfehlungen *mit Produktnamen* auszugeben, statt nur mit einer nackten `product_id`. Das ist der Punkt, an dem sich die saubere Normalisierung „auszahlt": Die Verknüpfung passiert deklarativ in *einer* Abfrage, statt in Python mehrere CSVs manuell zusammenzufügen. Genau diese wiederkehrende Join-Logik nimmt einem später das ORM ab → [[#SQLAlchemy und ORM in Python]].

# Transactions

## Grundidee: mehrere Schritte, „ganz oder gar nicht"

Eine **Transaktion** ist eine Gruppe von SQL-Anweisungen, die als **eine einzige, unteilbare Einheit** ausgeführt werden: Entweder alle Schritte gelingen und werden gemeinsam wirksam (**commit**), oder — wenn irgendwo etwas schiefgeht — wird die **gesamte** Gruppe rückgängig gemacht (**rollback**), als hätte sie nie stattgefunden. Es gibt keinen Zwischenzustand nach außen.

Das klassische Lehrbuchbeispiel ist die **Geldüberweisung**: Konto A abbuchen *und* Konto B gutschreiben sind zwei Schritte, die nur *gemeinsam* Sinn ergeben.

```sql
BEGIN;                                                    -- Transaktion starten
    UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
    UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;                                                   -- beide gemeinsam wirksam machen
```

Stell dir vor, der Server stürzt *zwischen* den beiden `UPDATE`s ab. Ohne Transaktion wäre das Geld bei A abgebucht, aber nie bei B angekommen — **verschwunden**. Mit Transaktion gilt: Kommt es nicht zum `COMMIT`, wird die erste Abbuchung automatisch zurückgerollt. Das Geld ist nie „halb überwiesen".

Das ist die **Atomarität** (das „A" in [[#ACID]], das als Nächstes im Detail kommt) in Aktion — hier zunächst rein praktisch.

## Die drei Grundbefehle (TCL)

Transaktionen werden über die **Transaction Control Language** gesteuert (vgl. die [[#Die Teilsprachen von SQL (DDL, DML, DQL, DCL, TCL)|Teilsprachen]]):

| Befehl | Wirkung |
|---|---|
| **`BEGIN`** (auch `START TRANSACTION`) | Startet eine Transaktion — ab hier werden Änderungen gesammelt, aber noch nicht endgültig |
| **`COMMIT`** | Macht *alle* Änderungen seit `BEGIN` dauerhaft und für andere sichtbar |
| **`ROLLBACK`** | Verwirft *alle* Änderungen seit `BEGIN` — der Stand von vor `BEGIN` bleibt |

```sql
BEGIN;
    DELETE FROM priceable_units WHERE product_id = 1;
    -- „Ups, falsches Produkt!"
ROLLBACK;                          -- nichts ist passiert, die Zeilen sind noch da
```

## Autocommit: jede einzelne Anweisung ist schon eine Transaktion

Wichtig zu verstehen: In PostgreSQL läuft **jede** SQL-Anweisung, die *nicht* explizit in `BEGIN … COMMIT` eingeschlossen ist, in ihrer **eigenen, automatisch committeten Transaktion** (**Autocommit**). Ein einzelnes `UPDATE ...` ist also bereits atomar — es wirkt vollständig oder gar nicht.

Der explizite `BEGIN … COMMIT`-Block ist genau dann nötig, wenn **mehrere** Anweisungen zusammen atomar sein sollen. Und praktisch relevant: Ein Client/ORM (siehe [[#SQLAlchemy und ORM in Python]]) öffnet für eine „Unit of Work" typischerweise eine Transaktion, führt mehrere Schreibvorgänge aus und committet am Ende gemeinsam.

## Savepoints: teilweiser Rollback

Innerhalb einer Transaktion kann man mit **`SAVEPOINT`** Zwischenmarken setzen und bei Bedarf nur bis dorthin zurückrollen, ohne die *ganze* Transaktion aufzugeben:

```sql
BEGIN;
    INSERT INTO products (name) VALUES ('Neu A');
    SAVEPOINT nach_a;
    INSERT INTO products (name) VALUES ('Neu B');
    ROLLBACK TO SAVEPOINT nach_a;   -- nur 'Neu B' verwerfen, 'Neu A' bleibt
    INSERT INTO products (name) VALUES ('Neu C');
COMMIT;                             -- 'Neu A' und 'Neu C' werden dauerhaft
```

Nützlich in längeren Transaktionen, in denen ein einzelner Teilschritt scheitern darf, ohne dass die bisherige Arbeit verloren geht.

## Warum Transaktionen? — die zwei Kernnutzen

1. **Fehler-/Absturzsicherheit (Atomarität + Dauerhaftigkeit)**: Mehrstufige Operationen hinterlassen nie einen inkonsistenten „halben" Zustand — weder bei einem Anwendungsfehler noch bei einem Stromausfall.
2. **Konsistenz bei Nebenläufigkeit (Isolation)**: Laufen viele Transaktionen *gleichzeitig*, sorgt die Datenbank dafür, dass sie sich nicht gegenseitig in inkonsistente Zwischenzustände hineinblicken lassen. Wie *streng* diese Abschottung ist, regeln die **Isolationsstufen** — und die behandeln wir zusammen mit dem „I" in [[#ACID]] gleich im nächsten Abschnitt im Detail.

## Bezug zur Übungsaufgabe

Sobald das Überführen der CSV-Daten aus *mehreren* Schritten besteht (z. B. erst ein Produkt in `products` anlegen, dann seine Buchungslagen in `priceable_units`), gehört das in **eine** Transaktion: Scheitert das Einfügen der Buchungslagen (etwa wegen eines Constraints), soll auch das zuvor angelegte Produkt nicht „halb" zurückbleiben. Ohne ORM setzt man dazu explizit `BEGIN … COMMIT` (bzw. steuert es über die Transaktions-API des Python-Treibers `psycopg`); mit SQLAlchemy übernimmt das die Session.

# Views

## Grundidee: eine gespeicherte Abfrage mit Namen

Eine **View** (Sicht) ist eine **benannte, gespeicherte `SELECT`-Abfrage**, die sich wie eine Tabelle abfragen lässt. Sie speichert selbst **keine Daten** — sie ist nur die *Definition* einer Abfrage. Fragt man die View ab, führt PostgreSQL im Hintergrund die hinterlegte `SELECT` aus und liefert das aktuelle Ergebnis. Man kann sich eine View als „virtuelle Tabelle" oder als **gespeichertes Rezept** vorstellen: Das Rezept liegt fest, die Zutaten (Daten in den zugrunde liegenden Tabellen) sind immer die aktuellen.

```sql
CREATE VIEW booking_overview AS
SELECT p.name        AS product_name,
       pu.calendar_date,
       pu.base_price,
       pu.booked_units,
       pu.bookable_units
FROM priceable_units AS pu
JOIN products        AS p ON p.id = pu.product_id;
```

Danach fragt man sie an wie eine ganz normale Tabelle:

```sql
SELECT * FROM booking_overview WHERE booked_units > 0;
```

Der komplexe [[#Joins und Unions|JOIN]] aus dem vorigen Abschnitt ist jetzt hinter dem schlichten Namen `booking_overview` versteckt.

## Wofür sind Views gut?

1. **Komplexität verstecken / Wiederverwendung**: Eine oft gebrauchte, komplizierte Abfrage (mehrere Joins, Aggregationen) schreibt man **einmal** als View und nutzt sie danach mit einem einfachen `SELECT * FROM view`. Ändert sich die Logik, passt man *eine* Stelle an. Das ist exakt das **DRY**-Prinzip (Don't Repeat Yourself) und die **Abstraktion**, die wir aus [[1.1 OOP - Vertiefung#Abstraktion|1.1]] kennen — nur auf Abfrageebene: Der Nutzer der View muss nicht wissen, *wie* das Ergebnis zustande kommt.
2. **Stabile Schnittstelle / Entkopplung**: Eine View kann die zugrunde liegende Tabellenstruktur nach außen stabil halten. Baut man die Tabellen intern um, kann man die View so anpassen, dass abfragender Code (oder Reports) unverändert weiterläuft — dasselbe **Information-Hiding**-Prinzip wie in [[1.1 OOP - Vertiefung|1.1]], nur für die Datenbank.
3. **Sicherheit / Zugriffskontrolle**: Man kann einer Nutzergruppe Zugriff nur auf eine View geben, die bewusst **nur bestimmte Spalten/Zeilen** zeigt (z. B. ohne sensible Gehaltsspalte), ohne Zugriff auf die volle Tabelle zu gewähren.

## Wichtig: Eine (normale) View speichert nichts

Der häufigste Denkfehler: Eine View ist **kein** Snapshot und **kein** Cache. Sie wird bei *jeder* Abfrage neu ausgewertet und zeigt daher **immer den aktuellen** Stand der Basistabellen. Das ist meist genau gewünscht (immer aktuell), hat aber eine Konsequenz: Ist die zugrunde liegende Abfrage teuer, ist auch jede Abfrage *auf die View* teuer — die View macht nichts „schneller", sie macht es nur **bequemer und wiederverwendbar**.

## Materialized Views — wenn doch gespeichert werden soll

Genau für den Performance-Fall gibt es die **Materialized View**: Sie speichert das Abfrageergebnis *physisch* auf der Platte. Abfragen darauf sind dann schnell (kein erneutes Ausführen der teuren Query), aber die Daten sind nur so aktuell wie die letzte **Aktualisierung** — die man explizit anstoßen muss:

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT calendar_date, SUM(base_price * booked_units) AS revenue
FROM priceable_units
GROUP BY calendar_date;

REFRESH MATERIALIZED VIEW daily_revenue;   -- neu berechnen (z. B. per nächtlichem Job)
```

| | Normale View | Materialized View |
|---|---|---|
| Speichert Daten? | Nein (nur die Abfrage-Definition) | Ja (das Ergebnis physisch) |
| Aktualität | Immer aktuell (live berechnet) | Stand der letzten `REFRESH` |
| Abfrage-Performance | So teuer wie die zugrunde liegende Query | Schnell (Ergebnis liegt vor) |
| Typischer Einsatz | Komplexität verstecken, stabile Schnittstelle | Teure Auswertungen/Reports cachen |

Die Materialized View ist damit auch ein sauberes Werkzeug für die kontrollierte [[#Kontrollfrage: Wann ist eine niedrigere Normalform (Denormalisierung) sinnvoll?|Denormalisierung]], die wir bei der Normalisierung angesprochen haben.

## Kann man in eine View schreiben? (kurz)

Grundsätzlich sind Views vor allem zum **Lesen** da. Ein `INSERT`/`UPDATE` auf eine *einfache* View (die genau einer Tabelle ohne Aggregation/Join entspricht) leitet PostgreSQL automatisch an die Basistabelle weiter. Sobald die View aber Joins, Aggregationen (`GROUP BY`) o. Ä. enthält, ist sie **nicht** ohne Weiteres beschreibbar — dann bräuchte man spezielle Konstrukte (`INSTEAD OF`-Trigger, [[1.2 Relationale Datenbanken & ORM - Leitfaden#Out of Scope|Out of Scope]]). Merke: Views sind primär eine Lese-Abstraktion.

## Bezug zur Übungsaufgabe

Die immer wiederkehrende „Buchungslage mit Produktname"-Abfrage (der JOIN aus dem [[#Joins und Unions|Joins-Abschnitt]]) ist ein idealer View-Kandidat: einmal als `booking_overview` definiert, danach überall bequem als `SELECT * FROM booking_overview` nutzbar — sowohl in weiteren SQL-Abfragen als auch als saubere Lese-Schnittstelle für Reports, ohne den Join jedes Mal neu auszuschreiben.

# ACID

## Was bedeutet ACID? (Kontrollfrage!)

> **Kontrollfrage aus dem Leitfaden:** *Was bedeutet ACID? In welchem Kontext ist es wichtig für Datenbanken?*

**ACID** ist ein Akronym für die vier Eigenschaften, die eine [[#Transactions|Transaktion]] in einem zuverlässigen Datenbanksystem garantiert. Sie sind der eigentliche Grund, warum man geschäftskritische Daten einem RDBMS wie [[#Was ist PostgreSQL — und warum ist es so beliebt? Kontrollfrage|PostgreSQL]] anvertraut:

| Buchstabe | Eigenschaft | Kernaussage |
|---|---|---|
| **A** | **Atomicity** (Atomarität) | Alles oder nichts — eine Transaktion wird ganz oder gar nicht wirksam |
| **C** | **Consistency** (Konsistenz) | Eine Transaktion führt von einem gültigen Zustand in einen anderen gültigen Zustand |
| **I** | **Isolation** (Isolation) | Gleichzeitige Transaktionen stören sich nicht gegenseitig |
| **D** | **Durability** (Dauerhaftigkeit) | Committete Änderungen überleben auch einen Stromausfall |

Der **Kontext**, in dem ACID zählt: überall, wo mehrstufige Änderungen und/oder **gleichzeitige Zugriffe** auf Daten passieren, deren Korrektheit wichtig ist — Finanztransaktionen, Bestellungen, Lagerbestände, Buchungen. Genau das Gegenteil des CSV-Ansatzes, mit dem wir das Kapitel begonnen haben, wo nichts davon garantiert ist.

## A — Atomicity (Atomarität)

Eine Transaktion ist **unteilbar**: Alle ihre Schritte werden gemeinsam wirksam (`COMMIT`) oder gemeinsam verworfen (`ROLLBACK`). Es gibt keinen Zustand, in dem nur die Hälfte passiert ist. Das haben wir im [[#Transactions|Transactions-Abschnitt]] am Geldüberweisungs-Beispiel gesehen: A abbuchen + B gutschreiben — nie nur das eine.

Technisch garantiert PostgreSQL das über ein **Write-Ahead-Log (WAL)**: Änderungen werden zuerst in ein Protokoll geschrieben, bevor sie die eigentlichen Datendateien berühren; ein abgebrochener Vorgang lässt sich daraus sauber zurückrollen.

## C — Consistency (Konsistenz)

Eine Transaktion überführt die Datenbank von einem **gültigen** Zustand in einen anderen **gültigen** Zustand — alle definierten Regeln bleiben gewahrt. „Gültig" heißt: Alle [[#Constraints|Constraints]] (`NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK`) und Regeln sind eingehalten. Verletzt eine Transaktion eine solche Regel, wird sie abgelehnt/zurückgerollt, statt einen ungültigen Zustand zu hinterlassen.

> Feinheit: Das „C" ist teils Sache der Datenbank (sie erzwingt die Constraints) und teils Sache des Entwicklers (die *fachliche* Konsistenz, z. B. dass eine Buchung überhaupt fachlich sinnvoll ist, muss man selbst korrekt modellieren). Deshalb wird das „C" manchmal als das „schwächste" ACID-Merkmal bezeichnet — es ergibt sich zum Teil aus A, I und D plus den Constraints.

## I — Isolation (Isolation) und die Nebenläufigkeits-Phänomene

Laufen mehrere Transaktionen **gleichzeitig**, sollen sie sich nach außen so verhalten, als liefen sie nacheinander. Wie *streng* diese Abschottung ist, regeln die **Isolationsstufen**. Ohne ausreichende Isolation können drei klassische **Nebenläufigkeits-Phänomene** (Anomalien) auftreten:

- **Dirty Read**: Transaktion T1 liest eine Änderung von T2, die T2 noch **nicht committet** hat — und dann macht T2 einen Rollback. T1 hat auf Daten reagiert, die es nie „offiziell" gab.
- **Non-Repeatable Read**: T1 liest dieselbe Zeile **zweimal** und bekommt **unterschiedliche Werte**, weil eine andere Transaktion sie zwischendurch geändert und committet hat.
- **Phantom Read**: T1 führt dieselbe **Bereichs-Abfrage** zweimal aus (z. B. „alle Buchungen im April") und bekommt beim zweiten Mal **zusätzliche/weniger Zeilen**, weil eine andere Transaktion welche eingefügt/gelöscht hat.

Der SQL-Standard definiert vier **Isolationsstufen**, die festlegen, welche dieser Phänomene erlaubt sind — je strenger, desto mehr Schutz, aber desto mehr Sperren/Aufwand:

| Isolationsstufe | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| **Read Uncommitted** | möglich | möglich | möglich |
| **Read Committed** | verhindert | möglich | möglich |
| **Repeatable Read** | verhindert | verhindert | möglich* |
| **Serializable** | verhindert | verhindert | verhindert |

**PostgreSQL-Besonderheiten** (wichtig, weil sie vom Lehrbuch abweichen):

- Der **Default ist `Read Committed`** — für die meisten Anwendungen der richtige Kompromiss.
- Dank [[#Was ist PostgreSQL — und warum ist es so beliebt? Kontrollfrage|MVCC]] kennt PostgreSQL **gar kein** echtes „Read Uncommitted" — ein Dirty Read ist hier grundsätzlich unmöglich, selbst auf der niedrigsten Stufe.
- (*) PostgreSQLs `Repeatable Read` verhindert dank MVCC sogar Phantom Reads schon mit — es ist strenger als der Standard es verlangt.
- `Serializable` ist die strengste Stufe (Transaktionen verhalten sich, als liefen sie streng nacheinander), erkauft aber mit möglichen „Serialization Failures", auf die die Anwendung mit einem Retry reagieren muss.

Die Isolationsstufe setzt man pro Transaktion:

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    -- ...
COMMIT;
```

## D — Durability (Dauerhaftigkeit)

Sobald eine Transaktion **committet** ist, sind ihre Änderungen **dauerhaft** — sie überleben Absturz, Stromausfall oder Neustart. Auch das leistet das **Write-Ahead-Log**: Vor der Bestätigung des `COMMIT` wird das Log auf ein dauerhaftes Medium geschrieben (`fsync`), sodass die Datenbank nach einem Absturz aus dem Log den committeten Stand wiederherstellen kann.

## ACID vs. BASE (kurze Einordnung)

Zum Abschluss die Brücke zurück zu [[#Relational vs. nicht-relational (NoSQL) — Kontrollfrage|relational vs. NoSQL]]: Viele NoSQL-Systeme setzen bewusst nicht auf ACID, sondern auf **BASE** (*Basically Available, Soft state, Eventual consistency*). Sie lockern die strengen Garantien zugunsten von Verfügbarkeit und horizontaler Skalierung — Daten sind dann *irgendwann* konsistent, nicht sofort. Das ist der grundlegende Trade-off (Stichwort **CAP-Theorem**): starke Konsistenz (ACID, klassisch relational) vs. maximale Verfügbarkeit/Partitionstoleranz (BASE, viele verteilte NoSQL-Systeme). Für unsere Übungsaufgabe mit ihren Integritätsanforderungen ist ACID genau richtig.

## Bezug zur Übungsaufgabe

ACID ist der theoretische Überbau dessen, was wir praktisch schon gebaut haben: Die [[#Constraints|Constraints]] sichern das **C**, die [[#Transactions|Transaktionen]] beim mehrschrittigen Überführen der CSV-Daten das **A**, PostgreSQLs MVCC/WAL das **I** und **D**. Man muss ACID nicht „einschalten" — es ist die Grundzusage von PostgreSQL, die man durch den Einsatz von Transaktionen und Constraints nutzt.

# SQLAlchemy und ORM in Python

## Was ist ein ORM? — die Theorie (Kontrollfrage!)

> **Kontrollfrage aus dem Leitfaden:** *Wie funktioniert ORM generell in der Theorie (nicht Python-spezifisch)?*

**ORM** steht für **Object-Relational Mapping**. Es überbrückt zwei unterschiedliche Welten:

- die **objektorientierte** Welt unseres Programms (Klassen, Objekte, Attribute, Referenzen — vgl. [[1.1 OOP - Vertiefung|1.1 OOP]])
- die **relationale** Welt der Datenbank (Tabellen, Zeilen, Spalten, Fremdschlüssel)

Ein ORM ist eine Bibliothek, die diese beiden Welten **automatisch aufeinander abbildet** (mapped). Die Grundregeln der Abbildung sind immer dieselbe, sprachunabhängige Idee:

| Objektwelt | ↔ | Relationale Welt |
|---|---|---|
| Klasse | ↔ | Tabelle |
| Objekt (Instanz) | ↔ | Zeile (Tupel) |
| Attribut | ↔ | Spalte |
| Referenz auf ein anderes Objekt | ↔ | Fremdschlüssel-Beziehung |

Statt SQL-Strings von Hand zu schreiben, arbeitet man mit **ganz normalen Objekten der Programmiersprache**, und das ORM übersetzt diese Operationen im Hintergrund in SQL:

- `session.add(product)` → `INSERT INTO products ...`
- `product.name = "Neu"` (nach dem Laden) → `UPDATE products SET name = ...`
- `session.get(Product, 1)` → `SELECT * FROM products WHERE id = 1`

Das Problem, das ein ORM löst, hat sogar einen Namen: die **Object-Relational Impedance Mismatch** — die konzeptionelle Reibung, dass Objektgraphen (mit Vererbung, Referenzen, Identität) und flache Tabellen (mit Werten, Joins, Schlüsseln) eben *nicht* dasselbe sind. Das ORM verwaltet diese Übersetzung, damit man nicht ständig manuell zwischen „Zeile ↔ Objekt" hin- und herkonvertieren muss.

### Was ein ORM „unter der Haube" leisten muss

Damit die obige Abbildung funktioniert, muss ein ORM (sprachunabhängig) im Kern vier Dinge erledigen — gut, das einmal explizit zu sehen, weil es erklärt, *warum* ein ORM so viel „Magie" enthält:

1. **Metadaten-Verwaltung**: Es muss wissen, welche Klasse auf welche Tabelle und welches Attribut auf welche Spalte (mit welchem Typ) zeigt. Diese „Landkarte" nennt man das *Mapping* bzw. die *Metadata*.
2. **SQL-Generierung**: Aus Objektoperationen die passenden `INSERT`/`UPDATE`/`DELETE`/`SELECT`-Strings erzeugen — inklusive korrekter Reihenfolge bei Beziehungen (erst das Elternteil, dann das Kind mit dem frischen Fremdschlüssel).
3. **Identität & Zustandsverfolgung (Change Tracking)**: Es muss erkennen, *welche* geladenen Objekte sich seit dem Laden geändert haben, um nur diese zu speichern (dazu unten „Objektzustände").
4. **Typkonvertierung**: Zwischen DB-Typen und Sprachtypen übersetzen (z. B. `NUMERIC` ↔ `Decimal`, `TIMESTAMP` ↔ `datetime`).

### Zwei ORM-Grundmuster: Active Record vs. Data Mapper

Ein zentraler theoretischer Punkt, der die ORM-Landschaft ordnet: Es gibt **zwei grundlegende Architekturmuster** dafür, *wo* die Persistenz-Logik lebt (beide von Martin Fowler geprägt):

|           | **Active Record**                                                    | **Data Mapper**                                                                      |
| --------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Idee      | Das Modellobjekt *kennt sich selbst* und weiß, wie es sich speichert | Die Persistenz liegt in einer *separaten* Schicht; das Modell weiß nichts von der DB |
| Speichern | `product.save()` (das Objekt spricht selbst mit der DB)              | `session.add(product); session.commit()` (eine Session vermittelt)                   |
| Kopplung  | Modell und DB-Zugriff eng verwoben                                   | Modell (reines Domänenobjekt) und DB sauber getrennt                                 |
| Beispiele | Ruby on Rails, **Django ORM**                                        | **SQLAlchemy (ORM)**, Hibernate (Java)                                               |
| Vorteil   | Sehr einfach/schnell für Standardfälle                               | Bessere Trennung der Belange, testbarer, flexibler                                   |

**SQLAlchemy folgt bewusst dem Data-Mapper-Muster** — das erklärt seine Bauweise: Die Modellklassen bleiben (weitgehend) reine Datenobjekte, und eine separate **`Session`** kümmert sich um alles Persistente. Das ist genau die [[1.1 OOP - Vertiefung#Separation of Concerns|Separation of Concerns]] aus Kapitel 1.1, angewandt auf Datenzugriff: Business-Objekt und Persistenz sind getrennt. (Django nutzt dagegen Active Record — dort erbt ein Modell von `models.Model` und hat eine eigene `.save()`-Methode.)

## Wie funktioniert SQLAlchemy? Wie wird es standardmäßig implementiert? (Kontrollfrage!)

> **Kontrollfrage aus dem Leitfaden:** *Wie funktioniert SQLAlchemy? Wie wird es standardmäßig implementiert?*

**SQLAlchemy** ist das mit Abstand verbreitetste ORM/Datenbank-Toolkit für Python. Es besteht aus **zwei Schichten**, was ein wichtiges Alleinstellungsmerkmal ist:

1. **Core** (SQL Expression Language): eine Schicht, um SQL programmatisch, aber sehr nah an SQL zu bauen — ohne volles Objekt-Mapping. Gibt volle Kontrolle.
2. **ORM**: die höhere Schicht mit dem eigentlichen Klassen-↔-Tabellen-Mapping, auf der man die meiste Zeit arbeitet. Sie baut auf dem Core auf.

### Die Standard-Bausteine

Ein typisches SQLAlchemy-Setup (moderne 2.0-Schreibweise) besteht aus:

```python
from sqlalchemy import create_engine, ForeignKey, String, Numeric
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship, Session

# 1) Engine: die Verbindung zur Datenbank (Connection Pool inklusive)
engine = create_engine("postgresql+psycopg://user:pass@localhost/pricing")

# 2) Declarative Base: gemeinsame Basisklasse für alle Modelle
class Base(DeclarativeBase):
    pass

# 3) Modelle: Klassen, die auf Tabellen gemappt werden
class Product(Base):
    __tablename__ = "products"
    id:   Mapped[int]  = mapped_column(primary_key=True)
    name: Mapped[str]  = mapped_column(String(200))
    # Beziehung: ein Produkt hat viele priceable_units (1:n aus dem Beziehungstypen-Abschnitt)
    units: Mapped[list["PriceableUnit"]] = relationship(back_populates="product")

class PriceableUnit(Base):
    __tablename__ = "priceable_units"
    id:         Mapped[int]   = mapped_column(primary_key=True)
    product_id: Mapped[int]   = mapped_column(ForeignKey("products.id"))
    base_price: Mapped[float] = mapped_column(Numeric(10, 2))
    product:    Mapped["Product"] = relationship(back_populates="units")
```

Man erkennt direkt alle Konzepte des Kapitels wieder: `primary_key=True` ([[#Datenbankdesign|PK]]), `ForeignKey` ([[#Foreign Keys|FK]]), `relationship` (die [[#Beziehungstypen — One-to-One, One-to-Many, Many-to-Many|1:n-Beziehung]]).

### Das Herzstück: die `Session` und das Unit-of-Work-Muster

Die **standardmäßige** Arbeitsweise mit dem ORM läuft über die **`Session`**. Sie ist der Dreh- und Angelpunkt und implementiert zwei klassische Muster:

- **Unit of Work**: Die Session **sammelt** alle Änderungen (neue, geänderte, gelöschte Objekte) und schreibt sie **gebündelt** beim `commit()` in **einer [[#Transactions|Transaktion]]** in die Datenbank. Man ändert Objekte einfach im Speicher; die Session merkt sich, was zu tun ist.
- **Identity Map**: Innerhalb einer Session gibt es pro Datenbankzeile **genau ein** Objekt — lädt man dieselbe Zeile zweimal, bekommt man dasselbe Python-Objekt zurück (Konsistenz + Caching).

```python
with Session(engine) as session:
    product = Product(name="Segeltörn")
    product.units.append(PriceableUnit(base_price=19.99))  # Beziehung rein objektorientiert setzen
    session.add(product)          # als "neu" vormerken
    session.commit()              # EINE Transaktion: INSERT products + INSERT priceable_units
```

Die Session öffnet also im Hintergrund eine Transaktion, führt beim `commit()` die passenden `INSERT`/`UPDATE`/`DELETE` in korrekter Reihenfolge aus (erst das Produkt, dann die Unit mit der frisch vergebenen `product_id`) und committet gemeinsam — genau das [[#Transactions|Transaktions-Prinzip]], aber automatisch.

### Abfragen

```python
from sqlalchemy import select

with Session(engine) as session:
    stmt = select(Product).where(Product.name == "Segeltörn")
    product = session.scalars(stmt).first()
    print(product.units)          # löst bei Zugriff ein SELECT auf priceable_units aus (Lazy Loading)
```

### Der vollständige CRUD-Zyklus im ORM

Damit klar wird, wie sich *jede* Grundoperation anfühlt — die vier CRUD-Operationen (Create, Read, Update, Delete) mit dem ORM, jeweils rein objektorientiert:

```python
with Session(engine) as session:
    # CREATE ---------------------------------------------------------
    p = Product(name="Kochkurs")
    session.add(p)
    session.commit()                       # INSERT INTO products ...

    # READ -----------------------------------------------------------
    p = session.get(Product, 1)            # SELECT ... WHERE id = 1  (per Primärschlüssel)
    liste = session.scalars(               # SELECT ... WHERE name LIKE 'K%'
        select(Product).where(Product.name.like("K%")).order_by(Product.name)
    ).all()

    # UPDATE ---------------------------------------------------------
    p.name = "Kochkurs Deluxe"             # nur das Attribut ändern ...
    session.commit()                       # ... die Session erkennt die Änderung -> UPDATE

    # DELETE ---------------------------------------------------------
    session.delete(p)                      # als "zu löschen" vormerken
    session.commit()                       # DELETE FROM products WHERE id = ...
```

Der entscheidende Aha-Moment beim **UPDATE**: Man ruft *keine* Speicher-Methode auf der Zeile auf — man ändert einfach ein Attribut eines geladenen Objekts, und die Session **erkennt beim `commit()` von selbst**, dass sich dieses Objekt geändert hat (Change Tracking, s. o.), und erzeugt das passende `UPDATE`. Genau das ist das Data-Mapper-Muster in Aktion.

### Objektzustände & der Session-Lebenszyklus (`flush` vs. `commit`)

Um das Change Tracking wirklich zu verstehen, muss man wissen, dass jedes gemappte Objekt bezogen auf eine Session einen von vier **Zuständen** hat:

| Zustand | Bedeutung |
|---|---|
| **transient** | Frisch mit `Product(...)` erzeugt, der Session **nicht** bekannt, (noch) keine DB-Zeile |
| **pending** | Mit `session.add()` vorgemerkt, aber noch nicht in die DB geschrieben |
| **persistent** | Hat eine DB-Zeile und ist von der Session verwaltet (Änderungen werden verfolgt) |
| **detached** | Hat eine DB-Zeile, gehört aber zu **keiner** aktiven Session mehr (z. B. nach `session.close()`) |

Der Übergang pending → persistent passiert beim **`flush`** — und hier ein Unterschied, den viele verwechseln:

- **`flush()`** sendet die gesammelten `INSERT`/`UPDATE`/`DELETE` an die Datenbank (innerhalb der laufenden Transaktion), sodass z. B. eine `SERIAL`-`id` schon vergeben ist — die Transaktion ist aber **noch nicht committet** und kann noch zurückgerollt werden. (SQLAlchemy flusht oft *automatisch*, bevor eine Abfrage ausgeführt wird, damit diese die noch nicht committeten Änderungen bereits „sieht".)
- **`commit()`** macht ein `flush` **und** committet danach die Transaktion — jetzt sind die Änderungen dauerhaft ([[#Transactions|COMMIT]]) und für andere sichtbar.

Ein weiterer wichtiger Effekt: Nach einem `commit()` sind die Objekte standardmäßig **expired** — der nächste Attributzugriff lädt frische Werte aus der DB nach (`refresh`). Das verhindert veraltete Daten, ist aber der Grund, warum man auf ein Objekt nach `session.close()` (Zustand *detached*) nicht mehr beliebig zugreifen kann, ohne eine `DetachedInstanceError` zu riskieren.

### Beziehungen: n:m mit `secondary`

Die [[#Many-to-Many (n:m) — die Verknüpfungstabelle (Kontrollfrage!)|n:m-Beziehung]] über eine Verknüpfungstabelle bildet das ORM elegant ab — man weist `relationship` per `secondary` die Zwischentabelle zu und arbeitet danach mit einer ganz normalen Python-Liste:

```python
from sqlalchemy import Table, Column

product_tags = Table(                       # die reine Verknüpfungstabelle
    "product_tags", Base.metadata,
    Column("product_id", ForeignKey("products.id"), primary_key=True),
    Column("tag_id",     ForeignKey("tags.id"),     primary_key=True),
)

class Product(Base):
    __tablename__ = "products"
    id:   Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(200))
    tags: Mapped[list["Tag"]] = relationship(secondary=product_tags, back_populates="products")

class Tag(Base):
    __tablename__ = "tags"
    id:   Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(100), unique=True)
    products: Mapped[list["Product"]] = relationship(secondary=product_tags, back_populates="tags")

# Nutzung: die beiden Joins aus dem Beziehungstypen-Abschnitt entfallen komplett
product.tags.append(some_tag)               # das ORM pflegt die Zeile in product_tags selbst
```

Die zwei Joins, die wir im [[#Beziehungstypen — One-to-One, One-to-Many, Many-to-Many|Beziehungstypen-Abschnitt]] von Hand schreiben mussten, erledigt das ORM hier im Hintergrund — das ist einer der größten Bequemlichkeitsgewinne eines ORM.

### Ladestrategien: Lazy vs. Eager (und die N+1-Lösung)

Wie eine Beziehung geladen wird, ist konfigurierbar — und genau hier entscheidet sich Performance:

- **Lazy Loading** (Default): `product.units` löst *erst beim Zugriff* ein eigenes `SELECT` aus. Bequem, aber die Quelle des N+1-Problems (unten).
- **Eager Loading**: Die Beziehung wird gleich mitgeladen. Zwei gängige Strategien:
  - `selectinload(Product.units)` — lädt alle Kinder in *einer* zusätzlichen `SELECT ... WHERE product_id IN (...)`-Abfrage (meist die beste Wahl).
  - `joinedload(Product.units)` — lädt Eltern und Kinder in *einem* JOIN.

```python
from sqlalchemy.orm import selectinload

# Statt N+1: 2 Abfragen insgesamt, egal wie viele Produkte
stmt = select(Product).options(selectinload(Product.units))
for product in session.scalars(stmt):
    print(product.name, len(product.units))   # kein zusätzliches SELECT pro Produkt mehr
```

### Ganz ohne ORM: derselbe Vorgang mit rohem SQL (`psycopg`)

Weil die [[1.2 Relationale Datenbanken & ORM - Leitfaden#Übungsaufgabe|Übungsaufgabe]] beide Wege verlangt, hier dieselbe „Produkt + Buchungslage anlegen"-Operation einmal **ohne** ORM, direkt über den PostgreSQL-Treiber `psycopg`. Ausführliche Referenz zu den psycopg-Objekten und -Methoden: [[psycopg 3 Grundlagen|psycopg 3 Grundlagen]].

```python
import psycopg

with psycopg.connect("postgresql://user:pass@localhost/pricing") as conn:
    with conn.cursor() as cur:
        # INSERT ... RETURNING, um die frische id zu bekommen (SQL selbst schreiben!)
        cur.execute(
            "INSERT INTO products (name) VALUES (%s) RETURNING id",
            ("Segeltörn",),
        )
        product_id = cur.fetchone()[0]
        cur.execute(
            "INSERT INTO priceable_units (product_id, base_price) VALUES (%s, %s)",
            (product_id, 19.99),
        )
    conn.commit()          # explizite Transaktion — man steuert alles selbst
```

Der Vergleich macht die Trade-offs greifbar:

|                         | Roh mit `psycopg`                                                               | Mit SQLAlchemy (ORM)                         |
| ----------------------- | ------------------------------------------------------------------------------- | -------------------------------------------- |
| SQL                     | Man schreibt jedes Statement selbst                                             | Wird generiert                               |
| Ergebnis                | `tuple`/`dict` pro Zeile — manuelles Mapping                                    | Fertige Objekte (`Product`, `PriceableUnit`) |
| Beziehungen             | FK-Werte von Hand durchreichen                                                  | `product.units.append(...)`                  |
| Transaktion/Reihenfolge | Selbst steuern                                                                  | Session/Unit of Work erledigt es             |
| Kontrolle über das SQL  | Maximal (jedes Zeichen)                                                         | Indirekt (aber via Core/`text()` möglich)    |
| Boilerplate             | Viel                                                                            | Wenig                                        |
| Risiko                  | SQL-Injection bei String-Bau (deshalb **immer** Parameter `%s`, nie f-Strings!) | Weitgehend abgeschirmt                       |

Das ist exakt die Diskussion, die der zweite Aufgabenteil verlangt: Das ORM spart Boilerplate und hält den Code objektorientiert, kostet dafür Kontrolle und etwas „Magie". Beides kann man erst *fundiert* gegeneinander abwägen, wenn man — wie in diesem Kapitel — das SQL darunter versteht.

### Migrationen: wie das Schema mitwächst (kurz)

Ein letzter Praxis-Baustein: Wenn sich die Modelle ändern (neue Spalte, neue Tabelle), muss auch das DB-Schema nachgezogen werden. Dafür nutzt man im SQLAlchemy-Ökosystem **Alembic** — es vergleicht die Modelle mit dem Ist-Zustand der DB und generiert versionierte Migrationsskripte (`upgrade`/`downgrade`), die man ins Git eincheckt. ## Warum ORMs kritisiert werden (Kontrollfrage!)

> **Kontrollfrage aus dem Leitfaden:** *ORM-Frameworks werden auch teilweise kritisiert. Was spricht gegen ihren Einsatz?*

ORMs sind mächtig, aber kein Allheilmittel. Die wichtigsten Kritikpunkte:

1. **Das N+1-Query-Problem** (der Klassiker): Iteriert man über 100 Produkte und greift je auf `product.units` zu, feuert das ORM bei naivem Lazy Loading **1 Query für die Produkte + 100 Queries für die Units** = 101 statt idealerweise 2. Solche versteckten Performance-Fallen entstehen, weil das ORM Datenbankzugriffe *verschleiert*. (Lösung: gezieltes Eager Loading / Joins — man muss das Problem aber erst kennen.)
2. **Leaky Abstraction**: Das ORM verspricht, SQL zu verstecken — aber sobald es um Performance geht, **muss** man doch verstehen, welches SQL erzeugt wird. Die Abstraktion „leckt". (Genau deshalb lernt man in diesem Kapitel erst SQL *ohne* ORM.)
3. **Komplexe Abfragen werden umständlich**: Für anspruchsvolle Analytics/Reporting-Queries (Window Functions, komplexe CTEs) ist handgeschriebenes SQL oft klarer und schneller als der Versuch, es durch die ORM-API zu zwängen.
4. **Overhead & Magie**: Das Mapping, die Identity Map, das Change Tracking kosten etwas Performance und verstecken viel „Magie", die man verstehen muss, um Fehler zu debuggen.
5. **Impedance Mismatch bleibt**: Das ORM *verwaltet* die Reibung zwischen Objekt- und Tabellenwelt, aber es *beseitigt* sie nicht — an den Rändern (Vererbung, komplexe Beziehungen) wird es kompliziert.

Der ausgewogene Konsens: Ein ORM ist hervorragend für den **Großteil der alltäglichen CRUD-Operationen** (spart enorm viel Boilerplate, hält Code objektorientiert). Für die **wenigen performance-kritischen oder komplexen Abfragen** greift man bewusst auf handgeschriebenes SQL zurück — was gute ORMs (auch SQLAlchemy über den Core) ausdrücklich erlauben. Deshalb ist es kein „ORM *oder* SQL", sondern „ORM *und*, wo nötig, SQL". Und genau darum ist das Fundament aus diesem Kapitel (SQL, Joins, Indizes, Transaktionen) die Voraussetzung, um ein ORM überhaupt *verantwortungsvoll* einzusetzen.

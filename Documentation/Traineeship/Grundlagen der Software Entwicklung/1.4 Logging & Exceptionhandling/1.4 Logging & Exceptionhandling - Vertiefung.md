# Loggen von Exceptions

## Mini-Grundlage vorweg

Der Leitfaden startet mitten im Thema, deshalb hier nur so viel Vorwissen, wie dieser Abschnitt braucht — die Details kommen in den späteren Stichworten:

> [!info] Das Nötigste zum `logging`-Modul
> - Man loggt nicht mit `print`, sondern über einen **Logger**: `logger = logging.getLogger(__name__)` — einmal ganz oben pro Modul. `__name__` sorgt dafür, dass die Meldung später ihren Herkunftsort kennt (`pricing.core.builder`).
> - Jede Meldung hat ein **Level**: `debug` < `info` < `warning` < `error` < `critical`. Details: Stichwort *Logging-Level*.
> - **Wo** die Meldung landet (Konsole, Datei) und **wie** sie aussieht, entscheidet nicht der Logger, sondern die Konfiguration am Programmrand. Details: Stichwort *Logging in Theorie und Praxis*.
>
> In unserem Projekt existiert dieses Muster schon, z. B. in `core/builder.py`:
> ```python
> import logging
> logger = logging.getLogger(__name__)
> ...
> logger.warning("%d Einheiten mit negativer Kapazität", neg)
> ```

## Warum Exceptions ein eigenes Logging-Thema sind

Eine normale Logmeldung ist ein Satz, den *du* formulierst. Eine Exception ist etwas anderes: Sie bringt einen **Datensatz** mit, den der Python-Interpreter für dich zusammengestellt hat — und der ist die wertvollste Information, die dein Programm im Fehlerfall besitzt.

Der Kern des Stichworts lautet deshalb: **Beim Loggen einer Exception darf dieser Datensatz nicht verloren gehen.** Fast alle Fehler, die man in echten Systemen beim Debuggen macht, sind Varianten desselben Fehlers — man wirft Information weg, die man zehn Minuten später dringend bräuchte.

Der Leitfaden begründet in der [[1.4 Logging & Exceptionhandling - Leitfaden#Motivation|Motivation]], warum: Ein Log ist nicht nur Debugging-Material, sondern auch Grundlage für Monitoring, Analyse, Nachvollziehbarkeit und Audits. Ein Fehler, der nirgends steht, ist für all das nicht existent — er ist aber trotzdem passiert.

## Was in einer Exception eigentlich drinsteckt

Eine Exception besteht aus **drei** Teilen, die zusammen erst das ganze Bild ergeben (das nennt Python intern `exc_info` — ein Tripel):

| Teil | Beispiel | Was es beantwortet |
|---|---|---|
| **Typ** | `KeyError` | *Was* für ein Fehler ist es? |
| **Wert / Nachricht** | `'DB_PRICING_PW'` | Welcher konkrete Fall? |
| **Traceback** | die Aufrufkette bis zur Fehlerstelle | *Wo* und über welchen Weg? |

Dazu kommen zwei Verweise auf **vorherige** Exceptions: `__cause__` (explizit gesetzt mit `raise ... from e`) und `__context__` (implizit, wenn während der Behandlung eines Fehlers ein neuer auftritt). Dazu unten mehr.

Warum das wichtig ist, zeigt ein Blick auf `str(e)` — das, was die meisten beim Loggen benutzen:

```python
try:
    {}["DB_PW"]
except Exception as e:
    print(str(e))    # → 'DB_PW'      ← nur der Schlüsselname!

try:
    [][3]
except Exception as e:
    print(str(e))    # → list index out of range   ← immerhin ein Satz
```

Bei `KeyError` ist `str(e)` also nur `'DB_PW'` — **ohne** die Information, dass es überhaupt ein `KeyError` war, und **ohne** jede Ortsangabe. Ein Logeintrag `ERROR: Fehler: 'DB_PW'` um 03:14 Uhr nachts ist praktisch wertlos. Genau diese Falle lauert übrigens real in unserem Projekt in `adapters/db.py`:

```python
def get_dsn() -> str:
    pw = os.environ["DB_PRICING_PW"]   # KeyError: 'DB_PRICING_PW'
```

> [!tip] Merksatz
> `str(e)` ist die **ärmste** Form der Fehlerinformation. Typ und Traceback sind das, was das Debuggen tatsächlich abkürzt — und beide gehen bei `str(e)` verloren.

## Das Werkzeug: `logger.exception()`

Das `logging`-Modul hat dafür eine eigene Methode. Sie ist der Kern dieses Stichworts:

```python
try:
    riskante_operation()
except ValueError:
    logger.exception("Verarbeitung der Preisdatei fehlgeschlagen")
```

Was dabei passiert:

- Die Meldung wird auf Level **ERROR** geloggt (`logger.exception` ist exakt `logger.error(..., exc_info=True)`).
- Zusätzlich wird der **komplette Traceback** an die Meldung angehängt — automatisch, ohne dass du ihn irgendwo herholen musst.

Ausgabe:

```text
ERROR demo: Verarbeitung der Preisdatei fehlgeschlagen
Traceback (most recent call last):
  File "/tmp/lg.py", line 21, in <module>
    riskante_operation()
  File "/tmp/lg.py", line 19, in riskante_operation
    raise KeyError("DB_PW")
KeyError: 'DB_PW'
```

Damit hast du **alle drei** Teile im Log: Typ, Wert, Traceback — plus deinen erklärenden Satz, *was* das Programm gerade versucht hat. Beides zusammen ist der Idealfall: Die Exception sagt, *was technisch schiefging*, deine Nachricht sagt, *was fachlich versucht wurde*.

### Die Varianten im Überblick

| Aufruf | Level | Traceback? | Wann benutzen |
|---|---|---|---|
| `logger.exception("...")` | ERROR (fest) | ja | Standardfall im `except`-Block |
| `logger.error("...", exc_info=True)` | ERROR | ja | identisch — explizitere Schreibweise |
| `logger.warning("...", exc_info=True)` | WARNING | ja | Fehler ist aufgetreten, aber sauber behandelt → soll nicht als ERROR alarmieren |
| `logger.critical("...", exc_info=True)` | CRITICAL | ja | Programm kann nicht weiterlaufen |
| `logger.error("...", exc_info=err)` | ERROR | ja | Exception-Objekt liegt vor, aber wir sind **nicht** im `except`-Block |
| `logger.error(str(e))` | ERROR | **nein** | ✗ Anti-Muster, s. u. |

Die vorletzte Zeile ist der weniger bekannte Trick: `exc_info` akzeptiert nicht nur `True`, sondern auch **eine Exception-Instanz**. Nützlich, wenn du einen Fehler zwischenspeicherst (z. B. in einer Schleife sammelst) und erst später loggst:

```python
fehler: list[Exception] = []
for datei in dateien:
    try:
        verarbeite(datei)
    except OSError as e:
        fehler.append(e)

for e in fehler:
    logger.error("Datei konnte nicht verarbeitet werden", exc_info=e)
```

### Fallstrick: `logger.exception()` außerhalb eines `except`-Blocks

`logger.exception` holt sich die Exception nicht aus einem Argument, sondern aus dem **aktuell behandelten Fehler** (intern `sys.exc_info()`). Ruft man sie auf, wenn gerade keiner behandelt wird, kommt das hier heraus:

```text
ERROR demo: kein aktiver Handler
NoneType: None
```

`NoneType: None` ist die typische Signatur für „hier wurde `exception()` an der falschen Stelle aufgerufen". Merke: **`logger.exception()` gehört ausschließlich in einen `except`-Block** (oder in eine Funktion, die von dort aufgerufen wird, solange der Handler noch aktiv ist).

### Verwandt: `stack_info=True`

Nicht zu verwechseln mit `exc_info`. `stack_info=True` hängt den **aktuellen Aufruf-Stack** an — auch ohne Exception. Beantwortet die Frage: *„Wer ruft diese Stelle überhaupt auf?"*

```python
logger.warning("Fallback-Preis verwendet", stack_info=True)
```
```text
WARNING demo: Fallback-Preis verwendet
Stack (most recent call last):
  File "/tmp/lg.py", line 40, in <module>
    logger.warning("Fallback-Preis verwendet", stack_info=True)
```

Praktisch bei „das dürfte eigentlich nie passieren"-Warnungen, deren Ursache im Aufrufpfad liegt.

## Die Anti-Muster

Diese fünf sind die häufigsten Arten, Fehlerinformation zu verlieren. Sie zu erkennen ist der eigentliche Lernertrag dieses Stichworts.

### 1. Das schwarze Loch: `except: pass`

```python
try:
    preis = berechne_preis(unit)
except Exception:
    pass          # ✗ der Fehler hat nie stattgefunden
```

Der Fehler verschwindet spurlos: kein Log, kein Traceback, kein Hinweis. Das Programm läuft mit falschen oder fehlenden Daten weiter, und die Ursache ist Wochen später nicht mehr rekonstruierbar. Das ist die teuerste Zeile Code in dieser ganzen Notiz.

Noch schlimmer ist die Variante ohne Exception-Typ (`except:` — „bare except"), weil sie zusätzlich `KeyboardInterrupt` und `SystemExit` abfängt: Das Programm lässt sich dann nicht einmal mehr mit Strg+C beenden.

Wenn ein Fehler wirklich ignoriert werden darf, dann **bewusst, eng und dokumentiert**:

```python
try:
    cache_datei.unlink()
except FileNotFoundError:
    logger.debug("Cache-Datei war schon weg — nichts zu tun.")
```

### 2. Traceback wegwerfen: `logger.error(str(e))` / `print(e)`

```python
except ValueError as e:
    logger.error(f"Fehler beim Parsen: {e}")     # ✗ Traceback weg
```

Der wohl häufigste Fehler überhaupt — und er *fühlt* sich richtig an, weil ja etwas im Log steht. Aber: Typ und Traceback fehlen, und bei `KeyError` bleibt (siehe oben) nur ein nackter Schlüsselname übrig. Richtig:

```python
except ValueError:
    logger.exception("Fehler beim Parsen der Preisdatei")   # ✓
```

*(Der f-String ist hier zusätzlich problematisch — warum, kommt beim Stichwort **Parametrisierte Logs**.)*

### 3. Doppeltes Logging (log-and-rethrow)

```python
def lade_preise(pfad: Path) -> list[Row]:
    try:
        return _parse(pfad)
    except OSError:
        logger.exception("Laden fehlgeschlagen")   # ✗ hier schon geloggt …
        raise                                       # … und oben nochmal
```

Wenn jede Schicht denselben Fehler loggt, steht ein einziges Problem drei- bis fünfmal im Log — mit fast identischem Traceback. Das Log wird unlesbar und Monitoring-Alarme zählen einen Vorfall mehrfach.

> [!important] Faustregel
> **Log *oder* raise — nicht beides.** Geloggt wird dort, wo der Fehler **behandelt** wird (also eine Entscheidung fällt), typischerweise am Rand der Anwendung. Wer den Fehler nur weiterreicht, loggt nicht.

Legitime Ausnahme: Man reichert unterwegs **Kontext** an, den die obere Schicht nicht mehr hat — dann aber besser über `raise ... from e` mit einer sprechenden neuen Exception oder über `add_note()` (s. u.) statt über einen zweiten Logeintrag.

### 4. Zu breit fangen: `except Exception` überall

```python
try:
    ergebnis = engine.recommend(units)
except Exception:                # ✗ fängt auch Tippfehler, AttributeError, …
    logger.exception("Empfehlung fehlgeschlagen")
```

Ein breites `except Exception` fängt auch **Programmierfehler** (`AttributeError`, `TypeError`), die man gar nicht behandeln *kann* — sie werden dadurch zu „normalen Betriebsmeldungen" degradiert und verschleiern echte Bugs. Fange so eng wie möglich: den Fehlertyp, den du an dieser Stelle tatsächlich erwartest und beantworten kannst.

Genau **eine** Stelle darf breit fangen: der äußerste Rand (`main`), damit nichts unbemerkt nach draußen fällt — siehe unten.

### 5. Loggen und dann so tun, als wäre nichts

```python
except ValueError:
    logger.exception("Preis ungültig")
    # kein raise, kein return, kein Fallback → Code läuft weiter
```

Ein Logeintrag ist **keine Fehlerbehandlung**. Nach dem Loggen braucht es eine Entscheidung: Fallback, Überspringen (mit gezähltem Ergebnis), Abbruch, Exit-Code. Das schöne Muster dafür haben wir im Projekt schon — `core/builder.py` überspringt fehlerhafte Einheiten und meldet am Ende die Summe:

```python
if neg:
    logger.warning("%d Einheiten mit negativer Kapazität", neg)
```

Das ist bewusstes Behandeln („überspringen und zählen"), nicht Ignorieren.

## Exception-Chaining: die Vorgeschichte mitloggen

Häufig will man einen technischen Low-Level-Fehler in einen **sprechenden** fachlichen Fehler übersetzen. Genau dafür gibt es `raise ... from e`:

```python
try:
    pw = os.environ["DB_PRICING_PW"]
except KeyError as e:
    raise KonfigurationsFehler("DB-Passwort nicht gesetzt") from e
```

Beim Loggen mit `logger.exception()` erscheinen **beide** Tracebacks, verbunden durch einen Erklärungssatz:

```text
KeyError: 'DB_PW'

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  ...
RuntimeError: Konfiguration fehlt
```

Man bekommt also die verständliche Botschaft *und* behält die technische Ursache. Ohne `from e` passiert das übrigens **auch**, nur mit anderem Verbindungssatz:

| Schreibweise | Attribut | Text im Traceback |
|---|---|---|
| `raise Neu() from e` | `__cause__` | *The above exception was the **direct cause** of the following exception* |
| `raise Neu()` (im `except`) | `__context__` | *During handling of the above exception, **another exception occurred*** |
| `raise Neu() from None` | — | Vorgeschichte wird **unterdrückt** |

`from None` ist die einzige Form, die Information *bewusst* verwirft — sinnvoll nur, wenn die interne Ursache für den Empfänger irrelevant oder sogar sensibel ist (z. B. an einer API-Grenze). Im Log will man sie fast immer behalten.

> [!tip] Seit Python 3.11: `add_note()`
> Wenn man den Fehler *nicht* ersetzen, sondern nur anreichern will, gibt es `e.add_note("…")` ([PEP 678](https://peps.python.org/pep-0678/)) — die Notiz erscheint direkt unter dem Traceback:
> ```python
> except KeyError as e:
>     e.add_note(f"Datei: {pfad}")
>     raise
> ```
> ```text
> KeyError: 'DB_PW'
> Datei: daily_data/20260108_prices.csv
> ```
> Unser Projekt läuft auf Python 3.13 (`requires-python = ">=3.11"`), das ist also verfügbar. Es ist die saubere Alternative zum Anti-Muster „doppeltes Logging", wenn man unterwegs nur Kontext ergänzen möchte.

## Wo im Programm loggt man Exceptions?

Die Regel folgt direkt aus dem Anti-Muster „doppeltes Logging":

> **Fangen und loggen, wo du entscheiden kannst — weiterwerfen, wo du es nicht kannst.**

Übersetzt auf die Schichten unserer Pricing-Anwendung (Struktur aus [[1.1 OOP - Vertiefung|1.1]] / [[1.2 Relationale Datenbanken & ORM - Vertiefung|1.2]]):

| Schicht | Beispiel-Modul | Verhalten im Fehlerfall |
|---|---|---|
| **Domäne / Kern** | `domain.py`, `core/` | **wirft** (z. B. `ValueError` bei verletzter Invariante) — kennt weder Nutzer noch Log-Ziel. Ausnahme: aggregierte Warnungen wie „N Einheiten übersprungen". |
| **Adapter** | `adapters/sources.py`, `db.py`, `writers.py` | **übersetzt** technische Fehler (`FileNotFoundError`, `KeyError`, DB-Fehler) in sprechende, projekteigene Exceptions via `raise ... from e`. Loggt in der Regel nicht selbst. |
| **Rand / Entrypoint** | `main.py` | **fängt, loggt, entscheidet** — hier steht das `logger.exception()` und der Exit-Code. |

Konkret fehlt unserem `main.py` genau dieser Rand — aktuell fliegt jede Exception ungefiltert bis vor die Füße des Nutzers:

```python
# vorher
def main() -> None:
    logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(message)s")
    app = PricingApp(...)
    top = app.run()
    print(f"Höchste Empfehlung: {top}")
```

```python
# nachher (Skizze — Details bauen wir in der Übungsaufgabe)
def main() -> int:
    logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(message)s")
    try:
        app = PricingApp(...)
        top = app.run()
    except PricingError:                     # eigene Basisklasse: erwartete Fehler
        logger.exception("Preislauf abgebrochen")
        return 1
    except Exception:                        # der eine legitime breite Fang
        logger.exception("Unerwarteter Fehler im Preislauf")
        return 2
    print(f"Höchste Empfehlung: {top}")
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

Zwei Dinge daran sind bewusst:

- **Zwei getrennte `except`-Zweige.** Der erste steht für „damit haben wir gerechnet" (fehlende Datei, fehlende Konfiguration), der zweite für „das ist ein Bug". Unterschiedliche Exit-Codes machen den Unterschied auch für ein aufrufendes Skript oder einen Scheduler sichtbar.
- **`sys.exit(main())`.** Ein geloggter Fehler mit Exit-Code 0 wäre für jeden Orchestrator (cron, Airflow, CI) ein *erfolgreicher* Lauf. Das Log allein rettet dich nicht — der Rückgabewert muss dazu passen. Was `sys.exit()` technisch tut (wirft `SystemExit`, erbt von `BaseException`, wird nie von `except Exception:` verschluckt) und was `sys` allgemein vom `os`-Modul unterscheidet: [[Documentation/Traineeship/Python Basics/Das sys-Modul & Exit-Codes.md|Das sys-Modul & Exit-Codes]].

> [!info] Und was ist mit Exceptions, die *niemand* fängt?
> Die schreibt Python über `sys.excepthook` nach **stderr** — also nicht in dein Logfile. Wer wirklich jeden Absturz im Log haben will, kann den Hook umbiegen:
> ```python
> def _log_uncaught(exc_type, exc_value, exc_tb):
>     if issubclass(exc_type, KeyboardInterrupt):        # Strg+C normal durchlassen
>         sys.__excepthook__(exc_type, exc_value, exc_tb)
>         return
>     logger.critical("Unbehandelte Exception", exc_info=(exc_type, exc_value, exc_tb))
>
> sys.excepthook = _log_uncaught
> ```
> Für Threads gibt es analog `threading.excepthook`. Ein `try/except` in `main()` ist für unser Skript aber der einfachere und ausreichende Weg.

## Anschluss an Kapitel 1.3: Exception-Logs testen

Aus [[1.3 Testing mit PyTest - Vertiefung|1.3]] kennen wir `caplog`. Damit lässt sich prüfen, dass ein Fehlerpfad tatsächlich *und mit Traceback* geloggt wird:

```python
def test_fehlende_datei_wird_geloggt(caplog, tmp_path):
    with caplog.at_level(logging.ERROR):
        rc = main_mit_leerem_verzeichnis(tmp_path)

    assert rc == 1
    record = caplog.records[0]
    assert record.levelname == "ERROR"
    assert record.exc_info is not None          # ← der Traceback ist wirklich dran
    assert "Preislauf abgebrochen" in record.message
```

Die Zeile `assert record.exc_info is not None` ist der eigentliche Wert dieses Tests: Sie fängt genau das Anti-Muster Nr. 2 ab. Ein `logger.error(str(e))` würde diesen Test rot machen — was er soll.

Passend dazu prüft man den Fehler selbst mit `pytest.raises` und dabei auch die Kette:

```python
def test_fehlendes_passwort_wird_uebersetzt(monkeypatch):
    monkeypatch.delenv("DB_PRICING_PW", raising=False)
    with pytest.raises(KonfigurationsFehler) as exc_info:
        get_dsn()
    assert isinstance(exc_info.value.__cause__, KeyError)   # `from e` hat gegriffen
```

## Bezug zu den Kontrollfragen

Dieses Stichwort beantwortet einen Teil der [[1.4 Logging & Exceptionhandling - Leitfaden#Kontrollfragen|Kontrollfrage]] *„Was sind die Grundprinzipien des Exceptionhandlings (v. a. in Python)?"* — der Rest folgt beim Stichwort *Exceptionhandling best practices*. Was wir bis hier festhalten können:

1. **Nie stillschweigend schlucken.** Kein `except: pass`, kein bare `except:`.
2. **So eng wie möglich fangen** — nur Fehlertypen, die man an dieser Stelle beantworten kann. Breit fangen genau einmal, am Rand.
3. **Traceback erhalten** — `logger.exception()` statt `str(e)`.
4. **Log *oder* raise**, nicht beides; geloggt wird dort, wo entschieden wird.
5. **Ursachen verketten** — `raise Sprechend(...) from e`, statt die technische Ursache zu verlieren.
6. **Auf das Loggen muss eine Entscheidung folgen** — Fallback, Skip, Abbruch, Exit-Code.

# Parametrisierte Logs

## Worum es geht

Es gibt vier Wege, einen Wert in eine Logmeldung zu bekommen — und nur einer davon ist richtig:

```python
logger.info(f"{n} Zeilen aus {datei} geladen")      # f-String
logger.info("%d Zeilen aus %s geladen" % (n, datei))  # %-Operator
logger.info("{} Zeilen aus {} geladen".format(n, datei))  # str.format
logger.info("%d Zeilen aus %s geladen", n, datei)     # ← parametrisiert (richtig)
```

Der Unterschied ist ein einziges Zeichen: **Komma statt Formatierung.** Die ersten drei bauen den fertigen String *vor* dem Aufruf und übergeben ihn als eine Zeichenkette. Der vierte übergibt **Template und Werte getrennt** — und lässt das `logging`-Modul entscheiden, ob und wann daraus ein Text wird.

Das klingt nach Geschmacksfrage, ist aber keine. Es gibt vier handfeste Gründe, und sie werden nach unten hin wichtiger.

## Grund 1: Die Formatierung passiert vielleicht nie (Lazy Formatting)

Ein `logger.debug(...)`-Aufruf in einer Anwendung, die auf `INFO` läuft, tut effektiv nichts — die Meldung wird verworfen. Aber: Ein f-String wird **vom Python-Interpreter ausgewertet, bevor `logger.debug` überhaupt aufgerufen wird**. Die Arbeit ist also bereits getan, wenn das Logging-Modul entscheidet, die Meldung wegzuwerfen.

Beim parametrisierten Aufruf landen Template und Werte unformatiert im `LogRecord`. Zusammengesetzt wird erst im Handler, über `record.getMessage()` — und dorthin kommt der Record nur, wenn das Level passt und ein Handler zuständig ist.

Nachgemessen mit einem Objekt, dessen `__str__` mitzählt (Level steht auf `INFO`, `debug` ist also unterdrückt):

| Aufruf | `__str__`-Aufrufe |
|---|---|
| `logger.debug("Detail: %s", o)` | **0** |
| `logger.info("Detail: %s", o)` | 1 |
| `logger.info(f"Detail: {o}")` | 1 |
| `logger.debug(f"Detail: {o}")` | **1** ← obwohl nichts geloggt wird |

Wie groß der Effekt ist, hängt komplett daran, wie teuer die Werte sind. Ehrlich gemessen (200 000 unterdrückte `debug`-Aufrufe):

- **Billige Werte** (`int`, kurzer `str`): 0,059 s vs. 0,077 s — Faktor **1,3×**. Das ist Rauschen, damit gewinnt man kein Argument.
- **Teures `__str__`** (Objekt, das 200 Zeilen zu einem String zusammenbaut): 0,006 s vs. 2,697 s — Faktor **~460×**.

> [!important] Der Performance-Grund ist echt, aber nicht der stärkste
> Wer parametrisiertes Logging nur mit Geschwindigkeit begründet, hat ein schwaches Argument — bei `logger.debug(f"{n} Zeilen")` ist der Unterschied irrelevant. Interessant wird es genau da, wo es weh tut: bei DataFrames, Dict-Dumps, `repr()` großer Objekte in `DEBUG`-Logs. Und **weil** der Unterschied dort dramatisch ist, gewöhnt man sich das richtige Muster überall an — man weiß beim Schreiben ja nicht, welche Logzeile später in einer Schleife mit 100 000 Durchläufen steht.

> [!warning] Lazy ist die *Formatierung*, nicht die *Auswertung*
> Die Argumente selbst werden ganz normal ausgewertet, bevor der Aufruf stattfindet:
> ```python
> logger.debug("Ergebnis: %s", teure_berechnung())   # ← läuft IMMER
> ```
> Gespart wird nur die String-Konvertierung. Wenn schon das Beschaffen des Wertes teuer ist, braucht es eine Abfrage davor:
> ```python
> if logger.isEnabledFor(logging.DEBUG):
>     logger.debug("Ergebnis: %s", teure_berechnung())
> ```
> Das ist die einzige Situation, in der ein solcher `if` gerechtfertigt ist — sonst bläht er nur den Code auf.

## Grund 2: Ein Formatfehler legt nicht die Anwendung lahm

Ein Tippfehler im Format-String ist ein Programmierfehler wie jeder andere. Nur: Bei einem f-String schlägt er als ganz normale Exception mitten im Anwendungscode zu — im schlimmsten Fall reißt eine kaputte **Logzeile** die Verarbeitung ab, die selbst völlig in Ordnung war.

Beim parametrisierten Aufruf fängt das `logging`-Modul den Fehler ab, schreibt eine Diagnose nach stderr und **lässt das Programm weiterlaufen**:

```
--- Logging error ---
Traceback (most recent call last):
  ...
    msg = msg % self.args
TypeError: %d format: a real number is required, not str
Call stack:
  File "/tmp/pl2.py", line 6, in <module>
    logger.info("%d Zeilen geladen", "keine Zahl")
Message: '%d Zeilen geladen'
Arguments: ('keine Zahl',)
>>> Programm läuft weiter
```

Das ist genau die richtige Priorisierung: **Logging ist Beobachtung, keine Fachlogik.** Es darf niemals der Grund sein, warum ein Preislauf abbricht. (Steuerbar ist das über `logging.raiseExceptions` — in Produktion lässt man es auf dem Standard `True`, damit man solche Fehler wenigstens sieht.)

## Grund 3: Die Meldung bleibt gruppierbar — der eigentliche Kern

Das ist der Grund, der in Vorstellungsgesprächen zählt und den man als Data Engineer am direktesten spürt.

Beim parametrisierten Aufruf bleiben Template und Werte im `LogRecord` **getrennt erhalten**:

```python
class Catcher(logging.Handler):
    def emit(self, record):
        print(record.msg)          # '%d Zeilen aus %s geladen'
        print(record.args)         # (5, 'prices.csv')
        print(record.getMessage()) # '5 Zeilen aus prices.csv geladen'

logger.info("%d Zeilen aus %s geladen", 5, "prices.csv")
```

`record.msg` ist damit eine **stabile Kennung des Ereignistyps**, `record.args` sind die Instanzdaten. Daraus folgt praktisch alles, wofür man Logs jenseits des Debuggens benutzt:

- **Aggregation.** „Wie oft trat *dieses* Ereignis heute auf?" ist eine Gruppierung über `record.msg`. Mit f-Strings ist jede Zeile ein Unikat (`5 Zeilen…`, `4711 Zeilen…`) und die Frage nur noch per Regex beantwortbar.
- **Fehler-Gruppierung in Monitoring-Tools.** Sentry & Co. bilden ihren Fingerprint u. a. aus dem Template. F-Strings erzeugen tausende „verschiedene" Fehler statt einem mit Zähler 1000.
- **Strukturiertes Logging (JSON).** Ein JSON-Formatter kann `msg` und `args` als getrennte Felder ausgeben. Aus einer Textzeile wird ein Datensatz — und damit etwas, das man in eine Tabelle laden und mit SQL abfragen kann. Genau der Punkt aus der [[1.4 Logging & Exceptionhandling - Leitfaden#Motivation|Motivation]]: *„Als Data Engineer stellt das Logging anderer Systeme oft eine wesentliche Datenquelle für uns dar."* Auf der anderen Seite dieser Aussage steht jemand, der die Logs so schreiben musste, dass man sie auswerten kann.
- **Suchbarkeit.** `grep "Zeilen aus"` findet das Template zuverlässig; `grep "5 Zeilen"` findet einen Zufall.

> [!tip] Merksatz
> Ein parametrisiertes Log ist eine **Ereignisklasse mit Daten**, ein f-String-Log ist ein **fertiger Satz**. Sätze kann man lesen, Ereignisklassen kann man zählen.

## Grund 4: Kein Format-String aus fremden Daten

Der subtilste Punkt. Diese Zeile ist harmlos:

```python
logger.info("Auslastung 85% erreicht")     # → INFO:Auslastung 85% erreicht
```

Ohne `args` findet **überhaupt keine Formatierung** statt (`getMessage()` prüft `if self.args:`), das `%` bleibt einfach stehen. Kritisch wird es, wenn Fremddaten in den *Template*-Teil geraten:

```python
logger.info("Produkt %s verarbeitet" % produkt_id)   # Fremddaten werden zum Template
logger.info("Produkt %s verarbeitet", produkt_id)    # Fremddaten bleiben Daten
```

Enthält `produkt_id` ein `%`, kann die erste Variante Formatfehler auslösen; im allgemeinen Fall ist „unkontrollierte Eingabe wird als Format-String interpretiert" eine bekannte Schwachstellenklasse. Die Trennung von Template und Daten ist dasselbe Prinzip, das man bei SQL kennt: **Platzhalter statt Stringverkettung** — genau der Grund, warum wir in `adapters/db.py` Parameter an `psycopg` übergeben, statt Werte in die Query zu kleben.

## Fallstricke bei der Schreibweise

**`%`-Style, nicht `{}`-Style.** Die Message-Argumente werden *immer* mit dem `%`-Operator zusammengesetzt — unabhängig davon, welchen `style` der Formatter benutzt:

```python
handler.setFormatter(logging.Formatter("{levelname} | {message}", style="{"))
lg.info("{} Zeilen", 5)     # → Logging error: not all arguments converted
lg.info("%d Zeilen", 5)     # → INFO | 5 Zeilen
```

Der `style="{"`-Parameter betrifft nur das **Format-Template des Formatters** (also wie Level, Zeitstempel und Message angeordnet werden), nicht die Meldung selbst. Häufige Verwechslung.

**Ein einzelnes `dict` wird als Mapping gelesen.** Das ist ein dokumentierter Sonderfall, der beides ermöglicht:

```python
logger.info("%(product)s kostet %(preis).2f", {"product": "P1", "preis": 12.5})
logger.info("Rohdaten: %s", {"a": 1})     # funktioniert trotzdem, da %s dazu passt
```

Die benannte Variante ist bei mehreren Werten lesbarer und robust gegen Reihenfolge-Fehler — muss man aber nicht überall benutzen.

## `extra=` — Daten, die nicht im Satz stehen

Neben den Platzhaltern gibt es einen zweiten Weg, Daten an einen Logeintrag zu hängen: `extra`. Die Werte landen als **Attribute auf dem `LogRecord`** und sind damit für Formatter und Handler verfügbar, ohne den Meldungstext zu verändern:

```python
logging.Formatter("%(levelname)s [unit=%(unit_id)s] %(message)s")
logger.info("Empfehlung geschrieben", extra={"unit_id": 42})
# → INFO [unit=42] Empfehlung geschrieben
```

Das ist der Einstieg ins strukturierte Logging: Felder wie `unit_id`, `run_id` oder `dauer_ms` gehören als Daten an den Record, nicht in den Satz — dann kann ein JSON-Formatter sie als eigene Spalten ausgeben.

> [!warning] Reservierte Namen in `extra`
> Schlüssel, die es auf dem `LogRecord` schon gibt (`message`, `asctime`, `name`, `levelname`, `args`, `module`, …), lösen sofort eine Exception aus:
> ```
> KeyError: "Attempt to overwrite 'message' in LogRecord"
> ```
> Deshalb Felder projektweit mit einem Präfix versehen (`app_unit_id`) oder wenigstens bewusst benennen. Zweiter Haken: Steht `%(unit_id)s` im Formatter, **muss** jeder Record das Feld haben — sonst scheitert die Formatierung bei allen anderen Logzeilen. Robuster ist ein Formatter, der fehlende Felder toleriert (eigener Formatter, `LoggerAdapter` mit Defaultwerten oder ein Filter, der das Feld ergänzt).

## Die eine Ausnahme, bei der man den Wert *weglässt*

Bei `logger.exception()` gilt das Gegenteil der Reflexes „Werte anhängen":

```python
logger.exception(f"Fehler beim Laden: {e}")     # ✗ doppelt gemoppelt
logger.exception("Fehler beim Laden von %s", pfad)   # ✓
```

Die Exception steht ohnehin komplett im angehängten Traceback — sie zusätzlich in den Meldungstext zu schreiben, verlängert das Log ohne Informationsgewinn und zerstört die Gruppierbarkeit aus Grund 3. Das verbindet dieses Stichwort direkt mit dem vorherigen: Die Nachricht sagt, **was du gerade versucht hast**; die Exception sagt, **was schiefging**.

## Werkzeugunterstützung: das muss man nicht selbst merken

`ruff` hat für genau diese Regeln die Gruppe **`G`** (`flake8-logging-format`). Getestet mit ruff 0.16.0 aus dem Projekt-venv:

| Code | Was es findet |
|---|---|
| `G001` | `logger.info("… {} …".format(x))` |
| `G002` | `logger.info("… %s …" % x)` |
| `G003` | `logger.info("Zeilen: " + str(x))` |
| `G004` | `logger.info(f"… {x} …")` — *„Convert to lazy `%` formatting"* |
| `TRY401` | *„Redundant exception object included in `logging.exception` call"* (die Ausnahme oben) |

Im Projekt sind diese Gruppen aktuell **nicht** aktiviert — `pyproject.toml` selektiert `E, W, F, I, N, UP, B, SIM`. Ein sinnvoller Schritt in der Übungsaufgabe:

```toml
[tool.ruff.lint]
select = [
    "E", "W", "F", "I", "N", "UP", "B", "SIM",
    "G",    # flake8-logging-format: parametrisiertes Logging erzwingen
    "LOG",  # flake8-logging: Fehler im Umgang mit dem logging-Modul
    "TRY",  # tryceratops: Exceptionhandling-Anti-Muster
]
```

Damit wird die Konvention **maschinell durchgesetzt** statt bei jedem Review neu diskutiert — dieselbe Logik wie bei mypy `strict`: Was ein Werkzeug prüfen kann, soll kein Mensch prüfen müssen.

def test_zeilenzahl_wird_geloggt(caplog):
    with caplog.at_level(logging.INFO):

# Logging in Theorie und Praxis (Context Python)

## Was hier noch offen ist

Die beiden bisherigen Stichworte haben die **Aufruf**-Seite behandelt: was man loggt (Stichwort 1) und wie man den Aufruf schreibt (Stichwort 2). Beides betraf immer nur die eine Zeile `logger.irgendwas(...)`.

Offen ist die andere Seite: **Was passiert mit dieser Meldung danach?** Wer entscheidet, ob sie auf der Konsole, in einer Datei oder gar nicht landet? Warum steht in `main.py` ein `basicConfig` und in `builder.py` nicht? Warum taucht eine Logzeile plötzlich doppelt auf?

Das ist kein Theorie-Beiwerk, sondern die Stelle, an der in der Praxis die meiste Zeit verloren geht. Die drei häufigsten Logging-Bugs überhaupt — *doppelte Ausgaben*, *`basicConfig` tut nichts*, *Logs verschwinden spurlos* — sind allesamt Missverständnisse über dieses Modell und nicht über die Aufrufe.

## Die vier Bausteine

Pythons `logging` ist bewusst als **Pipeline** gebaut, nicht als eine Funktion, die etwas ausgibt:

```
logger.info("%d Zeilen", n)
        │
        ▼
    ┌────────┐   ┌────────┐   ┌─────────┐   ┌───────────┐
    │ Logger │──▶│ Filter │──▶│ Handler │──▶│ Formatter │──▶ Ziel
    └────────┘   └────────┘   └─────────┘   └───────────┘
     WAS/WOHER      OB          WOHIN         WIE AUSSEHEN
```

| Baustein | Zuständig für | Beispiel |
|---|---|---|
| **Logger** | Nimmt die Meldung entgegen, kennt Herkunft (`__name__`) und Level | `logging.getLogger("pricing.core.builder")` |
| **Handler** | Wohin die Meldung geht — ein Logger kann mehrere haben | `StreamHandler` (Konsole), `RotatingFileHandler` (Datei) |
| **Formatter** | Wie die Zeile aussieht — hängt am **Handler**, nicht am Logger | `"%(asctime)s %(levelname)s %(name)s: %(message)s"` |
| **Filter** | Feinsteuerung „durchlassen oder nicht", jenseits des Levels | „nur Records mit `run_id`" |

> [!important] Die Trennung ist der ganze Punkt
> **Der Code, der loggt, weiß nicht, wohin geloggt wird.** `builder.py` sagt nur *„das ist passiert"*; ob das auf der Konsole landet, in einer Datei, in beidem oder nirgends, entscheidet die Anwendung an ihrem Rand. Deshalb kann man dasselbe Modul unverändert in einem CLI-Skript, in einem Airflow-Task und in einem Test benutzen. Genau das kann `print` nicht — und es ist die halbe Antwort auf die Kontrollfrage *„Warum gibt es Logging-Frameworks?"*.

## Der Weg einer Logmeldung — und die zwei Level-Prüfungen

Es gibt **zwei** unabhängige Level-Schwellen, und das erklärt die meisten „mein Log kommt nicht an"-Fälle:

1. `logger.info(...)` wird aufgerufen.
2. **Prüfung 1 (Logger):** Ist `INFO >= logger.getEffectiveLevel()`? Wenn nein → sofort verworfen, es entsteht nicht einmal ein `LogRecord`.
3. Ein `LogRecord` entsteht (mit `msg`, `args`, `exc_info`, Zeitstempel, Modulname …).
4. Die **Filter des Loggers** laufen.
5. Der Record wandert zu allen Handlern des Loggers **und** — falls `propagate` an ist — zu den Handlern aller Vorfahren bis zum Root.
6. **Prüfung 2 (Handler):** Jeder Handler hat ein *eigenes* Level und *eigene* Filter.
7. Der Formatter des Handlers baut den Text, der Handler schreibt ihn weg.

Daraus folgt eine sehr praktische Faustregel: **Logger-Level = „was interessiert mich überhaupt", Handler-Level = „was schreibe ich in dieses Ziel".** Typisch: Der Logger steht auf `DEBUG`, der Konsolen-Handler auf `INFO` und der Datei-Handler auf `DEBUG` — die Konsole bleibt lesbar, die Datei hat alles.

## Die Logger-Hierarchie und `__name__`

Logger bilden einen **Baum über Punkt-Namen**. `pricing.core.builder` ist Kind von `pricing.core`, das Kind von `pricing`, das Kind vom **Root-Logger** (`""`). Genau deshalb schreibt man `logging.getLogger(__name__)` — der Modulpfad *ist* die Hierarchie, geschenkt.

Der Nutzen zeigt sich beim Konfigurieren. Ein Logger ohne eigenes Level steht auf `NOTSET` (numerisch `0`) und **erbt** das Level vom nächsten Vorfahren, der eines gesetzt hat:

```python
logging.getLogger("pricing").setLevel(logging.INFO)
lg = logging.getLogger("pricing.core.builder")
lg.level                  # 0  (NOTSET — nichts eigenes gesetzt)
lg.getEffectiveLevel()    # 20 (INFO — geerbt von "pricing")
```

Damit kann man einen ganzen Teilbaum auf einmal steuern: *„die ganze Anwendung auf `INFO`, aber `pricing.adapters.db` auf `DEBUG`"* ist eine Zeile pro Regel — und `"sqlalchemy.engine"` auf `WARNING`, wenn eine Bibliothek zu geschwätzig ist. Das ist der Alltagsfall: Man dreht fremde Bibliotheken leise, ohne deren Code anzufassen.

> [!warning] Der überraschendste Teil: Vorfahren-**Level** werden nicht geprüft
> Bei der Weitergabe nach oben werden nur die **Handler** der Vorfahren benutzt — deren **Level wird ignoriert**. Nachgemessen:
> ```python
> root.setLevel(logging.ERROR)          # Root steht auf ERROR
> lg = logging.getLogger("app")
> lg.setLevel(logging.DEBUG)
> lg.debug("kommt das durch?")          # → JA, wird ausgegeben
> ```
> Entscheidend ist allein das **effective level des aufrufenden Loggers** (Prüfung 1) und danach das Level der einzelnen **Handler** (Prüfung 2). Wer die Ausgabe drosseln will, setzt sie am Handler — nicht am Root-Logger.

## Propagation und die doppelte Ausgabe

Standardmäßig gibt jeder Logger seinen Record zusätzlich nach oben weiter (`propagate = True`). Hängt man nun einen eigenen Handler an einen Modul-Logger, **obwohl** der Root bereits einen hat, erscheint jede Zeile zweimal:

```
EIGENER-HANDLER | diese Zeile erscheint ...
ROOT-HANDLER    | pricing.core.builder | INFO | diese Zeile erscheint ...
```

Die zwei sauberen Auswege:

- **Der Normalfall:** Handler *nur* am Root (bzw. an genau einer Stelle) registrieren. Modul-Logger bekommen **nie** Handler. Damit stellt sich die Frage gar nicht erst.
- **Der Sonderfall:** Ein Teilbaum soll woanders hin (z. B. Audit-Logs in eine eigene Datei) → eigener Handler **plus** `propagate = False`.

> [!warning] `propagate = False` bricht `caplog`
> Anschluss an [[1.3 Testing mit PyTest - Vertiefung|Kapitel 1.3]]: pytests `caplog` hängt seinen Handler an den **Root**-Logger. Ein `propagate = False` irgendwo darüber macht die Meldung für den Test unsichtbar — nachgestellt und bestätigt:
> ```
> assert len(caplog.records) == 1
> E   assert 0 == 1
> E    +  where 0 = len([])
> ```
> Der Test schlägt fehl, obwohl das Logging in der Anwendung einwandfrei funktioniert. Wer `propagate = False` benutzt, muss im Test entweder `caplog.set_level(..., logger="pricing")` verwenden oder direkt am betroffenen Logger ansetzen.

## Wer konfiguriert — und wer auf keinen Fall

Die wichtigste Konvention des ganzen Stichworts:

> [!important] Konfiguriert wird **einmal**, am Rand der **Anwendung**
> Nur der Entrypoint (`main.py`, das Airflow-Task-Skript, die `conftest.py`) legt Handler, Formatter und Level fest. **Bibliotheks- und Fachmodule konfigurieren nie** — sie holen sich nur ihren Logger und loggen.

Der Grund ist Besitz: Wohin Logs gehen, entscheidet der, der die Anwendung betreibt, nicht der, der ein Modul geschrieben hat. Ein Modul, das beim Import `basicConfig` aufruft, überschreibt (bzw. blockiert) die Konfiguration der Anwendung, die es benutzt — ein klassischer, schwer zu findender Fehler.

Für **veröffentlichte Bibliotheken** gibt es dafür die Standardlösung, den `NullHandler`:

```python
# in der __init__.py einer Bibliothek
logging.getLogger(__name__).addHandler(logging.NullHandler())
```

Er tut nichts, verhindert aber, dass die Bibliothek ohne Anwendungs-Konfiguration Warnungen produziert. Ohne jede Konfiguration greift nämlich Pythons `lastResort`-Handler: `<_StderrHandler <stderr> (WARNING)>` — er schreibt `WARNING` und höher nach stderr, ganz ohne Formatierung, und verschluckt `INFO`/`DEBUG` still. Wenn du also „nur Warnungen, aber keine Infos" siehst und dich wunderst: Du hast wahrscheinlich gar keine Konfiguration.

## Die drei Wege zu konfigurieren

**1. `basicConfig` — für Skripte, mit einer fiesen Falle.**

```python
logging.basicConfig(level=logging.INFO, format="%(levelname)s: %(message)s")
```

Bequem, aber: **`basicConfig` tut nichts, wenn der Root-Logger schon Handler hat.** Kein Fehler, keine Warnung — es passiert schlicht nichts. Nachgemessen:

```python
logging.basicConfig(level=logging.INFO,  format="ERSTER: %(message)s")
logging.basicConfig(level=logging.DEBUG, format="ZWEITER: %(message)s")
logging.getLogger("x").info("welches Format?")   # → "ERSTER: welches Format?"
```

Der zweite Aufruf ist wirkungslos — auch das Level bleibt auf `INFO`. Seit Python 3.8 gibt es dafür `force=True`, das bestehende Handler entfernt und neu aufsetzt:

```python
logging.basicConfig(level=logging.DEBUG, format="MIT-FORCE: %(message)s", force=True)
```

Das erklärt auch, warum ein `basicConfig` in einem Modul, das früh importiert wird, die Konfiguration der Anwendung *stillschweigend gewinnt*.

**2. `dictConfig` — der Praxis-Standard für Anwendungen.**

Sobald es mehr als einen Handler gibt, wird die Konfiguration zu Daten statt zu Code — und ist damit aus einer YAML-/TOML-Datei ladbar, ohne Neu-Deployment änderbar und pro Umgebung (lokal/Test/Produktion) austauschbar:

```python
import logging.config

logging.config.dictConfig({
    "version": 1,                       # Pflicht, immer 1
    "disable_existing_loggers": False,  # ← siehe Warnung unten
    "formatters": {
        "einfach":   {"format": "%(levelname)-8s %(name)s: %(message)s"},
        "detailliert": {
            "format": "%(asctime)s %(levelname)-8s %(name)s:%(lineno)d — %(message)s",
            "datefmt": "%Y-%m-%d %H:%M:%S",
        },
    },
    "handlers": {
        "konsole": {
            "class": "logging.StreamHandler",
            "level": "INFO",
            "formatter": "einfach",
            "stream": "ext://sys.stdout",
        },
        "datei": {
            "class": "logging.handlers.RotatingFileHandler",
            "level": "DEBUG",
            "formatter": "detailliert",
            "filename": "logs/pricing.log",
            "maxBytes": 5_000_000,
            "backupCount": 3,
            "encoding": "utf-8",
        },
    },
    "loggers": {
        "pricing": {"level": "DEBUG", "handlers": ["konsole", "datei"], "propagate": False},
        "sqlalchemy.engine": {"level": "WARNING"},
    },
    "root": {"level": "WARNING", "handlers": ["konsole"]},
})
```

Hier sieht man das ganze Modell auf einmal: ein Logger-Level (`DEBUG`), zwei Handler mit *unterschiedlichen* Levels (`INFO` für die Konsole, `DEBUG` für die Datei), zwei Formatter, und eine gezielte Bremse für eine fremde Bibliothek.

> [!warning] `disable_existing_loggers` steht standardmäßig auf `True`
> Alle Logger, die zum Zeitpunkt des `dictConfig`-Aufrufs bereits existieren und nicht explizit in der Config stehen, werden **stillgelegt**. Da `logger = logging.getLogger(__name__)` auf Modulebene beim *Import* läuft, trifft das genau die Module, die vor der Konfiguration importiert wurden. Nachgestellt:
> ```python
> vorher = logging.getLogger("frueh_importiert")
> logging.config.dictConfig({...})
> vorher.disabled          # → True
> vorher.warning("hallo")  # → keine Ausgabe, kein Fehler
> ```
> Deshalb in eigenen Anwendungen praktisch immer `"disable_existing_loggers": False` setzen.

**3. Direkt im Code** (`addHandler`, `setFormatter`) — nötig, wenn Handler zur Laufzeit von etwas abhängen (Pfad aus einer Umgebungsvariable, Verzeichnis erst anlegen). Häufig als Mischform: eine `setup_logging()`-Funktion, die intern `dictConfig` aufruft.

## Handler, die man tatsächlich benutzt

| Handler | Wofür |
|---|---|
| `StreamHandler` | Konsole. `stream=sys.stdout` oder `sys.stderr` — Standard ist **stderr** |
| `FileHandler` | Eine Datei, unbegrenzt wachsend — für Dauerbetrieb ungeeignet |
| `RotatingFileHandler` | Rotation nach **Größe** (`maxBytes`, `backupCount`) |
| `TimedRotatingFileHandler` | Rotation nach **Zeit** (`when="midnight"`) — passt zu täglichen Läufen |
| `QueueHandler` + `QueueListener` | Loggen blockiert den Arbeits-Thread nicht; Pflicht bei langsamen Zielen (Netzwerk, DB) |
| `SMTPHandler`, `HTTPHandler` | Alarmierung — in der Praxis meist besser der Monitoring-Plattform überlassen |

> [!tip] In Containern loggt man nach stdout — und rotiert gar nicht
> Läuft die Anwendung in Docker/Kubernetes/Airflow, ist der richtige Weg meist **nur `StreamHandler` auf stdout**. Rotation, Archivierung und Weiterleitung übernimmt die Plattform (Docker-Log-Driver, Fluent Bit, CloudWatch). Ein `RotatingFileHandler` in einem Container schreibt in ein Dateisystem, das beim nächsten Neustart weg ist. Für ein lokal per cron laufendes Skript ist die Datei dagegen genau richtig — die Entscheidung hängt am **Betriebsmodell**, nicht am Geschmack.

## Formatter in der Praxis

Ein brauchbarer Format-String für den Betrieb:

```python
"%(asctime)s %(levelname)-8s %(name)s:%(lineno)d — %(message)s"
# 2026-07-27 17:15:58 INFO     pricing.core.builder:39 — 1500 Buchungen expandiert
```

Die Bestandteile mit Begründung:

- `%(asctime)s` — ohne Zeitstempel ist ein Log für Nachvollziehbarkeit und Performance-Analyse wertlos. **Achtung:** Standard ist **lokale Zeit** inklusive Sommerzeit-Sprüngen. Wer Logs aus mehreren Systemen zusammenführt (der Data-Engineering-Fall), stellt auf UTC: `logging.Formatter.converter = time.gmtime`.
- `%(levelname)-8s` — die `-8` sorgt für feste Spaltenbreite, damit die Zeilen untereinander lesbar bleiben.
- `%(name)s` — der Logger-Name, also dank `__name__` der Modulpfad. **Das ist der Grund, warum `getLogger(__name__)` sich lohnt:** Man sieht sofort, welches Modul spricht, ohne es in jede Meldung schreiben zu müssen.
- `%(lineno)d`, `%(funcName)s` — praktisch beim Debuggen, in Produktion optional.

Beim `basicConfig`-Einzeiler in unserem `main.py` (`"%(levelname)s: %(message)s"`) fehlen Zeitstempel und Logger-Name — für ein Übungsskript in Ordnung, für „geht live" nicht.

## Filter — kurz, aber nützlich

Ein Filter ist ein Objekt (oder eine Funktion) mit `filter(record) -> bool`. Zwei realistische Anwendungen:

- **Auswählen:** nur Records eines bestimmten Teilbaums oder mit einem bestimmten Feld in ein Ziel lassen.
- **Anreichern:** Filter dürfen den Record *verändern* — der übliche Trick, um jedem Eintrag automatisch eine `run_id` zu verpassen, ohne sie an jedem `logger.info` mitzugeben:

```python
class RunIdFilter(logging.Filter):
    def __init__(self, run_id: str) -> None:
        super().__init__()
        self.run_id = run_id

    def filter(self, record: logging.LogRecord) -> bool:
        record.run_id = self.run_id
        return True      # nichts wird verworfen
```

Damit funktioniert `%(run_id)s` im Formatter für *jede* Zeile — und löst nebenbei den `extra`-Fallstrick aus [[#Parametrisierte Logs]] („steht das Feld im Formatter, muss jeder Record es haben"). Das ist der saubere Weg zur Korrelations-ID, die im [[Umsetzungsstand (Logging & Exceptionhandling)#Offene Punkte / Ausblick|Umsetzungsstand]] als offener Punkt steht.

## Bezug zum Projekt

Der Ist-Zustand in `main.py` ist ein einzelner `basicConfig`-Aufruf. Er ist **an der richtigen Stelle** (Entrypoint, nicht in den Fachmodulen) — das Muster stimmt also bereits, es fehlt nur der Ausbau. Für die Übungsaufgabe ergibt sich daraus konkret:

1. `setup_logging()` in ein eigenes Modul (`logging_config.py`), intern `dictConfig` mit `disable_existing_loggers: False`.
2. Zwei Handler: Konsole (`INFO`, knapp) und Datei mit Rotation (`DEBUG`, ausführlich).
3. Formatter mit Zeitstempel und `%(name)s`.
4. Aufruf **als erste Zeile** in `main()` — vor allem anderen, sonst gehen frühe Meldungen verloren.
5. Handler bleiben ausschließlich dort; kein Modul unter `src/pricing/` bekommt einen.

## Bezug zu den Kontrollfragen

Dieses Stichwort beantwortet die erste [[1.4 Logging & Exceptionhandling - Leitfaden#Kontrollfragen|Kontrollfrage]] *„Warum gibt es Logging-Frameworks?"* im Kern — was ein Framework leistet, das `print` nicht kann:

1. **Entkopplung von Erzeugung und Ziel** — der loggende Code weiß nicht, wohin geschrieben wird; dasselbe Modul funktioniert in CLI, Test und Scheduler.
2. **Zentrale, datengetriebene Konfiguration** — ein `dictConfig` steuert die ganze Anwendung, änderbar ohne Code-Änderung.
3. **Feingranulare Steuerung über die Hierarchie** — pro Modul und pro Fremdbibliothek ein eigenes Level.
4. **Mehrere Ziele gleichzeitig, mit je eigener Schwelle und Formatierung.**
5. **Strukturierte Metadaten gratis** — Zeitstempel, Level, Modul, Zeile, Thread, Prozess; dazu `exc_info` aus Stichwort 1.
6. **Robustheit** — Fehler im Logging reißen die Anwendung nicht ab (Stichwort 2).

Die konkreten Framework-Namen (`structlog`, `loguru`, und in der Java-Welt Log4j/SLF4J) folgen beim Stichwort *Logging-Frameworks*.

# Logging-Level

## Die sechs Stufen und ihre Zahlen

Level sind in Python schlicht **ganze Zahlen**. Die Namen sind Bequemlichkeit, verglichen wird numerisch:

| Level | Wert | Gedacht für |
|---|---|---|
| `NOTSET` | 0 | „nicht gesetzt" — erbt vom Elternlogger (siehe [[#Die Logger-Hierarchie und `__name__`]]) |
| `DEBUG` | 10 | Detaildaten zur Fehlersuche |
| `INFO` | 20 | Normaler Ablauf, bestätigt „es läuft wie gedacht" |
| `WARNING` | 30 | Etwas ist auffällig, das Programm läuft aber weiter |
| `ERROR` | 40 | Eine Aufgabe ist gescheitert |
| `CRITICAL` | 50 | Die Anwendung selbst ist nicht mehr arbeitsfähig |

Dass es Zahlen sind, hat zwei praktische Konsequenzen: Eine Schwelle bedeutet immer „**dieses Level und alles darüber**", und eigene Zwischenstufen sind möglich (dazu unten).

## Die entscheidende Umdeutung: nicht „wie schlimm", sondern „wer muss reagieren"

Der häufigste Fehler bei der Level-Wahl ist, sie als **Gefühlsskala** zu lesen — „das ist mir wichtig, also `WARNING`". Danach steht alles auf `WARNING`, und die Stufe sagt nichts mehr aus.

Die brauchbare Frage ist eine andere: **Wer liest diese Zeile, und was tut die Person daraufhin?**

| Level | Wer liest das? | Was folgt daraus? |
|---|---|---|
| `DEBUG` | Entwickler, gezielt bei einem konkreten Problem | Nichts — Material zum Nachvollziehen. Im Normalbetrieb ausgeschaltet. |
| `INFO` | Betrieb, im Nachhinein oder beim Zuschauen | Nichts. Beantwortet „was hat der Lauf getan?" |
| `WARNING` | Betrieb, beim Durchsehen | Vielleicht später etwas — beobachten, ggf. Datenquelle nachfragen. Kein Alarm. |
| `ERROR` | Betrieb, zeitnah | Jemand muss sich das ansehen. Eine Aufgabe ist nicht erledigt worden. |
| `CRITICAL` | Bereitschaft, sofort | Jemand wird geweckt. |

Daraus folgt eine harte Regel, die viel Streit erspart: **`ERROR` heißt, dass etwas nicht getan wurde, das getan werden sollte.** Ein Fehler, den das Programm selbst auffängt und korrekt kompensiert (Retry erfolgreich, Fallback gegriffen), ist kein `ERROR` — höchstens ein `WARNING`. Umgekehrt: Wenn der Preislauf abbricht, ist das kein `WARNING`, egal wie ruhig die Meldung formuliert ist.

> [!tip] Zwei Faustregeln zur Abgrenzung
> - **`WARNING` vs. `ERROR`:** Konnte die Anwendung ihre Aufgabe trotzdem erledigen? Ja → `WARNING`. Nein → `ERROR`.
> - **`INFO` vs. `DEBUG`:** Würdest du diese Zeile auch dann sehen wollen, wenn alles glattgeht — dauerhaft, in Produktion? Ja → `INFO`. Nur bei der Fehlersuche → `DEBUG`.

## Der Vorteil verschiedener Level

Das ist wörtlich die dritte [[1.4 Logging & Exceptionhandling - Leitfaden#Kontrollfragen|Kontrollfrage]]. Die Antwort in einem Satz: **Level entkoppeln, was der Code *aufschreibt*, von dem, was der Betrieb *sehen will* — und zwar ohne Code-Änderung.**

Ausgefaltet:

1. **Ein Code, viele Umgebungen.** Derselbe Preislauf schreibt lokal `DEBUG` und in Produktion `INFO`. Ohne Level müsste man Logzeilen zum Deployment ein- und auskommentieren — und genau die eine, die man gebraucht hätte, wäre auskommentiert.
2. **Nachträgliche Vertiefung im Fehlerfall.** Tritt in Produktion ein Problem auf, dreht man das Level für ein Modul hoch und bekommt Details — ohne Neubau, oft ohne Neustart. Das ist der Hauptgrund, überhaupt `DEBUG`-Zeilen zu schreiben, die im Normalbetrieb nie erscheinen.
3. **Granularität pro Modul.** Über die Hierarchie: `pricing.adapters.db` auf `DEBUG`, alles andere auf `INFO`. Besonders wertvoll gegen gesprächige Fremdbibliotheken (`sqlalchemy.engine`, `urllib3`).
4. **Mehrere Ziele mit je eigener Schwelle.** Konsole knapp auf `INFO`, Datei ausführlich auf `DEBUG` — dieselben Aufrufe, zwei Detailgrade (siehe [[#Der Weg einer Logmeldung — und die zwei Level-Prüfungen]]).
5. **Alarmierung wird automatisierbar.** Monitoring kann auf „`ERROR` oder schlimmer" reagieren. Das setzt aber voraus, dass die Level *diszipliniert* vergeben sind — sonst ist die Automatisierung wertlos.
6. **Kostensteuerung.** Log-Volumen ist in der Cloud eine Rechnungsposition. Das Level ist der Hebel, der Datenmenge reguliert, ohne Information dauerhaft aufzugeben.

## Warum `WARNING` der Default ist

Ein frisch importiertes `logging` hat den Root-Logger auf `WARNING` — nachgeprüft: `logging.getLogger().level` ist `WARNING` (30). Auch der `lastResort`-Handler steht auf `WARNING`.

Das ist eine bewusste Aussage der Standardbibliothek: **Ohne Konfiguration soll eine Bibliothek nur das melden, was den Nutzer wirklich angeht.** Eine importierte Bibliothek, die ungefragt `INFO` auf die Konsole schreibt, gilt als schlecht erzogen. Für die eigene *Anwendung* dreht man das im Entrypoint bewusst auf `INFO` — genau das tut `main.py` heute schon.

## Die Nachteile von niederschwelligem Logging

Kontrollfrage 4 — und die interessantere Hälfte des Themas, weil sie der naheliegenden Intuition widerspricht („mehr Logs = mehr Sicherheit").

1. **Signal-Rausch-Verhältnis.** Der teuerste Schaden. Wenn 10 000 `DEBUG`-Zeilen pro Minute laufen, findet niemand die eine `ERROR`-Zeile — und schlimmer: Man *gewöhnt* sich an ein volles Log. Auffälligkeiten fallen nicht mehr auf, weil ständig etwas scrollt. Ein Log, in dem alles steht, ist informationsärmer als eins, in dem das Wichtige steht.
2. **Volumen und Kosten.** Nachgerechnet mit ~120 Byte pro Zeile:

   | Zeilen/Tag | Pro Tag | Pro Jahr |
   |---|---|---|
   | 1 000 | 0,1 MB | 0,04 GB |
   | 100 000 | 12 MB | 4,4 GB |
   | 10 Mio. | 1,2 GB | **438 GB** |

   Zehn Millionen Zeilen am Tag sind für eine Zeile Logging in einer Schleife über einen Datensatz mit ein paar Millionen Zeilen schnell erreicht. Bei Cloud-Logging zahlt man das pro GB — für Aufnahme *und* Aufbewahrung.
3. **Laufzeit.** Aktiviertes `DEBUG` heißt: formatieren, sperren, schreiben — und Datei-I/O ist synchron. In einer heißen Schleife dominiert das irgendwann die eigentliche Arbeit. (Der Punkt aus [[#Parametrisierte Logs]] gilt nur für *unterdrückte* Meldungen; ist `DEBUG` an, ist die Arbeit real.)
4. **Betriebsrisiko.** Ein volllaufendes Log kann die Platte füllen und damit die Anwendung *und* ihre Nachbarn stoppen. Deshalb gehört zu `DEBUG` in Produktion immer Rotation mit Größenlimit.
5. **Datenschutz.** Je feiner geloggt wird, desto wahrscheinlicher landen personenbezogene Daten im Log — und ein Log ist eine Datensammlung wie jede andere: aufbewahrungspflichtig, auskunftspflichtig, löschpflichtig. Der Leitfaden nennt Datenschutz in der [[1.4 Logging & Exceptionhandling - Leitfaden#Motivation|Motivation]], setzt ihn aber [[1.4 Logging & Exceptionhandling - Leitfaden#Out of Scope|Out of Scope]] — deshalb hier nur die Merkregel: **Keine Klardaten von Personen und keine Geheimnisse ins Log**, auch nicht auf `DEBUG`. Ein `logger.debug("Verbinde mit %s", dsn)` mit Passwort in der DSN ist der Klassiker.

> [!warning] Der Fehler in die andere Richtung ist auch einer
> Zu wenig Logging ist kein sicherer Standardwert, sondern nur ein leiserer Fehler — er fällt erst um drei Uhr nachts auf, wenn ein Lauf fehlschlägt und das Log nichts hergibt. Die Lösung ist nicht „wenig loggen", sondern **auf der richtigen Stufe loggen**: großzügig `DEBUG` schreiben (kostet ausgeschaltet fast nichts), sparsam `INFO`, sehr sparsam `WARNING` und `ERROR`.

## Level zur Laufzeit steuern

Der Vorteil aus Punkt 1 und 2 wird erst real, wenn man das Level ändern kann, **ohne den Code anzufassen**. Zwei übliche Wege:

```python
import os, logging

level = os.getenv("LOG_LEVEL", "INFO").upper()      # Umgebungsvariable
logging.basicConfig(level=level)                     # akzeptiert auch den Namen als String
```

```python
parser.add_argument("-v", "--verbose", action="count", default=0)
# 0 → INFO, 1 → DEBUG
level = logging.DEBUG if args.verbose else logging.INFO
```

Die Umgebungsvariable ist der Standard für Dienste und Container (`LOG_LEVEL=DEBUG` im Scheduler setzen, Lauf beobachten, zurückstellen), das Flag der Standard für CLI-Werkzeuge. Für unsere Anwendung — als CLI *und* per cron aufrufbar — sind beide sinnvoll, mit der Umgebungsvariable als Default und dem Flag als Übersteuerung.

## Eigene Level — kann man, sollte man selten

```python
TRACE = 5
logging.addLevelName(TRACE, "TRACE")
logger.log(TRACE, "feinste Spur")     # → TRACE: feinste Spur
```

Funktioniert (`5` liegt unter `DEBUG`), ist aber fast immer die falsche Lösung: Fremdwerkzeuge, Formatter-Konfigurationen und Kollegen kennen das Level nicht, und es gibt kein `logger.trace()`, solange man nicht zusätzlich eine Methode auf die Logger-Klasse setzt. Die fünf Standardstufen reichen praktisch immer — was man wirklich will, ist meist **Granularität pro Modul**, und die gibt es über die Hierarchie gratis.

## Zwei Kleinigkeiten am Rand

**`logger.warn()` ist veraltet.** Es existiert in Python 3.13 noch, meldet aber beim Aufruf: `DeprecationWarning: The 'warn' method is deprecated, use 'warning' instead`. Immer `logger.warning()` schreiben.

**Warnungen ins Log umleiten.** `logging.captureWarnings(True)` schickt alles aus dem `warnings`-Modul (z. B. `DeprecationWarning` aus Fremdbibliotheken) an den Logger `py.warnings` — auf Level `WARNING`. Praktisch, damit solche Hinweise nicht nur auf stderr landen, sondern im selben Logfile wie alles andere.

## Vorschlag: Level-Matrix für die Pricing-Anwendung

Das ist der erste offene [[Umsetzungsstand (Logging & Exceptionhandling)#Umsetzungsschritte|Umsetzungsschritt]] („Logging-Konzept schriftlich festhalten"). Hier ein **Vorschlag als Diskussionsgrundlage** — die Entscheidung ist deine, und mindestens zwei Zeilen sind streitbar:

| Ereignis                                                       | Wo                     | Level                   | Begründung                                                           |
| -------------------------------------------------------------- | ---------------------- | ----------------------- | -------------------------------------------------------------------- |
| Lauf gestartet (mit Parametern)                                | `main` / `app.run`     | `INFO`                  | Klammert jeden Lauf; ohne Startzeile weiß man nicht, ob er lief      |
| Konfiguration/DSN geladen (**ohne Passwort**)                  | `adapters/db`          | `DEBUG`                 | Interessant nur bei Verbindungsproblemen                             |
| N Buchungen / N Kapazitätszeilen geladen                       | `adapters/sources`     | `INFO`                  | Kernkennzahl — „waren überhaupt Daten da?"                           |
| Einzelne Zeile/Unit verarbeitet                                | `core/builder`         | `DEBUG`                 | Skaliert mit der Datenmenge → nie auf `INFO`                         |
| Datenqualitätsproblem (Summe passt nicht, negative Kapazität)  | `ingest`, `builder`    | `WARNING`               | Lauf gelingt, aber die Quelle ist verdächtig                         |
| Einheit übersprungen (Kapazität 0, Datum in der Vergangenheit) | `core/recommendations` | `INFO` (Summe)          | Fachlich **erwartet**, kein Missstand — s. u.                        |
| N Empfehlungen geschrieben                                     | `adapters/writers`     | `INFO`                  | Das Ergebnis des Laufs                                               |
| Lauf beendet, Dauer                                            | `main` / `app.run`     | `INFO`                  | Grundlage für Performance-Monitoring                                 |
| Erwarteter Fehler (Datei/Konfiguration fehlt)                  | `main`                 | `ERROR` + `exception()` | Aufgabe nicht erledigt → Exit-Code ≠ 0                               |
| Unerwarteter Fehler                                            | `main`                 | `CRITICAL` oder `ERROR` | Vertretbar beides; `CRITICAL` nur, wenn daran eine Alarmierung hängt |

Zwei Punkte zum Nachdenken, bevor du das übernimmst:

- **Start- und Endzeile auf `INFO`** sind bei einem Batch-Lauf richtig; bei einem Dienst, der pro Sekunde hundertmal etwas tut, wären sie `DEBUG`. Der Unterschied ist die **Frequenz**, nicht die Wichtigkeit.
- **Alles, was pro Datensatz passiert, gehört auf `DEBUG`** — sonst wächst das Log linear mit den Daten. Das ist die einzige Regel aus dieser Tabelle, die man nie brechen sollte.

## Kritischer Blick auf die bestehenden `WARNING`s

Vier `WARNING`-Aufrufe existieren schon. Drei davon halte ich für richtig eingestuft, einen nicht:

| Meldung | Modul | Urteil |
|---|---|---|
| `%d Buchungen mit net_revenue != gross_revenue - discount_amount.` | `ingest` | ✅ Datenqualität, Lauf geht weiter — Lehrbuch-`WARNING` |
| `%d Einheiten mit negativer Kapazität übersprungen.` | `builder` | ✅ Physikalisch unmögliche Daten → die Quelle ist kaputt |
| `%d Recommendations ohne passende capacity-Zeile übersprungen.` | `writers` | ✅ Verletzte referenzielle Erwartung, Ergebnis unvollständig |
| `%d Einheiten mit total_capacity == 0 übersprungen.` | `recommendations` | ⚠️ **Kandidat für `INFO`** |

Zur letzten Zeile: Kapazität 0 kann ein völlig normaler Zustand sein (Einheit ausgebucht, geschlossen, nicht im Verkauf). Ist das der Regelfall, erscheint bei jedem Lauf eine Warnung, auf die niemand reagiert — und genau so verlieren Warnungen ihre Bedeutung. Das ist eine **fachliche** Frage, keine technische: Ist „Kapazität 0" in eurem Datenmodell erwartbar oder ein Defekt? Wenn erwartbar → `INFO`. Wenn es auf ein Ingest-Problem hindeutet → `WARNING` bleibt richtig.

> [!info] Was das Projekt hier schon richtig macht
> Alle vier Meldungen loggen eine **Summe am Ende**, nicht eine Zeile pro Vorfall. Das ist genau das Muster, das Punkt 2 der Nachteile-Liste verhindert: Bei 50 000 auffälligen Buchungen entsteht **eine** Logzeile, nicht 50 000. Wer die Einzelfälle braucht, bekommt sie auf `DEBUG` — der Standardaufbau für Datenqualitätsprüfungen.

## Bezug zu den Kontrollfragen

- *„Erkläre den Vorteil verschiedener Logging-Level."* → [[#Der Vorteil verschiedener Level]]: Entkopplung von Aufzeichnung und Anzeige, ohne Code-Änderung; dazu Granularität pro Modul, mehrere Ziele mit eigener Schwelle, Alarmierbarkeit, Kostensteuerung.
- *„Was sind die Nachteile von niederschwelligem Logging?"* → [[#Die Nachteile von niederschwelligem Logging]]: Rauschen (der eigentliche Schaden), Volumen/Kosten, Laufzeit, Betriebsrisiko, Datenschutz — bei gleichzeitiger Warnung, dass das Gegenteil kein sicherer Standard ist.

# Logging-Frameworks

## Warum es sie überhaupt gibt

Die Kernantwort auf die erste [[1.4 Logging & Exceptionhandling - Leitfaden#Kontrollfragen|Kontrollfrage]] steht schon bei [[#Bezug zu den Kontrollfragen]] in Stichwort 3: Entkopplung von Erzeugung und Ziel, zentrale Konfiguration, Hierarchie, mehrere Ziele, Metadaten gratis, Robustheit. Hier die historische Ergänzung, die erklärt, warum es *Frameworks* wurden und nicht nur Bibliotheken:

Jede größere Anwendung baut sich früher oder später ein `log()` — und jede baut ein anderes. Sobald man zwei Bibliotheken kombiniert, hat man zwei Logging-Systeme mit zwei Konfigurationen und zwei Ausgabeformaten. Ein Framework löst also nicht in erster Linie ein *technisches* Problem (Text in eine Datei schreiben kann jeder), sondern ein **Standardisierungsproblem**: Alle Beteiligten müssen sich auf dieselbe Pipeline einigen, damit der Betrieb *eine* Stelle hat, an der er alles steuert.

Genau deshalb hat Python `logging` in der Standardbibliothek — und deshalb ist die Antwort auf „welches Framework soll ich nehmen?" in Python öfter „das eingebaute", als Neulinge erwarten.

## Die zwei größten — die Antwort auf Kontrollfrage 2

Die Frage ist sprachübergreifend gemeint. Die zwei bekanntesten und meistverbreiteten:

1. **Log4j** (genauer: **Apache Log4j 2**) — Java, das Ur-Framework der Zunft. Hat die Begriffe geprägt, die heute überall gelten: Logger, Appender (= unser Handler), Layout (= Formatter), Level-Hierarchie. Pythons `logging`-Modul ist **direkt daran angelehnt** — deshalb kommt einem die Architektur aus Stichwort 3 in Java sofort bekannt vor.
2. **Logback** — ebenfalls Java, vom selben Autor als Nachfolger geschrieben, meist zusammen mit **SLF4J** benutzt.

Für den Python-Kontext ist die ehrlichere Antwort:

1. **Die Standardbibliothek `logging`** — de facto der Standard, weil jede Fremdbibliothek dagegen loggt.
2. **`structlog`** bzw. **`loguru`** als die beiden verbreiteten Ergänzungen (dazu gleich).

> [!tip] Ein Begriff, der in Java-Umgebungen ständig fällt: **SLF4J**
> SLF4J ist selbst *kein* Logging-Framework, sondern eine **Fassade** — eine einheitliche API, hinter der austauschbar Log4j 2, Logback oder etwas anderes steckt. Der Sinn: Eine *Bibliothek* programmiert gegen die Fassade und schreibt niemandem vor, welches Framework die *Anwendung* benutzt. Das ist exakt dasselbe Prinzip wie „Bibliotheken konfigurieren nicht, Anwendungen konfigurieren" aus [[#Wer konfiguriert — und wer auf keinen Fall]] — in Python übernimmt `logging` beide Rollen (Fassade *und* Implementierung) gleichzeitig.

## Die Python-Landschaft

Stand der aktuellen Versionen auf PyPI (abgefragt am 2026-07-28):

| Bibliothek | Version | Rolle |
|---|---|---|
| `logging` (stdlib) | — | Der Standard. Jede Fremdbibliothek loggt dagegen. |
| `structlog` | **26.1.0** (06.06.2026) | Strukturiertes Logging; baut auf `logging` auf, ersetzt es nicht |
| `loguru` | **0.7.3** (06.12.2024) | „Logging ohne Konfiguration"; ein einziges globales Logger-Objekt |
| `python-json-logger` | **4.1.0** | Nur ein JSON-**Formatter** für die stdlib — die kleinste mögliche Lösung |
| `picologging` | 0.9.3 | Performance-orientierter Ersatz von Microsoft; bis heute nicht in 1.0 |

Die Versionsstände sagen mehr, als sie zunächst wirken: `structlog` steht bei Version 26 mit einem Release aus diesem Jahr, `loguru` seit über eineinhalb Jahren bei 0.7.3 und formal immer noch vor 1.0. Das ist kein Ausschlusskriterium — aber ein Punkt, den man bei einer Abhängigkeit für ein Produktivsystem anschaut.

## `structlog` — der interessante für Data Engineering

Die Grundidee: Eine Logmeldung ist kein Satz, sondern ein **Dictionary**.

```python
log = structlog.get_logger()
log.info("empfehlungen_geschrieben", anzahl=1500, ziel="csv", dauer_ms=812)
```

Ausgegeben wird daraus wahlweise farbige Konsole für Entwickler oder **JSON** für die Maschine:

```json
{"event": "empfehlungen_geschrieben", "anzahl": 1500, "ziel": "csv", "dauer_ms": 812,
 "level": "info", "timestamp": "2026-07-28T09:14:22Z"}
```

Der Unterschied zum bloßen `extra=` aus [[#`extra=` — Daten, die nicht im Satz stehen]] ist die konsequente Umkehrung: Nicht „Satz mit angehängten Feldern", sondern „**Ereignisname plus Felder**". Dazu kommen zwei Dinge, die man mit der stdlib selbst bauen müsste:

- **Kontext, der mitwandert** (`bind()`): Einmal `log = log.bind(run_id=..., quelle="prices.csv")`, und jede weitere Zeile trägt diese Felder automatisch — die Korrelations-ID aus dem [[Umsetzungsstand (Logging & Exceptionhandling)#Offene Punkte / Ausblick|Umsetzungsstand]] fällt damit als Nebenprodukt ab.
- **Prozessor-Ketten**: konfigurierbare Verarbeitungsschritte pro Record (Zeitstempel ergänzen, Felder umbenennen, **Passwörter zensieren**, am Ende JSON rendern).

Warum das für uns relevant ist: Ein JSON-Log ist eine **Tabelle**. Man kann es in eine Datenbank laden und mit SQL abfragen, statt mit `grep` und Regex zu arbeiten. Genau die Perspektive aus der [[1.4 Logging & Exceptionhandling - Leitfaden#Motivation|Motivation]] des Leitfadens — nur diesmal von der Seite dessen, der die Logs *erzeugt*.

Wichtig: `structlog` **ersetzt `logging` nicht**, sondern setzt darauf auf. Handler, Level und Hierarchie aus Stichwort 3 bleiben gültig — man tauscht nur die Art, wie die Meldung entsteht.

## `loguru` — bequem, aber mit einem Haken

Der Verkaufsargument ist die Nullkonfiguration:

```python
from loguru import logger
logger.info("Es läuft")                       # funktioniert sofort, farbig, mit Zeitstempel
logger.add("app.log", rotation="10 MB", retention="7 days", level="DEBUG")
```

Eine Zeile für das, was in der stdlib ein `dictConfig` mit `RotatingFileHandler` ist. Dazu ein `@logger.catch`-Dekorator, der Exceptions samt Traceback automatisch loggt, und f-String-artige Formatierung ohne die `%`-Gymnastik.

Der Haken folgt direkt aus Stichwort 3: `loguru` arbeitet mit **einem einzigen globalen Logger-Objekt** statt mit einer Hierarchie. Damit entfällt die Granularität pro Modul (`pricing.adapters.db` auf `DEBUG`, Rest auf `INFO`) — die man über Filter nachbauen kann, aber eben nachbauen muss. Und der Kern der Kritik: In einer *Bibliothek* hat `loguru` nichts zu suchen, weil es die Logging-Entscheidung der Anwendung aufzwingt. Für abgeschlossene Anwendungen und Skripte ist es eine legitime, sehr komfortable Wahl.

## Der eigentliche Trend heißt nicht „Framework", sondern „strukturiert"

Die Wahl zwischen den Bibliotheken ist weniger wichtig als die dahinterliegende Verschiebung: **Logs werden nicht mehr gelesen, sondern abgefragt.** In einem System mit zwanzig Diensten öffnet niemand mehr eine Logdatei; die Zeilen landen in einer Aggregationsplattform (ELK/OpenSearch, Grafana Loki, Splunk, CloudWatch), und dort sucht man mit Filtern über Felder.

Für den Code heißt das nur zweierlei — und beides haben wir längst:

1. **Template und Daten trennen** ([[#Parametrisierte Logs]]) — sonst gibt es keine Felder, nur Text.
2. **Konfiguration am Rand austauschbar halten** ([[#Wer konfiguriert — und wer auf keinen Fall]]) — dann ist der Wechsel von Text auf JSON eine Konfigurationsänderung, kein Umbau.

> [!warning] Ein Logging-Framework ist Angriffsfläche: Log4Shell
> Im Dezember 2021 wurde in Log4j 2 die Lücke **Log4Shell** (CVE-2021-44228) bekannt — eine der folgenreichsten Sicherheitslücken überhaupt. Ursache: Log4j interpretierte in Logmeldungen bestimmte Ausdrücke (`${jndi:ldap://...}`) und lud daraufhin Code aus dem Netz nach. Es genügte also, einen präparierten String irgendwo hinzuschicken, wo er **geloggt** wurde — etwa in einem Benutzernamen.
>
> Zwei Lehren, die über Java hinausgehen: Erstens sind Logging-Bibliotheken sicherheitsrelevante Abhängigkeiten und gehören gepatcht wie jede andere. Zweitens — und das ist der allgemeine Punkt — **darf ungeprüfte Fremdeingabe nie in einen Teil geraten, der interpretiert wird**. Das ist dieselbe Regel wie „keine Fremddaten in den Format-String" aus [[#Grund 4: Kein Format-String aus fremden Daten]], nur mit dramatischerem Ausgang.

## Was heißt das für unser Projekt?

Ehrliche Empfehlung: **Bei der Standardbibliothek bleiben.** Die Anwendung ist ein einzelner Batch-Lauf, `logging` deckt alles ab, was der Leitfaden verlangt, und jede zusätzliche Abhängigkeit will begründet sein. Der Lerneffekt liegt ohnehin im Verstehen der Pipeline, nicht im Installieren einer Bibliothek.

Zwei realistische Ausbaustufen, falls du mehr willst:

- **Klein:** `python-json-logger` als zweiter Formatter für den Datei-Handler — Konsole bleibt lesbar, Datei wird JSON. Etwa zehn Zeilen Konfiguration, kein Eingriff in den Code.
- **Groß:** `structlog` für den `bind()`-Kontext (Run-ID pro Lauf). Lohnt sich, wenn mehrere Läufe parallel in dieselbe Datei schreiben — bei uns aktuell nicht der Fall.

# Exceptionhandling best practices

## Was davon schon steht

Ein guter Teil der Prinzipien ist beim ersten Stichwort gefallen, weil er dort nötig war. Um Wiederholung zu vermeiden, hier nur die Verweise — nachlesen lohnt, das ist die halbe Antwort auf Kontrollfrage 5:

- Anti-Muster (`except: pass`, bare `except:`, `str(e)`, log-and-rethrow, zu breites Fangen) → [[#Die Anti-Muster]]
- Ursachen verketten (`raise ... from e`, `__cause__` vs. `__context__`) → [[#Exception-Chaining: die Vorgeschichte mitloggen]]
- Wo im Programm gefangen wird (Kern wirft, Adapter übersetzt, Rand entscheidet) → [[#Wo im Programm loggt man Exceptions?]]
- Traceback erhalten, Logeintrag ≠ Behandlung → [[#Das Werkzeug: `logger.exception()`]]

Dieser Abschnitt ergänzt das um die **python-spezifischen** Punkte, die dort noch keinen Platz hatten.

## EAFP statt LBYL — die Grundhaltung

Zwei Denkweisen, wie man mit möglichen Fehlern umgeht:

- **LBYL** — *Look Before You Leap*: erst prüfen, dann handeln.
- **EAFP** — *Easier to Ask Forgiveness than Permission*: einfach handeln, den Fehlerfall abfangen.

```python
# LBYL
if "DB_PRICING_PW" in os.environ:
    pw = os.environ["DB_PRICING_PW"]
else:
    ...

# EAFP — pythonisch
try:
    pw = os.environ["DB_PRICING_PW"]
except KeyError as e:
    raise KonfigurationsFehler("DB_PRICING_PW ist nicht gesetzt") from e
```

Python bevorzugt klar **EAFP**, aus drei Gründen:

1. **Keine Race Condition.** Zwischen `if os.path.exists(p)` und `open(p)` kann die Datei verschwinden — die Prüfung garantiert nichts, das `except` schon. Bei allem, was außerhalb des Prozesses liegt (Dateien, Netz, Datenbank), ist LBYL grundsätzlich unzuverlässig.
2. **Vollständigkeit.** Eine Vorab-Prüfung deckt die Fälle ab, an die man gedacht hat. `except` deckt den Fall ab, der eintritt.
3. **Geschwindigkeit im Normalfall.** Seit Python 3.11 kostet ein `try`-Block ohne Exception praktisch nichts („zero-cost exceptions"). Gemessen (300 000 Durchläufe):

   | Fall | LBYL | EAFP |
   |---|---|---|
   | Schlüssel **vorhanden** | 0,049 s | **0,014 s** (~3,5× schneller) |
   | Schlüssel **fehlt** | **0,014 s** | 0,091 s (~6,5× langsamer) |

   Das ergibt die Regel: **EAFP gewinnt, wenn der Fehlerfall die Ausnahme ist** — und genau das bedeutet das Wort. Ist der „Fehler" der Regelfall (jede zweite Zeile fehlt), ist eine Prüfung sowohl schneller als auch ehrlicher: Dann ist es kein Fehler, sondern eine Fallunterscheidung.

## Die vier Blöcke: `try` / `except` / `else` / `finally`

```python
try:
    f = open(pfad)                # nur das, was scheitern kann
except FileNotFoundError as e:
    raise QuelleFehltError(pfad) from e
else:
    daten = f.read()              # läuft NUR, wenn kein Fehler auftrat
finally:
    logger.debug("Ladeversuch beendet")   # läuft IMMER
```

**`else` ist der unterschätzte Block.** Sein Zweck: den `try`-Block **klein** halten. Alles, was im `try` steht, ist potenziell vom `except` betroffen — steht die Weiterverarbeitung mit drin, fängt man versehentlich Fehler, die gar nicht von `open()` kommen. Das ist der praktische Weg, das Prinzip „so eng wie möglich fangen" umzusetzen: nicht nur enge Exception-*Typen*, sondern auch enge `try`-*Blöcke*.

**`finally` läuft immer** — auch bei `return` und bei einer weitergereichten Exception. Aber:

> [!warning] `return` im `finally` verschluckt Exceptions — spurlos
> ```python
> def f():
>     try:
>         raise ValueError("wichtig!")
>     finally:
>         return "harmlos"
>
> f()   # → 'harmlos'; die ValueError ist weg, kein Traceback, nichts
> ```
> Nachgeprüft: Das Ergebnis ist `'harmlos'`. Ein `return` (oder `break`/`continue`) im `finally`-Block **überschreibt eine laufende Exception**. Das ist `except: pass` mit zusätzlicher Tarnung — der Grund, warum ruff das mit `B012` meldet, sobald man `B` aktiviert hat (was im Projekt der Fall ist).

**Für Aufräumarbeiten ist `finally` trotzdem selten die richtige Wahl** — dafür gibt es Context Manager:

```python
with open(pfad) as f:        # schließt garantiert, auch bei Exception
    daten = f.read()
```

Das ist derselbe Mechanismus, nur wiederverwendbar und ohne die Möglichkeit, das Aufräumen zu vergessen. Eigene Ressourcen (DB-Verbindung, Transaktion) kapselt man mit `@contextlib.contextmanager`. In `adapters/db.py` ist das der natürliche Ort dafür.

## `BaseException` vs. `Exception`

Der Grund, warum `except Exception:` und `except:` **nicht** dasselbe sind:

```
BaseException
├── KeyboardInterrupt      (Strg+C)
├── SystemExit             (sys.exit())
├── GeneratorExit
└── Exception              ← alles „Normale": ValueError, KeyError, OSError, …
```

`KeyboardInterrupt` und `SystemExit` hängen **neben** `Exception`, nicht darunter — bewusst, denn sie sind keine Fehler, sondern Abbruchwünsche. Wer `except:` schreibt, fängt sie mit und macht sein Programm unabbrechbar. Praktische Konsequenz: **Von `Exception` erben, niemals von `BaseException`** — und `except BaseException` kommt in normalem Anwendungscode nicht vor.

## Eigene Exceptions entwerfen

Die Faustregel: **Eine Basisklasse pro Paket, davon abgeleitet die konkreten Fälle.**

```python
class PricingError(Exception):
    """Basis für alle Fehler dieser Anwendung."""

class KonfigurationsFehler(PricingError): ...
class QuelleFehltError(PricingError): ...
class DatenqualitaetsFehler(PricingError): ...
```

Der Nutzen zeigt sich am Rand: `except PricingError` fängt in `main()` **alles Eigene** mit einer Zeile — und lässt alles Fremde (also Bugs) durch zum zweiten, breiten `except`. Genau die Zweiteilung aus [[#Wo im Programm loggt man Exceptions?]]. Aufrufer können trotzdem feiner unterscheiden, wenn sie wollen.

**Exceptions tragen Daten, nicht nur Text.** Der häufigste Anfängerfehler ist, alles in die Nachricht zu schreiben:

```python
# schwach — die Information steckt in einem String
raise QuelleFehltError(f"Datei {pfad} fehlt")

# besser — die Information ist zugreifbar
class QuelleFehltError(PricingError):
    def __init__(self, pfad: Path) -> None:
        super().__init__(f"Datenquelle nicht gefunden: {pfad}")
        self.pfad = pfad
```

Damit kann ein `except`-Block **entscheiden** statt nur zu loggen (`if e.pfad.suffix == ".csv": ...`), und ein Test kann `exc_info.value.pfad` prüfen, statt Textbausteine zu vergleichen — was aus [[1.3 Testing mit PyTest - Vertiefung|Kapitel 1.3]] als brüchig bekannt ist. Merksatz: **Die Nachricht ist für Menschen, die Attribute sind für Code.**

## `assert` ist keine Fehlerbehandlung

```python
def preis_setzen(p):
    assert p > 0, "Preis muss positiv sein"
    return p
```

Nachgeprüft: Mit `python -O` (Optimierungsmodus) verschwindet die Prüfung ersatzlos — `preis_setzen(-5)` liefert dann klaglos `-5`. `assert` ist ein **Entwickler-Werkzeug für Annahmen, die nie falsch sein dürfen**, und für Tests. Für Eingabeprüfungen gehört dorthin ein echtes `raise`:

```python
if p <= 0:
    raise ValueError(f"Preis muss positiv sein, war {p}")
```

## `contextlib.suppress` — die einzige saubere Form von „ignorieren"

Es gibt Fälle, in denen ein Fehler wirklich egal ist — dann sagt man das *explizit*:

```python
from contextlib import suppress

with suppress(FileNotFoundError):
    tempdatei.unlink()          # weg ist weg, egal ob sie schon fehlte
```

Der Unterschied zu `except FileNotFoundError: pass` ist nicht technisch, sondern kommunikativ: `suppress` ist eine **Absichtserklärung**. Beim `pass` weiß der nächste Leser nie, ob da jemand nachgedacht oder nur einen Fehler weggeklickt hat. Wichtig bleibt: nur mit **konkretem** Typ und nur um genau eine Anweisung.

## `ExceptionGroup` und `except*` (ab Python 3.11)

Klassisches `raise` kann immer nur *einen* Fehler transportieren. Bei Stapelverarbeitung ist das falsch — man will alle Probleme sehen, nicht nur das erste:

```python
try:
    raise ExceptionGroup("Ingest-Fehler", [
        ValueError("Zeile 3"), KeyError("spalte_x"), ValueError("Zeile 9"),
    ])
except* ValueError as eg:
    print([str(e) for e in eg.exceptions])   # ['Zeile 3', 'Zeile 9']
except* KeyError as eg:
    print([str(e) for e in eg.exceptions])   # ["'spalte_x'"]
```

`except*` fängt **alle passenden** Teilfehler aus der Gruppe, mehrere `except*`-Zweige können nacheinander greifen. Für unseren Ingest ist das die passende Form von „500 Zeilen geprüft, 12 fehlerhaft" — die Alternative wäre, Fehler in einer Liste zu sammeln und am Ende selbst auszuwerten, was ohne Traceback-Erhalt weniger hergibt. Für die aktuelle Ausbaustufe des Projekts ist es Überbau, aber gut zu kennen.

## Python hat keine geprüften Exceptions — also dokumentieren

In Java zwingt der Compiler den Aufrufer, deklarierte Exceptions zu behandeln (`throws`). Python kennt das nicht, und auch mypy `strict` prüft es nicht: **Welche Fehler eine Funktion wirft, steht nirgends im Typsystem.** Der einzige Ersatz ist Dokumentation — und die gehört bei öffentlichen Funktionen in den Docstring:

```python
def get_dsn() -> str:
    """Baut den DSN aus der Umgebung.

    Raises:
        KonfigurationsFehler: wenn DB_PRICING_PW nicht gesetzt ist.
    """
```

Das ist kein Formalismus: Der Aufrufer kann nur fangen, was er kennt.

## Partielles Scheitern: die eigentliche Entscheidung bei Datenverarbeitung

Der praktisch wichtigste Punkt für unsere Anwendung, weil er über den Code hinausgeht. Wenn von 10 000 Buchungen 12 kaputt sind — was ist richtig?

| Strategie | Wann angebracht |
|---|---|
| **Fail fast** — ganzer Lauf bricht ab | Wenn ein Teilergebnis schlimmer ist als kein Ergebnis (falsche Preise gehen live) |
| **Skip & count** — überspringen, am Ende Summe loggen | Wenn Einzelausfälle normal sind und das Gesamtergebnis trotzdem trägt |
| **Skip mit Schwelle** — abbrechen ab X % Ausfall | Der übliche Kompromiss bei Datenpipelines |
| **Dead-Letter** — Fehlerfälle beiseitelegen, Rest verarbeiten | Wenn die Fälle später nachbearbeitet werden sollen |

Das Projekt verfolgt heute implizit **Skip & count** (die vier `WARNING`s aus [[#Kritischer Blick auf die bestehenden `WARNING`s]]). Das ist eine legitime Wahl — sie war nur nie eine bewusste. Eine Schwelle („mehr als 5 % übersprungen → `ERROR` + Exit-Code ≠ 0") wäre der Ausbau, der aus einer stillschweigenden Praxis eine Entscheidung macht. Denn die Regel aus Stichwort 1 gilt hier genauso: **Auf das Loggen muss eine Entscheidung folgen.**

## Die Grundprinzipien — vollständige Antwort auf Kontrollfrage 5

*„Was sind die Grundprinzipien des Exceptionhandlings (v. a. in Python)?"* — die Summe aus beiden Abschnitten, geordnet:

1. **EAFP statt LBYL** — handeln und abfangen, nicht vorab prüfen; die python-typische Grundhaltung.
2. **So eng wie möglich fangen** — konkrete Typen, kleine `try`-Blöcke (`else` benutzen). Breit fangen genau einmal: am Rand.
3. **Nie stillschweigend schlucken** — kein `except: pass`, kein bare `except:`, kein `return` im `finally`. Absichtliches Ignorieren nur explizit über `contextlib.suppress`.
4. **Traceback erhalten** — `logger.exception()` statt `str(e)`.
5. **Ursachen verketten** — `raise Sprechend(...) from e`; technische Fehler an Schichtgrenzen in fachliche übersetzen.
6. **Log *oder* raise, nicht beides** — geloggt wird, wo entschieden wird.
7. **Eigene Exception-Hierarchie** mit einer Basisklasse pro Paket; von `Exception` erben, nie von `BaseException`.
8. **Exceptions tragen Daten** als Attribute, nicht nur Text in der Nachricht.
9. **`assert` ist keine Fehlerbehandlung** — es verschwindet mit `-O`.
10. **Ressourcen über Context Manager** freigeben (`with`), nicht per `finally`.
11. **Auf das Fangen folgt eine Entscheidung** — Fallback, Skip, Abbruch, Exit-Code ≠ 0.
12. **Geworfene Fehler dokumentieren** (`Raises:`), weil Python sie nicht deklariert.

## Konkret für die Übungsaufgabe

Daraus ergibt sich die Reihenfolge für den Code-Teil — bewusst klein anfangen:

1. `exceptions.py` mit `PricingError` + drei bis vier Unterklassen, Attribute statt Textbausteine.
2. Die bestehenden generischen `raise`-Stellen umstellen (3× `ValueError` in `domain.py`, 2× `FileNotFoundError` in `adapters/sources.py`).
3. `os.environ["DB_PRICING_PW"]` in `adapters/db.py` → `try/except KeyError` → `raise KonfigurationsFehler(...) from e`. Das ist das Lehrbuchbeispiel aus Stichwort 1, und es steht schon im Code.
4. Rand-Behandlung in `main.py` (zwei `except`-Zweige, `logger.exception`, Exit-Codes, `sys.exit(main())`).
5. Tests: `pytest.raises` + `__cause__`-Prüfung, `caplog` + `record.exc_info is not None`.

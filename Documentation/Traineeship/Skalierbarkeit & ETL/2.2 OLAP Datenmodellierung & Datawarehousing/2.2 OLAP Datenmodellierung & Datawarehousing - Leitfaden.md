# 2.2 OLAP Datenmodellierung & Datawarehousing

*Richtwert: 3 Wochen*

## Motivation

Data Engineers arbeiten häufig nicht an einzelnen Softwareprodukten, sondern an zentralen Knotenpunkten, in denen Daten für das gesamte Unternehmen sowie für zahlreiche Downstream-User gespeichert, aufbereitet und modelliert werden. Die primären Anwendungsfälle sind dabei meist Datenanalyse, Auditing und Governance.

Für diese Art von analysegetriebenen und oft datenintensiven Systemen kommen entsprechend optimierte Technologien zum Einsatz: Data Warehouses. Für Data Engineers ist der sichere und korrekte Umgang mit Data Warehouses daher essenziell, und Best Practices der Datenmodellierung in solchen Umgebungen gehören zum absoluten Grundwissen.

### 1. Dimensionale Datenmodellierung

Du bist Data Engineer bei einem Unternehmen, welches beschließt künftig mit einem Datawarehouse arbeiten zu wollen, wo die produktiven Daten nach Kimball modelliert gespeichert werden sollen. Die folgenden Tabellen existieren in der produktiven Datenbank:

#### 1. `Customer`

| customer_id | first_name | last_name | email             | city    |
| ----------- | ---------- | --------- | ----------------- | ------- |
| 1           | Alice      | Smith     | alice@example.com | Berlin  |
| 2           | Bob        | Johnson   | bob@example.com   | Munich  |
| 3           | Clara      | Lee       | clara@example.com | Hamburg |

#### 2. `Product`

| product_id | product_name   | category    | price  |
| ---------- | -------------- | ----------- | ------ |
| 101        | Wireless Mouse | Electronics | 25.00  |
| 102        | Office Chair   | Furniture   | 150.00 |
| 103        | Standing Desk  | Furniture   | 300.00 |

#### 3. `Order`

| order_id | customer_id | order_date |
| -------- | ----------- | ---------- |
| 1001     | 1           | 2025-04-01 |
| 1002     | 2           | 2025-04-01 |
| 1003     | 1           | 2025-04-02 |

#### 4. `OrderItem`

| order_item_id | order_id | product_id | quantity |
| ------------- | -------- | ---------- | -------- |
| 1             | 1001     | 101        | 2        |
| 2             | 1001     | 102        | 1        |
| 3             | 1002     | 103        | 1        |
| 4             | 1003     | 101        | 1        |

#### 5. `Payment`

| payment_id | order_id | payment_date | amount | payment_method |
| ---------- | -------- | ------------ | ------ | -------------- |
| 501        | 1001     | 2025-04-01   | 100.00 | Credit Card    |
| 502        | 1002     | 2025-04-01   | 300.00 | PayPal         |
| 503        | 1003     | 2025-04-02   | 25.00  | Credit Card    |

#### Entity-Relations

- **Customer** (1) ↔ (M) **Order**
- **Order** (1) ↔ (M) **OrderItem**
- **Product** (1) ↔ (M) **OrderItem**
- **Order** (1) ↔ (1) **Payment**

#### Aufgabe

Modelliere daraus ein Star und ein Snowflake Schema. Ergebnis sollte also ein Diagramm pro Schema sein (Die Art des Diagramms muss keiner best practice folgen, nur verständlich sein). Das Diagramm sollte alle Tabellennamen mit Spalten und ca 3 Beispiel-Entries haben und klar machen welche Tabellen und Spalten Dimensionen/Fakten/FKs sind.

generieren:

```sql
-- 1. Drop tables if they exist (for reruns)
DROP TABLE IF EXISTS Payment;
DROP TABLE IF EXISTS OrderItem;
DROP TABLE IF EXISTS "Order";
DROP TABLE IF EXISTS Product;
DROP TABLE IF EXISTS Customer;

-- 2. Create tables
CREATE TABLE Customer (
    customer_id SERIAL PRIMARY KEY,
    first_name  VARCHAR(50),
    last_name   VARCHAR(50),
    email       VARCHAR(100),
    city        VARCHAR(50)
);

CREATE TABLE Product (
    product_id   SERIAL PRIMARY KEY,
    product_name VARCHAR(100),
    category     VARCHAR(50),
    price        DECIMAL(10,2)
);

CREATE TABLE "Order" (
    order_id    SERIAL PRIMARY KEY,
    customer_id INT REFERENCES Customer(customer_id),
    order_date  DATE
);

CREATE TABLE OrderItem (
    order_item_id SERIAL PRIMARY KEY,
    order_id      INT REFERENCES "Order"(order_id),
    product_id    INT REFERENCES Product(product_id),
    quantity      INT
);

CREATE TABLE Payment (
    payment_id     SERIAL PRIMARY KEY,
    order_id       INT REFERENCES "Order"(order_id),
    payment_date   DATE,
    amount         DECIMAL(10,2),
    payment_method VARCHAR(50)
);

-- 3. Insert data
-- Insert Customers
INSERT INTO Customer (first_name, last_name, email, city)
SELECT
    'FirstName' || i,
    'LastName' || i,
    'user' || i || '@example.com',
    CASE (i % 5)
        WHEN 0 THEN 'Berlin'
        WHEN 1 THEN 'Munich'
        WHEN 2 THEN 'Hamburg'
        WHEN 3 THEN 'Cologne'
        ELSE 'Frankfurt'
    END
FROM generate_series(1, 100) AS s(i);

-- Insert Products
INSERT INTO Product (product_name, category, price)
SELECT
    CASE (i % 5)
        WHEN 0 THEN 'Wireless Mouse'
        WHEN 1 THEN 'Mechanical Keyboard'
        WHEN 2 THEN 'USB-C Cable'
        WHEN 3 THEN 'Laptop Stand'
        ELSE 'Bluetooth Speaker'
    END || ' ' || i,
    CASE (i % 3)
        WHEN 0 THEN 'Electronics'
        WHEN 1 THEN 'Accessories'
        ELSE 'Furniture'
    END,
    (10 + random() * 290)::NUMERIC(10,2)  -- random price between 10 and 300
FROM generate_series(1, 50) AS s(i);

-- Insert Orders
INSERT INTO "Order" (customer_id, order_date)
SELECT
    (random() * 99 + 1)::INT,                  -- random customer_id between 1 and 100
    '2025-04-01'::DATE + (random() * 30)::INT  -- random day in April 2025
FROM generate_series(1, 500) AS s(i);

-- Insert OrderItems
INSERT INTO OrderItem (order_id, product_id, quantity)
SELECT
    (random() * 499 + 1)::INT,  -- random order_id between 1 and 500
    (random() * 49 + 1)::INT,   -- random product_id between 1 and 50
    (random() * 4 + 1)::INT     -- quantity between 1 and 5
FROM generate_series(1, 1200) AS s(i);

-- Insert Payments
INSERT INTO Payment (order_id, payment_date, amount, payment_method)
SELECT
    o.order_id,
    o.order_date + (random() * 2)::INT,  -- paid 0-2 days after order
    (SELECT SUM(p.price * oi.quantity)
       FROM OrderItem oi
       JOIN Product p ON oi.product_id = p.product_id
      WHERE oi.order_id = o.order_id),
    CASE (floor(random() * 3))
        WHEN 0 THEN 'Credit Card'
        WHEN 1 THEN 'PayPal'
        ELSE 'Bank Transfer'
    END
FROM "Order" o
WHERE o.order_id <= 500;  -- one payment per order
```

Schreibe jetzt 2 SQL-Skripts. Das erste enthält die DDL um das Star Schema zu erstellen. Das zweite ist die Pipeline um die Daten aus dem Ursprungsformat in das Starschema zu importieren. Die Pipeline, kann an dieser Stelle noch vernachlässigen, dass es deletes gibt. Es gibt also nur die Option für Upserts.

> [!important] Bevor du weitermachst, besprich das Ergebnis mit deinem Coach.

Im Anschluss:

Erweitert dann das Schema um alle relevanten SCDs nach Typ 2 zu modellieren. Passe anschließend deine SQL-Pipeline entsprechend an.

#### Tipps

1. Eine Frage ist, wie wir simulieren, dass die unterschiedlichen daily snapshots ein unterschiedliches CURRENT_DATE haben (mit dem wir dann in der SCD Tabelle start_date und end_date bestimmen). Du kannst das lösen wie du willst (z.B. eine Variable todays_date = '01.01.2025' erstellen und für jedes mal bevor ihr das Skript für den nächsten Snapshot ausführt manuell 1 hochsetzen). Mein Vorschlag wäre aber, dass du die daily snapshots um eine Spalte "todays_date" erweiterst, die für jeden Eintrag der Snapshot Tabelle den gleichen Wert hat. Du gibst dann entsprechend jeder Snapshot Tabelle einen anderen Wert für "todays_date". Deine Pipeline kann dann einfach die Spalte auslesen um zu bestimmen auf welches Datum sich die Daten beziehen.
2. Jetzt ist es möglich, dass Zeilen auch gelöscht werden. Wenn eine Zeile also plötzlich in einem Daily snapshot nichtmehr vorhanden ist, wurde sie gelöscht. Unsere Pipeline muss also dazu in der Lage sein, Upserts und Deletes entsprechend zu handeln.
